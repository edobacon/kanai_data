> **ID estable:** `HU-00-06` · **Estado:** `Ready` · **Orden recomendado:** `8` · **Puntos publicados:** `3`

## Objetivo
Resultado: Prisma 7 queda configurado en `server/`, las migraciones se aplican con el rol
migrador desde una base vacía, existe un runner de seeds nombrados idempotentes y el reinicio
local está protegido. Consumidor: HU-00-07, HU-00-09 (job `integration`), HU-00-17 y las épicas
con datos de servidor.

## Alcance
**Incluye**
- `server/prisma/schema.prisma`, `server/prisma.config.ts` y `server/prisma/migrations/`
  (tecnologia/21 §6), con Prisma major 7 fijado en el lockfile.
- `MIGRATION_DATABASE_URL` con el rol migrador y `DATABASE_URL` con el rol de aplicación, validadas
  con `zod`.
- Primera migración versionada que deja el schema de aplicación y los privilegios por defecto: lo
  que crea el migrador otorga DML a `taomangalam_app`.
- Pool de Prisma limitado a 8 conexiones (DEC-200) y sonda real de `GET /health/ready`.
- Comandos `pnpm db:migrate:dev`, `db:migrate:deploy`, `db:seed --scenario <id>`,
  `db:studio:local`, `db:psql:local` y `db:reset:local`.
- Runner de seeds con registro de escenarios por id estable, reloj controlado e idempotencia, y un
  escenario de verificación del propio mecanismo. Los escenarios de tecnologia/18 §6 se agregan en
  las épicas que crean sus entidades.
- `db:reset:local` verifica host local, base `taomangalam_dev` o `taomangalam_test` y
  `APP_ENV=development` antes de actuar.
- `prisma format`, `prisma validate` y `prisma generate` integrados a `pnpm generate` y al gate.

**No incluye**
- Tablas de dominio: épicas funcionales (EP-03a en adelante).
- Scripts remotos de túnel y Prisma Studio remoto: HU-00-14.
- `db push` fuera de desarrollo desechable: prohibido (tecnologia/17 §5).

## Criterios de aceptación
- [ ] Dada una base vacía, cuando se ejecuta `pnpm db:migrate:deploy` con el rol migrador,
  entonces se aplican todas las migraciones y una segunda ejecución informa que no hay pendientes.
- [ ] Dado `DATABASE_URL` del rol de aplicación, cuando se intenta aplicar migraciones con él,
  entonces falla por permisos.
- [ ] Dada una tabla creada por migración, cuando el rol de aplicación ejecuta `SELECT`, `INSERT`,
  `UPDATE` y `DELETE`, entonces las cuatro operaciones funcionan.
- [ ] Dado un escenario de seed, cuando se ejecuta dos veces, entonces el estado final es idéntico
  (mismos conteos e ids).
- [ ] Dado `--scenario` con un id inexistente, cuando se ejecuta, entonces termina con código
  distinto de 0 y lista los escenarios válidos.
- [ ] Dado `db:reset:local` con host no local, otra base o `APP_ENV` distinto de `development`,
  cuando se ejecuta, entonces se niega sin tocar la base.
- [ ] Dada la base disponible, cuando se llama a `GET /health/ready`, entonces responde 200 con el
  chequeo de base en `ok`.

## Requisitos transversales
- Permisos: no aplica (roles de base, no capacidades de producto).
- Offline/sync: no aplica.
- Seguridad/privacidad: el backend nunca recibe el rol migrador en ejecución normal; los seeds usan
  datos ficticios sin PII real (tecnologia/18 §6).
- Accesibilidad/responsive: no aplica.
- Observabilidad: la migración y el seed registran inicio, fin y resultado sin credenciales.
- Compatibilidad/migración: migraciones versionadas y aplicables desde cero; los cambios
  destructivos futuros siguen expand/contract.
