## Objetivo
Resultado: cada PR que cambia la app publica un APK `development` instalable, compila para iOS
Simulator cuando el cambio lo justifica y `pnpm qa:bundle` reúne la evidencia de revisión.
Consumidor: revisores y QA humana de cada PR (DEC-192) y HU-00-15.

## Alcance
**Incluye**
- En `build-smoke`, APK debug del sabor `development` subido como artifact con SHA corto y sabor en
  el nombre.
- Build iOS Simulator en runner macOS solo cuando el PR cambia `app/ios/**`, `app/pubspec.yaml` o
  `app/pubspec.lock`, y siempre en `nightly.yml`; cuando se omite, el summary indica el motivo.
- `pnpm qa:bundle`, local y en CI: APK, reporte de pruebas, cobertura, catálogo Widgetbook cuando
  HU-00-12 esté integrada y un manifiesto con SHA, sabor y fecha.
- Summary del PR con enlaces de descarga e instrucciones de instalación.
- Retención de APK, build de Simulator, capturas y `qa:bundle` de 30 días en PR; los artifacts de
  release se retienen 90 días cuando EP-17 los produzca (DEC-230).

**No incluye**
- Builds firmados, TestFlight y Play Internal Testing: EP-17.
- Capturas de vistas en teléfono y tablet: llegan cuando existan vistas (EP-01 en adelante).
- Lanes de Fastlane: HU-00-15.

## Criterios de aceptación
- [ ] Dado un PR que cambia `app/`, cuando termina `build-smoke`, entonces hay un artifact con el
  APK `development` que se instala en AVD API 24 y API 36 y arranca con el nombre del sabor.
- [ ] Dado un PR que solo cambia `server/`, cuando corre el workflow, entonces no se genera APK y
  el summary lo indica.
- [ ] Dado un PR que cambia `app/ios/**`, cuando corre el workflow, entonces hay un artifact con el
  build de Simulator que se instala con `xcrun simctl install`.
- [ ] Dado un PR que solo cambia Dart en `app/lib/`, cuando corre el workflow, entonces el build iOS
  se omite y el summary explica el motivo.
- [ ] Dado `pnpm qa:bundle`, cuando termina, entonces el paquete contiene el APK, el reporte de
  pruebas, la cobertura y un manifiesto cuyo SHA coincide con `HEAD`.
- [ ] Dado un build iOS que falla, cuando termina el job, entonces `quality-gate` queda rojo.
- [ ] Dado el workflow de PR, cuando se inspeccionan los pasos que suben el APK, el build de
  Simulator y el `qa:bundle`, entonces declaran `retention-days: 30`.

## Adendas al request

### Adenda 1 — 2026-09-30 — dev

Cambio de alcance por el flujo por épica (DEC-239). Los jobs pesados (incluido `build-smoke`) corren **solo** en PRs hacia `main` y quedan `skipped` en PRs `feat/* -> epic/*` (DEC-239 §3; `ci-pr.yml`). Por lo tanto, "APK por cada PR" tal como estaba redactado no se cumple en la jornada diaria: el APK no se generaría en los PRs de ticket, solo al integrar la épica.

Se alinea el ticket:

- El APK `development` y el build de iOS Simulator se publican en el **PR de cierre `epic/<EP-xx> -> main`** (y en `nightly.yml`), no en cada PR de ticket hacia la épica.
- El objetivo y los criterios que decían "cada PR" pasan a "el PR que apunta a `main`".
- `pnpm qa:bundle` conserva su parte local; en CI corre donde corre el job de build (PRs a `main`).
- La instalación del APK en AVD API 24 y API 36 queda acotada al cierre de la épica (no por ticket).
- Dependencia: el "siempre en `nightly.yml`" requiere `nightly.yml` (HU-00-10 / TAO-166), que aún no existe; el orden relativo TAO-166 / TAO-164 queda a definir antes de ejecutar.

**Motivo**: DEC-239 reserva los jobs pesados para el cierre de la épica; mantener "APK por cada PR" obligaría a pagar el build en cada ticket, que es exactamente lo que la decisión evita. Se elige A (alinear a DEC-239) frente a B (job liviano de artifact por PR) y C (a demanda/nightly).
