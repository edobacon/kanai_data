### Fuente conservada: HU-02-02

Referencia: `docs/backlog/EP-02_contenido_empaquetado_y_assets.md:252`. El texto y sus criterios siguen siendo obligatorios en la fase indicada; la inclusión como referencia no implica entrega.

#### Objetivo

Resultado: un manifiesto único con esquema que dice, para cada asset productivo, en qué estado está,
de dónde viene, dónde se usa, qué medidas tiene, para qué tema y plataforma sirve y si se empaqueta
o se descarga, y CI que falla ante cualquier incoherencia. Consumidores: HU-01-02 (resolvedor),
HU-02-03 (exportación), HU-02-07, HU-02-08 y las épicas con vistas.


#### Criterios de aceptación

- [ ] Dado el manifiesto, cuando corre el validador, entonces cada entrada cumple el JSON Schema y
  los `id` son únicos.
- [ ] Dada una entrada con estado fuera de los cinco admitidos, cuando corre CI, entonces falla
  nombrando el `id` y el valor.
- [ ] Dada una entrada cuyo maestro no existe, o cuyas medidas declaradas no coinciden con el
  archivo real, cuando corre CI, entonces falla nombrando el `id`.
- [ ] Dado un PNG bajo `app/assets/` que no está en el manifiesto ni en la lista de no productivos,
  cuando corre CI, entonces falla nombrando la ruta.
- [ ] Dada una entrada `aprobado` sin la aprobación registrada de Diseño o de Contenido, cuando corre
  el validador, entonces falla nombrando el `id` y la aprobación que falta.
- [ ] Dada una entrada `aprobado` cuyo maestro no tiene derivados registrados, cuando corre el
  validador, entonces falla indicando que su estado debe ser `por-optimizar` (DEC-230).
- [ ] Dada una entrada `faltante`, cuando corre el validador, entonces se acepta sin archivo pero
  exige destino y medidas objetivo.
- [ ] Dada una entrada con variante de tema `dark` no nula, cuando corre el validador en V1,
  entonces falla (DEC-196).
- [ ] Dada la migración, cuando se revisa el manifiesto, entonces las 64 entradas actuales conservan
  su `id` y su `alt`, y la permanencia figura como `provisional` (pendiente de aprobación estética
  según `content/imagenes/09`).
- [ ] Dados los fondos de 940/941 × 1672, cuando se clasifican, entonces no figuran como `aprobado`
  para uso final, porque `content/imagenes/12` los declara solo aptos para maqueta.


#### Casos de prueba

- [ ] QA-02-02-01 · Dado el manifiesto migrado, cuando corre el validador, entonces termina con 0
  errores y 0 PNG sin registrar.
- [ ] QA-02-02-02 · Dada una entrada con estado `listo`, cuando corre CI, entonces falla con el `id`
  y el valor inválido.
- [ ] QA-02-02-03 · Dado un PNG nuevo copiado a `app/assets/animales-ashura/` sin entrada, cuando

- [ ] QA-02-02-04 · Dado un maestro aprobado por Diseño y Contenido sin derivados (borde), cuando
  se clasifica, entonces figura como `por-optimizar` y el validador lo acepta.

### Fuente conservada: HU-02-03

Referencia: `docs/backlog/EP-02_contenido_empaquetado_y_assets.md:379`. El texto y sus criterios siguen siendo obligatorios en la fase indicada; la inclusión como referencia no implica entrega.

#### Objetivo

Resultado: un pipeline reproducible que genera, desde los maestros PNG del inventario, los derivados
WebP sRGB en los tamaños de `content/imagenes/12`, con nombre numerado y sin tocar los maestros.
Consumidores: HU-01-02 (resolvedor), HU-02-07, HU-02-09, HU-02-12 y el `pubspec.yaml` de la app.


#### Criterios de aceptación

- [ ] Dado un maestro cuadrado de 1254 px con un uso de 320 unidades lógicas, cuando corre el
  pipeline, entonces genera WebP de 320 (1x), 640 (`2.0x/`) y 960 (`3.0x/`) px de lado, con perfil
  sRGB.
- [ ] Dada una lámina de 1024 × 1536 con un uso de 256 unidades lógicas de ancho, cuando corre el
  pipeline, entonces genera 256 × 384, 512 × 768 y 768 × 1152 sin deformar la proporción 2:3.
- [ ] Dado un derivado que supera el peso máximo configurado para su familia, cuando corre el
  pipeline, entonces falla nombrando el `id`, la variante y el peso.
- [ ] Dado un maestro más pequeño que la variante 3x de un uso, cuando corre el pipeline, entonces no
  amplía y falla nombrando el `id` y el tamaño pedido.
- [ ] Dado el SHA-256 de todos los maestros antes y después de correr el pipeline, cuando se
  comparan, entonces son idénticos.
- [ ] Dado el pipeline ejecutado dos veces sin cambios, cuando corre `--check`, entonces no reporta
  diferencias (salida determinista).
- [ ] Dado un maestro cambiado sin regenerar sus derivados, cuando corre `--check` en CI, entonces
  falla nombrando el `id`.
- [ ] Dado el arcano 8, cuando se exporta, entonces su derivado se llama con el número delante
  (`arcano-08-la-fuerza`) y aparece así en el manifiesto.
- [ ] Dado un `pubspec.yaml` que declara `app/assets/` completo o un PNG maestro, cuando corre CI,
  entonces falla.
- [ ] Dado un maestro con transparencia, cuando se exporta, entonces el WebP conserva el canal alfa
  y no se aplana sobre gris ni blanco (doc 43 §9, DEC-235).


#### Casos de prueba

- [ ] QA-02-03-01 · Dado el maestro `minerales/cornalina.png` con un uso de 320 unidades lógicas,
  cuando corre el pipeline, entonces aparecen `cornalina.webp`, `2.0x/cornalina.webp` y
  `3.0x/cornalina.webp` con perfil sRGB y medidas 320, 640 y 960 registradas en el manifiesto.
- [ ] QA-02-03-02 · Dado un maestro de prueba de 800 × 800 con un uso de 418 unidades lógicas
  (3x = 1254), cuando corre el pipeline, entonces falla sin generar un archivo ampliado.
- [ ] QA-02-03-03 · Dada una hoja de contacto de los derivados de una familia, cuando la revisa
  Diseño, entonces no hay deformaciones, bandas ni cambios de color respecto del maestro.
