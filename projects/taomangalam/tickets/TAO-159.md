> **ID estable:** `HU-00-07` · **Estado:** `Ready` · **Orden recomendado:** `11` · **Puntos publicados:** `3` · **Referencia externa:** GH-12

## Objetivo
Resultado: una cola durable `pg-boss` opera en su schema `pgboss` con rol propio, con consumidores dentro del proceso del backend, un entrypoint `worker` separable, un trabajo de ejemplo idempotente con reintentos y estado observable, y un guard de presupuesto de conexiones. Consumidor: HU-00-14 y las épicas que usan la cola para correo, purgas y exportaciones (EP-03b y siguientes, doc 47).

## Alcance
**Incluye**
- `PGBOSS_DATABASE_URL` con el rol `taomangalam_queue`, validada con `zod`; `pg-boss` instala y migra su propio schema con ese rol (DEC-200).
- Pool de `pg-boss` limitado a 5 conexiones.
- El backend inicia los consumidores después de validar la configuración; el entrypoint `worker` (mismo artefacto, comando distinto) arranca solo consumidores, sin HTTP (DEC-195).
- Trabajo de ejemplo sin efecto de negocio en `server/src/jobs/`, con handler idempotente por clave y reintentos con backoff y límite, sin reintentos infinitos (tecnologia/17 §11).
- Logs con `jobId`, `queue` y `attempt`; el fallo definitivo se registra como `error`.
- Guard de arranque: (8 de Prisma + 5 de `pg-boss` + 5 de reserva) por réplica declarada debe ser menor o igual al 70 % de `max_connections`, leído al arrancar; si se excede, el arranque falla.
- Cierre ordenado de `pg-boss` ante SIGTERM, sin perder trabajos en curso.
- Sección en `docs/development/local-services.md` sobre cómo inspeccionar el estado de la cola.

**No incluye**
- Trabajos reales (correo, purgas, exportaciones): épicas consumidoras.
- Servicio worker separado en Railway: futuro condicionado por métricas (DEC-195).
- Redis o BullMQ: excluidos de V1.

## Criterios de aceptación
- [ ] Dada una base recién migrada, cuando arranca el backend, entonces existe el schema `pgboss` creado por `taomangalam_queue` y el schema de aplicación no cambia.
- [ ] Dado un trabajo de ejemplo encolado, cuando se procesa, entonces queda completado y el log incluye `jobId`, `queue` y `attempt`.
- [ ] Dado un handler que falla en los dos primeros intentos, cuando se procesa, entonces se reintenta con backoff y se completa en el tercero.
- [ ] Dado un handler que falla siempre, cuando se agota el límite de intentos, entonces el trabajo queda fallido, no se reintenta más y se registra un log `error`.
- [ ] Dado el mismo trabajo encolado dos veces con la misma clave, cuando se procesan, entonces se produce un solo efecto observable.
- [ ] Dado el entrypoint `worker`, cuando se ejecuta, entonces procesa trabajos y no abre puerto HTTP.
- [ ] Dado PostgreSQL con `max_connections=20` y una réplica declarada (18 conexiones frente a un tope de 14), cuando arranca el backend, entonces falla con un mensaje que cita el presupuesto.
- [ ] Dado el rol `taomangalam_queue`, cuando intenta leer una tabla del schema de aplicación, entonces recibe `permission denied`.

## Adendas al request

### Adenda 1 - 2026-09-28 - dev

Precisión de alcance sobre REQ-01 (schema `pgboss`): el schema NO lo crea pg-boss al arrancar; lo provee la infraestructura con el rol `taomangalam_queue` como propietario (`infra/postgres/init/001_roles.sql` en local; la provisión equivalente al habilitar cada entorno queda fuera del alcance de HU-00-07). El arranque usa `createSchema: false`, VERIFICA que el schema exista y falla con un mensaje accionable si falta; pg-boss instala y migra sus TABLAS dentro del schema existente, dejando el schema de aplicación sin cambios. Motivo: dar al rol de cola privilegio CREATE sobre la base para que la librería cree el schema ampliaría el rol más allá de DEC-200. En consecuencia, el criterio «base recién migrada → existe el schema `pgboss`» se interpreta como «base local inicializada con el schema provisto por `001_roles.sql`».

**Motivo**: El gate integral observó que el código contradice el texto literal de REQ-01 (la creación del schema se delega en la infraestructura, no en el arranque).
