## Objetivo
Resultado: la API se despliega en Railway desde `server/` con `railway.toml`, y staging se
despliega por workflow manual desde un SHA de `main` con migración previa y smoke de salud.
Consumidor: rondas de QA humana en staging, EP-17 (producción) y la operación.

## Alcance
**Incluye**
- `server/Dockerfile` multietapa reproducible con dependencias bloqueadas, sin leer nada fuera de
  `server/` (DEC-205).
- `server/railway.toml`: build con Dockerfile, pre-deploy `prisma migrate deploy` con
  `MIGRATION_DATABASE_URL`, inicio en `0.0.0.0:$PORT`, healthcheck `/health/ready` con timeout
  acotado, restart `On Failure` y una réplica (tecnologia/21 §4).
- Servicio configurado con Root Directory `/server`, Watch Paths `/server/**` y Config File Path
  `/server/railway.toml`.
- Despliegue automático desde GitHub apagado en el servicio de staging: staging se despliega solo
  por el workflow manual (DEC-199, DEC-230).
- Ambiente `staging` con servicios `server` y `postgres` con volumen; roles creados con el script
  de HU-00-05 usando el usuario administrador solo para bootstrap; variables por referencia privada,
  sin `DATABASE_PUBLIC_URL`.
- Workflow manual de staging: recibe un SHA, verifica que pertenece a `main` y que pasó
  `main.yml`, hace checkout y ejecuta
  `railway up ./server --path-as-root --ci --environment staging --service server` con el token de
  proyecto de staging guardado en el GitHub Environment `staging`; luego ejecuta el smoke de salud y
  registra SHA, versión y digest en el summary (DEC-199).
- Perfil de paridad de Compose que ejecuta el backend en contenedor con el mismo Dockerfile.
- `pnpm railway:db:tunnel --env staging` y `pnpm db:studio:remote --env staging`, que rechazan
  producción salvo flag explícito y nunca imprimen la contraseña.
- Sección de staging (despliegue y rollback) en `docs/development/release-runbook.md`.

**No incluye**
- Producción, aprobación de environment y `release.yml`: EP-17.
- Backups, PITR y dump lógico externo: EP-17.
- Sentry y alertas: EP-15. Servicio worker separado: futuro (DEC-195).

## Adendas al request

### Adenda 1 - 2026-09-29 - dev

Cambio de alcance por plataforma: Railway deprecó Config as Code (railway.json/railway.toml) y exige Infrastructure as Code (.railway/railway.ts). En consecuencia:
- REQ-02 deja de basarse en `server/railway.toml`: la config del deploy (builder Dockerfile, dockerfilePath, preDeploy `prisma migrate deploy`, startCommand, healthcheck /health/ready, restart ON_FAILURE, numReplicas=1) debe vivir en `.railway/railway.ts` (IaC), aplicada con `railway config plan/apply`. Se elimina (o deja de depender de) `server/railway.toml`.
- REQ-04 se ajusta a la realidad del flujo `railway up ./server --path-as-root`: el servicio `server` NO lleva `rootDirectory=/server` (el upload ya tiene server/ como raíz) ni `watchPatterns=/server/**` (rompe el build por skip); auto-deploy de GitHub off; variables por referencia privada; Config File Path ya no aplica (deprecado).
- El aprovisionamiento real de Railway quedó hecho y verificado (staging con server+postgres, roles, variables, dominio y token en el GitHub Environment staging). El proyecto/ambiente, el token y la URL de staging existen y el smoke pasa contra la plataforma.

**Motivo**: Railway deprecó Config as Code; el `railway.toml` del ticket no gobierna el deploy en la plataforma actual. El dev decidió adaptar la implementación a IaC (.railway/railway.ts) en vez de registrar la desviación.

### Adenda 2 - 2026-09-29 - dev

Modelo de deploy elegido (B: source + deploy por SHA) tras verificar que en la plataforma `rootDirectory=server` (necesario para builds desde la fuente GitHub) es incompatible con `railway up ./server --path-as-root`:

- REQ-04: el servicio `server` usa la fuente GitHub `edobacon/taomangalam` (branch main) con `rootDirectory = server` y `dockerfilePath = Dockerfile`; auto-deploy de GitHub off; variables por referencia privada sin DATABASE_PUBLIC_URL. El deploy NO usa `railway up --path-as-root`.
- REQ-05: el workflow manual de staging, tras validar SHA de main + main.yml verde y hacer checkout, despliega ESE SHA desde la fuente con `serviceInstanceDeploy(serviceId, environmentId, commitSha)` (API GraphQL de Railway, `https://backboard.railway.com/graphql/v2`, con el token del GitHub Environment staging), luego corre el smoke de /health/live y /health/ready y registra SHA, version y digest en el summary. Se reemplaza `railway up ./server --path-as-root --ci`.
- REQ-02: el IaC `.railway/railway.ts` declara ese `rootDirectory`/`dockerfilePath` y los ajustes de deploy del servicio `server`.
- Dependencia para la verificacion end-to-end: mergear la rama a `main` y que exista `main.yml` (HU-00-10); sin eso la guarda `ci-green` del workflow no puede pasar. Queda como pendiente trazado si no se resuelve en este ticket.

**Motivo**: Elegido Modelo B: la plataforma no permite coexistir `railway up ./server --path-as-root` con la fuente GitHub (rootDirectory server) en el mismo servicio. El dev optó por alinear el servicio a la fuente GitHub y desplegar por SHA explícito, fiel a DEC-199/205.
