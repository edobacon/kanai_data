# Edicion masiva de guias asociadas a una ruma (admin-only) — legacy

## Request

En las rumas, al levantar el modal de editar ruma, agregar una opcion "edicion masiva" disponible solo a usuarios ADMINISTRADOR. La opcion abre un modal secundario que permite editar 5 campos: `guiaArauco`, `especie`, `producto`, `fechaCorta` y `anioPlantacion`. El modal previsualiza los valores actuales (leyendo desde la ruma / primera guia asociada) y presenta un formulario para ingresar valores nuevos. `especie` y `producto` se ingresan via selectores poblados desde sus mantenedores respectivos. Al aceptar, el sistema muestra una advertencia "N guias seran modificadas en lote sin capacidad de revertir"; si el admin confirma, se envia el payload al backend.

Backend: endpoint nuevo en `pehuen-server` que valida JWT + rol ADMINISTRADOR, busca todas las guias asociadas a la ruma en edicion, y sobreescribe los campos indicados en TODAS esas guias. **Sin audit** (decision explicita: el legacy no tiene mecanismo de audit y este ticket no lo introduce; la irreversibilidad queda en UX puro).

**Paridad de UX**: el intake-explore debe observar como `pehuen-client` legacy maneja formularios, inputs, selectores (los populados desde mantenedores) y modals existentes. El modal masivo debe replicar esos patrones — mismos componentes Vue, mismo stack Harlem, misma convencion de validacion y manejo de estado. El draft (preview.html) debe reflejar el patron observado en el legacy, no proponer uno nuevo.

**Pre-condiciones operativas** (rule recurrente `legacy-preflight` a crear en este ticket):
- Ambos repos legacy en `main`, sincronizados con `origin`
- Working tree clean — resolver deuda actual en Session 0 del ticket
- Branches locales auditadas (5 ramas viejas en cada repo)
- Rama nueva desde `main` por repo para el ticket
- Si se levanta `pehuen-server` local para pruebas: `.env` apunta a `mongodb://localhost:27017/pehuen` (no al staging compose en 4402)

**Follow-up planificado**: ticket B futuro para mirror de la feature en `pehuen-nuxt`, una vez cerrado este. Documentar en teach-close exactamente que se construyo para que el ticket B replique con paridad. **Critico**: en `pehuen-nuxt` aplica `RULE-GEN-003` (audit-on-write, level: must) — el ticket B tendra que incluir AuditLog obligatoriamente. En este ticket (legacy) la rule no aplica.

Implicacion para el modal nuevo (5to `<ui-modal>` en `List.vue`):

**Patron de endpoints y services (backend, paridad — S2 lo replica):**

Investigado 2026-06-01 en `pehuen-server`. El endpoint nuevo debe seguir estos 3 patrones, no inventar.

1. **Registro de endpoints** (`controllers/ruma.controller.ts` + `classes/Controller.ts`):
   - `classes/Controller` es base minima: `{ public path: string; public router = Router() }`.
   - Cada controller extiende `Controller`; el constructor setea `this.path` (ej. `'/ruma'`) y llama `this.intializeRoutes()`.
   - Rutas: `this.router.<verb>(\`${this.path}...\`, jwtMiddleware('ACCESS', [roles?]), [dtoMiddleware?], this.handler)`. El plural se arma con `\`${this.path}s\`` (`/rumas`), sub-rutas con `\`${this.path}-guias/:id\`` (`/ruma-guias/:id`).
   - Handlers: arrow methods privados `async (req, res, next) => { try { ... res.status(200).json({payload}) } catch (e) { console.trace; next(new HttpException()) } }`. Errores de negocio: `next(new HttpException(status, msg))`.
   - Controllers montados en `server.ts` (array `new RumaController()`, ...) → `App` los `use`. Prefijo `/api` lo agrega App.
   - Socket: `const io = req.app.get('socketio'); io.sockets.to('rumas').emit('update-ruma', payload)`.
   - **Para el bulk**: agregar en `intializeRoutes` → `this.router.patch(\`${this.path}/:id/bulk-edit-guias\`, jwtMiddleware('ACCESS', [USER_ROLE.ADMINISTRADOR]), BulkEditGuiasDto.validatePartialDtoMiddleware, this.bulkEditGuias)` y `this.router.get(\`${this.path}/:id/guias-count\`, jwtMiddleware('ACCESS'), this.getGuiasCount)`.

2. **Uso de services** (`services/ruma.service.ts`, `services/guia.service.ts`):
   - Singleton a nivel modulo en el controller: `const rumaService = new RumaService(); const guiaService = new GuiaService()`.
   - Clases con metodos arrow async. Query Mongoose: `Model.find().sort().skip().limit().populate(...)` + `select` armado condicional + `countDocuments()`.
   - El controller llama `rumaService.queryRumas(...)`, `rumaService.fillRumaData(...)`, `guiaService.queryGuias(...)`. La logica de datos vive en el service, no en el controller.
   - **Para el bulk**: el `updateMany({ruma, estado:'VIGENTE'}, {$set})` y el count van como metodos del service (ej. `guiaService.bulkUpdateVigentes(...)`, `guiaService.countVigentes(...)`); el controller orquesta + responde.

3. **DTO / validacion** (`dtos/ruma.dto.ts`) — **NO es class-validator (correccion a la spec)**:
   - Clase plana con `static fromPlainObject(p)` (construye el DTO) y `static validateDtoMiddleware`/`validatePartialDtoMiddleware(req,res,next)` con **validacion manual**: `errors: string[]`, chequeos `isValidObjectId(...)`, push de mensajes, `if (errors.length) next(new HttpException(400, errors.join(', ')))`, sino `next()`.
   - **`validatePartialDtoMiddleware` es el patron exacto del bulk**: arranca con guard `if (!campoA && !campoB && ...) next(new HttpException(400, 'Nada que actualizar'))` (= REQ-06 "al menos 1 campo"), luego valida cada campo **solo si viene** (`campo && !isValidObjectId(campo) && errors.push(...)`) — que es justo la semantica vacio=preservar (D-3).
   - **Para el bulk**: crear `dtos/bulk-edit-guias.dto.ts` con `BulkEditGuiasDto.validatePartialDtoMiddleware` replicando este patron (8 campos opcionales; guard nada-que-editar; isValidObjectId para los 5 refs; enum ACTIVA/TERMINADA; regex DD-MM-YYYY; chequeo par especie-producto en el handler o service por requerir lookup).

**Impacto en artefactos del intake:** H2 y H5 actualizadas abajo; OQ-1 y OQ-2 resueltas; TC-11 (`guiaArauco`) queda **obsoleta**; design-feature agrega TCs para estado=guia, cascada especie→producto, card por prop, los 3 selectores nuevos (intervencion/zona/procedencia).
