## Alcance — 5 areas sin cobertura

### 1. Storage R2/S3 (alto)

> RE-SCOPE 2026-07-19 (intake + decision del dev): produccion usa `local` (filesystem), NO R2. R2 esta
> fuera del roadmap. Ver "## Intake" area 1 y "### Decisiones" #2. Lo de abajo es la redaccion original
> (asumia R2 en prod, incorrecto) y queda como referencia historica.

- **Evidencia**: produccion usa `CloudflareR2Storage` (`server/utils/storage/r2.ts`, via
  `server/utils/storage/index.ts`), pero el 100% de la cobertura de storage es sobre `LocalStorage`
  (`tests/unit/server/utils/storage/local.test.ts`). Un bug en R2 no lo detecta ningun test.
- **Accion**: test del adapter R2 (upload/download/delete/exists) contra un bucket de test o mock del SDK;
  smoke que confirme que la URL/key retornada es consumible.

### 2. anonymizeUser (alto, compliance/PII)

- **Evidencia**: `server/services/user.service.ts:36-40` limpia nombre/email/password; cero referencias
  en `tests/`.
- **Accion**: unit test que verifique que anonimiza los campos PII y **mantiene las referencias**
  (createdBy en guias/rumas no se rompe).

### 3. Descarga de reportes `?name=X` (medio-alto)

- **Evidencia**: `server/api/reports/file.get.ts:7-19` implementa descarga con validacion de ownership;
  cero tests (el e2e `reportes.spec.ts` solo navega la UI, nunca descarga).
- **Accion**: test que ejercite la descarga + el rechazo cuando el name no pertenece al usuario.

### 4. RBAC: ADMIN sobre otro ADMIN + toggle status del propio usuario (medio)

- **Evidencia**: `server/api/auth/users/[id]/status.patch.ts:8-24` implementa ambas restricciones; cero
  tests (la suite migration-paridad cubrio otras rutas de `/api/auth/*` pero no esta).
- **Accion**: e2e/API que verifique ADMIN no puede modificar a otro ADMIN, y que un usuario no puede
  cambiar su propio status.

### 5. Sockets realtime end-to-end (alto si es criterio de negocio)

- **Evidencia**: toda la cobertura de sockets es unit mockeada (contrato de rooms/eventos,
  `socket.test.ts`, `useDomainSocket.test.ts`). **No existe** un test que emita desde el server
  (`emitToRoom`) y confirme recepcion en un cliente real.
- **Accion**: test de integracion realtime (cliente socket.io real conecta a una room, el server emite,
  el cliente recibe). Decidir con el dev si "notificaciones en tiempo real funcionan" es criterio de corte.

### Notas de ejecucion

- **Area 1** ahora es PARIDAD con el legacy (filesystem in-system); R2 descartado (fuera de roadmap).
  **Areas 2 y 5(adiciones)**: RULE-MIGRATION-004 no aplica (sin legacy que igualar); disenar contra el
  comportamiento nuxt deseado.
- **Sockets**: el core de rooms/eventos SI es paridad (mismos nombres en ambos backends); la auth del
  handshake es mejora nuxt (BUG-07). El test cubre ambos.
- **Prioridad por riesgo**: anonymizeUser + sockets realtime = alto. RBAC + reportes + storage in-system = medio.

### Decisiones (2026-07-19)

1. **RESUELTA (dev) — sockets realtime ES criterio de corte.** Se exige un test realtime e2e: cliente
   `socket.io-client` real (server invoca `emitToRoom` → el cliente recibe con el payload esperado), +
   handshake sin cookie debe fallar, + `isAllowedRoom` rechaza una room no autorizada. La S3 (sockets)
   entra al alcance OBLIGATORIO de corte, no es opcional.
2. **RESUELTA (dev) — sin object storage cloud (R2/S3): fuera del roadmap.** Los uploads quedan dentro del
   sistema (filesystem). El provider real es `local` (o `railway` = volumen montado, tambien filesystem).
   El area 1 se testea sobre el storage in-system real (Local/Railway), NO R2. El adapter `r2.ts` queda sin
   test y marcado para posible eliminacion como dead code (decision aparte, baja prioridad).
