# Correr los tests en CI + thresholds minimos de cobertura

## Request

Derivado de la auditoria de migracion (2026-07-19), punto debil #1: el CI del repo (`.github/workflows/ci.yml`) **no corre ningun test** — solo `pnpm lint`, `pnpm format:check` y `pnpm build`. La suite unit (699 tests) solo se ejecuta en el hook `.husky/pre-push`, evitable con `git push --no-verify`; integration y e2e no tienen ningun gate automatico. Una regresion puede entrar al repo sin que nada la detecte. Este ticket agrega la red de seguridad automatica.

### Context found

- **Alcance minimo de alto valor**: agregar un job que corra `pnpm test:run` (unit, sin infra) en cada push/PR. Es el 90% del valor con 0 dependencia de infra.
- **Alcance extendido (opcional)**: job de integration/e2e con servicios (Mongo + clones) via `services:` de GitHub Actions o docker-compose; mas costoso y flaky, evaluar como job separado (nightly o on-demand).
- **Thresholds**: subir de 0 a un piso realista (no 100%) para evitar regresion de cobertura sin bloquear el equipo. Definir el valor con baseline real.
- **Warning**: no romper el pipeline existente; agregar jobs, no reemplazar. Verificar que `pnpm test:run` pasa en el runner de CI (node version del `.nvmrc` = 24).

**Necesidad y reuso (DET-32, light)**: reuse/reduce — no se crea infraestructura nueva; se reusa el script `test:coverage` ya existente y el patron de setup del job de build (checkout/node/pnpm/install/rebuild sqlite). El unico "build" es el bloque del job y los 4 thresholds. Veredicto: reduce.

**Decision de diseno (thresholds)**: piso anti-regresion ~3pt bajo baseline (no meta 100%), alineado al request ("piso realista, sin bloquear al equipo"). Alternativa descartada: thresholds por-directorio apuntando a las capas bien cubiertas (shared/schemas, server/utils) — mas preciso pero mas brittle y de mayor mantenimiento; contra "sin bloquear al equipo". El piso global tolera churn menor y reprueba caidas significativas; el grueso de la proteccion viene de los tests fallando (TC-1).

**Alcance CI (trigger)**: los triggers existentes (`push`/`pull_request` a `main`/`develop`) se mantienen. El gate protege las ramas protegidas — que es donde una regresion "entra al repo". PRs a `develop` corren el job antes del merge. No se ampliaron los triggers (evita scope creep).

**Backlog**:

- [could] Subir el piso de cobertura conforme se cierre deuda de tests unit sobre `server/**`.

**Discoveries / Learns nuevos**:
- L1: la cobertura unit "real" del repo (~23%) es mucho menor que el ~36% que reportaba el config/`test-coverage-report.md`, porque el `include` de coverage abarca `server/**` (handlers/servicios) que se cubren por integration/e2e, no por unit. El numero unit por si solo subestima la cobertura efectiva. Por eso el threshold es un piso anti-regresion, no una meta.
- L2: commitlint del repo (`commit-msg` hook) enforce conventional-commits (`type(scope): subj`); el `commit_format` de `config.yaml` (`{ticket} [{workspace}] tipo: desc`) no pasa el hook. El id PEH va al final entre parentesis (patron real: `test(stats): ... (PEH-024)`). Actualizar la convencion del proyecto o el linter es follow-up.
