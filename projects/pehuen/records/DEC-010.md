# Cleanup automático de reportes: mantener los 3 últimos por usuario (vs acumulación indefinida legacy)

## Context and problem statement

El legacy acumula reportes Excel generados en `uploads/reports/` indefinidamente, sin ningún mecanismo de limpieza. En producción, esto puede representar cientos de archivos por usuario a lo largo del tiempo. El nuxt implementa cleanup automático que mantiene solo los 3 reportes más recientes por usuario, eliminando los anteriores al generar uno nuevo. Se debe confirmar el número de reportes a mantener y el comportamiento del cleanup.

## Decision drivers

- Storage sostenible: el legacy en N años acumula linealmente.
- UX: mantener los más recientes es suficiente para el caso de uso (el usuario descarga el reporte y lo guarda localmente).
- Simplicidad: no requiere tabla de retención, solo un conteo y delete.
- Risk: si un usuario genera reportes en paralelo (race condition), el cleanup puede eliminar reportes no descargados.

## Considered options

| # | Option | Description |
|---|--------|-------------|
| A | Acumulación indefinida (paridad legacy) | Sin cleanup, storage crece linealmente |
| B | Mantener 3 más recientes (nuxt actual) | Cleanup al generar: borrar todos salvo los 3 últimos |
| C | TTL index (7 días) | Reportes se eliminan automáticamente a los 7 días |

### Option A: Acumulación indefinida
- **Pro**: Sin riesgo de eliminar reportes que el usuario no descargó.
- **Con**: Storage no sostenible. No aplica con storage cloud (S3/R2 tiene costo por GB).

### Option B: Mantener 3 más recientes
- **Pro**: Storage acotado. Simple de implementar.
- **Con**: Riesgo de eliminar reporte recién generado si hay concurrencia.
- **Con**: Si el usuario quiere un reporte de la semana pasada ya no está disponible.

### Option C: TTL 7 días
- **Pro**: Ventana de tiempo clara para el usuario.
- **Con**: Requiere campo de expiración en el modelo. Más complejo.

## Decision outcome

**Chosen option**: B — mantener 3 más recientes por usuario.

**Justification**: Es el comportamiento ya implementado en nuxt. El uso típico es generar → descargar inmediatamente. Mantener 3 es suficiente para el caso de error (necesito regenerar). El riesgo de concurrencia es bajo dado el volumen de usuarios concurrentes esperado.

## Consequences

### Positive
- Storage acotado y predecible independiente del tiempo de operación.

### Negative
- Reportes antiguos no disponibles server-side (el usuario debe descargar y guardar localmente).

### Mitigations
- Comunicar al equipo: "los reportes se mantienen disponibles por generación (3 últimos), descargar inmediatamente".
- Considerar aumentar de 3 a 5 si hay feedback de usuarios que necesitan más.

## Confirmation

- Test: generar 4 reportes → solo existen 3 en storage (el más antiguo fue eliminado).
- `grep -n "cleanup\|deleteOld\|reportes.*3" server/api/reports/` → debe aparecer la lógica de cleanup.
- `db.reportes.find({ userId: <id> }).count()` → nunca supera 3 tras varias generaciones.
