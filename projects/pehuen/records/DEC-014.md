# `PATCH /guia-status`: sin `requireRole` en legacy (cualquier autenticado) vs restringir a A/R/S en nuxt

## Context and problem statement

En el legacy, el endpoint `PATCH /guia-status/:id` (que cambia el estado de una guía entre VIGENTE y NULA) no tiene guard de rol: cualquier usuario autenticado puede anular o reactivar una guía, independientemente de su rol. El nuxt puede mejorar esto restringiendo el acceso a roles con responsabilidad operativa (ADMINISTRADOR, RECEPTOR, SUPERVISOR). Se debe decidir: ¿preservar paridad (cualquier autenticado) o agregar restricción de roles?

## Decision drivers

- Seguridad: anular una guía es una operación de alto impacto (puede afectar stock y trazabilidad).
- Paridad: en legacy cualquier rol puede hacerlo, incluyendo CONSULTOR y ASESOR.
- Operativa: en la práctica, ¿los CONSULTORs o ASESORs anulan guías? Si no, la restricción no impacta el flujo real.
- Auditoría: con AuditLog (DEC-004) cualquier anulación queda registrada independientemente del rol.

## Considered options

| # | Option | Description |
|---|--------|-------------|
| A | Paridad server legacy | Sin restricción de rol: cualquier usuario autenticado puede cambiar estado |
| B | Restringir a ADMINISTRADOR, RECEPTOR, SUPERVISOR | Roles operativos según criterio backend |
| C | Solo ADMINISTRADOR | Anulación reservada para administrador únicamente |
| **D** | **Paridad client legacy: ADMINISTRADOR + RECEPTOR + ASESOR** | **Coincide con lo que el client legacy renderiza (todos excepto CONSULTOR y SUPERVISOR)** |

### Option A: Paridad server legacy
- **Pro**: Sin cambio de comportamiento server. Sin riesgo de bloquear endpoints.
- **Con**: Preserva un hueco de seguridad. CONSULTOR/SUPERVISOR podrían llamar el endpoint aunque el client legacy no les renderiza el botón.

### Option B: Restringir a A/R/S (ADMIN+RECEPTOR+SUPERVISOR)
- **Pro**: Roles tradicionalmente asociados a operaciones administrativas.
- **Con**: NO coincide con el contrato del client legacy: SUPERVISOR no ve el botón hoy y ASESOR sí lo ve.

### Option C: Solo ADMINISTRADOR
- **Pro**: Control total centralizado.
- **Con**: Rompe la paridad client — RECEPTOR y ASESOR pierden una capability que ejercen hoy.

### Option D: Paridad client legacy (ADMIN+RECEPTOR+ASESOR)
- **Pro**: Aplicación directa de [RULE-AUTH-011](../rules/auth/RULE-AUTH-011-capabilities-from-client.md). El client legacy ya define exactamente quiénes ven el botón.
- **Pro**: Cierra el hueco del server (CONSULTOR y SUPERVISOR no podrán llamar el endpoint, alineado con que tampoco ven el botón).
- **Pro**: Cero cambio operativo: los usuarios que anulan hoy siguen anulando.
- **Con**: Pierde paridad teórica con el server legacy (que era abierto), pero gana paridad real con el contrato del client.

## Decision outcome

**Chosen option**: **D — Paridad client legacy (ADMIN + RECEPTOR + ASESOR)**.

**Justification**: Aplicación directa de [RULE-AUTH-011](../rules/auth/RULE-AUTH-011-capabilities-from-client.md). El client legacy ya define el contrato real:

- [guides/List.vue:125-142](../../pehuen-client/src/views/guides/List.vue#L125-L142): el botón "ESTADO" se agrega a `actions` solo si `role !== 'CONSULTOR' && role !== 'SUPERVISOR'`. Es decir: lo ven y pueden ejecutarlo **ADMINISTRADOR, RECEPTOR, ASESOR**.

El nuxt debe restringir el endpoint y la UI para que coincidan con ese contrato exacto. La apertura del server legacy (sin `requireRole`) es un hueco de seguridad histórico, no una decisión consciente.

## Consequences

### Positive
- Cierra hueco de auth del server legacy alineado con el contrato del client.
- Cero cambio operativo: los usuarios que anulan hoy siguen anulando.
- Visual y servicio quedan coherentes: el botón solo aparece donde el endpoint acepta.

### Negative
- Si en el futuro se quiere ampliar a SUPERVISOR (rol de auditoría), requiere DEC explícita.

### Mitigations
- AuditLog (DEC-004) registra todas las anulaciones con userId/role.
- Test E2E que verifica visibilidad del botón por rol y respuesta del endpoint.

## Confirmation

- **Backend**: `requireRole(['ADMINISTRADOR', 'RECEPTOR', 'ASESOR'])` en `server/api/guia-status/[id].patch.ts`.
- **Frontend**: el botón "ESTADO" / "Anular" en `app/components/guides/GuideListActions.vue` (o equivalente) debe ocultarse para `CONSULTOR` y `SUPERVISOR`, replicando [guides/List.vue:125](../../pehuen-client/src/views/guides/List.vue#L125).
- **Test E2E**: por cada rol, verificar visibilidad del botón + respuesta 403 del endpoint cuando corresponde.
- **Test contrato**: `grep -n "requireRole" server/api/guia-status/\[id\].patch.ts` → muestra los 3 roles exactos.
- Drift detector: el [script de auditoría de capabilities](../../pehuen_nuxt/scripts/audit-role-capabilities.ts) (a crear) debe alertar si la matriz client diverge del backend.
