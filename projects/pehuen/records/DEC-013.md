# Shape de respuesta paginada: `{ payload: { items, total } }` (legacy) vs `{ items, total, page, pages, qty }` (nuxt)

## Context and problem statement

El legacy retorna listas paginadas con shape `{ payload: { items: T[], total: number } }`. El nuxt retorna `{ items: T[], total: number, page: number, pages: number, qty: number }`. Son incompatibles. Si el cliente legacy (pehuen-client en transición o integraciones externas) consume el endpoint paginado de nuxt, recibirá un objeto sin `payload` y su código fallará con `undefined`. Se debe confirmar si hay consumidores del formato legacy antes del corte.

## Decision drivers

- Paridad de API: el cliente espera `response.payload.items` pero nuxt retorna `response.items`.
- El nuxt agrega campos útiles: `page`, `pages`, `qty` que el legacy no tenía.
- El nuevo shape es más ergonómico y estándar.
- Verificar si hay consumidores externos (dashboards, integraciones) que usen el formato legacy.

## Considered options

| # | Option | Description |
|---|--------|-------------|
| A | Paridad legacy | Retornar `{ payload: { items, total } }` |
| B | Nuxt actual | Retornar `{ items, total, page, pages, qty }` |
| C | Ambos | Retornar `{ payload: { items, total }, items, total, page, pages, qty }` durante transición |

### Option A: Paridad legacy
- **Pro**: Sin cambio en el cliente. Sin riesgo de romper integraciones.
- **Con**: Shape menos informativo. No incluye `page`/`pages`/`qty`.

### Option B: Nuxt actual
- **Pro**: Shape más completo. Patrón más ergonómico.
- **Con**: Rompe el cliente si consume directamente desde `response.payload`.

### Option C: Compatibilidad dual
- **Pro**: Transición sin romper nada.
- **Con**: Overhead de mantener doble shape. Confuso para los devs.

## Decision outcome

**Chosen option**: **B — Nuxt actual (`{ items, total, page, pages, qty }`)**.

**Justification**: La migración a Nuxt es la oportunidad para adoptar el shape más completo. El sistema legacy va a deprecarse; preservar `{ payload: { items, total } }` solo perpetúa una API menos expresiva sin upside operativo. Esta decisión **rompe paridad de API intencionalmente** y se registra como tal:

- El nuevo shape es la **forma canónica** del sistema migrado.
- Cualquier consumidor que use el formato legacy debe actualizarse al corte.
- No se implementa compatibilidad dual: el costo de mantener doble shape supera el beneficio de la transición gradual.

**Esta es una decisión de migración deliberada, no una decisión "cuestionable" de paridad. El nuevo shape manda.**

## Consequences

### Positive
- Si B: shape más expresivo con metadatos de paginación.

### Negative
- Si B: cualquier consumidor legacy del endpoint falla hasta actualizarse.

### Mitigations
- Grep en `app/` para verificar qué formato consume el cliente nuxt actual.
- Si hay consumidores externos: implementar C (dual) durante periodo de transición.

## Confirmation

- Decisión registrada como **breaking-change intencional** de la migración (tag `delta-intencional`).
- Documentar el shape canónico en `pehuen_nuxt/docs/02-architecture/api-conventions.md` (paginación).
- Auditoría: `grep -rn "\.payload\." app/composables/api/ pehuen_nuxt/app/` → confirmar que ningún consumidor del nuxt usa el formato legacy.
- Test: `GET /api/guias` → response contiene `{ items, total, page, pages, qty }` (no `payload`).
- Comunicación al corte: changelog explícito sobre el cambio de shape.
