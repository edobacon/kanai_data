# Recuperar patrones de lectura y assets utiles de DrunaDoors

## Context and problem statement

DrunaDoors fue un intento fallido por falta de orden inicial, pero contiene elementos de experiencia que si aportan valor a DrunAppGor: expandibles para leer contenido largo, zoom de texto, zoom de imagenes, assets ya preparados de setup/heroes/monstruos y algunos comportamientos de lectura por voz.

Correccion de fuente: las puertas de DrunaDoors son 1.0. DrunAppGor trabajara con puertas 1.5 desde `doors_es`, asi que las puertas de DrunaDoors no son contenido canonico ni deben usarse para poblar el explorador 1.5.

El riesgo es doble: perder trabajo util si se descarta todo DrunaDoors, o repetir el desorden si se copian componentes Vue y assets sin trazabilidad.

## Decision drivers

- Preservar lo que ya mejoraba la lectura de capitulos, puertas e interacciones.
- Mantener DrunAppGor Flutter-first y data-first.
- No copiar componentes Vue, Tailwind ni composables como arquitectura.
- Evitar que imagenes entren al proyecto sin IDs, `sourceRefs` y estado de confianza.
- Evitar que assets/textos de puertas 1.0 de DrunaDoors se mezclen con puertas 1.5 de `doors_es`.
- Hacer que los tickets de diseno consideren accesibilidad de lectura desde el inicio.

## Considered options

| # | Option | Description |
|---|--------|-------------|
| A | Descartar UX/assets de DrunaDoors | Usar solo documentos fuente y redisenar todo. |
| B | Copiar UI/assets tal como estan | Portar componentes e imagenes directamente al nuevo proyecto. |
| C | Migrar patrones y assets con contrato canonico | Recrear los patrones en Flutter y copiar assets solo cuando tengan mapeo canonico. |

### Option A: Descartar UX/assets de DrunaDoors
- **Pro**: Base limpia.
- **Con**: Pierde aprendizajes utiles de lectura y visualizacion.
- **Con**: Rehace trabajo de assets ya disponible.

### Option B: Copiar UI/assets tal como estan
- **Pro**: Avance visual rapido.
- **Con**: Reproduce deuda del intento anterior.
- **Con**: Deja assets sin trazabilidad y widgets acoplados a estructura vieja.

### Option C: Migrar patrones y assets con contrato canonico
- **Pro**: Recupera valor sin heredar arquitectura.
- **Pro**: Los assets quedan auditables y vinculados a entidades.
- **Pro**: Permite diseno Flutter consistente con modelos Deckard.
- **Con**: Requiere inventario y mapeo antes de copiar.

## Decision outcome

**Chosen option**: C — Migrar patrones y assets con contrato canonico.

**Justification**: Los expandibles, controles de texto, zoom de imagenes y assets de DrunaDoors son utiles para DrunAppGor, pero deben entrar como patrones de producto y datos normalizados, no como un port directo de la app anterior.

## Patterns to preserve

| Patron | Referencia DrunaDoors | Implementacion esperada en DrunAppGor |
|--------|-----------------------|----------------------------------------|
| Expandibles de lectura | `DoorExpandable.vue`, `ChapterDetailView.vue`, `InteractionsView.vue` | Widgets Flutter para secciones, puertas, opciones e interacciones colapsables. |
| Zoom de texto | Controles A-/A+ con preferencia persistida | Preferencia local de escala de lectura, compatible con accesibilidad del sistema. |
| Zoom de imagen | `ImageModal.vue` para puertas y setups | Visor full-screen/route modal con imagen contenida, pan/zoom si aplica. |
| Imagenes de setup/capitulo | `public/chapter-setup/**` | `mediaRefs` vinculados a capitulos, setups o interacciones. |
| Imagenes de puertas | `public/doors/**` | Solo referencia/candidato historico 1.0. No usar como fuente canonica de puertas 1.5; cualquier uso requiere cruce contra `doors_es`. |
| Héroes y monstruos | `public/heroes/**`, `public/monsters/**` | Assets asociados a modelos canonicos de personaje/monster. |
| Lectura por voz | `useSpeech.ts` | Referencia de comportamiento para proveedor TTS Flutter, no codigo a portar. |
| Overrides/randomizacion de monstruos | `useMonsterOverrides.ts` | Logica de dominio futura, despues del modelo canonico de monstruos. |

## Consequences

### Positive
- Los tickets de diseno no parten de cero.
- El lector de campana puede ofrecer una experiencia mas comoda desde las primeras pantallas.
- Las imagenes existentes se vuelven inventario migrable, no archivos sueltos.
- Se evita mezclar puertas 1.0 con el explorador de puertas 1.5.

### Negative
- Copiar assets queda bloqueado hasta tener IDs y `mediaRefs`.
- Algunos tickets visuales tendran dependencia con pipeline de datos.

### Mitigations
- Crear una spec o ticket de inventario/migracion de media antes de mover archivos.
- Requerir `sourceRefs`, `confidence` y entidad destino para cada imagen copiada.
- Usar `docs/drunadoors-reusable-ui-assets.md` como contexto operativo.

## Confirmation

- Ningun componente Vue/Tailwind se porta directamente a Flutter.
- Toda imagen copiada al nuevo proyecto tiene entidad canonica destino.
- Los tickets de lectura/campana/puertas consideran expandibles, zoom de texto y zoom de imagen.
- Los assets sin mapeo quedan inventariados como candidatos, no como assets activos.
- Cualquier dato o asset de puerta activo debe resolver contra `doors_es` 1.5; DrunaDoors/public/doors no basta.
