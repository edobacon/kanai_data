## 3. Reglas de dominio sobre el campo (REQ-03 / REQ-04)

**Validación por fila** (en `logic/helpers/validateCompetencyAlignment.js`, dentro de la transacción):

| Regla | Condición | Resultado si falla |
|---|---|---|
| Tipo de transporte | `string` (no number) | rechazo de la fila → rechazo del batch (todo o nada) |
| Rango | `0 ≤ valor ≤ 100` | rechazo |
| Precisión | máximo 2 decimales | rechazo |
| **R-6** | `contributionType ∈ {Evaluates, Both}` ⟹ peso admitido | — |
| **R-6** | `contributionType = Develops` ⟹ `contributionPercentage = null` | rechazo si viene valor |

**Reuso obligatorio (REQ-03):** `isValidWeight` / `hasWeightPrecision` ya vigentes en el módulo. No duplicar el criterio de precisión ni introducir un validador paralelo.

**Persistencia sin truncar:** el valor llega y se guarda como string; no se normaliza a float ni se redondea en el backend. El único ajuste de residuo ocurre **client-side** en `weights.ts` al repartir (REQ-05).

## 4. Clave de agrupación y scope de borrado

### 4.1 Grupo de peso (REQ-04)

Clave lógica, **no una entidad**:

```
grupo = (planId, competencyNodeId, developmentLevelId)
```

Filas del grupo que **pesan** = las de tipo `Evaluates` o `Both`. La suma esperada del grupo es 100, pero **no se valida en este ticket**: la validación "suma 100 al publicar" (D1) es cross-mod hacia `curriculum-design` y queda fuera de alcance.

Soportado por el **índice existente** (UPONE-1769) sobre esa terna.

### 4.2 Scope del batch (REQ-02) — confirmado en código

Como no existe `matrixId` en la tabla, el conjunto que el batch reemplaza se define por **join**, igual que el filtro ya presente en `competencyAlignmentView` (línea 293):

```
scope(planId, matrizId) =
  CompetencyAlignment
  WHERE planId = :planId
    AND competencyNodeId ∈ (competencias de :matrizId)
```

Invariantes del reemplazo total:

- Retira **solo** las filas de ese scope que no vinieron en el payload.
- **Nunca** toca tributaciones de otras matrices adoptadas por el mismo plan.
- **Nunca** borra filas "fuera de diseño" (R-12: se marcan, no se borran).
- Es seguro porque el cliente reenvía el conjunto completo del `(planId, matriz)` cargado — el view **no pagina** (contrato de guardado confirmado).

## 6. Objetos de transporte (NUEVOS, no persistidos)

No son entidades: son contratos de la mutación gobernada. Se listan porque definen la forma del dato que cruza la frontera.

### 6.1 Batch de upsert de conjunto (REQ-01 / REQ-11)

```
CompetencyAlignmentBatchInput
├─ matrixId                 : UUID, obligatorio   (define el scope junto con planId)
├─ planId                   : UUID, obligatorio   (se REVALIDA/DERIVA server-side)
└─ alignments[]             : lista, obligatoria (puede venir vacía = retirar todo el scope)
   ├─ planEntryId           : UUID, obligatorio
   ├─ competencyNodeId      : UUID, obligatorio
   ├─ developmentLevelId    : UUID, obligatorio
   ├─ contributionType      : enum Develops|Evaluates|Both, obligatorio
   └─ contributionPercentage: string|null, opcional (null obligado si Develops, R-6)
```

- **Mismo payload para las dos vistas** del editor (por competencia y por malla), REQ-11.
- Escritura `*Validated` con `runInTransaction`, **sin CRUD generic**.
- RBAC propio: exige **create + modify + delete** (patrón `planEntry-batch.resolver.js`).
- Historial: **una sola entrada** por batch.

### 6.2 Vía masiva (REQ-07)

```
CompetencyAlignmentBulkAssignInput
├─ planId                : UUID, obligatorio (derivado server-side)
├─ matrixId              : UUID, obligatorio
├─ competencyNodeId      : UUID, obligatorio
├─ developmentLevelId    : UUID, obligatorio   ─┐ el "destino"
├─ contributionType      : enum, obligatorio   ─┘

CompetencyAlignmentBulkAssignResult
├─ applied[]  : { planEntryId }
└─ skipped[]  : { planEntryId, reason }
```

- Una sola transacción, con **troceo en el backend** (AD-12, patrón `matrixAdoption.resolver.js:246-300`).
- El resultado **no se persiste**: es respuesta de la mutación.

### 6.3 Reparto en partes iguales (REQ-05, client-side)

Helper puro en `weights.ts`. **No toca el modelo**: produce los `contributionPercentage` que luego viajan en el batch de §6.1.

```
distributeEvenly(filasQuePesan: n) → n valores string, ≤2 decimales, suma exacta 100
```

El residuo de `100 / n` se ajusta en el cliente para que la suma cierre en 100.

### 6.4 Estado auto/manual (REQ-06, derivado)

```
isAutomatic(grupo) = pesos actuales del grupo === distributeEvenly(|filasQuePesan|)
```

Se recalcula en runtime para pintar el badge "REPARTO AUTOMÁTICO". **Sin campo, sin objeto, sin columna.**

## 7. Notas de migración

**No hay migración de esquema en este ticket.**

1. **`contributionPercentage` ya existe** como columna nullable, y el índice de grupo ya existe: ambos entraron con UPONE-1769 y están en `develop`. Este ticket solo los **usa**.
2. **Cambio de contrato, no de esquema:** agregar `contributionPercentage` a `WRITABLE_FIELDS` habilita su escritura por la vía gobernada. No requiere DDL.
3. **Datos preexistentes:** las filas creadas por UPONE-1756 tienen `contributionPercentage = null`. Es un estado **válido y esperado**, no un dato a backfillear:
   - filas `Develops` deben quedar en `null` permanentemente (R-6);
   - filas `Evaluates` / `Both` en `null` son "sin peso asignado aún" y el usuario las completa desde la UI o con "Repartir en partes iguales".
   - **No se propone backfill automático**: repartir 100 en grupos existentes sería una decisión de negocio, no de migración, y hoy no hay regla que obligue a que la suma sea 100 (D1 está fuera de alcance).
4. **Sin drift:** `sync` / `codegen` no deben producir diferencias, porque el modelo no cambia. Los artefactos de sync no se commitean.
5. **Reversibilidad:** alta. Revertir el ticket es quitar el campo de `WRITABLE_FIELDS` y los resolvers nuevos; los datos escritos quedan como valores válidos en una columna nullable que ya existía, sin necesidad de rollback de datos.
