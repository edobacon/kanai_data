# Diferir el fix del poison-pill del codegen (BUG-object-manager-002): el reset-from-scratch lo cubre mientras todos los tenants sean seed; reabrir al llegar el primer dato real no-reseteable

## Context and problem statement

TICKET-077 descubrió un bug latente en el codegen del registry (`generatePrismaSchema.js`): cuando un campo migra base↔RT, el lookup filtra por `isBaseField` → no encuentra la fila vieja → `create` → viola `@@unique([objectDefinitionId, name])` → throw; el try/catch por-RT aborta los campos siguientes en silencio; y no hay cleanup de orphans `isBaseField=false`. Resultado: el registry no se auto-repara con re-sync incremental (ver BUG-object-manager-002).

La tarea inicial fue "diseñar y aplicar el fix + abrir ticket DKC core-gated". Antes de abrir el ticket se evaluó la **necesidad real** (DET-32): ¿el proceso de deploy ya cubre esto?

## Decision drivers

- **YAGNI / costo-beneficio**: arreglar el codegen es `layer:core` (rama de épica UPONE-1206 + merge gated team up1, RULE-dev-004) — esfuerzo y riesgo no triviales para un bug que hoy no se manifiesta.
- **El deploy NO auto-repara** (verificado en código, no asumido): `migration-task` solo hace `prisma db push` (no toca el registry); `setup-task` corre `npm run sync` pero en modo `--resume` incremental (`setup-all-tenants.js:302`, "no destructive reset"); el registry sync no trunca `core_FieldDefinition`. → el camino automatizado es incremental, que es justo el que envenena.
- **Pero el reset SÍ cubre**: el único camino limpio (`tenant:reset` → tabla vacía → sin conflicto) está disponible mientras los tenants sean reseteables.
- **Estado vigente (dev, 2026-06-22)**: "en este momento no hay datos, todo es desde seed". Ningún tenant (UPU/TEST/DEMO/UC) tiene datos reales no-reseteables → el reset-from-scratch es siempre viable hoy.

## Decision outcome

**Chosen option: diferir el fix. NO se abre ticket de fix ni se toca el codegen ahora.** El bug se captura como BUG-object-manager-002 (`status: detected`, severity baja) con el mecanismo completo + line-refs + el hallazgo del deploy incremental, para que la decisión y el conocimiento queden trazados y el fix sea retomable en frío.

**Mitigante vigente**: mientras todos los tenants sean seed, desplegar cambios de modelo que muevan campos base↔RT vía reset-from-scratch por tenant (`tenant:reset` + reseed + full sync), no vía re-sync incremental.

**Trigger de reapertura (condición de necesidad)**: el **primer tenant con datos reales no-reseteables**. En ese punto el reset deja de ser opción, el sync incremental pasa a ser el único camino de deploy de modelo, y el poison-pill se vuelve un riesgo de corrupción de registry con recuperación manual por-tenant (SQL, sin rollback). El fix (reconciliar `isBaseField` + try/catch por-campo + cleanup de orphans RT, simétrico en ambas funciones) debe entrar ANTES de ese hito.

### Alternativas descartadas

- **Arreglar ahora (core-gated)**: descartado por costo-beneficio nulo hoy (reset cubre). Reconsiderable si surge una ventana barata (ej. otro ticket ya tocando el codegen).
- **No registrar nada (dejar pasar)**: descartado — el "por qué no" (deploy incremental no auto-repara, reset sí) es conocimiento nuevo de esta sesión, no estaba en ningún record; sin trazarlo, se re-investiga lo mismo más adelante.

## Consequences

### Positive

- Cero riesgo/esfuerzo en el codegen core mientras no aporta valor.
- Decisión y mecanismo trazados (BUG-object-manager-002) → el fix es retomable sin re-diagnóstico.
- Trigger explícito evita que el bug se vuelva incidente silencioso al llegar datos reales.

### Negative

- En dev local, el re-sync incremental sigue mordiendo ante un movimiento base↔RT (hay que recordar resetear) — fricción menor, ya conocida (mordió en 077).
- Deuda diferida: el fix queda pendiente con una condición de reapertura que el equipo debe vigilar (no hay enforcement automático del trigger).

## Confirmation

Dev confirmó (2026-06-22): el deploy es desde seed, sin datos reales → reset disponible; y aprobó capturar BUG-object-manager-002 + esta decisión en lugar de abrir el ticket de fix. Verificación de código (esta sesión): `migration-task-def.json`, `setup-task-def.json`, `setup-all-tenants.js:302`, `generatePrismaSchema.js` (lookups `:2448`/`:2753`/`:2833`, try/catch `:2389`-`:2566`/`:2661`-`:2864`, cleanup `:2553`/`:2788`).

## Lección

Antes de abrir un ticket de fix, correr el gate de necesidad (DET-32): verificar si el pipeline real ya cubre el problema — y verificarlo en el código del deploy, no asumirlo. Aquí el deploy NO cubre (incremental), pero el estado de datos (todo seed → reset disponible) sí → diferir con trigger explícito en vez de arreglar.
