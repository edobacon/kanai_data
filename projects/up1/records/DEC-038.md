# CurriculumMesh = adapter de dominio sobre un core presentacional; extracción del board genérico diferida a un 2º consumidor

## Context and problem statement

`CurriculumMesh` (MC-05) renderiza la malla como grid de columnas por período + tarjetas + resumen + gating. Hoy es **específico del dominio curricular** (planEntry, créditos de diseño, electivo, `Curriculum.status`). MC-06 (alta/edición) y MC-08 (filtros, prereqs, drag&drop) **agregan más dominio dentro del componente**, aumentando el acoplamiento. El dev planteó que el componente debería poder **reusarse en otras partes de up1** (representar otros elementos en un board de columnas) y que todo debe tener tests. ¿Generalizamos ahora, después, o no?

## Decision drivers

- **Reuso futuro**: un "board de columnas con tarjetas" es un patrón reusable (ofertas por período, secciones por fase, etc.).
- **DET-32 (necesidad/reuso)**: generalizar sin un 2º consumidor concreto = riesgo de abstracción equivocada (tan malo como no generalizar).
- **Costo/riesgo en SP5**: MC-06/MC-08 ya son Must/Should con SP altos; un refactor previo a "core genérico" agrega riesgo al critical path.
- **Lógica intrínsecamente curricular**: prereqs K-de-N, bloques electivos, `minToSatisfy`, herencia de créditos NO se generalizan limpio → forzarlas a un core genérico = abstracción con fugas.
- **Tests**: la lógica pura ya va a `.ts`+`.spec.ts`; las tasks UI-pesadas de MC-06/08 hoy NO declaran tests de interacción.

## Considered options

| # | Option | Description |
|---|--------|-------------|
| A | Seam ahora, extraer luego | Construir MC-06/08 con tarjetas por slot + acciones por evento + lógica pura en `.ts`, manteniendo separable el core presentacional. Extraer el board genérico cuando haya 2º consumidor. |
| B | Extraer `GroupedCardBoard` ahora | Refactor previo a MC-06/08 que separa el core presentacional genérico publicable. |
| C | Domain-specific | No invertir en agnosticismo; el componente queda acoplado al dominio. |

### Option A: Seam ahora, extraer luego
- **Pro**: bajo riesgo; no infla el critical path de MC-06/08; deja la extracción mecánica (no rewrite) cuando aparezca el 2º consumidor.
- **Pro**: respeta DET-32 (no se publica abstracción sin consumidor).
- **Con**: el reuso real llega sólo cuando se extrae; disciplina dependiente del que implemente MC-06/08 (mitigado por RULE).

### Option B: Extraer `GroupedCardBoard` ahora
- **Pro**: reuso disponible de inmediato.
- **Con**: abstracción prematura sin 2º consumidor (DET-32); costo/riesgo en el critical path; alto chance de diseñar la API equivocada.

### Option C: Domain-specific
- **Pro**: mínimo esfuerzo.
- **Con**: pierde reuso; cada board futuro se reescribe; contradice el espíritu de RULE-curriculum-design-014 (reusar el patrón agnóstico).

## Decision outcome

**Chosen option**: **A — Seam ahora, extraer luego.**

**Justification**: maximiza reversibilidad y reuso futuro al menor costo/riesgo, alineado con DET-32. Se separa en dos capas con un seam limpio: **(1) core presentacional** (columnas por campo de agrupación, tarjeta por **slot**, resumen config-driven, resaltado/atenuado, drag&drop que **emite eventos**, flag de edición — sin conocer planEntry/créditos/electivo) y **(2) adapter de dominio** `CurriculumMesh` (mapea planEntry/Activity/requirementCategory/Curriculum, aporta el slot de tarjeta, modales de alta/edición, checker de prereqs, lógica electiva). La extracción del core a un componente publicable (`GroupedCardBoard`) se difiere hasta confirmar un 2º consumidor concreto en up1.

## Consequences

### Positive
- Reuso futuro con extracción mecánica; core presentacional testeable aislado cuando se extraiga.
- Dominio aislado en el adapter → MC-06/08 no contaminan un core genérico.

### Negative
- El reuso no es inmediato (requiere la extracción posterior).
- Depende de disciplina al implementar MC-06/08 (que no horneen dominio en las primitivas de render).

### Mitigations
- **RULE-mods-051** codifica el seam (core slots/props/events + adapter + lógica pura testeable + tests de interacción).
- Las pre-specs de MC-06/MC-08 se enmiendan con la restricción explícita.
- Identificar el 2º consumidor (candidatos: ofertas por período, secciones por fase) antes de invertir en la extracción.

## Confirmation

- MC-06/MC-08: la lógica nueva (alta, prereq-checker, resaltado, recálculo period/position) vive en `.ts` con `.spec.ts`; las tasks UI incluyen tests de interacción.
- El `.vue` del adapter rinde las tarjetas por **slot** y dispara acciones por **evento/callback** (no llama mutations curriculares desde un primitivo de render).
- Ningún concepto curricular (planEntry, blockId, créditos, status) aparece en las primitivas de render (grid/columna/tarjeta-shell/summary-bar) — sólo en el adapter.
- Al aparecer un 2º consumidor: la extracción del board es mover archivos + tipar el view-model genérico, sin reescribir lógica de dominio.
