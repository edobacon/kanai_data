# MGR-06 cierra la via de columnas JSON en RecordList — visualizacion estructurada via `JsonFieldViewer` (drill-in) en RecordDetail

## Context and problem statement

MGR-06 (UPONE-1291, mergeado en develop 2026-07-08 commit 8c8cf52) elimina `processJsonSchema`; RecordList NUNCA renderiza campos `Json` como columnas/subcolumnas. La visualizacion estructurada de JSON pasa a RecordDetail via el nuevo `JsonFieldViewer` (molecule `components/molecules/JsonFieldViewer/` + elemento `json-field-viewer`).

## Decision drivers

- JSON crudo como columna del RecordList daba UX pobre (info-dump no actionable)
- Simplifica el motor de columnas
- Alineado a P3 DEC-LOCAL-02 (drill-in para el visor DataLog)
- Cambio upstream en develop, no en rama del mod

## Considered options

### Option A: A) Inline columns Campo/Antes/Despues
- **Pro**: UX legible sin drill-in
- **Con**: Requiere parser custom de `changes`, contradice MGR-06 upstream, codigo bloqueado por gateway de columnas

### Option B: B) Pretty-print JSON en columna
- **Pro**: Sin drill-in
- **Con**: Info-dump, no actionable, contradice DEC-LOCAL-02

### Option C: C) Refactor MGR-06 (permitir Json como columna)
- **Pro**: Libertad
- **Con**: Inversion del upstream, alto costo, riesgo de rebase


## Decision outcome

**Chosen option**: Visualizacion de `changes` (DataLog) hace drill-in via `JsonFieldViewer` (no inline columns). Columnas del RecordList solo escalares. Las columnas declaradas explicitamente en el layout (ej. 'Cambios' como string crudo) sobreviven el filtro MGR-06 — solo la auto-derivacion + el selector de columnas se ven afectados.

## Consequences

### Positive
- Alineado con plataforma (develop)
- Menos custom code (reuso JsonFieldViewer/jsonFieldUtils)
- Panel mod-only reutilizable
- Cero core
- Minimo esfuerzo

### Negative
- UX del visor Historial es drill-in (no inline Campo/Antes/Despues)
- Delegado externo (T020 B-follow-up) para 'amigable' (~800-950 LOC)
- MGR-06 es una decision upstream, cualquier reversion local rompe con plataforma
