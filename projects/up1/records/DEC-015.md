# Captura de auditoria de objetos UP1 usa event-driven BullMQ (no Prisma middleware ni GraphQL resolver wrapper) — sienta precedente para futuros mods con auditoria

## Context and problem statement

UPONE-1098 (HU2 — TICKET-020) implementa auditoria universal `changeLog` para 3 objetos (activity, curricularSection, curricularLink). El AC6 del ticket Jira presenta 3 mecanismos alternativos para capturar los cambios automaticamente y deja la decision al developer:

| Opcion | Descripcion | Pro (per ticket) | Contra (per ticket) |
|--------|-------------|------------------|----------------------|
| A | Prisma middleware/extension | Transparente, minimo codigo por objeto | Performance en batch |
| B | GraphQL resolver wrapper | Control fino, testeable | Instrumentar cada mutation |
| C | Event-driven BullMQ | Asincrono, escalable | Latencia, complejidad infra |

PM (Esteban Cortes) **recomendo A o B; descartando C** por "latencia, complejidad infra".

El intake DKC (TICKET-020 Session 6) evaluo el contexto adicional que el PM probablemente no considero al redactar la recomendacion:

1. El mod NO puede tocar `object-manager/` core (constraint scope mod — feedback de dev experiencia previa)
2. UPONE-1052 (cerrada SP17 2026-05-07) implementa `_previousData` + `_triggeredBy` en eventos BullMQ — el contra "complejidad infra" desaparece
3. El audit log es **eventually consistent** por naturaleza (no flujo transaccional critico) — latencia es aceptable

La decision es **estructural** (afecta el patron de captura para HU2 + futuros mods que necesiten audit), no solo tactica del ticket. Justifica decision formal level proyecto (DEC), no solo DEC-LOCAL del spec.

## Decision drivers

Ordenados por importancia (high → low):

1. **Constraint scope mod (HIGH)**: El mod NO modifica `object-manager/` ni `layout/` core per feedback de dev. Opciones A (Prisma middleware) y B (resolver wrapper) requieren cambios en `object-manager/src/middleware/` o `src/graphql/resolvers/` respectivamente. Eso bloquea o fuerza coordinacion con platform UP1 — fuera de scope SP2.
2. **Infraestructura ya disponible (HIGH)**: UPONE-1052 cerrada SP17 (Vignesh Somayaji, 3 SP, 2026-05-07) implemento `_previousData` + `_triggeredBy` en eventos BullMQ. El decorator `withEventPublish.js:52-66,113-123` enriquece el payload automatic. El contra "complejidad infra" del PM **desaparece**.
3. **Latencia aceptable para auditoria (MID)**: Audit logs son eventually consistent por definicion. Un drift de segundos entre la mutation y el row del changeLog es aceptable (no es flujo transaccional critico). Edge case batch transaccional **cubierto INDIRECTAMENTE**: rollback Prisma = sin evento BullMQ publicado = sin row changeLog (decorator emite POST-resolver).
4. **Recomendacion explicit del PM (LOW)**: El PM recomendo A/B sin descartar C explicit ("C solo si performance es critica"). Pero esa recomendacion asume constraint diferente (probable: no contemplo el scope mod ni UPONE-1052 cerrada el mismo sprint). Inversion justificable con drivers 1-3 arriba.

## Considered options

| # | Option | Description |
|---|--------|-------------|
| A | Prisma middleware/extension | `$use((params, next) => {...})` hook que intercepta TODAS las mutations create/update/delete y captura before/after sincronicamente. Persiste changeLog row en la misma transaction |
| B | GraphQL resolver wrapper | HoC decorator que wrappea cada resolver create/update/delete con captura before/after antes de delegar al CRUD generic |
| C | Event-driven BullMQ | Mod declara N event JSONs (1 per objectType+operation) en `events/`. Worker subscribe al canal core, recibe payload con `_previousData` + `data` + `_triggeredBy` enriquecido por UPONE-1052, hace diff field-by-field, emite N rows changeLog |

### Option A: Prisma middleware/extension

- **Pro**: Transparente — minimo codigo por objeto auditable. Solo declarar `auditable: true` en object schema (si platform soporta — no soporta hoy)
- **Pro**: Sincrono en transaction → batch transaccional cubierto NATIVO
- **Pro**: PM lo recomienda
- **Con**: **Modifica `object-manager/src/middleware/` core** — fuera de scope del mod
- **Con**: Performance hit en TODAS las mutations (no solo auditables) — el middleware corre siempre, decide en runtime
- **Con**: Requiere coordinacion con platform UP1 (decision cross-team)

### Option B: GraphQL resolver wrapper

- **Pro**: Control fino, testeable per-resolver
- **Pro**: Sincrono en transaction si se invoca dentro del resolver
- **Pro**: PM lo recomienda como alternativa
- **Con**: **Modifica `object-manager/src/graphql/resolvers/`** — fuera de scope del mod
- **Con**: Instrumentar CADA mutation manualmente (high effort + drift entre mods)
- **Con**: Mismo issue de scope que A

### Option C: Event-driven BullMQ

- **Pro**: **Zero core touch** — vive 100% en el mod (event JSONs + handler)
- **Pro**: UPONE-1052 entrega `_previousData` + `_triggeredBy` plug-and-play
- **Pro**: Asincrono — no penaliza performance de mutations sincronas
- **Pro**: Patron declarativo (event JSONs) consistente con el patron de mods
- **Pro**: Patron extensible — agregar objeto auditable = declarar 3 event JSONs (sin tocar handler central)
- **Con**: Eventual consistency (drift potencial — aceptable para audit)
- **Con**: Batch transaccional cubierto INDIRECTO (rollback Prisma = sin evento — validar empirico)
- **Con**: Invierte la recomendacion explicit del PM (requiere justificacion formal)
- **Con**: RULE-core-015 — worker es centralized, no per-mod → handler de mod debe vivir dentro del worker base O service externo invocado (decision arquitectonica OQ1 a cerrar en design-feature)

## Decision outcome

**Chosen option**: **C — Event-driven BullMQ**

**Justification**:

Driver dominante "constraint scope mod" descarta A y B por requerir cambios en `object-manager/` core. Sin UPONE-1052, la decision habria sido mas dificil (latencia + complejidad de implementar pre-fetch from scratch); con UPONE-1052 cerrada el mismo sprint, el unico contra significativo del C ("complejidad infra") desaparece. La eventual consistency es aceptable para audit por construccion. La inversion del PM se justifica con 3 drivers concretos (zero core touch, UPONE-1052 disponible, latencia OK) + plan empirico de validar batch transaccional indirecto (TC-16 del intake — TICKET-020).

## Consequences

### Positive

- HU2 (TICKET-020) ejecutable en 5 SP — sin esta decision, A/B requerirían 8-13 SP + coordinacion cross-team
- **Sienta precedente** para futuros mods que necesiten audit: declarar N event JSONs en `events/` + handler en el worker base → mod self-contained
- Patron extensible: agregar nuevo objeto auditable = 3 event JSONs (sin tocar codigo central)
- Performance no degradada en mutations (audit es async)

### Negative

- Eventually consistent: drift de segundos potencial entre mutation y changeLog row (aceptable para audit, no para flows transaccionales criticos)
- Batch transaccional cubierto INDIRECTAMENTE (no nativo como A) — depende de que rollback Prisma → evento NO publica
- Requiere infra BullMQ corriendo (docker-compose worker) — pero ya esta como parte de UP1 base
- Decision arquitectonica residual: OQ1 (handler dentro del worker base toca core; service externo invocado no toca core pero requiere convencion; auto-discovery toca core). DEC-LOCAL del spec a cerrar en design-feature

### Mitigations

- **Eventual consistency drift**: documentar en docs del mod que audit es eventually consistent. Para flows criticos que requieran sincronizacion estricta, escalar (no usar este patron — usar Prisma middleware en core con platform team approval)
- **Batch transaccional**: TC-16 en S9.T1 del spec — test integration con batch que falla mid-batch para validar empiricamente que rollback Prisma = sin evento. Si refuta, escalar o re-evaluar approach
- **Worker arquitectura (OQ1)**: cerrar en design-feature con 3 options + drivers + recomendacion. RULE-core-015 documenta el constraint del worker centralized
