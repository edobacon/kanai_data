# La sección "Requisitos" es UN mantenedor de árbol Y/O único, no un RecordList + árbol separado

## Context and problem statement

El draft v3 y la maqueta (`mockup-sp6.html`) planteaban la sección "Requisitos" del Programa de asignatura como una LISTA plana (RecordList nativo) + un modal "Ver regla unificada" (árbol Y/O read-only) + un modal de alta. En ejecución (S4/S10) se descubrió que el RecordList nativo NO puede representar el modelo real del requisito: las columnas "Vía" (derivada de `parentId`+`combinator`) y "Condición" (por-familia) no son campos reales (`useColumnConfiguration.ts:176` filtra a campos del objeto), y el catálogo de RTs polimórficos en una lista tiene más limitantes de core (L1-L4, ver `sp7/UPONE-1378-core-limitations.md`). El requisito ES un árbol (vías OR / condiciones AND / K-de-N); un RecordList lo aplana y, además, duplicar lista + árbol es doble estructura.

## Decision drivers

- Fidelidad al modelo: el requisito es un árbol Y/O; la superficie debe representarlo, no aplanarlo.
- Mod-only (RULE-dev-004): evitar tocar core. El RecordList exigía cambios de core (L1-L4) para lograr la maqueta 1:1.
- No duplicar: una sola superficie (el árbol) en vez de lista + árbol + modales separados.

## Considered options

| # | Option | Description |
|---|--------|-------------|
| A | RecordList nativo (lista) + árbol en modal | Draft v3 / maqueta. Requiere core (L1-L4) para columnas derivadas y RTs en lista |
| B | Mantenedor de árbol Y/O único editable | El árbol "regla unificada" es la vista principal, con detalles friendly + búsqueda + acciones por nodo + alta |

### Option A: RecordList + árbol en modal
- **Pro**: usa componentes nativos de plataforma.
- **Con**: no representa Vía/Condición (columnas derivadas, bloqueadas por `useColumnConfiguration`); requiere core (L1-L4); duplica estructura lista+árbol.

### Option B: mantenedor de árbol único
- **Pro**: representa fiel el árbol Y/O; 100% mod-only (esquiva L1-L4); una sola superficie; la fidelidad de la maqueta se logra sin tocar core.
- **Con**: componente custom (no RecordList nativo); acciones por nodo y alta se construyen a mano (reusando lo ya hecho en S1-S10).

## Decision outcome

**Chosen option**: B — el mantenedor de árbol Y/O único (dev, 2026-07-28, tras ver el render real). Supersede REQ-01 (RecordList) y el split lista+modal de la maqueta.

**Justification**: el requisito es un árbol; el RecordList lo aplanaba y exigía core. El mantenedor es 100% mod-only y esquiva las limitantes L1-L4 (que eran del RecordList → quedan como mejoras generales de plataforma, no bloqueantes de este ticket). Reusa lo ya construido (evaluador fiel S7, banner malla S8, modal stepper + catálogo multi + auto-derivar S10, guards S2). La familia Electivo (K-de-N) se persiste como `Group(OR, minToSatisfy=K)` con N hojas `RecordState` (interpretado por el evaluador fiel S7 como "K de N").

## Consequences

### Positive
- Fidelidad al modelo Y/O; mod-only; una sola superficie; maqueta lograda sin tocar core.

### Negative
- Componente custom (mantenimiento propio). Limitaciones LOW conocidas (follow-up en `sp7/UPONE-1378-out-of-scope-followups.md`): el kebab de acciones agrega un tab-stop dentro del treeitem (patrón preexistente del componente); editar/eliminar hojas de un pool electivo puede romper el invariante N≥K/N≥2 (gestionar el pool como unidad = follow-up).
