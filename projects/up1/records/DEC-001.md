# LLM-e2e con MCP chrome-devtools como reemplazo de Playwright para mods con auth efimero

## Context and problem statement

TICKET-011 necesitaba red de seguridad e2e para proteger refactor del TICKET-010. Playwright tradicional choca con limitaciones del platform: Clerk dev tiene sesiones efimeras que invalidan storageState capturado entre runs (TTL ~10min de inactividad), y el monorepo no expone login programatico via Clerk Backend API en scope SP1. Component tests sobre SFCs Vueform requieren mock costoso de @vueform/vueform defineElement + atoms + composables (estimado 3-4h de yak-shave para cobertura limitada).

## Decision drivers

- Necesidad de red de seguridad antes de iniciar refactor 010 (zero behavior change requiere validacion runtime)
- Auth Clerk dev no permite Playwright estable sin login programatico
- Custom Vueform elements no testeables con component tests sin mock pesado
- Cobertura visual de los TC override del 009 (UV/AIEP detail, stress modalities/outcomes, coexistence, edit/create flows)

## Considered options

### Option A: Playwright con storageState capturado manualmente
- **Pro**: Tooling estandar, integrable a CI
- **Con**: Clerk dev sessions invalidan storageState entre runs — TTL muy corto, no automatizable sin login programatico

### Option B: Playwright con login programatico Clerk Backend API
- **Pro**: Solucion definitiva para CI
- **Con**: 1-2h de research + integration con CLERK_SECRET_KEY, fuera de scope SP1

### Option C: Component tests con @vue/test-utils + jsdom
- **Pro**: Rapidos, deterministicos
- **Con**: Custom Vueform `defineElement` requiere mock costoso de Vueform + atoms + composables (3-4h). Cobertura limitada sin runtime real

### Option D: Verificacion manual por el dev
- **Pro**: Cero esfuerzo de tooling
- **Con**: No reproducible, lenta, propensa a olvidar TCs


## Decision outcome

**Chosen option**: Adoptar approach LLM-e2e: scenarios markdown ejecutables por agente LLM con acceso a chrome-devtools MCP. El LLM navega el browser real del dev (con sesion Clerk activa), aplica asserts sobre snapshot, captura screenshots baseline, registra resultados en `result.md`. Cuando un assert falla, el LLM razona sobre el snapshot y reporta hipotesis del root cause.

## Consequences

### Positive
- Cobertura runtime real con browser autenticado del dev
- LLM razona sobre fallos cualitativamente (no solo selector mismatch — detecta drift de datos como Q1 weight=13 vs 11)
- Documentacion viva: scenarios markdown legibles por humanos pueden ejecutarse manual sin LLM
- Sin overhead de auth setup
- Zero infra adicional — reusa el browser del dev y MCP existente
- Detecto C7 (bug walker shallow del sanitizer) en baseline — valor emergente del approach

### Negative
- No corre en CI sin agente LLM
- No detecta pixel-level diffs (color, alignment off-by-1)
- Performance benchmarks requieren medicion explicita de tiempo, no automatica
- LLM puede ser permisivo si los asserts son ambiguos — require asserts con datos especificos del seed
- Pre-step `npm run sync` obligatorio para evitar drift DB-vs-seed
- Sesiones largas para validar batches de cambios

## Confirmation

Adoptado en TICKET-011 (2026-05-05). 18 scenarios baseline ejecutados con 17 PASS + 1 FAIL real (Q1 weight drift, resuelto via sync). Integration tests Cl1.b validados via LLM-e2e check. Approach validado durante refactor TICKET-010 (Sessions 1-3) — detecto bug visual del CSS extract en C1, resuelto in-flight.
