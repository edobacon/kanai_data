# La asimetria entre deleteImpactPreview (siempre corre el motor) y el delete generico (gateado por hijos declarados) es intencional

## Context and problem statement

`deleteImpactPreview` corre el motor completo (`buildDeleteImpactPlan`, incluida la deteccion de referencias entrantes) para CUALQUIER objeto, declare hijos o no. El delete generico (`cascadeDeleteIfApplicable`) SI gatea por `objectDeclaresChildren`: para un objeto sin hijos declarados no invoca el motor y delega la integridad al FK constraint de la BD. Consecuencia: para un objeto sin hijos declarados pero con referencias entrantes reales, el preview devuelve `restricted` (bloquea UI/MCP) mientras el delete generico no revalida por el motor. La review de UPONE-1382 (TICKET-107, C5) pregunto si esto es un hueco o intencional.

## Decision drivers

- Fail-safe en una operacion destructiva: bloquear ante referencias reales es el comportamiento correcto/conservador para el preview (unica barrera aplicativa para consumidores como el MCP, que no ven el error crudo de la BD).
- No es hueco de integridad: el delete generico esta respaldado por el FK constraint de la BD (onDelete: Restrict), que aborta el borrado si hay referencias. La integridad NO depende del motor en ese path.
- Costo de unificar: hacer que el delete generico corra el motor para todo objeto agrega latencia a cada borrado simple sin beneficio de integridad (la BD ya protege).

## Considered options

| # | Option | Description |
|---|--------|-------------|
| A | Mantener la asimetria (documentarla) | Preview corre motor siempre; delete generico gatea por hijos + confia en FK de BD |
| B | Unificar: delete generico corre el motor para todo objeto | Simetria total preview/delete |
| C | Unificar hacia abajo: preview tambien gatea por hijos | Preview deja de bloquear objetos sin hijos declarados |

### Option A: mantener la asimetria
- **Pro**: preview fail-safe para UI/MCP (mensaje amigable ante refs reales); delete generico rapido; integridad garantizada por la BD.
- **Con**: UI/backend pueden divergir en el MENSAJE (preview bloquea con texto; delete generico dependeria del error de BD si el preview se saltara).

### Option B: unificar corriendo el motor en todo delete
- **Pro**: simetria total.
- **Con**: latencia en cada borrado simple sin beneficio de integridad (la BD ya protege); mas superficie de codigo core en el path caliente.

### Option C: preview gatea por hijos
- **Pro**: simetria.
- **Con**: pierde el fail-safe del preview para objetos sin hijos declarados pero con refs externas reales (el MCP dejaria de advertir).

## Decision outcome

**Chosen option**: A — mantener la asimetria, documentada.

**Justification**: la asimetria NO es un hueco de integridad (el FK constraint de la BD respalda el delete generico). El preview corriendo el motor siempre es un fail-safe deliberado para los consumidores aplicativos (UI/MCP) que necesitan un mensaje accionable antes de intentar el borrado. Unificar (B/C) agrega costo o pierde el fail-safe sin ganar integridad. La unica consecuencia real (divergencia de mensaje) se mitiga porque en la practica la UI y el MCP consumen el preview ANTES de disparar el delete.

## Consequences

### Positive
- Preview conserva el fail-safe para UI/MCP; delete simple sin overhead; integridad garantizada por la BD.

### Negative
- Divergencia potencial de MENSAJE entre preview (aplicativo) y delete generico (error de BD) si un consumidor saltara el preview. Backlog B7 (deteccion de FK no-convencional en el motor) reduce, si se aborda, la brecha entre lo que el preview detecta y lo que la BD restringe.
