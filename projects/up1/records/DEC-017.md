# Diferir la adaptacion cd -> OrgUnit reducido (Faculty) hasta que core reduzca el OrgUnit; cd se mantiene en el modelo que matchea el core funcionando

## Context and problem statement

DEC-016 estableció que cd se adapta al modelo reducido de engagement (Academic* -> Faculty + rol por FK + institucion via extension `rt__Faculty__OrgUnit`). TICKET-076 S1 implementó esa adaptación (aprobada por dual-judge, suite verde contra stubs). Pero S2 (validación DB-gated) destapó que **la reducción del OrgUnit NO está viva en core**:

- `object-manager/objects/business/Base/orgunit.json` (objeto core/Business, trackeado) sigue con el modelo VIEJO: `institutionId` inline + `enum OrgUnitRecordType {Geographic, AcademicGovernance, AcademicExecution}` (sin `Faculty`).
- `OrgUnit` es un objeto **core**: la plataforma rechaza que un mod le quite campos o cambie su enum ("Core objects are canonical; mods may only ADD new fields. To change a core object: `npm run model:propose`"). La def reducida que engagement declara en su mod es **inerte** — codegen lee el Base viejo y la shadowea.
- Verificado empíricamente (2026-06-22): tras `reset-tenant UPU --recreate` + `db push --accept-data-loss`, el schema sigue con el enum viejo; `orgUnit.create({recordType:'Faculty'})` es RECHAZADO por enum. Ningún reset mod-side cambia esto.

Conclusión: cd-con-Faculty no corre contra el core funcionando. La premisa de DEC-016 ("cd funcional con el modelo **actual** de engagement") fue aplicada contra el modelo **declarado** (reducido), no el **actual** (que sigue siendo el viejo). El "break" que motivó el ticket no era real en el entorno actual: cd con el modelo viejo (AcademicExecution + institutionId) corre sin problema.

## Decision drivers

- El código debe matchear el sistema que efectivamente corre, no un modelo especulativo/futuro.
- `OrgUnit` reducido es un cambio de objeto **core** (UPONE-1206), fuera del scope de un ticket mod-only.
- cd debe estar funcional HOY; no bloquearse esperando la reducción de core.
- Evitar cargar código roto contra la realidad (cd-con-Faculty falla contra el core actual).

## Considered options

### Option A: Mantener S1 (Faculty), esperar a que core reduzca
- **Pro**: cd queda forward-ready; alineado con la dirección declarada del org-spine.
- **Con**: bloqueado — no valida ni corre en DB hasta que UPONE-1206 reduzca el OrgUnit core; carga código incompatible con el core actual por tiempo indefinido.

### Option B: Revertir cd al modelo que matchea el core funcionando (elegida)
- **Pro**: cd corre HOY (validado en DB: OrgUnit AcademicExecution + institutionId, AcademicProgram resuelve, suite 746/746); mod-only; sin código roto contra la realidad.
- **Con**: cuando core reduzca el OrgUnit (UPONE-1206), hay que re-adaptar cd a Faculty (rework conocido y acotado); temporalmente va "en contra" de la dirección declarada del org-spine.

## Decision outcome

**Chosen option**: Revertir S1 (cd vuelve a `recordType: 'AcademicExecution'` + `institutionId` inline, su estado pre-ticket) y **diferir** la adaptación cd -> Faculty hasta que core efectivamente reduzca el `OrgUnit` (UPONE-1206, vía `model:propose`: quitar `institutionId`, alinear el enum con la RecordType `Faculty`, + ajustar `prisma/UPU/seed.js`).

Esto **refina DEC-016**: el principio "cd se adapta al modelo de engagement" aplica una vez que la reducción está **viva en core**; mientras la reducción sea solo declarada-pero-inerte, cd matchea el modelo **funcionando** (que hoy es el viejo). DEC-016 sigue válido como dirección; DEC-017 ajusta el *timing*.

## Consequences

### Positive
- cd funcional y validado contra el core actual (DB UPU rearmada, seed corre, AcademicProgram resuelve).
- Scope mod-only respetado: no se tocó object-manager.
- Hallazgo documentado: la reducción del org-spine quedó a medias del lado core (existe `rt__Faculty__OrgUnit` pero no el enum `Faculty`).

### Negative
- Rework futuro: cuando UPONE-1206 reduzca el OrgUnit core, la adaptación cd -> Faculty (lo que S1 implementó) habrá que rehacerla. El diff de S1 queda como referencia en la historia del ticket (commits revertidos `4e3ba5a`/`52ddb61`/`3953474`, removidos del branch por no estar pusheados).

## Confirmation

Directiva explícita del dev (2026-06-22): tras ver la evidencia de que el schema core no soporta `Faculty`, "revertir cd al modelo viejo" + "este ticket solo debe tocar el mod". Cierre del ticket como wont-do con esta decisión de diferimiento.

## Follow-up

Cuando UPONE-1206 reduzca el `OrgUnit` core (Base/orgunit.json sin `institutionId`, enum con `Faculty`), retomar la adaptación cd -> Faculty (mapeo Academic* -> Faculty + `rt__Faculty__OrgUnit.upsert(institutionId)` + rol por FK). El approach está validado a nivel diseño (S1 + dual-judge) y disponible en la historia del ticket.
