# Antes de escalar algo a core, verificar que la capacidad NO exista ya: buscar el mecanismo completo y el git log, no confiar en una función suelta ni en un comentario

## Context and problem statement

Durante UPONE-1619 se concluyó que "el motor RecordList no soporta columnas dot-path de relación → es core" y se escaló: se creó el ticket Jira UPONE-1686 (Historia, nueva capacidad opcional) para construir esa capacidad. La premisa era FALSA: la capacidad YA existía en el layout engine desde el commit `4b9bf665` (opt-in vía `visible: true`).

El error de análisis: se leyó UNA función (`applyLayoutColumnOverrides`, `RecordList.vue:7283-7298`) más un comentario obsoleto y mal atribuido (~7417), sin revisar el composable que realmente maneja el caso (`useColumnConfiguration.ts`) ni el git log de `layout`. La conclusión equivocada se propagó a un doc de followup, a un veredicto de Aduana, a drafts de core-extension y hasta a un ticket Jira creado sobre premisa falsa.

## Decision drivers

- Escalar a core (Aduana / core-extension / crear ticket) tiene costo real: un ticket de más, retrabajo de Aduana y de la redacción de la extensión, y ruido en el backlog de core.
- Un comentario en el código puede estar desactualizado o mal atribuido; la fuente de verdad es el código que corre, no el comentario.
- Una sola función rara vez representa el mecanismo completo de una feature transversal (columnas, fetch, formato viven en composables/utils distintos).

## Considered options

| # | Option | Description |
|---|--------|-------------|
| A | Verificar antes de escalar | Buscar el mecanismo completo (grep del feature en composables/utils) + `git log --grep` del feature, y recién ahí decidir si falta capacidad |
| B | Escalar sin verificar | Concluir "falta capacidad" desde una función + un comentario y abrir el ticket de core |

### Option A: Verificar antes de escalar
- **Pro**: evita tickets de core sobre premisa falsa y el retrabajo de Aduana / core-extension.
- **Pro**: el fix real suele ser mucho menor (aquí, mod-only: `visible: true`).
- **Con**: unos minutos extra de investigación antes de decidir escalar.

### Option B: Escalar sin verificar
- **Pro**: decisión rápida.
- **Con**: creó UPONE-1686 sobre una capacidad que ya existía; propagó la premisa falsa a varios artefactos; costo de reversión.

## Decision outcome

**Chosen option**: **A — verificar que la capacidad NO exista antes de escalar.** Antes de declarar "falta capacidad de core" y activar Aduana / core-extension / crear ticket:

1. Buscar el MECANISMO completo: grep del feature en composables/utils, no una sola función.
2. Revisar el historial: `git -C <workspace> log --grep <feature>` para ver si ya se implementó.
3. No confiar en los comentarios del código (pueden estar desactualizados o mal atribuidos): verificar contra el código que corre.
4. Verificar la premisa contra el código ANTES de escalar, no después.

**Justification**: el costo de escalar es alto y asimétrico frente al costo de verificar; y la evidencia mostró que la premisa era comprobable en minutos contra el código real.

## Consequences

### Positive
- El fix real de UPONE-1619 quedó mod-only (`visible: true` en las columnas de relación), sin tocar core.
- UPONE-1686 queda sin sustento: se comenta con el hallazgo y se cierra.

### Negative
- Se incurrió en el costo evitable (UPONE-1686 creado y luego cerrado) antes de establecer esta guardia.

## Confirmation

- Lo destapó una verificación en modo detective contra el código real (principios de verificar el self-report antes de declarar un hecho, y de no presentar inferencia como hecho).
- Verificación reproducible: grep del feature en `layout/src/composables/` (no en una sola función de `RecordList.vue`) + `git -C layout log --grep "relation columns"` muestran la capacidad ya mergeada.
- Criterio a aplicar en próximos escalamientos: no abrir ticket de core / core-extension sin haber corrido los pasos 1-4 y dejado la evidencia.
