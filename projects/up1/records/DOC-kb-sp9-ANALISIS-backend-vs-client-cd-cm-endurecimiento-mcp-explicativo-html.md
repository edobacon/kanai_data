Elric vs up1-mcp Integración del MCP · diseño curricular Elric vs up1-mcp Los dos resuelven el mismo dolor (un agente opera up1 con la identidad real del usuario), pero escriben las tools de forma opuesta. Este es el par a par, con código real de cada repo. Elric uplanner/mcp · TypeScript · una función por tool up1-mcp uplanner/up1 · JS declarativo · fichas + un motor 00 El modelo mental Función escrita a mano vs ficha de datos En Elric, cada tool es una función TypeScript que hace todo: valida auth, resuelve por nombre, arma el preview, llama a GraphQL y formatea la salida. En up1-mcp, la tool es una ficha (un objeto de datos) y un único motor genérico la convierte en tool real. Migrar de uno a otro no es copiar archivos: es reexpresar cada capacidad como ficha (si es simple) o como registerExtra (si tiene lógica). El escenario que planteaste Una regla client-side de un mod, sin backend. ¿La implemento también en la tool del MCP? El caso real: el mod tiene una regla que hoy solo vive en su frontend (no se pudo, o no se ha hecho, en el backend). El MCP es otro cliente y habla GraphQL directo, salteando ese frontend. Entonces la regla, para el MCP, no existe. Frontend del mod valida la regla Backend / resolver NO la valida MCP (otro cliente) la saltea, salvo que la replique Respuesta corta: sí, mientras el backend no la tenga, el MCP está obligado a replicarla , o se convierte en una puerta de escritura sin control, más peligrosa que la UI (un LLM puede crear justo la inconsistencia que el frontend evita). Eso es, exactamente, por qué existe validations.ts en Elric. Pero es una mitigación forzada, no una solución, y tiene tres costos. Frente al escenario hay tres respuestas legítimas: Opción A · Replicar Copiar la regla en la tool Lo que hace Elric. Protege el path del MCP mientras el backend no exista. Costo: la misma regla vive en 2+ lugares (frontend + MCP) y derivan. Sigue bypasseable por otros clientes. El MCP queda acoplado a la lógica del mod. Cuándo: es un invariante que corrompe datos y la escritura ya está expuesta. Obligatoria como stopgap, nunca como destino. Opción B · Declarar No replicar, exponer el hueco Lo que hace academic-scheduling: notExposed dice "el server no lo enforza todavía, deuda conocida del mod". Costo: el MCP puede producir la inconsistencia. Solo honesto, no seguro. Cuándo: la regla es menor / advisory, el riesgo es bajo, y replicar sería frágil. Nunca para una regla que corrompe. Opción C · Escalar Llevar la regla al resolver El fix real: una Core Extension que pone la validación en el write resolver, como el gate del 100%. Costo: trabajo de plataforma, dependencia de otro equipo/tiempo. Cuándo: es un invariante y existen (o existirán) otros clientes. Es el único que hace la regla real para todos. La regla de decisión: si la validación es un invariante (100%, un solo default, min≤max, máquina de estados) el destino es siempre C, el resolver. A es el puente obligatorio mientras C no está, y se paga la deuda cuando el backend cierra (ahí el resolver rechaza y la réplica del MCP pasa a ser un pre-check amable o se borra). B solo para reglas menores. Lo que nunca es correcto: dejar la regla client-side en el MCP y creer que con eso el dato está protegido. Si la replicás en A, marcala como réplica con procedencia (comentario al archivo fuente) y fijala con un test que clave la semántica, para que no derive en silencio cuando el mod cambie la regla. 08 Cerrar la puerta Réplica sola no alcanza Ya replicaste la regla en la tool de dominio (opción A del escenario). ¿Con eso el objeto está protegido dentro del MCP?
