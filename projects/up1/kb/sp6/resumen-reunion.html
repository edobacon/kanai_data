Contexto en 30 segundos

  • El cliente nos entrega un listado base de 5 puntos para SP6, sobre los objetos de la malla curricular. El alcance es ese listado — este análisis se ciñe a esos 5 puntos.
  • Cuatro de los cinco son capacidades transversales (secciones, historial, workflow, eliminación) que hay que aplicar a esos objetos; uno es funcional (requisitos de asignatura).
  • Cruzamos el listado contra el código real de core y del mod para ver qué ya existe, qué construimos nosotros, dónde chocan y cuánto cuesta cada opción.
Hallazgo central — por qué esta reunión importa

Core ya tiene un registro de cambios genérico (aplica a todos los objetos). En cambio, el motor de workflow / transiciones NO existe en core — lo construimos nosotros en el mod. La estrategia: que core sea el que regule — absorber la auditoría en el genérico que ya existe y promover el motor de workflow del mod a core — para no mantener capacidades duplicadas ni bespoke por mod.

Mostrar el
hijo origen

Requisito: en la ficha debe verse el hijo polimórfico que originó el cambio (no solo el padre) + los valores antes/después. Estado actual (verificado en código):

  • Antes/después (field/oldValue/newValue): ya se capturan y se muestran (columnas Campo / Antes / Después).
  • Hijo origen: la consolidación L40 redirige el entityType al padre Activity y guarda el hijo en sourceRef* (columnas Sección / Item). El "elemento de cambio" primario es el padre; el hijo queda como referencia secundaria.
  • Límite: esa consolidación está hardcodeada solo para CurricularSection→Activity. Para los objetos nuevos y sus hijos polimórficos (los que se definan en el punto 2), hoy no hay consolidación → el hijo origen no se mostraría.

Qué conlleva (en el mod): extender la función de consolidación (auditCapture.resolver.js) por cada relación padre↔hijo nueva + declarar las columnas del tab. No requiere componente Vue nuevo (el RecordList ya renderiza sourceRef*) — es lógica (mapping por relación) + config. Bespoke por relación → Medio.

Qué es

Hoy
El borrado hoy es físico (hard delete) genérico: deleteInstance borra ext__ + RecordType + base, con event/auth/dataLog. Config existente: onDelete (Cascade/Restrict/SetNull) por campo FK en el JSON — en toda la plataforma hay ~110 Cascade y solo 2 Restrict. Enfoque

La cascada declarativa —cada objeto declara su política de borrado por relación y un motor genérico la aplica— es la forma limpia de la opción core. Antes → después:

Hoy
  • FK reales: onDelete por campo en el JSON → lo ejecuta la BD. Ya es config-driven (ej. planEntry.categoryId = Restrict).
  • Polimórficas: sin config. Un resolver a medida (requirementCategoryDelete, override global) + categoryGuard.js cubren 1 solo caso. El resto → huérfanos.
Con config-driven (core)

  • Polimórficas: se declaran en el JSON con onDelete por relación; un handler genérico de core las aplica (Restrict / Cascade / lógico). Sin monkeypatch, sin resolver por mod, reutilizable por todos.
Ejemplo de declaración en el objeto:
"polymorphicRelations": [ { "child": "requirement", "owner": "ownerType/ownerId", "onDelete": "Cascade" }, { "child": "planEntry", "owner": "...", "onDelete": "Restrict" } ]

Esfuerzo: motor genérico (handler + schema de config) ~3-5 SP + declarar las relaciones en los 4 objetos (config, ~1-2). Multinivel + cascada lógica (soft-delete) suben desde ahí. Es la misma cifra del gap polimórfico — no es trabajo extra, es cómo se hace la opción core: declarativo en vez de monkeypatch.

Esfuerzo
Integridad (no huérfanos), factible solo-mod: ~1-2 FK Restrict/Cascade (config) + ~3-5 gap polimórfico + cascada aplicativa = ~4-7 SP.  ·  Soft-delete (opcional): core ~5-8 robusto (filtro de lectura genérico) / mod ~3-5 parcial con fuga. El soft-delete es el swing que decide si el punto es Bajo-Medio o entra al techo.
Factibilidad

Solo mod
¿hasta dónde?
  • ✓ FK reales (Restrict / Cascade) — es onDelete en el JSON de cada objeto (son del mod), honrado por core sin tocarlo. Bajo
  • ✓ pero frágil · gap polimórfico — extender el guard actual (categoryGuard.js + override de deleteInstance). Hoy ese override es un monkeypatch global; generalizarlo a todas las relaciones polimórficas sube el riesgo y sigue siendo bespoke. Medio
  • ✗ Soft-delete — techo duro — el mod puede marcar active/deletedAt en sus objetos, pero las lecturas y listados genéricos de core no conocen ese flag → seguirían mostrando el registro "borrado". Sin tocar core, el borrado lógico solo-mod queda inconsistente.

Solo-mod sí cubre la integridad (no huérfanos) con FK + guard. Lo único que exige core es el soft-delete robusto — es el único techo duro del punto.

Soft-delete
filtro de lectura

Si se hace soft-delete, las lecturas deben excluir lo borrado por defecto (deletedAt IS NULL). La pregunta es dónde vive ese filtro — y ahí está el techo:

En core — robusto ✓
  • El filtro vive en la lectura genérica (listInstances / getInstance + expansión de relaciones): el único punto por el que pasan TODAS las lecturas.
  • Incluye: convertir delete en update de deletedAt, inyectar el filtro por defecto, un arg includeDeleted para verlos, y manejar índices únicos.
  • Aplica a todos los objetos y mods.
~5-8 SP — el filtro de lectura es el grueso.
En el mod — parcial, con fuga ⚠
  • El mod solo filtra en sus propios resolvers/layouts. El camino genérico (relaciones, LayoutOrchestrator, otros mods, MCP, flows, exportes) seguiría mostrando los borrados.
  • Cerrarlo del todo exige monkeypatchear listInstances global — el mismo patrón frágil del delete, ahora en la ruta más caliente (todas las lecturas). No recomendable.
  • Precedente real — uengagement: ya usa soft-delete con un flag active (default true) + mutation custom softDeleteInstructorAvailability.
    Pro: barato, ya funciona, sin tocar core. Contra: el filtro es por-layout y manual — una vista filtra active=true, otra muestra activos e inactivos; el genérico no filtra → la fuga ya ocurre hoy.
~3-5 SP — versión parcial; no logra "por defecto" real.

Es el filtro por defecto lo que convierte al soft-delete en capacidad de plataforma. Por eso es el único techo duro del punto 5 que empuja a core — todo lo demás (integridad, no huérfanos) sí es solo-mod.

Impacto
cross-mod
  • Protección FK ya es global — referenceValidationService escanea todos los modelos al borrar cualquier objeto. Un cambio en curriculum-design no altera esto; ya afecta/beneficia a todos.
  • Cascade ya es el patrón dominante — 110 usos en uengagement / academic-scheduling. Declarar Cascade/Restrict en nuestros objetos es consistente, sin sorpresas para otros mods.
  • Handler polimórfico en core = opt-in por config — los mods que no declaren relaciones polimórficas siguen igual (cero impacto); los que sí (uengagement, academic-scheduling también tienen polimórficas) ganan protección al declararlas.
  • Riesgo — es ruta compartida: el handler debe gatear por presencia de config (sin declaración → skip) para no añadir latencia ni cambiar el comportamiento de deletes existentes.
Fuente
⚠️ No existe capacidad de eliminación en el catálogo Confluence (CAP-CUR). El patrón documentado es desactivar, no borrar (secciones/catálogos "no eliminables"). Confirmar de dónde sale este punto y si se refiere a desactivación.
Decidido
(reunión)
Hard delete, foco en integridad (no huérfanos) con cascada de hijos polimórficos en core, transversal. Soft delete descartado (capacidad core futura). Pendiente fino: por cada relación, Restrict vs Cascade.
Es un fix, no una feature. El hard delete genérico ya existe en core (deleteInstance + protección de FK reales automática). Que borrar estos objetos deje huérfanos polimórficos es un hueco/bug a cerrar (declarar onDelete + manejo polimórfico), no una capacidad nueva a construir. Si un borrado esperado no funciona, es error a corregir.
Nota: los facets de soft-delete de abajo quedan como contexto — ya no son alcance de SP6.
Mod · sin colisión Config / parcial · bajo costo Decisión de core / migración
Conclusión de factibilidad — post reunión

La reunión resolvió el rumbo: las tres transversales van a core (historial → DataLog, workflow → re-crear sobre el enum de core, eliminación → hard delete + cascada polimórfica transversal). El análisis técnico se mantiene: casi todo es alcanzable desde el mod, pero core aporta alcance de plataforma y robustez, y evita los parches (monkeypatch) en las rutas calientes. El soft-delete queda fuera de alcance (capacidad core futura). Los puntos finos que restan son de ubicación de config (estados permitidos para versionar → JSON) y alcance (qué secciones por entidad; Restrict vs Cascade por relación), más la confirmación con Klaus de qué está planificado en core.
