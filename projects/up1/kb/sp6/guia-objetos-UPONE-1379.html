Orientación

02

Contexto

Qué es UP1

UP1 (uPlanner One) es una aplicación multi-tenant y modular para instituciones educativas, construida como un monorepo de npm workspaces. Integra proyectos independientes (los mods) sobre una plataforma común.

El flujo de dependencia entre workspaces es lo primero que conviene fijar, porque un cambio de objeto atraviesa todos ellos:

Modscurriculum-design, …
→
Object ManagerAPI GraphQL · Prisma
→
Layoutcomponentes Vue
→
Suitefrontend Nuxt
WorkspaceRolStack
object-manager/Backend: API GraphQL, fuente de la BDNode, Express, Apollo, Prisma, PostgreSQL
layout/Librería de componentes UI (Atomic Design)Vue 3, Bootstrap 5, Vueform
suite/Frontend principal (lo que ve el usuario)Nuxt 4, Vue 3, Auth0
flow/Motor de workflows (fork de n8n)n8n
mods/Módulos autocontenidos que extienden UP1JSON + Vue + resolvers
Multi-tenant

Una sola base de datos con aislamiento por aplicación. El tenant viaja en el header X-Tenant-ID y la URL sigue el patrón /{tenant}/{objeto}/{layout}. Regla de oro: toda query filtra por tenant. El entorno de prueba del mod es el tenant UPU.

Dónde vive lo que toca el 1379

El ticket es de tipo “mod (config)”: casi todo el trabajo ocurre dentro del mod curriculum-design, no en el core. Su ubicación real es:

El curriculum-design que importa vive en uplanner/up1/mods/, no en el Workspace/up1 donde suele abrirse el core. Confirma siempre la ruta antes de editar.

03

Concepto central

Qué es un “objeto”

Un objeto es un archivo JSON que describe una entidad de negocio. Ese JSON es la fuente de verdad: de él se derivan la tabla de la base de datos, los tipos de GraphQL y hasta cómo se dibuja en la UI.

Esto se llama desarrollo schema-driven: no escribes el modelo Prisma ni el schema GraphQL a mano — describes el objeto en JSON y un generador (codegen) produce el resto. Entender este pipeline es la clave de todo el ticket.

1
Definición JSONmods/<mod>/objects/*.json — lo único que edita el dev
2
npm run synccopia los artefactos del mod hacia los workspaces core (objects, resolvers, componentes, lang…)
3
npm run codegenlee los JSON y genera prisma/schema.prisma + graphql/typeDefs/dynamic.js (autogenerados — nunca se editan a mano)
4
prisma migrateaplica el schema a PostgreSQL (por tenant)
5
Layout + Suiteel LayoutOrchestrator lee configuraciones de layout y renderiza el objeto como lista o detalle
Regla crítica

Nunca edites archivos autogenerados (schema.prisma, dynamic.js) ni los archivos sincronizados dentro de los workspaces core (p. ej. suite/modsComponents/). El cambio siempre nace en el mod y se propaga con sync + codegen.

04

Estructura

Anatomía de un objeto JSON

Todo objeto es un JSON Schema (draft-07) con unas pocas claves de nivel superior. Este es un objeto real del core, anotado:

objects/business/Base/Service.jsonjson
{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "title": "Service",          // nombre del objeto (PascalCase)
  "type": "object",
  "metadata": {              // etiquetas y config de UI (ver §06)
    "label": "Servicio",
    "labelPlural": "Servicios",
    "gender": "masculino",
    "description": "Servicio ofrecido por la institución",
    "defaultLayoutType": "RecordList"
  },
  "properties": {            // los campos del objeto (ver §05)
    "name": {
      "type": "string",
      "title": "Name",
      "not_null": true,
      "transformations": [{ "type": "trim" }]
    }
  },
  "required": ["name"]   // campos obligatorios
}
ClaveQué es
$schemaSiempre JSON Schema draft-07.
titleNombre del objeto en PascalCase. Da nombre a la tabla y al tipo GraphQL.
typeSiempre "object".
metadataEtiquetas visibles, género gramatical, layout por defecto.
propertiesDiccionario de campos; cada uno con su tipo y atributos.
requiredNombres de campos obligatorios a nivel de validación.

"integer"Intconteos, position
"number"Float / Decimalpesos, horas, notas

"string" + formatDateTime / Datedate, date-time, time

UI declarativa

Metadata (estilo Salesforce)

El bloque metadata es lo que hace que un objeto se “presente” bien sin escribir UI. Aporta etiquetas legibles, género gramatical (para armar textos en español), descripción y el tipo de layout por defecto.

Verás esto en el ticket

El nuevo RecordType GraduationProfile del 1379 trae exactamente este bloque: label: "Perfil de egreso", labelPlural: "Perfiles de egreso" y su description. Ahora sabes de dónde sale y qué hace.

07

Composición

Base · Extended · common

Los objetos se organizan en tres capas que se combinan:

Base

objects/business/Base/*.json — PascalCase. La estructura fundamental del objeto, fuente de la tabla Prisma.

Extended

ext__<CLIENTE>__<objeto>.json — agrega campos específicos de un tenant sin tocar el base (vía allOf con $ref).

common.json inyecta en todos los objetos los tres campos de sistema: id, createdAt, updatedAt. No necesitas declararlos.

objects/business/common.jsonjson
"properties": {
  "id":        { "type": "string" },
  "createdAt": { "type": "string", "format": "date-time" },
  "updatedAt": { "type": "string", "format": "date-time" }
}
08

Especialización

RecordTypes

Un RecordType es un subtipo de un objeto base: reutiliza su tabla y le agrega campos propios. Es el mecanismo que permite que un mismo objeto (p. ej. CurricularSection) tenga variantes tipadas.

Convención de archivo: rt__<RecordType>__<baseObject>.json. A diferencia de Extended, no usa allOf: declara su padre con la clave baseObject.

objects/RecordTypes/rt__LearningOutcome__curricularsection.jsonjson
{
  "title": "LearningOutcome",
  "baseObject": "CurricularSection",   // ← el padre
  "metadata": {
    "label": "Resultado de aprendizaje",
    "labelPlural": "Resultados de aprendizaje"
  },
  "properties": {                     // campos SOLO de este subtipo
    "code": { "type": "string" },
    "bloomLevel": {
      "type": "string",
      "enum": ["Remember","Understand","Apply",
               "Analyze","Evaluate","Create"]
    }
  }
}

En la base de datos, cada RecordType se materializa como una tabla propia (rt__LearningOutcome__curricularsection) unida al base por curricularsectionId. Guárdate este detalle: será relevante cuando veas cómo se actualizan (§13).

09

Flujo de trabajo

El pipeline: codegen y sync

Después de tocar cualquier JSON de objeto, hay un orden de comandos que respetar. Saltárselo produce el clásico “el objeto no aparece” o “la columna no existe”.

# 1 · propaga los artefactos del mod al core
npm run sync

# 2 · regenera schema.prisma + typeDefs GraphQL desde los JSON
npm run codegen --workspace=@uplanner/object-management-backend

# 3 · aplica el schema a PostgreSQL (por tenant)
npx prisma migrate dev
Sync canónico

Ante un desajuste de schema, la solución nunca es un ALTER TABLE manual ni un db push quirúrgico. Siempre se valida el flujo completo codegen → sync → migrate. Un reset destructivo requiere consentimiento explícito.

Y la Definition of Done del propio 1379 lo refuerza: tests verdes · lint + Prettier + tsc limpios · lang ES completo · sin artefactos de sync/seed commiteados · tools up1-mcp actualizadas · quality review + smoke en UPU.

Configuración

La config de Layout (JSON)

Los layouts también son JSON: viven en config/layouts/ del mod y se guardan en la tabla up1_layen_layout. Nombre por convención: default_{Objeto}_{modo} (p. ej. default_Activity_view).

Este es el fragmento que declara una sección embebida dentro del detalle de Activity — la estructura que tendrás que reconocer y replicar para Curriculum/Offering:

config/layouts/default_Activity_view.json (recorte)json
"modalitiesList": {
  "type": "record-list",               // campo que embebe una lista
  "objectName": "CurricularSection",
  "layoutConfig": {
    "relations": ["rt__Modality__curricularsection"],
    "columns": [ /* name, code, deliveryMode, hours… */ ],
    "filters": [
      { "field": "ownerId",    "operator": "EQUALS", "value": "{{parentId}}" },
      { "field": "recordType", "operator": "EQUALS", "value": "Modality" }
    ],
    "order": { "field": "position", "direction": "ASC" }
  }
}
PiezaQué hace
type: "record-list"Convierte un “campo” del formulario en una tabla embebida.
filters + {{parentId}}El orquestador reemplaza {{parentId}} por el id del registro padre, así la lista solo muestra sus hijos.
relationsTrae los campos del RecordType (join con la tabla rt__…).
rowActionsBotones por fila con RBAC (requiredCapability) y condiciones de visibilidad.
associatedLayoutConfigsEnlaza el layout de view/edit del hijo al hacer click en la fila.
12

Permisos

RBAC y capabilities

El control de acceso es jerárquico y por objeto. Cada mod declara sus permisos en capabilities.json. Hay dos niveles:

  • Object-level: objeto:view, objeto:create, objeto:edit, objeto:delete.
  • Field-level: objeto.campo:view, objeto.campo:edit (cuando falta permiso a nivel de objeto).
mods/curriculum-design/capabilities.json (recorte)json
{
  "name": "curricularsection:audit",
  "description": "Ver el tab Historial… aplica a todos los subtipos polimórficos",
  "riskLevel": "low"
}

Fíjate en el patrón: una capability de curricularsection:* cubre todos los RecordTypes polimórficos por igual. El criterio de aceptación del 1379 pide precisamente definir en capabilities.json los permisos de ver/editar las secciones que se declaren.

El corazón del ticket

Secciones polimórficas

Aquí converge todo. Una “sección” de un documento curricular es una fila de CurricularSection que apunta a su dueño mediante una FK polimórfica y se tipa con un RecordType.

El objeto CurricularSection

Un solo objeto sirve para todas las secciones de todos los documentos. Sus campos clave:

Los 7 RecordTypes que hoy tiene Activity.

Cómo un objeto “declara” sus secciones

Un objeto expone sus hijos polimórficos con la clave metadata.polymorphicChildren. Esta es la declaración real de Activity — y es la única que existe hoy:

mods/curriculum-design/objects/Activity.jsonjson
"polymorphicChildren": [
  {
    "name": "sections",                 // nodo en la query GraphQL
    "object": "CurricularSection",
    "via": "ownerType/ownerId",         // la FK polimórfica
    "ownerTypeValue": "Activity",       // discrimina los hijos de este dueño
    "recursiveBy": "parentId"          // habilita el árbol
  }
]

El resolver readPolymorphicChildren (existente, no se crea uno nuevo) lee esta declaración y resuelve las secciones. El estado de partida es asimétrico:

✓ Activity

Ya declara polymorphicChildren y muestra sus 7 secciones. Es el patrón de referencia.

✗ Curriculum · Offering

Hoy no declaran polymorphicChildren. Offering solo tiene activityId, recordType, termId. Ese es el hueco que el ticket cierra.

Detalle de implementación que conviene entender

Cada RecordType es una tabla propia unida al base por curricularsectionId (no tiene id propio). Por eso existe logic/polymorphicUpdate.resolver.js: al actualizar, hace pre-fetch por el base CurricularSection, separa el payload en base / rt__ / extensiones y ejecuta varios writes. No necesitas replicarlo, pero saber que existe explica muchas rarezas.

Cómo se siembran (seeds)

Los seeds crean primero la fila base y luego la fila del RecordType. Patrón real del seed de Univalle:

mods/curriculum-design/seed/_data-univalle.js (recorte)js
// 1 · fila base
const section = await prisma.curricularSection.create({ data: {
  ownerType: 'Activity', ownerId: programa.id,
  recordType: 'Modality', name: 'Modalidad Presencial', position: 1
} });
// 2 · fila del RecordType, unida por curricularsectionId
await prisma.rt__Modality__curricularsection.create({ data: {
  curricularsectionId: section.id,
  code: 'PRES', theoryHours: 4, deliveryMode: 'InPerson', isDefault: true
} });

Síntesis

El ticket 1379 en contexto

Ya tienes todas las piezas. El 1379 pide replicar por configuración el mecanismo de secciones que Activity ya tiene, llevándolo a Curriculum (Plan) y Offering (Syllabus), y estrenar un RecordType nuevo: GraduationProfile (Perfil de egreso).

La historia, en una frase

“Como dev del mod, quiero declarar por configuración las secciones (hijos polimórficos) de Curriculum y Offering replicando las de Activity, para que tengan la misma estructura sin construir un motor.”

Los tres frentes

EnumCurricularSection.ownerType pasa a incluir "Curriculum": ["Activity","Offering","Curriculum"].
CurriculumEstrena 1 RecordType nuevo: GraduationProfile (Perfil de egreso). Lo declara en polymorphicChildren + layout. Único por currículo.
OfferingEspejo 1:1 de Activity: declara los mismos 7 RecordTypes (LearningOutcome, EvaluationComponent, Content, Session, Modality, Bibliography, CustomSection).

En alcance (SP6 · v1)

Secciones por configuración del dev. sectionType = STRUCTURAL. Un solo GraduationProfile por currículo. Capabilities en capabilities.json. Seed de ejemplo (Ing. Civil 2026). Tools MCP cd_*_section operando sobre Curriculum y Offering.

Fuera de alcance / diferido a v2

El usuario final no crea ni edita secciones desde la UI en SP6. Diferido y solo documentado: GraduationProfileItem (Composite), EntryProfile, y el binding formal graduationProfileMapping a la matriz de competencias.

No-regresión

Un criterio explícito: una entidad sin secciones declaradas debe seguir sin mostrar secciones. Al tocar el enum ownerType y los objetos compartidos, el riesgo de romper Activity (que ya funciona) es real. Offering además es compartido con uengagement — recuerda el análisis de impacto colateral.

Antes de escribir código

Guía de estudio y mapa

No hay implementación aquí — a propósito. Estas preguntas te dicen si ya entendiste lo suficiente para diseñar la solución tú mismo. Si dudas de alguna, vuelve a la sección indicada.

  • ¿Sabrías leer el polymorphicChildren de Activity y explicar cada clave sin mirar? (§13)
  • ¿Por qué el ticket dice “sin construir un motor”? ¿Qué mecanismo ya existe y solo hay que declarar? (§13)
  • ¿Qué archivos concretos tocarías para agregar "Curriculum" al enum ownerType, y qué comando regenera el schema? (§05, §09)
  • ¿Cómo verificarías que Offering muestra sus 7 secciones en la UI real, no solo en la config? (§10)
  • ¿Qué consumidores tiene CurricularSection y qué podría romper cambiar su enum? ¿Quién más usa Offering? (§14)
  • ¿Dónde declararías las capabilities de las nuevas secciones y con qué patrón de nombre? (§12)
Verificar el render real

La UI de UP1 es config-driven y filtra columnas a campos reales del objeto. No cierres “por config + BD + unit”: corre el smoke en UPU y confirma que las secciones se dibujan de verdad, o deja un bloqueo honesto.
