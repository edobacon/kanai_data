Términos que aparecen en toda la presentación

Si algun término te suena extraño, aqui esta su definicion rapida para que no asumamos nada.

monorepo
Repositorio unico que contiene varios paquetes (workspaces) relacionados. UP1 tiene 5 workspaces npm en el mismo repo.
workspace
Un paquete npm dentro del monorepo. Ej: @uplanner/suite, @uplanner/object-management-backend.
tenant
Cliente/institucion que usa la plataforma. Los datos de cada tenant estan aislados por un tenantId.
GraphQL
API alternativa a REST. El cliente pide exactamente los campos que necesita en una sola query.
Prisma
ORM (Object-Relational Mapper) — traduce operaciones de JavaScript a SQL. prisma.user.findMany() → SELECT * FROM user.
codegen
Proceso que genera código automáticamente a partir de una fuente declarativa. En UP1: JSON → Prisma schema + GraphQL types.
Nuxt
Framework Vue.js para apps con routing, SSR y build automaticos. La Suite corre en Nuxt 4.
Vueform
Libreria de formularios para Vue. Permite definir inputs custom via defineElement(). Se usa para los "custom elements" de UP1.
Apollo Client
Cliente GraphQL para el frontend. Hace queries, cachea resultados, reactiva la UI al recibir datos.
composable
Funcion JavaScript que encapsula logica reutilizable en Vue 3 (Composition API). Equivalente a un "hook" de React.
n8n
Motor de workflows visuales (no-code). UP1 usa un fork personalizado para orquestar flujos async.
BullMQ
Cola de tareas async sobre Redis. Permite procesar eventos en background sin bloquear la UI.

· SECCION 00 ·

¿Qué es UP1?

Una plataforma multi-tenant modular para instituciones educativas.
Un solo deploy sirve a múltiples clientes, con mods como extension.

La idea central

UP1 = core extensible + mods autocontenidos

UP1 esta diseñado bajo tres decisiones de arquitectura que se refuerzan mutuamente. Entenderlas es entender UP1.

🏢
Multi-tenant
Un solo despliegue sirve a N instituciones. Aislamiento por tenantId a nivel de aplicacion (no de BD).
🧩
Modular
Los mods extienden el sistema sin modificar el core: agregan objects, layouts, logic, i18n, styles.
📐
Schema-driven
JSON define el modelo. El codegen genera Prisma + GraphQL + API automáticamente — no se escribe SQL ni endpoints.
Contexto para las siguientes preguntas
Estas tres decisiones tienen consecuencias practicas que no son obvias al principio: como se aislan los datos, por qué los mods viven en su propia carpeta, y por qué no escribes SQL. Las preguntas desempacan esas consecuencias.
Preguntas para entender el porqué
¿Qué significa "multi-tenant a nivel de aplicacion" y por qué importa?
Significa que todas las instituciones comparten la misma base de datos y el mismo deploy. No hay una BD por cliente. El aislamiento esta en la capa de aplicacion: cada tabla lleva una columna tenantId, cada request GraphQL lleva el header X-Tenant-ID, y cada query filtra por tenantId antes de devolver resultados.

Por qué importa: un solo deploy sirve a 10, 50 o 500 clientes. Ahorra infraestructura, permite actualizar a todos a la vez, y concentra el esfuerzo de desarrollo. Pero si olvidas el filtro por tenantId en un resolver, los datos de un cliente se exponen a otro — por eso toda query DEBE filtrar por tenantId, sin excepcion.
¿Por qué los mods no pueden editar archivos del core directamente?
Para que core y mods evolucionen de forma independiente. Los mods viven en mods/{nombre}/ y un proceso llamado sync copia sus artefactos a las carpetas del core donde hacen falta.

Beneficio: puedes actualizar el core sin que se rompa un mod, y desinstalar un mod sin contaminacion. Si los mods editaran el core directamente, cada actualizacion del core seria un nightmare de merge conflicts.
¿Qué significa "schema-driven"? ¿Qué obtengo gratis?
Que el modelo de datos se escribe en archivos JSON — no en SQL, no en Prisma schema a mano, no en TypeScript. Un comando (npm run codegen) lee esos JSON y genera:
  • El schema Prisma (tablas, columnas, constraints)
  • Las migraciones SQL
  • Los types GraphQL
  • Las queries y mutations CRUD (create, read, update, delete) automaticas
Lo que obtienes gratis: sin escribir una linea de codigo ves una API GraphQL funcional. Solo escribes resolvers custom para lo que va mas alla del CRUD (ej: un workflow, un calculo especial).

Cómo se conectan estas piezas
Cuando un usuario entra a la Suite (:3000), la pagina resuelve que layout cargar y llama al Object Manager (:4000) via GraphQL. El Object Manager valida que el usuario tenga permisos, filtra por tenant, y consulta PostgreSQL via Prisma. La respuesta viaja de vuelta hasta el componente Vue que la muestra.
# Flujo de una request tipica Usuario → Suite :3000 # el navegador ↓ LayoutOrchestrator # decide que mostrar ↓ lee layout JSON (guardado en DB) ↓ GraphQL query → Object Manager :4000 # API publica ↓ valida permisos + filtra por tenantId ↓ Prisma → PostgreSQL # BD real
Preguntas para fijar
¿Por qué el frontend no habla directo a Prisma / a la BD?
Porque Prisma es un ORM interno del Object Manager — le da acceso directo a la BD sin validaciones. Si el frontend hablara con Prisma, cualquier usuario podria leer/modificar cualquier tabla.

En cambio, GraphQL es el contrato publico: aplica permisos (withAuth), filtra por tenant automaticamente y solo expone lo que la aplicacion permite. Esta es la razon de separar backend y frontend.
¿Qué es el LayoutOrchestrator y por qué siempre se menciona?
Es el componente Vue del core que siempre esta entre la URL y lo que se renderiza. Suite no llama directo a RecordList o RecordDetail — le pasa al orquestador la URL, este lee de la BD el layout JSON correspondiente, y decide que componente montar segun el campo layoutType.

Es como un router universal: una sola pieza resuelve list, detail, create, filtros, permisos.

Los 5 conceptos que vas a ver mil veces

Estos cinco sustantivos aparecen en cada archivo, cada comando y cada slide que viene. Si los tienes claros, el resto fluye.

Object
Qué es: una entidad de negocio (Persona, Matriz, Curso) definida como JSON.
De dónde sale: tu lo escribes en objects/MiObjeto.json.
Qué produce: una tabla en la BD + queries/mutations GraphQL automaticas.
Layout
Qué es: configuracion JSON de una vista (un listado, un detalle, un formulario).
De dónde sale: tu lo escribes en config/layouts/mi-vista.json.
Qué produce: el LayoutOrchestrator lo lee y renderiza la UI.
Mod
Qué es: una feature autocontenida — una carpeta con su modelo, vistas, permisos y logica.
De dónde sale: tu lo creas en mods/mi-mod/.
Qué produce: al correr sync, su contenido se integra al core.
Capability
Qué es: un permiso granular con formato mod/mi-mod:accion.
De dónde sale: lo declaras en capabilities.json del mod.
Qué produce: controla quien puede ejecutar resolvers, ver botones o abrir vistas.
Tenant
Qué es: cada institucion cliente (UPU, DEMO, EAFIT...).
De dónde sale: se extrae de la URL — /{tenantId}/....
Qué produce: aislamiento de datos: cada registro lleva tenantId, cada query filtra por él.

Entrando a la seccion de mods

¿Qué es un mod, concretamente?

Un mod es una carpeta (si, literal, una carpeta) que contiene todo lo necesario para agregar una feature a UP1. Nada mas. Nada menos.

📂
Es autocontenido
Todo lo que el mod aporta — modelo, UI, logica, permisos, traducciones — vive dentro de mods/mi-mod/.
🔌
Se enchufa al core
El comando npm run sync copia los archivos del mod a los lugares del core que los consumen.
📦
Es opcional
Cada mod se puede instalar o no. Cada cliente puede tener un subset distinto de mods activos.
Qué cosas se agregan via un mod
Un mod puede aportar cualquier combinacion de estos 10 tipos de artefacto: objects (modelo de datos), layouts (vistas JSON), resolvers (logica GraphQL), components (widgets Vue custom), composables (logica JS reutilizable), traducciones, CSS, capabilities (permisos), seeds (datos iniciales), y events/flows (procesos async).

No todos los mods usan los 10 — un mod simple puede tener solo 1 object + 2 layouts.
Lo mínimo para tenerlo vivo

Un mod funcional con 3 archivos

Antes de ver el árbol completo, aqui esta lo minimo indispensable: si creas esta estructura, el mod se carga y aparece en el sidebar. El resto es incremental.

REQmods/mi-mod/package.json
Lo registra como workspace npm. Debe tener "name": "@uplanner/mod-mi-mod". Sin este archivo, el monorepo no lo ve.
REQmods/mi-mod/capabilities.json
Declara los permisos del mod. Puede ser un array vacio [] si el mod no define permisos propios. Requerido aunque este vacio.
REQmods/mi-mod/config/app.json
Registra el mod en el sidebar de la Suite. Define name, label, icon y en qué tenants es visible.
optmods/mi-mod/objects/MiObjeto.json
Si el mod necesita su propio modelo de datos. Genera tablas via codegen.
optmods/mi-mod/config/layouts/*.json
Si el mod tiene vistas propias (RecordList, RecordDetail).
optmods/mi-mod/lang/es_CL.json
Si el mod tiene labels o mensajes traducibles.
Flujo mental para empezar
1) Crear los 3 archivos REQ → 2) correr npm run sync → 3) el mod ya aparece en el sidebar (vacio) → 4) ir agregando objects, layouts, resolvers segun lo que necesites → 5) hacer sync entre cada cambio.

Preguntas antes de seguir

Lo que se pregunta todo el que empieza

Antes de responder: tres decisiones fundamentales
Al crear un mod, las dos primeras dudas que aparecen son: (1) ¿qué va al mod y qué al core?, y (2) ¿puedo tocar el core si lo necesito?. La tercera es ¿qué tipos de cosas puede aportar un mod?. Las respuestas definen el estilo con que vas a desarrollar toda tu vida en UP1.
¿Qué va al core y qué va a un mod?
Al core van las entidades y componentes compartidos por todos los tenants y features: Person, Faculty, Course, y los componentes base (RecordList, RecordDetail).

Al mod va cualquier feature vertical: un nuevo flujo de negocio, un dashboard especifico, una coleccion de objects con su UI.

Regla practica: si un futuro cliente podria NO querer esto instalado, entonces va a un mod.
¿Puedo modificar archivos del core desde un mod?
No. Un mod solo escribe en mods/{mi-mod}/. El proceso npm run sync se encarga de copiar sus artefactos a los destinos correctos del core.

Editar directamente en suite/modsComponents/, suite/lang/ o similares es un antipatron: el proximo sync sobrescribe tu cambio sin avisar. Si el core necesita un cambio, se hace en el workspace del core y pasa por su propia review.
¿Qué es el "sync mechanism" y por qué es tan critico?
Es el proceso que copia artefactos desde mods/{mi-mod}/ a los workspaces del core que los necesitan. Se ejecuta con npm run sync y corre 8 fases secuenciales:
  • Mirror — copia archivos simples (CSS, componentes, lang)
  • Merge — combina archivos que varios mods aportan (ej: traducciones)
  • Capabilities — registra permisos en la BD
  • Logic — integra resolvers al GraphQL
  • Apps & Layouts — inserta/actualiza layouts en up1_layen_layout
  • Default Layouts — aplica layouts por defecto por objeto
  • Seeds — ejecuta seeds de datos iniciales
  • Prisma Schema — actualiza el schema con los objects del mod
Despues de cualquier cambio en un mod, sync es obligatorio — sin el, el core no ve el cambio.

Fijacion del ciclo de desarrollo

Preguntas sobre el ciclo sync→codegen→migrate

El ciclo en una frase
Casi todos los bugs de un mod novato vienen de saltarse uno de los pasos del ciclo: editar el mod → sync → (si tocaste objects) codegen → (si genero migracion) prisma migrate → verificar. Las preguntas cubren los casos mas comunes.
¿En qué orden se ejecutan los comandos tras modificar un mod?
Depende del cambio:
  • Solo layouts o i18n: npm run sync
  • Nuevo/modificado object: sync → codegen → prisma migrate dev
  • Nuevo custom element .vue: sync + reiniciar dev server de Suite (primera vez, para que Vueform lo detecte)
  • Seeds: npm run seed tras sync
¿Cómo se registra una capability y cómo se usa?
Se declara en capabilities.json con formato mod/{mod}:{action}. Se usa en tres lugares:
1. Resolver: withAuth(['mod/mi-mod:manage'], resolver)
2. Row action: "requiredCapability": "mod/mi-mod:delete"
3. Layout/app: "roles": ["Admin"]
Mi custom element no aparece. ¿Qué pasó?
Revisa:
  • El archivo se llama MiNombreElement.vue y exporta defineElement
  • Hay un solo .vue por carpeta (sync rechaza subcarpetas con .vue)
  • Corriste npm run sync
  • Reiniciaste el dev server de Suite (import.meta.glob se evalua al bootstrap)
  • El type en el layout coincide con el kebab-case del name del element (sin "Element")
¿Cómo registrar el mod en el sidebar de la Suite?
En config/app.json: campos name, label, icon, order, tenants, defaultObjects. Cada entrada de defaultObjects es un tab del sidebar que apunta a un layout de listado.

El modelo es el cimiento

JSON es la fuente de verdad.
Cada decision del modelo genera un patron de UI mas adelante.

Principio fundamental

De un JSON sale toda la infraestructura

Este es el JSON que define una entidad de negocio. Sin escribir SQL ni Prisma a mano, este archivo produce una tabla en BD, una API GraphQL completa y las validaciones.

// objects/MiObjeto.json { "title": "MiObjeto", 1 "metadata": { 2 "label": "Mi Objeto", "gender": "masculino" }, "properties": { 3 "code": { "type": "string", "not_null": true, 4 "unique": true 4 }, "name": { "type": "string", "not_null": true }, "status": { "type": "string", "static_default": "DRAFT" 5 }, "otroObjetoId": { 6 "type": "string", "isForeignKey": true, "references": "OtroObjeto" } } }
1
title: nombre del object (PascalCase). Debe coincidir con el nombre del archivo. Aparecera como prisma.miObjeto y como type en GraphQL.
2
metadata: info "humana" del objeto — etiqueta visible (label), plural (labelPlural), genero gramatical (para i18n correcto).
3
properties: las columnas. Cada propiedad es un campo de la tabla. Los tipos usan JSON Schema (string, number, boolean, date-time).
4
not_null y unique: constraints que se traducen a NOT NULL y UNIQUE en la tabla.
5
static_default: valor por defecto si no se pasa al crear el registro.
6
isForeignKey + references: crea una relacion con otra tabla. GraphQL expondra otroObjeto { ... } para navegar la relacion automaticamente.

Donde vive un object

Las tres ubicaciones posibles

🌍
business/Base/
Core del dominio educativo compartido: Person, Institution, Course.
Criterio: todos los tenants lo usan con el mismo shape.
🏛️
tenants/{T}/Base/
Core pero distinto por tenant: Faculty, Course del tenant UPU.
Criterio: existe en todos los sistemas pero con variaciones.
🧩
mods/{mod}/objects/
Feature especifica del mod: CaCompetencyMatrix, RetentionCase.
Criterio: funcionalidad agregada.

Ademas: business/Extended/ext__<TENANT>__<obj>.json para agregar campos a un Base sin duplicarlo. Genera una tabla 1:1 que el codegen une transparentemente.

Herencia y relaciones

Qué NO declaras y cómo referenciar otra entidad

Dos temas cruzados: los campos que vienen gratis (no hay que escribirlos) y las tres formas de "apuntar" a otra entidad. Cada forma tiene su caso de uso.

Common fields — heredados

// objects/business/common.json { "id": "string", "createdAt": "datetime", "updatedAt": "datetime", "tenantId": /* auto */ }

Tres formas de referenciar

A
FK directa (mismo scope)
isForeignKey + references. Mod → mod. Crea FK real en DB.
B
publicId + denormalizacion
Cross-mod / cross-scope. Guarda ID + snapshot del nombre.
C

Agregar campos a un Base existente sin tocarlo.
Por qué hay tres formas — no una sola
Las tres formas no son equivalentes, responden a problemas distintos. FK directa es lo natural cuando la relacion es tight y esta en el mismo scope. publicId + denormalizacion aparece cuando cruzas scopes (mod → core) para evitar dependencias rigidas. Extended es para "esta entidad existe y quiero mas columnas solo para un cliente". Las preguntas aclaran cuándo usar cada una.
¿Por qué no uso FK directa siempre?
Porque cruzar mods con FK directa genera dependencia rigida entre mods: si el mod B se desinstala o cambia una entidad, el mod A se rompe. Ademas imposibilita tener mods opcionales.

Con publicId + campo denormalizado (ej: facultyPublicId + facultyName) cada mod es autonomo. Ademas, el nombre denormalizado funciona como snapshot historico: si la Facultad cambia de nombre, el registro mantiene el nombre que tenia al momento de crearse.
¿Cuándo uso Extended en vez de un object nuevo?
Cuando solo necesitas agregar columnas a una entidad que ya existe, y solo para un cliente. Ejemplo: Faculty en el core ya existe; UPU necesita un campo accreditationCode propio. Creas ext__UPU__faculty.json con ese campo.

Qué pasa bajo el capo: se genera una tabla ext__UPU__faculty aparte, con FK 1:1 a Faculty. El codegen las une transparentemente: en el type GraphQL de Faculty del tenant UPU, aparece accreditationCode; en otros tenants no existe.

Antes de las preguntas — qué hay que tener claro
Dos conceptos claves aparecen arriba y son los que mas confunden al inicio: el placeholder {{parentId}} y el type custom (ej: competency-tree). Las preguntas los desempacan.
¿Qué es exactamente {{parentId}}?
Un placeholder dinamico. Cuando renderizas el detalle de una matriz de ID abc123, el LayoutOrchestrator reemplaza {{parentId}} por abc123 antes de ejecutar la query de la sublista.

Por qué importa: la sublista facultiesList usa ese ID como filtro, asi que solo muestra las facultades de esta matriz. Sin el placeholder, mostraria todas las facultades de todas las matrices mezcladas.
¿Qué pasa si pongo un type custom que no existe?
El campo no se renderiza (aparece vacio o con error en consola). El LayoutOrchestrator busca los custom elements en modsComponents/ usando import.meta.glob. Si no encuentra uno con ese nombre, falla silenciosamente.

Checklist si no aparece:
  • El type es el kebab-case del name del defineElement(), quitando "Element". Ej: CompetencyTreeElement → competency-tree.
  • Corriste npm run sync despues de crear el .vue.
  • Reiniciaste el dev server de Suite (el import.meta.glob se evalua al arranque).
  • La estructura es correcta: un .vue por carpeta, sin subcarpetas con mas .vue dentro.

Preguntas sobre las capas de personalizacion

El espiritu detras de las preguntas
Todas las preguntas giran sobre un mismo principio: la personalizacion por cliente NUNCA es codigo condicional. Siempre es JSON declarativo. Si te encuentras escribiendo if (tenantId === 'UPU'), hay una capa de config que estas ignorando.
¿Cómo oculto un mod a un cliente?
En config/app.json, declara tenants: ["UPU"]. El mod solo aparece en el sidebar de ese tenant. Si omites el campo o usas ["*"], aparece en todos. La tabla up1_layen_application en DB tendra filas solo para los tenants declarados tras el sync.
¿Dos clientes pueden ver columnas distintas en la misma tabla?
Si, creando dos layouts distintos con el mismo objectName: uno con tenants: ["UPU"] y otro con tenants: ["DEMO"]. Luego en defaultObjects asignas cada layout a sus tenants correspondientes. El codigo del mod es uno solo.
¿Cuál es la diferencia entre Extended y tenant-only?
Extended agrega columnas a una entidad que ya existe (ext__UPU__person.json agrega riskScore a Person solo en UPU).
Tenant-only es una entidad completa que solo existe en un tenant (tenants/UPU/Base/ResearchProject.json). En otros tenants esa tabla ni siquiera se genera.
¿Las capabilities se asignan a roles globalmente o por tenant?
Por tenant. El mod declara las capabilities en capabilities.json. Luego cada tenant mapea esas capabilities a sus roles (tabla core_RoleCapability). Asi UPU puede asignar close_case solo a Coordinador, y DEMO puede dárselo a Admin y Coordinador — mismo mod, distintas politicas.
Mi resolver ya esta en un mod restringido a UPU. ¿Necesito filtrar por tenantId?
Si, siempre. Aunque la Suite no deberia invocar el resolver desde otro tenant, un cliente malicioso puede hacerlo por API directa. La regla es: where: { tenantId: context.tenantId, ... } en TODO query. El aislamiento se defiende en dos lugares: config (que tenants ven el mod) y resolver (tenantId en el where).

Nivel 2 — componentes custom del mod

¿Cuándo crear un componente custom?

Solo cuando la UI no se expresa con los patrones declarativos del layout. Hay cinco criterios claros.

✅ Sí crear custom
  • Visualizacion compleja: arbol drag-and-drop, grafico, heatmap, timeline, mapa.
  • Interaccion con estado local: rubrica, editor de matriz, comparador side-by-side.
  • Flujo multi-step embebido: wizard de n pasos que no cabe en un RecordDetail.
  • UI con save propio: editor que persiste sin pasar por el formulario del layout.
  • Widget de dashboard: KPI card, contador animado, chart con query propia.
❌ No crear custom
  • Quieres una tabla "mas bonita" que RecordList. → Usa columnas y CSS del layout.
  • Quieres un formulario con 20 campos. → Usa schema de RecordDetail.
  • Quieres una confirmacion antes de borrar. → rowAction tipo modal + layout confirm.
  • Quieres cambiar un color o label. → i18n y config del layout, no .vue custom.
  • Quieres un select dependiente. → field.dependencies y optionsResolver del layout.
Regla de tamaño
Si la parte custom es un solo campo dentro de un RecordDetail, no crees un layout nuevo — mete el custom element en el schema del layout existente. Solo cuando toda la pantalla es custom, tiene sentido un layoutType: "Custom".

Componentes custom — los 6 lugares

¿Dónde se puede colocar un custom element?

Un custom element tipo A (Vueform) puede vivir en cualquiera de estos seis puntos del arbol de un layout. Cada ubicacion tiene un proposito distinto.

1. Campo del schema
El mas comun. El custom element reemplaza un campo estandar (text, select, date) dentro del schema de un RecordDetail. Ocupa el espacio de un input en el formulario.

Ej: un color-picker, un map-location, un rubric-score.
2. Dentro de un tab
Todo el tab es el componente. En un RecordDetail con tabs, un tab completo referencia un elemento custom del schema — usa el ancho total del tab.

Ej: tab "Competencias" → competency-tree, tab "Riesgo" → risk-dashboard.
3. Paso de un wizard
Un step custom en RecordDetail mode: create. Util cuando uno de los pasos de la creacion necesita UI especial (seleccion jerarquica, mapeo de columnas de un CSV).

Ej: step "Mapeo" → csv-mapper.
4. Pantalla completa (layoutType Custom)
Cuando toda la vista es custom. El layout declara layoutType: "Custom" y el orquestador monta el componente directamente, sin RecordList ni RecordDetail alrededor.

Ej: dashboard, pantalla de importacion, pizarra.
5. Modal custom abierto
rowAction abre un layout Custom. Un click en fila dispara un modal cuyo targetLayoutId apunta a un layout con layoutType: "Custom" que monta el componente en overlay.

Ej: "Ver relaciones" → relations-graph.
6. Storybook (dev)
Entorno aislado para desarrollar. Cada componente tiene MiWidget.stories.ts que lo monta con useMockData: true. Permite trabajar sin Suite corriendo.

Ej: abrir localhost:6006 → "Custom Components / From Mods".

Patron B (standalone) no aparece en esta lista porque no lo monta el orquestador — lo usa otro .vue. Ej: un modal ConfirmDialog invocado desde un Patron A. Vive dentro del arbol de alguno de los seis casos de arriba.

Componentes custom — paso de datos

Pasar datos al componente: props + placeholders

Todo lo que declares en el JSON ademas de type, submits y columns llega como prop al setup del componente. Puedes mezclar valores fijos y placeholders.

JSON del layout

{ "type": "risk-widget", "submits": false, "columns": { "container": 12 }, // Props que llegan al componente "personId": "{{recordId}}", 1 "parentCase": "{{parentId}}", 1 "user": "{{CURRENT_USER_ID}}",1 "mode": "dashboard", 2 "range": "last-30d", "showScoreLabel": true, 2 "thresholds": { "low": 25, "high": 75 } }

En el componente Vue

export default defineElement({ name: 'RiskWidgetElement', submits: false, props: { 3 personId: { type: String }, parentCase: { type: String }, user: { type: String }, mode: { type: String, default: 'inline' }, range: { type: String }, showScoreLabel: { type: Boolean }, thresholds: { type: Object } }, setup(props) { // props.personId ya resuelto en runtime ... } });
1
Placeholders: {{recordId}}, {{parentId}}, {{CURRENT_USER_ID}}. El orquestador los reemplaza en runtime antes de pasarlos al componente.
2
Valores estaticos: string, number, boolean, object. Utiles para configurar el mismo componente en distintos lugares sin duplicar codigo.
3
Props declaradas: si no declaras la prop en props: {...}, Vueform la filtra y no llega. Declara TODAS las que uses en el JSON.
Patron A — Vueform element

Anatomía de un custom element

Este es el patron dominante: un componente que vive dentro de un schema de layout. Hereda de ElementLayout para integrarse visualmente con el resto del formulario.

<template> <ElementLayout> <template #element> <div class="risk-widget"> <Spinner v-if="loading" /> <div v-else>{{ score }}</div> </div> </template> </ElementLayout> </template> <script> import { defineElement } from '@vueform/vueform'; import { ElementLayout } from '@vueform/vueform'; import { useRiskScore } from '@/composables/useRiskScore'; // 👈 composable export default defineElement({ name: 'RiskWidgetElement', 1 submits: false, 2 props: { matrixId: { type: String } }, 3 setup(props) { const { score, loading, load } = useRiskScore(); 4 onMounted(() => load(props.matrixId)); return { score, loading }; }, }); </script>
1
name: obligatorio, termina en Element. El registro automatico lo convierte a kebab-case sin el sufijo.
2
submits: false si no es input. Si es un input custom (ej: selector especial), dejalo true.
3
props: todo lo que pongas en el schema JSON llega aqui. Suelen ser IDs, configuracion o datos del record.
4
Delega en el composable: queries y estado viven en useRiskScore(). El componente solo conecta template y logica.

Regla practica: template ~50 lineas, setup() ~10 lineas. Toda la logica en el composable. Si el .vue crece > 150 lineas, extrae mas logica al composable.

Patron B — standalone

Componente standalone: cuando no es Vueform

Para componentes que otros componentes Vue invocan — no un layout. Tipico: modales, barras de busqueda, tarjetas. Usa <script setup> normal, sin defineElement.

Ejemplo: modal de confirmacion

<template> <div v-if="visible" class="modal"> <Heading :level="3">{{ titulo }}</Heading> <slot /> <Button @click="emit('close')"> {{ $t('actions.cancel') }} 1 </Button> <Button :loading="saving" @click="emit('confirm')"> 2 {{ $t('actions.confirm') }} </Button> </div> </template> <script setup lang="ts"> import Button from '@/components/atoms/Button.vue'; 3 defineProps<{ visible: boolean; titulo: string; saving?: boolean }>(); defineEmits<{ close: []; confirm: [] 4 }>(); </script>

Cuándo usar patron B

  • ✅
    Modales custom abiertos desde otro componente Vue.
  • ✅
    Barras de busqueda, tarjetas, banners usados en varios layouts custom del mod.
  • ✅
    Componentes internos del arbol de otro Vueform element (split en partes).
  • ❌
    NO para algo que invoca un layout JSON: ahi SIEMPRE patron A.
1
$t() para i18n: nunca texto hardcodeado.
2
emit para notificar al padre (close, confirm, save).
3
Siempre atoms (Button, Heading, Text, Spinner) de layout/src/components/atoms/, nunca Bootstrap directo.
4
defineEmits tipado: declara los eventos que el componente emite.

Nivel 3 — composables

Composables: lógica reutilizable del mod

Un composable es una funcion JS que encapsula logica Vue (estado reactivo, queries, helpers). Es el equivalente a un "hook" de React. Vive en mods/{mod}/modsComposables/.

Query
Lee datos via Apollo GraphQL. Expone data, loading, error reactivos y una funcion fetch(). Usa SIEMPRE useTenantApolloClient().
Mutation
Escribe datos via Apollo. Expone saving y funciones como create(), update(), delete(). Retornan el resultado o lanzan error.
Pura / helper
Calculos, formateos, derivaciones. Sin side effects externos. Ej: calcularRiesgo(score), formatearFecha(iso), agruparPorEstado(items).
Para que sirven — 4 razones principales
1) Reutilizacion: varios componentes custom del mod usan la misma query o calculo. 2) Testabilidad: funcion JS pura, testeable sin montar Vue. 3) Separacion: el .vue queda delgado (template + wiring), la logica aislada. 4) Consistencia: un mismo endpoint se consume igual en todo el mod (no cambian filtros ni fetchPolicy por accidente).
Composable — patron query

Regla de oro: useTenantApolloClient

Toda query/mutation GraphQL del mod DEBE pasar por este helper. Inyecta el header X-Tenant-ID automaticamente — sin el, los datos cruzan tenants.

import { ref } from 'vue'; import { gql } from 'graphql-tag'; import { useTenantApolloClient } from '@/composables/useTenantApolloClient'; const GET_RISK = gql` query GetRisk($id: String!) { personRiskScore(id: $id) { level score lastUpdate } } `; export function useRiskScore() { const apollo = useTenantApolloClient(); 1 const data = ref(null); 2 const loading = ref(false); const error = ref(null); async function load(id) { loading.value = true; try { const r = await apollo.query({ query: GET_RISK, variables: { id }, fetchPolicy: 'network-only' 3 }); data.value = r.data.personRiskScore; } catch (e) { error.value = e; } finally { loading.value = false; } } return { data, loading, error, load }; }
1
useTenantApolloClient(): devuelve un cliente Apollo con X-Tenant-ID inyectado. Usar directamente apolloClient.query/mutate.
2
Estado reactivo: data, loading, error como ref. El componente hace binding directo y la UI se actualiza sola.
3
fetchPolicy: network-only evita cache cuando los datos cambian frecuentemente. Para lookups estables usa cache-first.

❌ NUNCA useQuery() / useMutation() de @vue/apollo-composable. Siempre el cliente imperativo apollo.query() / apollo.mutate(). Los hooks de Apollo no llevan el tenant correctamente en todos los contextos.

¿Puede un composable ser compartido entre mods?
Técnicamente si (tras sync llega a suite/modsComposables/), pero evitalo: rompe la autocontencion del mod. Si dos mods necesitan la misma logica, promuevela al core (layout/src/composables/) o duplicala. Mod A nunca debe depender de mod B.
¿Dónde va el manejo de errores?
En el composable — captura, guarda en error.value, y opcionalmente registra via useAuditLog() o muestra un toast. El componente solo hace v-if="error" y pinta el fallback. Asi el manejo es consistente en todos los consumidores.
Resolvers custom — backend

¿Cuándo escribir un resolver custom?

El codegen ya te da CRUD completo gratis por cada object. Un resolver custom solo existe si necesitas logica que el CRUD no cubre.

🆓 Lo que codegen te da gratis

  • ✅
    listMiObjetoInstances — listar todos
  • ✅
    getMiObjetoInstance(id) — obtener uno
  • ✅
    createMiObjetoInstance(input)
  • ✅
    updateMiObjetoInstance(id, input)
  • ✅
    deleteMiObjetoInstance(id)
  • ✅
    Filtrado por tenantId, permisos por object

Si tu feature es CRUD puro con un layout JSON, no escribas resolver — mapea el layout al CRUD auto.

🔧 Cuándo si crear resolver custom

  • ⚡
    Calculo agregado: getResumenMetricas con totales, promedios, grouping.
  • ⚡
    Workflow transition: publicarCaso(id) que cambia estado + crea audit log + dispara notificacion.
  • ⚡
    Mutacion transaccional: crea N registros atomicamente.
  • ⚡
    Shape custom: retornar un tipo que no corresponde 1:1 con un object.
  • ⚡
    Bulk operations: procesar lista en lote.
  • ⚡
    Integracion externa: llamar a otra API y mezclar con datos locales.
  • ⚡
    Logica de permisos custom: field-level, hasCapability soft, visibilidad condicional.

Capabilities — ¿qué son?

Capabilities: permisos granulares declarativos

Una capability es un permiso con formato mod/{mod}:{accion}. Se declara en capabilities.json, se sincroniza a la BD, y se aplica en cuatro lugares distintos.

1. App / Layout
Control de acceso a la vista. En app.json o un layout, el campo roles define quien ve la entrada del sidebar o el layout. Si no tiene el rol, ni siquiera aparece.
2. Row action
Control de UI condicional. En el layout JSON: requiredCapability: "mod/x:delete". Si no la tiene, el boton no se renderiza.
3. Resolver
Control de API. withAuth(['mod/x:manage'], handler). Si el usuario no la tiene, el resolver responde 403 antes de ejecutar la logica.
4. Field-level
Control de campo especifico. Nombre con dos puntos internos: case.salary:view, case.salary:modify. Usados por checkFieldPermissions (hard) o hasCapability (soft).
Por qué este modelo y no un if-else
Porque el admin debe poder asignar permisos a roles sin codigo. Las capabilities aparecen automaticamente en el administrador de roles. Con if (role === 'X'), cada nuevo rol requeriria recompilar. Con capabilities, el admin arrastra y suelta.

Lang / i18n — estructura

Traducciones: BD guarda claves, UI resuelve texto

La BD de UP1 guarda claves simbolicas (ej: actions.publish), nunca texto. El texto humano vive en archivos JSON por locale dentro del mod, y se resuelve en runtime con $t().

📁
mods/retention/lang/
Un archivo por locale + archivos per-object para overrides de campos/tabs/acciones de un objeto especifico.
lang/es_CL.json
Base del mod: object (nombre de objetos en sidebar/breadcrumb), layout (labels de layouts), riskLevel, actions, etc.
lang/es_CL@RetentionCase.json
Per-object: column (headers de tabla), tabs, steps, createModalTitle, actions.*Title. Tiene prioridad sobre la base cuando estas en contexto de ese object.
lang/en_CL.json
Misma estructura que es_CL.json, traducido a ingles. Si el mod es tenants: ["*"], cubre tambien pt_BR.
lang/es_CL-UPU.json
Override por tenant: solo las claves que difieren en ese cliente. Merge sobre la base.
Por qué almacenar claves y no texto
Porque la misma entidad en BD se muestra en 3 idiomas + 5 clientes con jerga distinta. Guardar texto significaria 15 copias. Con claves, la BD tiene una y los JSON resuelven cada variante.

Flujos sincronos en la UI

Tres modos de comunicación en la UI

Cuando el usuario interactua con la UI, los componentes se comunican de tres formas — cada una con su mecanismo y responsable.

A. Declarativo
Layout JSON describe la interaccion. El LayoutOrchestrator la ejecuta.

Ej: rowAction → abre modal, tab → renderiza layout hijo, createLayout → abre form de creacion.

Sin codigo. Todo vive en el JSON.
B. Placeholder
Paso de datos entre layouts padres e hijos.

Ej: un RecordDetail muestra sublista filtrada por {{parentId}}; un modal abre con initialDataMapping: {"personId": "record.id"}.

Aun declarativo, resuelto por el orquestador.
C. Imperativo
Un custom element dispara una accion (emit, composable, router).

Ej: el CompetencyTree, desde dentro del Vueform element, abre un modal o navega.

El modal sigue siendo JSON — solo la activacion es Vue.
Regla mental
Empieza declarativo (A). Si necesitas pasar datos del padre al hijo, usa placeholders (B). Solo si la interaccion nace dentro de un custom element que ya existe, usa imperativo (C) — pero el destino sigue siendo un layout JSON.

Flujos sincronos — imperativo

Eventos desde un custom element

Dentro de un Vueform element, la logica es codigo Vue — pero el destino de la accion sigue siendo un layout JSON orquestado. Hay 4 formas de disparar flujos desde dentro.

📣

1. emit() al padre

El Vueform element emite un evento estandar (change, input, submit). El RecordDetail padre lo recoge y actualiza su estado.

ctx.emit('input', newValue);
🧭

2. router.push programatico

Para navegar a otra URL desde un boton interno. El router construye la URL del orquestador: /{tenant}/{obj}/RecordDetail/{layoutId}/{id}.

router.push( `/UPU/Case/RecordDetail/case_view/${id}`)
🪟

3. useLayoutModal()

Abre otro layout como modal desde el codigo. El orquestador resuelve el layout, lo monta en un overlay, y devuelve el resultado cuando cierra.

const { openModal } = useLayoutModal(); await openModal({ objectName: 'CaCompetency', layoutId: 'ca_competency_create', data: { parentId: id } });
🔄

4. Mutation via composable

La accion dispara una mutation (custom resolver o CRUD auto). Tras success, refresca estado local y/o invalida cache de otros componentes.

const { save } = useCompetency(); await save(data); emit('refresh');

De listado → detalle → custom element → modal de creación

Sigue el camino de un click real. Cada paso es una pieza distinta — algunas declarativas, una sola imperativa dentro del custom element.

1
ca_matrix_list (RecordList)
Declarativo. Usuario hace click en rowAction "Ver detalle" → type: "navigate", targetLayoutId: "ca_matrix_view".
2
ca_matrix_view (RecordDetail)
Declarativo. El layout tiene un tab "Competencias" cuyo schema contiene un custom element type: "competency-tree" con prop matrixId: "{{recordId}}".
3
CompetencyTreeElement.vue
Custom element. Recibe matrixId, usa useCompetencyTree(matrixId) para cargar nodos. Render del arbol drag-and-drop.
4

Imperativo. El componente llama useLayoutModal().openModal({ layoutId: 'ca_competency_create', data: { parentId, matrixId } }).
5

Declarativo de nuevo. El orquestador monta el modal con el layout de creacion, prellenado con parentId y matrixId. Submit → createCaCompetencyInstance (CRUD auto).

Flujos async entre mods

Cuando la acción cruza mods o no espera al usuario

Para flujos que atraviesan el boundary de un mod (notificar, sincronizar con externo, recalcular) UP1 usa eventos + BullMQ + n8n — fire and forget.

# Camino de una accion async Mutation en Object Manager (createCase, updateMatrix, publishCompetency, ...) │ │ Object Manager inspecciona events/*.json de todos los mods │ ¿hay match con objectType + operation + condition? ▼ ✓ Evento publicado en Redis (canal {tenantId}/{Object}/{mod}:{op}) │ ▼ BullMQ worker toma el mensaje → lo entrega al workflow n8n que lo escucha │ ▼ Workflow n8n ejecuta nodos: notificar, llamar API, crear registro, reportar... │ ▼ ✓ La UI ya respondio al usuario hace rato. El worker no bloquea nada.

Por qué fire-and-forget

  • ⚡
    Mutation responde inmediato → UI fluida.
  • 🔒
    Si un workflow falla, el usuario no se queda colgado.
  • 🔄
    Retries automaticos (attempts) sin que el usuario lo note.
  • 🔗
    Desacopla mods: A publica, B y C reaccionan sin saber de A.

Cómo la UI "sabe" que termino

  • 🔔
    Notificacion in-app: nodo Up1Notification dispara una toast/campanita.
  • 📊
    Polling: la UI pregunta cada N segundos si el estado cambio.
  • 🔁
    Refetch manual: el usuario puede refrescar o navegar.
Flujos async — declaracion de un evento

events/*.json: qué dispara qué

events/case-closed.json

{ "id": "case:closed", 1 "description": "Caso cerrado", "trigger": { "objectType": "StudentSupport", 2 "operation": "update", 2 "condition": "data.status === 'CLOSED'" 3 }, "includeFields": [ 4 "id", "studentName", "closedAt" ], "priority": 3, 5 "attempts": 3 6 }
1
id: identificador unico del evento. Formato sugerido {domain}:{accion}.
2
trigger: que mutation dispara el evento. objectType + operation (create/update/delete).
3
condition: expresion JS contra data. Si falta, dispara en toda operacion que matchee el trigger. Con ella, filtra.
4
includeFields: campos que viajan en el payload. Sin esta clave, se envia todo el registro — evitalo por privacidad.
5
priority: 1 (alta) — 5 (baja). BullMQ procesa primero las altas.
6
attempts: numero de reintentos ante fallo del worker. 3-5 es tipico.
El canal de Redis lleva el tenantId
El evento se publica en {tenantId}/StudentSupport/{mod}:update. Esto permite a n8n filtrar por tenant declarando tenantId: "UPU" en el nodo up1EventCreate — un flow escucha solo los tenants que le interesan.

Anti-patrones — qué evitar

Los 5 anti-patrones mas frecuentes

❌ Componentes
  • Reimplementar RecordList. Ya existe. Usa layout JSON con columnas y filtros.
  • Logica en el .vue. 500 lineas de queries + estado. Extrae al composable.
  • Duplicar componentes por cliente. RiskUpu.vue + RiskDemo.vue. Un solo componente con props, variantes en layout.
  • Vue directo a la BD. Siempre via composable + useTenantApolloClient.
❌ Resolvers
  • Olvidar tenantId en el where. Datos cruzan tenants.
  • Resolver sin withAuth. Endpoint publico sin control.
  • Export sin "Query"/"Mutation". Sync lo ignora silenciosamente.
  • if (tenant === 'UPU'). Usa layouts / capabilities / extended objects.
❌ Lang / capabilities
  • Texto hardcodeado en templates. Siempre $t('clave').
  • Duplicar es_CL.json entero por tenant. Solo las claves que difieren en el override.
  • Capabilities sin riskLevel. El admin no puede ordenarlas por sensibilidad.
  • if (user.role === 'admin'). Usa withAuth / requiredCapability.
❌ Flujos
  • Bloquear UI esperando al worker BullMQ. Fire-and-forget es la regla.
  • Notificar desde el resolver con sendEmail. Usa evento + flow.
  • Flows con tenantId: "all" que luego hacen if interno. Un flow por tenant, o logica generica.
  • Event sin includeFields. Se envia todo el registro — riesgo de privacidad.
Fijacion — decisiones clave

Preguntas integradoras (1/2)

Componentes, composables, resolvers
Las tres piezas se eligen juntas: ¿donde va la UI? (componente), ¿donde va la logica? (composable), ¿donde va la operacion de datos? (resolver o CRUD auto). El orden de decision importa.
¿Custom element o layout JSON puro?
Primera pregunta: ¿se expresa con tabla, form, tabs o listado? → layout JSON. Segunda: ¿necesito visualizacion no tabular (arbol, chart, calendar)? → custom element. Tercera: ¿es solo un campo raro dentro de un form? → custom element solo para ese campo, no toda la pantalla. La regla: si puedes describirlo en terminos de columnas, filtros y acciones, no es custom.
¿Composable o logica en el componente?
Si una logica (query, calculo, estado) va a ser usada por 2+ componentes o tests, va al composable. Si es exclusivamente local a ese .vue y son < 30 lineas, puede quedar inline. Senal de alerta: tu .vue supera las 150 lineas — extrae logica al composable inmediatamente.
¿Resolver custom o CRUD auto?
CRUD auto si la operacion es estrictamente crear/leer/actualizar/borrar un registro sencillo. Resolver custom si hay: agregacion, transaccion multi-tabla, shape de retorno distinto, workflow transition con audit, logica de permisos mas alla de withAuth simple, o integracion con sistemas externos. Evita envolver el CRUD auto en un resolver custom "por si acaso".
¿Por qué el composable debe usar useTenantApolloClient() siempre?
Porque inyecta el header X-Tenant-ID en cada request. Si usas Apollo directo (o los hooks useQuery/useMutation), el header puede no propagarse en ciertos contextos (SSR, composables fuera de setup, bouncing de routing). El resolver entonces no encuentra tenant y, segun la config, puede lanzar error o — peor — devolver datos cruzados entre tenants. Es una linea de defensa critica.
Fijacion — decisiones clave

Preguntas integradoras (2/2)

Lang, capabilities, flujos
Lang decide como se ve el texto. Capabilities deciden quien puede. Flujos deciden que pasa despues. Los tres se combinan en cada feature para que la misma logica sirva a multiples clientes con distintos roles.
¿Cuándo crear un override por tenant en lang vs duplicar el archivo?
Override (es_CL-UPU.json) siempre. Solo incluye las claves que cambian. Nunca dupliques el archivo entero — se vuelve imposible mantener consistencia cuando agregas traducciones nuevas. El merge es shallow por clave, asi que tu override no necesita repetir lo que no cambia.
¿Capability por object, por field o por feature?
Por feature (mod-level): default. Ej: mod/retention:manage_cases. Por object: cuando varios mods gestionan el mismo object y hay que diferenciar. Field-level: solo para campos estrictamente sensibles (salario, notas medicas). No uses field-level por defecto — complica los permisos y el admin.
¿Flujo sincrono con mutation custom o async con evento?
Sincrono (mutation custom) si la accion debe completar antes de responder al usuario: publicar, validar, rechazar. El usuario ve el resultado inmediato. Async (evento + flow) si es un efecto colateral: notificar, sincronizar con externo, recalcular, agregar a log. Nunca mezcles: no bloquees la UI esperando al worker async.
¿Cómo habilito un flow solo para un cliente?
El nodo up1EventCreate declara tenantId: "UPU". Ese flow solo recibe eventos del tenant UPU. Puedes tener on-case-closed-upu.json con logica A y on-case-closed-demo.json con logica B. Si la logica es identica, un solo flow con tenantId: "all". Nunca pongas if (payload.tenantId === 'UPU') dentro del flow — es el mismo antipatron que en codigo.
¿Una sola Q final? — ¿cómo recuerdo cuándo usar qué?
"JSON primero, Vue custom despues, eventos al final." Layout JSON resuelve > 80% de la UI. Custom element solo cuando el JSON no alcanza. Composable solo cuando hay logica reusable. Resolver solo cuando no es CRUD. Lang siempre (nunca texto hardcodeado). Capability siempre (nunca if role). Evento + flow cuando el efecto es async o cruza mods. Si recuerdas esa secuencia, el 90% de las decisiones se toman solas.

UP1: qué tener en cuenta siempre

Los puntos que no se pueden olvidar cuando trabajas en UP1, independientemente del rol.

🏢 Multi-tenant a nivel aplicacion
Una sola BD, una sola instancia. El aislamiento vive en tenantId.
Regla de oro: toda query GraphQL DEBE llevar el filtro where: { tenantId: context.tenantId }.
📐 Schema-driven — JSON manda
El modelo se escribe en JSON objects. El codegen genera Prisma + GraphQL + CRUD.
Nunca editar schema.prisma, typeDefs/dynamic.js, ni migraciones aplicadas.
🧩 Todo se extiende via mods
Los mods viven en mods/{nombre}/. Nunca editar destinos de sync (suite/modsComponents/, suite/lang/, etc).
El core no se toca para agregar features.
🎨 Las vistas salen del JSON
LayoutOrchestrator lee layouts JSON de DB y renderiza. La UI es una proyeccion declarativa del modelo. No se escribe HTML standard.

Sidebar = lista de mods instalados (uno por app.json).
