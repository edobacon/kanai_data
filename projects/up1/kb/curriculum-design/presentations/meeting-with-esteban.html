P1
Pregunta agrupada · Convención de enums

Para cerrar el JSON Schema de los enums, nos faltan 2 piezas

Resuelve Q10 (casing) + Q2 (valor "Active" en workflowState)
Estamos modelando El campo AcademicActivity.workflowState y, transversalmente, todos los campos enum del agregado: programLevel recordType linkType referenceFormat ownerType sectionType deliveryMode · etc.
📥 Lo que tenemos para responder

Tu doc de Confluence describe los valores de cada enum en PascalCase (Draft, Approved, Theoretical) — funciona como notación legible para humanos. El legacy de Univalle y AIEP también usa PascalCase (Active, Course, Mandatory). Pero el código real de up1 — los 5 Bases del core que verifiqué (csenrollment, hwfactor, hwintervention, etc.) — usa UPPER_SNAKE_CASE sin excepción para todos los enums (ENROLLED, ACADEMIC_ADVISING, IN_PROGRESS). Y AGENTS.md confirma que esa es la convención del core.

Para workflowState en particular, tu modelo conceptual define 6 valores oficiales: Draft / Review / Approved / Published / OpenForEdit / Deprecated. Pero en los datos legacy de ambos tenants aparece "Active" — un valor que no está en esos 6.

❌ Lo que NO podemos cerrar sin tu input

Si seguimos UPPER_SNAKE (lo que dicta el código), nadie nos confirmó que esa sea la decisión correcta para este módulo — podríamos estar contradiciendo la intención del modelo conceptual. Si seguimos PascalCase (lo que muestran tu doc y los datos), salimos de la convención del core sin precedente.

Y sobre "Active": nadie más que vos sabe qué significa en términos del modelo Confluence. ¿Es el mismo concepto que Published? ¿Es Approved? ¿Es un séptimo valor que faltó documentar? Sin tu palabra, modelarlo es inventar.

💡 Lo que proponemos como camino

UPPER_SNAKE_CASE en todos los enums del módulo. workflowState queda con 6 valores en mayúsculas: DRAFT, REVIEW, APPROVED, PUBLISHED, OPEN_FOR_EDIT, DEPRECATED.

El código de up1 lo respalda. AGENTS.md tiene una regla meta — "si la guía contradice un Base del core, gana el Base" — y los 5 Bases verificados usan UPPER_SNAKE. Convertir el legacy es un script idempotente, costo bajo. Pero el mapping de "Active" sigue abierto, así que lo dejamos como pregunta para vos.

📊 Cómo viene en el legacy v2.2 (ambos tenants)

💡 Cómo quedaría con la propuesta

// Univalle (después de migración) { "workflowState": "PUBLISHED"?, "programLevel": "UNDERGRADUATE", "recordType": "COURSE" } // AIEP (después de migración) { "workflowState": "PUBLISHED"?, "programLevel": "TECHNICAL_PROFESSIONAL", "recordType": "COURSE" }

El ? marca lo que necesitamos confirmar (mapping de "Active").

Lo que necesitamos de ti
  • ¿Confirmás UPPER_SNAKE_CASE como casing oficial de los enums de este módulo? Si confirmás, convertimos el seed legacy mecánicamente. Si no, contanos qué casing prefieres y por qué.

Posibilidades que vimos: equivale a PUBLISHED (vigente, en uso), o a APPROVED (aprobado pero no publicado), o es un valor adicional que falta en el doc, o se elimina porque solo existió en el sistema legacy.

Si necesitamos Univalle Y AIEP funcionando 100%, ¿qué hacemos?

Profundiza la decisión de P2 con el caso "completo siempre"
Estamos modelando Cómo cubrir el seed completo del legacy para los dos tenants. AIEP usa 4 RTs (Modality, LearningOutcome, Content, EvaluationComponent). Univalle usa 6 (los anteriores menos Content + Session, Bibliography, CustomSection). Si los queremos completos: 7 RTs en juego.

up1 ofrece 3 mecanismos técnicos distintos para acomodar diversidad entre tenants — pero NO todos resuelven el problema de tener "más RTs":

Opción A — Modelar los 7 RTs todos globales en business/RecordTypes/. Ambos tenants los ven, cada uno usa los que necesita. Trade-off: 3 archivos + 3 layouts extra en TICKET-009 (~30-40% más esfuerzo) vs la propuesta P2 de 4 RTs.

Por qué A y no B: B obliga a tomar una decisión "esto es exclusivo de Univalle", lo cual no está justificado por los datos — AIEP simplemente no documentó bibliografía ni sesiones, no significa que nunca las quiera. A es reversible (mover archivo entre carpetas si más adelante hace falta), B requiere migrar registros si cambia. El costo extra del esfuerzo en TICKET-009 paga la cobertura completa de demos sin deuda técnica.
Lo que necesitamos de ti

📥 Lo que tenemos para responder

Sobre CustomSection: si hubiera sido N RTs específicos, tendríamos que modelar dinámicamente (mecanismo que up1 no tiene todavía). Sobre la Habilitación: si es ApprovalCondition, hay que modelar ese RT en TICKET-009 (no estaba previsto) y migrar el registro de Univalle. Sin tu palabra, ambos cambios son inferencia.

💡 Lo que proponemos como camino

Cargar literal lo que dice el legacy: (A) 1 RT genérico CustomSection con campos name, contentType, content, maxLength — las 2 secciones de Univalle se diferencian por name. (B) La Habilitación queda como Session con activityDescription="Habilitación", sin modelar ApprovalCondition en este sprint.

P4
Pregunta puntual · Identificador externo

¿Modelamos externalId como 1 campo o 2 separados?

Resuelve Q1 · Decisión menor — confirmable rápido
Estamos modelando El campo AcademicActivity.externalId — el identificador que traza el origen del programa cuando se importa de un sistema externo (Banner, Anthology, SIS local).
📥 Lo que tenemos para responder

Tu doc Confluence (BR-INT-001) dice textualmente que el identificador "puede ser compuesto" — da como ejemplo "código de programa + código de período para Banner". No especifica si eso significa 1 campo con valor compuesto en string o 2 campos separados.

El legacy v2.2 entrega valores simples: Univalle = "1124", AIEP = "TIR101". Y verifiqué que en el código de up1 el patrón externalId no existe en ningún Base actual — sería el primer campo de su tipo en el core.

❌ Lo que NO podemos cerrar sin tu input

Confluence permite ambas formas y el código no aporta convención. La decisión depende de cómo se planee el flujo de import desde SIS:

Si va a integrar con un solo sistema (ej: solo Banner), 1 campo basta. Si va a recibir desde varios SIS distintos (Banner + Anthology + interno), 2 campos separados ayudan a filtrar/auditar por sistema. Esa decisión es de arquitectura de integración, no se infiere del modelo.

💡 Opción A — 1 campo (propuesta)

"externalId": { "type": "string", "not_null": false } // Univalle: externalId: "1124" // AIEP: externalId: "TIR101" // Compuesto: externalId: "BANNER:MAT101-2024-S1"

📘 Opción B — 2 campos separados

"externalSystemId": { "type": "string", "transformations": [{"type":"uppercase"}] }, "externalRecordId": { "type": "string" } // Banner: externalSystemId="BANNER", // externalRecordId="MAT101-2024-S1"

💡 Lo que proponemos como camino

1 campo externalId string nullable, alineado con el legacy. Si más adelante se integra con varios SIS, la migración es idempotente: SPLIT_PART(external_id, ':', 1) → external_system_id + el resto a external_record_id.

El legacy v2.2 lo respalda. Confluence permite ambas formas. Riesgo bajo de retrabajo si se decide cambiar.
Lo que necesitamos de ti
  • ¿Modelamos 1 campo externalId (alineado con legacy) o preferís 2 campos separados externalSystemId + externalRecordId?
  • ¿Hay un plan de integración con múltiples SIS a corto plazo que justifique 2 campos desde el inicio? (Si solo es 1 sistema, 1 campo basta y la migración futura es trivial)
