Elric vs up1-mcp

Integración del MCP · diseño curricular

Elric vs up1-mcp

Los dos resuelven el mismo dolor (un agente opera up1 con la identidad real del usuario), pero escriben las tools de forma opuesta. Este es el par a par, con código real de cada repo.

Elric uplanner/mcp · TypeScript · una función por tool up1-mcp uplanner/up1 · JS declarativo · fichas + un motor

00 El modelo mental

Función escrita a mano vs ficha de datos

En Elric, cada tool es una función TypeScript que hace todo: valida auth, resuelve por nombre, arma el preview, llama a GraphQL y formatea la salida. En up1-mcp, la tool es una ficha (un objeto de datos) y un único motor genérico la convierte en tool real. Migrar de uno a otro no es copiar archivos: es reexpresar cada capacidad como ficha (si es simple) o como registerExtra (si tiene lógica).

01 El caso simple

Quitar entradas de un plan

La misma operación de negocio a cada lado. En Elric es una función completa; en up1-mcp es una ficha, y el borrado real, el preview, el confirm y la limpieza de campos internos los aporta el motor (siguiente sección).

02 Dónde vive la lógica común

El motor que Elric no tiene

En up1-mcp, preview, confirm, request GraphQL, poda de campos internos y gate por capability se escriben una sola vez, en un motor que recorre cualquier lista de fichas. En Elric ese mismo comportamiento se repite (o se importa) tool por tool.

up1-mcpregister-declarative-tools.js · motor único
// Se escribe UNA vez. Convierte cualquier ficha en tool.
function registerOne(server, d, { up1, ctxFor, onGatedTool }) {
  const isWrite = d.writePattern === "preview-confirm";
  const tool = server.registerTool(
    d.name,
    { title: d.title, description: d.description,
      inputSchema: zodShapeFromFields(inputFields) },
    async (args, { authInfo }) => {
      const { confirm, ...userVars } = args;
      const variables = { ...d.defaults, ...userVars };
      // preview, para TODAS las fichas de escritura
      if (isWrite && !confirm)
        return previewResult(d.title, variables);
      const ctx = await ctxFor(authInfo);
      const data = await up1.request(d.graphql, variables, ctx);
      // poda de campos internos (_) para TODAS
      const result = stripInternalDeep(data[d.resultPath]);
      return { content: [{ type: "text",
        text: JSON.stringify(result, null, 2) }] };
    }
  );
  if (d.requiresCapability)          // gate RBAC, opt-in
    onGatedTool?.(d.name, d.requiresCapability, tool);
  return tool;
}

03 El 68% que no entra en una ficha

El escape hatch: cuando hay que volver a escribir código

Sagas con rollback, upserts (buscar y según eso crear o editar), operaciones de árbol: son varias llamadas condicionadas entre sí. Una ficha no las expresa. Acá los dos vuelven a escribir un handler a mano, pero el online lo aísla en el pack y le inyecta todo por ctx.

04 Resolución por nombre

Auto-resolver vs flujo de dos pasos

El usuario dice "Cálculo I", no un id. Elric traduce nombre a id dentro del create, guiado por el contrato del objeto. up1-mcp, a propósito, no lo hace: el LLM primero pregunta las opciones con get_field_options y después crea con el valor ya resuelto. Es la divergencia del principio rector.

Elriccontracts/resolve-inputs.ts · auto-resuelve
// Resuelve enums y FKs DENTRO de create/update, por contrato.
export async function resolveContractInputs(api, ctx, contract, raw) {
  const data = {}, issues = [], resolved = {};
  for (const [field, value] of Object.entries(raw)) {
    // enum: por etiqueta/sinónimo (passthrough si ya es canónico)
    const enumValues = contract.enums[field];
    if (enumValues && !enumValues.includes(value)) {
      const r = resolveEnum(value, enumValues);
      if (r.status !== "resolved") { issues.push({ field, ...r }); continue; }
      data[field] = r.value; resolved[field] = `${value} -> ${r.value}`;
      continue;
    }
    // FK: por nombre/código -> resuelve el id
    const fk = contract.fieldDocs?.[field]?.fk;
    if (fk) {
      const r = await resolveReference(api, ctx, fk.objectType, value);
      if (r.status !== "resolved") { issues.push({ field, ...r }); continue; }
      data[field] = r.id;                // nombre -> id, transparente
      continue;
    }
    data[field] = value;                 // escalar: passthrough
  }
  return { data, issues, resolved };
}

05 El hueco de seguridad

La puerta lateral del CRUD genérico

Las reglas de negocio (pesos que suman 100, un solo default, máquina de estados) viven dentro de las mutations *Validated, no en la base. Elric bloquea el CRUD genérico sobre esos objetos y redirige a la tool de dominio. up1-mcp expone up1_create_object genérico sin ese bloqueo: hoy es una puerta abierta.

07 Dónde vive la validación

Réplica en el cliente vs invariante en el resolver

La misma clase de regla (que los pesos sumen su techo, 100 en la raíz) puede vivir en dos lugares muy distintos. Si vive en la tool, protege al que usa la tool. Si vive en el resolver, protege el dato. Solo lo segundo es un invariante real.

Elriccontracts/validations.ts · réplica client-side
// Regla del FRONTEND replicada en el MCP.
// up1 NO la enforza en el resolver -> el MCP la aplica
// antes de mutar. (línea 2 del archivo, literal)
export function validateWeights(nodes, tolerance = 0.01) {
  // hijos de cada nodo suman el peso del padre;
  // los nodos raíz suman 100.
  for (const [parentId, children] of childrenByParent) {
    const actual = children.reduce((s, c) => s + (c.weight ?? 0), 0);
    const expected = parentId ? byId.get(parentId)?.weight ?? 0 : 100;
    if (Math.abs(actual - expected) > tolerance)
      violations.push({ parentId, expected, actual });
  }
  return violations;
}
// El que NO llama la tool (genérico, otro cliente,
// llamada directa) nunca ve esta regla.

Qué muestra Misma regla, dos hogares. La de Elric protege al que usa la tool; la del online protege el dato. Un invariante client-side es una ficción: cualquier camino que no sea esa tool lo saltea. Por eso las evaluaciones (100%) ya están bien en el online, y el rango de créditos y el overflow de malla, que siguen client-side, no.

? El escenario que planteaste

Una regla client-side de un mod, sin backend. ¿La implemento también en la tool del MCP?

El caso real: el mod tiene una regla que hoy solo vive en su frontend (no se pudo, o no se ha hecho, en el backend). El MCP es otro cliente y habla GraphQL directo, salteando ese frontend. Entonces la regla, para el MCP, no existe.

Frontend del mod
valida la regla
Backend / resolver
NO la valida
MCP (otro cliente)
la saltea, salvo que la replique

Respuesta corta: sí, mientras el backend no la tenga, el MCP está obligado a replicarla, o se convierte en una puerta de escritura sin control, más peligrosa que la UI (un LLM puede crear justo la inconsistencia que el frontend evita). Eso es, exactamente, por qué existe validations.ts en Elric. Pero es una mitigación forzada, no una solución, y tiene tres costos. Frente al escenario hay tres respuestas legítimas:

Opción A · Replicar

Copiar la regla en la tool

Lo que hace Elric. Protege el path del MCP mientras el backend no exista.

Costo: la misma regla vive en 2+ lugares (frontend + MCP) y derivan. Sigue bypasseable por otros clientes. El MCP queda acoplado a la lógica del mod.

Cuándo: es un invariante que corrompe datos y la escritura ya está expuesta. Obligatoria como stopgap, nunca como destino.

Opción B · Declarar

No replicar, exponer el hueco

Lo que hace academic-scheduling: notExposed dice "el server no lo enforza todavía, deuda conocida del mod".

Costo: el MCP puede producir la inconsistencia. Solo honesto, no seguro.

Cuándo: la regla es menor / advisory, el riesgo es bajo, y replicar sería frágil. Nunca para una regla que corrompe.

Opción C · Escalar

Llevar la regla al resolver

El fix real: una Core Extension que pone la validación en el write resolver, como el gate del 100%.

Costo: trabajo de plataforma, dependencia de otro equipo/tiempo.

Cuándo: es un invariante y existen (o existirán) otros clientes. Es el único que hace la regla real para todos.

La regla de decisión: si la validación es un invariante (100%, un solo default, min≤max, máquina de estados) el destino es siempre C, el resolver. A es el puente obligatorio mientras C no está, y se paga la deuda cuando el backend cierra (ahí el resolver rechaza y la réplica del MCP pasa a ser un pre-check amable o se borra). B solo para reglas menores. Lo que nunca es correcto: dejar la regla client-side en el MCP y creer que con eso el dato está protegido. Si la replicás en A, marcala como réplica con procedencia (comentario al archivo fuente) y fijala con un test que clave la semántica, para que no derive en silencio cuando el mod cambie la regla.

08 Cerrar la puerta

Réplica sola no alcanza

Ya replicaste la regla en la tool de dominio (opción A del escenario). ¿Con eso el objeto está protegido dentro del MCP? No: mientras up1_update_object alcance ese tipo, el LLM tiene una puerta de al lado que saltea la tool validada. La réplica y el bloqueo del genérico van juntos, no por separado.

Pero incluso cerrada, esa puerta es la del MCP, no la del dato. Hay dos niveles de bypass distintos, y tu pregunta es sobre el primero:

NivelQué cierraMecanismoEstado en up1-mcp
Intra-MCP Que el propio MCP se auto-bypasee con la tool genérica blockGenericMutation (B3) Falta
Cross-client Que cualquiera (UI genérica, API directa, otra integración) saltee la regla La regla en el resolver (opción C) Depende del backend
El cierre: con solo replicar, la puerta genérica queda abierta (nivel 1). Para cerrarla dentro del MCP hace falta blockGenericMutation, que up1-mcp todavía no tiene. Réplica + bloqueo del genérico deja el MCP internamente consistente: sin puerta lateral propia. Pero el dato solo queda protegido de verdad cuando la regla vive en el resolver (nivel 2); ahí blockGenericMutation deja de importar porque ya no hay path que la saltee. Mientras la regla siga client-side, ese riesgo cross-client es residual: hay que aceptarlo y documentarlo.

11 Tool custom vs genérico

¿Es necesario un tool custom? Y cuánto endurecer según la necesidad

La decisión operativa del MCP, por objeto y operación: ¿alcanza el CRUD genérico, o hace falta un tool custom, y cuánto hay que cerrar la puerta genérica? Depende de dos ejes: dónde vive el invariante y si la operación entra en una ficha. La regla de fondo: un tool custom se justifica por lógica o por proteger un invariante que el genérico no cubre, nunca por gusto.
