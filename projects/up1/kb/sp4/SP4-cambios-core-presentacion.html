Contexto

Por qué hubo cambios en core

El objetivo de SP4 (clonar, versionar y converger Curriculum y AcademicProgram) es trabajo de mod. Al ejercitarlo end-to-end aparecieron límites del motor que no se resuelven desde el mod.

El motor de clonado no remapeaba las FKs internas entre hijos clonados (solo el self-ref parentId).

El clone del layout-engine inyectaba campos virtuales al createInstance → Prisma los rechazaba.

El helper de versionado asumía que todo objeto versionable tiene workflow.

El updateInstance no normalizaba la FK escalar requerida como sí lo hacía el createInstance.

Cada uno es una capacidad o corrección de plataforma, no un caso especial de Curriculum → el fix correcto es en core, generalizable, no un parche por-mod.

UPONE-1219 object-manager flujo: clonado/versionado profundo aplicado

1. polymorphicChildrenDerived

Remap declarativo de las FKs internas entre hijos clonados, dentro del deep-clone polimórfico (deep-clone-polymorphic.js).

El problema

Al versionar/clonar, el motor clonaba los hijos y remapeaba el self-ref (parentId) automático, pero no las FKs internas entre hijos: CurricularLink.sourceSectionId / targetSectionId seguían apuntando a las CurricularSection originales, no a las clonadas.

Por qué importa

En SP4 se parchó con un hook imperativo por mod (~93 líneas) + un flow n8n. Duplicado, frágil, y no generaliza: cualquier objeto con hijos que se referencian entre sí volvería a necesitar código propio.

Antes (SP4)

Hook a mano en el mod curriculum-design:

  • ~93 líneas imperativas
  • + flow n8n de remap
  • solo resuelve Activity/Curriculum
  • dos fuentes de verdad del walk de linaje
Ahora (SP4)

Capacidad declarativa del motor:

  • bloque en el JSON del owner
  • validador build-time en el codegen
  • fase "derived" genérica en el deep-clone
  • hook + flow por-mod retirados
UPONE-1219object-manager

1. Cómo funciona y por qué es seguro

El bloque declarativo (en el JSON del owner)

"polymorphicChildrenDerived": [
  { "object": "CurricularLink", "via": "sourceSectionId,targetSectionId", "remapTo": "sections" }
]

object: hijo derivado · via: FKs escalares a remapear · remapTo: alias de polymorphicChildren cuyo tipo clonado es el destino (resuelve el cloneMap por tipo).

Efecto

Mods futuros obtienen el remap de FKs internas gratis, solo declarando el bloque — sin código ni flow por mod.

¿Está contenido?

Backward-compatible: un objeto sin el bloque se comporta igual que antes. La fase derived es defensiva: si una FK cae fuera del cloneMap (cross-owner), loguea y la salta — mismo criterio que el hook que reemplaza.

Verificación

validador build-time (bloques malformados abortan el codegen, no en runtime)unit de applyDerivedRemap (skip cross-owner / cross-type)e2e del remap genéricoActivity: links remapeados preservados vía config genérica
Archivos: codegen/ (validator + reader), deep-clone-polymorphic.js, instance.resolver.js (fase derived en finalizeCreate) · Alternativa descartada: mantener el hook imperativo por mod (duplicación, sin generalización).
UPONE-1271 layout flujo: clone prefilledModal → createInstance aplicado

2. Filtrado de initialData en handleSubmit

Descubierto probando el clone de AcademicProgram. Afecta a cualquier objeto con FK display clonado vía prefilledModal.

El síntoma

Al guardar un clone, el create fallaba: "La información proporcionada no es válida — InstitutionName" (Prisma Unknown field).

La causa

El prefilledModal copia de la fila campos virtuales (institutionName, executionUnitName, governanceunit, extended) al initialData; handleSubmit inyectaba todas las keys al payload del createInstance.

Antes

handleSubmit inyectaba todas las keys de initialData al payload (bloque pensado para el owner polimórfico) → Prisma rechaza la 1ª columna desconocida.

Ahora

Inyección filtrada a baseFields ∪ customFields + allowlist de owner [ownerType, ownerId, recordType]; helper puro isInjectableInitialDataKey. Descarta el junk virtual.

¿Está contenido?

Sí. Preserva campos reales y owner; descarta solo el junk virtual. No cambia el contrato del create.

Verificación

unit 5/5regresión 1021/1021smoke UI: clone AcademicProgram guardacommit ce94be7
Archivos: RecordDetail.vue, recordDetailInitialData.ts + spec · Aprendizaje: la causa no era el field-loop del form sino la inyección de initialData — leer el flujo completo antes de fijar el lugar del fix.
UPONE-1270 object-manager flujo: versionado (prepareVersionData) aplicado

3a. prepareVersionData workflow-opcional

El helper de versionado asumía incondicionalmente que el objeto tiene workflow. Curriculum y AcademicProgram modelan el estado como enum simple, sin WorkflowStatus.

El crash (E2E)

PrismaClientValidationError: Unknown field `currentstatus` for include
statement on model `Curriculum`  — at prepareVersionData (version-from-source.js:54)

Es un crash en una lectura previa a cualquier write → no deja versiones a medias.

Antes
// asume workflow SIEMPRE
include: { currentstatus, workflow }
if(!currentstatus.allowsVersioning) throw
if(!workflow.initialStatusId)       throw
result[initialStateField] = workflow.initialStatusId
Ahora
const needsWorkflow = !!initialStateField
include: needsWorkflow ? {currentstatus,workflow} : undefined
if(needsWorkflow){ /* los 2 checks */ }
if(needsWorkflow) result[initialStateField]=…

Efecto · contención

La plataforma versiona objetos sin workflow (Curriculum hoy, AcademicProgram y futuros); la v2 nace en su static_default ("Draft"). Función pura; el gate preserva Activity 1:1.

Verificación · alternativas

unit 13/13 542/542 resolvers E2E
Descartadas: resolver custom en el mod (duplica el walk de linaje); dar workflow formal a Curriculum (sobre-modela).

UPONE-1270 object-manager flujo: actualización (updateInstance) aplicado

3b. updateInstance — FK escalar → relation connect

Simetría create/update. Emergió al editar Curriculum (relación requerida institution + extensión RecordType a la vez).

Antes

El updateInstance dejaba la FK escalar base (institutionId) en el payload. Junto con la escritura anidada de la extensión RecordType, Prisma fuerza el checked input y rechaza la FK escalar.

Ahora

Convierte la FK escalar a { relation: { connect } } — exactamente lo que createInstance ya hacía. Un solo patrón para create y update.

Efecto

La actualización de objetos con relación requerida + extensión ya no es rechazada; la relación se preserva. Aplica a cualquier objeto con FK base requerida, no solo Curriculum.

¿Está contenido? · verificación

Sí — replica el patrón ya probado del create (sin nueva lógica). 542/542 resolvers sin regresión unit nuevo E2E vivo.
