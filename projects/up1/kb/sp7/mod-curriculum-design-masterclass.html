00

El dominio

¿Qué modela este mod?

curriculum-design modela el diseño curricular de una institución educativa: el Programa de Asignatura (el sílabo como plantilla), su descomposición en secciones (resultados de aprendizaje, contenidos, sesiones, evaluación, bibliografía…), y el agregado curricular por encima: carreras (AcademicProgram), planes de estudio (Curriculum) y su malla por períodos.

📘
Activity

La asignatura / programa de asignatura. Es el nodo raíz que agrupa todas las secciones curriculares.

🧩
CurricularSection

Base abstracto con 7 subtipos (RecordTypes): modalidad, resultado, contenido, sesión, bibliografía, evaluación, custom.

🎓
AcademicProgram

La carrera. Contiene currículos (planes/minors) y se puede clonar.

📐
Curriculum

El plan de estudios tipado (Plan | Minor), con owner polimórfico y versionado por linaje.

🗓️
Malla

planEntry + requirementCategory + requirement: la vista del plan por períodos con prerequisitos.

📚
BibliographyReference

Catálogo bibliográfico compartido, reutilizable por N cursos sin duplicación.

Activity  (sílabo / Programa de Asignatura)
│  code · name · version · programLevel · credits · status
│
└─1:N─►  CurricularSection  (base abstracto — discriminator recordType)
         │  name · position · parentId(self-FK) · ownerType/ownerId
         │
         └─1:1─►  uno de 7 RecordTypes:
                  ├ rt__Modality__curricularsection          modalidad
                  ├ rt__LearningOutcome__curricularsection    resultado de aprendizaje
                  ├ rt__Content__curricularsection            contenido temático
                  ├ rt__Session__curricularsection            sesión (clase)
                  ├ rt__Bibliography__curricularsection ──N:1─► BibliographyReference
                  ├ rt__EvaluationComponent__curricularsection  árbol recursivo + weights
                  └ rt__CustomSection__curricularsection      richText

AcademicProgram ─1:N─► Curriculum ─1:1─► rt__Plan__curriculum | rt__Minor__curriculum
                                   └─owner polimórfico (AcademicProgram | Institution)
◆ Concepto clave

CurricularSection es un base abstracto casi sin campos propios: el contenido real vive en el RecordType 1:1. Así tenemos una sola tabla con 7 "tipos" de sección distinguidos por el discriminador recordType. Este patrón se repite en Curriculum (Plan/Minor) y requirement (RecordState/Group/MetricThreshold).

01

Fundamentos

Anatomía de un mod & cómo crear uno

Un mod es un repo autocontenido que extiende la plataforma up1 sin tocar el core. Todo se organiza por convención de carpetas: el sync lee cada carpeta por su nombre y ubicación, no por config. Estas son las carpetas que reconoce.

mods/<tu-mod>/ — estructura canónicatree
objects/            # Definiciones de objeto (JSON) + objects/RecordTypes/
logic/              # Resolvers custom (*.resolver.js + *.schema.graphql)
modsComponents/     # Componentes Vue custom (Vueform elements)
modsComposables/    # Composables compartidos
config/
  ├ app.json        # Manifiesto de la app (tenant, defaultObjects)
  └ layouts/        # Layouts JSON (RecordList / RecordDetail)
css/                # Estilos del módulo
lang/               # Traducciones i18n {es,en,pt}
events/             # Definiciones de eventos BullMQ
flows/              # Workflows n8n (JSON)
seed/               # Datos semilla por tenant
capabilities.json   # Permisos RBAC
package.json
◆ Scaffold vs mod maduro

npm run create-mod genera el "hola mundo". curriculum-design es la referencia de calidad productiva: agrega vitest, tsconfig, eslint propio, storybook, husky, vueform.config, capas de tests y .ai/ + docs/. Crea solo las carpetas que tu mod necesite.

1.1 Registrar el mod en el monorepo

Un solo registro manual: agregar el repo al array uPlannerMods del package.json raíz. Eso le dice a update-repos / setup qué clonar.

up1/package.json · L42-49json
"uPlannerMods": [
  "ai-agent.git",
  "up1-manager.git",
  "curriculum-design.git",
  "uengagement-up1.git"
]
▲ Aclaración importante

NO hace falta editar el array workspaces: ya usa el glob "mods/*", así que cualquier carpeta bajo mods/ queda cubierta automáticamente. El array ignoredMods excluye mods del sync (ej. el template hello-world-mod). Los mods no se instalan con el npm install del root, sino con npm run install-mods.

1.2 config/app.json: el manifiesto de la app

config/app.json · L1-12json
{
  "name": "curriculum-design",
  "label": "Curriculum Design",
  "icon": "bi-journal-text",
  "order": 10,
  "tenants": { "UPU": {} },
  "defaultObjects": ["Activity", "BibliographyReference", "AcademicProgram", "Offering", "Curriculum", "core_DataLog"],
  "up1ModelVersion": 1

◆ Por qué

Es el manifiesto que da de alta el mod como aplicación visible en el nav de Suite, con sus objetos raíz (defaultObjects) y en qué tenants aplica. Gotcha: el scaffold genera tenants como array, pero el mod maduro lo usa como objeto ({ "UPU": {} }) para permitir config por tenant.

1.3 capabilities.json: los permisos RBAC

Dos niveles conviven. mod/<mod>:<accion> gatea el acceso al módulo; <objeto>:<accion> (sin prefijo) gatea CRUD/transiciones sobre un objeto.

nivel módulojson
{
  "name": "mod/curriculum-design:view",
  "riskLevel": "low"
}
nivel objeto (RULE-mods-037)json
{
  "name": "activity:approve",
  "riskLevel": "high"
}
◆ Por qué

riskLevel (low/medium/high) clasifica el impacto y alimenta el RBAC. curriculum-design declara 40+ capabilities: una por cada transición de estado, clone, versión, etc. Estas capabilities se referencian luego desde las transitions del enum (sección 05) y las row actions de los layouts (sección 06).

El mecanismo de sync

npm run sync es el único mecanismo autorizado para propagar el contenido del mod a los workspaces core. Corre 10 fases y nunca se editan los destinos a mano (se regeneran en cada corrida).

Modobjects/ logic/ config/…
→

Coreobject-manager · layout · suite
→

Fase 3 regenera el schema Prisma combinado (BASEMODEL + todos los tenants) desde los objetos ya mergeados. Fase 10 valida drift entre tenants. Las fases 4-10 saltan operaciones de BD si SKIP_DB_OPERATIONS=true o durante builds de Docker.

2.2 El flujo completo para levantar el mod

orden obligatoriobash
npm run update-repos     # clona/actualiza el mod desde Bitbucket
npm install              # instala dependencias del workspace
npm run sync             # propaga objects, configs y seeds al core
npm run codegen --workspace=@uplanner/object-management-backend
npm run tenant:migrate --workspace=@uplanner/object-management-backend
./up1-start.sh --om --suite     # backend (4000) + frontend (3000)
◆ Por qué este orden

Sin él: el objeto no existe en Prisma (falta codegen), o la tabla no existe en la BD del tenant (falta migrate), o el mod nunca se clonó (falta update-repos).

✕ Regla crítica

Nunca edites archivos sincronizados en core (suite/modsComponents/, suite/lang/, object-manager/objects/…): se regeneran en cada sync y pierdes el cambio. Además, el sync es append-only para destinos que ya existen: si borras un field del JSON del mod, el sync NO propaga la eliminación; hay que borrar el destino en core y re-sincronizar.

Fundamentos

Schema-driven: el JSON es la fuente de verdad

No escribes Prisma ni el esquema GraphQL a mano. Defines el objeto en un JSON y el codegen genera la tabla Prisma, los tipos GraphQL y el CRUD genérico. Es el principio que hace posible todo lo demás.

objects/

→

→
schema.prismaauto-generado
+
typeDefs GraphQL+ CRUD genérico
▲ Archivos auto-generados: no editar

prisma/schema.prisma y src/graphql/typeDefs/dynamic.js se regeneran en cada codegen. Todo cambio de modelo empieza en el JSON del mod.

3.1 Anatomía de una definición de objeto

Un objeto declara properties (campos con tipo, FKs, unicidad), metadata (labels, versioning, hijos polimórficos, índices) y required. El discriminador, las FKs y las relaciones se declaran aquí, no en Prisma.

objects/activity.json — vista de pájaro (secciones clave)json
{
  "metadata": {
    "polymorphicChildren": [ // hijos (sections) → sección 04.2 ],
    "versioning": { // linaje de versiones → sección 05 },
    "uniqueConstraints": [["previousVersionId", "version"]]
  },
  "properties": {
    "recordType": { "enum": ["Course", "Service"] },
    "status":     { "enum": [...], "transitions": [ ... ] },
    "previousVersionId": { "isForeignKey": true, "references": "Activity" }
  }
}
◆ El pago del schema-driven

Como todo el modelo vive en JSON, el mismo objeto alimenta a la vez: la tabla (Prisma), la API (GraphQL CRUD), la UI (los layouts leen los campos), el RBAC (capabilities por campo/objeto) y hasta el MCP. Una definición, cinco consumidores. Por eso las relaciones se piensan como declaraciones, no como código.

04

El corazón del modelado

Los tipos de relaciones que usamos

up1 es schema-driven: las relaciones no se escriben en Prisma a mano, se declaran en el JSON del objeto y el codegen las materializa. El mod usa un abanico de patrones relacionales, cada uno elegido para un problema concreto. Este es el mapa completo.

Árbol recursivo self-FKparentId con isForeignKey → sí mismoJerarquías de profundidad variable

4.1 Base + RecordType (discriminator)

El objeto base declara un campo recordType; cada subtipo es un archivo aparte en objects/RecordTypes/ que apunta al base con baseObject y agrega solo sus campos. Es el patrón más importante del mod.

objects/activity.json · L69-76json
"recordType": {
  "type": "string",
  "not_null": true,
  "enum": ["Course", "Service"],
  "static_default": "Course"
}
objects/RecordTypes/rt__EvaluationComponent__curricularsection.json · L1-9json
{
  "title": "EvaluationComponent",
  "baseObject": "CurricularSection",
  "metadata": { "label": "Componente de evaluación" }
  // + solo los campos propios: weight, method, ...
}
◆ Por qué

El base modela lo común (identidad, owner, jerarquía) y cada RT agrega lo suyo. Evita duplicar el esquema N veces y permite que UI y RBAC traten el discriminador como filtro de subtipo sin tablas separadas. Una tabla física, 7 comportamientos.

4.2 Owner polimórfico + polymorphicChildren

Aquí resolvemos la relación Activity 1:N CurricularSection. El hijo no tiene una FK rígida al padre: guarda ownerType (tipo del padre) + ownerId (su id). El padre declara la colección en polymorphicChildren.

objects/activity.json · L12-19 — el padre declara sus hijosjson
"polymorphicChildren": [
  {
    "name": "sections",
    "object": "CurricularSection",
    "via": "ownerType/ownerId",
    "ownerTypeValue": "Activity",
    "recursiveBy": "parentId"
  }
]
objects/CurricularSection.json · L31-43 — el hijo apunta hacia arribajson
"ownerType": {
  "type": "string", "not_null": true,
  "enum": ["Activity", "Offering", "Curriculum"]
},
"ownerId": {
  "type": "string", "not_null": true
  // ID del owner según ownerType. Sin FK directa (polimórfica).
}
◆ Por qué

El mismo hijo (CurricularSection) cuelga de Activity, Offering o Curriculum sin duplicar tablas ni resolvers. El costo: la DB no garantiza la integridad ownerType↔ownerId (no hay FK real), así que esa validación vive en la capa de aplicación. Ese mismo polymorphicChildren alimenta después el borrado en cascada y la atribución de auditoría al padre.

4.3 Árbol recursivo (self-FK parentId)

Una CurricularSection puede tener sub-secciones del mismo tipo: un componente de evaluación con sub-componentes, un resultado con sub-resultados. Se modela con una FK reflexiva.

objects/CurricularSection.json · L73-81json
"parentId": {
  "type": "string", "not_null": false,
  "isForeignKey": true,
  "references": "CurricularSection",
  "targetField": "id"
  // FK self → jerarquía dentro del mismo recordType
}
◆ Por qué

Modela jerarquías de profundidad variable (árbol de evaluación, grupos AND/OR de requisitos) con una sola tabla y una FK a sí misma, en vez de una tabla por nivel. El componente CompositeSectionTree (sección 07) es la UI que renderiza y edita este árbol.

4.4 N:M con semántica: CurricularLink

Dos secciones (posiblemente de distinto tipo, ej. un Contenido que desarrolla un Resultado de Aprendizaje) se relacionan muchos-a-muchos con un significado propio que una FK simple no puede expresar.

objects/CurricularLink.json · L17-41json
"sourceSectionId": { "isForeignKey": true, "references": "CurricularSection" },
"targetSectionId": { "isForeignKey": true, "references": "CurricularSection" },
"linkType": {
  "enum": ["DEVELOPS", "EVALUATES", "COVERS", "USES", "CUSTOM"]
}
◆ Por qué

El objeto de vínculo permite N:M tipado (linkType). Es el opuesto conceptual del catálogo (4.5): cuando la relación tiene datos propios, se usa una tabla intermedia; cuando solo hay que "apuntar", basta una FK.

▲ Estado real

Según el propio archivo, CurricularLink está schema-validado pero aún no populado en seed ni expuesto en UI (SP2). Es un patrón declarado, no operativo todavía. Además sus FKs apuntan a CurricularSection, no a Activity directamente: el vínculo con la asignatura es indirecto vía el owner de la sección.

4.5 N:1 a catálogo compartido

La bibliografía de un programa apunta a una entrada del catálogo institucional reutilizable, con una FK directa.

objects/RecordTypes/rt__Bibliography__curricularsection.json · L11-19json
"libraryRefId": {
  "type": "string", "not_null": false,
  "isForeignKey": true,
  "references": "BibliographyReference",
  "targetField": "id"
}
◆ Por qué

"Una misma referencia puede ser usada por N cursos sin duplicación." En vez de copiar la cita en cada programa, se apunta al catálogo. FK directa N:1, sin tabla de vínculo.

4.6 Hijos derivados (polymorphicChildrenDerived)

A veces un dato llega por una FK indirecta de un tercer objeto, pero queremos exponerlo bajo una colección que el padre ya conoce.

objects/activity.json · L28-34json
"polymorphicChildrenDerived": [
  {
    "object": "CurricularLink",
    "via": "sourceSectionId,targetSectionId",
    "remapTo": "sections"
  }
]
◆ Por qué

Al clonar/versionar un Activity, el motor de core reapunta automáticamente los CurricularLink al nuevo mapa de sections clonadas, sin que el mod escriba un hook. El consumidor no necesita conocer CurricularLink como entidad intermedia.

4.7 Unicidad: uniqueScopedBy vs uniqueConstraints

El mod distingue dos capas del mismo contrato de unicidad: la regla de negocio declarativa (legible por MCP y UI) y el backstop físico (índice de Prisma).

CurricularSection.json · L57-66json
// regla declarativa
"name": {
  "uniqueScopedBy": ["ownerId", "recordType"]
}
// único dentro del mismo owner+tipo
AcademicProgram.json · L20json
// backstop físico (índice DB)
"uniqueConstraints": [
  ["institutionId", "code"]
]
◆ Por qué

Dos capas: uniqueScopedBy expresa la intención de forma legible y navegable por herramientas; uniqueConstraints la ejecuta a nivel de índice para que ni el CRUD genérico ni el MCP puedan violarla. Defensa en profundidad.

◆ Regla mental

¿FK directa o polimórfica? Si el hijo tiene un solo tipo de padre → directChildren + FK. Si cuelga de varios tipos → ownerType/ownerId + polymorphicChildren. ¿Relación con datos? Si el vínculo tiene atributos → objeto de vínculo (N:M). Si solo apunta → FK simple (N:1).

05

El corazón del modelado

Máquina de estados & versionado

Dos capacidades que no son "un campo más": el ciclo de vida gobernado por un enum con transiciones y RBAC por arista, y el versionado como cadena de linaje. Ambas se declaran en el JSON y las ejecuta el motor de core.

5.1 Estado: enum status + transitions

Antes había un motor de workflow relacional (tablas Workflow/WorkflowStatus…); se retiró. Hoy Activity gobierna su estado con un enum cerrado y un grafo de transiciones declarativo, validado por enforceEnumTransitions de core.

Draft→ InReview→ Approved→ Active→ Deprecated→ Archived
objects/activity.json · L134-151json
"status": {
  "enum": ["Draft", "InReview", "Approved", "Active", "Deprecated", "Archived"],
  "static_default": "Draft",
  "transitions": [
    { "from": "Draft",    "to": "InReview" },
    { "from": "InReview", "to": "Approved", "requiredCapabilities": ["activity:approve"] },
    { "from": "Approved", "to": "Active",   "requiredCapabilities": ["activity:publish"] },
    { "from": "Active",   "to": "Deprecated", "requiredCapabilities": ["activity:deprecate"], "requiresComment": true },
    { "from": "Deprecated", "to": "Archived", "requiredCapabilities": ["activity:archive"] }
  ]
}
◆ Por qué

Reemplaza una tabla de workflow por un grafo declarativo. Cada arista puede exigir una capability (activity:approve…) — el mismo string que declaraste en capabilities.json. El cambio de estado se hace por la mutation genérica updateInstance(id, { status }); no hay mutation dedicada. ActivityStatusBadge mapea status → variante de color de forma síncrona, sin query.

▲ Matiz

requiresComment es metadata declarada pero aún no la enforza el motor de enum de core. Al publicar (Approved → Active) hay además un gate de negocio: el árbol de evaluación debe sumar exacto (ver sección 11.3).

5.2 Versionado por linaje

Una versión nueva no es una tabla aparte: es una fila que apunta a su predecesora con previousVersionId (FK reflexiva) y un contador version. La metadata versioning declara toda la mecánica.

objects/activity.json · L39-48json
"versioning": {
  "linkageField": "previousVersionId",
  "versionField": "version",
  "versionStrategy": "increment",
  "stateField": "status",
  "versionableFromStates": ["Approved", "Active"],
  "requiredCapability": "activity:version"
},
"uniqueConstraints": [["previousVersionId", "version"]]
v1Active
←prev—
v2Draft
←prev—
v3Draft

Cada versión apunta a la anterior · getVersionChain() lee la cadena ordenada

◆ Por qué

Lista enlazada en vez de tabla de versiones. versionableFromStates restringe desde qué estados se puede versionar; requiredCapability es un gate RBAC opt-in que el server chequea antes de escribir. El par [previousVersionId, version] como constraint evita ramificar dos veces la misma versión.

✕ Trampas de adopción

1. Poner versioning/prefillFrom fuera de metadata → el sync los descarta en silencio. 2. Olvidar allowsVersioning/estado versionable → el botón no aparece y el resolver responde SOURCE_NOT_VERSIONABLE. 3. El casing de las relaciones lo baja el codegen a minúscula (currentstatus, no currentStatus) — usa el nombre generado o la condición no resuelve.

06

Capa UI

Layouts y vistas

La UI de up1 es config-driven: no escribes pantallas, las declaras en JSON (config/layouts/, 27 archivos en este mod). Un layout describe un RecordList (tabla) o un RecordDetail (form/vista), y el motor los renderiza. Aquí es donde se conectan objetos, filtros, tabs, modals y permisos.

◆ Convención de nombres

default_<Objeto>_<modo>.json — ej. default_Activity_list, default_Activity_view, default_Activity_edit, default_rt__Modality__curricularsection_create. Cada objeto y cada RecordType tiene sus modos create/edit/view/list.

6.1 RecordList: columnas, sort y filtros

default_Activity_list.json · L9-22json
"filters": [
  { "field": "recordType", "operator": "EQUALS", "value": "Course" }
],
"columns": [
  { "key": "name",   "label": "Nombre", "sortable": true, "filterable": true },
  { "key": "status", "label": "Estado", "sortable": true, "filterable": true }
],
"order": { "field": "name", "direction": "ASC" }
◆ Por qué

Cada columna declara sortable/filterable por separado. El filtro fijo recordType: "Course" acota el listado (Activity es un objeto compartido con Service) a solo programas de asignatura. Un audit log global usa en cambio un filtro IN con varios objetos y relationDisplayFields para resolver el FK userId → core_User.name.

6.2 RecordDetail: un tab embebido por RecordType

Aquí se ve el poder del patrón base+RT: el detalle de un Activity declara un tab por cada tipo de sección, y cada tab embebe un record-list filtrado a ese tipo. Así los "objetos compuestos" se editan en su contexto.

default_Activity_view.json · tab + record-list embebido (L16-96, 170-209)json
// 1) el tab, gateado por capability
"modalities": {
  "label": "Modalidades",
  "requiredCapability": "curricularsection:view",
  "elements": ["modalitiesList"]
},
// 2) la lista embebida que el tab renderiza
"modalitiesList": {
  "type": "record-list",
  "objectName": "CurricularSection",
  "layoutConfig": {
    "relations": ["rt__Modality__curricularsection"],
    "columns": [{ "key": "rt__Modality__curricularsection.code", "label": "Código" }],
    "filters": [
      { "field": "ownerId",     "operator": "EQUALS", "value": "{{parentId}}" },
      { "field": "recordType", "operator": "EQUALS", "value": "Modality" }
    ]
  }
}
◆ Por qué

El filtro combina ownerId = {{parentId}} (el id del Activity abierto, resuelto en runtime) + recordType = Modality para traer solo las secciones de ese tipo. Las columnas leen campos del RT con notación rt__X__curricularsection.campo vía la relación declarada en relations. Cada tab tiene su requiredCapability: RBAC por pestaña.

6.3 Crear un hijo desde el tab (canCreateInitialData)

default_Activity_edit.json · L135-141json
"canCreateLayoutId": "default_rt__Modality__curricularsection_create",

"canCreateInitialData": {
  "ownerType": "Activity",

◆ Por qué

9.1 buildTree — lista plana a árbol, con detección de ciclos

const hasCycle = (nodeId) => {
  const visited = new Set([nodeId])
  let cursor = byId.get(nodeId)?.parentId
  while (cursor && byId.has(cursor)) {
    if (visited.has(cursor)) return true   // self-FK corrupta detectada

}

9.3 computeInvalidNodes — suma ponderada del árbol de evaluación

validateWeightedSum.ts · L28-64ts
export function computeInvalidNodes(tree, tolerance = 1e-6) {
  const epsilon = Math.max(0, tolerance)
  const visit = (node) => {
    const children = node.children ?? []
    if (children.length === 0) return
    const expected = toFiniteNumber(node.metric)
    const actual = children.reduce((s, c) => s + toFiniteNumber(c.metric), 0)
    if (Math.abs(expected - actual) > epsilon) invalid.set(node.id, { expected, actual })
    children.forEach(visit)
  }
  tree.forEach(visit); return invalid
}
◆ Por qué

Valida que el peso del padre = suma de hijos directos, con tolerancia para el drift de floats (33.33+33.33+33.34=100). La coerción null/''/NaN → 0 es una decisión de negocio documentada. Clave: esta fórmula se comparte con el backend vía weightedSum.js (sección 11) — misma regla, un solo lugar.

9.4 sanitizeHtmlSafe — anti-XSS con DOMParser

RichTextRenderer/sanitizeHtml.ts · L18-89ts
const ALLOWED_TAGS = new Set(['p','br','strong','em','ul','ol','li','a','table', /* ... */])

export function sanitizeHtmlSafe(html) {
  if (typeof window === 'undefined' || !html) return ''   // SSR-safe
  const doc = new DOMParser().parseFromString(html, 'text/html')
  // 1) loop re-entrante: quita tags fuera de whitelist (y re-evalúa hijos promovidos)
  // 2) whitelist de atributos por tag
  if (name === 'href' && /^\s*(javascript|data):/i.test(attr.value)) el.removeAttribute(attr.name)
  return doc.body.innerHTML
}
◆ Por qué

El monorepo no tiene sanitize-html instalado, así que se usa el DOMParser nativo. Dos capas: whitelist de tags con un loop re-entrante (los hijos que "suben" al eliminar un tag padre se re-evalúan) y whitelist de atributos, con bloqueo explícito de href="javascript:"/data: — los vectores XSS clásicos. Habilita usar v-html de forma segura en el RichTextRenderer.

Resolvers & integridad server-side

La regla de oro: la validación de negocio vive en el resolver, no en el formulario. Cualquier cliente que hable GraphQL directo (MCP, integraciones, otro front) puede saltarse una validación que solo esté en Vue. Por eso el mod concentra las reglas de dominio en los resolvers.

11.1 Override de createInstance: valida y delega

✕ El gotcha del scanner de colisión (CONSTRAINT H7)

El sync acumula todo export con mutation en el nombre en un mapa global y el último gana en colisión, sin error. Por eso: un solo archivo puede definir cada campo Mutation. 11.2 Wrapper polimórfico de updateInstance para rt__

Para las secciones (rt__*__curricularsection) el wrapper no delega, replica la lógica del genérico. La razón es un bug estructural: withEventPublish hace findUnique({ where: { id } }), pero los modelos RT polimórficos no tienen id propio (usan curricularsectionId), así que el pre-fetch del diff de auditoría falla.

◆ Por qué replicar y no delegar

Al replicar, el wrapper controla el pre-fetch correcto vía la base CurricularSection (que sí tiene id) y logra que el audit trail funcione. Costo: mantenimiento manual (mitigado con 8 tests safety-net). Como no pasa por el genérico, emite el evento a mano con publishToChannel en try/catch (row-first, evento best-effort).

Cheat-sheet

Árboles de decisión rápidos

¿Qué relación uso?

Hijo con 1 tipo de padre → directChildren + FK.
Hijo con varios padres → ownerType/ownerId + polymorphicChildren.
Vínculo con atributos → objeto de vínculo N:M.
Solo apuntar a algo compartido → FK simple N:1.
Subtipos que comparten campos → base + recordType.
Jerarquía variable → self-FK parentId.

¿Dónde valido?

Regla de negocio → resolver (server-side), siempre.
Feedback inmediato → helper puro compartido en el front.
Unicidad simple → uniqueConstraints (índice DB).
Unicidad cross-tabla → guard de dominio en el resolver.
Transición de estado → transitions + capability por arista.

npm run codegen --workspace=@uplanner/object-management-backend   # si cambió un objeto
npx prisma migrate dev                                    # si cambió el schema
# nunca editar los destinos synced en core — se regeneran

Los gotchas que más muerden

  • Scanner de colisión: un solo archivo por campo Mutation (createInstance / updateInstance).
  • Sync append-only: borrar un field del JSON no borra el destino en core; hay que borrarlo a mano y re-sync.
  • Casing de relaciones: el codegen las baja a minúscula (currentstatus).
  • metadata: versioning/prefillFrom fuera de metadata se descartan en silencio.
  • 1 .vue por carpeta: los sub-componentes recursivos van en .ts con render functions.
  • Props + i18n: no llames $t en defaults de props; usa fallback en template.
