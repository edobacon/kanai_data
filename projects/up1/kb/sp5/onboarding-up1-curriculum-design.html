¿Qué es UP1?

Una plataforma modular y multi-tenant para instituciones educativas. En vez de programar cada pantalla, declaras objetos y configuración, y la plataforma los materializa.

🧩Modular

Cada funcionalidad grande es un mod que extiende el núcleo sin tocarlo.

🏢Multi-tenant

Una sola app y BD sirven a muchas instituciones aisladas entre sí.

📄Declarativa

Defines en JSON; la plataforma genera tabla, API y pantalla.

Parte 1 Esencial

Multi-tenancy

Una sola base de datos que sirve a muchas instituciones (tenants), aisladas por aplicación. Cada institución ve solo lo suyo y con su propio tema visual.

🔖Cómo se identifica

Cada request lleva su tenant en X-Tenant-ID; la URL es /{tenant}/{objeto}/{layout}.

⚠️La regla clave

Toda consulta filtra por tenantId. Olvidarlo = una institución ve datos de otra (el peor bug posible).

Parte 1 Esencial

¿Qué es un objeto?

La pieza central de UP1: una entidad de negocio (una carrera, un curso, una persona) descrita como JSON. Tiene tres partes.

objects/MiObjeto.json
{
  "title": "MiObjeto",
  "metadata": { "label": "Mi objeto" },
  "properties": {
    "name":   { "type": "string", "not_null": true },
    "status": { "enum": ["Draft", "Active"] }
  },
  "required": ["name"]
}
  • metadata — cómo se llama y se ve el objeto en la UI.
  • properties — sus campos (texto, número, opciones, relaciones…).
  • required — qué campos son obligatorios.
Cada línea tiene una consecuencia visible: un campo enum se vuelve un dropdown; una relación, un picker. (el detalle, en la Parte 2)

Objetos · concepto clave Profundidad

Los 3 patrones de modelado

Casi todo el modelo de UP1 se apoya en tres patrones que se repiten. Reconocerlos es captar la filosofía: minimizar objetos, maximizar abstracción.

RTRecordType

Un campo discriminador dice qué variante es cada fila, sin crear objetos separados.

Como un actor con distintos papeles: el mismo objeto, distinto rol.

▤Composite

Un parentId que apunta al mismo objeto arma árboles jerárquicos con esquema uniforme.

Cajas dentro de cajas: es recursión, no herencia.

◈FK polimórfica

tipo + id (ej. ownerType+ownerId) para apuntar a varias tablas según el caso.

Una dirección general: "la Facultad", sin fijar cuál.
Los verás en los próximos slides RecordType → Curriculum (Plan/Minor). Composite → el árbol de CurricularSection. FK polimórfica → el owner de Curriculum.
Objetos Profundidad

Los 4 tipos: cuándo usar cada uno

BBase

Concepto de negocio propio. Ej: Activity, AcademicProgram.

RTRecord-Type

Variantes 1:1 que difieren en pocos campos. Ej: Plan/Minor.

EExtended

Campos custom por tenant. ext__CLIENTE__obj.

Ccommon.json

De todos: id, createdAt…

✓ Se debe

  • Base cuando es una entidad conceptual nueva.
  • Record-type cuando varios "tipos" comparten estructura — evitas duplicar tablas.
  • Extended solo para lo específico de un cliente.

✕ No se debe

  • Crear varias bases casi idénticas en vez de base + record-types.
  • Meter un campo de un solo tenant en el objeto base.
  • Re-declarar id/createdAt: ya vienen de common.json.
Objetos Profundidad

¿Dónde vive un objeto?

Antes de escribir el JSON decides dónde ponerlo. La ubicación define su alcance: quién lo ve y quién lo puede extender.

business/Base/ core de todos los tenants
Person · Institution
business/Extended/ campos extra de un cliente
ext__UPU__person
tenants/{T}/Base/ objeto solo de ese tenant
solo UPU
mods/{mod}/objects/ objeto de una feature
Activity · Curriculum

✓ Se debe

  • Base si todos los tenants lo necesitan.
  • Extended para un campo de un solo cliente, sin tocar el base.
  • mods/objects/ para tu feature — ahí vive todo curriculum-design.

✕ No se debe

  • Meter un campo de un tenant en el Base global. Qué rompe: lo heredan tenants que no lo quieren.
  • Duplicar un objeto core dentro del mod. Qué rompe: dos fuentes de verdad que divergen.
Objetos · ejemplo: base Profundidad

Un objeto base por dentro (AcademicProgram)

Una carrera es una entidad propia → objeto base. Lo interesante es cómo cada línea define comportamiento. Veamos qué significa cada una.

objects/AcademicProgram.json
{
  "title": "AcademicProgram",
  "metadata": {
    "label": "Programa academico",
    "defaultLayoutType": "RecordList",
    "uniqueConstraints": [["institutionId", "code"]]
  },
  "properties": {
    "name":   { "type": "string", "not_null": true },
    "code":   { "type": "string", "not_null": true,
                "uniqueScopedBy": ["institutionId"] },
    "degree": { "type": "string", "not_null": true,
                "enum": ["Bachelor","Master","Doctorate"] },
    "institutionId": { "type": "string", "not_null": true,
      "isForeignKey": true, "references": "Institution" }
  },
  "required": ["name","code","degree","institutionId"]
}
Qué significa cada campo
labelEl nombre visible en la UI (no el técnico).
defaultLayoutTypeCon qué pantalla abre por defecto (una lista).
not_null: trueObligatorio: el form no guarda sin él; columna NOT NULL.
enumValores fijos → la UI muestra un dropdown.
isForeignKeyRelación a Institution → un picker + relación en BD.
uniqueScopedByEl code es único por institución, no global.
Cómo replicar: escribe el JSON y corre codegen → migrate → sync. Tabla + API + pantalla, sin programar la vista.

Objetos · record-type Profundidad

Record-type: una base, varias variantes

Plan y Minor son el mismo tipo de cosa (un currículo) que difieren en pocos campos. En vez de dos tablas, una base + record-types: una tabla, un discriminador, y cada variante aporta solo lo suyo.

Curriculum.json — discriminador
"recordType": {
  "enum": ["Plan", "Minor"],
  "static_default": "Plan"
}
rt__Plan__curriculum.json — solo lo extra
{ "title": "Plan", "baseObject": "Curriculum",
  "properties": {
    "progression": { "enum": ["Sequential","Modular"] },
    "totalCredits": { "type": "integer" },
    "totalPeriods": { "type": "integer" }
  } }
Cómo funciona recordType es el discriminador: en cada fila guarda "Plan" o "Minor". baseObject: "Curriculum" le dice al codegen "esto extiende Curriculum". Plan agrega columnas; Minor no → una sola tabla contiene ambas.
Qué significa cada decisión

✓ Se debe

  • Declarar en el RT solo los campos extra. El resto se hereda de la base. Si los repites: el codegen ve el campo dos veces y falla.
  • Discriminador como enum con static_default. Al crear nace "Plan" por defecto; la UI ofrece elegir.

✕ No se debe

  • Un objeto base por variante. Qué rompe: duplicas tabla, layouts, permisos e i18n; un cambio común hay que hacerlo dos veces.
  • Olvidar baseObject. Qué rompe: el RT no hereda nada, queda suelto.
Ejemplo: mañana un tipo "Postgrado" → añades "Postgrado" al enum y (si aporta campos) rt__Postgrado__curriculum.json. Cero tablas nuevas.

Objetos · caso: FK polimórfica Profundidad

El owner de Curriculum

Un currículo puede pertenecer a una carrera (Plan) o a una institución (Minor). Necesitamos una relación que apunte a dos tablas distintas según el caso. Una FK normal solo apunta a una. La solución: FK polimórfica = dos campos que dicen "a qué tipo" y "a cuál".

Curriculum.json (recorte)
"ownerType": {
  "enum": ["AcademicProgram", "Institution"],
  "static_default": "AcademicProgram"
},
"ownerId": {
  "type": "string", "not_null": true
  // sin isForeignKey: apunta a distintas tablas
}
Cómo funciona, en 3 pasos 1) ownerType guarda el tipo de dueño. 2) ownerId guarda el id del dueño. 3) En la UI, un composable lee ownerType y consulta la tabla correcta para el picker de ownerId.
Qué significa cada decisión

✓ Se debe

  • Acotar ownerType con un enum. Un enum es una lista cerrada de valores. Cómo afecta: la UI ofrece solo esas opciones y el resolver sabe a qué tabla resolver. Si no: entra cualquier texto y el picker no sabe qué consultar.
  • Validar ownerId en el resolver. El resolver es el código de servidor que atiende la mutation. Por qué: sin FK real, la BD no verifica; sin esa validación guardas un dueño inexistente.

✕ No se debe

  • Poner isForeignKey en ownerId. Ese flag fija una tabla. Qué rompe: el caso "a veces carrera, a veces institución" deja de ser posible y el codegen falla.
  • Dejar ownerType como string libre. Qué rompe: un typo no matchea, el picker queda vacío y el bug aparece en runtime.
Ejemplo concreto: creas un Minor → ownerType = Institution → el picker consulta Institution y eliges "U. del Valle". Mañana un Plan → ownerType = AcademicProgram y consulta carreras. Un solo par de campos cubre ambos.
Objetos · caso: versionado Profundidad

Versionar un currículo

Un plan evoluciona: v1 → v2 → v3, pero todas son "el mismo" plan con el mismo código. El reto: encadenar versiones sin que el código único choque. Se resuelve con versionado por linaje.

Curriculum.json (recorte)
"metadata": {
  "versioning": {
    "linkageField": "previousVersionId",
    "versionField": "version",
    "requiredCapability": "curriculum:version"
  }
},
"code": { "type": "string", "not_null": true
  // NO @@unique: se comparte entre versiones
},
"previousVersionId": {
  "isForeignKey": true, "references": "Curriculum"  // self-FK
}
Cómo funciona Cada versión guarda en previousVersionId el id de la anterior (self-FK: una FK a la misma tabla). Eso forma la cadena v1←v2←v3, el "linaje". El bloque versioning dice cómo numerar y qué permiso exige.
Qué significa cada decisión

✓ Se debe

  • Dejar code sin @@unique. Cómo afecta: como v1/v2/v3 comparten el code, la unicidad "una raíz por (institución, code)" la valida el resolver, no la columna.
  • Gatear con requiredCapability. Solo quien tenga curriculum:version versiona.

✕ No se debe

  • Poner @@unique en code. Qué rompe: la BD rechaza la v2 con el mismo código → versionar es imposible.
  • Setear version a mano. Qué rompe: se descoordina la numeración; dos "v2" en un linaje.
Ejemplo: "Plan Ing. Civil 2026" (v1, code=ICIV) → creas la v2: nace con code=ICIV (igual), version=2, previousVersionId = id de la v1. El código se repite a propósito; las distingue la cadena.
Objetos · caso: composite Profundidad

Composite: secciones y requisitos

Un programa tiene modalidades, resultados, contenidos, sesiones… 7 tipos de "sección" que comparten estructura pero cambian su contenido. El patrón Composite los resuelve con una sola tabla.

▤CurricularSection

Base abstracto (casi sin campos propios) + recordType (7 RTs) + parentId self-FK para el árbol + owner polimórfico al Activity.

⚖️requirement

Mismo patrón, 3 RTs: RecordState (prereq), Group (K de N), MetricThreshold (umbral).

Cómo funciona El base guarda lo común; el contenido de cada tipo vive en su RT 1:1. parentId apunta a otra fila del mismo objeto (self-FK) → así se arma el árbol (una evaluación con sub-evaluaciones).

✓ Se debe

  • Mantener el base delgado. Agregar un tipo es un RT más, no tocar la base ni la pantalla.
  • Filtrar por recordType al listar. Los 7 tipos conviven en la misma tabla.

✕ No se debe

  • Una tabla por tipo de sección. Qué rompe: 7 tablas y 7 sets de layouts; el árbol entre tipos se vuelve inviable.
Ejemplo: en la tab "Evaluación" el árbol "Nota Final → Q1..Q6 + Examen" son filas de CurricularSection con recordType=EvaluationComponent, enlazadas por parentId.
Objetos · caso: campos derivados Profundidad

La entrada de la malla (planEntry)

Cada tarjeta de la malla es un planEntry: "esta asignatura va en este período". Enseña dos ideas: no guardar lo que puedes calcular e integridad protegida por la BD, no solo por la UI.

planEntry.json (recorte)
"activityId": { "isForeignKey": true, "references": "Activity" },
"categoryId": {
  "isForeignKey": true, "references": "requirementCategory",
  "onDelete": "Restrict"   // la BD bloquea borrar una
},                          // categoría con entries
"blockId": { "type": "string" },  // null=obligatoria; si tiene valor=electiva
"credits": { "type": "number" },  // null → hereda de Activity.credits
"period":  { "type": "integer", "not_null": true }
Los dos conceptos Campo derivado = un dato que no se guarda porque se calcula al leer (crédito efectivo, "es electiva"). onDelete: Restrict = regla en la BD que impide borrar una categoría con entries colgando.
Qué significa cada decisión

✓ Se debe

  • Derivar el crédito en lectura. Si credits es null, muestra el de la Activity. Por qué: si el curso cambia, la malla se actualiza sola.
  • Deducir "electiva" de blockId. Un campo define dos cosas, sin flag redundante.

✕ No se debe

  • Persistir un isElective aparte. Qué rompe: duplica blockId; tarde o temprano quedan en desacuerdo.
  • Copiar el crédito de la Activity. Qué rompe: si la Activity cambia, la malla muestra el valor viejo.
Ejemplo: "Ecuaciones Diferenciales" vale 3 créd en su Activity. El planEntry no guarda "3": lo hereda. Si pasa a 4, la malla dice 4 sin tocar nada. Y borrar la línea "Núcleo" con asignaturas: la BD lo impide.
Objetos · reglas Profundidad

Cuando el schema no basta: mutations *Validated

Un programa pasa por estados (Borrador → Revisión → Publicado) con reglas que la BD no puede expresar. Por eso el estado no se edita a mano: se gobierna con mutations *Validated.

escritura del estado
// SÍ — valida 8 pre-condiciones + history atómico
transitionActivityValidated(input)
updateActivityValidated(id, input)

// NO — saltan la validación de negocio
updateActivity(id, input)     // CRUD genérico
prisma.activity.update(...)   // Node directo
Cómo funciona El estado vive en Activity.currentStatusId, read-only para el CRUD. transitionActivityValidated comprueba 8 reglas (la transición existe, sale del estado actual, el usuario tiene permiso…) y cambia estado + historial en una sola operación atómica.
Qué significa cada decisión

✓ Se debe

  • Cambiar el estado solo por la mutation *Validated. Único camino → todas las reglas en un lugar; nadie las salta.
  • Estado + historial atómicos. Nunca queda un cambio sin auditoría.

✕ No se debe

  • Usar CRUD genérico o prisma.update para el estado. Qué rompe: saltan las 8 validaciones → transición inválida, BD inconsistente y difícil de detectar.
  • Ofrecer currentStatusId en el formulario. Es read-only a propósito.
Cómo replicar el patrón: ante una regla que Prisma no expresa (unicidad condicional, transiciones, FK polimórfica), escribe una mutation *Validated y hazla la única puerta de escritura para ese caso.

Vistas · puente Profundidad

Del modelo a la vista

La UI de UP1 no es un render imperativo: es una proyección declarativa del modelo. Cada columna, select o sublista referencia un campo o relación del objeto. Si el modelo es sólido, la vista se arma en minutos.

En el objeto (JSON)En el layout (JSON)En la pantalla
campo enum / static_defaultselect con itemsdropdown de opciones fijas
isForeignKey (mismo scope)columna con relations + relationDisplayFieldscelda con el nombre del relacionado
parentId (self-FK)custom element (tree)árbol jerárquico / drag&drop
relación 1:N (hijos)campo record-list con {{parentId}}sublista embebida
campo status enumeradofiltros + rowActions con conditionsvistas por estado + acciones condicionales
Por qué el orden importa: modelas primero, la vista después. Si el modelo es ambiguo, la vista es "un parche constante".
Vistas Profundidad

La pantalla es JSON (LayoutOrchestrator)

Una pantalla es un layout JSON en la BD. La Suite no usa RecordList/RecordDetail directo — todo pasa por el LayoutOrchestrator, que decide qué renderizar según layoutType y resuelve sublistas y placeholders ({{parentId}}).

✓ Se debe

  • Reusar el layout default y ajustarlo por config.
  • Renderizar siempre vía LayoutOrchestrator.

✕ No se debe

  • Importar RecordList/RecordDetail directo en la Suite.

🗂️Tipos de layout

  • RecordList — tabla con búsqueda, filtros, acciones.
  • RecordDetail — form con tabs y listas embebidas.
  • ChibiList · Dashboard · OfferingCalendar · AiChatbox.
Vistas · ejemplo Profundidad

RecordDetail con tabs: config ↔ pantalla

El detalle agrupa campos en tabs y define cada uno en schema. Una lista embebida es un campo record-list filtrado por {{parentId}}.

default_Activity_view.json (recorte)
"tabs": {
  "general":    { "label": "General",
    "elements": ["name","code","version","credits"] },
  "modalities": { "label": "Modalidades",
    "elements": ["modalitiesList"] }
},
"schema": {
  "modalitiesList": {
    "type": "record-list",
    "objectName": "CurricularSection",
    "layoutConfig": {
      "filters": [
        { "field": "ownerId",    "value": "{{parentId}}" },
        { "field": "recordType", "value": "Modality" } ],
      "openMode": "modal"
    }
  }
}

Vistas · row actions Profundidad

Acciones de fila, propiedad por propiedad

Una row action es un botón en cada fila. Aquí, "Crear nueva versión" de un Activity. Cada propiedad controla un comportamiento.

default_Activity_list.json → rowActions[]
{
  "id": "create-new-version",
  "type": "create",
  "label": "Crear nueva versión",
  "requiredCapability": "activity:version",
  "prefillFromCurrent": true,
  "asNewVersion": true,
  "redirectTo": "edit",
  "confirmCascade": true,
  "visibilityConditions": {
    "operator": "AND",
    "conditions": [
      { "field": "currentstatus.allowsVersioning",
        "operator": "==", "value": true } ]
  }
}
Qué hace cada propiedad
type:"create"La acción crea un registro (vs. modal o mutation).
requiredCapabilitySolo aparece si el usuario tiene el permiso; el server revalida.
prefillFromCurrentCopia los campos de la fila actual al nuevo.
asNewVersion"Es una versión": encadena previousVersionId e incrementa version.
redirectTo:"edit"Tras crear, abre en edición.
confirmCascadePide confirmación (acción con consecuencias).
visibilityConditionsSolo se muestra si el estado permite versionar.
Ojo: la condición usa currentstatus.allowsVersioning; para leerlo, la relación currentstatus debe ir en relations del layout.
Vistas · modal vs ruta Profundidad

Modal vs Ruta

¿Overlay encima, o navegar a una URL propia? Lo decide openMode. Afecta el back del browser y si el link se comparte.

openMode: "modal"
Modal — encima, la URL no cambia. Ideal en listas embebidas: no pierdes el contexto del padre.
openMode: "route" (← Volver)
Ruta — navega a una URL con "Volver". Bookmarkeable y compartible.
La regla: listas de nivel superior → "route" + associatedLayoutConfigs; listas embebidas → "modal". Una row action type:"modal" siempre abre modal.

Capas · i18n Profundidad

i18n: por qué guardas claves, no textos

En el mod ningún texto está escrito "a mano": todo son claves que se resuelven según idioma e institución. Así una universidad llama "Asignatura" a lo que otra llama "Programa", sin tocar código.

lang/es_CL@activity.json (override por objeto)
{
  "column": { "name": "Nombre", "credits": "Créditos" },
  "enums": { "programLevel": {
    "Undergraduate": "Pregrado",
    "Postgraduate":  "Postgrado" } }
}
Cómo funciona es_CL@activity = "español de Chile, solo para el objeto activity" (override por entidad). Al pedir un texto se busca: override del objeto → global del locale → si no, la clave. En el código usas t('column.name') y recibe "Nombre".
Qué significa cada decisión

✓ Se debe

  • Usar t('clave') siempre. El mismo componente sirve en 3 idiomas y cualquier tenant.
  • Labels de enums en el override. "Undergraduate" es el valor guardado; el usuario ve "Pregrado".

✕ No se debe

  • Hardcodear texto (<span>Nombre</span>). Qué rompe: queda fijo, no se puede renombrar.
  • Traducir cambiando el valor del enum. Qué rompe: filtros y lógica que esperan "Undergraduate" fallan.
Ejemplo: "Créditos" viene de column.credits. Un tenant que prefiera "Unidades": un override con "credits": "Unidades" — mismo código, mismo dato, otra palabra.
Capas · RBAC Profundidad

RBAC: el mismo usuario ve cosas distintas

Mismo rol Consultor, misma lista: la única diferencia es tener o no la capability de clonar.

SIN permiso de clonar
Sin permiso — solo Ver y Editar.
CON el permiso
Con permiso — aparece Clonar.
Cómo funciona Una capability es un permiso con nombre (bibliographyreference:clone). El layout gatea la row action con requiredCapability: el frontend muestra/oculta el botón, pero el resolver del servidor lo revalida. La UI no es la seguridad.

✓ Se debe

  • Objeto sin prefijo, módulo con mod/. activity:view vs mod/curriculum-design:approve. Los de objeto se reutilizan entre mods.
  • Revalidar en el servidor. Aunque fuercen la UI o llamen la API directo, el resolver rechaza.

✕ No se debe

  • Tratar "ocultar el botón" como seguridad. Qué rompe: el MCP o GraphQL directo saltan la UI.
  • Poner mod/ en una capability de objeto. Deja de ser reutilizable.
