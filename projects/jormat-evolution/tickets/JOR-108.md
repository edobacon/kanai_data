# Imagenes de item: galeria read-only en vista + subir solo en crear/editar + navegar a la ficha post-guardado

## Request

Correcciones halladas al probar el modulo de imagenes de items (entregado en JOR-107 S4), en la revision del dev:

1. **Subir imagenes "falla"**: hay que revisar por que. Hipotesis del dev: la BD no tiene la tabla nueva (`attachments`) y hay que re-armarla. Si el error es la tabla faltante, correr el script/migracion necesaria.
2. **Galeria en vista debe ser SOLO LECTURA**: hoy al VISUALIZAR un item (modal de detalle o ficha `/inventario/items/[id]`) se vuelve a ofrecer "añadir imagen". Deberia mostrar la **galeria de imagenes del item (solo lectura)**. El **añadir/gestionar** imagenes debe estar SOLO al **crear o editar**.
3. **Navegacion post-guardado**: despues de **crear o editar** un item, deberia llevar a la **ficha del producto** (`/inventario/items/[id]`).
4. **Boton "Cerrar" en la ficha**: al ver la ficha standalone aparece el boton **"Cerrar"**, que es una accion de MODAL. En la pagina (que no es un dialogo) no corresponde — se sale por breadcrumb/back, no "cerrando". Ocultarlo cuando el contexto es la ficha (igual que ya se hizo con "Ver ficha", fix B2 de JOR-107 S2).

## Analisis (investigacion inicial — 2026-07-26)

### 1. El "falla al subir" — NO es un bug de codigo; es la migracion en el entorno del dev

Verificado contra el stack dev levantado (BD `jormat_evolution`, workspace demo):
- La migracion `20260725000000_attachments.ts` **esta aplicada** (`knex_migrations`), la tabla `attachments` **existe**, `migrate:status` = "No Pending Migration files Found".
- El upload por la API **funciona**: `POST /inventario/items/12/images` (multipart) devolvio **201** con la URL firmada. Sin error.

**Conclusion**: en un entorno con la migracion aplicada, subir funciona. Si al dev le falla, es porque su BD es **previa** a la tabla (mergeo la epica pero no corrio la migracion). **Fix inmediato para ese caso**: correr la migracion:
```bash
./run.sh migrate            # docker: exec api npm run migrate
# o dentro del contenedor: npx knex migrate:latest --knexfile knexfile.ts
```
No hace falta re-armar/re-crear la BD entera — solo aplicar las migraciones pendientes (la de `attachments` es aditiva, no destructiva).

> Pendiente a confirmar con el dev: si el fallo que ve es por el **path del navegador** (subir desde el front real, no la API directa), reproducirlo con el stack + login para descartar un problema del flujo front (reconstruccion del File desde blob URL en `MediaCard`).

### 1b. "Imagen cargada aparece rota" — CAUSA RAIZ REAL (fix `8aea0fb`)

Reportado despues por el dev: al cargar el detalle/modal la imagen aparece ROTA. Diagnostico contra la API real (no la carrera del browser):
- El **serving** funciona: la URL firmada devuelve HTTP 200 + bytes PNG validos (ruta binaria `/api/uploads` de S4 OK). El branch `readOnly` renderiza `<img src={url}>` bien. TTL 5min pero `staleTime=0` (refetch por apertura) → descarta cache/expiracion.
- El **UPLOAD** corrompia el archivo: el front sube multipart por `/api/proxy` (baseURL de axios), y ese proxy compartido leia el request body con **`await req.text()`** → decodifica como UTF-8 y corrompe binarios al re-enviar. **Reproducido**: PNG de 268 bytes subido → 478 bytes corruptos (sin firma PNG). El archivo se guardaba corrupto en disco → al verlo, roto.
- **Fix** (`8aea0fb`): el proxy reenvia el body como `arrayBuffer` (bytes crudos). Verificado: 268 bytes → **268 identicos** con firma PNG valida. Test del proxy nuevo (binario intacto / JSON ok / GET sin body).
- **Impacto extra**: el mismo proxy corrompia TODO upload multipart → tambien el **import CSV** (S5 lo probo por el service directo, sin el proxy, por eso paso). Este fix lo repara en el flujo real del browser.
- Es la misma clase de bug que el `.text()` de la DESCARGA (arreglado en S4 con la ruta binaria), pero del lado del REQUEST, que quedo sin cubrir en S4.

### 2. Galeria read-only en vista (el defecto de diseno real, de JOR-107 S4)

`ImageGalleryUploader` (componente con subir/borrar/reordenar) se usa en 3 lugares:
- `components/items/detail/MediaCard/MediaCard.tsx` — **DETALLE (vista, modal + ficha)** ← incorrecto: es contexto de solo-lectura pero ofrece subir/gestionar y persiste directo via `useUploadItemImage` (POST /:id/images).
- `components/items/create/ItemCreateForm/ItemCreateForm.tsx` — crear/editar (correcto).
- `components/shared/builder/LineItemsTable/LineItemsTable.tsx` — otro contexto builder (fuera de alcance).

Ademas, `ImageGalleryUploader` **no tiene modo read-only** (siempre muestra Upload/Trash/GripVertical).

**Direccion propuesta** (a validar en design):
- En el **detalle** (`MediaCard`/`ItemDetailContent`, modal y ficha): mostrar una **galeria de solo lectura** (imagenes + preview, sin añadir/borrar/reordenar). Quitar del detalle el `ImageGalleryUploader` editable y el `useUploadItemImage`.
- Opcion A: agregar un prop `readOnly` a `ImageGalleryUploader` (oculta acciones de subir/borrar/reordenar). Opcion B: un componente `ItemImageGallery` (read-only) aparte para la vista. Decidir en design (reuso vs separacion).
- El **añadir/gestionar** imagenes queda SOLO en crear/editar (`ItemCreateForm`).
- **Resolver la persistencia en edicion**: hoy el detalle persistia directo; si el manejo se mueve a crear/editar, confirmar como persiste el form las imagenes al guardar (el endpoint POST/DELETE /:id/images ya existe; `itemDetailToFormValues` documenta que las imagenes "se editan por endpoint aparte, no entran al PATCH"). Definir el flujo: el uploader del form persiste via el endpoint de imagenes al guardar el item (o inmediatamente, como hoy en el detalle).

### 2b. Afordances de modal que se filtran a la ficha standalone (`context='page'`)

Al extraer `ItemDetailContent` en JOR-107 S1, el footer completo del modal quedo compartido con la ficha. El fix B2 (S2) ya oculta **"Ver ficha"** en `context='page'`. Falta el mismo tratamiento para el boton **"Cerrar"**: en la ficha standalone (no hay dialogo que cerrar) no corresponde — la salida es por breadcrumb/back. Ocultar "Cerrar" cuando `context==='page'` (mismo patron ya existente en `ItemDetailContent`). Revisar de paso que no queden otras afordances de modal en la pagina (ej. la semantica del selector de bodega en la ficha vs el modal — confirmar que aporta o dejarlo).

### 3. Navegacion post-guardado -> ficha del item

Hoy, tras crear/editar, `ItemCreateForm` navega al **listado** (`/inventario/items`) — ej. el clone (JOR-107 S1) mostraba `toast + push('/inventario/items')`. El dev quiere que lleve a la **ficha** (`/inventario/items/[id]`, ruta creada en JOR-107 S1).
- **Crear**: el alta devuelve el id del item creado -> `push('/inventario/items/{id}')`.
- **Editar**: ya se conoce el id -> `push('/inventario/items/{id}')`.
- Confirmar el caso Clonar (crea nuevo): tambien a la ficha del nuevo id.
