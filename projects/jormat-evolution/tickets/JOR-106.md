## Analisis: por que baja y por que el gate falla hoy

El `test:cov` mide **solo la suite unit** (`jest.config.ts`). La estrategia del equipo separa a proposito:
- Logica de negocio (services, controllers, DTOs, guards) -> unit tests -> ~100%.
- Acceso a datos (repositories, SQL Knex) -> se prueba por **e2e** contra una BD efimera (`jest.e2e.config.ts`, JOR-041, `maxWorkers:1`).

Existen 6 suites e2e que **si ejercitan** los repositories: `catalogos-read.e2e-spec.ts`, `catalogos-write.e2e-spec.ts`, `catalogos-clientes-reuse.e2e-spec.ts`, `customers.e2e-spec.ts`, `items-read.e2e-spec.ts`, `items-write.e2e-spec.ts` (instancian repos/servicios directo contra la BD de test). Pero `jest.e2e.config.ts` **NO recolecta coverage** (`collectCoverage` ausente) y su reporte no se une al de unit. Resultado: el repo se ejecuta en e2e pero figura 0-21% en el unico reporte que corre el gate.

Consecuencia: el gate de 90% sobre unit-only es, hoy, inalcanzable por diseno (mide una capa que a proposito no tiene unit tests). O se mergea la cobertura, o se ajusta que mide el gate.

## Decision pendiente (bloqueante del design): que estrategia de coverage

| Opcion | Que | Pros | Contras |
|--------|-----|------|---------|
| **A. Merge e2e + unit** (recomendada) | `jest.e2e.config.ts` recolecta coverage; combinar reportes unit+e2e (istanbul/nyc merge o `coverageDirectory` separados + merge) y aplicar el gate de 90 sobre el merge | Refleja la cobertura real de los repos sin escribir tests nuevos; fiel al patron logica=unit / datos=e2e; el gate vuelve a ser alcanzable y significativo | Requiere infra de merge en el runner + CI corre e2e (necesita BD efimera, mas lento); el numero por-archivo mezcla dos suites |
| **B. Unit tests de repos con Knex mockeado** | Mockear `db` (Knex) y testear cada metodo del repository armando el query builder esperado | Sube cobertura unitaria "pura", sin BD | SQL contra mock es fragil y de bajo valor (testea el mock, no el SQL real); duplica lo que ya cubre e2e; alto costo de mantenimiento |
| **C. Excluir repositories del gate unit** | Agregar `!**/*.repository.ts` a `collectCoverageFrom` | Rapido, hace pasar el gate | El SQL queda sin medicion en el gate; el 90 se vuelve cosmetico; oculta regresiones de la capa de datos |

Recomendacion: **A**. Deja el gate midiendo lo que realmente se ejercita. B y C se documentan como descartadas salvo que el dev prefiera lo contrario.

**DECISION (2026-07-24): opcion A confirmada por el dev.** El gate de 90% pasa a medir el merge de cobertura unit + e2e. B (Knex mockeado) y C (excluir repos del gate) quedan descartadas. Track 1 del plan de test queda habilitado (e2e con coverage + merge + gate sobre el merge). Los quick wins unit (Track 2) son independientes de esta decision y suben cobertura real igual.

Independiente de A/B/C, hay quick wins de unit test que suben cobertura real (controller + validator + csv), abordables ya.
