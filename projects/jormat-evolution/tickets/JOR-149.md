# Unificar identidad de inventario a serial + uuid y cerrar toda la fachada publica por uuid

## Request

Llevar el dominio de inventario al modelo de identidad objetivo y cerrar todas las divergencias
detectadas en el catastro de [[JOR-148]] (verificado contra `epic/jormat-v1`). Modelo objetivo:

1. **Todo registro tiene id incremental (serial) + uuid.** Las tablas uuid-native del dominio hoy no
   tienen serial; se les agrega.
2. **En la fachada publica, TODAS las relaciones se exponen/aceptan por uuid.** Los FK internos siguen
   apuntando al serial (la fachada resuelve uuid -> serial en el limite); ver D-FK.

Se ejecuta sobre `epic/jormat-v1` con datos dev, por lo que se aceptan cambios de esquema y migracion
de datos (backfill). Alcance ampliado respecto del catastro inicial: entra tambien lo que antes estaba
diferido (identidad serial+uuid en uuid-native, backfill de snapshots, downstream de sales/purchases).

**Objetivo central — homologar a UNA sola regla.** Este ticket homologa el modelo de identidad de todo
el dominio a un unico estandar, con `items` y `trucks` como **modelo canonico**: dos campos, `id`
incremental + `uuid`; el **uuid se usa para las relaciones publicas**, el **id (serial) puede usarse en
las relaciones internas**. Se elimina la coexistencia de dos moldes (fachada-serial vs uuid-native) que
la regla permite hoy. RULE-api-001 se reescribe a ese estandar unico (ver "Regla homologada" abajo).

> **Nota de estado**: ticket scaffoldeado con el request y el diagnostico verificado contra
> `epic/jormat-v1`. NO se corrio design ni execute. Proximo paso: `design-improvement` para convertir
> los casos en REQs + tasks. Tier T3 por tocar esquema + migracion de datos + cross-module.

#### Re-apuntado de trucks.client_id (R1) — detalle

Estado actual (epic, verificado): como `customers` es uuid-native, trucks guarda/joina/expone el uuid
del cliente directo, sin resolucion uuid -> serial.
- `trucks.client_id` uuid NOT NULL, FK -> `customers.id` (uuid): `migrations/20260813000003_trucks_facade.ts:47`
- `create`: `client_id: input.clientId` guarda el uuid: `src/trucks/trucks.repository.ts:191`
- `isActiveClient`: `where('customers.id', clientId)` valida el uuid: `src/trucks/trucks.repository.ts:230`
- `joinedScope`: `.join('customers','customers.id','trucks.client_id')` (uuid): `src/trucks/trucks.repository.ts:243`
- `SELECT_COLS`: `'trucks.client_id as client_id'` expone el uuid: `src/trucks/trucks.repository.ts:97`
- DTO `clientId` uuid (`@IsUUID`), inmutable en edicion: `src/trucks/dto/truck.dto.ts:106,129`

Enfoque **R1** (relacion interna por serial, publico por uuid; coherente con D-FK). El contrato publico
NO cambia (`clientId` sigue uuid; front intacto). Cambios:

1. **Esquema**: `trucks.client_id` uuid -> **integer**, FK -> `customers.id` (serial). Backfill (customers
   primero): `UPDATE trucks SET client_id = c.id FROM customers c WHERE c.uuid = trucks.client_id`. En dev
   trucks suele estar vacio (trucks_facade aborta con filas).
2. **`create`**: resolver `input.clientId` (uuid) -> serial de customers antes de insertar (paso de
   resolucion nuevo, como los pivotes de items).
3. **`isActiveClient`**: `where('customers.uuid', clientId)` (validar por uuid) devolviendo el serial.
4. **`joinedScope`**: el join queda `customers.id = trucks.client_id` con AMBOS serial (semantica nueva).
5. **`SELECT_COLS` (CRITICO)**: hoy `'trucks.client_id as client_id'` pasaria a exponer el **serial** ->
   **fuga del id interno, viola RULE-api-001**. Debe cambiar a **`'customers.uuid as client_id'`**. Es el
   cambio que realmente cierra la fachada del cliente en trucks.
6. **DTO**: sin cambios (`clientId` sigue uuid).

Alternativa **R2 descartada** (FK uuid -> `customers.uuid`): igual hay que mover los joins de
`customers.id` a `customers.uuid`, y deja una relacion interna referenciando un uuid, contra el principio
"internas por serial". No es cero cambios y rompe la uniformidad.

**Coordinacion con [[JOR-147]]**: R1 revierte parcialmente lo que trucks_facade (JOR-147) hizo
(`client_id` uuid -> `customers.id`). Como JOR-147 vive solo en `epic/jormat-v1` (no shippeado), decidir
en design si JOR-149 lo corrige encima o si se ajusta el enfoque de `trucks_facade` en origen.
2. **Guards uuid (DV1, DV3, DV4)**: extraer `UUID_RE` a `common/uuid.util.ts` (hoy repetido inline) y
   guardar -> 404 en catalogos-repuestos, item-images (`attachmentId`) y customers.
3. **Contrato filtro itemId (DV5)**: no-uuid -> 400 en `items.repository` (alinear con `parseUuidCsv`).
4. **Snapshot catalogos_repuestos por uuid (DV2)**: validar miembros como uuid, actualizar Swagger, y
   **backfill** de snapshots existentes (serial -> uuid, resolviendo por la maestra).
5. **Downstream sales/purchases/payments (DV6)**: line items referencian el item por uuid; migrar la
   data mock/seed. Revisar consumidores en front de esos line items (contrato ya string).
6. **Gap de filtros catalogos_repuestos (GF1)**: `search` + paginacion server-side si la pantalla lo
   requiere (confirmar en design).
7. **Guardarrail de regresion**: extender `inventory-uuid-regression` e2e: id malformado -> 404 (no
   500) en catalogos_repuestos/customers/item-images; `itemId` no-uuid -> 400; miembros del snapshot

8. **Tests de dominio + migracion**: actualizar unit/e2e afectados (ver "Impacto en documentacion y

### Regla homologada (target de RULE-api-001)

Texto objetivo de la regla tras este ticket (se aplica al archivo vivo en execute, cuando el codigo ya
cumple; hoy NO se sobrescribe porque una regla `must` no puede afirmar algo que el codigo aun incumple):

- **Modelo canonico**: `items` y `trucks` (dos campos: `id` serial + `uuid` unique).
- **Toda tabla de negocio tiene DOS campos**: `id` = serial incremental (PK interno) + `uuid` = uuid
  unique (identificador publico). Se elimina el molde uuid-native (PK uuid como `id` sin serial): las
  tablas que hoy lo usan (customers/attachments/catalogos_repuestos) se migran al modelo canonico.
- **Relaciones publicas por uuid**: cualquier identificador o referencia que cruza la API (propio o de
  una entidad relacionada) es el uuid. El serial nunca se emite ni se acepta (`:id` no-uuid -> 404).
- **Relaciones internas por serial**: los FK entre tablas del dominio apuntan al `id` serial; la
  resolucion uuid -> serial ocurre una sola vez en el limite del repo.
- **DTO**: el identificador se llama `id` y su valor es el uuid (un solo shape de cara al front; sin
  cambio respecto de la regla actual).
- **Tabla nueva**: nace con los dos campos. Una tabla de negocio sin ambos es un incumplimiento.
- **Plataforma/auth** (workspaces/users/roles/...): alcanzadas por el estandar pero con compliance
  pendiente (migracion en ticket propio, D-PLATFORM).

Nota: esto REESCRIBE las lineas 19 y 30 de la RULE-api-001 actual (que hoy dicen "NO se agrega un campo
uuid separado" y citan customers/catalogos_repuestos como molde uuid-native correcto). El invariante de
seguridad (serial nunca cruza la API, anti-IDOR) se conserva.
