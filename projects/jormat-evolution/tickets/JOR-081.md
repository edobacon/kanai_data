### Learns

- **L1 (2026-07-22) — `items.repository.ts` casi no lo muerden los tests (evidencia de mutación)**: mutation testing (stryker, scoped) dio **~1% en covered / 151 mutantes sin cobertura** en `items.repository.ts`. El mutante que blanquea el nombre de tabla (`this.db('items')` → `this.db('')`) **sobrevive** porque los tests del repo son mocks de knex que ignoran el argumento de tabla. El listado "funciona" solo por verificación manual (query real, 11 items). **Impacto en S1**: `S1.T4` (integration tests contra DB real) NO es opcional — es lo que sube esa cobertura de mordida de ~1% a real. Cualquier método nuevo (findById/getSummary) que se pruebe solo con mock repetirá el gap. Fuente: run de stryker 2026-07-22.
- **L2 (2026-07-22) — aparato stub queda parcialmente huérfano tras conectar read paths**: al conectar `getSummary`/`findOne` a DB, `ItemsService.findAll` (JOR-064 catalog filter) pierde su único consumidor de producción, pero `STUB_ITEMS`/`STUB_DETAIL` + helpers (`parseCsv`/`matchesAny`/`compareItems`) siguen sosteniendo los stubs de `create`/`update`. Limpieza diferida a **S2.T3**, donde al conectar el write path se puede remover el aparato completo de una vez (removerlo en S1 sería parcial). Tracking para no dejar dead code al cerrar.
- **L3 (2026-07-22) — DEC-LOCAL-4 (scope del gating de costo)**: `priority`/`failure` se exponen en listado y detalle (no sensibles, ya fetcheados); `costoCompra` se expone SOLO en el detalle, gateado por `items.parts:cost-view`. Rationale: evita threadear capabilities por el path del listado (que hoy funciona) — menor superficie de regresión — y el costo per-item es dato de ficha, no de tabla. Si el front necesita costo en el listado, es follow-up (threadear `canViewCost` en `findAllPaginated`/`mapRowToDto`, ya preparado porque la query fetchea `net_price`).
- **L4 (2026-07-23) — el dual-judge sobre el write path caza lo que el test-suite verde esconde**: S2 cerró con 12/12 integration verdes contra DB real, PERO el dual-judge (2 jueces ciegos) descubrió que el write path no funcionaba end-to-end (C1: el catálogo servía ids stub `cat-001` que el front manda pero el repo no puede castear) + una fuga cross-tenant en los FK de catálogo (C2). Ni los unit ni los integration lo veían porque los fixtures usaban ids enteros que coincidían con las tablas reales — nunca ejercían el id REAL que el front envía. Lección: para paths que cruzan capas (front→API→DB con catálogos), el test verde con fixtures propios NO prueba el contrato real; el juez adversarial que rastrea la fuente real del dato (CatalogosService) sí. Refuerza por qué DET-35 (dual-judge) va en T3.
