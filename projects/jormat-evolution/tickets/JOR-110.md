# Dinamizar catálogos de repuestos a DB

## Request

Migrar el CRUD de "catálogos de repuestos guardados" (backend/jormat-api/src/items/catalogos-repuestos.*) del stub in-memory actual a persistencia real en PostgreSQL vía Knex, para que los catálogos guardados sobrevivan al reinicio del proceso y queden aislados por workspace. El frontend (/inventario/catalogos, CatalogoDto) ya está conectado; el contrato CatalogoDto queda congelado. Es el paso "modelo real" que el propio stub anticipa ("cuando llegue el modelo real, solo cambia la fuente"), y sigue el mismo patrón que JOR-057 (stub) -> JOR-082 (dinamizado a DB) del módulo src/catalogos.

### Context found

- **Stub actual** (`src/items/`): `catalogos-repuestos.service.ts` (array `this.store` + `seq`, sin Knex), `catalogos-repuestos.controller.ts` (`@Controller('inventario/catalogos')`, guards + capabilities `items.catalogs:view|edit|delete`), `dto/catalogo.dto.ts` (contrato congelado). Registrado en `items.module.ts:29` como provider directo.
- **Modelo del catálogo** (`CatalogoDto`): metadata (`descripcion`, `marca`, `oferta`) + 4 relaciones N:M como arrays de ids (`aplicaciones[]`, `categorias[]`, `proveedores[]`, `items[]`) + `createdAt`.
- **Patrón canónico a espejar** (`src/catalogos/catalogos.repository.ts`): interfaz de repositorio + `KnexCatalogosRepository` bajo token `CATALOGOS_REPOSITORY`, `tenantScoped` (RLS removida — el filtro por `workspace_id` es la frontera real), `insert().returning()`.
- **Molde de tabla app-native** disponible como referencia: `migrations/20260723000000_customers.ts` y `20260725000000_attachments.ts` (uuid PK + workspace_id FK + timestamps). Última migración: `20260725000000_attachments`.
- **Deuda relacionada (no bloquea, se registra)**: la tabla `providers` no tiene columna `rut` real (JOR reciente: el `<Select>` de proveedor recibía `rut=""`); los ids de relación que guarda el catálogo son los que envía el frontend desde los endpoints ya conectados.

Migración `20260726000000_catalogos_repuestos.ts` | Consistencia con las tablas app-native recientes; el id opaco (uuid) no afecta al frontend |

## Summary

JOR-110 queda implementado y cerrado: los catálogos de repuestos guardados ya no viven en memoria del proceso, sino en la tabla PostgreSQL `catalogos_repuestos`, acotada por `workspace_id`. El contrato HTTP y el `CatalogoDto` se mantienen estables para el frontend existente (`/inventario/catalogos`). La implementación usa repositorio Knex por interfaz, `tenantScoped` para lectura/edición/borrado, hard-delete para conservar el 204 actual, y columnas `jsonb` para las cuatro selecciones (`aplicaciones`, `categorias`, `proveedores`, `items`) según decisión del ticket.

Datos canónicos de cierre:
- Modelo DB: `backend/jormat-api/migrations/20260726000000_catalogos_repuestos.ts`.
- Acceso a datos: `backend/jormat-api/src/items/catalogos-repuestos.repository.ts`.
- Service/controller conectados: `backend/jormat-api/src/items/catalogos-repuestos.service.ts`, `backend/jormat-api/src/items/catalogos-repuestos.controller.ts`.
- DI: `backend/jormat-api/src/items/items.module.ts`.
- Pruebas: unit/controller + e2e DB real verdes, registradas en `Testing`.

Nota de consistencia documental: cualquier referencia previa en `jormat_docs` o comentarios antiguos que describa estos catálogos como “stub in-memory” corresponde al estado anterior a JOR-110. El estado canónico posterior a este ticket es persistencia real en DB.
