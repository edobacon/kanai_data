### Decisión: alcance de Camiones (incluir vs excluir)

**Hechos (verificados en captura + código nuevo):**
- Camión (ficha) depende de: **Cliente** (autocomplete, requerido) + **Marca** (select).
- **Cliente**: YA existe fuente en el nuevo sistema (`useClientes(q)` → `GET /catalogos/clientes?q=`, usado en Ventas/Pagos; legacy `/api/clients/dsname`). El camión solo necesita **buscar/seleccionar** cliente existente → reusa lo que hay, NO exige un mantenedor de clientes nuevo.
- **Marca**: NO existe catálogo de marcas en el nuevo front (en items `marca` es texto libre). El select de Marca del camión necesitaría fuente (catálogo nuevo o degradar a texto libre).
- **Nadie del core depende de camiones**: categorías, aplicaciones, catálogos (generador) e items funcionan sin las fichas de camión. La ficha es un registro cliente↔vehículo aislado.

| Opción | Qué implica | Impacto | Costo |
|--------|-------------|---------|-------|
| **A — Incluir camiones** | tabla `trucks` (modelo rico) + CRUD + modal + reuso del buscador de clientes (existe) + **resolver fuente de Marca** (catálogo nuevo o texto libre) | Suma la feature de registro de vehículos por cliente. Requiere clientes accesibles (ok) + decidir Marca | Alto (entidad rica + 2 dependencias) |
| **B — Excluir camiones (por ahora)** | alcance = Categorías + Aplicaciones (CRUD) + Catálogos (generador) + RBAC. Camiones a ticket aparte | **Cero impacto en el core**: los otros mantenedores + items + generación de catálogos quedan completos. Se pospone solo el registro de vehículos | Bajo — desbloquea el resto ya |

**Recomendación (a confirmar por el dev)**: **Opción B** para este ciclo — entrega el valor pedido (categorías/aplicaciones/catálogos gateados) sin arrastrar las dependencias de camiones (Marca sin catálogo, entidad rica). Camiones → ticket propio que reusa el buscador de clientes y define la fuente de Marca. Si el negocio necesita camiones ya, Opción A con Marca como texto libre v1.

> **RESUELTO (dev, 2026-07-04): Opción B — excluir camiones.** Alcance de este ciclo: **Categorías + Aplicaciones** (mantenedores CRUD) + **Catálogos** (generador) + **RBAC** (capabilities view/edit/delete por mantenedor + grant a internal-admin). **Camiones** se difiere a un ticket propio (backlog B7) que reusará el buscador de clientes existente y resolverá la fuente de Marca.

### Decisión de diseño: crear/editar como MODAL + guard de dismiss (dev, 2026-07-04)

En vez de páginas completas (como el legacy y como `ItemCreateForm`), los formularios de **crear/editar** de los mantenedores serán **modales**, con el guard de cambios sin guardar (JOR-063) al hacer dismiss.

| Vista | Forma óptima | Por qué |
|-------|--------------|---------|
| Categorías (crear/editar) | **Modal** (2 campos) | Consistente con `CreateRoleModal`/`UserFormModal`; mantiene el contexto del listado; ágil |
| Aplicaciones (crear/editar) | **Modal** (2 campos) | idem |
| Catálogos (generador) | **Vista completa** (NO modal) | Es un builder (filtros + grilla de items + Generar/Imprimir); un modal quedaría apretado. Patrón `TransactionBuilder` |
| Camiones (diferido) | Modal (7 campos) | El legacy ya usa modal "Ficha Camión"; encaja al construirlo (B7) |

**Patrón técnico del modal-con-guard** (reusa lo existente, sin reinventar):
- `Dialog` controlado: `open` + `onOpenChange={(isOpen) => { if (!isOpen) requestLeave(() => onClose()); }}` — una sola intercepción cubre Escape / clic fuera / botón X (Radix los enruta todos a `onOpenChange(false)`).
- `const { requestLeave } = useUnsavedChangesGuard({ when: isDirty })` — dirty → muestra `UnsavedChangesDialog` (ya existe); limpio → cierra directo. Botón Cancelar también vía `requestLeave(() => onClose())`. Precedente: `AplicarPagoView` (`requestLeave(() => router.back())`).
- `useFormMountBaseline(methods)` dentro del form + **remonte por apertura** (`key`/`reset` al abrir) → `isDirty` parte en false cada vez que se abre (evita el falso dirty JOR-063).
- Los vectores ruta/link/back/recarga siguen cubiertos automáticamente por `NavigationGuardProvider` (si el usuario navega con el modal sucio).
- **Stacking**: el `UnsavedChangesDialog` (confirmación) monta sobre el `Dialog` del form (ambos Radix, portaled); el form permanece `open` hasta que el usuario confirme "Salir sin guardar".

**Optimización de mantenibilidad**: extraer un hook/wrapper reusable (`useUnsavedChangesModal({ isDirty, onClose })` → devuelve el `onOpenChange` guardado) para que todos los modales-form compartan el comportamiento. Además permite **retrofit** de `CreateRoleModal`/`UserFormModal` (hoy cierran sin guardar) → consistencia global. Ver backlog B8.

### Relaciones / dependencias (evidenciadas por lo que carga cada form/vista)
```
Item (repuesto) ──N:M──> Categoría        (clasificación; item form carga /categorias)
Item ──N:M──> Aplicación                  (modelos a los que aplica; item form carga /aplicaciones)
Item ──N:M──> Proveedor                   (item form carga /proveedores)
Camión (ficha) ──N:1──> Cliente           (modal Ficha Camión carga GET /api/clients/dsname?name= )  ⭐dependencia nueva
Camión ──> Marca                          (select de marca en el modal)
Catálogo (generador) ──filtra por──> Categorías × Aplicaciones × Proveedores × Marca × Oferta
```
- **Dependencia bloqueante para el rediseño**: para crear una **Ficha de Camión** se necesita el mantenedor/búsqueda de **Clientes** (autocomplete). Camiones NO es standalone.
- **Categorías y Aplicaciones son standalone** (crear solo pide nombre+código; sus forms no cargan otros servicios — `api=[]`).
- **Catálogos** (generador) y **Items** son los **consumidores** de categorías/aplicaciones/proveedores. Si estos mantenedores cambian, impactan el form de item (vista 06), el detalle (05), el listado con filtros (04) y el generador de catálogos.
- **Asimetría de permisos por fila**: aplicaciones solo expone "Visualizar" desde la fila; categorías y camiones exponen editar/eliminar → el RBAC por-acción del rediseño debe soportar esta granularidad (view vs edit vs delete por mantenedor).

### Vínculo items ↔ mantenedores (puntos de consumo + gap ID/nombre)

Dónde items consume categorías/aplicaciones/proveedores (el "vínculo" a establecer):

| Punto de consumo | Archivo | Cómo referencia hoy |
|------------------|---------|---------------------|
| Crear/editar item (MultiSelect) | `ItemCreateForm.tsx` (opts `{value: c.id, label: c.nombre}`) | **por ID** (`useCategorias/useAplicaciones/useProveedores`) |
| Listado — filtros | `ItemsListView.tsx:67-69,116-124` (`item.categorias?.includes(id)` + `find(c=>c.id===id).nombre`) | **por ID** (asume `item.categorias` = ids) |
| Detalle (vista 05) | `ItemDetailModal.tsx:68,91-103` (`item.categorias.map / join`) | muestra strings tal cual |
| Detalle → form (edición) | `itemDetailToFormValues.ts:29-31` (⚠️ limitación documentada) | detalle devuelve **nombres**, el form espera **ids** → no resuelve |
| Backend | `items/dto/{item,create-item}.dto.ts` (`string[]`) + `items.service.ts:64-66` stub | **nombres** (`['Frenos']`, `['Volvo FH']`, `['INPART']`) |

**Gap (causa del vínculo roto)**: items guarda/lee `string[]` que en el stub son **nombres**, pero el front (form + filtros) los trata como **IDs**. Inconsistencia ID↔nombre.

**Requisito del rediseño (fuente de verdad = los mantenedores)**:
- Los mantenedores exponen `{ id, codigo, nombre }` estables (IDs).
- Items **referencia por ID** (categorías/aplicaciones/proveedores como arrays de ids); se **resuelve a nombre** para display (el front ya sabe hacerlo con `find(c=>c.id===id).nombre`).
- Alinear el **detalle de item** para devolver IDs (no nombres) → `itemDetailToFormValues` deja de ser lossy y el ciclo crear→editar→listar es coherente.
