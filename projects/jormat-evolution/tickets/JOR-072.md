# KPIs de Documentos: endpoint summary server-side (dejar de traer todo el catálogo)

## Request

Escindido de [JOR-071](JOR-071.md) (T3). Las KPI cards de la vista Documentos (Total / Pendientes / Aceptados / Rechazados / Total facturado) se calculan client-side desde `useDocumentosResumen()`, que pide `limit: 1000` para traer TODO el conjunto y contar. Contra el backend real eso da **400** (excede `@Max(100)`, RULE-global-002), y aunque no lo diera, agregar contando 10k+ filas client-side es ineficiente. Falta un endpoint de **summary server-side** para documentos (como ya existe para items: `getItemsSummary`/`useItemsSummary`).

## KB consulted

- **Specs**: [SPEC-tables-server-side-pagination](../specs/SPEC-tables-server-side-pagination.md) (JOR-068) — introdujo el cap `@Max(100)`.
- **Rules**: [RULE-global-002](../rules/global/RULE-global-002.md) — no debilitar el cap; la solución es un endpoint de agregación, no subir el límite.
- **Ticket origen**: [JOR-071](JOR-071.md) (fix, closed) — resolvió el lado items (builder + catálogo) y escindió esto.

## Discoveries / decisions

- **D1**: `useDocumentosResumen` (`front/jormat-front/src/hooks/useVentas.ts:53`) usa `listDocumentos({ limit: 1000 })`. `ListDocumentosQueryDto extends PaginationQueryDto` → hereda `@Max(100)` → 400.
- **D2 — Decisión (de JOR-071)**: NO usar paginar-hasta-agotar (`fetchAllPages`) para documentos: con 10k+ filas serían 100+ requests en cada carga de la vista. El patrón correcto es agregación en la DB.
- **D3 — Precedente**: items ya tiene `GET /inventario/items/summary` (`ItemsSummary` = total + conStock/bajoStock/sinStock). Espejar ese patrón para documentos.

## Propuesta (a refinar en design)

### Backend
- Nuevo endpoint `GET /api/ventas/documentos/summary` (o `/resumen`) que devuelva los agregados que hoy calcula el front: `total`, `pendientes` (estadoComercial=pendiente), `aceptados` (estadoSII=aceptado), `rechazados` (estadoSII=rechazado), `totalFacturado` (suma de total).
- Calcular con agregaciones Knex (`count`/`sum` + `where`), filtrado por `workspace_id` (aislamiento). RBAC: misma capability que el listado (`sales.documents:view`).
- DTO de respuesta tipado + Swagger. Tests unit (service) + e2e (controller).

### Frontend
- Reemplazar `useDocumentosResumen` (limit:1000) por `useDocumentosSummary()` que consuma el nuevo endpoint (patrón `useItemsSummary`). `DocumentosListView` consume los counts del summary.
- Ajustar/crear tests (MSW) del nuevo endpoint y de la vista.

## Summary

**Qué se hizo**: 3 endpoints `/summary` server-side (documentos, cobranza, facturas-proveedor) que agregan los KPIs sobre el MISMO universo filtrado que su listado (helper `filterX` compartido en cada service). El frontend consume `useXSummary(filtros)` con key de React Query por filtros → los KPIs reflejan lo filtrado y recalculan al cambiar filtros. Se corrigió: el 400 de documentos/pagos (limit:1000 vs @Max(100)) y el conteo incorrecto de facturas-proveedor (antes solo la página). Iconos/colores de los cards alineados a maqueta (Pagos Clientes) y patrón canónico (Facturas Proveedor).

**Cómo se validó**: backend `jest` 463/463 + tsc 0; frontend vitest **1535/1535** + coverage **96.22 / 91.64 branch / 96.45 / 96.83** (gate ≥90/85) + tsc 0; Storybook (chromium) de ambas ListViews 11/11. Sub-agentes verificados independientemente (DET-33). **Verificación runtime (DET-36): `smoke-not-reproducible`** — el stack autenticado (MSAL + docker) no se levanta headless; el 400 queda descartado por construcción (agregación server-side, sin limit:1000) y por los tests MSW que espejan el backend.

**Qué NO se hizo** (out-of-scope): integración real DB (los dominios siguen siendo stubs — la agregación corre sobre el stub con los mismos filtros; el contrato aplicará igual contra DB en Bn.4+). Optimización de índices/consultas SQL reales queda para la fase de persistencia.
