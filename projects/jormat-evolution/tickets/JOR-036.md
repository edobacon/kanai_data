# Robustez del workspace activo del internal-admin (override stale → listados vacíos sin señal)

## Request

En jormat-evolution (`front/jormat-front`), el `EmpresaSwitcher` (TopBar) persiste el workspace activo de un internal-admin en `localStorage['admin_active_workspace']` (`src/stores/ui.store.ts` + `src/services/api.ts:28-32`, que lo manda como header `X-Admin-Workspace`). El backend (`auth.guard.ts:69-72`) honra ese header para admins y scopea TODA query a ese workspace.

**Problema**: si el workspace persistido ya no existe (borrado/recreado por seed/db:reset, o el admin perdió acceso), todos los listados (usuarios, etc.) vuelven vacíos `[]` SIN ninguna señal al usuario — diagnóstico confuso (parece que "no hay datos"). Observado en JOR-035: `GET /config/users` devolvía `[]` por un `admin_active_workspace` stale; también se vio `GET /api/proxy/workspaces/current` 404.

**Objetivo (alcance aprobado por el dev = B + C + A)**:
- **B (self-healing)**: si `GET /workspaces/current` devuelve 404 **y** hay override seteado, limpiar el override (localStorage + store) y refetch; caer al workspace propio. Distinguir 404 (override inválido → curar) de `NETWORK_ERROR` (no tocar) vía `ApiError.status`.
- **C (estado visible)**: mostrar claramente el workspace activo en el switcher + estado "no encontrado / fuera de rango" cuando `current` falla.
- **A (feature)**: `GET /workspaces` admin-only (lista workspaces) gateado a `internal-admin` (no-admin → 403); cablear el switcher multi-workspace real (hoy `workspaceOptions` hardcodeado a `[user.workspace_id]`, TODO en `EmpresaSwitcher.tsx:49`); validar el override contra la lista disponible al hidratar.

**Restricción dura**: NO cambiar el contrato del header `X-Admin-Workspace` (es la base de la operación cross-tenant del internal-admin). Incluir tests (front + back).

> Follow-up de JOR-035 (proyecto sin tracker — `external: null`; el vínculo es `relates_to` interno, no Jira).

## Triage

Causa raíz **única** con dos manifestaciones, confirmada leyendo el código:

- `auth.guard.ts:72`: `resolvedWorkspaceId = (isAdmin && adminWorkspaceOverride) ? adminWorkspaceOverride : user.workspace_id` — honra el override **sin validar que exista**. Las queries scopeadas a un workspace fantasma devuelven `[]` (no error → silencio).
- `workspaces.service.ts:27-29` (`findById`): lanza `NotFoundException` si el id no existe → ese es el **404** de `GET /workspaces/current`. Es la **única señal fiable** de override stale; el resto de endpoints calla con `[]`.

`auth.guard.ts` es **base entregada** (RULE-global-003) → el "resolver sin validar" se **reporta como defecto heredado**, NO se corrige en el guard. El fix es **aditivo**: self-heal en front + endpoint nuevo + cableado del switcher.
