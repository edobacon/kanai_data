# Tests de configuracion de roles: 1 cuenta de prueba + DB de test efimera (crear/limpiar automatico)

## Request

Reducir las cuentas de testing a **1 sola cuenta de prueba** (modificar el env — no se necesitan 6).
Al correr los tests, **setear el tipo de rol a probar para esa cuenta**. Crear una **DB nueva para
el test y luego limpiarla**; `correr test` debe hacer estos procesos automaticamente (o, alternativa,
ayudar a crear la DB de pruebas y agregarla al env para que la bateria de tests se conecte). Se debe
**probar la configuracion de todos los roles** (los 6: vendedor, bodega, jefe-local, jefe-venta,
gerencia, cajero). Analizar para crear el ticket.

## Diseno propuesto (a refinar en design)

**1. Cuenta de prueba unica (env) — DECIDIDO: `gerencia`**
- La cuenta de prueba es una **existente**: `jormat.gerencia.01@syscodeexternalid.onmicrosoft.com` (decision del dev). NO se crea una cuenta dedicada nueva.
- Reducir en `~/.jormat.env` las 6 `JORMAT_TEST_*` a 1 (la de gerencia), p. ej. renombrar a `JORMAT_TEST_USER`/`JORMAT_TEST_PASS` o conservar `JORMAT_TEST_GERENCIA_*` como la cuenta de prueba canonica. Las otras 5 entradas se quitan del env.
- El seed de test crea 1 fila `users` con la identidad de gerencia (email + oid placeholder `dev-gerencia-oid`); el test le **asigna/cambia el rol** (replace en `user_roles`) por cada uno de los 6 roles a probar — la cuenta es portadora, su "rol natural" no importa.
- Las 5 cuentas CIAM restantes quedan fuera de los tests; uso QA manual. Limpieza en Azure = decision del dev (fuera de scope).

**2. DB de test efimera (automatica)**
- knexfile: agregar env `test` → DB `jormat_evolution_test` (host/port/user/pass reusados; nombre via `DB_NAME_TEST`).
- jest `globalSetup`: conectar a DB `postgres`, `DROP DATABASE IF EXISTS` + `CREATE DATABASE jormat_evolution_test`; correr `migrate:latest` + seed minimo de test (capabilities + 6 roles + 1 user) sobre ella.
- jest `globalTeardown`: `DROP DATABASE jormat_evolution_test`.
- Aislar en `jest.e2e.config.ts` + script `test:e2e`. Decidir si `npm test` encadena unit + e2e (el dev pidio "correr test haga estos procesos automaticamente").

**3. Test de configuracion de roles (`*.e2e-spec.ts`)**
- Por cada uno de los 6 roles: asignar el rol a la cuenta de prueba → resolver `PermissionsService.resolve(userId, workspaceId)` → **assert `effectiveCaps` == set exacto de la matriz** (vendedor 2, bodega 11, cajero 14, jefe-local 25, jefe-venta 25, gerencia 26).
- Opcional (mismo spec): un endpoint representativo via Supertest por rol → 200 con capability / 403 sin ella.
- Cleanup de `user_roles` entre iteraciones.

### Decisiones abiertas (resolver en design-feature)
1. ~~**Identidad de la cuenta de prueba**~~ — RESUELTO: cuenta existente `gerencia` (`jormat.gerencia.01@…`), decision del dev. El env se reduce a esa.
2. **`npm test` encadena e2e**: `test` corre unit+e2e (cumple "automatico" pero mas lento) vs `test:e2e` separado (unit rapido) — recomendable separar + un `test:all`.
3. **Conexion test-DB**: `DB_NAME_TEST=jormat_evolution_test` en `.env`/`.env.example` reusando host/port/user/pass dev.
4. **Concurrencia**: `--runInBand` para el suite e2e vs cleanup transaccional por test.
