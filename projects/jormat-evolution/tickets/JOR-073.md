# Performance de carga de vistas (bundle / code-splitting) — investigación primero

## Request

Las vistas se demoran en cargar, sobre todo las de muchos componentes (builders, listados con modales). Analizar la causa real y proponer acciones. **Investigación primero** (medir antes de optimizar): separar la lentitud de dev (compilación on-demand de Next) del rendimiento real de producción.

## KB consulted

- **Rules**: [RULE-frontend-001](../rules/frontend/RULE-frontend-001.md) (carpeta-por-componente con test+story — mantener al hacer code-splitting), [RULE-frontend-002](../rules/frontend/RULE-frontend-002.md).
- Tickets recientes tocaron estas vistas: JOR-068 (server-side), JOR-070 (selector/KPIs), JOR-071 (builder server-side), JOR-072 (KPIs summary). Ninguno introdujo lazy-loading.

## Discoveries (análisis 2026-07-07)

- **D1 — Cero code-splitting**: 0 usos de `next/dynamic`/`React.lazy` en 129 componentes → todo import estático; cada ruta embarca el árbol completo + deps en su bundle inicial. Las vistas pesadas (builders, listados con modales) cargan todo upfront.
- **D2 — Casi todo es client component**: 84/129 con `'use client'` → bundles JS grandes; el beneficio de server components (App Router) está poco usado (limitado por MSAL/interactividad, pero no todo lo requiere).
- **D3 — `next.config` sin optimizaciones**: no hay `experimental.optimizePackageImports`, `modularizeImports` ni bundle-analyzer.
- **D4 — lucide-react sin optimizar**: 112 íconos distintos en 72 imports. Sin `optimizePackageImports`, el barrel de lucide (~1500 íconos) es un costo conocido de compilación en dev.
- **D5 — Uso intensivo de barrels**: 103 `index.ts` reexportando → grafo de imports ancho (peor sin splitting).
- **D6 — 2-3 queries por vista** (list + summary [+ proveedores]): paralelas (menor), el summary es un 2º round-trip.
- **D7 — Sin medición**: solo `next build`/`next start`, sin analyzer → no hay números de peso por ruta.
- **D8 (crítico) — dev ≠ prod**: el entorno local corre `./run.sh dev` (Next dev, compila la ruta on-demand la primera vez). Gran parte de la lentitud percibida es compilación de dev, NO rendimiento de producción. **Hay que medir en `next build && next start` + analyzer antes de optimizar.**

## Medición (Fase 0 — 2026-07-07)

**Build de producción** (`next build`, Next 14.2.35). First Load JS por ruta:
- Shared por todas: **87.5 kB**.
- Más pesadas: `/ventas/crear-factura` **329 kB** · `/compras/facturas-proveedor/crear` 317 kB · `/finanzas/aplicar-pago` 312 kB · `/config/users` 311 kB · items (aplicaciones/categorias/editar/nuevo) ~309-311 kB · listados (documentos/pagos/compras) ~297-298 kB.
- **Conclusión clave: ~300 kB es moderado; NO explica lentitud de varios segundos en prod.** Confirma D8 — el dolor percibido es sobre todo **compilación on-demand de Next dev** (`./run.sh dev` compila la ruta la primera vez). Para dev, el lever es `optimizePackageImports` + caché de Next.

**Composición del bundle** (`@next/bundle-analyzer`, parsed, suma de chunks client = 1771 kB):
| Peso | Paquete |
|---|---|
| 452 kB | next (runtime, inevitable) |
| 381 kB | **(app code)** — nuestros componentes across rutas |
| **136 + 121 = 257 kB** | **@azure/msal-browser + @azure/msal-common (MSAL)** |
| 126 kB | react-dom (inevitable) |
| 64 kB | zod |
| 49 kB | @tanstack/table-core |
| 41 kB | axios · 37 kB lucide-react · 35 kB @dnd-kit · 33 kB react-hook-form · 33 kB sonner · 32 kB date-fns · 32 kB @tanstack/query-core · 26 kB tailwind-merge · radix (~40 kB total) |

**Hallazgos de la medición:**
- **M1 (lever #1 prod): MSAL ~257 kB se carga EAGER en todas las rutas.** `MsalProviderWrapper` (que hace `new PublicClientApplication` de `@azure/msal-browser`) se importa estático en `src/app/layout.tsx` (envuelve toda la app). Es la mayor dep de terceros y está en el First Load de cada ruta.
- **M2: lucide en prod es solo 37 kB** (el tree-shaking ya funciona) → `optimizePackageImports` de lucide es sobre todo ganancia de **dev-compile**, no de bundle. Ajusta la prioridad de D4.
- **M3: app code 381 kB** distribuido → el code-splitting (dynamic import de builders/modales) mueve peso fuera del First Load de las rutas pesadas (crear-factura).
- **M4: deps medianas** (zod 64, tanstack-table 49, date-fns 32) — candidatas menores (modular imports / evaluar).

## Propuesta (a refinar en design)

### Fase 0 — Medir (bloqueante, define el alcance real)
- Agregar `@next/bundle-analyzer` (script `analyze`) y correr `next build` → tamaño de JS por ruta (First Load JS).
- Medir tiempos en `next start` (prod) vs dev para cuantificar cuánto es compilación de dev.

### Fase 1 — Quick wins (re-priorizado con la medición)
- **P1a (prod, mayor lever) — diferir MSAL (~257 kB)**: no cargar `@azure/msal-browser` eager en `layout.tsx`. Opciones a evaluar: cargar el provider MSAL solo cuando se necesita (boundary de auth) / `next/dynamic` del wrapper / mantenerlo fuera del First Load de rutas que no lo requieren. Mayor impacto en First Load de TODAS las rutas.
- **P1b (dev, mayor lever) — `optimizePackageImports: ['lucide-react', '@radix-ui/*', 'date-fns']`** en `next.config`: corta el costo de barrels en la compilación de dev (el dolor percibido). En prod es menor (lucide ya tree-shakea, M2).
- **P1c (prod) — `next/dynamic`** para lo pesado y no-inicial: builders (TransactionBuilder 17.4 kB de app code, PurchaseInvoiceBuilder), modales (ItemDetailModal). Mueve app code (M3) fuera del First Load de crear-factura (329 kB) y afines.

### Fase 2 — Estructural (según medición)
- Revisar barrels que arrastran dominios enteros; acotar reexports.
- Evaluar mover a server components lo no-interactivo.
- Revisar `fetchAllPages` de catálogo (JOR-071) en mount de builders (lazy/on-demand).
- Evaluar colapsar list+summary si el waterfall importa.

## Alcance

- **Dentro**: medición (Fase 0) + quick wins (Fase 1). Fase 2 según números.
- **Fuera / a confirmar**: refactor a server components a gran escala (Fase 3, alto esfuerzo — decidir con datos).

## Validación esperada

- First Load JS por ruta antes/después (analyzer). Reducción medible en las vistas pesadas.
- Sin regresiones: vitest full + coverage ≥90/85; Storybook; verificación de que las vistas con dynamic import siguen rindiendo (loading states).

## Notas
