# Exponer uuid publico como identificador en las vistas de inventario (dejar de exponer/direccionar por el id serial)

## Request

Usar el patron de identificador publico uuid en las vistas/endpoints de inventario, para proteger los elementos de que se expongan y direccionen por su id entero (serial). Reflejar el plan en este ticket y en una regla de implementacion a futuro.

### Context found

#### Diagnostico verificado (estado actual)

- **12 tablas de inventario** con PK serial `increments` **+ columna `uuid` ya provista** (`NOT NULL`, `UNIQUE`, default `uuid_generate_v4()`): `items`, `warehouses`, `providers`, `categories`, `applications`, `locations`, `item_references`, `item_providers`, `item_categories`, `application_items`, `item_warehouses`, `item_warehouse_locations` (`20260714000000_inventory_schema.ts` + `20260721000000_normalize_inventory_plural.ts:33-47,98-104`). El uuid **existe y es direccionable; falta cablearlo**. (`trucks` tambien recibio `uuid` en esa migracion pero se excluye: [[JOR-147]] lo rehace uuid-PK nativo, no fachada.)
- El CRUD **hoy direcciona por el serial**: controllers `@Param('id')`, repos `.where('i.id', id)` + `Number(id)`, DTOs emiten `i.id` (`items.controller.ts:118,180,237`; `items.repository.ts:341,365,564`).
- **Front**: rutas dinamicas `/inventario/items/[id]` y cliente API `/api/inventario/items/{id}` transportan el serial (`front/jormat-front/src/app/(app)/inventario/items/[id]/...`, `src/types/api.gen.ts:281`).
- **Convencion de referencia** (ya correcta): `customers` y `catalogos_repuestos` exponen `id`=uuid; son el molde a replicar.
- **Superficie interna que consume el serial** (debe seguir funcionando via resolucion uuid->serial):
  - Filtros de pivote por `i.id`: `applyPivotFilter(..., 'i.id')` y filtros CSV de categorias/aplicaciones/proveedores (`items.repository.ts:324,328`; catalog filter DTO).
  - Sort: `SORTABLE_COLUMNS` incluye `'id'` y `defaultSort { column: 'id', direction: 'desc' }` (`items.repository.ts:47,179`). El orden interno por serial es valido; el token de sort `id` expuesto al front debe mapear a un campo estable (uuid o `created_at`).
  - Pivotes/sync de FKs en create/update (`syncPivots(trx, Number(id), ...)`, `.returning('id')`, `items.repository.ts:563-588`): resolver el uuid a serial una sola vez y seguir operando con el serial internamente.

#### Riesgo que se cierra
Exponer el serial secuencial habilita enumeracion trivial de recursos (IDOR / fuga de conteos de negocio por incremento). El uuid publico corta esa superficie sin tocar el modelo interno.

#### Fases propuestas (borrador para design; ordenadas por dependencia, dominio `items` primero)

1. **Repo items (resolucion por uuid)**: `SELECT uuid AS id` en las proyecciones, `WHERE uuid = :id` en lecturas/updates/delete, `RETURNING uuid` en create. Para operaciones que tocan pivotes/FK, resolver `uuid -> serial` una vez y mantener el serial interno. Traducir filtros de pivote y CSV de catalogo de uuid a serial en el limite. **Preservar los marcadores `DEUDA_TECNICA` de DT-18 (`bloqueoDescuento`) y DT-19 (`canales.catalogo`)** que [[JOR-144]] dejo vivos en `items.repository.ts`: no borrarlos al reescribir las proyecciones.
2. **Contrato/DTO items**: el campo `id` del DTO pasa a llevar el uuid; el serial deja de emitirse en cualquier salida. Regenerar Swagger/OpenAPI.
3. **Front items**: regenerar `api.gen.ts`, las rutas `[id]` y las llamadas del cliente API pasan a transportar uuid. El componente sigue leyendo `record.id` (cambia el valor, no el shape). Mapear el sort `id` a un campo estable.
4. **Resto de dominios de inventario**: repetir 1-3 por dominio segun sus endpoints (`warehouses`, `providers`, `categories`, `applications`, `locations`, y los pivotes que expongan endpoints propios). Big bang por dominio (D3). **`trucks` NO entra**: lo cubre [[JOR-147]] como uuid-PK nativo.
5. **Guardarrail de regresion**: test que verifique que ningun endpoint de inventario emite un identificador numerico y que `:id` con un serial no resuelve (404). Cierra la puerta a re-exponer el serial a futuro.
6. **Docs + regla**: actualizar `jormat_docs` (back/front) y dejar viva la regla de implementacion a futuro (ver [[RULE-api-001]]).

#### Fuera de alcance
- Migrar los PK internos a uuid o tocar FKs internos (D2).
- Reconectar `sales`/`purchases`/`payments` al uuid de item (D4): impacto downstream registrado, no se ejecuta aca.
- Dominios que ya usan uuid como `id` (`customers`, `catalogos_repuestos`): ya cumplen.

#### Encadenamiento (orden de ejecucion)
Cadena epic-jormat-v1: **[[JOR-144]] → [[JOR-145]] → { [[JOR-146]], JOR-148 } → [[JOR-147]]**. Depende de:
- **[[JOR-144]]**: comparte `items.repository.ts` e `items.controller.ts` (comentarios limpiados, sin commit al 2026-08-13). Commitear 144 antes de ramificar.
- **[[JOR-145]]**: 145 reescribe los mismos repos de items (filtro `is_active`); ejecutar la fachada uuid despues evita colision y deja el contrato de lectura (`WHERE is_active=1`, front no lista `is_active=0`) como base estable para el guardarrail (fase 5). El sort `id` mapea a un campo estable (uuid o `created_at`).
[[JOR-147]] (trucks) es independiente: no comparte los repos de items ni el regimen serial-fachada.

#### Coordinacion con [[JOR-147]] (trucks)
`trucks` recibio `uuid NOT NULL UNIQUE` en `20260721` junto al resto del inventario, pero **queda fuera de este rollout**: [[JOR-147]] lo rehace **uuid-PK app-native** (molde `customers`/`catalogos_repuestos`), no serial+fachada. Razon: trucks **no tiene FK inbound** (nada referencia `trucks.id`), asi que la excepcion que justifica la fachada en las 12 tablas de inventario (malla de pivotes) no le aplica; el estandar del repo para tablas sin esa atadura es uuid PK. Los dos tickets pueden ejecutarse en paralelo, sin dependencia de orden.

### Revision de filtros de los mantenedores (2026-08-13)

Barrido de los filtros de todos los mantenedores. El unico que filtra por relacion (id de otra
entidad) es `items` (`categorias`/`aplicaciones` por CSV de uuid, con guard `parseUuidCsv` -> 400, y
`itemId` por uuid). El resto (`catalogos` categorias/aplicaciones/proveedores/bodegas/clientes,
`customers`) filtra solo por texto libre (`search`/`q`) o no tiene filtros. Conclusion: la migracion
uuid cubrio los filtros relacionales de forma completa; ningun mantenedor acepta un serial como
filtro. La unica inconsistencia es DV5 (`itemId` no-uuid ignorado en silencio en vez de 400).
