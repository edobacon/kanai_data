# Acceso dev durable: habilitar 02_local_admin (ENABLE_DEV_ADMIN_SEED) + documentarlo en .env.example

## Request

Tras correr el seed en JOR-033, la cuenta del dev (CIAM) quedó sin permisos y sin poder acceder
a las partes protegidas. Además: "si vuelvo a hacer seed, se volverá a perder la cuenta y sus
capacidades" → se necesita un fix DURABLE, no un grant puntual.

## KB consulted

- **Bugs**: n/a (sin bugs abiertos)

## Discoveries / decisions

- D1: `seeds/01_initial_data.ts:5-7` hace `knex('users').del()` + `workspaces` + `workspace_memberships` en CADA corrida → `npm run seed` es **destructivo** de usuarios/workspaces (no solo `db:reset`). Mi caracterización previa como "idempotente/no destructivo" fue incorrecta.
- D2: el auto-provision (AuthGuard, login CIAM) crea el usuario como `role='owner'` pero **NO asigna ningún rol RBAC** → 0 capabilities. El rol RBAC `internal-admin` solo lo otorga el `step-4` de `03_rbac` a usuarios con `users.role IN ('owner','internal-admin')` existentes al momento del seed.
- D3: **el mecanismo durable YA EXISTÍA** — `seeds/02_local_admin.ts` (A7.7) upserta el usuario CIAM del dev por `b2c_oid` desde `.env` con `role='internal-admin'`, gateado por `ENABLE_DEV_ADMIN_SEED==='true'`. Corre antes de `03`, así que su `step-4` le asigna el rol RBAC internal-admin. El `.env` del dev ya tenía `DEV_ADMIN_OID/EMAIL/NAME/DEV_WORKSPACE_ID` pero **faltaba `ENABLE_DEV_ADMIN_SEED=true`** (y el flag no estaba documentado en `.env.example`) → el seed dev-admin nunca corría → el dev caía en auto-provision sin caps.
- M1 (micro-decision): fix por **configuración + doc**, no código nuevo (DET-32 reuse). Habilitar el flag en `.env` (local) + documentarlo en `.env.example` (committeable) para que el próximo dev no caiga en lo mismo. Descartado: escribir un seed nuevo (duplicaría 02_local_admin); descartado tocar AuthGuard (RULE-global-003).
