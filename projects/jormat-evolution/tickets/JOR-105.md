# JOR-105 · Bypass de login dev/test-only para E2E y Playwright

## Request

Implementar un bypass de login **exclusivo de dev/test** que permita autenticar automaticamente a un usuario a partir de su email (dominio de test reservado), sin pasar por el login interactivo de Azure CIAM (B2C). Objetivo: habilitar tests E2E HTTP autenticados y tests de Playwright (browser) que hoy no pueden autenticarse. El bypass debe ser imposible de habilitar en produccion.

## Alcance

**Dentro:**
- Backend: el AuthGuard acepta, solo en no-prod, un token de test firmado localmente con HS256 usando un secreto compartido (`E2E_AUTH_SECRET`). `verifyToken` ramifica por `alg`: el path HS256 solo se evalua en no-prod + flag on + secreto presente. El path RS256/JWKS sigue siendo el UNICO valido en produccion.
- Validacion de entorno (`env.validation.ts`): registrar `ENABLE_E2E_LOGIN` y `E2E_AUTH_SECRET`; exigir secreto fuerte cuando el flag esta on; garantizar que el flag/secreto no tengan efecto si `NODE_ENV=production`.
- Restriccion de identidad: solo emails de un dominio de test reservado (ej. `@e2e.jormat.test`) pueden auto-loguearse via el token de test.
- Frontend/PW: un entry dev-login (solo no-prod) que arma la sesion con ese token para que Playwright loguee en browser; el token viaja por el proxy Next existente (`/api/proxy`) hacia la API.
- Helper de test (backend e2e): firmar el token de test por email/rol para las specs HTTP.
- Tests: e2e HTTP autenticados de ejemplo (a traves del AuthGuard real) + smoke de PW con login; test de regresion que verifique el fail-closed en prod.

**Fuera:**
- Migrar los e2e backend actuales (que hoy instancian servicios/repos directo) a HTTP: se hara incrementalmente en tickets propios; JOR-105 provee solo el seam.
- Cualquier cambio al flujo real de MSAL/CIAM de produccion.
- Emision de refresh tokens o manejo de sesion productiva.

## Backend y frontend requerido

Fullstack. El seam de auth vive en backend (`auth.guard.ts` + `env.validation.ts`); el entry dev-login vive en frontend (bypass de MSAL solo en no-prod). El proxy Next ya reenvia el header `Authorization` sin cambios.

## Decisiones (fijadas con el dev antes del intake)

| Decision | Eleccion | Descartadas |
|----------|----------|-------------|
| Enfoque | **A - Token de test HS256 gated**: bypass aislado en un branch de `verifyToken`, fail-closed en prod | B (email magico en el path principal del guard, mas riesgo de fuga a prod); C (mock de MSAL en build de test, mas andamiaje) |
| Alcance | **Backend + Frontend/PW (completo)**: habilita e2e HTTP y PW en un solo ticket | Solo backend, o solo frontend |
| Identidad | **Dominio de test reservado**: limita el blast radius aunque el flag se prenda por error | Marca `+e2e` en el email; cualquier email (solo secreto+flag) |

## Guardrails (candidatos a REQ del spec, no negociables)

1. Gate duro `NODE_ENV !== 'production'`: en prod el path HS256 ni se evalua.
2. Flag opt-in explicito `ENABLE_E2E_LOGIN` (default off), al estilo de `ENABLE_DEV_ADMIN_SEED`.
3. Secreto compartido `E2E_AUTH_SECRET`, validado en `env.validation` (fuerte si el flag esta on).
4. El token de test (HS256) jamas se acepta en prod: fail-closed, coherente con JOR-100 (D2) y JOR-100/D-x (admin-token sin default, fail-closed).
5. Solo emails del dominio de test reservado pueden auto-loguearse.
6. Log/auditoria de cada uso del bypass (quien, que email, cuando).

**Riesgo principal a mitigar:** que el bypass quede habilitable en produccion. Mitigacion: triple candado (NODE_ENV + flag + secreto) mas un algoritmo/clave (HS256 local) que en prod ni se evalua. Debe existir un test que falle si el path de test se activa con `NODE_ENV=production`.

## Context found

- Auth backend: `backend/jormat-api/src/auth/auth.guard.ts`. `verifyToken` exige `Bearer` JWT RS256 verificado contra las JWKS reales de Azure CIAM (`getSigningKey`/`fetchJwks`). Chequea `exp` y `aud`. La via `x-admin-token` eleva a admin pero requiere un JWT valido primero (JOR-100/D2, JOR-100 hardening: sin default, fail-closed). `resolveUser` engancha por `b2c_oid` y luego por email (`resolveEmailClaim` cubre `emails`/`email`/`preferred_username`/`upn`); auto-provisiona workspace+user si no existe.
- Frontend: MSAL redirect flow contra CIAM (`front/jormat-front/src/auth/msalConfig.ts`, scopes `openid/profile/email`). El token va por el proxy `front/jormat-front/src/app/api/proxy/[...path]/route.ts` que reenvia el header `Authorization` a la API interna.
- e2e backend actuales (`backend/jormat-api/test/e2e/*.e2e-spec.ts`, config `jest.e2e.config.ts`, BD efimera JOR-041, `maxWorkers:1`): NO pasan por HTTP ni por el AuthGuard; instancian repos/servicios directo contra la BD de test. No hay cobertura del stack real de auth. No hay PW con login.
- Precedente de tooling dev-only: `ENABLE_DEV_ADMIN_SEED` + `DEV_ADMIN_OID`/`DEV_ADMIN_EMAIL` (seed de admin local opt-in), `DEV_WORKSPACE_ID`. `env.validation.ts` ya rechaza secretos debiles/vacios en `NODE_ENV=production` (patron a extender para `E2E_AUTH_SECRET`).

**Hallazgos del dual-judge (T3) y resolucion**:
- **[juez 1] Allowlist vs blocklist de NODE_ENV** (alta, condicionada): el candado `NODE_ENV !== 'production'` dejaba fail-open si `NODE_ENV` quedaba ausente en un deploy de prod real (el Dockerfile del backend no lo setea). **Resuelto**: allowlist explicita `development|test` en guard y env.validation.
- **[juez 2] Impersonacion por `oid`** (critica): el chequeo de dominio validaba el claim `email` pero `resolveUser` resolvia por `oid` (claim libre) -> con el secreto se podia impersonar una cuenta real. **Resuelto**: la identidad se deriva deterministicamente del email (sha256), ignorando `oid`/`sub`.
- **[juez 2] `exp` ausente no expiraba** (alta): `undefined < now` es false. **Resuelto**: `exp` obligatorio y numerico.
- **[juez 2] `JSON.parse` sin try/catch** (baja): 500 en vez de 401. **Resuelto**: try/catch en header y payload.
- Sin hallazgos en: confusion de algoritmo, path RS256/JWKS (intacto), `timingSafeEqual`, evasion de dominio, fuga en el log.

**Evidencia**: jest 76/76 verde (7 suites auth+config; +5 casos de seguridad), `tsc --noEmit -p tsconfig.build.json` sin errores, eslint solo warnings de estilo. Commits: 885a860 (feat) + 454ba6e (fix dual-judge).
