# Buscador de items del builder falla (limit:1000 vs @Max(100)) — pasar a paginación server-side 10/página

## Request

En la vista de creación de facturas (`/ventas/crear-factura`) el buscador de ítems **no lista items y marca error**. El buscador debe paginar como el resto: **fijo 10 por página, server-side (paginado desde el backend)**, en vez del patrón actual de traer todo el catálogo client-side. Analizar causa raíz y dejar el ticket con el plan.

> Reportado por el dev el 2026-07-07 durante la revisión de JOR-070. Diagnóstico ya realizado (ver Discoveries).

## KB consulted

- **Rules**: [RULE-global-002](../rules/global/RULE-global-002.md) (el cap `@Max(100)` en `limit` es una guarda de seguridad deliberada — NO removerla), [RULE-frontend-001](../rules/frontend/RULE-frontend-001.md), [RULE-frontend-002](../rules/frontend/RULE-frontend-002.md) (Radix Select mockeado en jsdom; los tests con MSW no ejercen la validación real del DTO), [RULE-testing-coverage-threshold-002](../rules/testing/RULE-testing-coverage-threshold-002.md).

- **Bugs**: n/a (este ticket es el que documenta el bug).

## Discoveries / decisions

- **D1 — Causa raíz (confirmada)**: el frontend usa un patrón "traer todo el catálogo client-side" que manda `limit: 1000`; el backend acota `limit` a `[1,100]` con `@Max(100)` (guarda de JOR-068 S4, RULE-global-002). El `ValidationPipe` global (whitelist+transform) rechaza `limit=1000` con **400 BAD_REQUEST** → los datos no cargan y salta el error.
  - Frontend: `useItemsCatalog` → `front/jormat-front/src/hooks/useItems.ts:58` → `listItems({ limit: 1000 })`.
  - Backend: `backend/jormat-api/src/items/dto/list-items-query.dto.ts:26` (`@Max(100)`), heredado del patrón de `common/dto/pagination-query.dto.ts:27`.
  - Evidencia adicional: `backend/jormat-api/src/common/foundations.integration.spec.ts:112` ya verifica `limit=999 → 400`.
- **D2 — Los tests del front no lo detectan**: MSW mockea la respuesta del endpoint sin ejecutar la validación real del DTO (bug clásico "pasa con mock, falla contra backend real"). Los e2e backend sí validarían, pero no hay e2e que cruce el front con `limit:1000`.
- **D3 — Radio de impacto (2 hooks, mismo bug)**:
  | Hook (limit:1000) | Vistas afectadas |
  |---|---|
  | `useItemsCatalog` (useItems.ts:58) | `TransactionBuilder` + `ItemSearchPanel` (crear-factura, COMPARTIDO Ventas/Compras) y `CrearCatalogoView` (crear-catálogo) |
  | `useDocumentosResumen` (useVentas.ts:53) | KPI cards de Documentos (`DocumentosListView`) — `ListDocumentosQueryDto extends PaginationQueryDto`, hereda el mismo `@Max(100)` |
  Nota: las KPIs de Documentos (JOR-070) están afectadas por lo mismo contra el backend real.
- **D4 — Decisión del dev**: el buscador de items del builder debe **paginar server-side, fijo 10/página** (no traer todo client-side). El backend `/api/inventario/items` YA soporta `page`/`limit`/`search`/`estado`/`sort` (JOR-068), así que el fix del builder es **frontend** (rewire), sin cambio de backend.
- **D5 — Descartado**: subir/quitar `@Max(100)` — debilita RULE-global-002 (un cliente podría forzar una página gigante contra la DB). No se toca la guarda.

## Propuesta de solución (a refinar en design-fix)

### T1 — `ItemSearchPanel` a paginación server-side (10/página) [núcleo del request]
- Reemplazar `useItemsCatalog()` + filtrado client-side por `useItems({ page, limit: 10, search })` server-side (el mismo patrón que `ItemsListView`).
- El campo de búsqueda pasa a enviar `search` al backend (con debounce) y resetea a página 1; la `Pagination` usa `total`/`pageCount` del envelope.
- **Impacto colateral**: `ItemSearchPanel` es COMPARTIDO por Ventas (JOR-014) y Compras (JOR-015) — el cambio afecta ambos builders. Verificar `TransactionBuilder` de ventas y el de compras.
- Detección de "ya seleccionado" (`selectedIds`) sigue funcionando por id sobre la página visible.

### T2 — `CrearCatalogoView` (usa `useItemsCatalog`)
- Evaluar en design: el generador de catálogos puede necesitar el set completo. Opciones: (a) paginación server-side con selección acumulada, o (b) helper "paginar hasta agotar" (loop de páginas a limit=100) si realmente necesita todo. Decidir según UX del generador.

### T3 — KPIs de Documentos (`useDocumentosResumen`)
- No traer 10k filas para contarlas client-side. Proponer **endpoint de summary server-side** para documentos (agregados/counts en la DB), espejando el patrón de items (`getItemsSummary`/`useItemsSummary` ya existen). Requiere trabajo backend (agregación + RBAC + tests). Alternativa puente si se prioriza: paginar-hasta-agotar, pero es peor (N requests + transferencia).

### T4 — Regresión / guardas
- Agregar test que ejercite la validación real del `limit` (o un contract test) para que el desfase front↔backend no vuelva a pasar silenciosamente. Considerar un lint/guard que prohíba `limit > 100` en llamadas del cliente.

## Alcance

- **Dentro**: T1 (builder server-side 10/página) como entrega principal; T2 y T3 a diseñar (T3 implica backend). 
- **Fuera / a confirmar**: el endpoint de summary de documentos (T3) puede separarse a su propio ticket si crece. Los 4 widgets con `Pagination` directo que quedaron fuera de JOR-070 (ItemsGrid, ItemsPickerTable, CapabilityMatrix) no entran salvo que compartan la causa.
