# JOR-146 · Soft-delete is_active en RBAC/acceso: roles, user_roles, role_capabilities, capabilities, workspace_memberships

## Request (backlog local — NO Jira)

Migrar las tablas de **control de acceso** a la convencion `is_active smallint NOT NULL DEFAULT 1` (1 = activo, 0 = eliminado) ([[RULE-database-001]]), convirtiendo su borrado de hard-delete a soft-delete. Se aparta de [[JOR-145]] porque soft-deletear filas de acceso introduce un **riesgo de fuga de permisos** que exige un barrido de seguridad y regresion dedicada.

## Alcance (5 tablas)

- capabilities, roles, role_capabilities, user_roles, workspace_memberships. Todas nacen/pasan a `is_active smallint NOT NULL DEFAULT 1`.
- Hard-delete actual a convertir en soft (`update({ is_active: 0 })`):
  - `src/permissions/roles.service.ts:131` (roles), `:155` (role_capabilities), `:186` (user_roles).
  - `src/workspaces/workspaces.service.ts:65` (workspace_memberships, en la cascada de borrado de workspace).

## Riesgo central: fuga de permisos (bloqueante de seguridad)

Al pasar filas de acceso a soft-delete, **todo** join de hidratacion de permisos/membresia debe filtrar `is_active = 1`, o un permiso/membresia "revocado" (marcado inactivo) sigue autorizando. Barrido obligatorio de:
- `CapabilitiesHydrationGuard` / `CapabilitiesGuard` (`src/common/`, hidrata `req.user.capabilities`).
- `src/permissions/roles.service.ts` (todos los reads de roles/role_capabilities/user_roles).
- Cualquier query de membresia por `workspace_id` que hoy asuma que la fila existente = miembro activo.
Cada join tocado lleva su assert; se agrega un test de regresion: **revocar (soft-delete) → el endpoint protegido responde 403** y la capability desaparece de la hidratacion.

## Constraints unicos → indices parciales

Los pivotes con unique deben convertirse a **indice parcial `WHERE is_active = 1`** para permitir re-otorgar algo previamente revocado sin colisionar con la fila inactiva:
- `user_roles` (unique por user_id + role_id), `role_capabilities` (role_id + capability_id), `workspace_memberships` (user_id + workspace_id). Verificar el unique real de cada uno en las migraciones antes de reemplazar.

## Enfoque: expand-contract (2 migraciones)

1. **Expand**: agrega `is_active smallint NOT NULL DEFAULT 1` (todo lo existente queda activo) a las 5 tablas + convierte los unique a indices parciales `WHERE is_active = 1`.
2. **Switch de codigo**: hard-delete → soft (`is_active = 0`); barrido de filtros `is_active = 1` en TODOS los joins de acceso (seccion de riesgo).
3. **Tests**: regresion de fuga de permisos (revocar → 403) + re-otorgar tras revocar (valida el indice parcial).
4. **Contract**: no hay columna vieja que dropear (estas tablas no tenian columna de estado); el "contract" es cerrar la conversion de todos los `.del()` a soft y verificar que no queda hard-delete de acceso salvo el documentado.

## Coordinacion con JOR-145

La cascada de `src/workspaces/workspaces.service.ts` toca `users` (JOR-145) + `workspace_memberships` (este ticket) + `workspaces` (fuera de alcance, sigue hard). Alinear con JOR-145 el comportamiento de la cascada para no dejar hijos soft-deleteados huerfanos de un workspace borrado fisico.
