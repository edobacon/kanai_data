# Las peticiones de red del front no se cancelan al navegar — una nueva petición debe abortar la anterior

## Request

Al presionar diferentes vínculos en jormat-front, las llamadas de red previas quedan activas
aunque ya no sean necesarias (la vista que las pidió se desmontó). Una nueva navegación debería
cancelar la petición anterior. El dev pide analizar el problema y darle alternativas; tras el
análisis se eligió la **opción A + convención D**:

- **A — Propagar el `signal` de React Query a axios** en todos los servicios de dominio y sus hooks.
- **D — Convención compartida**: tipo `RequestOptions { signal?: AbortSignal }` en la capa
  `lib/api` + rule/decision que fije que todo servicio de dominio futuro nazca aceptando y
  propagando `signal`.

Las **mutations quedan fuera de alcance** (React Query no cancela mutations por diseño, y no se
quiere abortar un POST a medio camino).

## Triage

Causa raiz confirmada por inspección del código (no hay incertidumbre): la cadena de cancelación
de React Query está cortada en ambos extremos. RQ v5 crea un `AbortController` por query y aborta
su `signal` cuando la query queda sin observers (navegación → desmonta el componente). Pero:

1. Los `queryFn` ignoran el `signal` del `QueryFunctionContext` (`queryFn: listItems`, `() => getItem(id)`).
2. Los servicios axios no aceptan ni pasan `signal` a `api.get(...)`.

Resultado: el abort de RQ nunca llega a axios → la petición HTTP sigue viva, gasta red y puede
producir respuestas fuera de orden en navegación rápida (A→B→A, detalle id1→id2). El cache por
`queryKey` mitiga *qué se muestra*, no *qué está en vuelo*.

### Hipotesis

| # | Hipotesis | Status | Evidencia |
|---|-----------|--------|-----------|
| H1 | Los `queryFn` descartan el `signal` que RQ inyecta en el contexto | ✓ confirmada | `hooks/useItems.ts`: `queryFn: listItems` / `() => getItem(id)` — sin destructurar `{ signal }`. Idéntico en los 8 hooks de query |
| H2 | Los servicios axios no aceptan ni propagan `AbortSignal` | ✓ confirmada | `grep AbortController\|signal\|CancelToken` en `lib services hooks app components` → 0 matches; servicios hacen `api.get<T>(BASE)` sin segundo arg `{ signal }` |
| H3 | El cliente axios global tampoco inyecta signal | ✓ confirmada | `services/api.ts`: `axios.create` + interceptores de auth/workspace; ningún manejo de cancelación |

- **Docs relevantes**: `jormat_docs/ongoing/frontend-api-layer.md` (patrón normativo "estilo petlog")

- **Warnings**:
  - Las **mutations** (`useApiMutation` / `api.post|put|patch|delete`) quedan fuera de alcance por
    diseño de RQ. No tocar sus firmas salvo decisión explícita.
  - `useWorkspace` tiene lógica de self-heal (404/network) cubierta por tests (JOR-036) — al tocar
    su `queryFn` re-correr esos tests (regresión).
  - El cliente axios usa interceptor `request` async (acquireTokenSilent). El `signal` debe llegar
    en `config`, no romper ese interceptor. Verificar que axios respeta `signal` con interceptor async.

**Discoveries / Learns nuevos**:
- L1: React Query (v5.101) NO aborta el fetch en vuelo por unmount solo — la query queda inactiva pero el fetch completa y se cachea. El abort se dispara cuando una **nueva petición supersede** a la anterior (misma key) o vía `cancelQueries`. El fix habilita que ese abort llegue a axios. El caso del usuario ("nueva petición cancela la anterior") es exactamente el de supersede → cubierto.
- L2: con un **observer activo**, `cancelQueries` revierte/refetch-ea y el abort no es determinista en test; el contrato (signal consumido + forwarded se aborta al cancelar) se prueba sin observer (prefetch). Mockear el módulo de servicio + `prefetchQuery` cuelga el test (indirección) → el test del abort usa un servicio fake inline.
- L3: el `CanceledError` de axios no trae `response` → sin el mapeo caería en `NETWORK_ERROR` (status 0) y dispararía toast "No se pudo conectar" al navegar. REQ-FIX-02 lo evita.
