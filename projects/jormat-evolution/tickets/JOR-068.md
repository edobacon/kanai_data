# Paginación server-side para todas las tablas (total/rango/páginas calculados en el backend)

## Request

En las tablas/listados, la barra de paginación ("Mostrando 1 a 10 de 1.248 items", números de página, "10 por página") debe alimentarse **desde el backend y calcularse ahí**, no en el cliente.

Decisiones de alcance tomadas con el dev en intake:
- **Alcance**: TODAS las tablas de una (Items, Ventas/Documentos, Pagos-clientes, Compras/Facturas-proveedor, Usuarios, Roles + mantenedores de catálogos).
- **Server-side completo**: paginación + filtros + orden calculados en el backend (no solo paginación). El front envía `page`/`limit`/`sort`/filtros y recibe la página + total.
- **Flujo**: ticket DKC completo (improvement, full-path), modo conversacional.

## Creation scope

| Dimension | Aplica | Descripcion |
|-----------|--------|-------------|

## Triage

Improvement **transversal multi-capa** de riesgo medio-alto: cambia el contrato de listado (array plano → envelope paginado) en ~6 endpoints + mueve filtro/orden al backend + cambia `DataTable` a modo server + recablea todas las list views. Riesgo principal: regresión (todas las tablas deben seguir listando/filtrando bien). Mitigante fuerte: el andamiaje de paginación del backend YA existe y no se usa aún.

## Summary

**Qué se hizo**: se migró la paginación de **todas las tablas** de client-side (TanStack en memoria sobre el dataset completo) a **server-side completo** (paginación + filtro + orden calculados en el backend). Cada endpoint de listado acepta `page`/`limit`/`sort`/filtros y devuelve el envelope uniforme `{ data, page, limit, total }`; el `DataTable` opera en modo controlado (`manualPagination`) consumiendo el total del backend.

**Cómo (5 sessions)**:
- **S1** — Infra frontend: `DataTable` gana modo server opt-in + tipo `Paginated<T>` + helper `toPaginationParams`/`pageCountOf` (`lib/api/pagination.ts`). Client-mode intacto (REQ-PRESERVE-01).
- **S2** — Piloto e2e en Items: backend paginado/filtrado + frontend server-side + endpoint `/items/summary` para KPIs/facets.
- **S3** — Rollout backend (6 dominios): ventas/pagos/compras (stubs, `resolvePagination`+slice), roles+users (DB Knex, `applyPagination`+count+`workspace_id`), catálogos (endpoints `/list` dedicados). Reuso de `common/pagination/paginate.ts` (DEC-LOCAL-01).
- **S4** — Rollout frontend (5 dominios): recableado de cada `*ListView` al patrón server-side + MSW + tipos; extensión de DTOs backend a los filtros de las vistas (fecha/currency/proveedor/formaPago). Fix del bug de tipo del `DataTable` (S1).
- **S5** — Regresión final + cobertura + docs (`jormat_docs/api/`).

**Resultado / acceptance**: backend jest **443/443** (48 suites), frontend vitest **1504/1504** (185 files), coverage global ≥90 (S 96.72 · B 91.47 · F 97.1 · L 97.39), **tsc front+back limpio**. REQ-IMPROVE-01/02/03 + REQ-PRESERVE-01/02 cumplidos. Tenant isolation (RULE-global-002) en queries DB (users/roles). 0 regresiones.

**Decisiones clave**: envelope uniforme en todos los GET de listado (decisión #4); catálogos con endpoints `/list` dedicados para no romper los GET planos que alimentan dropdowns (DET-16); roles como listbox sin UI de paginación (desempaqueta el envelope).
