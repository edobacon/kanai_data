# Arbol estructural del layout + cross-links vivos al Datamodel

## Request

Rediseno del `DetailPanel` de la vista Layouts. Hoy muestra info plana (secciones separadas para columns, tabs, rowActions, etc.) sin explicitar la estructura interna de la vista ni conectar con el modelo de datos real.

Lo que queremos:

1. **Arbol estructural** de la vista seleccionada — tabs con sus elements, columns con sus relations, schema con sus custom elements y record-list embebidos, rowActions con sus targets
2. **Cada nodo del arbol es clickeable** y lleva al destino correcto:
   - Columna con `relations: "X"` → Datamodel con `X` seleccionado
   - Field con `references: Y` → idem
   - `record-list` con `layoutId` → selecciona ese layout en el grafo
   - `rowAction.targetLayoutId` → idem
   - Custom element `type: "x"` → (futuro BLY-005: link al componente) por ahora solo muestra info
   - `objectName` raiz → Datamodel con ese object
3. **Fix del cross-link a Datamodel** — al clickear "Ver object", que realmente abra el object como seleccionado (hoy la heuristica `mod-{X}:{objectName}` puede no matchear si el object vive en `core-base` o `tenant-*`)

Base del rediseno futuro: si pegas URL de UP1 o clickeas un nodo, ves en un vistazo **todo lo que la vista tiene dentro** y desde cada pieza puedes saltar al modelo relacionado.

## Artifacts

### Fix cross-link

Composable o helper en el store de layouts:

```typescript
// nuevo helper en useLayoutsStore
function resolveObjectInDatamodel(objectName: string): string | null {
  const datamodel = useDataModelStore();
  const obj = datamodel.model?.objects.find((o) => o.name === objectName);
  return obj?.id ?? null;
}
```

O mejor: composable `useCrossView()` que encapsula la resolucion + router:

```typescript
export function useCrossView() {
  const router = useRouter();
  const datamodel = useDataModelStore();

  function gotoObjectInDatamodel(objectName: string): boolean {
    const obj = datamodel.model?.objects.find((o) => o.name === objectName);
    if (!obj) return false;
    router.push({ path: '/datamodel', query: { entity: obj.id } });
    return true;
  }

  function gotoLayoutInView(layoutId: string) {
    const layouts = useLayoutsStore();
    layouts.selectLayout(layoutId);
  }

  return { gotoObjectInDatamodel, gotoLayoutInView };
}
```

## Decisiones

- **Tree con `<details>` nativo vs componente custom**: elegido nativo por accesibilidad gratis + persistencia de estado trivial + sin watchers. Tradeoff: estilos custom se escriben, pero es CSS trivial (~50 lineas).
- **Secciones abiertas por default**: Tabs y Row actions. Son las ramas mas relevantes para un RecordDetail/RecordList. Columnas/Schema/Custom elements/Capabilities cerradas por default para no saturar.
- **Validacion de dangling por rama**: cada target `layoutId` pasa por `layoutExists()`. Dangling se indica con ⚠ ambar (consistente con anomalies) y sin boton clickeable. Evita navegacion rota.
- **"Invocado desde" siempre visible**: anteriormente solo aparecia dentro del box de "layout auxiliar". Ahora es seccion propia — mostrar aristas entrantes es util tambien para layouts navegables (saber quien los invoca ademas del sidebar).
- **Sub-componentes**: todo quedo inline en DetailPanel (~600 lineas con template + style). Cerca del limite de ~400 lineas que sugiere la convencion de refactor, pero aun manejable. Si crece mas, extraer `StructureTree.vue` con slots por rama.
