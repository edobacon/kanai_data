# Vista Layouts — grafo de flujos UI entre layouts core y de mods

## Request

Agregar a Bayley una nueva vista `/layouts` que muestre un grafo interactivo donde los nodos son layouts (tanto core como de mods) y las aristas representan la navegacion entre ellos (rowActions, record-list embebidos, associatedLayouts, createLayout). Debe permitir responder de un vistazo "¿como llega el usuario desde este listado al detalle del registro hijo?".

La vista cubrira **tanto layouts de mods como layouts del core** — entendiendo por core los layouts default que genera UP1 automaticamente para sus objects base y los layoutTypes standard (RecordList, RecordDetail, ChibiList, OfferingCalendar, ImportTaskList, AiChatbox) que son componentes del workspace `layout/`.

## Scope

### IN

- Nuevo parser `parsers/layouts/` que escanea **todos** los paths de layouts:
  - `mods/*/config/layouts/*.json` — layouts de mods
  - `object-manager/**/config/layouts/*.json` y cualquier otro path donde el core declare layouts por default, si existen como archivo
  - Layouts auto-generados por codegen (tipo `default_{Object}_create.json`) — detectar via convencion de nombre si aparecen en mods o en core
- Reconocimiento de **layoutTypes base** del workspace `layout/src/` como tipos validos aunque el layout no tenga archivo fuente (los genera el core)
- Vista `/layouts` con grafo Vue Flow estilo DataModelView:
  - Nodos = layouts (con tipo, object asociado, tenants, mod/core)
  - Aristas = relaciones de navegacion entre layouts
- Panel de detalle lateral con columnas, tabs, row actions, custom elements invocados, capabilities usadas
- Filtros: por mod/core, por tenant, por objectName, por layoutType, por rol
- Cross-link: click en un nodo resalta el object asociado en DataModelView
- Deep-link: `/layouts?layout=<id>`
- Export JSON del modelo intermedio parseado

### OUT

- Edicion de layouts desde Bayley (solo lectura)
- Renderizado de vista previa del layout (separado, no es parte de este ticket)
- Validacion cross-layer (ticket separado BLY-002)

## Design tecnico

### Estructura de datos (modelo intermedio)

```typescript
// src/types/layouts.ts
export type LayoutSource = { kind: 'core' } | { kind: 'mod'; modName: string };

export type LayoutType =
  | 'RecordList'
  | 'RecordDetail'
  | 'ChibiList'
  | 'OfferingCalendar'
  | 'ImportTaskList'
  | 'AiChatbox'
  | string;  // permitir unknown sin crashear

export type NavigationEdgeType =
  | 'rowaction-navigate'
  | 'rowaction-modal'
  | 'create-layout'
  | 'record-list'
  | 'associated-layout'
  | 'associated-config-view'
  | 'associated-config-edit';

export interface LayoutNode {
  id: string;
  name: string;
  filePath: string | null;           // null si es layoutType core sin archivo
  source: LayoutSource;
  objectName: string;
  layoutType: LayoutType;
  applicationId: string | null;       // null = layout auxiliar
  tenants: string[];                  // ["*"] o ids
  roles: string[];
  mode: 'view' | 'edit' | 'create' | null;
  columns: ColumnRef[];
  tabs: TabRef[];
  rowActions: RowActionRef[];
  customElements: string[];           // types invocados en schema (no standard)
  capabilitiesUsed: string[];
  rawRefs: {
    createLayout: string | null;
    associatedView: string | null;
    associatedEdit: string | null;
    recordListLayouts: string[];      // layoutIds de record-list embebidos
    associatedLayoutIds: string[];    // de tabs
    rowActionTargets: string[];
  };
}

export interface NavigationEdge {
  from: string;
  to: string;
  type: NavigationEdgeType;
  label: string;                      // p.ej. "Ver detalle" (label de la rowAction)
}

export interface LayoutsModel {
  nodes: LayoutNode[];
  edges: NavigationEdge[];
  anomalies: Anomaly[];               // archivos mal formados, targets sin resolver, etc.
}
```

### Parser

```
src/parsers/layouts/
├── index.ts          # export runLayoutsParser(fs): Promise<LayoutsModel>
├── scan.ts           # walk de todos los paths de layouts (mods + core)
├── extract.ts        # parsea un layout JSON → LayoutNode
├── detectEdges.ts    # analiza LayoutNode y extrae NavigationEdge[]
├── coreCatalog.ts    # catalogo de layoutTypes base del workspace layout/
└── validate.ts       # detecta anomalias (targets rotos, campos faltantes)
```

**Rutas escaneadas** (orden):

1. `mods/*/config/layouts/*.json` — categorizados como `mod:<modname>`
2. `object-manager/**/config/layouts/*.json` si existen — `core`
3. `up1/core/**/layouts/*.json` como fallback por si el core publica layouts en otra ubicacion
4. Layouts de archivos con nombre `default_*.json` anywhere — flag `isAutoGenerated: true`

**Core catalog** — archivo `coreCatalog.ts` con lista hardcoded de layoutTypes base (RecordList, RecordDetail, ChibiList, OfferingCalendar, ImportTaskList, AiChatbox) y su description. Si un layout `layoutType` no matchea nada, se marca como anomaly `unknown-layout-type`.

**Extract**: recorrer el JSON del layout y coleccionar:

- Columnas (para RecordList): cada `column.key`, `label`, `sortable`, `relations`, `relationDisplayFields`
- Tabs (para RecordDetail): por cada tab, guardar `label`, `elements[]`, `associatedLayoutId` (si tipo `associatedLayout`)
- Schema (para RecordDetail): por cada campo, guardar `type`, `label`, si `type` es standard (text, textarea, select, toggle, date, number, record-list) o custom (`competency-tree`, etc.)
- rowActions: por cada accion, `id`, `label`, `type` (navigate/modal/delete/default), `targetLayoutId`, `requiredCapability`, `visibilityConditions`
- Capabilities usadas: union de `requiredCapability` en rowActions + cualquier otro lugar

**DetectEdges**: por cada LayoutNode generar aristas:

| Source en JSON | NavigationEdgeType |
|----------------|-------------------|
| `rowAction.type === "navigate" && rowAction.targetLayoutId` | `rowaction-navigate` |
| `rowAction.type === "modal" && rowAction.targetLayoutId` | `rowaction-modal` |
| `layoutConfig.createLayout` | `create-layout` |
| Campo en `schema` con `type: "record-list" && layoutId` | `record-list` |
| Tab con `type: "associatedLayout" && associatedLayoutId` | `associated-layout` |
| `layoutConfig.associatedLayoutConfigs.view.layoutId` | `associated-config-view` |
| `layoutConfig.associatedLayoutConfigs.edit.layoutId` | `associated-config-edit` |

Si un `to` no resuelve a ningun nodo, registrar `anomaly` tipo `dangling-layout-ref`.

### UI

```
src/views/LayoutsView.vue
src/components/layouts/
├── LayoutNode.vue          # nodo custom Vue Flow
├── FiltersSidebar.vue
├── DetailPanel.vue          # columnas, tabs, rowActions, custom elements
├── Legend.vue
└── EdgeLabel.vue

src/stores/layouts.ts        # Pinia store
src/composables/useLayoutGraph.ts  # layout automatico (dagre)
```

**Nodos Vue Flow**: color de fondo distingue `core` (gris claro) vs `mod:<name>` (paleta por mod, consistente con DataModelView). Icono distinto segun `layoutType`. Badge con `applicationId: null` para layouts auxiliares.

**Aristas**: color por `NavigationEdgeType`:
- navigate = azul
- modal = violeta
- create = verde
- record-list = naranja
- associated = rosa

**Filtros** (misma UX que DataModelView):
- Toggle "Solo mods" / "Solo core" / "Ambos"
- Multi-select tenants
- Multi-select objectNames
- Multi-select layoutTypes
- Multi-select roles

### Consideracion core + mods

| Situacion | Que hacer |
|-----------|-----------|
| Layout JSON en mod referencia un `targetLayoutId` de otro mod | Arista cross-mod, color punteado |
| Layout JSON en mod referencia un layout del core | Idem, fuente/destino de `source.kind` distinto |
| LayoutType que no tiene archivo (es un tipo base del core) | El custom element se reconoce desde `coreCatalog.ts`; aparece en panel de detalle pero no como nodo del grafo (solo los layouts reales son nodos) |
| Layout auto-generado (ej. `default_StudyNote_create.json`) | Flag `isAutoGenerated`, mismo tratamiento, label "(auto)" |
| Anomaly: target no resuelto | Nodo "ghost" gris con borde rojo, aparece en panel de anomalias |

Causa raiz: dev server muerto o zombie. Fix: lsof -ti:5173 \| xargs kill -9 antes de npm run dev | reviewer | #2 | raw — relevante para cualquier proyecto vite, no solo bayley |
| L3 | MiniMap de Vue Flow no respeta dark mode por default. Override con CSS `.dark .vue-flow__minimap { background-color: ... }` + `.dark .vue-flow__minimap-mask { fill: ... }` en estilos globales | reviewer | #2 | raw — rule de bayley |
| L4 | Preview (`npm run preview`) vs dev (`npm run dev`) con HMR: cuando hay errores acumulativos, preview es la forma correcta de aislar si el bug es de la app o del dev server | reviewer | #2 | raw |
| L5 | objectFilter arrancando en ALL con 123 layouts reales de UP1 saturaba Vue Flow. Empty-by-default con CTA "seleccionar todos" es mejor UX | reviewer | #2 | raw — aplicable a otras vistas con volumen alto |
| L6 | `backdrop-blur` (backdrop-filter CSS) crea un nuevo stacking context, lo que atrapa el `z-index` de dropdowns de Headless UI dentro de ese contexto local. Fix: remover `backdrop-blur` o elevar el dropdown a un Teleport fuera del contexto. | reviewer | #2 | raw — rule muy relevante: aplicable a cualquier lugar con backdrop-filter + overlay con z-index |
| L7 | Cuando un filter/search recalcula una vista parcial, TODAS las derivadas deben recalcularse — no hacer spread `...model.stats` y sobreescribir algunas. Los contadores que no se sobreescriben arrastran valores globales y producen export inconsistente. Regla: al crear un sub-modelo, derivar stats desde cero sobre el subset, no desde el modelo padre. | reviewer | #2 | raw — aplica a las 3 utilidades en `filterExport.ts` tambien (filterDataModel, filterPermissionsModel, filterI18nModel). Revisar si tienen el mismo patron |
| L8 | Vue Flow MiniMap no colorea nodos por default — acepta prop `:node-color` que toma funcion `(node) => string-hex`. Importante: Tailwind classes NO funcionan, hay que pasar hex literal. Si se usa sistema de paletas basado en clases (MOD_PALETTES con `bg-amber-500`), es necesario un mapeo paralelo a hex para los minimap/SVGs | reviewer | #2 | raw — rule de Vue Flow para bayley |
