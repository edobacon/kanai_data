# Code splitting del bundle — chunk principal < 500 KB

## Request

Sub-ticket #5 del plan de auditoria BLY-028 — ver `SPEC-quality-audit` REQ-IMPROVE-04.

`npm run build` emite warning: "Some chunks are larger than 500 kB after minification". El chunk principal `dist/assets/index-*.js` mide **923 KB raw / 281 KB gzip** — casi el doble del limite recomendado por Vite. Resolver con lazy imports y posibles `manualChunks`.

## Scope

### Estrategia 1: lazy imports en router

Convertir vistas de `import Direct` a `() => import('./views/...')` en `src/router.ts`:

- `DataModelView.vue` (628 lineas, importa Vue Flow + componentes)
- `AppsView.vue` (473 lineas, importa subcomponentes)
- `LangView.vue`
- `SandboxView.vue`
- `PermisosView.vue`

Probable que la primera vista (default) NO se lazy-loade — depende del flujo inicial.

### Estrategia 2: manualChunks (si necesario)

Si el chunk sigue > 500 KB tras lazy: configurar `vite.config.ts`:

```ts
build: {
  rolldownOptions: {
    output: {
      manualChunks: {
        'vue-flow': ['@vue-flow/core', '@vue-flow/background', '@vue-flow/controls', '@vue-flow/minimap', 'dagre'],
        'tanstack': ['@tanstack/vue-table'],
        'jszip': ['jszip'],
      }
    }
  }
}
```

**Discoveries / Learns:**
- **L1**: el bundle no estaba code-split por defecto en Vite — era una sola entry. Convertir las vistas a lazy imports redujo el chunk principal a la **mitad** del limite recomendado (293 KB de 500 KB). En proyectos Vue medianos vale la pena hacer este cambio desde el principio.
- **L2**: la separacion natural por chunks resulto en agrupamientos por dependencia compartida (useScan + useGraphLayout = el cluster mas pesado, viven en su propio chunk porque varias vistas los importan). Vite hace este split automaticamente — no requiere `manualChunks` salvo casos edge.
- **L3**: cero-config (BLY-029) y SW unregister (BLY-038) viven en `main.ts`/store y se cargan eager. El lazy de vistas no los afecta — confirma la hipotesis del SPEC sobre desacoplamiento.
