# Empaquetar bayley como app auto-ejecutable para macOS y Windows manteniendo modos dev y servidor Node

## Request

> "crea ticket para la modificacion en bayley y poder transformarla en una app autoejecutable en macos y windows, pero que siga funcionando tambien como modo dev o servidor node, considera que use puertos que nos e vayan a topar con otros servicios comunes"

Restricciones extraidas del request:

- **Triple modo de ejecucion**:
  1. **Desktop app** — binarios standalone para macOS y Windows (uso interno, sin firma).
  2. **Dev mode** — flujo actual de `npm run dev` (Vite + sidecar con HMR).
  3. **Server Node** — sidecar Express sirve el Vite build como static + API. Permite acceso remoto via LAN o deploy.
- **Puertos no-conflictivos** — evitar rangos comunes (3000, 5000, 8000, 8080, 5173, 5174, 27017, 5432, 3306, 6379, 9000). Aplica como minimo al modo Desktop donde el puerto es invisible al usuario.
- **Uso interno** — sin firma de Apple Developer ni Windows EV code signing. Documentar workaround Gatekeeper/SmartScreen.

## Triage

Caso con tres runtimes que tienen requerimientos distintos pero comparten el mismo build de front + sidecar:

- **Desktop (Electron)**: sidecar embebido, puerto interno oculto, FSA via Chromium del BrowserWindow, sin sidecar visible al usuario.
- **Dev**: HMR de Vite + tsx del sidecar, como esta hoy.
- **Server Node**: Express sirve `dist/` + API. Accesible desde LAN si se expone fuera de localhost. Podria correr en un servidor compartido y que multiples devs lo consuman.

Puntos de tension:

- `SIDECAR_URL` hoy es build-time (`import.meta.env.VITE_SIDECAR_URL`) con default `http://localhost:5174`. Para app Desktop con puerto dinamico, hay que inyectar runtime (preload + `window.bayleyConfig`) o hacer el front puerto-agnostic (mismo origen).
- CORS del sidecar hoy permite solo `http://localhost:5173`. En modo server, el front sirve desde el mismo origen del sidecar → sin CORS. En modo Desktop con `file://`, el origen es `null`/`file://` → requiere relajar CORS.
- El modo "Server Node" puede eliminar CORS por completo si el Express del sidecar sirve el build estatico en el mismo puerto. Sugiere unificar: un solo proceso Express que sirve front+API.
- "Puertos no-comunes": depende del modo. Desktop puede usar puerto dinamico (0 → OS-assigned). Dev puede mantener 5173/5174 (workflow conocido). Server debe ser configurable via env pero con default no-conflictivo.

## Summary

### What was requested
Transformar bayley en app auto-ejecutable para macOS y Windows conservando los modos dev (Vite+sidecar) y server Node, con puertos que no choquen con servicios comunes.

### What was done

**Packaging Electron completo** — 11/12 tasks del SPEC (Task #12 → backlog B1):

- **Frontend preparado para `file://`**: `vite.config.ts` base `'./'`; helper `getSidecarUrl()` runtime-aware que lee `window.bayleyConfig.sidecarUrl` (inyectado via preload `sendSync`) con fallback a `VITE_SIDECAR_URL` build-time. 4 consumidores refactorizados (`stores/app.ts`, `useRuntimeLayouts`, `useRuntimeApps`, `FolderPicker`).
- **Sidecar bundleable**: `esbuild --bundle --platform=node --target=node22` → `sidecar/dist/server.js` 1.7MB. Triple-mode config via `SIDECAR_MODE`: `dev` (CORS localhost:5173, port 5174), `desktop` (CORS `file://, app://bayley, null`, port 0 OS-assigned), `server` (CORS disabled same-origin, port default 59173).
- **Endpoint privilegiado**: `PUT /api/config/root` con auth via header `X-IPC-Token` (shared secret main↔sidecar, generado al spawn). Valida path UP1 con marker check antes de actualizar en memoria. `GET /api/config/root` expone el valor actual.
- **Static serving (modo server)**: `express.static(distPath)` + catch-all SPA routing `/^\/(?!api|health).*/` — un solo proceso sirve frontend + API sin CORS.
- **Electron wrapper** (`electron/main.ts`, `electron/preload.ts`): BrowserWindow con `contextIsolation: true`, `nodeIntegration: false`, `sandbox: true`. Main spawnea sidecar con `child_process.fork` + `cwd: sidecarDir` (para dotenv) + `stdio: ['ignore', 'pipe', 'pipe', 'ipc']`. Sidecar emite `{type:'listening', port}` via `process.send` al terminar `listen(0)`. Preload expone `window.bayleyConfig` via `ipcRenderer.sendSync('bayley:get-config-sync')` para evitar race con el mount del renderer.
- **Integracion con UP1**: helper `electron/read-up1-env.ts` parsea `<up1>/.env` y extrae `OBJECT_MANAGER_URL` (← `GRAPHQL_ENDPOINT`), `TENANT_ID`, `AUTH_TOKEN` (← `STORYBOOK_STATIC_TOKEN` preferido / `UP1_FLOW_SERVICE_TOKEN` fallback — verificado en `userExtractor.js` que `STORYBOOK_STATIC_TOKEN` resuelve a admin real con roleAssignments mientras que `UP1_FLOW_SERVICE_TOKEN` retorna synthetic sin roles → solo ve apps publicas).
- **Persistencia minima**: `electron-store` en `{userData}/bayley-config.json` solo guarda `up1RootPath`. Cero secrets en userData — el `.env` de UP1 es la fuente de verdad en runtime.
- **Menu nativo**: File → Abrir carpeta UP1 (`Cmd+O`), Cambiar carpeta UP1, Reiniciar sidecar. Tras operaciones que cambian sidecarUrl, se usa `createWindow()` recrear la ventana (en lugar de `webContents.reload()` que dejaba pantalla en blanco).
- **Resiliencia**: si el sidecar falla al arrancar (puerto ocupado, `.env` incompleto, object-manager down), la ventana se abre igual con features runtime degradadas y dialog informa. Usuario puede corregir y usar File → Reiniciar sidecar.
- **Auto-activacion inteligente en Electron**: el FolderPicker auto-activa `app.useSidecar()` solo en primer mount (flag `electronAutoActivated` module-scoped + guard `!app.isReady`). Click logo Bayley o "x" Olvidar carpeta no disparan re-activate — el user puede ver el picker de modos.
- **Fix buildMenu (AppsView)**: agregados fallbacks para que layouts con `applicationId: null` (defaults/auxiliares) aparezcan en el grafo cuando el object esta en `defaultObjects` de la app — evita el caso "1 solo nodo" en seeds sin RecordList app-especifico.
- **electron-builder.yml**: appId `com.bayley.desktop`, targets macOS dmg arm64 + Windows portable x64, `asarUnpack: sidecar/dist/**`, icon placeholder 512x512 amber.
- **Scripts npm**: `sidecar:build`, `electron:build`, `electron:dev` (via `scripts/electron-dev.mjs` con `BAYLEY_DEBUG=1`), `electron:dist`, `serve:node` (via `scripts/serve-node.mjs`). Wrappers en Node evitan dep `cross-env` — cross-platform.
- **DevTools opt-in** via `BAYLEY_DEBUG=1` env var. `electron:dev` lo setea automatico para DX; packaged `.dmg` cerrado.
- **README** con seccion Packaging Desktop completa: 3 modos (dev/desktop/server), flujo de config via `.env` de UP1, workarounds Gatekeeper (`xattr -cr`) + SmartScreen, leak de `ELECTRON_RUN_AS_NODE` en shells con MCP tools.
