# Remocion de packaging-as-app — borrar electron/, deps electron*, install scripts y bloque packaging del README

**Decisiones tomadas (DEC-LOCAL del ticket):**

- **DEC-LOCAL-01: Remocion completa del enum `SidecarMode = 'desktop'`** (no mantenerlo como dead value). CLAUDE.md "sin codigo muerto". El parseMode rechaza explicitamente con error claro "Valores aceptados: dev | server".
- **DEC-LOCAL-02: Mantener `bayleyConfig.sidecarUrl` runtime override**. Aunque originalmente fue introducido para Electron preload, es un mecanismo generico util para deployments custom (ej: produccion en LAN, hosting con proxy). Solo se removio `isElectron` + `platform` flags (Electron-specificos).
- **DEC-LOCAL-03: Mantener `?fs=sidecar` auto-activate path** en FolderPicker. Util para Playwright (BLY-035) y deep-links de tests. El flag `electronAutoActivated` se removio porque era especifico al ciclo Electron (renderer life cycle).
- **DEC-LOCAL-04: Mantener `ipcToken` + `requireIpcAuth` en sidecar**. Aunque originalmente para Electron IPC, es patron generico de auth para endpoints privilegiados (`PUT /api/config/root`). Si en server mode el dev quiere usarlo, basta setear IPC_TOKEN env var.

**Discoveries / Learns:**
- **L1**: la remocion del wrapper Electron quitó **3,901 lineas** del package-lock.json + 556 lineas de codigo Electron-especifico. Confirma la hipotesis del audit (BLY-028) de que "packaging-as-app introduce peso innecesario al repo".
- **L2**: el patron `bayleyConfig.sidecarUrl` injection desde una pagina HTML de wrapper es un mecanismo generico util mas alla de Electron — preservarlo abre la puerta a deployments custom sin necesidad de re-introducir wrapper especifico. Documentar en SPEC futuro si surge necesidad.
- **L3**: la presencia de `ipcToken` + `requireIpcAuth` en sidecar/src/server.ts no esta acoplada al ciclo Electron — es un patron generico de auth para endpoints privilegiados que sigue util si server mode necesita configurarse en runtime. Mantenerlo evita re-implementar auth desde cero en el futuro.
