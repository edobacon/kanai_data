# Matriz por tenant — pivot de apps, layouts, objects, capabilities por cliente

## Closure (archivado 2026-04-23)

**Razon**: la matriz incluye `layouts` como una de las 6 filas (apps / layouts / objects / capabilities / components / i18n) con cross-link a `/layouts`, y el ticket depende parcialmente de BLY-001 (LayoutsModel). El contrato de `TenantsMatrix` usa el id de layout como elemento de celda, asumiendo que `/layouts` es la superficie de aterrizaje.

**Estado del eje**: AppsView absorbio el modelo de layouts dentro del contenedor App → Object → Layouts, y [BLY-023](BLY-023.md) (draft) propone eliminar `/layouts`. La dimension "layouts" de la matriz debe re-pensarse como "apps + layout-paths dentro de AppsView".

**No reabrir automaticamente**. Si se retoma la idea de una matriz pivot por tenant, redefinir contra el modelo actual: apps / objects / capabilities / i18n como filas primarias, con "layouts de cada app" como sub-dimension navegable desde AppsView. Muchos REQs (deteccion dinamica de tenants, coverage %, filtros) siguen siendo validos conceptualmente.

Ticket archivado sin implementar.

## Request (original)

Agregar a Bayley una nueva vista `/tenants` que muestre una matriz pivot donde cada columna es un tenant (UPU, DEMO, ACME, ...) y las filas son los elementos configurables: apps (mods), layouts, objects (base / tenant / extended), capabilities, custom components, i18n locales. Cada celda indica si el elemento aplica a ese tenant y con que nivel de detalle (p.ej. rol asignado).

Debe responder sin ambiguedad: "¿que ve el cliente UPU? ¿que cambia entre UPU y DEMO? ¿si habilito el tenant ACME, que falta configurar?". Escanea tanto configuraciones de mods como del core.

## Scope

### IN

- Nuevo parser `parsers/tenants/` que consolida informacion por tenant desde:
  - `app.json` (mods): campo `tenants: [...]`
  - Layouts (mods y core): campo `tenants: [...]`
  - Objects en `tenants/{TENANT}/Base/` — tenant-specific
  - Extended objects `ext__<TENANT>__*.json`
  - Capabilities: lectura de `core_RoleCapability` mapping si es accesible via archivos de seed; si no, marcar como "requiere BD"
  - i18n: locales declarados en `lang/` de cada mod
  - Roles: declarados en `app.json` y layouts
- Vista `/tenants` con tabla pivot: filas = elementos; columnas = tenants dinamicos (detectados)
- Celda con indicador: ✓ (aplica), ✗ (no aplica), estilo especial para "wildcard" (`["*"]`)
- Filtros: tipo de elemento (app / layout / object / capability / ...), por mod, por scope (core / tenant / mod)
- Toggle "modo diff": selecciona 2 tenants → muestra solo filas donde difieren
- Deep-link `/tenants?tenant=UPU` preselecciona columna
- Export CSV y JSON

### OUT

- Lectura desde BD real (Bayley es filesystem-only). Capabilities por tenant asignadas en runtime quedan fuera a menos que haya seed statico
- Edicion de configuraciones por tenant
- Simulacion de "cambiar tenant" (separate ticket BLY-007 si se quiere)

## Design tecnico

### Estructura de datos

```typescript
// src/types/tenants.ts
export type TenantId = string;         // "UPU", "DEMO", "*", "core"
export type ElementKind =
  | 'app'
  | 'layout'
  | 'object-core-base'
  | 'object-tenant-base'
  | 'object-extended'
  | 'object-mod'
  | 'capability'
  | 'custom-component'
  | 'locale'
  | 'role';

export interface TenantElement {
  kind: ElementKind;
  id: string;                          // e.g. layout id, object name, capability name
  sourceFile: string;
  mod: string | null;                  // null = core
  enabledInTenants: TenantId[];        // despues de resolver "*" contra la lista detectada
  rawTenantsSpec: string[];            // tal como aparece en el JSON ("*", ["UPU", "DEMO"], etc.)
  rolesScoped: string[];               // roles del layout/app que aplican
  extras: Record<string, unknown>;     // detalles especificos por kind
}

export interface TenantsMatrix {
  tenants: TenantId[];                 // dinamicos detectados
  elements: TenantElement[];
  orphans: { tenant: TenantId; reason: string }[];
  coverage: Record<TenantId, { total: number; enabled: number; percent: number }>;
}
```

### Parser

```
src/parsers/tenants/
├── index.ts                  # runTenantsParser(fs, { datamodel, layouts, permisos, lang }): TenantsMatrix
├── detectTenants.ts          # union de fuentes de tenants detectados
├── collectElements.ts        # consolida TenantElement[] desde los modelos existentes
├── resolveWildcards.ts       # expande "*" a lista concreta
└── computeCoverage.ts        # calcula % por tenant
```

**Detecta tenants** (union):

1. Directorios en `object-manager/objects/tenants/*/` (salvo Base)
2. Prefijos `ext__<TENANT>__` en `Extended/`
3. Todos los valores no-`*` en campos `tenants: [...]` de mods, apps, layouts
4. Nombres de subdirs en `seed/` que aparezcan como id de tenant

**Resolve wildcards**: un elemento con `tenants: ["*"]` despues de resolver → `enabledInTenants = [...todosLosDetectados]`.

**Coverage**: por tenant, cuenta cuantos elementos de cada tipo estan enabled. Se normaliza: tenant UPU puede tener 80% de apps habilitadas, 60% de layouts, 100% de objects core (siempre activos).

### UI

```
src/views/TenantsView.vue
src/components/tenants/
├── MatrixTable.vue           # TanStack + columnas dinamicas (tenants)
├── DiffMode.vue              # selector 2 tenants + toggle
├── CellDetail.vue            # popover/panel al click
├── CoverageBar.vue           # por columna (tenant)
├── GroupByKind.vue           # agrupacion por ElementKind
└── FilterBar.vue

src/stores/tenants.ts
```

**MatrixTable** — columnas:

| Elemento | Mod | Core | UPU | DEMO | ACME |
|---------|-----|------|-----|------|------|
| App: retention | retention | — | ✓ | ✓ | ✗ |
| Layout: ca_matrix_list | assessment-matrix | — | ✓ | ✓ | ✓ |
| Layout: retention_list_upu | retention | — | ✓ | ✗ | ✗ |
| Object: Person | — | ✓ | ✓ | ✓ | ✓ |
| Object: ext__UPU__person | — | ✓ | ✓ | ✗ | ✗ |
| Object: ResearchProject | — | tenant-UPU | ✓ | ✗ | ✗ |
| Capability: mod/retention:close_case | retention | — | Admin,Coord | Admin | — |

- Celdas con `✓` verde / `✗` rojo, y con tag de rol si aplica
- Columna "Core" solo para elementos que son del core (objects base, layouts base)
- Header de tenant con badge "completitud %"

**Modo diff** — seleccionar 2 tenants, filtra filas donde columnas difieren. Resalta diferencias.

**Cell detail** — click en celda abre panel lateral con:
- Archivo fuente + mod
- Valor literal de `tenants: [...]` en el JSON
- Otros atributos (roles, capability, version)
- Links a DataModel/Layouts/Permisos/Lang segun corresponda

### Consideracion core + mods

| Elemento core | Como se representa |
|---------------|-------------------|
| Object en `business/Base/` | Fila con `mod: null`, `core: ✓`, todas las celdas tenants `✓` (es base, siempre aplica) |
| Object en `tenants/UPU/Base/ResearchProject` | Fila tipo `object-tenant-base`, solo UPU `✓`, resto `✗` |
| Extended `ext__UPU__person` | Fila tipo `object-extended`, solo UPU `✓` |
| Layout default auto-generado | Fila con badge "auto", `tenants: ["*"]` implicito → todas `✓` |
| Capability core (del workspace layout/ o object-manager/) | Fila con `mod: null`, aplica a todos los tenants donde haya algun rol que la use |

El orden de filas en la tabla es: apps → layouts → objects (core → tenant → extended → mod) → capabilities → custom components → locales → roles.
