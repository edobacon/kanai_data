# Workspace snapshot: cachear el ultimo up1 visto en IndexedDB para modo offline

## Summary

### What was requested

Persistir snapshot del up1 real en IndexedDB para operar offline cuando la carpeta FSA o el sidecar no esten disponibles. Indicador UI de fuente activa + staleness.

### What was done

Lo que el dev puede hacer ahora que antes no podia:

- **Modo offline real**: cada scan up1 exitoso replica los archivos que los parsers consumen (~234 files / 700KB) a `bayley.snapshot.up1` en IDB. Al volver sin up1, el FolderPicker ofrece "Usar snapshot offline" con metadata (edad + file count).
- **Indicador visual de fuente**: nuevo `SourcePill` en TopBar que muestra `live / disk / offline / embedded / sandbox` segun `activeWorkspace` + `fsSource`. En cache, agrega badge "sync hace Xd" con staleness color (neutral / amber >7d / red >30d).
- **Re-sincronizar manual**: boton en SourcePill (visible cuando primary accesible y workspace up1) invoca `resyncSnapshot()` que llama a `persistSnapshot` con el primary actual. Feedback visual: spinner mientras sync.
- **Fallback UX transparente**: el flujo de `restore()` al mount carga meta del snapshot en paralelo con handles FSA; expone `capabilities.hasSnapshot` para que FolderPicker ofrezca el modo cache cuando corresponde.
- **Size ceiling defensivo**: `SnapshotTooLargeError` si el snapshot excede 50MB (ceiling por encima del 700KB real del up1). IDB nunca queda en estado corrupto — el snapshot previo se preserva si el nuevo falla.
- **Jerarquia final de fuentes**: `live (sidecar) > disk (FSA) > cache (IDB) > embedded`. Cada capa degrada features gracefulmente (capabilities gate en TabNav).

### What was learned

- **Tamaño real del snapshot muy por debajo de H1**: 700KB vs 5-50MB estimado. Compresion (B2 backlog) innecesaria. 1-key blob IDB es suficiente.
- **D6-D10 confirmadas en Session 2**: eager persist + replicate-on-scan + pill UI + 1-key IDB + walk dirigido.
- **Ruta limpia de reutilizacion**: `InMemoryFsAdapter` de BLY-021 sirve como adapter del snapshot — cero adapter nuevo.

## Request

Al montar un workspace up1 (carpeta FSA o sidecar corriendo), bayley MUST persistir un **snapshot** de los archivos leidos en IndexedDB. Cuando up1 no este disponible en una sesion posterior, bayley DEBE ofrecer operar sobre ese snapshot como fuente de datos (con banner "modo offline, sincronizado {fecha}").

Casos de uso:

1. **Dev con up1 que viaja / trabaja offline**: abrio bayley con up1 montado ayer. Hoy, sin up1 corriendo ni la carpeta accesible, bayley sigue mostrando DataModel/Permisos/Lang/Layouts-disk del up1 real del dev (no del embedded generico).
2. **Dev que perdio el permiso FSA**: al re-abrir bayley, el handle IDB esta pero el permiso del browser se revoco. En lugar de bloquear, cae al snapshot.
3. **Dev que quiere comparar states**: el snapshot refleja el up1 que uso la ultima vez; puede contrastar contra up1 vivo (cuando lo recupera) para detectar drift.

**Depende de BLY-021** (embedded + feature-gate). Este ticket suma una capa entre "up1 vivo" y "embedded": `up1 vivo > up1 disk > snapshot IDB > embedded`.

**Fuera de alcance**:
- Snapshots multiples / historial (solo el ultimo).
- Snapshot de sandbox (sandbox es carpeta local, no tiene sentido cachearlo).
- Cache de respuestas del sidecar **runtime** (Apps/Layouts-runtime) — esto cachea solo el filesystem. Runtime sigue requiriendo up1 corriendo.

## Triage

Scope **medio-alto** — 4-6 tasks. La complejidad esta en:
- Decorator `CachedFsAdapter` que envuelve al primary (FSA o sidecar), lee, y replica a IDB.
- Estrategia de invalidacion (fecha + botoneo manual).
- Indicador claro de fuente activa + "staleness" del snapshot.
- Limites: tamano del snapshot (5-50MB tipico — dentro del budget IDB), path traversal seguro al serializar.

Riesgos: confusion del dev entre up1 vivo y snapshot (banner insuficiente), snapshots grandes que saturan IDB en un browser con cuota apretada, inconsistencia si el snapshot se genero con up1 A pero el dev monta up1 B con otro tenant.

### Context found

**Rules del modulo:**
- CLAUDE.md bayley critical_rule: "Parsers NO usan Apollo ni fetch — solo FsAdapter + JSON.parse". `CachedFsAdapter` respeta esta regla — la lectura sigue siendo FsAdapter.

**Specs relacionados:**
- SPEC-workspace-embedded (BLY-021): base sobre la que este ticket suma capa de cache.
- SPEC-runtime-sidecar (BLY-011): el sidecar fs puede ser primary del cache (se cachea lo que el sidecar entrega).

**Codigo relevante:**
- `parsers/fs/` — FSA + sidecar adapters. Agregar `cached.ts` con decorator.
- [stores/app.ts](bayley/src/stores/app.ts) — source metadata: agregar `cachedAt: Date`, `cachedSource: 'fsa' | 'sidecar'`, `isStale: boolean`.
- `idb-keyval` ya esta en deps para `bayley.folder-handle` — reusar, bucket nuevo `bayley.snapshot.{kind}`.
- [components/shell/TopBar.vue](bayley/src/components/shell/TopBar.vue) + WorkspaceSelector — indicador de fuente activa (live / cached / embedded) + boton re-sincronizar.

**Warnings:**
- **Cuota IDB**: un up1 completo puede superar 50MB. Navegadores dan 50MB-unlimited segun origen (http://localhost vs https con permisos). Documentar que si el usuario usa bayley sobre file:// o http sin permisos, el cache puede fallar.
- **Drift silencioso**: si el usuario cambia de rol en up1 (ej: agrega un mod), el snapshot queda stale hasta proximo sync. El banner DEBE mostrar fecha del ultimo sync prominentemente.
- **Dos up1 distintos**: si el dev monta up1-dev y up1-stage en secuencia, el snapshot se sobreescribe. Aceptable para alcance inicial; si aparece como dolor → BLY posterior con multiples snapshots nombrados.
- **Path traversal / size limits**: al serializar paths como keys, validar contra inyeccion de paths raros. Ceiling hardcodeado de tamano total (ej: abort si snapshot >100MB con mensaje).

### Decisiones previas

**D1 — Solo un snapshot por `WorkspaceKind`**: bucket `bayley.snapshot.up1`. Sandbox no se cachea (es carpeta local). Embedded no se cachea (esta en bundle). Simplifica el modelo mental.

**D2 — Invalidacion manual**: boton "Re-sincronizar" en TopBar cuando up1 esta vivo y hay snapshot. Reemplaza snapshot completo. Alternativa descartada: sync automatico al switch — introduce latencia al activar workspace.

**D3 — Staleness warning visual**: banner sutil en TopBar si snapshot es >7 dias. Color amarillo si >7 dias, rojo si >30 dias. No bloquea uso, solo informa.

**D4 — Fallback automatico a snapshot si primary falla**: si FSA permission denied o sidecar down, `CachedFsAdapter` cae al snapshot transparente + setea flag `store.workspaces.up1.fsSource = 'cache'`. UI muestra banner "modo offline".

**D5 — Jerarquia final de fuentes** (con BLY-021 ya mergeado):
1. up1 live (sidecar fs o FSA + sidecar runtime) — todo habilitado
2. up1 disk (FSA sin sidecar) — Apps/Layouts-runtime off
3. up1 cache (snapshot IDB) — Apps/Layouts-runtime off, banner offline
4. embedded — Apps/Layouts-runtime off, Base genericos del bundle

Usuario elige entre (1-3) via el selector de fuente dentro del workspace up1 + embedded como tab separada.
