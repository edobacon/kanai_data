# Vista Eventos y Flows — grafo de eventos de objects y workflows n8n que los consumen

## Closure (archivado 2026-04-23)

**Razon**: el ticket esta escrito sobre la era donde `/layouts` + deep-link format `id1>id2>id3` eran el eje (ver BLY-006 archivado por la misma razon). El deep-link `/eventos?flow=case:closed>on-case-closed-upu>Up1Notification` reutiliza el formato deprecado, y el concepto de "grafo separado de eventos" fue concebido como vista hermana de `/layouts`.

**Estado del eje**: AppsView + DataModelView son las lentes primarias actuales de bayley. El grafo de eventos/flows podria integrarse como capa adicional sobre una de ellas (ej: flechas de eventos entrantes/salientes desde los objects en DataModel) en lugar de una vista separada.

**No reabrir automaticamente**. El concepto de "visualizar comunicacion asincrona event → flow → action" sigue siendo valido, pero debe rediseñarse desde cero sin heredar el acoplamiento a `/layouts` ni el deep-link format antiguo. Si se retoma, considerar primero si la superficie correcta es una nueva vista o un overlay sobre DataModelView/AppsView.

**Observacion**: los fixtures en `src/embedded/mods/hello-world-mod/events/` y `src/embedded/mods/hello-world-mod/flows/` quedan disponibles para un eventual rediseño.

Ticket archivado sin implementar.

## Request (original)

Agregar a Bayley una vista `/eventos` que muestre como grafo la comunicacion asincrona del sistema: que eventos declara cada mod (y el core, si aplica), que flows n8n los consumen, y que nodos/acciones ejecuta cada workflow. Debe responder: "¿si modifico este object, que workflows se disparan?"; "¿hay eventos sin listener?"; "¿hay flows que escuchan eventos que ya no existen?".

Cubre tanto eventos/flows de mods (`mods/*/events/`, `mods/*/flows/`) como cualquier evento/flow que viva en el core si aplica.

## Scope

### IN

- Parser `parsers/eventsflows/` que escanea:
  - `mods/*/events/*.json` — eventos declarados
  - `mods/*/flows/*.json` — workflows n8n exportados
  - `object-manager/**/events/*.json` si el core publica eventos (fallback)
- Grafo Vue Flow con dos tipos de nodo:
  - Event nodes (azul): declaran un objectType + operation + condition
  - Flow nodes (verde): workflows n8n con sus nodos internos resumidos
- Aristas:
  - `event → flow` (rosa): flow escucha el evento (basado en `up1EventCreate` trigger params)
  - `flow → action` (gris): nodos internos del flow (notification, createObject, http, etc.)
- Panel de detalle: parametros del evento, lista de nodos del flow con sus parametros, tenants asociados
- Filtros: por mod, por objectType, por operation (create/update/delete), por tenant, por tipo de nodo n8n
- Deep-link `/eventos?event=<id>` o `/eventos?flow=<name>`
- Export JSON

### OUT

- Ejecutar workflows desde Bayley (lectura)
- Editar eventos o flows
- Simulacion de payload (posible ticket futuro)

## Design tecnico

```typescript
// src/types/eventsflows.ts
export interface EventNode {
  id: string;                    // p.ej. "case:closed"
  filePath: string;
  mod: string | null;            // null = core
  description: string;
  objectType: string;
  operation: 'create' | 'update' | 'delete';
  condition: string | null;
  conditionValid: boolean;
  includeFields: string[] | null;
  priority: number;
  attempts: number;
}

export interface FlowNodeDetail {
  name: string;
  type: string;                  // e.g. "n8n-nodes-base.up1Notification"
  parameters: Record<string, unknown>;
  position: [number, number];
}

export interface FlowNode {
  name: string;                   // nombre del workflow
  filePath: string;
  mod: string | null;
  active: boolean;
  up1Source: string | null;       // tag de sync
  triggers: Array<{
    nodeName: string;
    tenantId: string;             // puede ser "all"
    objectType: string;
    domain: string;
  }>;
  nodes: FlowNodeDetail[];
  connections: Array<{ from: string; to: string }>;
}

export type GraphEdgeType = 'event-to-flow' | 'flow-internal';

export interface GraphEdge {
  from: string;                    // id de EventNode o nombre de FlowNode / FlowNodeDetail
  to: string;
  type: GraphEdgeType;
}

export interface EventsFlowsModel {
  events: EventNode[];
  flows: FlowNode[];
  edges: GraphEdge[];
  anomalies: Anomaly[];
}
```

### Parser

```
src/parsers/eventsflows/
├── index.ts
├── scanEvents.ts        # walk mods/*/events + core fallback
├── scanFlows.ts         # walk mods/*/flows + core fallback
├── linkEventsFlows.ts   # matchea trigger up1EventCreate con eventos
├── nodeCatalog.ts       # lista de tipos UP1 core con descripcion (para etiquetar nodos)
└── validate.ts
```

**Matching evento ↔ flow**:

1. Por cada `FlowNode.triggers[]`, buscar eventos cuyo `objectType` coincida
2. Si `domain === "all"`, conecta con todos los eventos del mismo `objectType` independientemente del mod
3. Si `domain === <modname>`, conecta solo con eventos del mod cuyo `objectType` coincide
4. Filtrar por `tenantId`: si el flow escucha solo UPU, se muestra con etiqueta de tenant en la arista

**Anomalias**:

- Evento declarado pero ningun flow lo escucha → warning `event-no-listener`
- Flow trigger sin evento matcheable → error `trigger-without-event`
- `active: false` → info `flow-inactive`
- `condition` con error de parseo (JS eval/parse falla) → warning `invalid-condition`

### UI

```
src/views/EventosFlowsView.vue
src/components/eventosflows/
├── EventNode.vue         # nodo Vue Flow azul
├── FlowNode.vue          # nodo verde, expandible
├── FlowInternalGraph.vue # sub-grafo dentro de un flow
├── DetailPanel.vue
├── FiltersSidebar.vue
└── NodeTypeBadge.vue     # icono segun tipo UP1 node

src/stores/eventsflows.ts
```

**Nodos Vue Flow**:

- EventNode: titulo = `event.id`, badges con objectType + operation, icono segun operation
- FlowNode: titulo = `flow.name`, badges con tenantId (o "all"), active/inactive, mini-lista de acciones principales

**Sub-grafo interno**:

Cuando el usuario hace doble click en un FlowNode, se abre un modal/panel con un Vue Flow separado que muestra los `nodes` del workflow con sus `connections`. Nodos coloreados por tipo (notification, createObject, http, etc.).

### Consideracion core + mods

| Caso | Tratamiento |
|------|-------------|
| Evento declarado en core (si existe) | `mod: null`, mismo tratamiento |
| Flow con `domain: "all"` | Escucha eventos de todos los mods del mismo objectType; arista wildcard (punteada) |
| Nodo `up1EventCreate` cuyo `objectType` es un object core (ej. Person) | Valido: el flow escucha creaciones de entidad core |
| Nodo `up1EventCreate` cuyo `objectType` es un object de tenant-base | Solo aplica cuando ese tenant esta activo |
| Nodo n8n custom fuera del catalogo UP1 | Se muestra con tipo literal (ej. "n8n-nodes-base.httpRequest"); badge "generico" |
