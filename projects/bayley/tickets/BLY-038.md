# Auto-unregister Service Worker stale al startup — fix de Vite HMR roto en ventana normal

## Request

> "siempre que inicia me pregunta por la carpeta, el problema es lo incomodo de cada vez tener que navegar a la carpeta, la docs depende si ya existe docs o no, pues hay tickets previos que se encargan de crear la doc"
>
> [tras diagnostico]: "detuve el SW y ahora funciona bien"

El sintoma original que reporto el dev (tener que pickear carpeta cada vez) **no era el bug real** — era una consecuencia de usar incognito como workaround. El bug real es:

En **ventana normal** del browser, bayley se ve "no responsivo" / "no carga los elementos correctamente". Sintomas observados (screenshot del dev en `localhost:5173/datamodel`):
- Datamodel renderea pero el grafo aparece clusterizado en una esquina
- Tabs **Apps** y **Sandbox** ausentes del TabNav
- Console con **62.413+ errores** `TypeError: Cannot read properties of undefined (reading 'send')` en el client de Vite
- **1.001+ failed WebSocket connections** a `ws://localhost:5173/?token=...`

En **ventana incognito**, bayley funciona perfectamente. La diferencia es que incognito desactiva Service Workers + extensiones + caches del sitio.

**Causa raiz confirmada (2026-05-09)**: un Service Worker huerfano registrado en `localhost:5173` interceptaba/rompia el WebSocket de Vite HMR. Bayley actual NO registra SW (verificado: 0 referencias en `src/`, `public/`, sin plugin PWA, sin `sw.js`). El SW vino de una version previa de bayley o de otra herramienta que corrio antes en ese puerto. El browser ejecuta SWs registrados indefinidamente hasta que algo los unregistre.

El dev confirmo: **deteniendo manualmente el SW (DevTools → Application → Service Workers → Unregister) bayley funciona normal sin necesidad de incognito**.

**Workaround aceptado por el dev**: incognito. **Costo del workaround**: incognito no persiste el handle FSA → cada vez hay que re-pickear la carpeta UP1 (la friccion original que motivo este ticket).

Este ticket arregla el problema **automatizando el unregister** para que cualquier dev/tester futuro no tenga que diagnosticar manualmente.

**Warnings:**
- ⚠️ El unregister es asincrono. Si se ejecuta DESPUES de que Vite intento conectar el WS, los primeros errores ya ocurrieron. Mitigacion: ejecutar lo mas temprano posible en `main.ts` (antes de `createApp().mount()`), idealmente como primera linea ejecutable.
- ⚠️ Unregistrar un SW solo evita que se ACTIVE en futuras requests. La pestana actual sigue controlada por el SW activo hasta que se cierra y abre. Mitigacion: opcional → `window.location.reload()` despues del unregister para refrescar sin SW. Pero un reload en cada arranque seria invasivo. **Mejor**: unregister + console.warn explicando que para limpieza completa la pestana se cierre y reabra.

**Decisiones tomadas (DEC-LOCAL del ticket):**

- **DEC-LOCAL-01: Warning-only, sin auto-reload de la pestana**. Auto-reload es invasivo y sorprende al user. El warning con sugerencia "recarga la pestana" es suficientemente explicito.
- **DEC-LOCAL-02: Invocacion en `main.ts` antes de `createApp()`**. Minimiza la ventana donde Vite HMR intenta conectar antes del cleanup. Fire-and-forget para no bloquear el mount.
- **DEC-LOCAL-03: Solo en dev mode (`import.meta.env.DEV`)**. En produccion bayley puede llegar a registrar SW propio en el futuro y este cleanup defensivo seria invasivo. En dev el SW propio nunca se registra.
- **DEC-LOCAL-04: Interfaces locales `SwLikeContainer`/`SwLikeRegistration` en vez de globals `ServiceWorkerContainer`/`ServiceWorkerRegistration`**. La lib del tsconfig actual de bayley (extends `@vue/tsconfig/tsconfig.dom.json`) no expone estos types al codigo, causando errors en build. Las interfaces locales son minimas (solo `getRegistrations` y `unregister`) y simplifican el mocking en tests.

**Discoveries / Learns:**
- **L1**: `@vue/tsconfig/tsconfig.dom.json` no expone los globals `ServiceWorkerContainer`/`ServiceWorkerRegistration` aunque tecnicamente son parte del lib `dom`. Patron a recordar: si una API DOM "moderna" no compila, definir interfaces locales minimas en vez de pelear con `lib` config (segunda parte: simplifica mocking).
- **L2**: vitest pattern para mockear APIs del browser sin depender de jsdom: pasar el container como parametro opcional (default = lookup global) → tests pasan mock, codigo de prod usa el default. Util para futuros helpers que toquen `navigator.*` o `window.*` o APIs que jsdom no implementa.
