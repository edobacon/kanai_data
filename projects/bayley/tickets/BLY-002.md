# Validaciones cross-layer — detectar referencias rotas entre layouts, objects, capabilities, i18n

## Closure (archivado 2026-04-23)

**Razon**: el motor de validacion se disena sobre `LayoutsModel` como uno de los 4 inputs centrales. Las familias de reglas **VAL-LL-*** (layout→layout) y **VAL-LO-*** (layout→object) asumen la vista `/layouts` como superficie de navegacion de hallazgos, y el ticket depende explicitamente de BLY-001 (parser de layouts para LayoutsView).

**Estado del eje**: LayoutsView esta deprecada — BLY-006 ya fue archivado por la misma razon y [BLY-023](BLY-023.md) (draft) propone eliminar `/layouts` preservando AppsView. La aproximacion actual de bayley usa AppsView + DataModelView como lentes primarias.

**No reabrir automaticamente**. Si se retoma la idea de validaciones cross-artifact, redefinir como "validaciones sobre el modelo de Apps + DataModel" con navegacion de findings desde esas vistas, no desde `/layouts`. Muchos REQs (familias de reglas) siguen siendo conceptualmente validos y pueden inspirar el rediseño, pero el alcance y contrato actual estan invalidados por el cambio de eje.

Ticket archivado sin implementar.

## Request (original)

Implementar un motor de validacion que cruce los modelos parseados (datamodel, layouts, permisos, i18n) y detecte inconsistencias que hoy solo aparecen en runtime o en produccion. Resultado: una nueva vista `/validacion` con tabla de hallazgos clasificados por severidad, archivo, linea (cuando aplica), y sugerencia de fix.

Debe cubrir **tanto codigo de mods como codigo core** de UP1. Ej: un mod que referencia un object core con campo inexistente debe detectarse igual que un mod que referencia algo inexistente dentro de si mismo.

## Scope

### IN

- Nuevo motor `parsers/crosscheck/` que consume `DataModel`, `LayoutsModel`, `PermisosModel`, `LangModel`
- Catalogo de reglas de validacion con id, severidad (error/warning/info), descripcion, mensaje parametrizado
- Cada hallazgo: `ruleId`, `severity`, `message`, `filePath`, `locationHint` (key o path dentro del JSON), `suggestion`, links a otras vistas
- Vista `/validacion` con tabla filtrable (severidad, modulo, mod, regla)
- Export JSON de hallazgos

### OUT

- Auto-fix de problemas detectados (solo reporte, no modifica archivos)
- Validacion de sintaxis JS/TS de resolvers (fuera de scope; se trataria en otro ticket si se quiere linting)
- Validacion de performance o runtime (solo estatica)

## Design tecnico

```typescript
// src/types/validation.ts
export type Severity = 'error' | 'warning' | 'info';

export interface Finding {
  ruleId: string;
  severity: Severity;
  family: 'layout-object' | 'layout-layout' | 'layout-capability' | 'layout-i18n' | 'layout-tenant' | 'object-object' | 'resolver-capability';
  message: string;
  filePath: string;
  locationHint: string;          // e.g., "$.columns[3].key" o "line 42"
  suggestion: string;
  context: {
    mod?: string;
    core?: boolean;
    tenant?: string;
    layoutId?: string;
    objectName?: string;
    capability?: string;
  };
  relatedViewLinks: {
    datamodel?: string;
    layouts?: string;
    permisos?: string;
    lang?: string;
  };
}

export interface ValidationReport {
  findings: Finding[];
  summary: {
    total: number;
    byServerity: Record<Severity, number>;
    byFamily: Record<string, number>;
  };
  suppressed: string[];         // ruleIds ignorados via .bayley-ignore.json
  runAt: string;
}
```

### Estructura del parser

```
src/parsers/crosscheck/
├── index.ts              # runCrosscheck(models): Promise<ValidationReport>
├── rules/
│   ├── layoutObject.ts   # VAL-LO-*
│   ├── layoutLayout.ts   # VAL-LL-*
│   ├── layoutCapability.ts
│   ├── layoutI18n.ts
│   ├── layoutTenant.ts
│   ├── objectObject.ts
│   └── resolverCapability.ts
├── suppress.ts           # lee .bayley-ignore.json y filtra findings
└── types.ts
```

Cada archivo de reglas exporta `rules: Rule[]`, donde `Rule`:

```typescript
interface Rule {
  id: string;
  family: string;
  severity: Severity;
  check: (ctx: ValidationContext) => Finding[];
}

interface ValidationContext {
  datamodel: DataModel;
  layouts: LayoutsModel;
  permisos: PermisosModel;
  lang: LangModel;
  fs: FsAdapter;
}
```

El orquestador `index.ts` importa todas las reglas, ejecuta cada una con el contexto, concatena findings, aplica suppress.

### Consideracion core + mods

Todas las reglas deben funcionar tanto si las dos partes son del core, como si una es del core y otra del mod, como si ambas son del mod. Ejemplo VAL-LO-001:

| Layout (source) | Object (referenciado) | Caso |
|-----------------|----------------------|------|
| mod | mod | campo renombrado en object del mismo mod |
| mod | core base | campo renombrado en object core |
| mod | tenant core | campo no existe en ese tenant |
| mod | extended | campo declarado en extended de otro tenant |
| core | core | caso menos comun pero posible |

La regla no distingue — compara por object + field. El contexto del finding reporta ambos origenes (`mod` y/o `core: true`).

```json

  "suppressedRules": [
    { "ruleId": "VAL-LO-007", "scope": "all", "reason": "aceptamos que created_at no este en create layouts" },
    { "ruleId": "VAL-LC-002", "scope": "mod:legacy-mod", "reason": "mod de migracion, no cambiar" }
```

Bayley lo lee en scan; findings suprimidos se cuentan aparte pero no ensucian la tabla principal.
