# Workspace embedded: arrancar bayley sin up1 + ocultar vistas inviables

## Summary

### What was requested

Habilitar un tercer `WorkspaceKind = 'embedded'` que permita usar bayley sin tener up1 clonado ni corriendo: assets bundleados, in-memory fs adapter, feature-gate que deshabilita vistas dependientes del sidecar.

### What was done

Lo que el dev puede hacer ahora que antes no podia:

- **Onboarding sin up1**: primer mount de bayley ofrece boton emerald "Usar embedded (demo)" en FolderPicker. Click → lazy-import + scan → DataModel renderea 43 objects distribuidos en 5 scopes (Core Base / Core Extended / Tenant TEST / Tenant UPU / hello-world-mod).
- **Switch 3 workspaces**: WorkspaceSelector en TopBar ofrece UP1 / SANDBOX / EMBEDDED con indicador de scan por workspace. Activacion embedded via `activateEmbedded()` es idempotente (adapter cacheado en el store).
- **Feature-gate centralizado**: computed `capabilities = { hasSidecarRuntime, hasDiskAccess, canGenerateSandboxKit }` en app store. TabNav consume el flag y renderea tab Apps como button disabled con tooltip "Requiere up1 + sidecar corriendo" cuando el workspace activo no tiene sidecar. Navegacion manual a `/apps` (deep-link) redirige a `/datamodel` via router guard.
- **sandboxKit agnostico**: parametro renombrado `fsUp1` → `fs: FsAdapter`. Funciona identicamente desde cualquier workspace que tenga adapter.
- **Script reproducible**: `scripts/sync-embedded-base.mjs --up1=<path>` regenera `src/embedded/` con 79 JSON (Base, Extended, Tenants UPU/TEST, hello-world-mod completo). Idempotente, genera `manifest.json` con metadata.
- **Bundle optimizado**: chunk `embedded-*.js` separado de 140KB raw / **17.48KB gzipped**. El bundle inicial de bayley NO paga el costo hasta que el usuario active el workspace.

## Request

Habilitar un tercer `WorkspaceKind = 'embedded'` que permita usar bayley **sin tener up1 clonado ni corriendo**. El workspace embedded:

1. No pide carpeta al usuario — se activa con un click en el selector.
2. Sirve un set de archivos JSON empaquetados con el bundle de bayley (Base + un mod de ejemplo) via un `InMemoryFsAdapter` que cumple la interfaz `FsAdapter` existente.
3. Las vistas **DataModel, Permisos, Lang, Layouts (disk)** operan normal sobre el embedded — los parsers ya son agnósticos al origen de los archivos.
4. Las vistas **Apps y Layouts (runtime)** se ocultan o muestran banner "requiere up1 corriendo" cuando el workspace activo es embedded o sandbox (generalizable: cuando `workspaceKind !== 'up1'` o `fsSource !== 'sidecar'`).
5. El generador `sandboxKit.ts` se desacopla de up1 y pasa a operar sobre cualquier `FsAdapter` — el usuario en embedded puede descargar el zip para dárselo a un LLM.

**Motivacion del dev**: onboarding instantáneo (ver datamodel/layouts sin setup) + permite compartir bayley como herramienta standalone. Hoy el único bloqueante para usar bayley sin up1 es el bootstrap del sandbox (sandboxKit necesita fsUp1 para generar el zip inicial).

**Fuera de alcance (BLY-022)**: snapshot IDB del último up1 visto como fuente cacheada. Esta fase entrega solo embedded estático + feature-gate de vistas.

## Triage

Feature de scope **medio** — 5-7 tasks. No toca parsers (son agnósticos), pero introduce:
- Nuevo literal `'embedded'` en `WorkspaceKind` + ajustes mecánicos en `app.ts`, `HANDLE_KEYS`, selector UI.
- Nuevo `InMemoryFsAdapter` (lectura desde assets embebidos via `import.meta.glob`).
- Generalización de `sandboxKit.ts` (`fsUp1` → `fs: FsAdapter`).
- Feature-gate: router/tab nav oculta Apps y Layouts-runtime para workspaces sin sidecar runtime.
- Pipeline de build (`scripts/sync-embedded-base.ts`) para regenerar los assets embebidos desde un up1 local o CI.

Riesgos: tamaño del bundle si Base crece, desincronización de embedded vs up1 real, UX del selector con 3 kinds.

### Context found

**Rules del modulo (workspace/parsers):**
- CLAUDE.md bayley critical_rule: "Parsers NO usan Apollo ni fetch — solo FsAdapter + JSON.parse". `InMemoryFsAdapter` respeta esta regla (es un FsAdapter local).

**Specs relacionados:**
- SPEC-runtime-sidecar (BLY-011): dependencia que embedded NO usa — queda apagado en este workspace.
- SPEC-views-apps-flow (BLY-016): AppsView consume sidecar runtime — debe ocultarse con feature-gate.
- BLY-019 commits ya introdujeron el concepto de workspace multiple (up1 + sandbox) — este ticket extiende ese pattern.

**Codigo relevante:**
- [types/workspace.ts](bayley/src/types/workspace.ts) — `WorkspaceKind` union, agregar `'embedded'`.
- [stores/app.ts](bayley/src/stores/app.ts) — `workspaces` reactivo, `HANDLE_KEYS`, logica de active workspace + switch.
- [utils/sandboxKit.ts](bayley/src/utils/sandboxKit.ts) — firma `generateSandboxKit(fsUp1)` a generalizar.
- [components/shell/WorkspaceSelector.vue](bayley/src/components/shell/WorkspaceSelector.vue) — UI selector.
- [components/shell/FolderPicker.vue](bayley/src/components/shell/FolderPicker.vue) — onboarding.
- [components/shell/TabNav.vue](bayley/src/components/shell/TabNav.vue) — tabs Apps / Layouts — aplicar feature-gate.
- `parsers/fs/` — crear `memory.ts` con `createInMemoryFsAdapter(files)`.

**Warnings:**
- **Base desactualizado**: el embedded se empaqueta al build time. Si up1 cambia Base, el embedded queda stale hasta el proximo release de bayley. Aceptable — up1 montado siempre lo supera (banner "embedded: Base v{date}" para claridad).
- **Bundle size**: Base completo de up1 puede ser 5-20MB JSON. Mitigar con lazy-load del modulo embedded (dynamic import solo cuando se activa el workspace embedded) + curado del Base (solo lo minimo util para demo: ~10-20 objects clave).
- **Sidecar fs vs embedded**: el `FsAdapter` source actual tiene 2 valores (`'fsa' | 'sidecar'`). Sumar `'memory'` como tercer source. Validar que codigo downstream no asume `fsSource === 'fsa'` cuando `!== 'sidecar'`.
- **Feature-gate no-funcional vs deshabilitado**: decidir en diseno si Apps/Layouts-runtime se ocultan completamente del TabNav o se muestran con estado disabled + tooltip. Ocultar es mas limpio; disabled es mas discoverable.

### Decisiones previas

**D1 — Workspace kind separado, no workspace auto-adaptativo**: agregar `'embedded'` como tercer literal. El usuario elige explicitamente via selector. Rationale: predictibilidad vs magia de fallback automatico; coherente con el patron up1/sandbox ya establecido.

**D2 — Assets embebidos via `import.meta.glob('/src/embedded/**/*.json', { eager: true, as: 'raw' })`**: Vite resuelve en build time. Alternativa descartada: `fetch('/embedded/...')` — requiere coordinar paths runtime y no aprovecha tree-shaking.

**D3 — Lazy-load del modulo embedded**: dynamic import `() => import('@/embedded')` solo cuando el usuario selecciona el workspace. Bundle inicial no paga el costo si no lo usa.

**D4 — Feature-gate centralizado**: un computed `currentWorkspaceCapabilities` en `app.ts` que exponga flags `hasSidecarRuntime: boolean`, `hasDiskAccess: boolean`. TabNav y views leen de ahi.

**D5 — Ocultar vs disabled**: **ocultar** las tabs Apps + Layouts-runtime mode cuando `!hasSidecarRuntime`. Fila de confirmacion con el dev durante el design. (TBC)

**D6 — `sandboxKit` agnostico**: `generateSandboxKit(fs: FsAdapter, opts)` — funciona desde up1, sandbox o embedded. Al correr desde embedded, el zip resultante contiene los Base embebidos + AGENTS.md + EXAMPLES.md.
