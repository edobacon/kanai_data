# Sidecar Node para traer layouts runtime desde object-manager

## Request

Muchos layouts de UP1 no viven en JSON declarados — se generan/persisten en la DB via el LayoutOrchestrator (caso descubierto en BLY-009: `up1suiteapp_list_387920` no existe en disco, solo en DB). Hoy la vista Jerarquia los marca como "sin layout JSON — runtime UP1" pero no podemos inspeccionar su schema, flow ni diferencias vs un layout declarado.

Necesitamos un **sidecar Node (Express)** que:
1. Reciba pedidos desde Bayley frontend (`localhost:5173`)
2. Hable GraphQL con **object-manager** (`localhost:4000`) con los headers correctos (`X-Tenant-ID`, auth)
3. Ejecute los mismos queries que el LayoutOrchestrator (`resolveDefaultLayout`, `getInstance(objectType:"up1_layen_layout")`, `GetLayoutByName`)
4. Devuelva el JSON del layout runtime a Bayley para que lo parsee con `extractLayout` existente

Bayley lo muestra como "layout runtime" al lado del declarado (o solo, si no hay declarado), con badge `[DB]`.

## Scope

### IN

- Nuevo workspace/folder en Bayley: `bayley/sidecar/` (Express mini, <200 lineas)
- Queries portados desde `up1/layout/src/layouts/LayoutOrchestrator.vue` (3-4 queries copy-paste)
- Endpoints del sidecar:
  - `GET /api/runtime-layout/:layoutId` → GetLayoutConfig
  - `POST /api/resolve-default-layout` body: `{objectName, layoutType, mode?, roleName?, applicationId?}` → RESOLVE_DEFAULT_LAYOUT
  - `GET /api/runtime-layout/by-name/:name` → GetLayoutByName
- Config del sidecar: `objectManagerUrl`, `tenantId`, `authToken` via `.env` o CLI args
- Cliente en Bayley (`src/composables/useRuntimeLayouts.ts`) que llama al sidecar
- UI en HierarchyTree: boton "Cargar layout runtime" en objects con `hasDeclaredLayouts: false`
- UI en DetailPanel de Layouts: seccion "Runtime comparison" cuando hay ambos declarado + runtime
- Render del layout runtime usando `extractLayout` (el mismo parser) con badge `source: 'runtime-db'`
- **Single-command dev**: `npm run dev` en `bayley/` arranca Vite + sidecar en paralelo (concurrently). No pedirle al dev arrancar dos terminales
- Script `npm run dev:sidecar` tambien disponible standalone por si alguien quiere solo el sidecar
- Output unificado con prefijos claros (`[vite]`, `[sidecar]`) para distinguir logs
- Kill coordinado: Ctrl+C en el terminal baja ambos procesos limpiamente
- README con instrucciones: como obtener auth token, que tenant usar, que corra object-manager primero

### OUT

- Escritura de layouts en DB (solo lectura)
- Soporte multi-tenant simultaneo (un sidecar, un tenant)
- Proxy de otros endpoints de object-manager (solo layouts)
- Replicar el LayoutOrchestrator — solo llamamos a object-manager que ya tiene esa logica
- Integracion con Auth0 real — para dev basta con un token pre-generado

## Decisiones

- **Express vs Nuxt/Nitro**: Express. Sidecar es 150 lineas de proxy, Nuxt agrega SSR que no necesitamos.
- **Portar queries vs importar orchestrator**: portar. El orchestrator acopla a Vue + Apollo + Nuxt runtime. Copy-paste de 3 queries se mantiene solo.
- **Single-tenant por sidecar**: simplicidad. Multi-tenant = varios sidecars en puertos distintos.
- **Adapter reusa `extractLayout`**: paridad garantizada entre layouts JSON y runtime. Mismo shape, mismas anomalies.
- **`addRuntimeLayouts` en vez de `setModel`**: mergea en lugar de reemplazar. Dedup por id, popula objectFilter.
- **Paleta indigo para runtime-db**: distingue visualmente pero no grita. Consistencia con patron de colores por source.

## Open questions

1. ¿Como conseguimos el auth token para el sidecar en dev? → R: usuario lo extrae de cookies de UP1 logueado y lo pone en `.env`. Documentar en README.
2. ¿Cache de responses en el sidecar? → R: no en V1. Cada pedido pega a object-manager. Si pesa, agregar LRU con 5min TTL despues.
3. ¿Que pasa si object-manager cambia los queries (breaking)? → R: sidecar rompe. Fix: actualizar queries. Monitorear via tests de integracion opcional.
4. ¿Nuxt Nitro en vez de Express? → R: Express por simplicidad (sidecar es trivial). Nuxt seria overkill y agrega SSR no necesaria.
5. ¿El sidecar debe soportar multiples tenants simultaneos? → R: no en V1. Un sidecar = un tenant. Si se necesitan multiples, corre varios o agrega `tenantId` por request.

## Riesgos

- **Auth token expira**: no hay refresh automatico en V1. El usuario actualiza `.env` y reinicia sidecar.
- **object-manager down**: el sidecar responde 503 y Bayley muestra banner "servicio no disponible".
- **CORS con object-manager**: el sidecar es el unico que habla con object-manager (server-to-server), no hay CORS entre ellos. CORS solo entre Bayley frontend y sidecar, que es cross-origin pero local-local, facil de habilitar.
