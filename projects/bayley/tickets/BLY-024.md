# Vista Sandbox: overlay de un mod candidato sobre el workspace activo

## Summary

### What was requested

Re-enfocar Sandbox: de `WorkspaceKind` paralelo a **vista** (pestaña) que compone una carpeta candidata (mod en desarrollo) sobre el workspace activo (up1 o embedded). Deprecar el `WorkspaceKind = 'sandbox'` anterior.

### What was done

Lo que el dev puede hacer ahora que antes no podia:

- **Iterar un mod sin up1 completo**: activa embedded (Base + Extended + Tenants + hello-world bundleados) y usa SandboxView para cargar su mod → ve el mod integrado con el core sin setup.
- **Iterar un mod contra up1 real**: workspace up1 (live/disk/cache) + SandboxView overlay → ve su mod superpuesto con el UP1 de la empresa.
- **Comparar con/sin overlay**: toggle separado del picker. Enciende/apaga la composicion con un click. Debugging "¿esta diferencia viene de mi mod o del core?".
- **Overrides de core**: si el mod tiene override de `object-manager/objects/business/Base/Person.json`, overlay-wins gana — ve el efecto immediate.
- **Sandbox-kit**: boton "Descargar candidate-model.zip" reubicado en SandboxView. El kit se genera del CORE base (sin overlay) — util para darle a un LLM como punto de partida.
- **Indicador visual**: SourcePill agrega segmento `+ overlay · {nombre}` violeta cuando overlay on.

### Arquitectura

| Capa | Cambio |
|------|--------|
| **Types** | `WorkspaceKind = 'up1' \| 'embedded'` (sin sandbox) |
| **Adapter** | `parsers/fs/layered.ts` con overlay-wins. 14 casos unit |
| **Store** | Overlay state (handle IDB + enabled localStorage + meta); actions pickOverlayFolder/toggleOverlay/forget/reconnect; `baseAdapterFor` (sin overlay) + `fsAdapterFor` (con composicion) |
| **Scan** | 2 slots snapshot por workspace (`snapshot` + `snapshotOverlay`). Toggle instantaneo cuando slot ya cargado |
| **UI** | Ruta `/sandbox` + tab en TabNav + `SandboxView.vue` (picker, toggle, summary, kit); SourcePill con segmento overlay; FolderPicker simplificado |

### What was learned

- **Pinia unwrappea refs anidados de forma inconsistente**: al retornar un objeto complejo (`overlayFolder` con refs adentro) desde setup store, el acceso desde consumidores via `store.overlayFolder.handle.value` falla con "Cannot read properties of null (reading 'value')" porque el ref fue desempacado pero el getter espera un ref. **Solucion**: exponer computeds top-level en el store (`overlayHandle`, `overlayPermissionState`) en vez del objeto completo. Learn potencial para refactor de patrones similares en el futuro — candidato a RULE.

## Request

**Replantear Sandbox**: hoy es `WorkspaceKind = 'sandbox'` — una carpeta up1-like que se monta como workspace paralelo. El dev propone moverlo de workspace a **vista** (al lado de DataModel/Apps/Permisos/Lang).

Comportamiento:
- El workspace activo (`up1` o `embedded`) aporta los **datos base**.
- La vista Sandbox permite cargar una **carpeta candidata** (mod en desarrollo) y activarla como **overlay**.
- Cuando overlay esta activo, todas las vistas (DataModel, Apps, etc.) muestran la composicion `overlay + base`.
- Util para **iterar en el modelo de datos de un mod**: el dev ve su mod integrado con UP1 real (si tiene up1) o con los Base/Extended/Tenants/hello-world bundleados (si usa embedded).

**Motivacion del dev**: ahorrar setup al iterar en el modelo de un mod — no hace falta montar un up1 completo para previsualizar como queda el mod.

**Deprecar** `WorkspaceKind = 'sandbox'` en este mismo ticket.

### Context found

**Rules del modulo:**
- CLAUDE.md bayley: parsers NO usan Apollo ni fetch — solo FsAdapter. LayeredFsAdapter respeta esta regla.

**Specs relacionados:**
- SPEC-workspace-embedded (BLY-021): provee el `InMemoryFsAdapter` que sirve como base cuando workspace = embedded.
- SPEC-workspace-snapshot-cache (BLY-022): provee `activateCached` — orthogonal, el overlay puede componer sobre cache igual que sobre live/disk.

**Codigo relevante:**
- `types/workspace.ts` — remover `'sandbox'` del union.
- `stores/app.ts` — mucho a cambiar: remover `sandboxFolder`, branches sandbox, agregar `overlay*` refs + actions.
- `parsers/fs/` — crear `layered.ts`.
- `views/` — nueva `SandboxView.vue`.
- `components/shell/WorkspaceSelector.vue` — remover opcion sandbox.
- `components/shell/FolderPicker.vue` — remover branches sandbox (quedan up1 + embedded + snapshot).
- `components/shell/SourcePill.vue` — agregar pill secundario "+ overlay · {nombre}".
- `components/shell/TabNav.vue` — agregar tab Sandbox.
- `router.ts` — ruta `/sandbox`.
- `utils/sandboxKit.ts` — sigue funcionando (FsAdapter generico); call site migra a SandboxView.

**Warnings:**
- **Handle huerfano en IDB**: users con `bayley.folder-handle.sandbox` guardado no pierden data (solo queda entry inalcanzable). Documentar en CHANGELOG/README. Opcional: limpiar automaticamente al primer mount con la version nueva (no critico).
- **Overlay + workspace embedded**: la carpeta candidata puede overridear archivos del embedded. Ej: dev modifica `object-manager/objects/business/Base/Person.json` en su carpeta → se sobreescribe al renderear. Aceptable (es el punto del overlay) pero debe quedar claro visualmente.
- **Persistencia del handle overlay + del toggle**: IDB para el handle (nueva key `bayley.folder-handle.overlay`), localStorage para `overlayEnabled`.
- **Re-scan al togglear**: cambiar overlay on/off requiere re-hidratar los stores de dominio. Opcion 1: re-scan completo (lento, 500ms-2s). Opcion 2: mantener 2 snapshots (base y overlay) y switchear (instantaneo). H3 apuesta por opcion 2.
