### P7 — UX feo: doble render de fences (rawMarkdown muestra YAML plain + componente rico repite contenido abajo)

**Sintoma reportado por el dev**: "esos textos se deben ver asi? debemos buscar una mejor forma de mostrar esos textos, no son amigables al usuario". El comportamiento actual:
- MarkdownBody renderea el rawMarkdown completo del archivo `.teach/*.md` con los fences `\`\`\`dkc:hypothesis-map ...\`\`\`` como **code blocks plain** (texto YAML crudo, feo, ocupa muchas lineas).
- Debajo, la seccion "Visualizaciones · N bloques" del SectionTeachings renderea **los mismos bloques** ahora con los componentes ricos (HypothesisMap dual-mode, DecisionMatrix heatmap, LearningPath timeline).
- Resultado: el contenido aparece **2 veces** — una como YAML feo en el flujo del markdown, otra como componente rico al final. Confunde al lector y rompe el flujo educativo.

**Origen — L7 de HOR-013**: durante S5, modificar MarkdownBody.vue para interceptar fences `dkc:*` inline requeria refactor mayor (cambiar de `v-html="rendered"` a render basado en tokens). Pivot pragmatico: dejar MarkdownBody intacto, render rico aparte. Costo asumido: doble render. Backlog item B2 de HOR-013 marcado como `could`. **Se reclasifica a `must` con HOR-014 P7**.

**Diseno propuesto** (a iterar en intake-explore):
- Refactorizar `MarkdownBody.vue` y/o `useMarkdown` composable para que **al detectar un fence `dkc:hypothesis-map | decision-matrix | learning-path`** renderee el componente rico **inline en el lugar exacto** del markdown, no como code block plain.
- Mismo trato para fences `\`\`\`mermaid\`\`\`` — actualmente aparecen como code block; deben renderear via `MermaidBlock.vue` inline.
- Eliminar la seccion separada "Visualizaciones · N bloques" del SectionTeachings — ya no es necesaria si los bloques renderean inline.
- Resultado UX: el lector ve el flujo educativo del archivo `.teach/*.md` con los componentes ricos integrados al markdown — sin duplicacion, sin YAML feo, sin scroll innecesario.

**Implementacion candidata**:
- Vue 3 + markdown-it: usar custom renderer/plugin para que `markdown-it.renderer.rules.fence` matchee `info: 'dkc:*' | 'mermaid'` y emita un placeholder unico (ej: `<div data-dkc-block="N"></div>`).
- Componente Vue post-render reemplaza placeholders con los componentes Vue correspondientes (via Teleport o `defineCustomElement`).
- Mantener legacy: si el fence kind no se reconoce (futuras extensiones de bloques), cae a code block plain con el rawYaml.

**Riesgos**:
- markdown-it plugin custom + Vue Teleport necesitan tests cuidadosos para edge cases (fences anidados, info string con espacios, escape de HTML).
- Cambio toca `MarkdownBody.vue` que es consumido por **muchos otros tabs** (request, details, testing, summary, draft-intent). El refactor debe **no romper** esos tabs — solo cambiar el comportamiento para fences `dkc:*` y `mermaid`.
- Performance: si hay muchos bloques mermaid en un teaching grande, render async puede causar layout shift. Necesita Suspense o skeleton.

### P2 — Teachings deben enseñar a nivel de codigo, no solo intencion

**Estado actual** (post-HOR-013): los templates `teach-intake.md` y `teach-close.md` tienen secciones para hipotesis, decisiones, basics, learning path. Generan archivos educativos sobre el caso pero **abstractos** — explican QUE se hizo y POR QUE, sin mostrar QUE codigo cambio.

**Lo que pide el dev**: los teachings deben incluir **snippets concretos del codigo afectado** con explicacion de por que ese cambio. El dev futuro (o el mismo dev retomando) debe poder leer el teach-close y entender no solo la intencion sino tambien la implementacion — que archivos cambiaron, que lineas, por que esa solucion y no otra.

**Areas a extender**:
- Template `teach-intake.md`: agregar seccion "Codigo a tocar" con paths concretos + snippets relevantes del estado actual (pre-cambio) y descripcion del delta esperado.
- Template `teach-close.md`: agregar seccion "Codigo final" con snippets post-cambio + diff conceptual + explicacion de las decisiones de implementacion (no solo arquitecturales).
- Probable nuevo bloque `dkc:code-walkthrough`: snippets numerados con `path:line` + comentario educativo por snippet. Schema: `steps: [{ path, lines, code, why }]`.
