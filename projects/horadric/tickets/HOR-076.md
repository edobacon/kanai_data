# Prevenir drift de Gate decision tras done-task sobre S{N}.GATE

## Request

Durante la ejecucion de BLY-043 (proyecto bayley) emergió un patron de drift sistemico: 3 de 4 sessions cerraron con la **task `S{N}.GATE`** marcada `[x]` en la tabla, **pero** el bloque `**Gate decision:**` con los 4 checkboxes (`continue/iterate/escalate/standby`) quedo con los 4 en `[ ]`. HC viewer parsea `gateDecision.decision` desde ese bloque (no desde la task GATE), inferiendo `in_progress` cuando deberia ver `done`. El dev observa visualmente sessions "en ejecucion" cuando logicamente estan cerradas.

**Causa raiz** (confirmada via investigacion):
1. **El LLM ejecutor uso `dkc-execute-task done-task S{N}.GATE`** que solo marca la task GATE en la tabla — NO inserta el bloque `Gate decision:` canonical. Es el camino incorrecto.
2. **El comando correcto es `dkc-execute-task close-gate <N> --decision <continue|iterate|escalate|standby>`** — documentado en `prompts/steps/request-execute/session-gate.md` (sub-archivo lazy-loaded post HOR-059). El LLM no lo cargo, no lo conocia.
3. **El validator `SessionBlockSchema` tiene `gateDecision: z.optional()`** — permite el shape inconsistente sin error. `dkc-validate Ticket` pasa OK aunque la session esta rota para HC viewer.

**Pedido del dev**: revisar el sistema DKC para que esto no siga pasando. Defensa en profundidad — combinar prevencion en origen + deteccion post-write + docs + auto-hook.

## Summary

**Que se hizo**: defensa-en-profundidad (4 capas) para prevenir drift del bloque `**Gate decision:**` cuando el LLM usa `done-task S{N}.GATE` en vez del comando canonical `close-gate <N> --decision`. Trigger: BLY-043 cerro 3 de 4 sessions con drift (HC viewer renderizo como `in_progress`).

**Capas implementadas**:

| Capa | Implementacion | Archivo |
|------|----------------|---------|
| A — Validator zod refine | `SessionBlockSchema` cross-field refine: si `S{N}.GATE.completed === true` → `gateDecision.decision` REQUIRED. Mensaje pointa a `close-gate` con instruccion explicita | `commands/lib/schemas/session-block.ts:139-159` |
| B — Bash command guard | `dkc-execute-task done-task S{N}.GATE` rechaza con exit 1 + mensaje educativo que sugiere `close-gate` | `commands/dkc-execute-task` (funcion `cmd_done_task`) |
| C — Docs en step root | Warning callout en `prompts/steps/request-execute.md` entre tabla GATES y indice de fases | `prompts/steps/request-execute.md:52-58` |
| D — A-hook opt-in | Snippet copy-pasteable `settings.local.json` PostToolUse Edit→validate SessionBlock. Opt-in (no se instala por default) | `docs/hooks-example.md` |

**Tests**: 4 TCs HOR-076 (TC-1: drift rejected, TC-2: valid closed, TC-3: no GATE task ok, TC-4: GATE [~] ok) — todos pasan en self-test `npx tsx commands/lib/schemas/session-block.ts`.

**Audit retroactivo (S2.T1)**: sweep `dkc-validate SessionBlock` strict sobre todos los tickets cerrados → 5 tickets con drift latente (8 sessions): `HOR-075` (S1/S2/S3), `PEH-012` (S0), `up1/ticket-020` (S11), `up1/ticket-029` (S1/S2), `up1/ticket-030` (S3). Documentado en Backlog B1 — NO migracion retroactiva (out of scope per spec).

**Decisions clave**:

- DEC-LOCAL-01: refine cross-field en zod (vs migration de tickets historicos) — fix preventivo de O(0) costo de mantenimiento vs migration que requiere editorial humana por caso
- DEC-LOCAL-02: comando bash exit 1 con mensaje educativo (vs silent fallback a close-gate) — preserva claridad sobre que el usuario uso el path incorrecto
- DEC-LOCAL-03: a-hook como opt-in en `docs/hooks-example.md` (vs always-on en settings.json del repo) — no romper flujos legacy

**Trade-offs aceptados**:

- Tickets cerrados pre-fix con drift latente quedan invisibles hasta que se vuelvan a editar (limitacion de capa A) — mitigado parcialmente por audit retroactivo del Backlog
- La a-hook D depende de que el dev la instale manualmente — solo activa para devs paranoicos / entornos sin supervisor

**Capas A+B+C siempre activas para flujos nuevos. Capa D opt-in para safety net adicional.**
