# Output schemas tipados (Pydantic-style validated output, inspirado CrewAI structured output)

## Request

Patron CrewAI: `Task(output_pydantic=MyModel)` fuerza al agent a producir output validado contra schema. Reduce bugs por output mal formado (claves faltantes, types incorrectos, etc.).

**Estado DKC actual**: records en markdown con frontmatter YAML. Parseable pero **no fuertemente tipado** — el LLM puede escribir labels custom, columnas mal nombradas, types inconsistentes. HOR-022 tuvo **5 bug fixes mid-gate** ATRIBUIBLES a falta de validacion:
1. Cross-spec join Caso 2 (parser no maneja formato real)
2. Regex extractSkipReason sin anchor (matches dentro de texto)
3. Label `Tasks (copiadas...)` no canonical → duplicacion
4. Label `Gate decision (...)` con sufijos → no parsea
5. Shape canonico spec → 13 specs migrados retroactivamente

Todos atrapables con validation upfront.

**Propuesta**: capa **intermedia JSON→markdown**:

- El LLM produce JSON validado contra schema (Pydantic-like en TypeScript zod o equivalente)
- Tool DKC genera markdown desde JSON via template fijo
- Markdown sigue siendo human-friendly; JSON es el contrato

Ejemplos:

**Spec task** schema:
```ts
const SpecTaskSchema = z.object({
  id: z.string().regex(/^S\d+\.(T\d+|GATE)$/),
  task: z.string().min(1),
  source_ref: z.string().or(z.literal('—')),
  agent: z.enum(['researcher', 'architect', 'developer', 'reviewer', 'scribe']),
  depends_on: z.string(),
  files: z.string(),
  validation: z.string(),
  rollback: z.string(),
  rules: z.string(),
  status: z.enum(['pending', 'in_progress', 'done', 'blocked']),
  session: z.number().int().positive(),
})
```

**Session block** schema:
```ts
const SessionBlockSchema = z.object({
  number: z.number().int().nonnegative(),
  date: z.string().regex(/^\d{4}-\d{2}-\d{2}/),
  objective: z.string().min(1),
  type: z.enum(['auto', 'strong']),  // ⚑ fuerte → strong
  tier: z.enum(['T0', 'T1', 'T2', 'T3']),
  tasksCompleted: z.array(TaskCheckboxSchema),
  qualityReview: QualityReviewSchema.optional(),
  gateDecision: z.object({
    decision: z.enum(['continue', 'iterate', 'escalate', 'standby']),
    approvedBy: z.enum(['dev', 'autopilot']),
  }).optional(),
})
```

**Alcance**:

- Empezar con 2 entidades criticas: SpecTask, SessionBlock (los que mas bugs generan)
- Schema en `shared/schemas/` (TypeScript zod o JSON Schema)
- Tool `dkc-validate {record}` que valida cualquier record contra su schema
- `prompts/steps/*.md`: al producir record, validar contra schema antes de escribir markdown
- HC viewer puede usar schemas para hint visual (ej. inputs validables si HC adquiere edicion)

**Fuera de alcance**:

- NO reemplazar markdown como fuente de verdad — schemas validan, markdown persiste
- NO validar todos los records — solo los que mas bugs generan (SpecTask, SessionBlock primero; otros follow-up)
- NO requerir Python/Pydantic — usar zod (TypeScript) por compatibilidad con horadric-cube

**Repos tocados**:

- `horadric-cube` (`shared/schemas/`, opcional validacion en parser server)
- `deckard` (prompts + tool `commands/dkc-validate`)

### Learns promovidos

**L1 — Validate-after-markdown supera Validate-before (JSON intermedio)**

Decision tecnica: validar markdown post-escritura es mas robusto que JSON intermedio. Markdown sigue siendo source of truth. Los steps NO cambian como escriben. Sin friction en adopcion. **Candidata a regla**: "schemas DKC validan output post-escritura. NO se requiere JSON intermedio en el flujo de escritura". No promovido en este ticket — emerge si patron se confirma.

**L2 — Tolerancia con warnings es mejor que strict universal**

Parser captura formatos canonicos Y no canonicos (`**Tasks**:` y `**Tasks completadas**:`), pero emite warning para el no canonical. Esto permite:
- Tickets pre-HOR-026 NO fallan (graceful)
- Bugs retroactivos se detectan (proof of value via HOR-029)
- Nuevos tickets pueden usar `--strict` para bloquear

Trade-off vs strict universal: bug detection con flexibilidad de adopcion gradual.

**L3 — Dogfood automatico = signal inmediato de drift**

HOR-026 termina cada session con `dkc-validate` sobre su propio markdown. Si drift emerge, signal inmediato en la session, no post-mortem. Patron extendible: cualquier ticket de foundation (HOR-023, HOR-026, HOR-031) deberia hacer dogfood en cada session. **Candidata a antipatron documentado**: "no marcar S{N}.GATE continue sin haber ejecutado el tool de validacion sobre el propio ticket+spec".

**L4 — JavaScript regex `$` + flag `m` + lookahead = bug latente**

Combinacion peligrosa: `$` con `m` matchea fin de linea, y lookahead lazy puede capturar cero caracteres si hay `$` cercano. **Lesson universal aplicable a parsers**: usar split-based approach o `\Z`/`(?![\s\S])` para fin de string explicito. Aplicable a futuros parsers DKC y consumers (HC viewer).
