# Implementar Solucion C — Validator post-step para post-conditions (~30% de las directivas, ~27 estimadas)

## Request

**Derivado de HOR-050** (closed 2026-05-16, spec en draft). Implementa la **Solucion C** del SPEC-workflow-directive-enforcement-50.

**Problema que resuelve**:

Las directivas tipo `**BLOQUEANTE**: verificar que las llamadas MCP se ejecutaron antes de pasar a la siguiente task` o `MUST: todas las tasks marcadas con [x]` NO son ejecucion programatica directa — requieren **verificacion del estado producido**. Estas representan ~30% de las ~90 directivas (~27 estimadas).

**Solucion C**: extender `commands/lib/validate.ts` con kind `Directive` que verifica post-conditions tras un step. Cada directiva etiquetada `<!-- enforcement: c-validator check: "..." -->` declara la condicion a verificar.

Ventaja sobre Solucion A (hooks): **portable a otros LLM hosts** (no depende de Claude Code `.claude/settings.json`). Reusable con Ollama, Qwen local, etc.

**Plan tentativo (refinable en intake)**:

1. **Etiquetado**: agregar `<!-- enforcement: c-validator check: "<script-id>" -->` antes de cada directiva validable
2. **Validator kind `Directive`** en `commands/lib/validate.ts`: nuevo case que ejecuta los checks por step
3. **Catalogo de checks**: `commands/lib/schemas/directive-checks/*.ts` con scripts predefinidos (ej. `all-tasks-checked.ts`, `gate-decision-marked.ts`, `mcp-calls-logged.ts`)
4. **Integracion con pipeline HOR-042**: hookable via `dkc-write` post-write si flag `validate_on_write` esta activo
5. **Tests**: 5-10 checks pasando con sample real

**Acceptance criteria (NFR spec)**:
- Latency validator: < 500ms por check
- Cobertura: ~27 directivas etiquetadas + checks correspondientes
- Zero falsos positivos en corpus actual (HOR-040..049)

**No es alcance**:
- Solucion A hooks (HOR-051)
- Solucion B protocols (HOR-052)

### D16 — Bug observado in-vivo (S3 dogfooding): transicion checkbox per-task no se respeto

**Descubierto 2026-05-22 al cerrar S3 (L7).** Durante el execute de Session 3, el ticket markdown permanecio con `S3.T1 [~]` + 6 tasks `[ ]` durante todas las 6 tasks + GATE ejecutadas internamente. HC viewer mostro banner amber "Format drift detectado: 0 completadas, 1 in_progress, 6 pending" persistente. Solo al cerrar S3.GATE se escribio el bloque completo con `[x]` en todas. Viole `request-execute.md` Gate D + HOR-056 capa B + HOR-063 L1.

**Implicacion**:

1. **Anti-patron NO detectado** por el catalogo actual de 8 checks. `session-log-inline-per-task` verifica que tasks `[x]` tengan descripcion (post-cierre) pero NO el patron "session activa con N tasks pendientes y 0 transiciones checkbox durante M minutos/edits".
2. **El propio sistema construido para detectar drift fue victima de su propio anti-patron** — meta-bug ironico.

**Propuesta de check follow-up (`session-task-transition-flow`)**:

```typescript
// schemas/directive-checks/session-task-transition-flow.ts
interface Params {
  // Max # de tasks consecutivas pending mientras hay 1 in_progress sin transicionar a [x]
  max_pending_with_one_in_progress: number  // default 3
  // Max # de tasks pending si NO hay ninguna [x] aun
  max_pending_zero_completed: number  // default 2
}
// Lee sessions, encuentra la session activa (ultima sin gate decision marcado),
// cuenta {pending, in_progress, completed}. Si pending >= threshold + completed === 0,
// flag como drift "checkbox transition flow violated".
```

**Sub-task adicional cuando se aborde**: agregar como check 9 del catalogo (opcional, no mandatorio). Costo bajo (1 archivo + ~5 self-tests). Alto valor preventivo — flagged este bug exacto en el momento que ocurre.

### What was learned

- **L1**: `\Z` end-of-string no existe en JS regex; usar split por lineas + findIndex (detectado y corregido en `plan-sessions-present.ts`)
- **L2**: ES modules con tsx rechazan `require()`; usar `import` al top del archivo (detectado y corregido en `parsers/markdown.ts`)
- **L3**: Patron `parse-once-validate-many` (C1) ya no es preocupacion empirica — cada check parsea su propio archivo en ~0.1-0.2ms; el overhead es despreciable vs NFR 500ms
- **L4**: Etiquetado 1-tag-por-bloque-GATE (no 1-tag-por-checkbox individual). Reduce ruido visual + simplifica mantenimiento. Tradeoff: 14 tags vs 42 directivas inventariadas, pero cobertura funcional alta
- **L5**: HOR-056/058/060 tienen drifts retroactivos no detectados previamente (Quality reviews missing, gates sin `[x]`). El validator c-validator hubiera flagged en su momento — validacion empirica del valor del frente C
- **L6**: Patron canonical de kinds en `validate.ts` admite cleanly el kind 18 sin tocar los 17 existentes (shape ValidationResult + dispatch + parseArgs con extraFile posicional, todo aditivo)
- **L7** (meta-bug self-detectado, **el aprendizaje mas importante del ticket**): durante todo S3 ejecute 6 tasks + GATE con `TaskUpdate` interno pero NO actualice el ticket markdown progresivamente — solo en batch al cerrar. HC viewer mostro banner "Format drift detectado" durante toda la session. Ironico porque el ticket que implementa el validator para detectar exactamente este tipo de drift fue victima de su propio anti-patron. Captura el bug + D17 (fix preventivo en protocolo) + D16 (check follow-up opcional). **Root cause**: confundi `TaskUpdate` (tool tracker interno del LLM) con persistencia al ticket markdown — eran 2 escrituras distintas pero las trate como una
