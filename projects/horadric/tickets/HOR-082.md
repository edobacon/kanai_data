# Explorar: alinear output schema del reviewer con las 10 dims DET-23 (dim_results)

## Request

**Origen**: delta no cubierto de HOR-027 (cerrado 2026-05-30 por supersesion de HOR-079+HOR-054). El nucleo de HOR-027 (reviewer aislado, contexto limpio, verdict estructurado, gate como pre-condition) quedo cubierto y superado. Lo unico que NO quedo cubierto es esto:

**El delta**: el output JSON del reviewer (`prompts/agents/reviewer.md`) estructura `spec_compliance + rules_compliance + findings + recommendation`, pero **NO** mapea 1:1 las **10 dimensiones del quality review DET-23** (`code_quality, lint, typing, testing, scalability, maintainability, clarity, a11y, storybook, error_handling`) como campo `dim_results` consumible por maquina.

Hoy las 10 dims viven en el bloque markdown `#### Quality review (DET-23)` del ticket (tabla con `pass | warn | fail | n/a` por dimension). Eso es legible para humano y LLM, pero NO es un objeto estructurado que un gate programatico pueda consumir directamente.


## Que se explora (no se compromete implementacion)

1. **¿Aporta valor el `dim_results` estructurado?** — solo aporta si existe (o se planea) un **consumidor programatico** que lea las dims como JSON: un gate automatico, el HC viewer filtrando tickets por dims en `warn`/`fail` (DET-23 lo menciona como caso de uso: "construir backlog de deuda de calidad"), o un validador `dkc-validate`.
2. **¿Esta el consumidor vivo?** — verificar estado de HOR-023 (gates programaticos, sinergia que HOR-027 citaba) y si el HC viewer ya parsea el bloque Quality review markdown. Si el viewer ya parsea el markdown bien, el JSON podria ser redundante.
3. **¿Redundancia vs el bloque markdown?** — el bloque `#### Quality review (DET-23)` ya captura las 10 dims. Duplicarlas en el output JSON del reviewer crea dos fuentes de verdad. Evaluar: ¿el JSON reemplaza al markdown, lo complementa, o se genera el markdown DESDE el JSON?
4. **Costo vs beneficio** — el cambio es chico (extender el Output schema en `reviewer.md` + ajustar el consumo en `request-execute`/`session-gate`). Pero si no hay consumidor programatico, es complejidad sin retorno.

## Verdict del explore (2026-06-13)

**NO implementar `dim_results` ahora — H1 refutada.** No existe consumidor programatico de las 10 dims como JSON en ninguna de las 3 capas verificadas (gate, HC viewer, validador). Agregar el campo al output del reviewer duplicaria la tabla markdown (fuente de verdad DKC) sin lector → deuda pura + riesgo de drift (H3 confirmada). El caso de uso humano+LLM ya esta 100% cubierto por el bloque markdown (H2 confirmada).

**El prerequisito real es el consumidor, no el schema.** El caso de uso "filtrar tickets por dims en warn/fail para backlog de deuda de calidad" esta declarado en DET-23 (`deterministic-rules.md:650`) pero **no implementado** en el HC viewer. 2. **Entonces** — `dim_results` JSON en el output del reviewer se vuelve el habilitador natural (o el viewer parsea la tabla markdown directo, evitando el JSON; decision de diseno de ESE ticket, no de este).

**Reactivacion**: este ticket se reabre (o se crea uno nuevo de `improvement` sobre el HC viewer) cuando se priorice el filtrado por dims. Mientras tanto, `declined` — won't_do con razon, segun la regla de decision del propio scaffold ("si H1 resulta falsa, cerrar como won't_do con razon").
