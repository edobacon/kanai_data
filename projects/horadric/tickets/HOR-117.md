# Telemetria de gates — medir gasto (proxy) + latencia + estructura por gate

## Request

Q1 del analisis de "flujo optimo": instrumentar el flujo para MEDIR el gasto por gate y volver el proceso observable/tuneable (prerequisito de la calibracion Q2). Como Claude Code NO expone el conteo de tokens por sub-agente al layer markdown de DKC, el mecanismo captura: (a) conteos ESTRUCTURALES reales (tier, work_type, review_mode single-pass/dual-judge/dual-judge-tiered, #jueces, #adjudicador, #iteraciones fix→re-judge, outcome); (b) LATENCIA real (delta de timestamps del decisions_log de la session); (c) tokens ESTIMADOS via heuristica `chars/3.7` (la que ya usa dkc-measure-context-base) sobre el diff del gate. Decision del dev: "Mecanismo + proxies" — durable, self-contained, honesto sobre el limite (tokens = estimacion; latencia y estructura = reales). Reusa el patron de reporte agregador de dkc-sp-calibration + la heuristica de dkc-measure-context-base. Sin depender de fuente externa de tokens.

### Context found

- **dkc-measure-context-base** (`commands/`) — bash, mide contexto ESTATICO (tamaño de prompts) con `calc_tokens()` chars×10/37 + `--json`. Reusar la heuristica y el patron de flags. NO mide gasto dinamico por gate (gap que cubre este ticket).
- **dkc-sp-calibration** (`commands/*.md`) — reporte agregador prompt-driven desde el frontmatter de tickets. Patron de "scan tickets → tabla + breakdown". Telemetria sigue el mismo espiritu pero como comando bash determinista (los numeros importan).
- **decisions_log** — fuente de la latencia (timestamps ISO por entry, delta open-session→gate-close) y del review_mode (presencia del step `dual-judge` + su choice; `agent-invocation` cuenta jueces).
- **DET-35 / HOR-116** — review_mode = dual-judge-tiered cuando los jueces corren balanced; el bloque Quality review ya registra el tier en prosa (HOR-116). La telemetria estructura eso.
- **DET-32** (necesidad/reuso) — reusa heuristica + decisions_log + patron sp-calibration. Lo unico net-new: el comando `dkc-telemetry` + el bloque de captura estructurado. Veredicto: build (comando) + reduce (captura: estructura lo que ya se registra en prosa).
- **RULE-workflow-catalog-executor-pattern-005** — patron de comando ejecutor; el reporte lo sigue.

**Warnings**:
- Tokens = ESTIMACION (chars/3.7), NO medidos. El reporte DEBE etiquetarlos como estimacion para no inducir falsa precision. Latencia y conteos estructurales SI son reales.
- Latencia via timestamps del decisions_log es un PROXY del wall-clock del gate (incluye pausas humanas entre entries). Etiquetar como "span del gate", no "tiempo de computo".
- Parsing fragil: el comando parsea markdown. Acotar a campos `key: value` en un bloque delimitado (no prosa libre) + smoke self-test contra los 3 gates backfilled.
- Backfill de tickets cerrados (HOR-114/115/116): es ADITIVO (bloque de observabilidad), no altera outcome ni reabre. Aceptable.

**Gaps**:
- Formato del bloque de captura. Resuelto: bloque fenced ```dkc:gate-telemetry``` con lineas `key: value` en el cierre del gate (parseable por awk, robusto).
- diff_chars de gates pasados. Resuelto: estimar del diff de los commits del ticket (`git show`/numstat); para gates nuevos, del diff real al cierre.
