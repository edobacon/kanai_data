# Context budget reduction — manifest DET + compresion sessions + lazy-load steps

## Request

**Direccion estrategica del dev (2026-05-17)**: el context base de DKC consume ~85-100K tokens por turno (medido). Aunque Claude opus 4.7 (1M context) absorbe sin problema, el costo por ticket es $4-8 y la velocidad de prefill es alta. Para LLMs locales modernos (256K efectivo claim, ~64-128K efectivo real validable), el budget queda apretado: 33-66% consumido solo en cargar el sistema, sin margen para razonamiento sostenido en tickets grandes (HOR-022 = 121 KB, 8 sessions).

**Objetivo**: bajar el context base a **~35-45K tokens** (target ~50% reduccion) mediante 3 mejoras integradas que comparten infraestructura comun (parsers de markdown, MCP tools, telemetria):

1. **DKC-lite manifest** — derivar `prompts/det-manifest.md` autogenerado desde `deterministic-rules.md`. Compacta cada DET a 1 fila (numero + titulo + rule + cuando aplica). Lookup completo de la DET on-demand cuando el LLM lo necesita.
2. **Compresion semantica de sessions** — scribe genera summary destilado (~200 tokens) al cerrar cada session con gate `continue`. Original queda en `tickets/{id}.sessions/S{N}.md`. HC renderiza summary inline + click-to-expand al original.
3. **Lazy-loading de steps** — split de los 5 steps grandes (`request-execute.md`, `request-close.md`, `request-intake.md`, `_design-shared.md`, `intake-explore.md`) en archivos por fase. LLM carga solo la fase activa.

**Por que las 3 en un ticket**:

- Comparten infraestructura: parser de manifest, scribe extendido, MCP tool de step-phase resolution
- Beneficio compuesto: la suma reduce ~50K tokens; cada una por separado solo 10-25K
- Testing integrado: validar empirico que las 3 juntas NO rompen DET-16 (propagacion) ni DET-13 (cierre con evidencia)
- Decision points conjuntos: heuristica de "cuando expandir DET completa" interactua con "cuando cargar fase siguiente del step"

**Beneficio operativo (medible)**:

- **Claude Code**: $4-8 → $2-4 por ticket (~50% reduccion costo)
- **Local 128K efectivo**: pasa de "presion alta" a "comodo" (~33% del budget vs 75%)
- **Local 256K efectivo**: pasa de "comodo" a "abundante" (margen para tickets >10 sessions)
- **Velocidad de turno**: reduccion proporcional al tamano del prefill (40-50% en local lento)
- **Calidad de retrieval activo del LLM**: mejora medible — menos ruido, mas accuracy en encontrar la rule correcta (validable con casos representativos)

**No es alcance**:

- Embeddings KB retrieval → HOR-031 ya scaffolded, ejecuta en paralelo o despues
- Validation gate con modelo pequeno → roadmap nominal HOR-033, no aqui
- Multi-modelo routing → roadmap nominal HOR-035, no aqui
- Cambio de host (opencode) → HOR-017 intake-explore, no aqui
- Telemetria de drift global → out of scope, abre como ticket separado si emerge

### What was discovered

- **Defensive split design pattern**: preservar el monolitico como INDEX/REDIRECT de ~5K (en lugar de borrarlo) mantiene 100% de refs operativas funcionando — refs externas siguen apuntando al monolitico que ahora redirige a sub-archivos. Patron reusable para futuros splits.
- **Refs `:LXX` brittle**: numeros de linea hardcoded en refs entre archivos se invalidan al splitear/refactorizar. Solucion: refs conceptuales (por nombre de seccion o fase) en lugar de por linea.
- **HOR-058 SessionDetailModal reusable**: pattern Vue3 disponible desde 2026-05-17 — S3.T6 lo reuso sin re-implementar, ahorrando ~2h.
- **Validator `dkc-validate-step-references` encontro bugs pre-existentes**: descubrio `rule.ts:68` apuntaba a path inexistente — evidencia de que el detector cumple proposito mas alla del scope inmediato del ticket.
- **Falsos positivos del grep regex**: prose narrativa explicando archivos hipoteticos descartados + ejemplos dentro de code fences generan FPs. Mitigaciones: skip automatico de code blocks + suppression inline `dkc-vsr-skip`.
