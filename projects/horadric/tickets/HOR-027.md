# Handoff explicit developer→reviewer (inspirado CrewAI agent delegation)

## Request

Patron CrewAI `Agent(allow_delegation=True)`: un agent puede invocar otro explicit — `delegate_to('reviewer', 'check this change')`. CrewAI maneja el handoff y returns.

**Estado DKC actual**: DET-9 declara contrato de handoffs entre agents (objetivo + alcance + evidencia + archivos + criterio de terminado) — pero **descriptivo**, no invocacion formal. El LLM identifica cuando emerge handoff. En gates ⚑ fuerte, el handoff developer→reviewer ocurre **implicito** (el mismo LLM cambia "modo").

**Problema observado**: en HOR-022 algunos quality reviews quedaron poco rigurosos porque el LLM cambia entre developer y reviewer sin "salida" explicita — sigue con el mismo contexto. Riesgo: self-review menos critica que peer-review.

**Propuesta**:

- Formalizar `handoff` como invocacion explicit en steps:
  - Developer al cerrar task: `handoff_to_reviewer(task_id, validation_context, files_changed)`
  - Reviewer recibe contexto estructurado (no narrativo) y retorna verdict
  - Gate sync usa el verdict del reviewer como pre-condition (no auto-evaluacion del developer)
- Verdict del reviewer estructurado:
  ```yaml
  recommendation: approve | iterate | escalate  # DET-14
  dim_results:  # DET-23 dim 1-10
    code_quality: pass | warn | fail | n/a
    testing: pass | warn | fail | n/a
    # ...
  issues_found: []  # bugs detectados
  recommendations: []  # mejoras opcionales
  ```
- Implementacion: en HC con un solo LLM, "handoff" significa **switch de role + clear de context** — el mismo LLM se reposiciona como reviewer leyendo solo el handoff payload (no el contexto previo del developer)

**Beneficio observable**:
- Reduce ambiguedad "¿cuando entra el reviewer?"
- Reviewer evalua con context limitado a lo necesario (no sesgado por la implementacion previa)
- Output estructurado del reviewer es consumible por gates programaticos (sinergia con HOR-023)

**Alcance**:

- `prompts/agents/reviewer.md`: input schema definido (handoff payload)
- `prompts/steps/request-execute.md`: paso "Validar (C)" formaliza la invocacion del handoff
- `prompts/agents/developer.md`: output schema del developer ENTRY al handoff
- Documentar en `prompts/_style.md` Principio 9 (nuevo)

**Fuera de alcance**:

- NO requerir LLM separado para reviewer — el mismo LLM cambia de role con context reset
- NO formalizar todos los handoffs DKC (researcher→architect, scribe→scribe, etc.) — empezar con developer→reviewer que es el mas frecuente
- NO bloquear si handoff payload incompleto — degradacion graceful (fallback a auto-eval)

**Repos tocados**:

- `deckard` (prompts/agents + prompts/steps + _style.md)

### Delta NO cubierto (derivado a HOR-082)

El output JSON del reviewer NO mapea 1:1 las 10 dimensiones DET-23 (`dim_results: code_quality, testing, ...`). Hoy las 10 dims viven en el bloque "Quality review" del ticket markdown (tabla), no en el output programatico del reviewer. Es delta **menor/cosmetico** — solo relevante si un gate programatico necesita consumir las dims como JSON. Se deriva a **HOR-082** (exploratorio) para evaluar si aporta valor antes de implementar.
