# Fix enforcement de gates DKC (DET-27 + DET-25 + DET-21-0b) via convencion T2 evidencia observable + modal HC

## Request

El dev reporta dos sintomas iniciales conectados al tracking de sesiones del ciclo execute:

1. **Workflow DKC — commits**: por sesion no se estan haciendo los commits automaticos (DET-27) y no se estan registrando los detalles en el bloque de session del ticket. El LLM se esta saltando el paso de auto-commit post-session pese a que DET-27 lo define como bloqueante.
2. **HC viewer — modal**: el detalle de session se visualiza hoy como expandable inline ([SectionSessions.vue:305-378](../../../horadric-cube/src/components/ticket-sections/SectionSessions.vue)) y resulta incomodo. El dev quiere que el detalle se levante en un modal sobre la lista.

Durante `intake-explore` (2026-05-17), emergio un **tercer sintoma** que valida la hipotesis de un patron sistemico: el LLM se salto el paso 0b de `teach-intake.md` (pregunta explicita "¿generar teach-intake?") asumiendo default por la respuesta previa ambigua del dev ("avanza"). Esto, junto al sintoma DET-27, confirma un patron mas amplio:

> **El gate de salida de un step verifica el RESULTADO (frontmatter, fila en tabla), pero no verifica que el PASO INTERNO se haya ejecutado.** El LLM puede satisfacer el resultado sin haber ejecutado el paso real — asumiendo defaults, marcando "pendiente" como satisfactor verbal, o difiriendo al close donde el contexto se pierde.

El dev decidio **ampliar el scope** de HOR-058 (opcion A en intake) para atacar los **3 patrones simultaneos** con una convencion unificada:

- **DET-27** (commits post-session): cerrar escape verbal "pendiente"; gate verifica hash real en `**Commit DET-27**:` linea
- **DET-25** (test cases registrados): cerrar deferred-to-close; gate verifica columna `Actual` poblada por session
- **DET-21 paso 0b** (pregunta skip teach-intake): cerrar default-silencioso; gate verifica entry observable en ticket markdown
- **Convencion T2 generalizada**: validator `dkc-validate StepDecisions` + campo `decisions_log` en frontmatter del ticket + sub-seccion `## Decisiones del workflow` con timestamp + step + choice + reason. Cada step interactivo escribe entry; gate de salida del step exige entry con campos obligatorios

Plus: **modal HC** que reemplace el expandable inline de detalle de session.

> Ambos componentes (workflow + UI) viven en la misma cadena "tracking observable de sesiones": sin la convencion T2 los gates siguen siendo evadibles; sin modal, leer lo que el T2 genera cuesta.

## Triage

El sintoma del workflow (commits no se hacen + session no se registra) es el problema dominante: erosiona la fuente de verdad recuperable y rompe la trazabilidad bidireccional commit ↔ session ↔ ticket. El sintoma UX (expandable incomodo) es el efecto observable cuando si hay datos — vale la pena resolver en paralelo porque el modal facilita revisar lo que produzca el fix de enforcement.

DET-27 ya define el comportamiento canonico (commits granulares por tipo + gate del scribe verificando working tree limpio). El fix NO redefine la regla — refuerza el enforcement runtime para que el LLM no la salte.

### Active questions (gaps post-loop)

- **AQ1**: ¿La granularidad de commits DET-27 es "1+ commits por session, cada uno cubriendo solo esa session" (estricto) o "agrupacion permitida si las sessions estan relacionadas y se documenta razon" (flexible)? Resolver en design-fix S3.
- **AQ2**: ¿El a-hook que dispara `dkc-verify-gate G1` debe invocarse en (a) cada Edit del ticket, (b) solo cuando el Edit toca `**Gate decision:**` con valor `continue|iterate`, o (c) cuando `dkc_set_ticket_status` cambia de status? Resolver en design-fix.
- **AQ3**: H6 inferred — tension granularidad-DKC vs atomicidad-logica-codigo (commits). Preferencia explicita del dev (estricto vs flexible) facilita design-fix.
- **AQ4 (nueva)**: ¿La convencion T2 (`decisions_log` en frontmatter + sub-seccion `## Decisiones del workflow` en ticket markdown) debe ser **append-only inmutable** (cada decision queda registrada para siempre, util para audit) o **mutable con history** (el dev puede corregir, pero se guarda log de cambios)? Append-only es mas simple de validar; mutable es mas amigable si el dev se equivoca al elegir. Resolver en design-fix S3.
- **AQ5 (nueva)**: ¿El validator `dkc-validate StepDecisions` debe (a) verificar **cobertura completa** (todo step pasado en workflow_state tiene entry correspondiente en decisions_log), o (b) verificar solo **steps que tienen pregunta interactiva** (lista whitelisteada: `teach-intake-0b`, `commit-det-27`, `test-case-registration`, etc.)? (a) es mas estricto pero genera friction en steps lineales; (b) es mas focalizado pero requiere mantener whitelist. Resolver en design-fix S3.
- **AQ6 (nueva)**: ¿La sub-seccion `## Decisiones del workflow` del ticket markdown debe ir antes o despues de `## Sessions`? Antes = visible al abrir ticket en HC (top); despues = el flujo cronologico es intake → sessions → decisiones. Resolver en design-draft S2 (o early en design-fix si no afecta visual).

### Reproduction steps

**Para el sintoma de workflow (commits + registro)**:

1. **Precondicion**: ticket con `work_type ∈ {implement, fix, improvement, refactor}` en `status: in_progress`, dentro de execute, session activa con tasks que tocan codigo.
2. **Accion**: ejecutar `S{N}.GATE` con decision `continue` o `iterate` desde el LLM en autonomia (sin intervencion humana entre tasks).
3. **Resultado observado**: la session se marca cerrada, pero (a) no se proponen commits granulares por tipo, (b) la tabla `## Commits` del ticket markdown queda sin la fila correspondiente, (c) `git status` muestra archivos modificados sin commit.
4. **Resultado esperado**: scribe propone commits agrupados por tipo, dev aprueba, se ejecutan, tabla `## Commits` se actualiza, working tree queda limpio antes de S{N+1}.

**Para el sintoma UX (expandable)**:

1. **Precondicion**: ticket cualquiera con 3+ sessions en HC viewer (`http://localhost:3016/projects/horadric/tickets/HOR-057`).
2. **Accion**: intentar revisar detalle de Session 2 + Session 4 simultaneamente, luego volver al listado limpio.
3. **Resultado observado**: necesita expandir ambas (contenido inline ocupa pantalla), scroll para comparar, click por session para colapsar al volver.
4. **Resultado esperado**: click en session → modal con detalle completo; cerrar modal → vuelta al listado intacto. Comparar sessions → cambiar de session en el modal (next/prev opcional) o cerrar + abrir otra.
