# Parser de frontmatter de dkc-validate ignora comentarios inline YAML

## Request

El parser de frontmatter de `dkc-validate` (`commands/lib/parsers/markdown.ts`) NO soporta
comentarios inline `#` en lineas del frontmatter YAML. `parseFrontmatterWithDuplicates`
(lineas 635/647) valida `rawValue.trim().endsWith(']'|'}')`, asi que `execute_scope: []   # HOR-079`
o `teachings: { ... }   # DET-21` se truncan y caen al branch string → Zod rechaza con
"Expected array/object, received string". `parseYamlScalar` (500) tampoco quita el comentario,
asi que sub-keys de objetos multilinea (`llm_factor_calculated: 6   # ceil(...)`) se guardan como
string en vez de numero. El template canonico `templates/records/ticket.md` trae comentarios inline
en ~10 lineas, asi que cualquier ticket que copie el shape literalmente falla validacion.

Fix (opcion A, decidido con el dev): helper que strip-ea el comentario inline ` #...` a fin de
linea (fuera de comillas, regla YAML "espacio antes de #" para no romper URLs/hex), aplicado en
`parseYamlScalar` + el loop de `parseFrontmatter` y `parseFrontmatterWithDuplicates`. Zero-dep,
retroactivo, mantiene deteccion de duplicados D12, alinea con YAML estandar.

## Discoveries / decisions

- D1: el sintoma se descubrio durante backfill de frontmatter de tickets de pehuen (2026-05-31). PEH-002 (cerrado) fallaba validacion por comentario inline preexistente en `teachings`.
- D2: impacto real medido via strip-and-revalidate sobre los 209 tickets de todos los proyectos: **6 tickets fallan HOY por esto** y pasarian a VALID sin editarlos — `HOR-079, HOR-081, HOR-083, HOR-084, HOR-086, PEH-002`. Los otros ~85 que fallan validacion lo hacen por shape legacy no relacionado (fuera de alcance).
- D3: el escaneo estructural inicial subcontaba (solo truncacion top-level). El validador real revelo que comentarios en sub-keys de objetos multilinea (`story_points.llm_factor_calculated: 6 # ceil(...)`) tambien corrompen (string en vez de numero).
- M1 (micro-decision): el helper NO hace `.trim()` — solo corta el comentario. Asi se preserva la deteccion de multilinea (`rawValue.trim() === ''`) que dependen del whitespace residual; los `.trim()` existentes del caller siguen aplicando.

## Summary

**Que se hizo**:

- T1 + `e2c70dc`: helper `stripInlineComment` en [markdown.ts](../../../commands/lib/parsers/markdown.ts) aplicado en los 3 puntos de parsing de frontmatter. Antes: `execute_scope: []   # nota` o `teachings: { ... }   # DET-21` se truncaban al branch string → Zod rechazaba "Expected array/object, received string"; sub-keys numericas con comentario (`llm_factor_calculated: 6 # ...`) quedaban string. Despues: el comentario inline se corta respetando semantica YAML (comillas + `#` con whitespace previo), valores parsean a su tipo correcto.

**Como se valido**: los 6 tickets que fallaban por esto (HOR-079/081/083/084/086, PEH-002) pasan a `valid:true` sin editarlos (fix retroactivo). Sweep completo de 210 tickets: invalid 91→85 (delta exacto −6, cero regresion sobre los previamente validos). D12 (deteccion de duplicate keys) sigue disparando. 8 edge cases verificados (URLs con `#`, hex `#fff`, `#` dentro de comillas, numeros, valor vacio + solo-comentario, `a#b` sin espacio). `npm run test:schemas` 19/19 + 6/6.

**Que NO se hizo** (out-of-scope):

- El template canonico `templates/records/ticket.md` y `ticket-tactic.md` conservan sus comentarios inline (ahora parsean bien gracias al fix — no requieren edicion). Limpiarlos a bloque seria cosmetico.
- Caso raro flow-object-en-array-item con comentario (`- { id: x } # nota`) sigue cayendo a string: pre-existente, no reportado, fuera de alcance del fix de causa raiz.
- Test unitario permanente del helper: el repo no tiene harness de tests en `parsers/` (los self-tests viven en `schemas/*.ts`). La regresion empirica (sweep + edge cases + D12) cubre DET-13. Candidato a follow-up si se quiere durabilidad.
