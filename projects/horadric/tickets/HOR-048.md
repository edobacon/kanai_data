# Path resolver / repository layer — abstraer filesystem detras de API tipada

## Request

**Origen**: analisis 2026-05-16 sobre debilidades arquitecturales de DKC pensando en LLM-only futuro. Gap identificado: **acoplamiento paths/semantica**.

**Que es el problema hoy** (DKC v1):

Las convenciones de paths viven **hardcoded como strings** en multiples capas:

1. En `deckard/prompts/steps/*.md` — cada step menciona paths textuales como `tickets/{TICKET-id}.draft/`, `tickets/{TICKET-id}.teach/teach-intake.md`, `specs/SPEC-*.md`, `bugs/{module}/`, `rules/{module}/`
2. En `deckard/templates/records/*.md` — tambien hardcoded
3. En `deckard/server/` (dkc-mcp) y `commands/` — paths construidos manualmente con `path.join` en JS/TS
4. En `horadric-cube/server/deckard/` — parsers que asumen layout especifico
5. En `deckard/commands/dkc-validate`, `dkc-verify-gate`, etc. — cada uno reimplementa resolucion de paths

**Sintoma**: cambiar **una convencion** (ej. renombrar `.teach/` a `.learnings/`) implica:

- Grep en `deckard/prompts/steps/*` (≥10 archivos)
- Grep en `deckard/templates/records/*` (≥5 archivos)
- Edits en `deckard/server/src/*.ts` (varios)
- Edits en `deckard/commands/*` (~10 scripts)
- Edits en `horadric-cube/server/deckard/*.ts` (parsers)
- Y aun asi, no hay garantia de cobertura: si se queda un string sin actualizar, el sistema sigue "funcionando" pero genera artifacts en lugar inconsistente

**Casos concretos:**

- DET-19 (external id en commits/branches/PRs) requiere resolucion condicional `external ?? ticket_id`. Hoy se reimplementa en cada lugar que la necesita
- DET-20 introdujo `### Plan de sessions` como sub-seccion del ticket markdown — varios prompts tuvieron que actualizarse para referenciarla. Sin abstraccion, cada uno la construye textual
- HOR-040 introdujo `dkc-validate SessionBlock` que reimplementa parsing de sessions del ticket markdown — porque no hay una capa "leer session N del ticket X"
- HOR-013 introdujo `tickets/{id}.teach/teach-intake.md` y `teach-close.md` — paths que ahora viven en docs + multiples steps + HC parsers

**Propuesta** (post-HOR-042, complementaria):

Implementar una **repository layer tipada** que abstraiga el filesystem layout de DKC:

### API conceptual (refinable en design)

```typescript
// Acceso por entidad, no por path
const ticket = await dkc.tickets.get(project, ticketId);
const draft = await dkc.tickets.draft.get(project, ticketId, version);
const teach = await dkc.tickets.teach.get(project, ticketId, 'intake' | 'close');
const screenshots = await dkc.tickets.screenshots.list(project, ticketId);

const spec = await dkc.specs.get(project, specId);
const archivedSpec = await dkc.specs.archived.get(project, specId);

const rules = await dkc.rules.byModule(project, moduleSlug);
const bug = await dkc.bugs.get(project, moduleSlug, bugId);
const decision = await dkc.decisions.get(project, decisionId);

// Resolucion de identificadores externos
const repoId = dkc.tickets.resolveRepoId(ticket); // external ?? ticket_id (DET-19)

// Existence checks tipados
const hasDraft = await dkc.tickets.draft.exists(project, ticketId);
const teachStatus = await dkc.tickets.teach.status(project, ticketId, 'intake');
// → 'pending' | 'done' | 'skipped' | 'missing'
```

### Beneficios concretos

- **Single source of truth para paths**: renombrar `.teach/` → solo 1 lugar
- **Validacion de existence**: hoy cada consumer hace `fs.existsSync(path.join(...))`. Con repo layer: `await dkc.tickets.teach.exists(...)` — tipado, testeable, mockable
- **DET-19 implementado una vez**: `resolveRepoId(ticket)` aplica la regla globalmente
- **Tests unitarios**: la capa es testeable sin tocar filesystem (mockear fs)
- **Migracion segura**: si la convencion cambia, los tests rompen ANTES de produccion
- **Documentacion ejecutable**: la API es el contrato, no la prosa de los prompts

### Que NO es

- **No reemplaza markdown como SoT** (eso es HOR-046)
- **No es una DB**: sigue siendo filesystem. Solo abstrae la capa de acceso
- **No cambia los paths actuales**: backwards compat completo en este ticket. Renombres futuros se vuelven baratos, pero no se hacen aqui

### Quien consume

- `deckard/commands/*` — scripts pasan a usar la layer
- `deckard/server/src/` (dkc-mcp tools) — internamente usan la layer
- `horadric-cube/server/deckard/` — parsers pueden usar la layer para localizar archivos (sin cambiar la logica de parsing markdown)
- Prompts (`prompts/steps/*.md`) — siguen mencionando paths textuales en su prosa (lectura humana), pero el "como" lo ejecuta el LLM via la layer

**Coordinacion con HOR-042**:

HOR-042 introduce el pipeline write→validate→commit. La layer de paths es **complementaria**: el pipeline usa la layer para resolver donde escribir; la layer no implementa pipeline. Pueden desarrollarse en paralelo o serializadamente.

**Beneficio para LLM-only futuro**:

- Modelos locales generan menos errores tipograficos en paths cuando la API es tipada
- Tooling externo (fine-tuning data extractor, RAG indexer) consume la layer en vez de re-escanear filesystem
- Skill composer (CrewAI-inspired) declara dependencias en terminos de entidades, no paths

**No es alcance**:

- Renombrar convenciones existentes (`.draft/`, `.teach/`, etc.) — se mantienen
- Cambiar shape de markdown — solo abstraer acceso
- Reemplazar SQLite — independiente

#### Evidencia de validacion (intake-explore — 2026-06-13)

- **H1 ✗→✓**: `deckard/server/src/deckard_cain/` es **Python**, no TS (`pyproject.toml`, `.venv`, `core/*.py`). La premisa "modulo TS en server/src" es inviable. **Correccion**: la layer TS vive en `commands/lib/repo/` — donde YA existe el toolchain TS (tsx + Node 22 + zod, `commands/lib/parsers/markdown.ts`, `commands/lib/schemas/*.ts`, `vitest`). Ese es el hogar natural. Evidencia: `commands/lib/package.json`, `commands/dkc-validate:9` ("invoca tsx + Node 22 + zod"). Los strings de paths duplicados estan concentrados en `commands/lib/compress-session.ts:71,126`, `commands/lib/validate.ts:1093-1105` (dispatch por string-includes sobre `/rules/`, `/decisions/`, `/bugs/`, `/specs/`, `/tickets/`).
- **H2 ✓**: la layer envuelve la construccion de paths existente; no renombra convenciones (fuera de alcance explicito). Aditiva por diseno → ningun consumer rompe al introducirla.
- **H3 ✗→✓**: `horadric-cube` es **repo git independiente** (`package.json name: horadric-cube`, NO workspace de deckard). Import cross-repo en build-time es fragil (DECKARD_ROOT es runtime-env, no build-path) y coincide con anti-patron documentado del dev (up1: cross-layer/cross-bundle import rompe el bundle; fuente unica via **test de paridad**, no import). **Correccion**: HC ya tiene su semilla de layer (`server/deckard/root.ts`: `getDeckardRoot`/`projectPath`; `server/deckard/paths.ts`: `resolveRecordPath`). HC mantiene su layer propia; se alinea la **forma de la API** via test de paridad, no import directo.
- **H4 ✓**: `resolveRepoId(ticket) = external ?? ticket_id` es funcion pura, trivialmente centralizable en la layer TS. Python necesitaria su propia copia (ver boundary abajo).
- **H5 ✓**: consecuencia directa de H2 — codigo viejo con string-paths sigue funcionando hasta migrarse uno a uno.
- **H6 ✓**: `commands/lib` ya corre vitest (`get-section.test.ts`, `schemas/session-checkboxes.test.ts`). Layer thin + pure-ish → fs-mock cubre ≥80% sin filesystem real.

#### Decisiones criticas (resueltas en intake — super autopilot, decide+documenta)

- **Boundary Python/TS (MAYOR)**: existen **3 implementaciones de path-logic en 2 lenguajes**: (1) Python `server/src/deckard_cain/config.py`+`core/records.py`, (2) TS `commands/lib/*.ts`, (3) TS `horadric-cube/server/deckard/`. Un modulo unico compartido es **imposible** cross-language. **Decision (reversible)**: alcance de HOR-048 = **layer TS en `commands/lib/repo/`** consumida por `commands/lib/*.ts`. El server Python queda **fuera de alcance** (su path-logic ya esta razonablemente centralizada en `config.py`; documentar la duplicacion como backlog `should`, no `must`). HC se alinea por paridad-de-test. Racional: maximiza valor (los commands son el mayor foco de strings duplicados + tienen el toolchain) con minimo blast radius. Alternativa descartada: contrato declarativo (YAML/JSON leido por ambos lenguajes) — mayor complejidad, se difiere a HOR-046 (SoT) si emerge necesidad real.
- **API sync vs async**: los scripts de `commands/lib` corren bajo tsx con top-level await disponible. **Decision**: API async (`fs/promises`) con helpers sync opcionales solo donde un script CLI lo requiera. Reversible.

  - DET-16 (propagacion) — refactors de paths se reducen drasticamente
  - DET-19 (external id) — caso clasico de logica condicional que se centraliza

  - Performance: la layer envolviendo `fs` puede agregar overhead. Mantenerla thin (sin caching agresivo inicialmente)
