# Cobertura completa de contratos DKC — validators de artefactos + de ejecucion enforced + disponibilizados + en uso + auditados (pre-requisito HOR-054)

## Request

**Derivado de**: analisis del estado de guias/contratos DKC realizado tras cierre de HOR-051+052 (2026-05-16). El dev pregunto explicit: *"hay guias? tienen forma de uso? aplica en todo?"*.

**Respuesta**: hay guias (templates + steps + DETs + validators), tienen forma de uso (encadenados en el workflow), **pero NO aplica en todo** — gaps especificos identificados.

**Por que es pre-requisito de HOR-054**:

HOR-054 implementa `dkc_enforce_step` (Frente A) + `dkc_invoke_agent` (Frente B) — MCP tools que leen artefactos del filesystem (markdown de tickets/specs/steps) para hacer enforcement programatico. Si los artefactos tienen drift silencioso heredado (frontmatter YAML con duplicate keys, fences sin parser, narrativas no-enforced), los MCP tools van a:

- Inferir mal el catalogo a-hook (drift en formato del tag, parser falla)
- Fallar al parsear fence `dkc:agent-invocation` si formato varia entre archivos
- Producir output inconsistente con la realidad del filesystem

Decision del dev (2026-05-16): cerrar gaps ANTES de pasar a HOR-054. Bloquea HOR-054.

**Principio clave del ticket** (feedback del dev 2026-05-16): *"no sirve tener algo documentado que no se usara, o el llm hara caso omiso"*. **No basta con que los validators existan** — deben:

1. **Existir** (codigo ejecutable disponible en `commands/lib/schemas/`)
2. **Estar disponibilizados** (comando `dkc-validate <kind>` resuelve el schema sin error)
3. **Estar invocados** (los gates de los steps DKC los llaman en el momento correcto)
4. **Ser enforced** (el LLM NO puede saltar la invocacion silenciosamente — gate bloqueante programatico, no advisory)
5. **Ser auditables** (hay script que detecta drift entre validators declarados vs validators efectivamente invocados)

Este es el meta-problema D11 trasladado al universo validators: documentar = facil, enforcement = dificil. **HOR-055 prepara el terreno** (catalogo + audit) que HOR-054 (MCP tool ejecutor) consume para enforcement automatic.

**Gaps identificados (8)**:

### Gap 1 — Cobertura asimetrica de validators (6/12+ kinds)

**Validators existentes** (`commands/lib/schemas/`):
- ✅ SpecTask (`spec-task.ts`)
- ✅ SessionBlock (`session-block.ts`)
- ✅ Teach (`teach.ts`)
- ✅ Decision (`decision.ts`)
- ✅ Rule (`rule.ts`)
- ✅ AntiPatterns (`anti-patterns.ts`)

**Validators faltantes**:
- ❌ **Ticket** (frontmatter rico: story_points, teachings, autopilot, sprint, reclassified, blocks, implications, etc.)
- ❌ **Bug** (templates/records/bug.md, sin schema Zod)
- ❌ **MetaSpec** (templates/records/meta-spec.md, sin schema)
- ❌ **Spec full** (solo SpecTask cubre la tabla `## Tasks`. Resto del spec — Executive summary, REQ callouts F8, Decisions matrix, Acceptance — sin validator)
- ❌ **Draft** (tickets/{id}.draft/intent.md, sin schema)
- ❌ **Transcript** (templates/records/transcript.md, sin schema)

### Gap 2 — `yaml-strict-no-duplicates` NO implementado

Bug D12 capturado en backlog de HOR-053: el LLM agrega claves nuevas al cerrar tickets sin remover las del template original (`closed: '2026-05-16'` + `closed: null` legacy). `gray-matter` rechaza duplicate keys → HC server retorna `frontmatter: {}`. SQLite mas permisivo. Listing funciona pero detail rompe.

**Fix in-vivo aplicado** en HOR-046+050. **Pero no hay validator que prevenga recurrencia**.

**Evidencia adicional**: en la sesion de HOR-051 (esta sesion) introduje yaml duplicate (`## Sessions` headers doble) y yaml mapping invalido (`acceptance:` dentro de valor sin quotes). Ambos detectados manualmente o por reindex falla, no por validator preventivo.

### Gap 3 — Reglas narrativas verificadas por grep, no por schema

**Reglas que viven en prosa del template**:
- **R1-R5** (HOR-016 narrative discourse): glosario inline + por-que-antes-que-que + citas previas + conexiones posteriores + lessons learned
- **H12** intros narrativas (3 lineas: Que es / Como te afecta / Por que mirarla)

Verificacion actual: gate manual via grep mental del LLM. **Mismo problema D11 que HOR-051+052 estan resolviendo** — el LLM falla 97.5% inline en directivas declarativas. Las reglas narrativas son directivas declarativas tambien — fallan por la misma razon.

### Gap 4 — Parser HC asimetrico para fences `dkc:*`

**Fences renderizados en HC** (HOR-015): hypothesis-map, decision-matrix, learning-path, code-walkthrough.

**Fences propuestos sin parser**: `dkc:agent-invocation` (HOR-054 introduce — los 6 mentions de AGENT INVOCATION se refactorizan a este fence). Sin extension del parser HC, los archivos refactoreados muestran el fence como bloque code plain — funcional pero feo.

**Implicacion sistemica**: cada vez que se agregue un fence `dkc:*` nuevo (futuro frente del enforcement, nuevo tipo de artefacto), el parser HC debe extenderse. Sin proceso formal de "agregar fence dkc:X + parser HC + tests".

### Gap 5 — Templates project-scoped (HOR-021) opt-in vacio en horadric

**Estado horadric**: `projects/horadric/templates/` no existe / esta vacio. Gate A3 silencioso. Si se quiere enforcement maximo de codigo vs templates de horadric mismo, hay que popular.

### Gap 8 — Validacion de EJECUCION enforced (no solo de artefactos producidos)

> **Feedback del dev (2026-05-16)**: *"quiero ampliar el 055 a validacion de ejecucion de sesiones, si esta enforced los pasos que se deben ir haciendo o cae en lo que el llm entiende"*.

**El problema**: los validators actuales (existentes y los nuevos en Gap 1) verifican **el producto final** de un step (frontmatter del ticket, tabla de tasks del spec, archivo de teach). NO verifican que **el proceso de ejecucion** siga las directivas declarativas durante el run. Caso real D11 amplificado: el LLM produce ARTEFACTOS validos al final pero salta o ignora pasos intermedios durante la ejecucion.

**Manifestaciones observadas hoy** (causa raiz: directivas declarativas sin enforcement programatico):

| # | Directiva declarada | Comportamiento observado | Validator faltante |
|---|---------------------|--------------------------|---------------------|
| **D9** | task status fluye `[ ]` → `[~]` → `[x]` (HOR-015 H10 — marca in-progress visible para HC) | LLM va de `[ ]` directo a `[x]` (0% uso de `[~]` medido HOR-046) | Detectar transiciones `[~]` ausentes en spec.md cuando una session marca tasks como done |
| **D2 / Gate D request-execute** | post-cada-task: registrar inline session log + MCP calls (`dkc_append_session_log`, `dkc_update_task_status`) | Registro retroactivo al close (no inline). MCP calls ~2.5% reales (D11) | Detectar tasks marcadas `[x]` sin entry correspondiente en `## Sessions` del ticket markdown (gap entre completion de task y registro) |
| **DET-23** | Quality Review (10 dimensiones) presente en cada session T1/T2/T3 ANTES de la decision del gate | Quality Review escrito al final, o solo en gate ⚑ fuerte | Detectar `### Session N` sin sub-seccion `#### Quality review (DET-23)` para tier T1+ |
| **DET-25** | Test cases registrados INLINE en el momento de ejecucion (no diferidos al close) | Registro retroactivo al close. TC con `Actual: —` hasta cierre | `dkc-validate-tcs` ya existe — pero verifica al close, no detecta el patron "inline vs deferred" durante execute |
| **Gate decision** | Cada session cierra con decision explicit `continue \| iterate \| escalate \| standby` | LLM avanza a siguiente session sin marcar decision (asumida implicita) | Detectar `### Session N` sin linea literal `**Gate decision:**` |
| **State machine de steps** | Orden: request-intake → intake-explore → teach-intake → design-{tipo} → execute → close | LLM puede saltar pasos (ej: intake → design sin teach-intake). DET-21 detecta esto **manualmente** (grep en gate del step ejecutor) | No hay tracking de "que step esta corriendo ahora mismo" ni validador de transicion |

**Solucion propuesta**:

Tres nuevos validators de **ejecucion** (kind set distinto a los validators de artefactos):

#### 8.1 — Validator `SessionExecution`

Lee `## Sessions` del ticket markdown + tabla de tasks del spec, verifica:

- **Transiciones consistentes**: si una task aparece como `[x]` en spec, su session correspondiente DEBE tener entry en `## Sessions` del ticket con timestamp y session log no vacio
- **Quality Review presente**: para sessions con tier T1/T2/T3, sub-seccion `#### Quality review (DET-23)` existe con tabla de 10 dimensiones y resultado global (pass/iterate/escalate)
- **Gate decision explicit**: cada `### Session N` cierra con linea `**Gate decision:** continue | iterate | escalate | standby` (no asumir implicito)
- **Sessions cronologicas inmutables**: entries con timestamps en orden creciente, sin re-edicion retroactiva (DET-6)
- **Pattern `[~]` presente**: heuristica — al menos 30% de tasks de la session pasaron por estado intermedio `[~]` visible en spec history (validable solo via git history, o via marcadores explicit del LLM)

#### 8.2 — Validator `StepTransition`

Lee secuencia de invocaciones de steps en el ticket + spec, verifica:

- **Orden valido**: las transiciones registradas siguen el grafo de `invoked_after` / `invoked_before` declarado en frontmatter de cada `prompts/steps/*.md`
- **Gates bloqueantes respetados**: si `design-{tipo}` corrio, `teachings.intake` MUST ser `done` o `skipped-con-razon` (DET-21). Equivalente para close + teach-close (DET-22)
- **Sin step duplicado en la misma session**: no se vuelve a correr `intake-explore` despues de `design-{tipo}` (excepto reclassificacion explicit, como HOR-051 v1 → v2)

#### 8.3 — Marker explicit de "step en curso" + auto-tracking

Patron complementario: cada step declara al inicio un marker machine-readable en el ticket markdown:

```markdown
## Workflow state

| Step | Status | Started | Closed |
|------|--------|---------|--------|
| request-intake | done | 2026-05-16 11:00 | 2026-05-16 11:15 |
| intake-explore | done | 2026-05-16 11:15 | 2026-05-16 11:30 |
| teach-intake | done | 2026-05-16 11:30 | 2026-05-16 11:45 |
| design-improvement | in_progress | 2026-05-16 11:45 | — |
```

Validator `SessionExecution` + `StepTransition` leen esta tabla para verificar coherencia. **Solucion al "no hay tracking de step actual"** mencionado arriba.

**Integracion con audit (Gap 7)**:

El `dkc-audit-validators` extendido (Gap 7) tambien reporta:
- Tickets `closed` con sessions sin Quality Review en tier T1+ (drift retroactivo)
- Tickets con tasks `[x]` sin entry en `## Sessions` (registro perdido)
- Tickets sin `## Workflow state` (legacy o LLM omitio el marker)

**Integracion con HOR-054**:

Cuando HOR-054 implemente `dkc_enforce_step`, el MCP tool puede:
- Forzar transicion `[ ]` → `[~]` al iniciar task (escribir spec.md con `[~]` antes de retornar control al LLM)
- Forzar entry en `## Sessions` post-task (escribir session log antes de retornar)
- Forzar Quality Review template al cerrar gate (escribir tabla 10-dim antes de retornar)
- Forzar update de `## Workflow state` al cambiar de step

**Sin enforcement programatico (situacion actual), las directivas declarativas siguen siendo prosa**. Con HOR-054 + validators de Gap 8, el ciclo se cierra: enforcement automatic + validator que detecta cuando algo se salto.

### Gap 7 — Audit script para detectar drift validator declarado vs invocado en steps

**El problema**: aun con Gap 6 resuelto al momento del ticket, los validators y los steps evolucionan. Se agrega validator nuevo → ¿esta invocado? Se renombra un step → ¿la invocacion sigue valida? Hoy sin audit, el drift acumula silencioso.

**Solucion**: script `commands/dkc-audit-validators` que:

1. Lista todos los validators en `commands/lib/schemas/`
2. Lista todas las invocaciones `dkc-validate <kind>` en `prompts/steps/**/*.md` + tags `<!-- enforcement: a-hook command: "./commands/dkc-validate ..." -->`
3. Reporta:
   - Validators sin invocaciones (codigo muerto)
   - Invocaciones a validators que no existen (referencia rota)
   - Validators invocados en steps incorrectos (heuristica: kind Teach debe invocarse en steps de teach-*, kind SpecTask en design-* o close, etc.)
4. Exit 1 si hay drift, 0 si OK

**Como se usa**: gate periodico (manual o en CI) que el dev corre antes de cerrar tickets que modifican validators o steps. Integrable con HOR-054 a-hook tag en futuro: el MCP tool puede invocar audit automaticamente.

**Patron analogo**: `validate-templates` (HOR-021) ya tiene este principio para templates project-scoped. Generalizamos para validators del kind set.
