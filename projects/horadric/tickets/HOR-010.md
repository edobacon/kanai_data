# Empaquetado como app macOS (Tauri launcher del `npm run dev`)

## Request

El dev quiere transformar horadric-cube en una app macOS nativa para uso personal. El objetivo concreto es **evitar tener que abrir consola y correr comandos cada vez** — abrir la app desde el dock y tener el panel funcionando.

La app debe:

- Correr como app nativa de macOS (icono en dock, ventana con controles del sistema, menu bar propia).
- No requerir abrir navegador externo — webview embebido.
- Ocuparse de levantar el servicio (`npm run dev` del repo) si no esta corriendo. Si detecta uno corriendo en el puerto, usarlo y no levantar otro.
- Al cerrar la app: si ella spawneo el servicio, matarlo. Si ya estaba corriendo externo, respetarlo.
- Reflejar cambios de codigo del frontend al instante (HMR de vite preservado).
- Manejar "aperturas de pestañas" (hoy el flujo asume cmd+click = nueva tab del browser). Explorar tabs internas tipo VSCode o modo fullscreen como alternativa.
- Permitir cambiar el `deckard_root` desde la app (con restart del sidecar).

Scope: solo macOS, solo uso personal. Sin firma con Apple Developer ID (codesign ad-hoc basta). Sin auto-update. Sin cross-platform.

## Triage

Explore de arquitectura. El stack actual (Vue3 + Vite + Node + Hono + better-sqlite3) se conserva intacto — la shell Tauri es una capa nueva que envuelve lo existente.

**Arquitectura acordada en intake**: **Opcion B** — Tauri como launcher del `npm run dev`. La app no empaqueta el frontend ni el backend; actua como shell + orquestador de procesos. El webview apunta siempre a `http://localhost:3016` servido por vite dev.

**Consecuencias positivas de opcion B**:

- HMR de vite funciona dentro del webview (identico al browser actual).
- No hay que empaquetar `better-sqlite3` (modulo nativo) — el server corre tal cual con `tsx watch`.
- Un solo flujo de desarrollo: editas codigo, la app refleja cambios al instante.
- La shell Tauri se toca una vez en setup y casi nunca despues.

**Consecuencias a aceptar**:

- La app depende de tener el repo clonado en un path conocido (picker en primera apertura).
- Requiere Node 22 disponible en el sistema (via nvm o global).
- Puerto 5180/3016 puede colisionar con otra instancia de dev corriendo — se resuelve con deteccion previa.
