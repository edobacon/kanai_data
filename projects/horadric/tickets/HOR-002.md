# Fixes UX + git avanzado — loading bar, badges, archivados, diff de commits, selector de rama, render de secciones anidadas

## Request

Cinco fixes/mejoras al v1 del Horadric Cube despues de uso inicial:

1. **Loading bar global**: las peticiones al api son algo lentas, deberia haber un marcador de cargando — barra superior fina que cargue a lo largo del viewport (estilo YouTube/Vercel/NProgress).
2. **Badges en pestañas del proyecto**: cada tab del header (Tickets, Specs, Rules, Decisions, Bugs, Meta) debe mostrar un badge con la cantidad de elementos que tiene.
3. **Tickets archivados**: deberia detectar los tickets con `status: archived` y manejarlos correctamente — hoy caen en columna "Other" del kanban porque el backend no los conoce y el index SQLite no los indexa.
4. **Diff de commits**: implementar ver el diff de cada commit dentro del Cube (estaba en backlog B6 del HOR-001).
5. **Selector de rama en seccion commits**: debe haber una parte de la seccion commit donde se pueda escoger la rama para revisar commits de otras ramas. Requiere exploracion (como listar ramas, cual es el default, como mostrar el grafo si se cruzan).

**Descubiertos durante el intake (Session #2 del ticket):**

6. **Tab Sessions del ticket aparece vacia**: el backend devuelve `sections.sessions` como `content` plano del heading `## Sessions`, pero las sessions reales viven en subsecciones `### Session #1`, `### Session #2`, etc. El content del heading queda vacio y la tab no muestra nada — aunque el `.md` tenia 21KB de sessions.
7. **Tasks por fase en specs se ven como "varias tablas sueltas"**: el spec separa tasks en fases (`### Fase 0 — Scaffolding`, `### Fase 1 — ...`) para comunicar orden por dependencia y progreso parcial. El viewer concatenaba todas las tablas sin mostrar los headings — la decision estructural del spec se perdia.

## Preguntas abiertas (a cerrar durante el design)

1. **Reindex vs fs-scan para archivados**: ¿agregamos a `reindex.md` de deckard que capture archived? O dejamos el index como esta y el server hace scan del fs cuando falta un ticket en el index? Tradeoff: la primera opcion cambia el contrato de deckard (afecta otros consumers); la segunda es mas aislada pero duplica scan al listar. **Propuesta default**: fs-scan on-demand — horadric no toca el reindex de deckard.

2. **Alcance del branch selector**: ¿soportar multi-branch (checkbox de varias ramas) o solo single? Multi implica merge de outputs de `git log` por rama, deduplicar y ordenar. Single es 10× mas simple. **Propuesta default**: single, con "All branches" como opcion especial (`--all`).

3. **UX del diff viewer**: ¿modal que ocupa 80% del viewport, panel lateral que empuja contenido, o pagina completa con ruta `/p/:p/commits/:hash`? La pagina completa permite deep-link y side-by-side view al abrirlo. **Propuesta default**: pagina con ruta.

4. **Granularidad del loading bar**: ¿cuenta TODOS los requests (incluyendo polling ETag cada 4s que generalmente da 304) o solo los "nuevos" (status 200 con payload)? Si cuenta todos, parpadea constantemente. **Propuesta default**: solo cuenta requests que empiezan sin ETag previo o que fueron invalidados con `no-cache`.

5. **Badges con 0**: ¿mostrar `Rules 0` o ocultar el contador? Mostrarlo es mas consistente, ocultarlo es menos ruido. **Propuesta default**: mostrar siempre — el usuario entiende rapido que 0 significa "vacio".

6. **Diff de commits de repos externos**: los commits de bayley viven en `/Users/edobacon/Workspace/uplanner/bayley/.git`. ¿El server de horadric lee esos `.git` directamente? Si el usuario corre el cube desde otra maquina sin acceso, fallan. **Propuesta default**: degradar con `reason: 'repo-unreachable'` como ya hace `/commits` hoy.
