### Decisiones tempranas confirmadas en intake

Tomadas antes de pasar a design para reducir el espacio de exploracion. Se promoveran a records formales `DEC-*` durante design.

| # | Decision | Valor elegido | Por que | Alternativa descartada |
|---|----------|---------------|---------|------------------------|
| D1 | SQLite access layer | **better-sqlite3 server-side** (readonly) | Proceso node adicional es trivial en dev mode; evita bundlear sql.js (~1MB WASM) y cargar el `.db` entero en browser; soporta FTS5 nativo sin setup | sql.js browser-only — mas simple en topologia pero peor en arranque/memoria y requiere copiar el `.db` al frontend |
| D2 | Parser del body de records (sessions, learns, tasks, test cases, backlog) | **Regex pragmatica por seccion** (`## Sessions`, `## Learns`, etc.) con parser de tablas markdown simple | 10× mas rapido de escribir; los templates estan estables y son controlados por nosotros; si cambian, se rompe un test dedicado y se arregla | markdown-it AST walk — robusto pero overkill para templates propios; se puede migrar sin romper la API publica si duele |
| D3 | Server framework | **Hono** (o Express si se prefiere ecosistema maduro) | Hono: TS-first, chico, funciona en node/deno/bun; suficiente para ~10 endpoints REST | Sin framework (http nativo): mas codigo boilerplate; Fastify: overkill |
| D4 | Estrategia de sincronizacion con cambios del filesystem | **Polling HTTP condicional con ETag** en vista activa (3-5s) + boton refresh manual. El server calcula ETag como `content_hash` del `.md` (o max mtime del directorio para listados). Responde `304 Not Modified` si no cambio | 1 usuario, uso interactivo, cambios disparados por Claude Code. Polling 304 es practicamente gratis. No hay colaboracion que justifique push real-time | SSE + chokidar watcher — mejor UX (<100ms) pero requiere conexion persistente, reconexion, watcher en server. Queda en backlog B3. WebSocket: overkill (bidireccional, no aplica a read-only) |
| D5 | Commits relacionados al ticket | **`git log --grep="<ticket_id>"`** sobre el repo apuntado por `config.yaml.repo.path` del proyecto deckard. Match en el mensaje del commit (hash, fecha, autor, subject, files changed count). Exec via `simple-git` (wrapper node maduro y tipado) o `child_process.spawn('git', ...)` — decidir en design segun peso de dependencias | Los commits de bayley ya siguen la convencion `BLY-001 <tipo>: <msg>` (ver recent commits). Sin parsing extra: `git log` hace el trabajo. Repo local, sin latencia de red | Parsear `git log --format=...` a mano: fragil; usar libgit2/nodegit: overkill para un `log --grep` |
| D6 | Libreria para diagrama de flujo | **vue-flow** (misma que bayley usa para DataModelView y LayoutsView) | Familiaridad cero-curva, componentes custom para nodos, layout dagre ya probado en bayley. El flow del ticket es un grafo dirigido pequeño (~5 nodos) | Mermaid: mas declarativo pero menos flexible para nodos interactivos; d3: overkill; render custom SVG: mas codigo sin ventaja |

## Scope del explore

### IN — preguntas que debe responder el spec draft

1. **Arquitectura de datos**
   - Que se lee de SQLite vs. que se parsea de markdown — mapa completo por vista.
   - Shape del modelo intermedio (types TS) para cada tipo de record.
   - Como se parsea el frontmatter heterogeneo (gray-matter + normalizacion por tipo).
   - Como se parsean secciones del body del ticket (sessions, learns, tasks, test cases, backlog) — markdown-it AST vs. regex pragmatico.

2. **Arquitectura de server**
   - Endpoints REST necesarios y su payload:
     - `GET /api/projects` — lista proyectos (desde filesystem).
     - `GET /api/projects/:project/overview` — stats generales.
     - `GET /api/projects/:project/tickets` — listado filtrable.
     - `GET /api/projects/:project/tickets/:id` — detalle parseado.
     - `GET /api/projects/:project/specs` / `:id`.
     - `GET /api/projects/:project/rules` (con filtro por `module`).
     - `GET /api/projects/:project/decisions` / `:id`.
     - `GET /api/projects/:project/bugs` / `:id`.
     - `GET /api/projects/:project/meta-specs` / `:id`.
     - `GET /api/projects/:project/search?q=...` — FTS5 sobre records_fts.
     - `GET /api/projects/:project/relations?from_id=...` — grafo de relaciones.
     - `GET /api/projects/:project/tickets/:id/commits` — commits del repo del proyecto que mencionan el `ticket_id` en el mensaje (ver D5).
     - `GET /api/projects/:project/tickets/:id/flow` — flow del work_type con estado inferido (ver D6). Response: `{ nodes: [{id, label, status, description, agents, produces}], edges: [{from, to, conditional}], current: <node_id>, next: <node_id> }`.
     - `GET /api/workflow/steps/:step` — metadata de un step (description, produces, agentes involucrados) leida de `prompts/steps/<step>.md`. Cacheable (los prompts no cambian en runtime).
   - Estrategia de lectura SQLite (better-sqlite3 readonly mode).
   - **Invalidacion por ETag** (D4): cada endpoint de detalle calcula `content_hash` del `.md` como ETag y soporta `If-None-Match` → `304 Not Modified`. Listados: ETag = max(mtime) del directorio.
   - Proteccion contra path traversal (sandbox al deckard_root).

3. **Vistas y navegacion**
   - **Home / Projects**: grilla de proyectos con metricas (N tickets open, N closed, N rules, N bugs, ultimo cambio).
   - **Kanban de tickets** (vista principal por proyecto):
     - Columnas por `status` (open / in_progress / done / closed).
     - Tarjetas con: id, titulo, module, tags, work_type, spec asociado, fecha.
     - Filtros laterales: module, work_type, tags, spec.
     - Busqueda rapida por texto.
     - Swim lanes opcionales por `module` o `work_type`.
   - **Grilla alternativa**: tabla tanstack-table con columnas configurables y sort.
   - **Detalle de ticket**:
     - Header: id, titulo, badges (status, work_type, module, spec).
     - **Top bar debajo del header**: diagrama de flujo vue-flow horizontal y compacto con estado actual + panel expandible "paso actual / siguiente paso" (ver D6).
     - Tabs o secciones: Request, Classification, Triage (con hipotesis), Sessions (timeline), Learns (tabla), Failed approaches, Testing (coverage map + test cases + artifacts + regression), **Commits** (git log grep por ticket_id — ver D5), Backlog, Summary.
     - Render del markdown con markdown-it (tablas, code blocks).
     - Sidebar de relaciones: specs relacionados, rules descubiertas, decisions tomadas, bugs encontrados, commits.
   - **Detalle de spec**: similar estructura con requirements, design tecnico, tasks, test cases; linkea al ticket origen.
   - **Lista de rules** por modulo con filtro por `level` (must/should/may).
   - **Lista de decisions** con filtro por modulo y estado.
   - **Lista de bugs** con filtro por severidad y modulo.
   - **Vista de relaciones** (opcional fase 2): grafo de un record y sus referencias in/out.

4. **Detalle del ticket — propuesta practica**
   - Layout recomendado: 3 columnas (main + sidebar + TOC) o 2 columnas (main + sidebar).
   - Como presentar **sessions** (timeline vertical con fechas + accordion por sesion).
   - Como presentar **learns** (tabla sortable con status, badge color por promoted_to).
   - Como presentar **test coverage** (barra de progreso REQs covered / total).
   - Navegacion interna: TOC fijo con secciones.

5. **Render de markdown**
   - markdown-it + plugins: anchor, frontmatter, highlight.js o shiki, table, task-lists.
   - Resolver links internos `SPEC-xxx`, `RULE-yyy`, `BUG-zzz`, `DEC-www` — transformar en `<RouterLink>` a la vista correspondiente.
   - Resolver paths relativos `../../templates/...` — abrir en vista de archivo generica o link al VSCode local (`vscode://file/...`).

6. **Proyecto activo y navegacion**
   - Selector de proyecto en el header (combo) — independiente de `.active_project`.
   - Persistir ultima seleccion en localStorage.
   - Deep-link: `/p/:project/tickets`, `/p/:project/tickets/:id`, `/p/:project/specs/:id`, etc.

7. **Diagrama de flujo del ticket** (D6)
   - Vista grafica del workflow deckard aplicado al ticket actual. Muestra el camino completo y el estado de cada paso.
   - **Fases del flow** (de `prompts/workflows/request.md`):
     1. `intake` — ticket creado
     2. `design-draft` (condicional: `creates_visual` o `creates_data`)
     3. `design-{work_type}` — spec generado
     4. `execute` — tasks ejecutandose
     5. `close` — acceptance + summary
     Para `work_type: explore` el flow termina en `design-{subtipo}` (no pasa a execute/close).
   - **Colores por estado** del nodo:
     - verde: paso completado
     - azul (actual): paso en curso
     - gris: paso pendiente
     - naranja: paso bloqueado (ej: draft no aprobado)
     - punteado: paso condicional no aplicable (ej: design-draft cuando ambos flags son false)
   - **Inferencia del estado actual** (sin leer codigo ni ejecutar nada):
     - `status: open` + sin `spec` → en `design-{tipo}` (o `design-draft` si los flags aplican y `draft_approved != true`)
     - `status: in_progress` + `spec` con tasks pendientes → en `execute`
     - `status: in_progress` + todas las tasks del spec completas → en `close`
     - `status: closed` / `done` → flow completo
   - **Panel lateral "Paso actual y proximo"**:
     - Nombre del paso (ej: `design-feature`).
     - Que consiste — **description y proposito** leidos del frontmatter de `prompts/steps/<step>.md` + primer heading del body.
     - Agentes involucrados (tabla "Agentes por fase" del workflow).
     - Que produce (campo `produces` del frontmatter del step).
     - Como avanzar: comando a invocar desde Claude Code (`/dkc` con el ticket activo).
   - **Tambien aplicable a specs**: un spec tiene su propio mini-flow de tasks. Mismo componente renderiza `pending → in_progress → done` por task.
   - Lib: **vue-flow** (misma que usa bayley — familiaridad + curva cero).
   - El diagrama es **estatico por work_type**: se genera una sola vez a partir del workflow de deckard (leido al arrancar el server). No se infiere del markdown de cada ticket.

9. **Commits relacionados al ticket** (D5)
   - Cada ticket muestra en su detalle los commits del repo del proyecto cuyo mensaje mencione el `ticket_id` (ej: `BLY-001`, `HOR-001`).
   - El path del repo sale de `config.yaml` del proyecto deckard (`repo.path`).
   - Datos a mostrar por commit: hash corto, fecha, autor, mensaje (primera linea), archivos cambiados (conteo), link a diff (al mismo Cube en fase 2, o a `vscode://` en v1).
   - Cache: bajo — los commits historicos no cambian; solo se invalida el cache cuando `HEAD` del repo cambia (checkeable con un `mtime` de `.git/logs/HEAD`).
   - Opcional: heuristica adicional para commits que NO tienen el ID — matchear por rama (`branch_pattern: HOR-{id}-{slug}` del config), queda como backlog.

10. **Sincronizacion con cambios del filesystem** (D4)
   - Composable `useETagPoll<T>(url, interval)` en el frontend — encapsula `fetch` con header `If-None-Match`, maneja 304 como no-op, 200 como update del state.
   - Intervalo default 4s para vista activa. Detener polling cuando la tab pierde foco (`document.hidden`).
   - Boton "refresh" en header dispara fetch inmediato forzando `Cache-Control: no-cache`.
   - Header muestra timestamp del ultimo cambio detectado ("actualizado hace Xs").
   - `index.db`: NO se poolea — solo se invalida cuando el usuario hace "reindex" manual desde UI (que tambien muestra el `last_reindex` del `index_meta`).

7. **Stack concreto y decisiones tecnicas**
   - better-sqlite3 (server-side, readonly) vs sql.js (browser-side, mas lento pero sin server) — decidir.
   - markdown-it vs unified+remark — decidir.
   - shadcn-vue / headless-ui / reka-ui para primitives — decidir.
   - tanstack-table vs ag-grid vs build custom — decidir.

## Preguntas abiertas (a cerrar durante el design)

1. **Markdown parsing del body**: ¿parser AST tipado o extraccion por regex pragmatica por seccion (`## Sessions`, `## Learns`)? Tradeoff: AST es robusto pero pesa mas; regex es rapido pero fragil ante cambios en templates.
2. **SQLite direct vs. re-indexar**: ¿el Cube asume que el SQLite esta al dia, o ofrece un boton "reindex" que dispara el prompt/step correspondiente? Como es read-only, la opcion natural es "usar lo que haya" y mostrar timestamp de `last_reindex` en el header.
3. **Kanban statuses**: ¿que valores de `status` usa cada tipo? Normalizar un enum comun en el tipo Ticket o mostrar los literales del frontmatter.
4. **Sesiones en detalle**: ¿renderizar la tabla entera tal cual esta en el `.md` o parsear timestamps y agente para mostrarla como timeline visual? Probablemente timeline — es mas visual y el `.md` ya esta si alguien quiere el crudo.
5. **Proyecto activo visualmente**: ¿marcar con badge el proyecto que matchea `.active_project` aunque se pueda navegar cualquiera?
6. **Stack UI**: ¿usar las mismas convenciones de bayley (Tailwind + headless-ui + lucide) para consistencia mental? Probablemente si.
