# Cycle validation: intake→design→execute→close en orden (DKC v2 Phase 4 — conditional)

## Request

**Ticket exploratorio conditional**. Origen: post-refundacion DKC v2. Cubre gap C identificado en el analisis 2026-05-16: validacion del ciclo del workflow.

**Que es**: el flujo DKC tiene orden canonical (intake → design → execute → close) pero no hay enforcement programatico de que los pasos ocurran en orden ni que se completaron todos. Hoy el LLM principal puede saltar pasos en teoria. En practica, el dev gobierna el orden con el comando `/dkc` clasificador.

**Riesgos no observables**:
- LLM ejecuta `request-execute` sin `design-{tipo}` previo (sin spec)
- `request-close` se invoca sin gates D y E completados
- Quick path crece a multi-archivo sin escalate explicito (G2 de HOR-023 detecta esto como warning, este ticket lo formalizaria)

**Por que conditional**: dolor NO observable HOY. El dev + el comando `/dkc` gobiernan el orden. En setup local-only (Qwen 30B) el LLM principal puede ser menos disciplinado — ahi vale mas. Tambien util si abrimos paralelismo (HOR-024).

## Conditions for activation (BLOQUEANTE)

Activar SI o SI ocurren UNA o MAS de estas condiciones:

| # | Condicion | Como se detecta |
|---|-----------|-----------------|
| **C1** | LLM principal ejecuta paso fuera de orden >= 2 veces en proximos 5 tickets (ej. design sin intake, execute sin design) | Documentado en learns con tag `cycle-violation` |
| **C2** | HOR-024 (Async tasks paralelas) se activa — paralelismo requiere cycle awareness para evitar race conditions estructurales | Decision en HOR-024 planning |

| **C4** | Dev reporta que un ticket cerro como `closed` sin haber pasado por todos los gates esperados | Audit post-close revela inconsistencia |

**Si NINGUNA condicion activa**: HOR-044 queda `open` indefinido. Si dev gobierna bien el ciclo: cerrar como `won't_do` con razon.
