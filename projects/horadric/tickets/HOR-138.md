# `creation_gate` opt-in por proyecto: acoplar la cascada DET-32 a la puerta de creacion propia del repo (`/up1-check`) + COMMANDMENTS por repo

## Request

Que un flujo DKC, al tomar un ticket de up1, corra la puerta de creacion propia del repo (`/up1-check`) y respete los COMMANDMENTS de up1. up1 es multi-repo (raiz + workspaces core como submodulos + up1-mcp standalone): los COMMANDMENTS deben leerse por CADA repo que el trabajo alcanza, no como set fijo.

Contexto del problema: DKC ya tenia el check semanticamente identico — **DET-32** (necesidad/reuso, Paso 0d de `design-*`), misma cascada que `/up1-check` (¿necesita existir? → ¿ya existe? → ¿lo da el framework? → ¿se reduce a config? → build). Pero eran **gemelos desacoplados**: DKC nunca invocaba `/up1-check` ni producia el registro de sesion (`.claude/.session/up1-check-passed`) que el hook del repo (`validate-write.js`) exige. Resultado: trabajo dirigido por DKC podia crear archivos en up1 saltandose la puerta del repo, y en los paths que el hook no cubre, sin ninguna senal. Los COMMANDMENTS tenian el mismo gap por otra via: no estaban acoplados al `execute_scope`, asi que ni intake ni el sub-agente developer sabian cual leer.

## Alcance

### Dentro

- **`creation_gate:` en `config.yaml` del proyecto** (bloque OPCIONAL, patron override como `mutation`/`smoke`/`trigger_rules`): declara el comando propio del repo que implementa la cascada DET-32, su `cwd`, el `session_record` que el hook verifica, y la cobertura real del hook (`hook_paths`) vs el alcance del gate (`paths`). Ausente = cascada inline (comportamiento base).
- **Enganche en `_design-shared.md` (Paso 0d)**: si el proyecto declara `creation_gate: enabled`, la cascada DET-32 se implementa CORRIENDO ese comando (no razonandola inline), y su salida se mapea al veredicto `necessity-assessment` (`reuse|reduce|drop|build`). Mapeo REQUEST EXTENSION → `drop` + pedido registrado. Fallback explicito con razon si el comando no esta disponible.
- **`deterministic-rules.md` (DET-32)**: parrafo "implementacion por proyecto" + Capa 2 del enforcement, para que el texto integro de la DET no contradiga al step.
- **`RULE-dev-012` (proyecto up1)**: el contrato del gate — `/up1-check` una vez por requerimiento, el session record como parte del contrato, el hook como piso (no garantia), y los COMMANDMENTS por repo alcanzado.
- **`commandments:` en `config.yaml` del proyecto up1**: mapeo `execute_scope`-prefix → COMMANDMENTS por repo. `platform_always` (raiz) + `by_scope` (por subtree/repo). Montado sobre la misma iteracion por repo destino que la guarda de rama (RULE-dev-004 / DET-30).

### Fuera

- Reforzar `validate-write.js` del lado up1 (cubrir `Edit`, mas paths, resolver por repo root) — es la opcion D del analisis, toca el repo up1 con ticket/PR propio. Follow-up local.
- Gate duro en execute (verificar el session record en `request-execute/start.md`) — opcion C, mayor superficie en DKC core. No pedido.
- Sembrar `RULE-dev-012` en `rules[]` del scaffold de tickets up1 para garantizar descubrimiento por module distinto de `dev`. Ver limite honesto abajo.

## Context found

- **Hook**: `up1/.claude/hooks/validate-write.js` — cobertura PARCIAL: solo `Write` de archivos nuevos, solo `mods/` + `layout/src/components/`, solo si cwd es el repo up1 (`settings.json` project-scoped), `UP1_EXPERT_BYPASS=true` lo apaga.
- **DET-32**: `deterministic-rules.md:1294` + Paso 0d de `_design-shared.md:267`. Ya observable via `dkc-record-decision --step necessity-assessment` (`choice: build|reuse|reduce|drop|mixed`, enum en `commands/lib/schemas/decisions.ts`).
- **Multi-repo up1 (verificado)**: object-manager/layout/suite/flow/report-builder son git repos propios (submodulos); mods NO (parte de la raiz); up1-mcp es standalone (`uplanner/mcp`). COMMANDMENTS existen para raiz+mods+object-manager+layout+suite+flow; NO para report-builder ni up1-mcp.
- **execute_scope como fuente de "repos alcanzados"**: verificado en `projects/up1/tickets/TICKET-103.md:29` — entries con prefijo `<repo>:<path>` (`up1:object-manager/`, `up1:mods/curriculum-design/`, `up1-mcp:src/`). Los mismos que itera la guarda de rama (RULE-dev-004 / DET-30, por repo destino).
- **Precedente del pointer rule desde config**: `projects/up1/config.yaml` `core_work_policy: rule: RULE-dev-004`. `creation_gate.rule: RULE-dev-012` lo espeja.
- **Los dos clones de up1 divergen**: `Workspace/up1` (root+mods COMMANDMENTS) vs `uplanner/up1` (per-workspace, el que usa DKC via `repo.path`). Por eso los paths de COMMANDMENTS son opcionales.

## Summary

Acoplado el gate de creacion propio de up1 (`/up1-check` + hook) a la cascada DET-32 de DKC via un bloque opt-in `creation_gate:` por proyecto (patron `mutation`/`smoke`), y mapeados los COMMANDMENTS por repo alcanzado (`commandments:` keyeado por prefijo de `execute_scope`, montado sobre la misma iteracion por repo destino que la guarda de rama). Contrato en `RULE-dev-012`. Generico para otros proyectos con puerta de creacion propia; up1 es el primer consumidor.

**Follow-ups conocidos (backlog local, no Jira):**
- **Alinear los COMMANDMENTS entre los dos clones de up1** (L1): el clone que DKC usa (`uplanner/up1`) no tiene `.ai/COMMANDMENTS.md` ni `mods/.ai/COMMANDMENTS.md` (estan en `Workspace/up1`). Mientras no se alineen, `platform_always` y el mapeo `up1:mods/` no resuelven en el clone de DKC. Fix: unificar ramas/archivos para que el clone de `repo.path` tenga los 6 COMMANDMENTS, o mover los COMMANDMENTS de raiz+mods a la rama que ese clone tiene checkouteada.
- **Reforzar `validate-write.js` del lado up1** (opcion D del analisis): cubrir `Edit`, ampliar paths (`object-manager/objects/`, `src/resolvers/`, `suite/`, `flow/`), resolver por repo root en vez de `process.cwd()`. Toca el repo up1 con ticket/PR propio.
- **Descubrimiento de `RULE-dev-012` por module distinto de `dev`**: hoy alcanzable via el pointer `creation_gate.rule` / `commandments` del config (convencion). Si se quiere garantia dura, sembrarla en `rules[]` del scaffold de tickets up1.
