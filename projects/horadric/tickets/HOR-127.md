# Gate de verificacion runtime/UI — cerrar el hueco APPROVED-que-no-funciona (HOR-125 P2)

## Request

**Origen**: HOR-125 P2 (N1). Fricion F1 (la #1, en up1 Y jormat): el quality gate (dual-judge DET-35) + unit tests dan `APPROVED` pero el codigo falla en runtime; el verificador real es el smoke manual del dev, FUERA del automation de DKC. `explore` porque el alcance tiene rango amplio (formalizar vs ejecutar) y hay que decidir enfoque antes de implementar.

## Context found (KB map — verificacion/gates DKC hoy)

- **DKC nunca ejecuta la app en runtime**. El tester (`prompts/agents/tester.md`, unico con Bash) solo corre unit runners (vitest/jest/pytest); no monta componentes, no levanta servidor, no navega. El reviewer/dual-judge (`prompts/agents/reviewer.md:6-7`) es **read-only** (sin Bash) — analiza `git diff` estatico. Por diseno no puede reproducir el caso up1 TICKET-097 (`props.default` de Vueform, solo visible al montar el form).
- **"Affects UI: yes" (DET-25) + tier T3 "smoke manual UI" existen pero son texto libre** verificado sintacticamente: `dkc-verify-gate check_g3` (`commands/dkc-verify-gate:301-403`) solo chequea que la celda `Evidence` no este vacia — no valida contenido ni re-ejecuta. El `override` con `reason` permite cerrar comodo ("no reproducible en sandbox").
- **DET-33** (`deterministic-rules.md:1332-1379`) da el mandato conceptual (verificar el self-report, no confiar) y su motivacion cita "un TC cerrado por override sobre un runtime que nunca se ejecuto" — pero su tabla verifica build/tests/archivos, no exige *ejecutar* un smoke UI.
- **Precedente maduro**: `RULE-global-004` (jormat, project-scoped) ya exige "el dev stack debe levantar + consola limpia" (probado en JOR-003/JOR-060). Candidato a promover a DET-core.
- **Tooling latente**: `templates/outputs/playwright-config-dkc.ts` resuelve screenshots al ticket activo, pero es opt-in y ningun agente/step lo invoca. No hay runner de smoke automatico ni agente con navegador en el ciclo.
- **Patron reusable**: "convencion T2 evidencia observable" (HOR-058, `deterministic-rules.md:756-782`) — entry en `decisions_log` + validator. Es el mecanismo natural para instrumentar un gate runtime/UI.

Evidencia F1: up1 TICKET-097 (dual-judge APPROVED + vitest 862/862, roto en smoke x2; L3 lo documenta), jormat JOR-061 L4 (tests "fake" que renderizan sin ejecutar el handler), JOR-060 (smoke docker no reproducible → cerrado con la limitacion documentada via RULE-global-004).

Faseado: **Fase A** (gate honesto, portable, ahora) + **Fase B** (ejecucion real opt-in por proyecto, incremental).

### Fase A — Gate honesto (DET-core + gate + validator)

**A1. Nueva DET-36 — "Verificacion runtime/UI"** (`deterministic-rules.md` + `dets_catalog.py`, regenerar con `dkc-export-rules --global`).
- Contrato (condensado): toda session/task que toca UI (`creates_visual: true` o algun TC `Affects UI: yes`) MUST registrar el resultado de verificacion runtime como entry observable en `decisions_log`: `step: runtime-verification`, `choice: smoke-executed | smoke-not-reproducible | not-applicable`. `smoke-not-reproducible` exige `reason` auditada (no override silencioso). WARN-FIRST (calibrable a bloqueante en T3). Refuerza DET-25/DET-33. Base: generaliza `RULE-global-004` (jormat) a core.
- Numero: DET-36 (el catalogo llega a DET-35).

**A2. GATE RUNTIME** (`prompts/steps/request-execute/gates.md`, analogo a GATE D):
- Bloqueante antes de `done-task`/cierre de `S{N}.GATE` cuando la task toca UI: exige la entry `runtime-verification` en `decisions_log`. Patron "convencion T2 evidencia observable" (HOR-058, `deterministic-rules.md:756-782`).

**A3. Validator** (`commands/dkc-verify-gate`, extender `check_g3` o nuevo `check_g5`):
- Para TCs `Affects UI=yes`: distinguir `Evidence: runtime` (con marca de corrida real — timestamp/hash/screenshot path) vs `Evidence: static` (referencia a test file). Exigir `runtime` salvo `smoke-not-reproducible` + `reason`. Hoy `check_g3` (`dkc-verify-gate:301-403`) solo valida celda no vacia → cerrar ese hueco.

**A4. Refuerzo DET-25/DET-33**:
- DET-33 (`deterministic-rules.md:1342-1349`): agregar fila a la tabla de verificacion — `Claim "smoke OK"/"Affects UI cumplido"` → re-ejecutar/inspeccionar evidencia runtime real, no aceptar narracion.
- DET-25: la clausula "Evidence con verificacion real, no override sobre runtime no ejecutado" pasa de prosa a chequeo del validator (A3).

### Fase B — Ejecucion real opt-in (incremental, despues de A)

**B1. Rol `smoke-runner`** (`prompts/agents/smoke-runner.md`, nuevo): capabilities `[read, bash, browser]`; fase **C3** post-tester (`task-loop.md`), SOLO si `Affects UI: yes` Y el proyecto declara harness. Levanta entorno (dev server / build / Playwright headless o `run.sh dev`), captura evidencia real (screenshot/console/DOM). Output estructurado (`executed | failed | not_reproducible` + evidencia) consumido por GATE RUNTIME (A2) y el dual-judge (como parte del handoff, los jueces no ejecutan).

**B2. Opt-in por proyecto** (`config.yaml`, bloque `smoke:` opcional, patron override como `mutation`/`trigger_rules`): `enabled`, `command`/`harness`, `url`, `tier`. Ausente → Fase A pura (gate honesto sin ejecucion). Reusa `templates/outputs/playwright-config-dkc.ts`.

**B3. `smoke-not-reproducible` legitimo**: cuando la infra no corre en el entorno (JOR-060: Docker/MSAL), el gate acepta el estado con `reason` — deja de ser excepcion silenciosa, queda trazado.
