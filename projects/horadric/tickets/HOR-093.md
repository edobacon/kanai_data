# Explore — dkc_get_ticket_section: lectura parcial de records

## Request

Evaluar y disenar `dkc_get_ticket_section`: un tool que lea (y opcionalmente escriba) una seccion
puntual de un record DKC sin cargar el archivo entero. Motivacion (analisis de tokens 2026-05-31):
el cuerpo de un ticket es ~91% del archivo, la seccion `## Sessions` domina (27-48%), y los tickets
llegan a 1610 lineas / 170KB / ~42k tokens. Hoy cualquier step que necesita una seccion (agregar un
commit, leer el plan de sessions, actualizar un test case) carga el ticket COMPLETO en contexto.
El backlog #6 de HOR-085 ya identifico este tool pero quedo sin iniciar.

Explore (subtipo feature) → produce spec DRAFT, sin execute. El dev decide activarlo despues.

## Context found

> KB-first (DET-11) + hallazgos del analisis de esta sesion.

- **Parser reusable**: `extractSection(md, sectionTitle)` ya existe en [parsers/markdown.ts:80](../../../commands/lib/parsers/markdown.ts) — extrae el contenido de una seccion `##` por titulo (acepta string o array de aliases). Es la primitiva que el tool envolveria.
- **Patron analogo existente**: `dkc_get_step_phase` ([server/src/deckard_cain/tools/steps.py:76](../../../server/src/deckard_cain/tools/steps.py)) ya implementa lazy-loading de STEPS grandes por fase (HOR-059/086). `dkc_get_ticket_section` es el mismo patron aplicado a RECORDS. Registro via `@mcp.tool()` en un modulo de `tools/`.
- **HC no cambia**: horadric-cube lee el `.md` completo via gray-matter + markdown-it para render (confirmado en analisis). El tool es para consumo del LLM en steps, no para HC. Cero impacto en el viewer.
- **Tamanos reales**: 214 tickets, mediana 276 lineas / ~4k tokens, max 1610 lineas / ~42k tokens. Frontmatter 8.7%, cuerpo 91%. Sesiones dominan en los grandes.
- **Secciones canonicas** del ticket (frecuencia medida): Request (203), Classification (190), Sessions (186), Triage (169), Setup (160), Backlog (145), Teaching (140), Summary (138), Testing (117), Commits (31), Workflow state (28).
