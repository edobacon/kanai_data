# Hybrid retrieval degrada a semantic-only en queries NL largas (FTS5 AND implicito)

## Request

**Origen**: hallazgo lateral del pre-check de HOR-028 (2026-05-30).

**Sintoma**: al consultar `dkc_semantic_search` con queries en lenguaje natural largas (ej. "que es una evaluation en curriculum design y cuales son sus caracteristicas"), el componente BM25 del hybrid retrieval devuelve **0 candidatos** → el RRF queda con solo la rama semantic. El "hybrid" deja de ser hybrid justo en el caso de uso conversacional (que es como el researcher formula queries).

**Causa raiz (confirmada)**: FTS5 usa **AND implicito** entre tokens. `_bm25_search` (`server/src/deckard_cain/tools/embeddings.py`) pasa la query sanitizada directo a `chunks_fts MATCH ?`. Con una query de N tokens, exige que **todos** aparezcan en el mismo chunk → para queries largas, 0 matches.

**Evidencia**:

```
_bm25_search("programa de asignatura")      -> 10 hits   (raw FTS: 162)
_bm25_search("workflowState aprobacion")    -> 10 hits   (raw FTS: 10)
_bm25_search("que es actividad academica")  -> 0 hits    (raw FTS: 0)  ← AND: ningun chunk tiene los 4 tokens
```

El comentario en el codigo dice "OR implicit entre palabras" — **pero FTS5 default es AND**. El comentario esta equivocado o el comportamiento divergio.

**Impacto**: medio. El pre-check mostro que semantic-only igual recupera bien (5/5 conceptos OK). Pero el hybrid esta pensado para capturar matches literales (identificadores tipo `DET-25`, `BUG-X`, nombres de objetos) que semantic puede perder. Si bm25 cae a 0 en queries NL, ese beneficio se pierde silenciosamente.

**Propuesta de fix** (evaluar en design):

- **Opcion A** — unir tokens con `OR` explicito antes del MATCH: `"tok1 OR tok2 OR tok3"`. Recupera el comportamiento OR documentado. Riesgo: queries muy genericas traen ruido (mitigable con el RRF + score_threshold).
- **Opcion B** — extraer solo tokens "significativos" (quitar stopwords es/en) y unir con OR. Mas preciso, mas codigo.
- **Opcion C** — dejar AND pero hacer fallback: si AND da 0, reintentar con OR. Pragmatico, preserva precision cuando AND funciona.

Recomendacion preliminar: **C** (fallback AND→OR) — preserva precision en queries cortas y recupera recall en NL largas. Decidir en design-fix.

**Alcance**:

- `server/src/deckard_cain/tools/embeddings.py` — `_bm25_search` (logica de query + corregir comentario)
- Tests: query corta (AND OK), query NL larga (antes 0, ahora >0), query con identificador literal (DET-X)

**Repos tocados**: `deckard` (server)

## Summary — cierre (2026-05-30)

**Fix aplicado** (Opcion C del ticket — fallback AND→OR): `_bm25_search` (`server/src/deckard_cain/tools/embeddings.py`) ahora intenta el match AND implicito de FTS5 primero (precision en queries cortas / identificadores) y, si da 0 resultados con >1 token, reintenta uniendo los tokens con `OR` (recall en queries NL largas). El RRF + score_threshold downstream filtran el ruido del OR. Comentario corregido ("OR implicit" era falso — FTS5 usa AND).

**Verificacion empirica** (contra `projects/up1/embeddings.sqlite`): las 5 queries NL del probe pasaron de `bm25_candidates=0` a `bm25_candidates=20` — el hybrid vuelve a ser hibrido en queries conversacionales (que es como el researcher las formula).
