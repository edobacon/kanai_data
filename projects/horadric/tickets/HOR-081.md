# Teaching v2 — formato HTML didactico self-contained renderizado via iframe

## Request

> Quiero crear un ticket que revise el teaching. Al ser solo prosa se vuelven tediosos de leer
> cuando se manejan conceptos y flujos. Preferiria tener algo como
> `file:///Users/edobacon/Workspace/uplanner/specs/ongoing/up1/clonning-versioning/sprint-4-flujo-y-estado.html`,
> que se puede generar como HTML y mostrar mediante iframe — algo como lo que DKC y HC hacen con los drafts
> de diseno. Pero se debe tener en cuenta que esto sera desde el siguiente ticket en adelante: NO haremos
> revision hacia atras. El sistema debe detectar si tiene el teaching legacy en MD o el nuevo en HTML y
> mostrar el que corresponda.

**Refinamientos del dev durante intake** (no reescriben el request — DET-3):

- La finalidad real es hacer el teaching **mas didactico** (flujos, casos, mejores explicaciones). El HTML es el medio elegido por su libertad de composicion.
- Se debe tener **libertad** en que se muestra: no todos los casos usan los mismos bloques. Generar un **modelo base con un catalogo de todos los bloques didacticos posibles** que el autor combina segun necesidad y que **crece con el tiempo**.
- La dependencia CDN debe resolverse **localmente** (libs descargadas via package.json / servidas localmente), no online.

### Decisiones abiertas (resolver en design-draft / design-feature)

- ~~**OQ1 — Vendored vs inlined**~~ → **RESUELTA (2026-05-29): vendored servido por HC.** Libs locales (`@tailwindcss/browser@4.3.0` + mermaid ESM) en ruta del server; el teach HTML las referencia por URL local. Offline-safe, integrado, HTML liviano. "Abrir en pestaña" cubre full-page. Se acepta que el `.html` suelto no rinda via `file://` (no es el caso de uso). Descarta inlined (teaches de varios MB).
- **OQ2 — Marcador de version**: ¿`teach_format: v2` en frontmatter del teach, deteccion por existencia de `.html`, o ambos? Define como HC y los validators distinguen v1/v2.
- **OQ3 — Verificacion DET-21/22 en v2**: ¿que reemplaza al grep de bloques `dkc:*` para validar cobertura didactica en un teach HTML? (ej: marcadores `data-dkc-block="..."` en el HTML, o seccion de metadata).
- **OQ4 — Convivencia de catalogo**: ¿el catalogo de bloques se documenta en el template base, en una rule, o en design-system del proyecto? Como se amplia "con el tiempo" sin romper teaches existentes.
- **OQ5 — Quien autora el HTML**: el LLM en `teach-intake.md`/`teach-close.md` genera el HTML directamente desde el catalogo. ¿Se conservan los bloques `dkc:*` como insumo intermedio o se autora HTML directo?
