# Red de seguridad para autopilot autonomo — 2 niveles + guarda de inicio + validacion de cierre reforzada + teach reforzado

## Request

> Peticion del dev (verbatim, DET-3 — no reescribir).

Hoy DKC tiene modo autopilot (`false` / `true` / `strict` + triggers). Cuando un ticket corre autonomo, baja la supervision del dev durante la ejecucion. El dev quiere un esquema con **red de seguridad al inicio** (revertibilidad) y **validacion reforzada al final**, mas teach obligatorio, para poder ejecutar tickets de forma autonoma sin perder control ni educacion.

Requisitos (frentes):

1. **Dos niveles de autopilot autonomo** (reconciliar con `false`/`true`/`strict` actuales, sin romper triggers):
   - Nivel **por-sesion**: pregunta/gate al cierre de CADA sesion (supervision por sesion).
   - Nivel **por-ticket**: NO pregunta hasta terminar TODAS las sesiones; ejecuta el ticket completo de forma autonoma.
2. **Streaming de avances al chat** durante la ejecucion autonoma: el LLM va mostrando su progreso (que sesion/task, que cambio) para que el dev pueda **interrumpir/detener a fuerza bruta** si algo va mal.
3. **Guarda de inicio** (red al inicio, bloqueante antes de la 1a task cuando autopilot activo): verificar que NO se esta en develop/master; estar o crear rama de ticket; declarar el scope de repos/paths del ticket (de donde NO debe salir). Garantiza revertibilidad a nivel codigo (descartar la rama).
4. **Validacion de cierre reforzada** (red al final, sesion obligatoria cuando autopilot activo): contrastar cada cambio vs lo especificado en el ticket/spec; propagacion a lugares relacionados (DET-16); verificar que los cambios no salieron del scope declarado; verificar que sigue en rama de ticket sin tocar develop/master. Consolida DET-13+16+23.
5. **Intake exhaustivo**: toda la recopilacion de informacion se hace en intake (o la 1a sesion se encarga), revisando que se cubre todo lo necesario, para reducir al minimo las dudas durante la ejecucion autonoma (un ticket autonomo no puede parar a preguntar).
6. **Teach reforzado — MUST en autopilot** (no skip; condiciona DET-21/DET-22 que hoy permiten skip):
   - teach-intake: "que se tiene ahora / que se quiere hacer / por que", didactico, para que el dev entienda lo que se va a ejecutar antes y durante.
   - teach-close: "que se hizo / por que / que cambio y por que / si hubo variaciones del plan original, por que las hubo".
   - Ambos en PROSA legible, entendible, didactica — su funcion crece: mantener al dev educado de lo que se realiza/realizo y que vaya conociendo el producto cada vez mas.
7. **Permisos** (capa harness, no DKC): el dev activa el permission mode al lanzar la sesion (`--dangerously-skip-permissions` o un wrapper/alias); el LLM NO puede auto-elevar permisos a mitad de sesion. Opcional: git hook pre-commit/pre-push que rechace commits a develop/master (red dura real, independiente del LLM).
