# Enforce multi-LLM existente + agregar `tester` + validar context preservation empirico

## Request

**Hallazgos critico pre-execute (2026-05-15)** — antes de proponer cambios, audit del KB DKC revelo:

1. **Agents ya existen** (5 agents en `prompts/agents/*.md`): researcher/scribe (tier fast), developer/reviewer (tier balanced), architect (tier reasoning). Con `capabilities` + `restrictions` formales.
2. **agent-tiers.md ya existe** con mapping multi-provider (anthropic/openai/google/local) + configuraciones mixtas ejemplares + fallback entre tiers.
3. **Output schemas JSON ya definidos** en cada agent doc (researcher/developer/reviewer).
4. **PERO** — auditoria de invocacion real:
   - 10 steps **MENCIONAN** agents (texto declarativo)
   - **0 steps INVOCAN** Agent tool explicitamente con `subagent_type`
   - En HOR-022 (5h, 200K+ tokens) un solo LLM (Claude Code Opus 4.7) hizo TODO en un solo context window — la separacion era textual, no operacional

**Mi propuesta original HOR-025 violaba DET-11 (KB-first)** — proponia reinventar agent-tiers.md que ya existe. Pero el audit reveal algo mas importante: el sistema esta **declarado pero NO enforced**.

## Re-scope: 4 dimensiones cohesivas

### Dimension 1 — Enforcement de invocacion real de agents

**Problema**: steps dicen "Activar researcher" pero el LLM principal lo interpreta como instruccion textual, no como `Agent({subagent_type: "researcher", ...})`.

**Propuesta**:
- `prompts/steps/*.md` ajustados para invocacion explicita con sintaxis canonical:
  ```
  > AGENT INVOCATION (HOR-025): subagent_type=researcher, tier=fast, prompt="<task description>"
  ```
- LLM principal MUST invocar Agent tool ante esa instruccion (no inline)
- Falla graceful si Agent tool no soporta el tier requerido (logear + fallback al host LLM)

### Dimension 2 — Per-project override de agent-tiers global

**Problema**: `prompts/agent-tiers.md` es global. Algunos proyectos necesitan override (ej. bayley personal con todo sonnet, up1 SP3 con opus para architect).

**Propuesta**:
- `projects/{project}/config.yaml` admite seccion opcional `tiers:` que override agent-tiers.md global
- Resolution order: project config > global agent-tiers.md > host default

### Dimension 3 — Agregar agent `tester`

**Hallazgo audit**: 5 agents existen, pero el ciclo "implement → run tests → parse output → report" no tiene agent dedicado. En HOR-022 lo hice todo yo (developer + parsing implicito).

**Propuesta**: nuevo agent `tester` (tier balanced):
- **Capabilities**: bash (read tests output), read (test files), grep (parse errors)
- **Restrictions**: no_edit, no_write (NO arregla tests, solo ejecuta + reporta)
- **Output schema** structurado:
  ```json
  {
    "suite": "vitest|jest|pytest|go-test|...",
    "command_run": "npm run test ...",
    "passed": 12, "failed": 2,
    "failures": [{"file": "", "test": "", "error": "", "stacktrace": ""}],
    "coverage_delta": {"before": 0.0, "after": 0.0, "changed_files": []},
    "duration_ms": 0,
    "recommendation": "developer_review_needed | all_pass | infrastructure_issue"
  }
  ```
- Reemplaza el bloque "ejecutar tests" del developer (developer.md → ya no corre tests, delega al tester)
- Ciclo nuevo: `researcher → developer → tester → reviewer → scribe`

**Otros agents propuestos descartados**: debugger (fusion con architect), bug-hunter (reviewer cubre), migrator (scripts mejor), benchmarker (sin necesidad actual), doc-writer (scribe cubre).

### Dimension 4 — Medicion empirica de context preservation

**Problema**: la hipotesis "multi-LLM alivia context del principal" nunca se valido — siempre un solo LLM hizo todo.

**Propuesta**:
- En S3 del ticket: re-correr tasks de HOR-022 (researcher inicial + scribe registros + tester) **realmente delegando** via Agent tool
- Medir:
  - Tokens del LLM principal (Opus 4.7) antes vs despues
  - Activaciones DET-15 (contexto agotado) en proximos 3-5 tickets
  - Calidad de outputs por agent (degradation check)
- **Validar H5/H6/H7** del Triage original

**Alcance**:

- `prompts/steps/*.md`: enforcement de invocacion (10 steps tocados)
- `prompts/agents/tester.md` (nuevo)
- `prompts/agents/developer.md`: delega corrida de tests al tester (refactor menor)
- `projects/{project}/config.yaml`: schema admite seccion opcional `tiers:`
- `prompts/agent-tiers.md`: documentar resolution order (project > global)
- Medicion empirica documentada en S3

**Fuera de alcance**:

- NO requerir invocacion explicita (backwards compat — steps que no usen sintaxis canonical siguen funcionando como antes)
- NO migrar todos los agents a output schemas mas estrictos (mantener los existentes; tester usa el patron como referencia)
- NO implementar adapters de provider — Anthropic via Agent tool es el unico actualmente operativo; otros providers son "via API custom" como future path

**Propuesta** — dos dimensiones cohesivas:

### Dimension 1 — Abstraccion provider-agnostic via tiers semanticos

DKC define **tiers semanticos** (no modelos especificos) en config:

```yaml
# projects/{project}/config.yaml
roles:
  researcher: { tier: fast, max_tokens: 8000 }       # recoleccion + lookup
  scribe:     { tier: fast, max_tokens: 4000 }        # logs + edits puntuales
  developer:  { tier: balanced, max_tokens: 16000 }   # implementacion
  reviewer:   { tier: balanced, max_tokens: 8000 }    # criticismo
  architect:  { tier: reasoning, max_tokens: 16000 }  # razonamiento complejo
```

Mapping global por proveedor disponible (opcional — DKC puede inferir si el LLM principal sabe que proveedor tiene):

```yaml
# deckard/model_aliases.yaml  (global, fallback per-project)
tiers:
  fast:
    anthropic: claude-haiku-4-5
    openai: gpt-4o-mini
    google: gemini-1.5-flash
    mistral: mistral-small-latest
    local: llama-3.1-8b-instruct
  balanced:
    anthropic: claude-sonnet-4-6
    openai: gpt-4o
    google: gemini-1.5-pro
    mistral: mistral-large-latest
    local: llama-3.1-70b-instruct
  reasoning:
    anthropic: claude-opus-4-7
    openai: o1-preview
    google: gemini-2.0-flash-thinking
    mistral: mistral-large-latest
    local: deepseek-r1
```

Override per-project si se quiere lock a un modelo especifico:

```yaml
roles:
  architect:
    tier: reasoning
    model_override: claude-opus-4-7   # ignora alias, usa este modelo exacto
    provider: anthropic
```

**Por que tiers semanticos**:
- DKC no asume proveedor — funciona con Claude, GPT, Gemini, Mistral, locales
- Cambio de proveedor = 1 archivo (`model_aliases.yaml`), no N prompts
- Tickets DKC siguen referenciando `tier: fast` sin saber cual modelo concreto se uso
- Permite mezclar proveedores en un mismo proyecto (researcher=local Llama, architect=Claude Opus)

### Dimension 2 — Explorar context preservation

**Hipotesis**: distribuir el trabajo entre LLMs con context windows separados **alivia la presion sobre el LLM principal** (DET-15 protocolo de contexto agotado se activa menos).

Hoy:
- LLM principal (Claude Code, ~1M tokens) lleva TODO el contexto del ticket
- En tickets largos (HOR-022: 5h, 200K+ tokens), el window se aproxima al limite
- DET-15 fuerza persistir antes de pedir confirmacion

Con multi-LLM per rol:
- Researcher (LLM fast) recolecta info y entrega RESUMEN al architect
- Architect (LLM reasoning) recibe resumen, no contexto completo del codebase
- Developer (LLM balanced) recibe contract del architect, no reasoning del researcher
- Reviewer (LLM balanced) recibe payload + validation context, no contract original

Cada agent tiene su **propio context window** — el contexto DKC persiste en filesystem (records), no en una conversation. El LLM principal solo orquesta — su context se usa para handoffs, no para acumular detalle.

**Predicciones a validar empirico durante el ticket**:
1. Tokens del LLM principal por ticket bajan ~50-70% (la mayor parte va a agents)
2. Tickets largos completan sin trigger DET-15 (no se llega al limite del principal)
3. Calidad de outputs por rol no se degrada (tier semantico mantiene capability matching)
4. Costo total puede no bajar (haiku barato + sonnet medio + opus poco) — el ROI principal es **context preservation + escalabilidad**, no solo cost

**Metrica a registrar en HOR-025 mismo**:
- Tokens consumidos antes (HOR-022 baseline) vs despues (proximo ticket grande)
- Numero de DET-15 activations en proximos 3-5 tickets

**Alcance**:

- `deckard/model_aliases.yaml` (nuevo, global): mapping tier → modelo por proveedor
- `projects/{project}/config.yaml`: seccion opcional `roles:` con tiers semanticos + override
- `prompts/steps/*.md`: al invocar Agent, leer config del proyecto + alias → modelo concreto
- `prompts/agents/*.md`: cada agent doc recomienda tier default
- Documentar en `prompts/_style.md` Principio 8 (nuevo): seleccion por rol + tier
- **Componente exploratorio**: medicion empirica de context preservation en proximo ticket grande

**Fuera de alcance**:

- NO requerir multi-LLM — backwards compat (sin config.roles, LLM principal default)
- NO permitir override en runtime via prompts (config como fuente de verdad)
- NO implementar adapters de provider — DKC declara tier+modelo, LLM principal sabe como invocarlo (Agent tool, o futuras integraciones API)
- NO migrar tickets historicos a anotacion de tier — solo aplica forward

**Repos tocados**:

- `deckard` (`model_aliases.yaml` nuevo + `prompts/` + agents docs + config.yaml ejemplo en horadric)
