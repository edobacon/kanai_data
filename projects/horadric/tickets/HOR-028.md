# Entity tracking cross-ticket — piloto exploratorio en up1 (inspirado CrewAI entity_memory)

## Request

Patron CrewAI `entity_memory`: agents construyen tracking de entidades (personas, organizaciones, conceptos) que persisten cross-task. CrewAI las usa para que tasks futuras "recuerden" entidades sin re-extraerlas.

**Estado DKC actual**: rules + decisions + bugs son entidades — pero `decisions` son punto-en-el-tiempo, `rules` son contratos, `bugs` son patologias. **No hay entity tipo "concepto del dominio"** que se acumule.

**Observacion en up1 (curriculum-design)**: cada ticket repite definicion contextual de:
- `evaluation` (entidad academica)
- `competencia` (skill curricular)
- `actividad` (unidad academica)
- `workflow` (estado de aprobacion)
- `programa de asignatura` (documento canonical)

Hoy esos conceptos viven dispersos en `## Context found` de N tickets — el LLM re-extrae cada vez. **Up1 ticket-005**: 28 learns (record). **ticket-009**: 45 learns. Muchos son **re-definiciones del mismo concepto**.

**Propuesta** (exploratorio):

- Nueva capa `entities/` en cada proyecto: `projects/{project}/entities/{kind}-{slug}.md`
- Kinds posibles: `concept`, `actor`, `system`, `domain` (acotado)
- Entity record:
  ```yaml
  id: concept-evaluation
  kind: concept
  domain: academica
  related_specs: [SPEC-curriculum-eval-matrix]
  related_rules: []
  glossary: |
    Definicion canonical en 2-3 lineas.
  characteristics:
    - immutable_after_publish: true
    - reviewable: true
  related_entities: [concept-competencia, concept-actividad]
  ```
- Indexable en `index.db` (tabla nueva `entities`)
- `intake-explore` researcher consulta entities relacionadas al modulo del ticket antes de re-extraer

**Justificacion exploratoria**:

Es `explore` no `implement` porque:
- No esta claro si el patron paga en proyectos de meta-sistema (horadric) — alto overhead, poco contenido de dominio
- Up1 SP3 tiene volumen suficiente para validar (21 tickets, 7.7 learns/ticket avg)
- El patron de CrewAI viene de agents EFIMEROS — DKC ya tiene `Context found` que es similar; entidad seria capa adicional

**Decision a tomar en design-explore**: si el ROI real (en up1) justifica adoptar el patron, o si learns + rules + decisions de DKC cubren el mismo ground.

**Alcance del explore**:

- Survey de learns en up1 — identificar conceptos repetidos (candidatos a entidad)
- Diseno de schema entity record
- Piloto: 3-5 entities en up1 (curriculum-design)
- Medicion: tokens ahorrados en proximo ticket up1 al usar entities vs re-extraer
- Decision: implementar production-wide vs descartar

**Fuera de alcance** (del explore):

- NO implementar en horadric/bayley (proyectos meta-sistema, sin dominio rico)
- NO migrar learns historicos a entities (riesgo de mass-renaming sin valor)
- NO modificar HC viewer hasta validar patron (UI de entities = follow-up si vale la pena)

**Repos tocados** (del explore):

- `deckard/projects/up1/entities/` (nuevo directorio, 3-5 records piloto)
- Documento explore con findings + recomendacion

**Repos tocados** (si el explore convence — follow-up):

- `deckard` (schema + indexer extension + step researcher consulta entities)
- `horadric-cube` (HC viewer renderea entities — gran cambio de UI)

### Pregunta del pre-check

¿`dkc_semantic_search` (HOR-031, cerrado) ya recupera las definiciones canonicas de conceptos del dominio up1 → haria redundante la capa `entities/`?

### Metodo

1. Se genero el indice de embeddings de up1 (`embeddings.sqlite`, 9456 chunks: rules/decisions/bugs/specs/tickets/meta-specs — sin root docs) que **nunca habia existido** para up1.
2. Se consultaron 5 conceptos del dominio via el pipeline real de `dkc_semantic_search` (semantic + RRF).

### Evidencia (5/5 recuperaron material canonico desde specs)

| Concepto | Top hit | Calidad |
|----------|---------|---------|
| programa de asignatura | `specs/curriculum-design/programa-de-asignatura.md` **§ Definicion** (literal) | Perfecto |
| actividad academica | `overview.md` (+ nota rename `AcademicActivity → Activity`) + `SPEC-academic-activity-list.md` | Excelente |
| workflow states | `open-questions.md` (6 valores enum) + `BR-WKF-001` (enum canonico) | Excelente |
| competencia | `CAP-MAP-017` + objects-model snapshot + `ticket-005` | Bueno |
| evaluation | `CAP-CUR-037` (catalogo metodos) + `ticket-015` (clasificacion canonica) | Bueno |

### Conclusion

- Las definiciones canonicas **ya viven en las specs** (`curriculum-design/` es, de hecho, el glosario del dominio). Semantic search las recupera limpiamente.
- La capa `entities/` **duplicaria** lo que specs ya provee + lo que HOR-031 ya retorna. Delta residual (glosario corto + grafo `related_entities` + `characteristics`) marginal: la def de la spec ES el glosario; el grafo solapa con HOR-043; las caracteristicas viven como business rules (ej. BR-WKF-001).
- **El dolor de re-extraccion era REAL pero su causa era operacional**: up1 nunca tuvo embeddings generados → el researcher caia a grep y re-extraia. Se resolvio generando el indice (hecho en este pre-check). No requiere arquitectura nueva.

### Correccion de un hallazgo interino

Un muestreo intermedio (indice a medio construir) sugirio "semantic search no indexa tickets". **Falso** — los tickets SI se indexan (3377 chunks); el muestreo fue mid-run.
