# Explore Frente A cross-host — directive enforcement portable a multiples LLM hosts (reclasificado de improvement a explore)

## Request

**Derivado de HOR-050** (closed 2026-05-16, spec en draft). Implementa la **Solucion A** del SPEC-workflow-directive-enforcement-50 (DEC-LOCAL-01 — A+B+C combinados, cada uno en ticket independiente).

**Problema que resuelve**:

Las directivas en `prompts/steps/*.md` etiquetadas `<!-- enforcement: a-hook -->` (estimado ~40% de las ~90 totales = ~36 directivas) son **ejecutables como comando directo** (`./commands/dkc-reindex`, `./commands/dkc-validate <kind>`, MCP calls especificas). Hoy dependen de disciplina del LLM — observado ~80% skip rate (D2 capturado en HOR-046 backlog).

**Solucion A**: hook engine en Claude Code via `.claude/settings.json` PostToolUse / PreToolUse que dispara el comando declarado tras el step relevante.

**Plan tentativo (refinable en intake-explore)**:

1. **Etiquetado canonical**: agregar `<!-- enforcement: a-hook command: "..." -->` antes de cada directiva ejecutable directa
2. **Hook wrapper bash/tsx**: script en `.claude/hooks/dkc-enforcer` que detecta el step ejecutado + parsea las etiquetas + dispara los comandos
3. **`.claude/settings.json` config**: `PostToolUse: { Edit: ".claude/hooks/dkc-enforcer step-context" }`
4. **Tests**: idempotencia (multi-fire del hook no rompe), latencia (< 1s por hook simple)
5. **Documentacion**: README en `.claude/hooks/` para el dev

**Acceptance criteria (de NFR del spec)**:
- Auto-reindex skip rate: ~80% → < 5%
- Latency hook simple: < 1s
- Tests pass + zero regresion en steps actuales

**No es alcance**:
- Solucion B (protocolos ejecutables — HOR-052)
- Solucion C (validator post-step — HOR-053)
- Refactor masivo de prompts (Solucion B problem)

### Hipotesis (v2 cross-host)

| H | Enunciado | Status | Evidencia (multi-capa) |
|---|-----------|--------|------------------------|
| H1 | El catalogo machine-readable de directivas (comment HTML `<!-- enforcement: a-hook command: "..." -->`) es portable a 100% de LLM hosts — solo cambia el ejecutor del catalogo, no el catalogo en si | ✓ confirmada | **meta**: HTML comments son estandar markdown universal. Cualquier parser (incluido el del LLM que lee el archivo) puede detectarlos. **arquitectura**: separar "que" (catalogo) de "como" (ejecutor) es el patron clasico de portabilidad. DEC-LOCAL-02 del spec parent HOR-050 ya elige este formato |
| H2 | Existen al menos 3 approaches viables para el "ejecutor" del catalogo, cubriendo el espectro de portabilidad vs automaticidad: (a) host-native hooks Claude Code, (b) file watcher daemon host-agnostic, (c) wrapper CLI manual invocado por el LLM, (d) MCP tool dedicado, (e) git hook post-commit, (f) interface abstracta con adapters | inferred | **meta**: cada approach corresponde a un punto de integracion distinto (settings.json, filesystem, LLM tool call, MCP protocol, git lifecycle, abstraction layer). **arquitectura**: trade-off claro entre "automatico pero acoplado" (a) y "manual pero universal" (c). Validable en exploracion comparativa de S1 |
| H3 | El approach mas portable host-agnostic es **file watcher daemon** (fswatch macOS / inotify linux) — observa filesystem y dispara comandos. Funciona con cualquier LLM porque NO requiere integracion con el LLM | inferred | **meta**: file watchers son tecnologia madura (fswatch, inotify, chokidar). **arquitectura**: el LLM solo necesita escribir archivos — cualquier LLM hace eso. Trade-off: requiere proceso daemon corriendo en background (lifecycle management) |
| H4 | LLM-local con context chico (Qwen3-local con ~32K efectivo) fallara mas que Claude (200K) en interpretacion de directivas declarativas — el approach correcto debe asumir este caso, no solo el Claude actual | ✓ confirmada direccional | **meta**: HOR-046 D11 medio 97.5% inline con Claude (1/40+ AGENT INVOCATION reales). **inferencia**: si Claude con 200K falla 97.5%, Qwen con 32K efectivo fallara mas. **evidencia HOR-029**: proyeccion 25-30% ahorro context via subagents aislados depende criticamente de enforcement. **conclusion**: el target del approach es **NO depender de la disciplina del LLM**, sea cual sea su context size |
| H5 | MCP tool dedicado (`mcp__deckard-cain__dkc_enforce_step`) es un sweet spot: el LLM lo invoca explicito como tool call (estandar abierto, portable a cualquier MCP client), el tool ejecuta el catalogo declarado por el step. Mas portable que (a), mas automatico que (c) | inferred | **meta**: MCP es estandar abierto del ecosistema Anthropic + comunidad. **integracion**: deckard-cain ya tiene MCP server propio (28 tools). Agregar 1 tool mas es trivial. **trade-off**: requiere que el LLM invoque el tool — si olvida, perdemos enforcement (volvemos al problema D2). Mitigacion: explicit en el step prompt + validator C secundario |
| H6 | Interface abstracta con adapters por host (a la "JDBC para LLM hosts") es over-engineering si solo hay 1 adapter implementado hoy. Debemos disenar simple primero, abstraer despues cuando emerja segundo adapter | ✓ confirmada | **meta**: principio YAGNI (You Aren't Gonna Need It). **historia**: deckard ya hizo HOR-029 mapping host con tabla simple por role; no se hizo abstraccion premature. **conclusion**: empezar con un adapter concreto + catalogo universal. La abstraccion emerge si se implementa segundo adapter |
