# Fix: HC y request-execute no reflejan sessions/tasks en progreso (parser `[~]` + prompt)

## Request

> *(Peticion original del dev, 2026-05-17)*
>
> revisa en dkc y hc, porque sigue pasando que al avanzar un ticket, las sesiones no se van actualizando segun el avance, no se ponen en ejecucion hasta que termina la sesion o hasta que termina todo. ¿es error de como se registra? ¿de como se lee? ¿del llm que evita registrar? ¿de la actualizacion o lectura desde hc? abarca todos los puntos de analisis posibles, es algo recurrente que no hemos podido arreglar hasta ahora.

Diagnostico previo (en chat) identifico 4 capas. **HOR-040 (closed 2026-05-16) ya resolvio la Capa 2** (SSE + chokidar + re-render solo `## Sessions`). El alcance real de este ticket queda en:

- **A** — Capa 1: parser HC en `horadric-cube/server/deckard/sessions.ts:901` no captura `- [~]` (in_progress). Regex literal `^\s*[-*]\s*\[(x|X|\s)\]\s+(.*)$` matchea solo `x|X|\s` — tasks con `[~]` retornan `null` del match, se hacen `continue`, desaparecen del array `tasks`. Comentario en `sessions.ts:503-508` documenta el gap: "Para soportar [~], extractTasksFromContent se extiende abajo" — la extension nunca se hizo. Linea 509: `const status: StepStatus = task.checked ? 'executed' : 'pending'` — solo binario aunque el tipo soporta `'in_progress'`.
- **B** — Capa 3: `prompts/steps/request-execute.md` no instruye al LLM transicionar checkbox `- [ ]` → `- [~]` al abrir una task ni `- [~]` → `- [x]` al cerrar. Linea 217 explicita: *"NO marcar el checkbox como `[x]` aun (eso es responsabilidad del scribe en gate D, despues de que el reviewer confirme `approve`)"* — no contempla un estado intermedio. El propio prompt (linea 344) admite que el LLM "salta el registro para avanzar con la implementacion".
- **C** — Capa 5 (descubierta durante intake 2026-05-17): frontmatter `status` del ticket no fluye per-step. HC viewer ya tiene constantes `INTAKE_STATUSES = {'intake-explore', 'teach-intake', 'design-fix', ...}` y `EXECUTION_STATUSES = {'request-execute', 'in_progress', 'request-close'}` en [TicketsBoard.vue:103-123](horadric-cube/src/views/TicketsBoard.vue:103) — pero ningun step deckard escribe esos valores al frontmatter. El ticket permanece `status: open` durante todo el flujo intake/design/teach hasta que `request-execute` lo cambia a `in_progress`. Resultado: el ticket aparece en columna **Registro** del kanban aunque ya este en `design-fix`. Patron identico al sintoma original — feature listada en codigo HC pero huerfana sin cableado en prompts deckard.
- **D** — Capa 6 (descubierta durante S2 feedback 2026-05-17): **enforcement estructural ausente**. Las capas A+B+C dependen de que el LLM siga el prompt. `request-execute.md:344` admite el patron "el LLM salta el registro para avanzar con la implementacion". Sin mecanismo que FUERCE la sincronizacion entre spec.Status / ticket.checkbox / frontmatter.status, el bug recurrente vuelve. Causa raiz real del problema persistente. **Fix**: tool MCP dedicado `dkc_set_task_state` (atomic edit checkbox + status spec) + `dkc_set_ticket_status` (atomic edit frontmatter) que reemplazan Edit libre, validator `dkc-validate SessionCheckboxes` que detecta drift, a-hook que bloquea Gate D si validator falla. Opcion D4 elegida por el dev (2026-05-17).

**Confirmacion adicional (render no es bloqueante)**: `horadric-cube/src/components/ticket-sections/SectionSessions.vue:85` define `stepStatusMeta: Record<StepStatus, ...>` que incluye `in_progress`. Lineas 311, 407, 430 aplican `animate-spin` cuando `status === 'in_progress'`. **El render ya esta listo — fixear el parser desbloquea automaticamente la UI** sin tocar componentes.
