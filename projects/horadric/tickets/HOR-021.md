# Templates DKC project-scoped: convencion + ciclo de vida + visualizacion en HC

## Request

Crear un nuevo tipo de artefacto DKC: **templates project-scoped** que viven dentro de DKC pero son especificos del producto (no globales). Setear la convencion + ciclo de vida completo (creacion, consumo, validacion, actualizacion) + visualizacion en HC viewer.

### Origen del request

Durante el cierre de S15 del TICKET-019 (HU4 en up1), se identificaron 4 patrones de codigo recurrentes en mods de up1 (mod-object-definition, mod-resolver-validated, mod-schema-graphql, mod-seed) que viven inline como ejemplos en rules (`rule-mods-002/004/006/008`, `rule-curriculum-design-003`) pero NO existen como templates ejecutables. El dev (Eduardo) pidio crear el espacio para estos templates, con la condicion de que viva en DKC pero sea exclusivo del producto up1.

Tras analisis, ningun espacio actual encaja:
- `deckard/templates/` es agnostico al producto (artefactos DKC workflow)
- `up1/mods/hello-world-mod/` es un ejemplo funcional completo, no snippets aislados
- `up1/.ai/templates/` viviria en el monorepo, no en DKC
- `up1/templates/` requiere cambio top-level del monorepo

La decision es **crear convencion DKC nueva** `deckard/projects/{project}/templates/` (simetrica con `tickets/`, `specs/`, `rules/`) que **otros proyectos DKC pueden adoptar opcionalmente sin afectar a los no-relacionados**.

### Session 0 — Discovery: resolucion empirica Q1+Q3+Q5 pre-design (2026-05-15) [phase: intake]

**Objetivo**: resolver las 3 open questions bloqueantes (Q1 validates_against syntax, Q3 SQLite schema, Q5 last_validated flow) mediante inspeccion empirica antes de invocar teach-intake + design-draft. Asi el teach-intake captura decisiones tomadas con evidencia, no hipotesis abiertas.

**Discoveries cronologicos:**

1. **2026-05-15 — Q3 SQLite schema: tabla generica `records` discriminada por `type`** (RESUELTA)
   - **Fuente**: `deckard/templates/schema.sql` linea 9-32
   - **Evidencia**: schema actual tiene tabla unica `records` con columna `type` que discrimina los record types existentes (rule, bug, spec, decision, ticket, meta-spec). NO hay tablas tipadas por record type.
   - **Implicancia para F7**: agregar `template` como nuevo type discriminator NO requiere migration destructiva. Solo:
     - Bump `schema_version` 3 → 4 (linea 113)
     - Agregar columna `last_validated TEXT` (nullable, solo populada en records con type='template')
     - El MCP server `deckard_cain` debe aceptar `type='template'` en sus tools (`dkc_index_record`, `dkc_find_records`, etc.)
   - **Mapeo de campos especificos de templates a schema generico**:
     - `applies_to` → cabe en `tags` (JSON array, ya soportado)
     - `referenced_rules` → cabe en tabla `relations` con `type='references'` y `from_id=template_id, to_id=rule_id`
     - `consumed_by` → cabe en `tags` (informativo, no FK validable)
     - `validates_against` → vive SOLO en markdown frontmatter, NO en SQLite (no se busca por bash inline)
     - `last_validated` → columna nueva en `records` (nullable, scope: solo templates)
     - `related_tickets` → cabe en tabla `relations` con `type='discovered_in'` ya existente
   - **Decision**: opcion A (minimal migration) confirmada como aproach correcto.

2. **2026-05-15 — Q1 validates_against syntax: bash inline (idiomatic DKC)** (RESUELTA)
   - **Fuente**: inspeccion de patrones existentes en `deckard/prompts/` + `deckard/projects/up1/rules/`
   - **Evidencia**:
     - Rules existentes usan `## Verification` con instrucciones + comandos bash inline (ej: `rule-dev-001.md` "`./up1-start.sh --status` debe mostrar los servicios esperados como activos")
     - DKC prompts usan `grep -E` directo (ej: `request-close.md:288` `grep -cE "^### Session [0-9]"`, `_design-shared.md:55` `grep -E "^### Session [0-9]+" projects/{project}/tickets/{TICKET-id}.md`)
     - Zero precedentes de DSL declarativa de validacion en el codebase DKC
   - **Trade-offs evaluados**:

   | Approach | Pros | Contras | Decision |
   |----------|------|---------|----------|
   | **Bash inline** | Idiomatic DKC. Cero abstraccion. Ejecutable directo. Consistente con `## Verification` de rules. | Shell-dependent (mac/linux). No portable a Windows nativo. Si script crece, hard to test | **ELEGIDO** |
   | Script separado | Testeable independiente. Reusable cross-templates | Requiere I/O extra. Frontmatter solo guarda path, no logica | Escape hatch: bash inline puede invocar `bash projects/{p}/templates/validators/{t}.sh` |
   | DSL declarativa (JSON con must_match/must_not_match) | Portable. Parsable estatico | Parser custom. Limitada expresividad. Overkill | Descartada — sin precedente |
   | AST parsing (tree-sitter/babel) | Robusto, sin false positives | Setup pesado. Overkill para casos simples | Descartada — out of scope |
   - **Decision**: **bash inline en frontmatter del template**. Si un template requiere logica compleja, invoca script separado desde el bash inline (escape hatch documentado). Frontmatter shape:

     ```yaml
     validates_against: |
       for f in mods/*/logic/*Validated*.resolver.js; do
         grep -E "export const [a-zA-Z]+Validated" "$f" >/dev/null || { echo "FAIL: $f no expone *Validated"; exit 1; }
         grep -E "prisma\.\w+\.(create|update|delete)" "$f" >/dev/null || { echo "FAIL: $f no delega a CRUD generic"; exit 1; }
       done
     ```

   - **Pre-condicion**: el step F3 ejecuta el bash inline con `bash -c "$validates_against"` desde el cwd del repo del proyecto (resuelto via `config.yaml.repo.path`). Exit code 0 = sin drift; exit != 0 = drift detectado.

3. **2026-05-15 — Q5 last_validated flow: automatico desde F3 cuando validacion pasa** (RESUELTA)
   - **Fuente**: derivado de la decision Q1 (bash inline ejecutable directo)
   - **Decision**: `last_validated` se actualiza **automaticamente** por F3 (step `validate-templates`) en estos casos:
     1. F3 itera todos los templates del proyecto activo
     2. Para cada template, ejecuta su `validates_against`
     3. Si exit 0 (sin drift) → actualizar frontmatter `last_validated: $(date -I)` (formato ISO YYYY-MM-DD)
     4. Si exit != 0 → reportar drift, NO actualizar `last_validated` (preserva el ultimo valor)
   - **F6 (update-template) actualiza `last_validated`** en escenario distinto:
     - Trigger: drift legitimo (template stale, codigo evoluciono y debe ser la nueva norma)
     - F6 regenera el contenido del template desde el codigo + actualiza `last_validated` + crea `DECISION-{id}` que documenta la evolucion
   - **Implicancias UI (F8 HC viewer)**:
     - `last_validated` reciente (< 7 dias) → template fresco — chip verde
     - `last_validated` 7-30 dias → template tibio — chip amarillo (sugerir re-validar)
     - `last_validated` > 30 dias o `null` → template potencialmente stale — chip rojo
     - Auto-refresh: HC viewer puede invocar el step F3 desde un boton "Validate now" en TemplateDetail (opcional, decision en design)
