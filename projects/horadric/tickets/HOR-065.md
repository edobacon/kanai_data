# Auditoria operacional de flujos DKC — contrato estricto para que el LLM ejecutor no salte pasos ni divergencia de formato

## Request

**Peticion del dev (2026-05-23)**: revisar todos los flujos DKC para verificar si la estructura actual previene que el LLM ejecutor (a) se salte pasos informativos y (b) escriba datos en formatos distintos a los que HC viewer espera. La observacion es que el problema persiste cronicamente: HOR-058 (saltar DET-25/27), HOR-064 (falso positivo del drift detector), HOR-062 (banner amber del drift) ya atacaron casos puntuales, pero el sintoma reaparece. Hay que auditar sistematicamente y proponer un contrato estricto que el LLM no pueda saltar.

**Diferencia con HOR-015** (audit previo cerrado 2026-05-10): HOR-015 ataco la capa **estructural** — peso de prompts, asimetria de DETs declaradas vs implementadas, granularidad de sessions en HC, sync CLAUDE.md global. Este ticket ataca la capa **operacional** — dado el diseño que existe HOY (post HOR-015..064), ¿que pasos concretos del flujo siguen siendo interpretables y se saltan en la practica? El alcance temporal es distinto: HOR-015 vio el sistema 50 tickets atras; HOR-065 ve el estado actual con DET-29 reciente y la triada execute (`dkc-execute-task` + `dkc-verify-gate` + a-hooks) ya consolidada.

**Modo de operacion**: autopilot on, teach off. El dev confio en autovalidacion de gates auto + el spec output mismo como material de referencia.

**Alcance acordado** (dev decision 2026-05-23): "Deckard + contrato HC viewer" — auditar (a) los 25 steps en `prompts/steps/`, (b) las 29 DETs en `prompts/deterministic-rules.md`, (c) los commands/validators en `commands/`, Y (d) los parsers de HC viewer en `horadric-cube/server/deckard/` que definen el formato esperado del markdown. NO incluye analisis cuantitativo de tickets historicos (descartado para mantener ~5 SP).

## Addendum 2026-05-23 — diagnostico revisado por HOR-066

> Esta seccion es **aditiva** (preserva DET-3: inmutabilidad del request original) y documenta que el diagnostico principal del audit fue revisado en HOR-066 S0 con evidencia empirica directa.

### Que se reviso

El audit de HOR-065 reporto en L3 que "13 de 17 validators referenciados en a-hooks no existen". HOR-066 S0 (2026-05-23) realizo verificacion empirica directa sobre `commands/lib/` con node 22 (no v10 como tenia el shell del dev cuando se hizo el audit original).

### Que cambio

**Diagnostico revisado** (HOR-066 L7-L11):

- **16 de 17 validators YA EXISTEN** en `commands/lib/schemas/` + dispatch en `validate.ts`. SOLO `StatusCoherence` realmente faltaba (implementado en HOR-066 S2.T1).
- El **"bug del parser YAML inline"** (HOR-065 L6) NO era un bug del parser zod. Era node v10 activo en el shell del dev: `tsx` requiere Node 18+ para parsear ES module syntax (`import { ... }`). Con `nvm use 22` el validator funciona perfecto sobre tickets con frontmatter `teachings: { ... }` inline.
- El **gap real** era el wrapper bash `commands/dkc-validate`: Usage hardcoded con solo 4 kinds (resuelto en HOR-066 S1.T1) + no validaba node version (resuelto en HOR-066 S1.T2).
- **Patron meta**: el audit de HOR-065 fue victima exacta del problema que estaba auditando — "el LLM lee un contrato declarativo (Usage del wrapper bash) y razona en base a el sin verificar empiricamente". Lesson learned para futuros audits: verificacion empirica directa antes de declarar gaps.

### Scope real entregado

**HOR-066** (cerrado 2026-05-23, SPEC-workflow-cli-wrapper-fix-and-status-coherence-66 done):

- S1: fix wrapper bash con auto-switch nvm + 17 kinds en Usage + docs Node 22+
- S2: `StatusCoherence` validator implementado + fix enum `executed_method` (sincronizado template ↔ schema)
- S3: RULE-workflow-enforcement-pattern-009 (formaliza patron de 5 capas)

**SP gastados**: 6 estimated, ~6 executed. Vs 18 SP que habria implicado si el diagnostico original (13 validators a implementar) se hubiera ejecutado sin revisar.
