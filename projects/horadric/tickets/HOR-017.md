# Universalizar DKC para LLMs con agentes o comandos

## Request

Registrar para futuro una mejora de arquitectura: hacer que Deckard Cain pueda funcionar de forma portable en cualquier LLM que soporte agentes, comandos o MCP, reduciendo la dependencia de slash commands y prompts interpretativos. No es prioridad ahora. Contexto del analisis: la forma actual ya es parcialmente portable porque existen prompts markdown, slash commands, MCP tools dkc_*, agents por rol y fallbacks por edicion manual, pero hay drift entre commands/dkc.md, INSTALL.md y dkc_get_workflow(), y la orquestacion vive demasiado en prompts largos. Objetivo futuro: mover DKC hacia un contrato runtime/manifest canonical con entrypoints como dkc_route(request), dkc_capabilities(), dkc_install_check(), dkc_next_action(), workflows parseados desde YAML/manifest como fuente unica, modos de host slash/mcp/agent/single/manual, y agentes expresados como contratos con input schema, output schema, allowed operations y escalation conditions. Estimacion registrada: MVP portable 1-2 dias; bueno para varios LLMs 3-5 dias; robusto/universal 1-2 semanas; runtime serio 3-5 semanas. Recomendacion por fases: 1 eliminar drift y fuente unica para intents/comandos/workflows; 2 agregar host modes y health checks; 3 convertir agentes en contratos portables; 4 opcional runtime/orquestador que pueda delegar pasos.

### Context found

#### Estado actual observado

- DKC tiene **tres superficies de uso**:
  - Slash commands: `commands/dkc*.md` para hosts tipo Claude Code.
  - MCP tools: `dkc_status`, `dkc_get_workflow`, `dkc_find_*`, `dkc_create_record`, `dkc_append_session_log`, etc.
  - Fallback markdown/manual: prompts describen como editar archivos si MCP no esta disponible.
- El server MCP existe y funciona, pero actualmente expone operaciones atomicas/mecanicas mas que un runtime de orquestacion completo.
- `prompts/agent-tiers.md` ya separa tiers de capacidad de modelos concretos, lo que ayuda al objetivo LLM-agnostico.
- `prompts/workflows/request.md` ya tiene frontmatter/YAML de workflow, pero `dkc_get_workflow()` mantenia una copia manual en Python.
- `commands/dkc.md` es el entrypoint humano actual: saluda, clasifica intencion y decide el flujo. Esa logica todavia no esta disponible como tool canonico tipo `dkc_route(request)`.

#### Diagnostico principal

DKC es portable **a medias**:

- Portable para LLMs capaces de leer prompts largos, seguir instrucciones y usar tools.
- Menos portable para hosts que necesitan contratos estructurados, manifests, schemas o un protocolo claro de "next action".
- El riesgo principal no es falta de capacidades, sino **drift y ambiguedad de orquestacion**: slash command, workflow markdown, docs de instalacion y MCP router pueden divergir.

#### Objetivo arquitectonico futuro

Mover DKC hacia un modelo **runtime-first, prompt-second**:

```text
Host LLM
  -> dkc_status()
  -> dkc_route(user_request)
  -> dkc_get_step(step_id)
  -> ejecuta con tools propias
  -> dkc_record_progress(...)
  -> dkc_next_action(...)
```

Los prompts seguirian existiendo, pero como material de ejecucion/explicacion. La fuente canonica de comandos, intents, workflows, gates y roles deberia ser estructurada.

#### Cambios sugeridos

1. **Entrypoint unico de routing**
   - Agregar `dkc_route(request: str)` para devolver `intent`, `confidence`, `workflow`, `next_step`, `required_context`.
   - Evitar que cada host reinterprete `commands/dkc.md`.

2. **Manifest de capacidades**
   - Agregar `dkc_capabilities()` con:
     - comandos soportados
     - intents validas
     - tools requeridas/opcionales
     - modos de host soportados
     - fallbacks disponibles

3. **Health check de instalacion**
   - Agregar `dkc_install_check(host_mode)`:
     - MCP cargado
     - `DECKARD_ROOT` correcto
     - proyecto activo
     - index presente/fecha
     - workflows parseables
     - commands instalados si aplica

4. **Fuente unica para workflows**
   - Parsear `prompts/workflows/*.md` desde frontmatter/YAML.
   - Eliminar copias hardcodeadas en `dkc_get_workflow()`.
   - Validar drift automaticamente.

5. **Modos de host**
   - `slash`: host con comandos tipo `/dkc`.
   - `mcp`: host con tools MCP pero sin slash commands.
   - `agent`: host con subagentes/delegacion.
   - `single`: host sin subagentes, ejecuta roles secuencialmente.
   - `manual`: sin MCP, edicion markdown + helpers CLI.

6. **Agentes como contratos portables**
   - Para cada rol declarar:
     - input schema
     - output schema
     - allowed operations
     - forbidden operations
     - escalation conditions
     - handoff schema
   - Mantener el prompt narrativo como guia, no como unica fuente de contrato.

7. **Runtime/orquestador opcional**
   - Futuro no-MVP: `dkc_next_action()` y, eventualmente, `dkc_delegate(tier, task)`.
   - Permite que incluso un host limitado ejecute DKC de forma guiada.

#### Analisis de casos por tipo de LLM/host

El objetivo no es cambiar la experiencia DKC, sino **preservar la misma experiencia conceptual** en hosts distintos:

- El dev pide algo en lenguaje natural.
- DKC detecta proyecto/ticket/contexto.
- DKC clasifica intencion.
- DKC crea o retoma ticket.
- DKC ejecuta intake -> intake-explore -> teach-intake -> design -> execute -> close con gates.
- DKC registra conocimiento en markdown/index.
- El dev ve progreso claro en HC.

La diferencia entre hosts debe ser solo el **adaptador de entrada/salida**, no el comportamiento de fondo.

##### Caso A: Host con slash commands y tools completas (Claude Code-like)

**Estado actual esperado**: `/dkc`, `/dkc-learn`, `/dkc-sync`, `/dkc-space`, etc. siguen siendo la interfaz natural.

**Impacto del cambio**:

- `/dkc` deberia convertirse en wrapper de `dkc_route(request)` + `dkc_get_workflow(intent)`.
- Los archivos `commands/dkc*.md` dejan de ser fuente primaria de logica y pasan a ser interfaz/ayuda.
- La experiencia no cambia para el dev: sigue escribiendo `/dkc necesito...`.
- Se reduce drift porque el slash command lee manifest/runtime canonico.

**Riesgo**: si el wrapper queda demasiado delgado, puede perder tono/estilo Deckard. Mitigacion: mantener `DECKARD.md` y prompts como capa narrativa, pero no como fuente unica de routing.

##### Caso B: Host con MCP pero sin slash commands (Codex, Cursor, Windsurf-like)

**Estado actual esperado**: el LLM llama tools `dkc_status()` y `dkc_get_workflow(intent)`, pero debe interpretar docs/prompts para clasificar y avanzar.

**Impacto del cambio**:

- El host deberia iniciar con `dkc_status()` y luego `dkc_route(user_request)`.
- `dkc_route` devuelve el proximo paso y los prompts/contratos que debe leer.
- `dkc_next_action()` evita que el host tenga que reconstruir si esta en intake, design, execute o close.
- `dkc_install_check("codex")` detecta si MCP esta cargado, root correcto, proyecto activo, index y workflow disponibles.

**Experiencia buscada**: el usuario no deberia notar que Codex no tiene slash commands. Puede escribir "dkc, retomemos" o "necesito X" y el LLM usa MCP para replicar el mismo flujo.

**Riesgo**: hosts con reglas de herramientas diferentes pueden no editar archivos igual que Claude. Mitigacion: MCP debe cubrir operaciones mecanicas importantes (`create_record`, `append_session_log`, `update_task_status`, etc.) y documentar fallback manual.

##### Caso C: Host con agentes/subagentes (Codex con spawn_agent, opencode si soporta agentes, otros agent runners)

**Estado actual esperado**: DKC define roles, pero la delegacion depende de que el host entienda los prompts de agentes.

**Impacto del cambio**:

- Cada agente debe tener contrato estructurado:
  - input
  - output
  - allowed operations
  - forbidden operations
  - escalation conditions
  - handoff schema
- El runtime entrega al host un "agent task packet" portable.
- El host puede delegar a subagentes reales cuando existan.
- Si no puede, cae a modo `single` sin cambiar el workflow.

**Experiencia buscada**: el dev ve los mismos roles DKC (researcher, architect, developer, reviewer, scribe), pero el host decide si los ejecuta en paralelo, secuencial o con subagentes reales.

**Riesgo**: paralelismo puede romper orden de gates si el host delega demasiado pronto. Mitigacion: `dkc_next_action()` y schemas de handoff deben declarar dependencias y pasos bloqueantes.

##### Caso D: Host sin agentes, pero con comandos o tools basicas

**Estado actual esperado**: un solo LLM ejecuta todos los roles leyendo prompts.

**Impacto del cambio**:

- Modo `single`: el runtime devuelve una lista secuencial de roles/acciones.
- No se requiere paralelismo.
- Los contratos de agentes ayudan igual porque definen salida esperada.

**Experiencia buscada**: misma disciplina DKC, menor performance. El dev no debe tener que entender la diferencia.

**Riesgo**: el LLM puede saltarse registros por fatiga/contexto. Mitigacion: gates mecanicos obligatorios y `dkc_sync`/`dkc_next_action` para reentrada.

##### Caso E: Host sin MCP, solo comandos/prompts markdown

**Estado actual esperado**: usar slash commands o copiar prompts; persistencia via edicion manual y helpers CLI.

**Impacto del cambio**:

- Manifest exportable en markdown/JSON.
- Commands siguen funcionando como interfaz standalone.
- Helpers CLI (`dkc-reindex`, `dkc-active-ticket`, `dkc-export-rules`) siguen siendo escape hatch.

**Experiencia buscada**: degradacion aceptable, no primera clase. Mantener compatibilidad, pero no optimizar aqui primero.

**Riesgo**: alto drift si no hay MCP. Mitigacion: `dkc-export-manifest` o snapshot generado desde fuente canonica.

##### Caso F: opencode / hosts de agente con comandos propios

**Supuesto a validar en el futuro**: opencode puede tener un modelo de comandos/agentes distinto a Claude/Codex.

**Impacto del cambio**:

- Si soporta comandos: mapear comandos propios a `dkc_route` y `dkc_get_step`.
- Si soporta agentes: usar contracts de roles.
- Si soporta tools MCP: camino igual a Codex.
- Si soporta config de proyecto: instalar `DECKARD.md` + manifest del host.

**Experiencia buscada**: no crear una variante "DKC opencode" con reglas divergentes. Crear un adapter que consuma la misma fuente canonica.

##### Invariantes de experiencia

Estos comportamientos deben mantenerse iguales en todos los hosts:

| Invariante | Razon |
|------------|-------|
| KB-first antes de proponer | Evita trabajo en vacio y mantiene DKC spec-driven |
| Intencion clasificada antes de actuar | Evita flujo incorrecto |
| Request original inmutable | DET-3, trazabilidad |
| Intake-explore antes de design | Reduce supuestos y confirma hipotesis |
| Teach-intake antes de design cuando aplica | El dev entiende contexto antes de decidir |
| Design-draft cuando crea visual/data | Evita retrabajo caro |
| Execute con registro por task | Evita perdida de conocimiento |
| Gates de reviewer/scribe | Evita cerrar sin evidencia |
| Reentrada por markdown/index, no por memoria del chat | Soporta compactacion y cambio de LLM |
| HC como superficie de lectura del dev | La KB debe ser navegable, no solo archivos internos |

##### Matriz de compatibilidad objetivo

| Host/capacidad | Entrada | Orquestacion | Agentes | Persistencia | Experiencia objetivo |
|----------------|---------|--------------|---------|--------------|----------------------|
| Claude Code-like | slash commands | `dkc_route` bajo `/dkc` | nativos/por prompt | MCP + markdown | igual que hoy, menos drift |

##### Preguntas abiertas para el futuro design

- ¿El status del ticket debe representar etapa exacta (`intake-explore`, `teach-intake`, `design-*`) o solo macro estado (`open`, `in_progress`, `closed`) + campo separado `phase`?
- ¿`dkc_route` debe usar reglas deterministicas simples o puede invocar LLM/classifier?
- ¿`dkc_next_action` debe persistir estado propio o inferir siempre desde markdown/index?
- ¿Los contratos de agentes viven en frontmatter de `prompts/agents/*.md` o en un manifest separado?
- ¿Cuanto debe ejecutar el MCP server por si mismo vs solo guiar al host?
- ¿Como se valida que un adapter nuevo preserve la experiencia DKC y no cree una variante incompatible?

#### Impacto esperado en instalacion

Este cambio probablemente requiere actualizar la instalacion de DKC. No basta con agregar tools nuevas: cada host necesita saber **como engancharse a la misma fuente canonica** sin duplicar reglas.

##### Instalacion actual

| Host | Instalacion actual | Limitacion |
|------|--------------------|------------|
| Claude Code-like | MCP + copiar/linkear `commands/dkc*.md` + agregar `DECKARD.md` a instrucciones | Slash commands son primera clase, pero pueden divergir del MCP router |
| Codex-like | MCP en `~/.codex/config.toml` + instrucciones persistentes/manuales | No hay slash commands; depende de que el LLM recuerde llamar `dkc_status`/`dkc_get_workflow` |
| Cursor/Windsurf-like | MCP + `.cursorrules`/`.windsurfrules` | Similar a Codex, sin entrypoint canonico de routing |
| Host sin MCP | Copiar prompts/commands + helpers CLI | Mucho riesgo de drift y registros manuales incompletos |

##### Cambios de instalacion a evaluar

1. **Manifest canonico instalable**
   - Nuevo archivo generado o mantenido: `deckard/manifest.json` o `deckard/dkc.manifest.yaml`.
   - Contenido:
     - comandos
     - intents
     - workflows
     - steps
     - agents
     - host modes
     - required tools
     - fallbacks
   - Todos los adapters leen este manifest.

2. **Health check por host**
   - `dkc_install_check(host_mode)` o CLI equivalente:
     - `dkc install-check codex`
     - `dkc install-check claude`
     - `dkc install-check opencode`
   - Debe detectar:
     - MCP configurado y reachable
     - `DECKARD_ROOT`
     - proyecto activo
     - index DB
     - commands instalados si el host usa slash
     - instrucciones `DECKARD.md` presentes o referenciadas
     - version del manifest compatible con server MCP

3. **Adapters de instalacion por host**
   - `install/codex.md` o seccion dedicada en `INSTALL.md`.
   - `install/claude.md`.
   - `install/opencode.md` cuando se valide el modelo de comandos/agentes.
   - Cada adapter debe explicar solo el pegamento del host; la semantica DKC viene del manifest.

4. **Exportadores**
   - `dkc-export-commands claude` para slash commands.
   - `dkc-export-rules` ya existe; evaluar si debe extenderse para Codex/opencode.
   - `dkc-export-manifest` para hosts sin MCP o para auditoria.

5. **Versionado de instalacion**
   - Agregar version de protocolo DKC:
     - `manifest_version`
     - `mcp_server_version`
     - `commands_version`
   - El health check debe advertir si hay mismatch.

- Un host nuevo debe poder responder "DKC esta listo" con un solo check.

- La instalacion no debe requerir copiar logica de workflow a mano.
- Los comandos slash, MCP tools y adapters deben apuntar a la misma fuente canonica.
- Cambiar un workflow debe invalidar o advertir instalaciones desactualizadas.
- La experiencia del dev debe seguir siendo: "invoco DKC y DKC sabe que hacer", no "leo diez archivos de instalacion".

## Summary

Ticket futuro para convertir DKC en una capa portable entre LLMs. No es prioridad actual.

Decision preliminar: no reescribir DKC; evolucionarlo por fases. La base existente sirve, pero hay que sacar la logica critica de orquestacion fuera de prompts interpretativos largos y llevarla a manifests/tools estructurados. El primer valor esta en eliminar drift y dar a cualquier host un protocolo claro: status -> route -> workflow/step -> record -> next action.
