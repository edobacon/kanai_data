# Async tasks paralelas dentro de session (inspirado CrewAI async_execution)

## Request

Patron CrewAI `async_execution: true` permite que tasks independientes corran en paralelo y el crew espera todas para consolidar. DKC actualmente ejecuta tasks dentro de una session estrictamente secuenciales — incluso cuando son independientes.

**Caso real**: HOR-022 S3 (F4 kanban — 1 archivo) y S4 (F3 teach skip — server+view) son independientes (no comparten archivos, ni rules cruzadas, ni dependencias). Si hubieran sido paralelas: ~30% del tiempo wall-clock del ticket ahorrado.

**Propuesta**:

- Agregar campo opcional `parallel_with: [S{N}.T{M}, ...]` en la columna de task contract del spec
- `design-{tipo}` decide al partir si tasks son paralelizables segun heuristica:
  - (a) no comparten archivos modificados (verificable via Files column)
  - (b) sus rules no se cruzan (verificable via Rules column)
  - (c) sus validation gates son independientes (no testean lo mismo)
  - (d) ningun task depende del output de otro (verificable via Depends on column)
- `request-execute.md` paso de ejecucion: si una task tiene `parallel_with`, invocar Agent tool en paralelo via mensaje con multiples tool_use blocks
- Quality review DET-23 de la session espera a TODAS las tasks paralelas antes de declararse

**Beneficio observable**: 
- Tickets multi-feature acotados (HOR-022 tipo) → 20-30% reduccion en wall-clock
- Tickets con migracion masiva (HOR-021 templates) → migrar grupos por modulo en paralelo

**Alcance**:

- `templates/records/spec.md`: columna `parallel_with` opcional en task table (12 cols si esta — `# | Task | source_ref | Agent | Depends on | parallel_with | Files | Validation | Rollback | Rules | Status | Session`)
- `prompts/steps/_design-shared.md`: heuristica de paralelizacion documentada como decision del architect
- `prompts/steps/request-execute.md`: ciclo por task soporta invocacion paralela (multiples Agent tool calls en un mensaje)
- HC viewer (opcional): renderear tasks paralelas visualmente agrupadas (mismo group color en SpecSessionTree)

**Fuera de alcance**:

- NO paralelizar sessions completas (DET-20 sigue secuencial por session)
- NO permitir paralelizacion de tasks que toquen mismo archivo (race conditions)
- NO inferir paralelizacion automatica al execute si el design no la declaro

**Repos tocados**:

- `deckard` (templates + prompts + opcional spec del shared)
- `horadric-cube` opcional (viewer parallel groups)

### Active questions (para design-improvement)

Las hipotesis convergieron sin gaps bloqueantes. Pero la investigacion revelo una **decision de diseno** que design-improvement debe resolver antes de tocar el template — el Request asume una 12va columna `parallel_with`, y eso colisiona con el shape canonico actual:

> **AQ-1 — Como expresar `parallel_with` sin romper el shape canonico de 11 columnas.**
> **Hecho**: el gate HOR-022 F8 (`_design-shared.md:64-66`) valida que la task table tenga 11 columnas con 6 obligatorias, y el viewer HC `SpecSessionTree.vue:94` expande exactamente 6 columnas conocidas. Agregar una 12va columna `parallel_with` (como propone el Request linea 50) obliga a tocar ambos: el gate de conteo y el parser/expand del viewer.
>
> Alternativas a evaluar en design (no decidir en intake):
> - **A) 12va columna** `parallel_with` — explicita y legible, pero rompe el shape de 11 y arrastra cambios al gate F8 + viewer (mayor blast radius; toca repo `horadric-cube`).
> - **B) Notacion inline en `Depends on`** — reutiliza una columna existente con un marcador (ej. `∥ S5.T2` = "corre en paralelo con"). Cero cambios al shape ni al viewer; semantica menos obvia.
> - **C) Anotacion fuera de tabla** — bloque `parallel_groups: [[S5.T1, S5.T2]]` bajo cada `### Session N`. No toca la tabla; el viewer lo ignora salvo que se extienda; agrupacion explicita.
>
> Esta decision define el alcance real de S1 (template) y si S4 (viewer) es necesario o no. Es decision MEDIANA (patron) — design-improvement la presenta al dev con pros/contras.
>
> **RESUELTA (2026-05-26) → Opcion C**: bloque `parallel_groups: [[S{N}.T{x}, S{N}.T{y}]]` declarado bajo cada `### Session N`, fuera de la tabla de tasks. Driver: minimo blast radius — cero cambios al shape de 11 columnas, al gate F8 ni al viewer; sin redundancia bidireccional (los grupos se declaran una vez). **Consecuencia en alcance**: el cambio queda contenido en repo `deckard` (template + `_design-shared.md` + `request-execute.md`). S4 (viewer HC) pasa a **opcional/diferible** — el viewer puede ignorar `parallel_groups` sin romperse; renderizarlo es mejora cosmetica posterior, no requisito.

> **AQ-2 — Registro de evidencia DET-25 por task paralela.** Cada task paralela debe registrar su evidencia inline (DET-25) al cerrar. Verificar en S3 que el quality review consolidado (DET-23 dim 4) lee la evidencia de todas las tasks paralelas, no solo la ultima en retornar. No bloqueante; es checklist de design.

### Scope extension (dev 2026-05-26, al confirmar generacion del spec)

El dev confirmo generar el spec y agrego 3 requisitos que amplian el alcance acordado en AQ-1:

1. **Declaracion explicita paralelas vs dependientes**: al establecer las sessions, `design-{tipo}` debe especificar claramente que tasks pueden correr en paralelo y cuales tienen dependencias (no solo declarar `parallel_groups`, sino hacer legible la distincion). Refuerza S1 + la heuristica.
2. **Capability detection del host LLM** (NUEVO REQ): el sistema debe saber si el modelo/host LLM soporta ejecucion paralela (multi tool_use en un mensaje). Si NO la soporta (hosts tipo Codex/Cursor/Ollama segun HOR-060 multi-provider), degradar a ejecucion secuencial sin romperse. Conecta con `prompts/agent-tiers.md` multi-provider compatibility + `config.yaml > tiers`.
3. **HC viewer DENTRO de alcance** (ya NO diferible): HC debe indicar visualmente que tasks estan consideradas para ejecucion paralela. Saca S4 de "diferible" — entra como session ejecutable (repo `horadric-cube`).

**Impacto en alcance**: se agrega REQ-IMPROVE de capability-detection + REQ-PRESERVE de degradacion segura en hosts sin soporte paralelo. El plan de sessions se re-particiona (ver plan ajustado). Repos tocados ahora: `deckard` (firme) + `horadric-cube` (firme, ya no opcional).
