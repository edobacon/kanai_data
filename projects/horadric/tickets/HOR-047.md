# DET architecture refactor — capas formales + lifecycle (deprecation/supersession)

## Request

**Origen**: analisis 2026-05-16 sobre debilidades arquitecturales de DKC pensando en LLM-only futuro. Gap identificado: **DETs sin jerarquia formal**.

**Que es el problema hoy** (DKC v1):

Las 25 DETs (DET-1..DET-25, mas DET-26/DET-27 recientes) viven como **lista plana en `deckard/prompts/deterministic-rules.md`** con referencias cruzadas heterogeneas. Concretamente:

1. **Sin capas**: DET-7 (test cases referencian discoveries) es regla de **evidencia**. DET-20 (sessions con gate) es regla de **proceso**. DET-24 (callouts en REQs) es regla de **formato**. DET-17 (lifecycle de backlog) es regla de **ciclo de vida**. Estas son 4 capas distintas pero la lista no las distingue.
2. **Sin lifecycle**: no hay mecanismo formal de **deprecation**. Si una DET se vuelve obsoleta o queda superada por una mas amplia, queda en la lista. Tampoco hay **supersession** explicita (DET-X reemplaza a DET-Y).
3. **Sin dependency graph**: DET-25 referencia DET-7 + DET-13 + DET-23. DET-23 referencia DET-20. El grafo existe en prosa pero no es maquina-legible. Refactorear DET-7 implica grep manual de DET-25 para validar no romper la cadena.
4. **Costo marginal creciente**: agregar la DET-26 requiere leer 25 anteriores. La DET-30va requerira leer 29. No es sostenible si DKC sigue creciendo.

**Sintomas observables hoy:**

- **Heterogeneidad de gates**: DET-20 (Gate de session), DET-22 (Gate de close), DET-21 (Gate de design). Tres "gates" en niveles distintos del proceso sin taxonomia.
- **Format rules mezcladas con process rules**: DET-24 (callouts) y DET-20 (sessions) viven al lado. Una se valida con linter, la otra requiere el LLM siga el workflow. Tratarlas igual oculta que necesitan enforcement distinto.
- **Skip semantics ad-hoc**: DET-18 introduce `draft_approved: skipped`. DET-21+DET-22 extienden a `teachings.* skipped` (HOR-020 F5). Cada DET re-inventa el patron skip sin un modelo formal.
- **Referencias bidireccionales fragiles**: DET-7 dice "regression obligatoria"; DET-13 dice "tests con resultados reales"; DET-25 ata ambos. Si DET-7 cambia, no hay tooling que detecte que DET-25 quedo inconsistente.

**Propuesta** (exploratoria — esto es work_type `explore` porque produce un modelo conceptual y solo despues se decide implementacion):

Disenar un **modelo de capas + lifecycle** para las DETs:

### Modelo tentativo de capas (a refinar en intake)

| Capa | Que regula | Ejemplos actuales | Enforcement primario |
|------|-----------|-------------------|----------------------|
| **L1 — Process** | Orden y existencia de pasos del workflow | DET-20 (sessions+gates), DET-21 (teach-intake), DET-22 (teach-close), DET-17 (backlog lifecycle) | Gate engine (HOR-044) + cycle validator |
| **L2 — Evidence** | Que debe registrarse, donde, en que momento | DET-6 (discoveries cronologicos), DET-7 (TCs trazan a discovery), DET-13 (cierre con evidencia), DET-25 (TCs inline) | Validator + gates A2/D |
| **L3 — Format** | Como se ve un record en markdown | DET-24 (callouts REQs), DET-2 (source_ref obligatorio), DET-20 sub-clausulas de formato | Linter + Zod schemas (HOR-026/041/045) |
| **L4 — Semantics** | Significado de campos y valores | DET-1 (certainty levels), DET-4 (hechos vs inferencias), DET-14 (approve/iterate/escalate) | LLM understanding + validator de enum |
| **L5 — Boundaries** | Limites entre roles, sistemas, repos | DET-10 (limites por rol), DET-19 (external id en artefactos del repo) | Prompt design + access control |
| **L6 — Meta** | Reglas sobre las reglas mismas | (nueva) DET-lifecycle, supersession, deprecation | Tooling del repo deckard |

### Lifecycle states (a refinar)

```
active → deprecated → superseded_by(DET-X) → archived
                  ↘ relaxed_to(condition) → ...
```

- **active**: en uso, enforced
- **deprecated**: aun documentada pero proximas DETs no deben referenciarla; se mantiene por backwards compat
- **superseded**: cubierta por otra DET mas general; refs externas se redirigen
- **archived**: removida de enforcement; historial preservado para auditoria

### Dependency graph

DETs como nodos, referencias como aristas, tipos de arista (`requires`, `extends`, `supersedes`, `composed-with`). Permite:

- Detectar refactor de DET-X que rompe DET-Y dependiente
- Visualizar el grafo (HC viewer puede renderear)
- Validar coherencia automatica

### Tooling esperado (si el modelo cuaja)

- `commands/dkc-det-validate` — valida dependency graph + lifecycle states + capas asignadas
- `commands/dkc-det-graph` — exporta DOT/JSON del grafo
- HC viewer tab "DETs" que renderea grafo + capas + lifecycle visualmente

**Beneficio inmediato (HOY)**:

- Reduce el costo cognitivo al agregar DET nueva (lees solo tu capa)
- Detecta inconsistencias automaticamente
- Hace explicito quien-depende-de-quien

**Beneficio para LLM-only futuro**:

- Modelos locales con contexto pequeño pueden cargar **solo las capas relevantes** al step actual (ej. design-{tipo} carga L1+L4; format validator carga solo L3)
- Fine-tuning puede generar dataset por capa
- Skill compositions futuras (CrewAI-inspired, ver HOR-027/028) pueden componer DETs por capa

**Por que `explore` (no improvement)**:

Este ticket produce **un modelo conceptual primero**. Solo despues de validar el modelo (¿las 5-6 capas son las correctas? ¿lifecycle states son suficientes?) se decide la implementacion (que se vuelve un improvement ticket nuevo, post-explore). El explore puede cerrar con spec draft + decision documentada sin implementar.

**No es alcance**:

- Reescribir las 25 DETs actuales — solo categorizarlas en capas y agregar metadata lifecycle
- Cambiar la semantica de las DETs — solo organizarlas
- Implementar el tooling completo — solo definir el modelo + prueba de concepto
