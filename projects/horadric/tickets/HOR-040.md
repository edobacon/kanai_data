# HC live updates de ticket activo via file watcher

## Request

**Refundacion DKC v2 — Phase 1**. Bug operacional observado durante HOR-023 + HOR-026 (2026-05-16): HC viewer en `localhost:3016` no refleja cambios al markdown del ticket en ejecucion hasta despues de `dkc-reindex` post-gate. Sintoma: el dev viendo HC durante una session larga (3-5 tasks) no ve progreso. Solo al cerrar el gate aparecen los cambios acumulados.

**Causa raiz**: decision tomada en HOR-015 H10-B — reindex post-gate (no post-task) para evitar spam de updates. Trade-off: granularidad media vs UX live. La decision sigue siendo razonable para el reindex global (SQLite + relations), pero **falta un canal liviano para reflejar cambios al markdown del ticket activo en HC sin pasar por el reindex completo**.

**Solucion propuesta**: HC adquiere un **file watcher** sobre el path del ticket activo. Cuando el markdown cambia (LLM principal hace Edit), HC re-parsea + re-renderiza el bloque Sessions en vivo. NO requiere reindex global — la DB queda igual hasta el gate. HC consume directamente el markdown para el ticket en foco.

**Posicion en la refundacion DKC v2**:
- Phase 1 (este ticket): UX fix — dev ve progreso en vivo
- Phase 2 (HOR-041): Foundation extension — schemas Rule + Decision
- Phase 3 (HOR-042): Cambio arquitectural — pipeline write→validate→commit

**Por que primero esto**: bajo riesgo (cambio aislado al cliente HC + server-side file watcher), alto valor inmediato (resuelve dolor que el dev observa hoy), no requiere coordinacion multi-repo con steps de deckard.

## Open questions

- **HC abierto en multiples tabs**: ¿soportamos 2 ventanas viendo el mismo ticket? Default: si, cada cliente SSE recibe el evento independiente. No coordination necesaria.
- **Backpressure**: si markdown cambia 10 veces en 1s, ¿envias 10 eventos o el ultimo? Default: debounce 300ms → 1 evento por ventana.
- **Scope del re-render**: ¿solo bloque Sessions o todo el ticket? Default: solo Sessions (donde esta el dolor). Frontmatter cambios = reindex (gate).
