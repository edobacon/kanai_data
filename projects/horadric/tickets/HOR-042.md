# Pipeline write→validate→commit (DKC v2 atomic writes)

## Request

**Refundacion DKC v2 — Phase 3. Punto de inflexion DKC v1 → v2**.

**Estado actual (DKC v1)**:
- LLM escribe markdown libremente (Edit/Write)
- Validation post-escritura via `dkc-verify-gate` + `dkc-validate` (HOR-023 + HOR-026)
- Si hay drift, el markdown queda mal escrito hasta el siguiente gate. El dev tiene que avisar (o el verifier detectar al cerrar)
- **Trabajo se hace y despues se valida** — patron "write-then-validate"

**Problema observado**:
- HOR-029 sufrio 3 rondas de fix del dev sobre formato canonical antes de que el ticket cerrara correctamente
- HOR-026 documenta 5 bugs HOR-022 mid-gate que fueron post-write
- En setup local-only (modelos pequeños como Qwen 30B), el write-then-validate genera multiples ciclos de fix porque el modelo divaga sin contract previo
- **El validate post-write detecta el bug pero NO previene su escritura** — el markdown ya esta sucio

**Solucion propuesta (DKC v2)**: invertir el flujo.

```
DKC v1 (actual):
  LLM → Edit markdown → [post-hoc] dkc-validate detecta drift → dev/LLM fix → re-Edit

DKC v2 (este ticket):
  LLM → produce JSON estructurado → schema valida → tool genera markdown desde template → commit
                                ↑
                       SI invalido, bloquear ANTES de escribir
                       LLM corrige JSON, re-valida
```

**Beneficios**:

1. **Markdown nunca esta drift**: validacion antes de escritura garantiza shape canonical
2. **Cero round-trips de fix de formato** entre dev↔LLM: si JSON pasa schema, MD generado es 100% canonical
3. **Templating consistente**: MD generado desde template parametrizable. Si cambia la convencion, ajuste en 1 lugar (no 30+ tickets)
4. **Local-only viable**: Qwen 30B con context 32K no puede holdcanonical en mente — pero PUEDE producir JSON validado. Es el unlock para que modelos pequeños sean confiables
5. **Dataset estructurado para fine-tuning** (roadmap HOR-037 LoRA): JSONs validados son training data perfecta

**Costo**:

- Cambio arquitectural mayor. Patron actual de write libre se reemplaza
- Steps actuales (request-execute, request-close, etc.) deben aprender a producir JSON antes de invocar el generador
- Templating engine para MD (mustache, handlebars, o custom simple)
- Opt-in via flag `--validate-on-write` inicialmente para no bloquear flujo existente
- Migracion gradual: tickets nuevos usan v2, tickets historicos quedan en v1 (sin migracion retroactiva)

**Riesgo MEDIO-ALTO**: si Phase 3 se rompe mid-implementation, el LLM principal no puede escribir tickets correctamente hasta rollback. Plan de mitigation:

- Opt-in via flag durante S1-S4
- Mandatory solo desde S5 (despues de validacion en HOR-042 mismo)
- Fallback graceful a v1 si el generador falla
