# Embedding-based KB retrieval (quick win) + roadmap de funciones para DKC local-only

## Request

**Direccion estrategica del dev (2026-05-15, ajustada 2026-05-16)**: preparar DKC para correr en modelos locales-only (Qwen 3 30B MoE multi-modelo en M5 Max 128GB cuando llegue el equipo nuevo), pero **primero optimizar el camino actual con Claude**. Este ticket es el primer paso del roadmap — implementacion de embedding-based KB retrieval que beneficia HOY (Claude Code) y queda como prerequisito habilitador para todo el resto.

**Re-scope 2026-05-16** (post-conversacion costos/rendimiento local M5 Max 128GB): el alcance incorpora **7 mejoras local-aware que YA benefician HOY al entorno Claude**. Mejoras local-specific puras (re-ranking, query caching, memory budget awareness) quedan diferidas a iteracion post-M5 Max.

**Por que es el primer paso**:

1. **Funciona HOY sin cambiar host**: el MCP server existente (`deckard-cain`) recibe un tool nuevo, el resto del workflow no cambia
2. **Beneficio inmediato medible**: reduce el contexto que el principal carga al hacer `KB-first` (DET-11). FTS keyword match → semantic+hybrid = mejor retrieval con menos contexto. Reduce DET-15 friction en tickets largos
3. **Multilingual desde dia 1**: DKC es ~80% español. MiniLM-L6 ingles-only pierde ~30-40% recall en queries ES. multilingual-e5-base resuelve hoy + queda listo para local
4. **Prerequisito habilitador** para modelos locales con context windows pequeños (32K efectivo en Qwen local): sin retrieval semantico + hybrid + context budget, agents locales se ahogan
5. **Reversible**: si embeddings no aportan, el tool nuevo coexiste con FTS — no rompe el sistema actual

**Alcance HOR-031** (re-scoped 2026-05-16):

- Pipeline de embeddings con **`fastembed` (ONNX, ~80MB sin PyTorch)** — runtime ligero que ahorra ~1.5GB vs sentence-transformers + prep para coexistir con LLMs locales en futuro
- Modelo: **`intfloat/multilingual-e5-base`** (768-dim, multilingual ES+EN, 280MB) — calidad ~85% en español vs ~60% de MiniLM-L6
- Persistencia con `sqlite-vec` extension (no introducir vector store standalone)
- Nuevo tool MCP: `dkc_semantic_search(query, max_tokens=1500, score_threshold=0.4, scope?)` returns fragmentos hasta cubrir budget en tokens (no fijo en top_k)
- **Hybrid retrieval**: semantic search + BM25 simultaneo, combinados con Reciprocal Rank Fusion (RRF). Captura tanto queries conceptuales como con identificadores literales (DET-15, BUG-platform-010)
- **Chunking adaptivo**: chunks 200-400 tokens (no 500-char fijo) + metadata por chunk (kind, module, project, section_title, language) para filtering pre-search
- Indexacion automatica al hacer `dkc-reindex {project}` (extension del comando existente, flag `--no-embed` para skip)
- 4 tools MCP de management: `dkc_embeddings_status/rebuild/prune/benchmark`
- Configuracion abstraida en `agent-tiers.md` (modelo de embedding swappeable)
- Migracion gradual de los steps que hacen KB-first: researcher consulta semantic search antes de fallback a grep

**Fuera de alcance HOR-031** (anotado abajo como roadmap futuro):

- Re-ranking con cross-encoder → diferido a **HOR-031.2** post-M5 Max (marginal con Claude, critico con Qwen local)
- Query caching LRU → HOR-032 (prompt cache local) — marginal con Claude rapido, critico con local lento
- Memory budget awareness para LLMs cargados → cuando se implemente local (HOR-035 multi-modelo routing)
- Prompt cache local con prefilling → HOR-032 conditional
- Validation gate con modelo pequeño separado → HOR-033 conditional
- Compresion semantica de sessions → HOR-034 conditional
- Multi-modelo routing concurrent → HOR-035 conditional (requiere modelos locales)
- Hibrid escalate a cloud → HOR-036 conditional
- Auto-distillation feedback → HOR-037 conditional (largo plazo)
- Reasoning scaffolds explicitos para architect en 70B → HOR-038 conditional

**Decisiones criticas tomadas en ejecucion**:

Trade-off positivo: calidad ES superior (100% recall@5 en POC vs target 80%) sin costo significativo (storage 4.5MB para 295 chunks, irrelevante). Spec actualizado retroactivo en S2 + agent-tiers.md.
- **L3 — patron batches para indexer**: dos runs del POC indexer colgaron (30+ min y 9+ min) por `list(model.embed())` acumulando todos los vectores + state ONNX en memoria. Fix: batches de 25 chunks + persistencia incremental + `del vectors` post-batch + `OMP_NUM_THREADS=4`. Post-fix: 295 chunks en 4:19 wall sin memory pressure. Patron aplicado en `EmbeddingIndexer` para produccion.
