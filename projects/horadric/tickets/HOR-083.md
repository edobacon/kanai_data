# Embeddings incremental — reindex solo de archivos nuevos/cambiados (TODO S2.T6.b)

## Request

**Origen**: pre-check de HOR-028 (cerrado won't_do 2026-05-30). Para correr ese pre-check hubo que generar los embeddings de up1, y el reindex full tomo **~1 hora** (430 archivos, e5-large en CPU). Quedo evidente el gap operacional que vuelve costoso mantener el indice fresco.

**Que es el problema hoy**:

- `commands/dkc-reindex {project} --with-embed` hardcodea `build_embeddings_index(..., fresh=True)` → **rebuild completo siempre**. Re-embebe todos los archivos aunque solo haya cambiado uno.
- El modo incremental (`fresh=False`) existe en la firma de `build_embeddings_index` pero esta documentado como **TODO (S2.T6.b)** — no implementado: igual re-itera y re-inserta todo.
- Consecuencia: en un proyecto activo (up1 suma tickets/specs constantemente), mantener embeddings al dia cuesta ~1h cada vez → en la practica nadie reindexa → el indice queda stale o directamente no se genera (caso up1: nunca tuvo embeddings hasta el pre-check de HOR-028).

**Workaround actual** (parcial): el script `/tmp/dkc_embed_up1_batched.py` (del pre-check de HOR-028) hace un *resume* — salta archivos cuyo `source_path` ya esta en el indice. Pero **NO detecta archivos editados** (un ticket ya indexado que se modifica queda stale) ni borrados. Sirve para reanudar un build interrumpido, no como incremental real.

**Propuesta**:

Implementar incremental real por **mtime o content-hash**:

1. Persistir por archivo indexado: `source_path`, `content_hash` (sha1 del contenido) o `mtime`, en una tabla `indexed_files` (o columna en `chunks`).
2. En `build_embeddings_index(fresh=False)`:
   - Para cada archivo del proyecto: si `hash(actual) == hash(indexado)` → skip. Si cambio o es nuevo → re-chunk + re-embed (borrando los chunks viejos de ese `source_path` primero, incluyendo `vec_chunks` + `chunks_fts` por id).
   - Archivos borrados del FS pero presentes en el indice → purgar sus chunks.
3. Exponer flag en el CLI: `dkc-reindex {project} --with-embed --incremental` (o hacer incremental el default y `--rebuild` para full).

**Beneficio**: reindex de minutos → **segundos** en runs sucesivos. Habilita mantener embeddings al dia como parte del flujo normal (ej. post-close de cada ticket).

**Alcance**:

- `server/src/deckard_cain/core/embedding_index.py` — `build_embeddings_index` + `EmbeddingIndexer` (tracking de hash/mtime + delete-by-source_path con cascada a vec_chunks/chunks_fts)
- `commands/dkc-reindex` — flag `--incremental`
- Tests: archivo nuevo, archivo editado, archivo borrado, archivo sin cambios (skip), full rebuild sigue funcionando

**Repos tocados**: `deckard` (server + commands)

## Summary — cierre (2026-05-30)

**Implementado** (incremental real por content-hash, el TODO `S2.T6.b`):

- **Schema** (`embedding_index.py`): tabla `indexed_files (source_path, content_hash, indexed_at)` + index `idx_chunks_source_path`. `CREATE IF NOT EXISTS` → compatible con DBs pre-HOR-083 (degradan a full en el primer run).
- **EmbeddingIndexer**: 5 metodos nuevos — `file_hash` (sha1, robusto a git checkout vs mtime), `get_indexed_hashes`, `delete_file_chunks` (cascada: vec_chunks manual por rowid + chunks → trigger limpia chunks_fts), `record_file_hash` (upsert), `purge_deleted`.
- **`build_embeddings_index`**: refactor a recolectar→indexar. `fresh=False` ahora es incremental real: skip si hash igual, borrar+reembeber si cambio, purgar borrados. `fresh=True` ahora tambien puebla `indexed_files` (habilita incrementales posteriores).
- **`dkc-reindex --incremental`**: nuevo flag (implica `--with-embed`). Output reporta `mode=incremental reindexed=N skipped=N purged=N`.

**Verificacion**:
- pytest `test_embeddings_incremental.py` (4 casos: hash determinista, tracking roundtrip+upsert, delete cascada vec+fts, purge). Suite 22/22 verde.
- E2e con modelo real (proyecto temporal): fresh=2 reindexed → incremental sin cambios=2 skipped → 1 archivo modificado=1 reindexed/1 skipped → 1 borrado=1 purged. Comportamiento correcto end-to-end.

**Impacto**: reindex de embeddings pasa de ~1h (full rebuild, caso pre-check HOR-028) a **segundos** en runs sucesivos. Primer `--incremental` sobre una DB pre-HOR-083 es full (puebla el tracking); los siguientes son rapidos.

**Nota DX**: para mantener el indice fresco, usar `dkc-reindex {project} --incremental` (vs `--with-embed` que sigue siendo full rebuild, preservado para backward-compat).
