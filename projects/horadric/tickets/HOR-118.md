# dkc-doctor — detector de staleness de anclas al código en rules y bugs

## Request

Derivado del análisis comparativo con el repo [engram](https://github.com/Gentleman-Programming/engram) (memoria persistente para agentes). Engram expone `mem_doctor`, una validación diagnóstica de la base de memoria. DKC no tiene equivalente: rules y bugs anclan a ubicaciones del código (sección `## Where` de rules, `## Root cause` de bugs) pero esas anclas **nunca se validan contra el código vivo**. La propia memoria global del dev ya advierte "verify it still exists before recommending" — hoy ese chequeo queda librado al LLM en cada recall.

Construir un comando **read-only** `dkc-doctor` que recorra rules y bugs del proyecto, parsee las anclas al código, y verifique con Grep/Glob si el archivo/símbolo referenciado aún existe. Reporta drift (anclas a código muerto). NO muta nada (consistente con el invariante read-only del ecosistema viewer/diagnóstico). Sin cambio de schema.

**Origen y corte acordados** (sesión de evaluación 2026-06-21):
- Feature "B" de un par B+A. Acordado ejecutar B primero (quick win, de-riesga el parseo de anclas) y luego A-mínima (reconciliación, HOR-119).
- La **línea exacta** de un ancla envejece muy rápido → el doctor verifica existencia de **archivo y símbolo**, no número de línea.

### Alcance de investigación (HOR-118 — agregado 2026-06-21)

El **comando read-only core** (parsear anclas + verificar existencia + reportar drift, REQ-01/02) es el entregable shippable e **independiente**: no depende de lo siguiente y no debe verse afectado por ello. Sobre esa base, el ticket debe **investigar** dos cosas que preparan a DKC para operar sobre un **KB validado**:

1. **Modelo de invocación / mejor trigger** (REQ-03): ¿dónde corre el doctor para máximo valor? Candidatos: on-demand (base), post-close scoped al diff (la causa raíz del drift es el cambio de código → DET-16), intake/KB-first (verify-before-recommend), pegado a reindex, programado. **La decisión se zanja con una prueba de drift sobre el KB real** (DET-13 — evidencia, no preferencia), que además valida H1/H2 del parser.

2. **Tiempo de validez de las rules (TTL / frescura)** (REQ-04): investigar si una rule (y opcionalmente un bug) puede portar un estado `last_validated` + una **ventana de validez** tras la cual se considera "vencida" y debe revalidarse. Habilita:
   - Revalidar **solo lo vencido o lo afectado por un diff** (no todo el KB en cada corrida) → barato de correr seguido.
   - Un estado de **"KB validado"** que los consumers (intake KB-first) pueden preferir, advirtiendo cuando se trae al contexto una rule vencida.
   - **Síntesis con el trigger**: post-close cubre la invalidación por *cambio de código*; el TTL cubre la invalidación por *paso del tiempo*. Son complementarios, no excluyentes — esto vuelve la pregunta del trigger menos binaria.

> **Tensión clave a resolver en la investigación (DET-32 necesidad/reuso + invariante read-only):** guardar `last_validated`/TTL en el frontmatter de la rule es un **cambio de schema** (mismo costo que diferimos para rules en HOR-119: template + modelo + RecordStatus + posible impacto HC viewer) **y** rompería el invariante read-only del doctor (escribiría el markdown del KB). Alternativa a evaluar primero: que el estado de validación viva en un **store propio del doctor** (tabla en `index.db` o archivo de reporte `.doctor`), dejando los markdown de rules/bugs intactos. La investigación debe decidir **dónde vive el estado de validación** antes de tocar cualquier schema. Implementar el TTL en este ticket solo si la alternativa barata (store externo) resulta viable; si exige schema de rule, queda como propuesta de diseño + follow-up.
