# Estado `deferred` canonical para tasks movidas a backlog (StepStatus + spec.Status + marker `[D]` + render HC + validator)

## Request

> *(Captura del descubrimiento, 2026-05-21 — cierre de HOR-062)*
>
> que podemos hacer con la t3? se ejecutara despues? cuando? puede quedar con un estado distinto, ya que fue deferred, que quede con una D, algo que marque su estado cambiado, y se evalue con eso si es necesario o no para el cierre

**Contexto**: durante S1 de HOR-062, S1.T3 (banner DET-20 para `## Plan de sessions` fuera de `## Sessions`) quedo deferred a backlog B1 porque requeria refactor adicional (prop con markdown raw o detect server-side). Quedo marcado `- [ ] S1.T3` en ticket + `Status: blocked` en spec con nota inline `(DEFERRED a B1)`. **Problema**: visualmente identico a `[ ]` pending, y `Status: blocked` es semanticamente incorrecto (no esta bloqueado por dependencia externa; fue diferido por decision).

**Gap conceptual del sistema canonical**:

| Estado real | Spec.Status actual | Ticket checkbox actual | Problema |
|-------------|---------------------|------------------------|----------|
| Task identificada, no ejecutada, esperando trigger externo | `blocked` | `[ ]` | OK semantico |
| Task **diferida explicitamente por decision** (movida a backlog `should/could`) | `blocked` ← MAL | `[ ]` ← indistinguible | Falta estado canonical |
| Task no priorizada aun | `pending` | `[ ]` | OK |
| Task en progreso | `in_progress` | `[~]` | OK (HOR-056 capa A) |
| Task completada | `done` | `[x]` | OK |

**Alcance del fix**: extender el sistema canonical de status con `deferred` (spec) + `[D]` (ticket marker) en todas las capas:

| Capa | Cambio |
|------|--------|
| Spec.Status enum | Agregar `deferred` al enum canonical (junto a `pending/in_progress/done/blocked`) |
| Ticket checkbox marker | `[D]` (mayuscula distintiva) — diferente de `[ ]/[x]/[~]` |
| HC parser (`sessions.ts`) | Reconocer `[D]` como `StepStatus = 'deferred'` (extension del patron HOR-056 capa A) |
| HC render (`SectionSessions.vue` + atoms render) | Icono dash o chevron + tooltip que muestra backlog ref |
| Validator `SessionCheckboxes` | Mapping `spec.deferred ↔ ticket.[D]` valido. NO genera drift. Cross-check con `## Backlog`: si `Status: deferred`, debe haber item correspondiente |
| Template + prompt | Documentar uso correcto + cuando usar deferred vs blocked vs pending |
| DET / RULE update | Extension de RULE-workflow-session-format-canonical-002 + posible DET nuevo `deferred state semantics` |
| Gate D / cierre | Tasks `deferred` NO bloquean cierre (a diferencia de `blocked` que con priority `must` si bloquea) |

**Fuera de alcance**:

- Migracion retroactiva de tickets cerrados con `Status: blocked` que en realidad son deferred (no retroactivo, criterio igual a DET-21/22/24)
- HOR-062 S1.T3 — migrara al nuevo formato durante S2 de HOR-063 como dogfood (de `blocked` + nota → `deferred` + `[D]`)
- Auto-transicion `deferred → done` cuando se ejecuta el backlog item asociado — semantica futura (probable HOR-063.2)
