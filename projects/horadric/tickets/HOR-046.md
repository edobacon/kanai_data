# State source-of-truth consolidation — markdown canonical + proyecciones derivadas

## Request

**Origen**: analisis 2026-05-16 sobre debilidades arquitecturales de DKC pensando en LLM-only futuro. Gap identificado: **estado distribuido sin owner unico**.

**Que es el problema hoy** (DKC v1):

Para un mismo ticket coexisten en paridad operacional:

1. Frontmatter YAML del ticket markdown (`projects/{project}/tickets/{id}.md`)
2. Body del ticket markdown (Sessions, Testing, Backlog, Commits, Summary)
3. Spec markdown asociado (`projects/{project}/specs/SPEC-*.md`)
4. Sub-carpetas hermanas (`{id}.draft/`, `{id}.teach/`, `{id}.screenshots/`)
5. Index SQLite del MCP (`projects/{project}/.dkc/index.db`)
6. Config global del proyecto (`projects/{project}/config.yaml`, `.active_project`)

**Sintoma**: cada DET nueva (DET-16 propagacion, DET-25 inline TCs, DET-27 commit-per-session) tiene que enumerar manualmente "donde mas se refleja esto" porque no hay una capa que **proyecte estado canonical a vistas derivadas**. El LLM termina siendo el encargado de mantener consistencia entre 6 capas.

**Casos concretos del dolor:**

- HOR-018/019/020 cerraron con TCs `pending` en el body del ticket markdown pese a que los tests SI se ejecutaron en sessions. La verdad estaba en el commit history + session log; el "estado oficial" (body del ticket) no la reflejaba. Motivo DET-25.
- HC viewer reflejaba sessions abiertas porque el parser difiere del shape "real" (caso RULE-dev-002, RULE-dev-003) — drift entre body del ticket y representacion en el index/UI.
- HOR-040 (live updates) **refleja** estado sincronizado pero no lo **centraliza**: file watcher + SSE propaga cambios del markdown a la UI, no resuelve la pregunta "que es la fuente de verdad cuando frontmatter dice X y el body dice Y".

**Propuesta** (DKC v2 extension, post-HOR-042):

Declarar **markdown como Source of Truth canonical** y **degradar formalmente SQLite + frontmatter parseado a proyecciones derivadas**. Concretamente:

- **Pipeline de derivacion unico**: cualquier consumer (HC, dkc-validate, queries del MCP, indexers de embeddings de HOR-031) NO lee del SQLite directo — lee de una capa de proyeccion alimentada por el pipeline write→validate→commit de HOR-042.
- **Index SQLite reconstruible**: nunca se escribe a SQLite "a mano" desde un step. Solo `dkc_reindex` rebuilds del markdown. Si SQLite se borra, el sistema reconstruye sin perdida.
- **Frontmatter como vista**: el frontmatter del ticket es la proyeccion mas "barata" del estado canonical pero NO es la verdad — si el body dice "Session 4 closed" y el frontmatter dice `status: open`, el body gana. Validator detecta divergencia.
- **Eliminar campos redundantes en frontmatter**: campos que son calculables del body (ej. `teachings.intake: done` cuando existe `tickets/{id}.teach/teach-intake.md`) pasan a ser **inferidos**, no almacenados — o si se almacenan, el pipeline los recalcula post-escritura.
- **Sub-carpetas como artifacts**: `.draft/`, `.teach/`, `.screenshots/` son artifacts referenciados desde el ticket markdown via paths, no estado paralelo. Su existencia se valida desde el ticket.

**Beneficio inmediato (HOY con Claude)**:

- Reduce el costo cognitivo del LLM al ejecutar DET-16 propagacion (de "actualizar 6 capas" a "actualizar 1 capa + invocar pipeline")
- Reduce bugs de drift (caso HOR-018..020)
- Habilita reindex deterministicos
- Simplifica los gates verificables (HOR-023) — solo validan markdown, no la consistencia entre capas

**Beneficio para LLM-only futuro (HOR-031..038 roadmap)**:

- Modelos locales (Qwen 30B) con context window pequeño NO pueden cargar 6 capas y razonar sobre consistencia. SoT unica reduce el carga.
- Fine-tuning (HOR-037 LoRA) requiere dataset coherente — sin SoT unica, el dataset aprende variance entre capas.

**No es alcance**:

- Reescribir tickets/specs existentes — backwards compatible
- Cambiar el formato markdown — solo formalizar quien gana
- Reemplazar SQLite — sigue como index/proyeccion

## Request — Extension 2026-05-16 (scope expansion)

### Frentes adicionales en alcance

**Frente A — Tipado de contrato mas fuerte para artefactos DKC consumidos por HC**

Los archivos `teach-intake.md`, `teach-close.md` y `## Sessions` en tickets son la interfaz principal entre DKC y HC. Hoy:

- Bloques `dkc:hypothesis-map`, `dkc:decision-matrix`, `dkc:learning-path` en teach files son YAML embebido sin schema validado en write-time
- Sessions en `## Sessions` del ticket markdown tienen un shape esperado por HC (`### Session N — {objetivo}`, sub-secciones con labels literales como `**Gate decision:**`) pero ninguna validacion bloquea writes que no cumplan
- El LLM "sabe" el shape pero lo rompe (sufijos `(FINAL)` en labels, sub-headers en vez de checkboxes para tasks, comments `#` sin indentar dentro de fenced code, etc.) → HC deja de renderizar elementos

**Linea de extension**: HOR-026 (Output schemas Zod) + HOR-041 (Rule + Decision) + HOR-045 (discoveries/learns/bug tipados) cubrieron specs y discoveries pero NO cubrieron **teach files** ni **session shape**. Este frente extiende los schemas Zod a esos dominios + integra con el pipeline write→validate→commit de HOR-042 para bloquear writes que rompen contrato.

**Frente B — Variant de autopilot con flag explicito `teach: on | off`**

Sintoma: el dev observa que el autopilot aplica DET-21 + DET-22 (teach-intake + teach-close) automaticamente sin pedir confirmacion al dev al activar autopilot. Aunque DET-21/22 ya soportan `skipped` con justificacion (HOR-020 F5), el autopilot no esta dando el control al dev al **inicio del ticket**, sino que entra al teach asumiendo `on`.

**Propuesta**: el autopilot al activarse pregunta `teach: on | off` y persiste la decision en frontmatter del ticket (`teachings: { intake: skipped|pending, close: skipped|pending }`). El step `request-intake` lee la decision al alcanzar la fase teach y aplica el skip con justificacion auto-generada referenciando que el dev lo eligio al activar autopilot. Esto convierte la decision de teach en **explicita y declarable**, no un default heredado.

**Frente C — Audit retroactivo HOR-040 a HOR-049 con discoveries inline**

Revisar los 10 tickets ultimos cerrados (o explore) para extraer **toda inconsistencia detectada** entre lo que el LLM escribio y lo que HC parsea correctamente. Cada inconsistencia se registra como `discovery` en este ticket (no se modifica retroactivamente los tickets origen — DET-6 inmutabilidad).

**Output esperado**: tabla de discoveries con columnas `ticket | archivo | shape esperado | shape escrito | impacto en HC | tipo de violacion (schema | label | order | other)`. Esta tabla alimenta el diseno de los schemas Zod del Frente A (cuales reglas debe enforce el pipeline) y el RULE-* nuevo que documente el contrato.

**Caso especifico fixture**: HOR-049 quedo con orden de sesiones mal registrado. Ese caso entra como discovery citable y sirve de test fixture para validar el schema.

**Frente D — Bug independiente: modal de detalles de commits en HC**

Al levantar el modal desde sessions para ver detalles de commits, HC presenta un error. Investigar repro, identificar causa raiz (parser? endpoint? frontend?) y corregir. Es un fix concreto, NO estructural, pero entra al ticket porque (1) afecta la experiencia de revision del audit del Frente C — sin modal funcionando, revisar commits desde sessions queda manual; (2) puede revelar mismatch entre el shape esperado por el componente y el shape provisto por el server (relacionado con causa raiz comun).

### Por que absorber en HOR-046 (no abrir HOR-050)

1. **DET-11 (KB-first)**: HOR-046 ya plantea "estado distribuido sin owner unico" y cita HOR-018/019/020 + HC viewer drift. Los frentes A+B+C son sintomas del mismo problema desde otros angulos

- **Frente D (bug modal) es independiente**: si la causa raiz NO esta relacionada con el contrato tipado, puede sacarse a sub-ticket separado en design. Por ahora se incluye porque el repro puede revelar mismatch de shape
