# Valor del dev supervisor en HC: detalle de sessions en ejecucion + teach skip visible + kanban cerrados ordenado + audit liviano

## Request

Post-HOR-020 emergen 5 mejoras adicionales al valor que HC entrega al dev que supervisa la ejecucion del LLM. Estan agrupadas en un solo ticket por decision del dev (2026-05-15, en linea con el patron HOR-020/HOR-015).

**F1**. Detalle de tasks visible en sessions executed Y projected (HC viewer + proceso LLM):

- Hoy SectionSessions atomico (introducido en HOR-015) muestra `S16.T1` / `S16.T2` sin descripcion en **ambos casos**:
  - Sessions en ejecucion (status `in_progress` o `executed` parcial) → atoms con `description = id` por bug en `parsePlannedTaskIds`
  - Sessions projected (no iniciadas) → caen al render legacy con `plannedTasks` que tienen el mismo bug, o quedan como placeholders sin tasks
- El spec **siempre** tiene los detalles en `## Tasks` con descripcion completa + status + commit, accesible via `ticket.spec` del frontmatter — pero el viewer no lo cruza
- El LLM tampoco escribe la descripcion de cada task en el ticket markdown al iniciar la session — solo al final
- El dev supervisor pierde:
  - "que esta corriendo ahora" en tiempo real (sesiones executed)
  - "que viene en la proxima sesion" (sesiones projected) — informacion clave para anticipar gates, planificar interrupciones, validar el plan
- **Condicion**: requiere que el ticket ya tenga `spec` populated y el spec exista (post design-{tipo}). Tickets en intake o sin spec siguen usando el render actual (degradacion limpia)

**F2**. Audit liviano del flujo DKC post HOR-015 + HOR-020:

- Muchas DETs nuevas (DET-20..25), changes en intake/design/execute/close, gates `⚑ fuerte` y tiers T0-T3, quality review, etc.
- Revisar coherencia, redundancia y posibles agujeros donde el LLM puede saltar gates en modo autonomo
- Foco: en cada step del flujo, que info termina en el ticket vs spec, y como se hace visible al dev supervisor en HC

**F3**. Teach skip verificable + visible en HC:

- HOR-020 F5 introdujo skip con razon en DET-21/22 y los prompts (teach-intake paso 0 + request-close paso 3 con pregunta)
- Validar que en la practica el LLM esta preguntando antes de producir el archivo
- Si el dev elige skip, la razon debe ser visible en HC (tab Teaching > Intake/Close debe renderear estado `skipped` + razon, no error 404)

**F4**. Kanban cerrados ordenados por `closed` desc:

- HOR-020 F3 ordeno por `updated || created` desc en cada columna
- Para la columna cerrados, el sort correcto es `closed` desc con fallback a `updated || created`
- Sin esto los cerrados recientes se mezclan con cerrados viejos que tuvieron update reciente por reindex/touch

**F5**. Coherencia y persistencia de session state durante la ejecucion (relacionado con F1):

- Cada vez que el LLM arranca una task de una session, el ticket markdown debe registrar la task con su descripcion ANTES de implementar (no solo el ID)
- Patron analogo al "registrar TC antes de ejecutarlo" (DET-25). Aplicable a tasks en general
- Sin esto, si la sesion del LLM se interrumpe a mitad de una task, no hay rastro de que estaba haciendo

**F6**. Commits sensibles al contexto del proyecto + DKC trackea la relacion en su index:

**Regla** (basada en `external` del ticket):

| Proyecto | Senal | Commit message | Tabla DKC |
|----------|-------|----------------|-----------|
| **DKC-only** (uso personal, sin sistema externo) | `external: null` | Toda la info DKC permitida (TICKET-id, S{N}.T{M}, REQ, learns) | Opcional — el dev puede consultar el markdown si quiere |
| **Compartido** (otros devs no usan DKC, hay tracker externo Jira/Linear/etc.) | `external: "UPONE-1100"` (o similar) | Limpio, normativa transversal del equipo. Header con `external` id segun DET-19. SIN granularidad DKC interna (sin S{N}.T{M}, sin REQ, sin learns) | Obligatoria — sin esto la relacion se pierde porque el git history no la lleva |

**Por que esta regla**: el proposito de los artifacts DKC en commits es trazabilidad. En proyectos DKC-only el unico lector es el propio dev DKC + el LLM — ninguno se confunde, todos se benefician. En proyectos compartidos, los lectores son MAYORITARIAMENTE devs no-DKC — el ruido los confunde y la trazabilidad se mantiene mejor en una capa propia de DKC.

**Implementacion**:

- El step `request-execute` detecta `external` del ticket al armar el commit message. Si existe → modo limpio. Si no → modo libre
- Captura hash post-commit (`git log -1 --format=%H`) en ambos modos y anexa a:
  - **Columna `commit` en SessionTask** (ya existe en el modelo, vista en `sessions.ts:340`)
  - **Tabla `## Commits`** en el ticket markdown — fuente de verdad textual
- HC viewer ya renderea commits ligados desde atoms. Extender opcionalmente con vista resumen por commit
- Guideline en `prompts/_style.md` o seccion del step: que campos del commit ajustar segun modo

**Sub-decision para analizar en S1 (audit) o en S5 (design propio de F6)** — H11:

¿Vale la pena ademas indexar la relacion en SQL (`index.db` tabla `commits`)? El markdown sigue siendo fuente de verdad; SQL seria layer de query optimizada. Analizar valor + velocidad:

- **Valor**: queries cross-ticket ("que commits tocan modulo X", "que commits cubren REQ-Y", "que tasks cierra el hash abc"), dashboards en HC, agentes DKC haciendo audit consultan SQL barato vs leer N markdown
- **Velocidad**: 1 query SQL vs grep multi-archivo. Write barata si reindex parsea `## Commits` igual que parsea `## Sessions`
- **Costo**: tabla nueva en `index.db` (siguiendo patron `records` + `relations`), parser en reindex, mantenimiento sincronizado (markdown gana en conflicto, reindex regenera)
- **Decision en S5**: si vale, agregar `commits` table + parser. Si no, dejar solo en markdown

**F7**. Modo autonomo formal de ejecucion del ticket:

- Hoy el LLM aplica "modo autonomo" de forma **informal** — HOR-020 S2/S4/S5 lo evidencia ("modo autonomo asume aprobacion visual del dev"). Mi memoria global tiene `feedback_autopilot_mode.md` ("ejecutar de corrido sin preguntar, salvo acciones irreversibles")
- Falta formalizarlo: estado dinamico activable en cualquier punto del ciclo, reglas claras de que se autoriza, manejo de gates `⚑ fuerte`, visibilidad en HC para que el dev observe mientras el LLM corre
- **Propuesta**:

**Activacion dinamica** (no un solo punto de declaracion): el dev decide cuando le conviene. El autopilot es un **estado** del ticket, no un parametro de arranque.

| Cuando activar | Como |
|----------------|------|
| Antes del intake | Dev escribe en el chat (`activa autopilot`, `modo autonomo`, `/dkc autopilot on`) — el LLM marca el estado en el frontmatter del ticket al crearlo |
| Antes de las sessions (post-design, pre-execute) | Mismo mecanismo. El LLM actualiza el frontmatter y arranca execute con el estado |
| Durante las sessions (mid-flow) | El dev puede cambiar el estado entre tasks o entre gates. El LLM lee el estado en cada gate antes de decidir continue/iterate/escalate |
| Cambio de modo (true ↔ strict ↔ false) | En cualquier punto, misma mecanica. Cambio queda registrado |

**Persistencia**: el frontmatter del ticket lleva el **estado actual** (`autopilot: false` default, `true` u `'strict'`). El LLM consulta ese estado en cada gate; no se cachea en variables de sesion. Esto garantiza que el cambio del dev tenga efecto desde el proximo gate sin reset.

**Registro de cambios**: cada activacion/desactivacion queda como linea en una sub-tabla `### Modo (autopilot)` del ticket o como learn raw con tag `mode-change`. Util para audit posterior — saber en que tramo el ticket corrio en autopilot.

**Comando explicito disponible**: ademas del frontmatter, el dev puede escribir frases que el LLM reconoce como triggers (lista cerrada definida en design — ej. `autopilot on/off/strict`, `modo manual`, `para`, `pausa`).

**Reglas en autopilot**:

| Accion | Autopilot=true | Autopilot=false |
|--------|---------------|-----------------|
| Decision de design entre alternativas viables, con KB que respalde una | Elegir + documentar racional | Preguntar al dev |
| Aplicar patron ya documentado en rules/specs | Ejecutar sin preguntar | Confirmar antes |
| Commit local (sin push) | Ejecutar con mensaje propuesto + commit | Mostrar mensaje + esperar confirmacion |
| Gate `auto` con tests verdes | Continuar | Continuar |
| Gate `⚑ fuerte` — modo `true` (optimistic) | Asumir aprobacion, marcar gate como `auto-approved` en HC, anotar "PENDING REVIEW" | Pausa, presenta al dev, espera decision |
| Gate `⚑ fuerte` — modo `strict` | Pausa siempre, emite "PENDING REVIEW" a HC, espera | Pausa, espera decision |
| Push a remote (origin) | **Siempre pregunta** — accion compartida | Pregunta |
| Merge a main/develop, force-push | **Siempre pregunta** — irreversible | Pregunta |
| Close del ticket sin acceptance verde | **Siempre pregunta** | Pregunta |
| Cambio fuera del alcance del ticket | **Siempre pausa y reporta** | Pausa y reporta |
| Dependencia externa nueva (npm install lib) | **Siempre pregunta** | Pregunta |
| Git reset, delete branch, rm -rf | **Siempre pregunta** — destructivo | Pregunta |

**Visibilidad en HC** (clave para el dev supervisor):

- Auto-reindex post cada step DKC completo (ya existe desde HOR-014/HOR-015) — confirmar que sigue funcionando con autopilot
- Badge "autopilot" en el ticket activo (kanban + detail view)
- Gates ⚑ fuerte que fueron asumidos en autopilot se renderean diferente que los aprobados por el dev (ej. icono distinto, color amarillo "auto-approved" vs verde "dev-approved")
- Cada decision de design tomada en autopilot queda registrada como learn (raw → refinable) con el racional usado

**Interrupcion / cambio de modo dinamico**:

- Dev puede escribir en la conversacion `pausa`, `iterate`, `para`, `stop` → el LLM se detiene en el proximo gate (autopilot pasa a `false` efectivo)
- Dev puede escribir `autopilot strict` o `modo strict` → cambia a strict on the fly. Proximos gates ⚑ fuerte pausan
- Dev puede escribir `autopilot on` desde modo conversacional → activa el modo desde el proximo gate
- Dev puede iterar despues sobre un gate `auto-approved` si emerge problema (no se pierde la opcion de revision tardia)
- El LLM **lee el estado en cada gate** — un cambio entre gate N y N+1 surte efecto desde N+1 sin reset

**Donde se implementa**:

- `prompts/steps/request-execute.md` — leer estado del frontmatter en cada gate, aplicar reglas, registrar cambios
- `prompts/steps/request-intake.md` + `commands/dkc.md` — reconocer triggers en la conversacion (`autopilot on/off/strict`) y actualizar frontmatter
- Frontmatter del ticket — campo `autopilot: false | true | 'strict'` opcional, mutable durante el ciclo
- Sub-tabla `### Modo (autopilot)` en `## Sessions` del ticket o seccion similar — historial de cambios (timestamp, mode, motivo opcional, gate donde aplica desde)
- HC viewer — badge global + diferenciacion visual de gates `approvedBy: 'dev' \| 'autopilot'`; idealmente mini-timeline de modo
- Posible DET nueva post-audit (decidir en F2 + en S6 con propuesta)
