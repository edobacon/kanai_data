Por qué la selección de los pickers no se ve, y por qué los íconos están mal curados

TICKET-094 entregó el ColorPicker y el IconPicker. Al usarlos en la suite emergieron dos cosas: el swatch/ícono seleccionado no se resalta (ni el guardado al abrir edición, ni el que clickeas), y el catálogo de íconos arranca con flechas y alineaciones en vez de íconos educacionales. Este ticket corrige ambas. La primera es un bug de reactividad con causa raíz ya localizada; la segunda es curaduría.

TL;DR — Qué pasa: ambos pickers derivan el estado seleccionado de element.value dentro de un computed → no reacciona al update() (click no resalta) y está vacío al montar (no hidrata). El indicador CSS ya existe; el estado no cambia. Qué se hará: migrar a estado LOCAL (ref + init desde element.value con fallback a element.form$.data + watch + element.update()), patrón de ValidationTextEditorElement. Y curar el default del IconPicker a un set educacional (catálogo completo sigue buscable). Por qué: sin feedback de selección el componente es inusable; los íconos de navegación no representan líneas de formación.

Cómo fluye el valor en un Vueform element writable

Un element que escribe (submits:true) tiene dos momentos: hidratar (el form de edición carga el valor del registro) y seleccionar (el usuario hace click). El display debe reflejar AMBOS. El error de TICKET-094 fue intentar leer el valor "en vivo" con un computed, que no cubre ninguno de los dos de forma fiable.

flowchart LR
  Edit[Form edit abre] -->|carga async| EV["element.value (puede llegar vacío al setup)"]
  EV -->|init| LOCAL["ref local 'selected'"]
  FD["element.form$.data (fallback hidratación)"] -->|init si EV vacío| LOCAL
  Click[Usuario click] -->|select| LOCAL
  LOCAL -->|persiste| UP["element.update()"]
  LOCAL -->|render reactivo| UI["borde + check / aria-checked"]
  EV -.watch.-> LOCAL

La trampa de reactividad (y por qué RULE-019 se queda corta)

✗ Lo que hicimos (TICKET-094) — const currentValue = computed(() => element.value). El computed no vuelve a evaluar de forma fiable cuando element.update() cambia el valor, y al montar la edición element.value aún no trae el dato → ni resalta al click ni hidrata.
✓ El patrón probado — ValidationTextEditorElement (mod object-manager-editor) mantiene estado LOCAL: const text = ref(typeof element.value === 'string' ? element.value : props.default), con un fallback que lee element.form$.data para el valor cargado, y persiste con element.update().
⚠ RULE-curriculum-design-019 hoy dice "writable = setup()+element.update()". Le falta el matiz: el estado de display debe ser LOCAL, no un computed sobre element.value. Este ticket la refuerza.

Q&A de estudio

¿Por qué el computed sobre element.value no alcanza?
Dos motivos: (1) tras element.update() el computed no re-evalúa de forma fiable (la dependencia reactiva sobre la propiedad del element no se rastrea como un ref propio), así que el resalte no cambia; (2) al montar el form de edición, el valor del registro llega async — al momento del setup element.value puede estar vacío, y el computed se queda con ese vacío. El estado local + watch + fallback a form$.data cubre ambos.
¿El CSS de selección estaba mal?
No. .cp-swatch--selected (borde + SVG check) y .ip-cell--selected (borde + fondo) existen y son correctos. El bug es que isSelected() nunca devuelve true porque el estado del que depende no cambia. Es un bug de estado, no de estilo.
¿Por qué salían flechas en el IconPicker?
filterIcons('') devuelve los primeros 120 nombres del manifest en orden alfabético, que arranca con align-*, arrow-*, chevron-*. No había curaduría. El fix: un set educacional curado se muestra primero; el catálogo completo (2078) sigue accesible al escribir en la búsqueda.
¿Cómo se valida que esta vez sí funciona?
El gap de TICKET-094 fue confiar solo en tests de lógica pura. Acá se agrega cobertura del flujo de selección y, sobre todo, el smoke runtime es obligatorio al cierre: tras npm run sync + reinicio de la suite, abrir una línea con color/ícono guardados y verificar hidratación + click. Es DB-gated; lo corre el dev, pero el cierre exige evidencia.
