HU-5 · Query getVersionChain

Vamos a agregar una query GraphQL nueva al backend object-manager (la API del proyecto up1 — CRUD multi-tenant sobre objetos de negocio definidos por schema). La query getVersionChain(objectType, instanceId) devuelve todo el linaje de versiones de una instancia: dado un registro cualquiera de una cadena de versiones, reconstruye la cadena completa y la devuelve ordenada. Es el Ladrillo 3 del versionamiento de SP3 — el que permite que la UI muestre el historial "v1 → v2 → v3" de, por ejemplo, una Activity. No cambia datos: solo lee.

TL;DR — Qué hay: HU-4 (TICKET-038, ya cerrado) dejó persistida en la DB una config de versionamiento por objeto (core_ObjectDefinition.versioningConfig) y un FK reflexivo (previousVersionId) que encadena versiones. Qué se hará: una query genérica de solo-lectura que sigue ese FK en ambas direcciones, arma el linaje, lo ordena por número de versión ascendente y marca isLatest/versionNumber por instancia, respetando RBAC. Por qué: sin ella la UI no puede listar el historial de versiones; es la pieza de lectura del sistema de versionado.

Las bases: conceptos del dominio

Cinco ladrillos conceptuales sostienen el caso. Los dos primeros (config + FK reflexivo) son el corazón: definen cómo el sistema sabe que un objeto versiona y cómo encadena versiones.

versioningConfig

Columna Json? en core_ObjectDefinition (tabla que describe cada tipo de objeto). Guarda { versioning: { linkageField, versionField, versionStrategy } }. Es null si el objeto no versiona. La fuente de verdad de "este tipo es versionable y así se encadena".

linkageField (FK reflexivo)

Nombre del campo que apunta a la versión anterior — en Activity es previousVersionId. Una versión apunta a su predecesora; la raíz tiene el campo en null. Recorriéndolo se reconstruye el linaje.

versionField + strategy increment

Campo entero del número de versión (version: Int). En SP3 la única estrategia es increment: cada versión nueva suma 1. Es el criterio de orden canónico de la cadena.

RBAC three-layer / withObjectAuth

El patrón de autorización del proyecto. withObjectAuth('view', resolver) envuelve el resolver y verifica permiso a nivel de tipo de objeto antes de ejecutar. Para filtrado por fila se usa getBusinessContextFilter (como en listInstances).

SDL estático + acceso dinámico a Prisma

El SDL GraphQL vive escrito a mano en object-manager/src/graphql/typeDefs/static.js (no hay type Instance genérico — el equivalente es InstanceResult { id, data, extended }). Como el objectType es un parámetro string, el resolver accede a la tabla vía prisma[modelName] (modelName = objectType con primera letra minúscula).

Estado actual: cómo HU-4 ya lee la config

No partimos de cero. La mutación createInstance (rama asNewVersion, HU-3) ya lee versioningConfig y lanza el error de dominio que nuestra query reusa. Este snippet real (instance.resolver.js:2222) es el patrón a imitar para leer la config y rechazar objetos no versionables: 

// instance.resolver.js — patrón existente que getVersionChain reusa
const objDef = await prisma.core_ObjectDefinition.findUnique({
  where: { name: objectType },
  select: { versioningConfig: true },
});
const versioningConfig = objDef?.versioningConfig?.versioning ?? null;
if (!versioningConfig) {
  throw new Error('OBJECT_NOT_VERSIONABLE'); // mismo error que pide HU-5
}
const { linkageField, versionField } = versioningConfig;

El proyecto lanza errores de dominio con throw new Error('CODIGO_STRING') (no clases custom), y los unit tests mockean withObjectAuth como pass-through. Eso fija el estilo de implementación y de testing de esta HU.

Hacia adelante: el flujo de la query

A alto nivel, el resolver hace 4 cosas: (1) lee la config y valida que el objeto versione, (2) reconstruye el linaje siguiendo el FK reflexivo en ambas direcciones, (3) aplica RBAC a las instancias del linaje, (4) ordena por version ascendente y computa los flags. El diagrama muestra la ruta feliz y la de rechazo.

  D --> F[map: isLatest = ultima
versionNumber = i+1]
  F --> G[[Instance!]! ordenado]

El invariante del orden

En SP3 el linaje se ordena por versionField (Int) ascendente, no por createdAt.
Corolario: si un draft viejo se retoma, su createdAt sería incoherente con el orden real de versiones — por eso createdAt queda solo como tiebreaker. Nota v5 del diseño: cuando SP4 habilite la strategy user-provided + version String, el orden pasará a seguir el linaje (linkageField); hoy increment + Int es la única vía.

Q&A — ¿entendiste el caso?

¿De qué se trata el caso?
De agregar una query GraphQL de solo-lectura, getVersionChain(objectType, instanceId), al backend object-manager. Devuelve el linaje completo de versiones de una instancia (todas las versiones de su cadena), ordenado por número de versión ascendente, con flags isLatest y versionNumber por instancia. Es la pieza de lectura del sistema de versionamiento de SP3 (Ladrillo 3).
¿Qué se va a hacer (alto nivel) y por qué importa?
Un resolver genérico que: lee versioningConfig del tipo, valida que versione, reconstruye el linaje siguiendo el FK reflexivo previousVersionId en ambas direcciones, aplica RBAC y ordena por version Int ascendente computando los flags. Importa porque sin esta query la UI no puede mostrar el historial "v1→v2→v3" de un objeto; es lo que hace visible el versionamiento que HU-3/HU-4 dejaron escribiendo datos.
¿Qué hipótesis quedaron abiertas y cuál es la más crítica?
Dos hipótesis se asumieron confirmadas en intake: H1 — un linaje pequeño (≤10 versiones) no necesita CTE recursivo, basta un walk simple (Activity típica tiene 1-5 versiones). H2 — el RBAC se resuelve con el patrón existente (withObjectAuth + filtro post-fetch). La más crítica de verificar empíricamente es H2 en S2: hay que confirmar que el filtro de contexto de negocio se compone bien sobre una query por id IN (linaje), porque getInstance hoy no aplica filtro por fila y listInstances sí — getVersionChain está en el medio.
¿Qué decisiones críticas se tomaron en el intake y por qué?
El intake fue mayormente lineal (la HU venía muy especificada desde el diseño v5). La decisión técnica de fondo ya estaba tomada en diseño (Ladrillo 3): query genérica nueva con resolver custom, orden por version Int (no createdAt). Lo que el intake fijó es el alcance de validación: como ningún objeto es versionable aún en seed (HU-8 abierta), se decidió cubrir con unit tests sobre Prisma mockeado + test de rechazo, y documentar que el happy-path contra DB real queda gated por HU-8. No hubo alternativas comparables que justifiquen una matriz de decisión.
