La decisión que rigió el diseño

DEC-LOCAL-01 — cómo enforcear sin romper flujos ajenos.

Contexto

Enforcear RBAC server-side sobre createInstance, resolver genérico compartido por ~14 call-sites de creación scratch.

Decisión

Opt-in declarativo: el core lee requiredCapability de la metadata y enforce solo si está presente. Sin declaración → permite.

Resultado

Cero impacto colateral (unit test scratch lo prueba) + soberanía del mod preservada. Promovido a RULE-core-020.

Lecciones aprendidas

¿Por qué la cobertura dual salió más simple de lo previsto?
Porque el clone de objeto base y el de RecordType/Modalidad consumen el mismo prefillFrom resuelto una sola vez (antes del RecordType early-return). Ubicar el check ahí cubre ambos con una línea. Lección: mapear el flujo real del resolver antes de asumir que dos paths necesitan dos checks — el caveat conservador del intake (L1) sobre-estimó la complejidad.
¿Qué confirmó que el opt-in no rompe nada?
El unit test de scratch: un createInstance sin asNewVersion/prefillFrom.source nunca surface requiredCapability (el helper retorna temprano con source==null), así que checkCapability jamás se invoca. El test asserta not.toHaveBeenCalled() — falla si el enforcement se activa de más.
¿Cómo se demostró el gating sin dos usuarios distintos?
Con el selector de rol de un mismo usuario (eduardo.bacon): rol Admin/Consultor (con la cap) muestra "Nueva versión"/"Clonar"; el mismo Consultor con la cap removida (toggle reversible en DB, restaurado) las oculta. getMyPermissions es scoped por selectedRole, así que el rol activo determina las caps efectivas. Coordinador no servía (sin acceso al mod).
¿Por qué el ticket cierra con trabajo en backlog?
El entregable (gating RBAC) está implementado, commiteado y validado (UI live + backend unit-proven). Lo que queda — npm run codegen para propagar la metadata al registry (confirmación backend live) + push de las 3 ramas — es DB-gated/acción del dev y quedó como backlog B1 (should, no bloquea cierre por DET-17).
