SP7 · P1: Requisitos de asignatura (editor Y/O + alerta de impacto)

Este ticket (UPONE-1378) construye la primera interfaz para editar los prerrequisitos y correquisitos de una asignatura como un arbol de condiciones combinables con Y (todas) y O (al menos una). Hoy el modelo de datos que respalda esas condiciones (el objeto requirement) ya existe y se llena por seed, pero no hay pantalla para crearlo ni editarlo. Este documento te da el mapa completo antes de disenar la solucion: sobre que bases te paras, que hay alrededor del cambio, y hacia donde vamos.

TL;DR — Hay que darle al configurador curricular un editor visual del arbol Y/O de requisitos de una Activity (curso), con alta por un modal de 2 pasos, edicion anidable a cualquier profundidad, y una alerta que avisa que planes se ven afectados al cambiar un requisito. El modelo requirement ya esta construido (SP5); lo que falta es la UI mas un habilitador de backend no trivial: hoy el update de estos RecordTypes no existe (el create ya usa el RT literal — premisa original refutada en design, DEC-LOCAL-01). Ese habilitador (BL-1, acotado a update + recableo del guard) es el riesgo numero uno y se verifica primero. Adecuacion 2026-07-27: el circuito con la malla (REQ-11) exige que la malla respete el arbol Y/O. Se descubrio que la evaluacion actual lo aplana (convierte O en Y, ignora advisory/anidamiento). Por eso se agrego REQ-14: un evaluador recursivo fiel que reemplaza al aplanado antes de extender la malla. El plan pasa de 8 a 9 sessions (~20 SP).

Las bases: el dominio de requirement

Todo el ticket se apoya sobre el objeto requirement y sus tres RecordTypes. Un RecordType (RT) es una "variante tipada" de un objeto base: comparten la tabla base pero cada uno agrega sus propios campos. Estas diez tarjetas son el vocabulario minimo para entender el resto del documento.

requirement

Objeto Composite (arbol por parentId) con base polimorfica ownerType/ownerId (curriculum, activity u offering). Campos base: effect, label (requerido), isHardRule, negate, position.

Group (RT)

Nodo combinador. combinator = AND (Y, todas) u OR (O, al menos una), minToSatisfy (K de N) y creditsRequired (bloque electivo). Es el unico nodo que anida hijos.

RecordState (RT)

Hoja "aprobar/cursar un curso". targetType=activity, targetId, mustBe (Approved/Taken), thresholdMinGrade, timing (Before/Concurrent/Either, para correquisito).

MetricThreshold (RT)

Hoja "umbral de metrica". metric=Credits, operator (Gte/Gt/Eq/Lt/Lte), value (ej. 60 creditos), scope (plan/category).

RT literal vs base

La plataforma persiste un RT nombrando el objectType con el nombre literal (rt__Group__requirement), lo que dispara el bucket-split que separa y guarda los campos del RT. Crear con el nombre base (REQUIREMENT) NO separa esos campos: es la raiz del gap BL-1.

Guard de plan Active

requirementActivityGuard.js (SP5, MC-09) bloquea crear o editar requisitos de una Activity que ya esta en un Curriculum con status=Active, obligando a versionar. Solo Active bloquea; Draft y Archived no.

CompositeSectionTree

Componente hermano del mod que edita OTRO arbol (secciones de evaluacion). Su modal es de 1 solo paso y no tiene combinador. Es un precedente PARCIAL: reusamos sus piezas de bajo nivel (operaciones de arbol y navegacion por teclado), no el componente entero.

validateBaseFieldFormats

Validador de core (jsonFieldValidator.resolver.js) que ya enforza minimum/maximum a nivel API leyendo la definicion del campo. REQ-09 (no negativos) lo reusa: solo agregamos "minimum": 0 al JSON del mod, sin construir motor nuevo.

Grafo de prerrequisitos

Al conectar cursos con RecordState, se forma un grafo entre Activities. CAP-CUR-004 (regla del cliente) prohibe ciclos cruzados (A pide B, B pide A). Hoy la deteccion de ciclos solo mira dentro de un mismo arbol; falta el recorrido transitivo entre Activities.

Evaluador de la malla (REQ-14)

Cuando la malla arma el plan, chequea que cada curso tenga sus prerrequisitos colocados antes. Hoy findMissingPrereqs aplana el arbol (Y global, ignora O/anidamiento/advisory). REQ-14 lo reemplaza por un evaluador recursivo fiel: respeta combinator, anidamiento, isHardRule, negate y creditsRequired. Hoja = colocado antes (estructural).

Como encaja el editor en el flujo

El editor vive en una pestana nueva de la ficha de la Activity. El usuario arma el arbol, y al guardar cada nodo viaja por la misma capa de persistencia que el resto de la plataforma. El gap BL-1, en codigo

Por que BL-1 es el corazon del riesgo: el resolver que hace editable un RT limita hoy su patron a curricularsection. Mientras no incluya requirement, el arbol se puede crear pero no editar. La ampliacion es de una linea, pero toca codigo compartido (por eso la regresion de CurricularSection es obligatoria). 

// polymorphicUpdate.resolver.js:199 (mod curriculum-design) - HOY
const RT_PATTERN = /^rt__([a-zA-Z0-9_]+)__(curricularsection)$/;

// objetivo BL-1: incluir requirement para que updateInstance lo reconozca
const RT_PATTERN = /^rt__([a-zA-Z0-9_]+)__(curricularsection|requirement)$/;

// y el create (MCP requirement-write.ts:~209) debe pasar de base a RT literal:
//   REQUIREMENT  ->  typedRecordName(recordType)  == rt__Group__requirement

Approach del editor: por que arbol anidable y no "vias"

La maqueta de SP6 dibujaba el requisito como "vias" (un OR de varios AND, dos niveles). El intake eligio el arbol generico anidable. La razon la fija el propio dato de prueba: el seed EST200 tiene tres niveles, y REQ-03 exige que el arbol "se reconstruya identico al reabrir". Con "vias" los casos de mas de dos niveles no serian editables con fidelidad. La fila destacada es la que llevamos al draft.

Consecuencia directa para tu trabajo: la maqueta SP6 NO sirve como draft (por eso este ticket exige un draft nuevo, DET-18), y el modal de 2 pasos es UI nueva que toma piezas de bajo nivel de CompositeSectionTree, no una extension de ese componente.

Hacia adelante: el plan de 9 sessions

El plan del spec ordena el trabajo riesgo-primero. La session 1 no es UI: es el habilitador de backend y su verificacion runtime, porque de el depende que todo lo visual pueda guardar. Backend primero (S1-S3), editor FE despues (S4-S6), y el circuito con la malla al final (S7 evaluador fiel, S8 superficie), con el cierre declarativo + docs + smoke en S9. La adecuacion 2026-07-27 agrego S7 y corrio REQ-11 a S8.

Q&A: comprobA que entendiste el caso

De que se trata el caso?
De dar la primera UI para editar los prerrequisitos y correquisitos de una asignatura como un arbol de condiciones Y/O, con alta por modal de 2 pasos y una alerta que avisa que planes se afectan al cambiar un requisito. El modelo ya existe; falta la pantalla y un habilitador de backend.
Que se va a hacer a alto nivel y por que importa?
Un editor FE mod-native (pestana + modal + arbol anidable + alerta) sobre el objeto requirement, mas el fix de backend BL-1 que lo hace realmente editable. Importa porque hoy los requisitos solo se pueden cargar por seed; el configurador curricular no puede definir la malla sin depender de un ingeniero.
Que hipotesis quedo abierta y cual es la mas critica de verificar primero?
La mas critica es AQ-1: que el fix BL-1 (create con RT literal + update reconociendo requirement) realmente persista y reconstruya el arbol end to end. No se verifico con el server corriendo en el intake, y sin eso el editor no guarda. Es la primera tarea de la session 1.
Que decisiones criticas se tomaron en el intake y por que esas?
Seis decisiones de alcance: (1) convencion RT literal y BL-1 ampliado; (2) arbol anidable a cualquier profundidad, no "vias" (por EST200 con 3 niveles); (3) permitir eliminar nodos con guard de delete; (4) solo 3 familias con respaldo en el modelo; (5) validacion completa de ciclos cruzados (CAP-CUR-004), que amplia el alcance mas alla de los 8 SP publicados; (6) no negativos reusando el validador de core. La numero 2 y la numero 5 son las que mas mueven el esfuerzo. La adecuacion 2026-07-27 sumo una septima: (7) la malla evalua el arbol de forma fiel (REQ-14, evaluador recursivo) en vez de aplanarlo — es la que agrega la nueva S7 y sube el estimado a ~20 SP.
