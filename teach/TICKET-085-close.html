Lo que dejó MC-05 — la malla, en grilla

Cerramos MC-05 (UPONE-1348): la pestaña "Malla curricular" del detalle de un Plan dejó de ser una tabla y ahora es la vista por período — un componente full-page del mod (curriculum-mesh) con grid de columnas, tarjetas, barra de resumen y gating de edición. Este documento mira hacia atrás: qué se construyó, cómo evolucionaron las hipótesis, qué decidimos y qué aprendimos. (El contexto de partida está en el teach-intake.)

TL;DR — Se entregó REQ-01/03/04 (grid por período + badge electivo, barra de resumen, gating canEdit(status,mode)) y el MUST de REQ-02 (la pestaña del RecordDetail renderiza el element). La acción de listado de REQ-02 (SHOULD) se difirió a backlog porque el motor de layouts no soporta navegación-a-tab. El valor real del cierre: dos bugs de runtime cazados por el dual-judge (relación GraphQL mal nombrada/ubicada) que habrían roto la malla en producción, confirmados verificando el resolver real.

Dos sessions, ~1080 líneas. La S1 puso el motor (lógica + datos + render); la S2 lo enchufó (config + gating + stories).

Evolución de hipótesis

✓ H1 confirmada — "el entrypoint vía config del mod evita tocar core". Quedó probada: el swap se hizo 100% en config de layouts del mod (tab + element), sin registrar layoutType en core. La frontera mod-only se sostuvo de punta a punta.
⚠ Hipótesis implícita que falló — "leer la relación Activity de item.extended['Activity']". El resolver real entrega las relaciones de FK no-core en item.data['activity'] (lowercase). No era hipótesis del Triage sino un supuesto del primer código — y el dual-judge lo cazó.

El caso que enseña — la relación fantasma

Contexto

El primer composable leía la asignatura desde extended['Activity']. Tests verdes, lint limpio, tipos OK. Un juez aprobó; el otro marcó WARNING.

Decisión

Ante la discrepancia (DET-35 → suspect), no se confió en ningún juez: se verificó el resolver real (getRelationName) y el precedente (buildTree.ts).

Resultado

Confirmado bug: relación en data['activity'] (lowercase). Fix: pickRelation(data ?? extended) + relations:['activity']. Re-judge: APPROVED.

✗ Si no se hubiera cazado: en producción la malla habría mostrado UUIDs en lugar de códigos, nombres vacíos y créditos en 0 — y los tests unitarios (lógica pura) NO lo habrían detectado, porque el bug vive en la capa de carga, no en la lógica.

El invariante se mantuvo

Cero core: todo quedó en el mod (modsComponents/ + config/layouts/ + lang/), sin layoutType nuevo.
Corolario: el element se registra y los layouts se aplican vía npm run sync (DB-gated) — el smoke runtime lo corre el dev, no es parte del cierre de código.

Lessons learned

L1 — relaciones en listInstances: las FK no-core se incluyen en item.data[rel] con rel en lowercase (activityId→activity), per getRelationName. Leer extended['Activity'] falla silenciosamente. Candidato a RULE del módulo platform.
L2 — rowActions y navegación a tab: el motor de layouts no tiene un rowAction que abra el detalle en una pestaña específica. modal+RecordDetail fuerza mode:create sin instanceId. Candidato a BUG/RULE del módulo layout.
Proceso: el dual-judge adversarial ganó su lugar — un juez aprobó código con un bug de runtime; el segundo lo marcó; la verificación contra el código real (no contra la opinión de los jueces) lo confirmó. La lógica pura testeable no alcanza si el bug vive en la capa de integración.

Q&A — para quien retoma

¿Dónde vive la malla y cómo se accede?
Componente CurriculumMeshElement.vue (type curriculum-mesh) en mods/curriculum-design/modsComponents/CurriculumMesh/. Se accede por la pestaña "Malla curricular" del detalle del Plan (default_Curriculum_view/_edit.json, prop planId={{parentId}}).
¿Por qué la lógica está en un .ts aparte?
Para testearla sin Vue/GraphQL: agrupación, badge, resumen y gating son funciones puras (16 tests, TC-01..05). El composable sólo carga y normaliza; el componente sólo renderiza.
¿Qué falta / qué sigue?
(1) Backlog B-1: acción "Malla curricular" en el listado (requiere soporte del motor para navegación-a-tab). (2) MC-06: alta/edición de asignaturas (drag&drop, modal de catálogo) — el placeholder "+ Asignatura" gated ya está. (3) MC-08: filtros interactivos (las líneas hoy son leyenda estática). (4) Correr npm run sync + smoke en UPU.
¿Qué NO testean los tests unitarios?
La capa de carga GraphQL (nombres de relación, mapeo de item.data). Ese fue justo el lugar del bug. Validación: smoke DB-gated por el dev tras el sync.
