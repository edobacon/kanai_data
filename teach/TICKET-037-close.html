Cierre · HU-2 prefillFrom declarativo

El ticket arrancó con un análisis de impacto contra el código real del sprint, y eso definió todo: HU-2 no era "construir prefill", era cablear la capa declarativa sobre primitivos que 033 y 036 ya dejaron. El intake original asumía cosas que el código contradecía. Este cierre cuenta qué se verificó, las 4 decisiones que salieron del análisis, y la única pieza genuinamente nueva (directChildren).

TL;DR — HU-2 cableó el prefillFrom declarativo en 3 costuras + 1 rama nueva: (1) abrió el gate de persistencia del codegen a (versioning || prefillFrom); (2) validador prefillFrom build-time; (3) el resolver lee versioningConfig.prefillFrom del registry y lo combina con el runtime (precedencia: declarativo=política, runtime=target, activación gated por source); (4) deepClone de relación directa vía bloque nuevo directChildren. Lo no obvio: 033 dejó el gate cerrado a propósito ("se contempla en HU-2"), y el modelo no declara hijos 1-N directos — por eso la relación directa necesitó su propio bloque, como 033 hizo con polymorphicChildren. Resultado: 518/518 verde, regresión codegen empírica en 6 tenants limpia, 0 impacto en ~64 callers.

La historia del caso

Contexto (lo que creíamos)

El intake describía "implementar prefillFrom declarativo": validar+persistir, resolver lee el registry, deepClone polimórfico+directo. Asumía que casi todo era nuevo.

Decisión (al ver el código)

El trabajo real eran 3 costuras + cablear el resolver. La relación directa no tenía consumidor ni metadata → bloque nuevo directChildren.

Resultado

Qué se construyó (las 3 costuras + la rama nueva)

Casi todo el cambio cabe sobre código existente. El corazón: abrir un gate de una línea, leer el registry gated por source, y un helper directo espejo del polimórfico. 

// 1. gate de persistencia (generatePrismaSchema.js) — antes: versioning ? ... : null
const versioningConfig = (versioning || prefillFrom)
  ? { versioning: versioning || null, prefillFrom: prefillFrom || null } : null;

// 2. resolver combina declarativo (registry) + runtime, gated por source (prefill-from-source.js)
export async function resolveEffectivePrefillFrom({ prisma, objectType, prefillFrom }) {
  if (prefillFrom?.source == null) return prefillFrom;   // sin source: ni lee registry ni activa
  const declared = (await prisma.core_ObjectDefinition.findUnique(...))?.versioningConfig?.prefillFrom;
  return { ...prefillFrom, exclude: union(declared.exclude, prefillFrom.exclude),
                          deepClone: union(declared.deepClone, prefillFrom.deepClone) };
}

// 3. routing del deepClone (instance.resolver.js): particiona poly vs directo y fusiona mapas
const polyAliases = deepClone.filter(a => polyNames.has(a));
const directAliases = deepClone.filter(a => directNames.has(a));  // directChildren (nuevo)

Lecciones aprendidas

L1 — Un cambio de comportamiento del spec puede requerir tocar un test de otro ticket

El gate de DEC-A invirtió el contrato que 033 había codificado en su TC-13b (standalone → null). Hubo que actualizarlo al nuevo contrato; 033 ya lo anticipaba. Cross-ticket, mandado por spec.

L2 — Separar lo que toca la DB de lo que toca los archivos generados

El cambio de codegen escribe al registry (DB), no a schema.prisma → la regresión de schemas es vacía por construcción. Verificado empíricamente con DB en Docker.

L3 — Correr codegen sobre tenants stale revela drift de otros tickets

UCASMT/UCENG/UCPLN/TEST tenían schemas stale de 034/035. Revertido para no contaminar el diff de HU-2; regenerado y commiteado aparte como UPONE-1220.

L4 — Cuando no hay metadata declarativa, créala explícita (no introspección frágil)

directChildren nació porque el JSON del padre no lista sus hijos 1-N. Igual que polymorphicChildren — un bloque declarativo estable supera al DMMF en runtime.

L5 (proceso) — No materializar bloques de session futuros (DET-28 lazy)

Materializar S2/S3/S4 de una vez hizo que HC los mostrara todos "en ejecución" (regla: bloque con tareas + ticket vivo → in_progress). Materializar lazy con open-session N; y registrar cada checkbox por la ruta canónica (DET-29), no Edit libre.

Q&A de cierre

¿Cómo declaro la política de clonación de un tipo nuevo?
En el JSON del objeto: metadata.prefillFrom = { exclude: [...], deepClone: [...] }. Cada entry de deepClone debe estar en metadata.polymorphicChildren (hijos por ownerType/ownerId) o metadata.directChildren (hijos por FK directa). El codegen lo valida y persiste a versioningConfig. Ver docs/prefill-capability.md.
¿Por qué un objeto con prefillFrom declarado no clona solo?
Porque la activación está gated por data.prefillFrom.source runtime. La config declarativa solo aporta defaults de exclude/deepClone; sin un source en la mutation, createInstance se comporta idéntico a hoy. Eso protege a los ~64 callers existentes.
¿Qué quedó como deuda/residual?
(1) directChildren no tiene consumidor en SP3 (Activity→CurricularSection es polimórfico) — es capacidad para futuros adoptantes. (2) La redacción de REQ-02/REQ-04 del spec dice "relación Prisma directa del objeto"; la implementación lo concretó como bloque directChildren (ver L4 / DEC-C). (3) SP sugerido (4) por heurística diverge del estimado (~2); recalibrable con dkc-sp-calibration.
Si HU-4 (versioning declarativo) se construye encima, ¿qué reusa?
El mismo gate de persistencia (ya abierto a versioning||prefillFrom) y la misma columna versioningConfig. HU-4 agregará la lectura runtime de versioningConfig.versioning (hoy solo se persiste; nadie la lee aún).
