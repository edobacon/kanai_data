Validación restrictiva de requisitos en planes publicados (MC-09)

Un requisito (requirement) es una regla académica que cuelga de una asignatura (ownerType='activity'): prerrequisitos, gates de progresión, etc. Cuando esa asignatura ya forma parte de una malla publicada (un Curriculum con status='Active'), editar sus requisitos invalidaría planes que ya están vigentes. MC-09 introduce un guard restrictivo que bloquea esa mutación y obliga a versionar el programa. Este documento orienta en tres direcciones: las bases del dominio (qué es un requirement y cómo se detecta "publicado"), el entorno (las restricciones del mod que condicionan dónde vive el guard) y el plan de sesiones.

TL;DR — La regla es 100% BE: requirement no tiene resolver propio, así que el guard se inyecta en los dos overrides singleton del mod (create + update) — no en un archivo nuevo (CONSTRAINT H7). "Publicado" = status='Active'. En SP5 no hay editor de requisitos por UI (eso es S7-01/SP6), así que la regla actúa a nivel de mutación (API/MCP/seed) y el mensaje del error es el canal accionable. La única superficie FE de SP5 es una alerta "malla no editable" en la vista de malla (REQ-04).

Glosario del dominio

requirement (owner polimórfico)

Regla académica. El dueño es polimórfico: ownerType ∈ curriculum|activity|offering + ownerId (string, sin FK en DB — validación por capa app, REQ-06 de MC-03). MC-09 sólo mira los de ownerType='activity'.

planEntry

La asignatura colocada en un plan. Liga activityId (string) → Activity y planId → Curriculum. Es el puente que dice "esta Activity está en estos planes".

Curriculum.status

Enum plano ['Draft','Active','Archived'], static_default:'Draft'. Sin workflow ("no workflow formal en v1"). "Publicado" = Active (audit C-2).

CONSTRAINT H7

El scanner del platform junta todos los *Mutation exports del mod y el último gana en colisión. ⇒ un solo override por campo de mutación. Ya existen: createInstance en sectionValidation, updateInstance en polymorphicUpdate.

helper-guard (patrón)

Reglas de dominio como funciones puras { prisma, ...ids } que lanzan Error(`${ERR.CODE}: mensaje`). Plantilla: categoryGuard.js (assertNoEntriesForCategory). Testeable con prisma mockeado.

canEdit (gate de malla)

canEdit(status, mode) en curriculumMesh.logic.ts gatea las acciones de la malla (MC-05/06). Hoy hardcodea status==='Draft'. REQ-04 lo apoya en una constante compartida.

Cómo muta hoy un requirement (sin guard)

Como requirement no tiene resolver propio, hoy toda mutación cae al CRUD genérico del platform vía los dos overrides del mod, sin ninguna validación de "plan publicado". Ahí es donde MC-09 inserta el guard. 

flowchart TD
  M[Mutacion requirement\nownerType=activity] --> O{objectType?}
  O -- create --> C[sectionValidation.createInstance\nvalidateSectionCreate]
  O -- update --> U[polymorphicUpdate.updateInstance\nbranch !RT_PATTERN]
  C --> G[[guard MC-09\nassertActivityNotInActivePlan]]
  U --> G
  G --> Q1[planEntry.findMany\nwhere activityId = ownerId]
  Q1 --> Q2{planIds en\nCurriculum.status=Active?}
  Q2 -- si --> X[RECHAZA\nversiona el programa]
  Q2 -- no / sin planes --> D[delega al generic\nmutacion normal]

El guard hace short-circuit si ownerType!=='activity' (no toca curriculum/offering) y es no-op si la Activity sólo está en planes Draft o sin planes.

Restricciones del entorno

H7 — un override por mutación (dónde vive el guard) — No se puede crear un requirement.resolver.js que exporte createInstance/updateInstance: clobbearía los overrides existentes. El guard debe inyectarse dentro de validateSectionCreate (create) y del branch genérico de polymorphicUpdate (update).
Sin editor de requisitos en SP5 — La UI de edición de requisitos es S7-01 (SP6). En SP5 la regla actúa sólo a nivel de mutación (API/MCP/seed); el mensaje del error es el canal accionable. La única superficie FE de SP5 es la alerta "malla no editable" (REQ-04), que vive en la vista de malla ya existente (MC-05).
Sync de dos pasos (RULE-mods-050) — Cambios en lang/*.json y componentes del mod requieren layout npm run sync + suite npm run sync + restart. El smoke visual de la alerta es DB-gated (tenant con plan Active abierto en edición).

Preguntas abiertas a explorar

Incógnitas que el dev debe validar durante la ejecución — no son conclusiones.

¿Sólo Active bloquea, o también Archived?
El enum tiene un tercer estado, Archived. La reunión y el audit C-2 definen "publicado = Active". Archived es histórico (protegido por inmutabilidad de versión, no por este guard). A confirmar en design: bloquear sólo Active; si el negocio quisiera proteger Archived, es un cambio de alcance.
En el path de update, ¿el payload trae siempre ownerType/ownerId?
Una edición parcial puede no incluir el owner. El guard de update debe resolver el owner efectivo del registro (por id) cuando el data no lo trae — mismo patrón que assertCreditRangeOnUpdate.
¿Dónde debería vivir el criterio "editable/publicado" para no hardcodearlo dos veces?
Idealmente una sola fuente (config/metadata) consumida por BE y FE. A explorar: ¿el core expone la metadata del objeto al FE? ¿Curriculum tiene una config de versionamiento que defina estos estados? Si el core limita, la alternativa es una constante por capa derivada del enum.
¿El guard rompe la creación de requisitos en planes Draft o de otros ownerType?
No debería: short-circuit por ownerType y chequeo explícito de status='Active'. El análisis de impacto (REQ-03) y los tests TC-02/TC-03 + la suite del mod lo verifican.
