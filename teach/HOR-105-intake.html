Mutation testing gate para el flujo de DKC

DKC ya manda que los tests "fallen cuando la condición no se cumple" (DET-7) y que el cierre sea "por evidencia" (DET-13). Pero hoy nada mide si los tests realmente sirven: una suite verde solo prueba que el código no explota, no que las aserciones distingan un defecto de su ausencia. Este ticket introduce mutation testing — inyectar defectos a propósito y exigir que algún test falle — como respaldo empírico de la dimensión #4 (testing) de DET-23. El desafío central no es la técnica (es conocida) sino ubicarla sin enlentecer el flujo, porque es compute-bound por naturaleza.

TL;DR — Qué hay: un gate de calidad (DET-23 dim testing) que se juzga a ojo. Qué se hará: un comando dkc-mutate que muta solo el diff de la session, corre solo los tests que cubren cada línea, en un worktree aislado en background; el score alimenta la dimensión testing en modo warn. Por qué: hace empírica una regla que hoy es declarativa, sin meter latencia en el camino crítico (async + 3 palancas de velocidad).

Conceptos clave — las bases

Mutante

Una copia del código con UN defecto inyectado (ej. <=→<, ==→!=, return x→return null).

Mutante muerto

Al menos un test falla con el defecto presente. La red lo atrapó: bien.

Mutante sobreviviente

Toda la suite sigue verde con el defecto. Un agujero en la red = un test que falta, no un bug de producción.

Mutation score

killed / total. Mide la calidad de la suite, no la cobertura. 100% cobertura puede tener score bajo.

Coverage-scoped run

Por cada mutante, correr solo los tests que ejercitan esa línea (no la suite entera). La palanca de velocidad grande.

Test-gap

Lo que produce un sobreviviente: un test faltante. Es aditivo y seguro de diferir — no toca producción.

Por qué no copiar el mutador de referencia

Naïve (harness-sdd · mutate.py)

Muta el archivo entero; corre la suite completa por cada mutante.

+ Simple, sin dependencias, ~200 líneas.

− Costo O(mutantes × suite). Viable en un CLI de juguete; inviable en up1/horadric.

Scoped (este ticket · dkc-mutate)

Muta solo el diff de la session; por mutante corre solo los tests que cubren esa línea; incremental + async en worktree.

+ Costo O(mutantes_del_diff × tests_que_cubren). 10-100× más rápido.

− Apoyado en Stryker/mutmut (dependencia por stack) + requiere mapa de cobertura previo.

El entorno — dependencias y restricciones

ℹ DETs que ya hacen el trabajo pesado — DET-17 (backlog must bloquea cierre) garantiza que ningún test-gap se pierda; G-open (gate de apertura de session) es el punto de reconciliación de findings críticos. No se inventan mecanismos nuevos — se cablean los existentes.
⚠ Tocar el catálogo de DETs propaga — agregar DET-31 cambia el conteo de reglas en CLAUDE.md global, DECKARD.md y el bloque condensado. Hay que regenerar con dkc-export-rules --global (NO editar a mano) y propagar el conteo (DET-16).
✗ El worktree async NUNCA toca el working tree del dev — la mutación reescribe archivos para inyectar defectos; debe ocurrir en un worktree git aislado, jamás in-place. Riesgo conocido: la contaminación git observada con el reviewer aislado. El agente es read-only sobre el repo principal.

El plan — medir antes de cablear

S1 — Prototipo dkc-mutate + medición de latencia (⚑ fuerte)

El riesgo real (H1) es la latencia. S1 construye el motor y mide wall-clock sobre un diff real ANTES de comprometer DETs/gates. Si la medición mata H1, el diseño se revisa.

S2 — Agente mutation_tester + schema JSON

Espejo del agente tester existente: corre dkc-mutate, reporta score + sobrevivientes + severidad.

S3 — DET-31 + bloque mutation en config (⚑ fuerte)

La regla + el threshold config-driven por proyecto, patrón override como tiers. Regenerar condensado.

S4 — Cableado de gates en modo WARN (⚑ fuerte)

Dispatch async en S{N}.GATE + reconciliación híbrida en G-open + bloqueo en close. Warn-first: no bloquea mientras se calibra.
