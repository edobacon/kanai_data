SP6 · P5 — Eliminacion segura con cascada, restrict y DataLog

Este intake prepara el terreno para arreglar una inconsistencia del borrado generico de UP1: el core ya puede razonar sobre hijos polimorficos para clone/versionado, pero el delete no recorre el mismo grafo. El resultado actual puede dejar huerfanos o esconder impactos. Este teaching explica las bases del flujo de delete, el entorno que lo condiciona y el camino de diseno sin aplicar cambios a los repos de UP1.

TL;DR — Que hay: `deleteBulkInstances` y `deleteInstance` protegen FKs reales, pero no modelan todo el arbol polimorfico de curriculum-design (`ownerType`/`ownerId`, RecordTypes y self-ref). Que se hara: disenar un motor core de preview + delete real con `Cascade` para hijos poseidos, `Restrict` para referencias externas/versiones, y `core_DataLog` por cada nodo eliminado. Por que: es un fix de plataforma, no un parche del mod; UI, API y MCP deben borrar con el mismo contrato y sin huerfanos.

Las bases — conceptos que hay que tener en la cabeza

El delete de P5 cruza core, mod, UI y MCP. Estos conceptos son el piso: sin ellos se puede confundir un hijo de dominio con una fila tecnica o tratar una relacion externa como si fuera un hijo poseido.

Hard delete

Borrado fisico de registros. En SP6 se descarto soft delete porque la lectura generica de core no filtra flags custom de cada mod.

Cascade

Eliminar junto con el padre los hijos poseidos y exclusivos dentro del mismo subarbol. Debe ser explicito por relacion, no default global.

Restrict

Bloquear todo el borrado si un nodo esta referenciado desde fuera del subarbol o por una cadena de version. El mensaje debe decir que resolver primero.

Hijo polimorfico

Registro que pertenece a padres variables mediante ownerType/ownerId. La base de datos no lo protege como FK real.

RecordType / subtipo

Capa de dominio sobre un objeto base, por ejemplo una seccion con tipo de plan, minor o perfil. El preview debe hablar en terminos entendibles para el usuario.

core_DataLog

Historial actual de core despues de P3/TICKET-102. Cada nodo eliminado por cascada debe generar su propia entrada, no solo el padre.

Las bases — como funciona hoy el delete

El flujo real de usuario empieza en RecordList y llega a deleteBulkInstances. El modal critico existe, pero hoy sus consecuencias son texto estatico. El punto debil esta entre la validacion de referencias reales y los hijos polimorficos: las FKs se pueden bloquear o cascadar, pero un ownerType/ownerId no se descubre por Prisma.

La sorpresa importante: P5 no es "poner Cascade por defecto". Hacerlo globalmente podria arrastrar datos de otros mods. El fix sano es construir el subarbol declarado, distinguir referencias internas de externas y solo entonces ejecutar el delete.

Hacia los lados — que rodea este ticket

P2 / UPONE-1379 — amplia la declaracion de hijos polimorficos que P5 debe consumir. El design debe asumir el nuevo objeto y completar lo que aun falte para delete, especialmente `AcademicProgram -> Curriculum` y requirements.
P3 / TICKET-102 — depreco ChangeLog como destino nuevo. P5 debe auditar borrados en `core_DataLog` hijo por hijo, usando snapshot pre-delete para no perder atribucion.
UI y MCP comparten preview — `CriticalWarningModal`, `cd_delete_section` y `delete_object` necesitan el mismo calculo de impacto. Si cada capa calcula distinto, el usuario confirma una cosa y el backend ejecuta otra.
No es una solucion contenida en el mod — un resolver local de curriculum-design dejaria inconsistentes `deleteBulkInstances`, `deleteInstance`, MCP y cualquier otro consumidor generico del core.
Invariante del diseno
Preview y delete real deben usar el mismo motor de grafo. Si el preview dice "se borran N hijos", el commit debe borrar exactamente ese subarbol o abortar completo con Restrict. No se aceptan deletes parciales.

Hacia adelante — orientacion del plan

La spec baja esto a sesiones ejecutables. El orden esperado va de core a mod y luego a UI/MCP, porque la UI no puede mostrar un impacto que el backend aun no sabe calcular.

S1 · Discovery ejecutable del grafo de delete

Confirmar metadata actual, gaps y tests seed disponibles para cada familia de dato.

S2 · Motor core de preview + restrict

Construir subarbol, detectar referencias externas y version chains, devolver impacto accionable.

S3 · Delete real transaccional + DataLog

Ejecutar cascada del mismo plan, auditar cada nodo y abortar completo ante Restrict.

S4 · Metadata curriculum-design

Completar declaraciones de hijos y semantica por relacion sin tocar otros mods.

S5 · UI/MCP + casos destructivos

Preview dinamico en modal y MCP; pruebas que verifican DB sin dato + DataLog por nodo.

Q&A de estudio

Por que esto va en object-manager y no solo en curriculum-design?
Porque el entrypoint real de UI usa `deleteBulkInstances` generico, y tambien existen `deleteInstance` y MCP. Si el mod implementa su propio delete, el resto de consumidores queda con el bug.
Por que no Cascade global?
Porque un default global puede borrar datos de otros mods que no pertenecen al subarbol curricular. El criterio correcto es por relacion: Cascade para posesion exclusiva, Restrict para referencias externas o linaje de version.
Que debe probar cada caso destructivo?
Primero confirmar que el dato existe en DB; luego gatillar el delete; despues confirmar que ya no existe; finalmente confirmar que quedo `core_DataLog` por ese nodo. Si hace falta recuperar datos, se puede re-sincronizar desde seed.
