HU-3 — cierre: qué se construyó y qué aprendimos

createInstance ahora sabe versionar: con asNewVersion: true crea la siguiente versión de un objeto (bump + linkage + estado inicial del workflow), con los writes acotados a un $transaction Serializable. Este teach-close mira hacia atrás — lo ejecutado, cómo evolucionaron las hipótesis, y las lecciones. (Las bases del dominio están en el teach-intake.)

TL;DR — Se entregó la capa de versionamiento de createInstance en 5 sesiones: guards (REQ-01/02), helper prepareVersionData (REQ-03/04), y el $transaction Serializable atómico (REQ-05). 91 unit tests + e2e de rollback contra UPU real, cero regresión en 64 callers, 9 commits. El audit con versionSourceId se delegó a HU-6; la UI a HU-7/10/11.

Qué se realizó

S1 · guards baratos

Extracción de asNewVersion de data + AS_NEW_VERSION_REQUIRES_PREFILL + OBJECT_NOT_VERSIONABLE (lee el registry). 2 unit.

S2 · validación multi-capa + prepare data

Helper prepareVersionData: carga source+currentStatus+workflow, valida SOURCE_NOT_VERSIONABLE/WORKFLOW_HAS_NO_INITIAL_STATUS, prepara increment+linkage+estado inicial. 6 unit.

S3 · transacción atómica

finalizeCreate(db): create+deepClone en $transaction({isolationLevel:'Serializable'}) para asNewVersion; path normal byte-idéntico. Review exhaustive. 91/91 sin regresión.

S4 · e2e contra DB real

Reset canónico de UPU + e2e: rollback del $transaction (write+throw → 0 filas) + commit persiste. Evidencia real de atomicidad.

S5 · cierre

Commits granulares DET-27, teach-close, acceptance checkpoints, status closed.

Lecciones

Extraer la preparación de versión a un helper desacopló el testing
Igual que applyPrefillFromSource (HU-1), mover la lógica a version-from-source.js permitió unit-testear REQ-03/04 sin arrastrar el path completo de createInstance (que es muy acoplado: fieldDefinitions, formula, layout). Patrón a repetir.
El audit con versionSourceId NO era de HU-3
Descubrimos que logInstanceOperation escribe core_SchemaAuditLog (best-effort), mientras el audit de negocio con versionSourceId en ChangeLog viaja por el event path → flow n8n, que es HU-6 (TICKET-041). DEC-LOCAL-03: HU-3 entrega solo la atomicidad, no duplica HU-6.
El unit no puede probar rollback transaccional — eso es e2e
El mock de $transaction no simula rollback. La garantía de atomicidad de REQ-05 solo se verifica contra Postgres real (S4 e2e). El unit cubre la matriz de errores + no-regresión; el e2e cubre la semántica transaccional.
El e2e debe usar ctx.skip(), no early-return
Un if (!isDbReady) return hace que vitest reporte el test como passed aunque no corra nada → falso verde en CI sin DB. ctx.skip() lo marca skipped (honesto).
