Polish de la plataforma de clonación/versionamiento

Cuando HU-10 (UPONE-1216) habilitó clonar y versionar objetos en up1, el cierre dejó tres asperezas marcadas como could: un título de modal feo para objetos Record-Type, un enforcement de unicidad que solo sabía hablar de CurricularSection, y un toast que no decía qué versión acababas de crear. Este ticket (UPONE-1219, capa core de la épica UPONE-1206) las pule. Ninguna es un bug que rompa producción — son deuda de plataforma que conviene saldar antes de que más objetos entren al flujo de clonación.

TL;DR — Tres polish de plataforma sobre layout + object-manager: B6 título legible para modales RT (humanizar rt__Mod__obj en el choke point del modal), B5 generalizar el enforcement de unicidad scoped para que sea config-driven (leer uniqueScopedBy desde la DB en vez de hardcodear CurricularSection) + su unit test faltante, B2 toast de versión parametrizado ("Versión N creada desde versión N-1").
Modo super autopilot: se ejecutan las 2 sesiones (S1 layout, S2 object-manager) de corrido, decidiendo y documentando; solo el push pide aprobación. Branch core UPONE-1206 (RULE-dev-004) — el cierre DKC no mergea a develop.

Por qué duele hoy

B6 — Al abrir "Crear registro" sobre una Modalidad, el modal titula Crear Nuevo rt__Modality__curricularsection. El usuario ve el nombre técnico de la proyección RT, no un label legible. El clone ya se arregló en 044, pero el create normal y otros modales RT siguen crudos.
B5 — La regla "no dos modalidades con el mismo nombre/código en el mismo Activity" está escrita con if (baseModelName === 'CurricularSection'). El próximo objeto que necesite unicidad scoped tendría que volver a tocar el resolver. Y la lógica no tiene unit test (lo advirtió el reviewer en 044).
B2 — Crear una versión muestra "Nueva versión creada", sin número. El dev de 044 (DEC-LOCAL-03) quería "Versión N creada desde versión N-1" pero faltaba que el front recibiera el version.

Conceptos clave

RT projection

Record-Type: un subtipo de un objeto base, nombrado rt__<Mod>__<base> (ej. rt__Modality__curricularsection). Tiene su propia tabla y campos además de los del base.

uniqueScopedBy

Propiedad declarada en un campo del JSON del objeto: array de campos que forman el scope de unicidad. Ej. name.uniqueScopedBy = ["ownerId","recordType"]: el name es único dentro de ese par.

version-from-source

Helper que al crear una versión setea version = maxVersionInLineage + 1 y previousVersionId. Por eso N-1 se puede inferir como version - 1.

El invariante que B5 generaliza

crear un registro con valor v en campo f FALLA si:
(a) f declara uniqueScopedBy = [s1..sn]  Y
(b) ya existe otro registro con el mismo v donde todos los s1..sn coinciden
Hoy: la condición está hardcodeada a CurricularSection + {name, code}. Después: cualquier objeto/campo que declare uniqueScopedBy la obtiene gratis.

Q&A de estudio

¿Por qué B2 no toca el backend?
Porque el resolver de createInstance ya retorna data: JSON con el registro completo, que incluye version. El selection set del front solo pedía id. Basta pedir data; el SDL InstanceResult.data ya existe.
¿Por qué B6 humaniza en vez de fetchear el label i18n real del RT?
El objectLabel solo está fetcheado para el objeto padre, no para el RT específico en el path no-clone. Fetchearlo por RT agrega latencia async antes de abrir el modal (parpadeo). Humanizar rt__Modality__curricularsection → "Modality" en el choke point cubre todos los call sites sin latencia. El label i18n exacto queda como mejora futura.
¿El cambio de B5 puede romper el enforcement actual de CurricularSection?
No debería: la generalización debe producir exactamente el mismo scopeWhere + findFirst para CurricularSection (name/code, scope [ownerId, recordType]). El unit test (parte de B5) fija ese comportamiento como regression, y se corre la suite vitest existente.
¿Qué gobierna el branch y el merge?
RULE-dev-004 / core_work_policy: todo trabajo core de la épica va en la rama UPONE-1206; se mergea a develop SOLO tras revisión del team up1. El cierre DKC de este ticket NO implica merge — solo deja commits en la rama de épica.

Gaps activos al entrar a design

El enforcement de unicidad corre en createInstance pero NO en updateInstance. B5 mantiene ese alcance (solo create) — generalizar a update es out-of-scope; se anota si el dev lo quiere después.
B6 humaniza el discriminador técnico (segmento central del nombre RT), no el label i18n de BD. Suficiente para un fallback; el label exacto es mejora futura.
