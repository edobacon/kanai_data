El bulk delete dejo de bloquear un borrado legitimo por confundir la proyeccion propia con una referencia externa

Borrar en bloque filas de un objeto base que tiene extensiones RecordType (las tablas rt__<RT>__<base>, la capa 1:1 que proyecta el mismo registro) fallaba sistematicamente con CONSTRAINT_VIOLATION aunque no existiera ninguna referencia real. El borrado individual ya lo hacia bien; este ticket llevo el bulk a paridad con una exclusion quirurgica. El intake ya explico el terreno (los dos motores de deteccion, el casing de las FK); este close mira hacia atras: que se hizo, que hipotesis quedaron confirmadas, y por que la implementacion final se aparto un paso del mecanismo que el spec sugeria.

TL;DR — validateBulkDelete (el gate que corre ANTES del loop de borrado, en referenceValidationService.js) contaba las proyecciones RT del propio objeto como referencias entrantes. Se excluyen esas proyecciones propias, identificadas por introspeccion real (la tabla rt__ cuya PRIMARY KEY es la FK a base.id), no por un patron de string. Bulk queda a paridad con el single. Verificado 23/23 contra la BD real de UPU; juez dual ciego approved.

Que se hizo

Se agrego una exclusion en discoverFKRelationshipsFromPrisma (la funcion de referenceValidationService.js que descubre quien referencia al objeto por la convencion <base>Id): antes de contar un modelo como referencia entrante, se saltan las proyecciones RT propias del objeto que se borra. Esas proyecciones se resuelven consultando information_schema (introspeccion de la FK/PK real, insensible al casing), no adivinando el nombre. El resto de la deteccion (FK externa real, custom field de tipo reference, exclusiones self/ext__/core_) quedo intacto.

✓ Resultado — un deleteBulkInstances de un base con proyeccion RT y sin referencia externa borra base + proyeccion con errors: [] (antes fallaba); las referencias reales y los custom fields siguen bloqueando.

La desviacion clave: PK==FK, no el set crudo

El spec sugeria anclar la exclusion en el "set exacto de resolveRtProjectionFks" — la funcion que el loop de borrado usa para limpiar proyecciones. Al verificar contra la BD real (no asumir) aparecio que esa funcion es un superconjunto: para bases como OrgUnit tambien devuelve rt__ de OTROS objetos que apuntan al base por una columna secundaria. Excluir ese set crudo habria dejado pasar un borrado que debe bloquear. La solucion fue afinar el criterio a la proyeccion propia: aquella cuya llave primaria ES la FK al base.

Anclar en el set crudo (lo sugerido)

Excluir toda rt__ con FK a base.id.

+ Simple, reusa la funcion existente.

− Sobre-excluye: rt__InstructorAvailability__availability.orgUnitId (proyeccion de Availability) referencia a OrgUnit y dejaria de bloquear su borrado. Viola el requerimiento de regresion.

Anclar en PK==FK (lo implementado)

Excluir solo la rt__ cuya PRIMARY KEY es la FK al base (proyeccion 1:1 de identidad).

+ Preciso: solo la capa del propio registro. Las rt__ ajenas siguen bloqueando.

+ Mas conservador: es un subconjunto de lo que el loop limpia, asi que nunca deja una capa huerfana.

El invariante que ancla el fix

Una proyeccion RT propia es la capa 1:1 del mismo registro logico: su PRIMARY KEY ES la FK al base. Esa capa nunca es una referencia externa.
Corolario: si la rt__ referencia al base por una columna que NO es su PK, es la proyeccion de OTRO objeto y sigue siendo una referencia entrante que debe bloquear.

El criterio exacto de exclusion

Se excluye una tabla rt__ del gate de referencias SI Y SOLO SI:
(a) tiene una FOREIGN KEY que referencia <base>.id (case-insensitive sobre la tabla base), y
(b) esa misma columna es la PRIMARY KEY de la tabla rt__.

El fix, en una linea de logica

Dentro del loop que recorre cada modelo Prisma buscando una columna <base>Id, se agrega un guard mas junto a los ya existentes (self/ext__/core_): saltar el modelo si es una proyeccion propia. El set de proyecciones propias se resuelve una vez por objeto, via information_schema, con la condicion PK==FK. Ante un error de introspeccion devuelve vacio: no excluye nada y se mantiene el bloqueo (comportamiento fail-safe, nunca borra de mas).

Lessons learned (autoevaluacion)

¿Por que no bastaba con reusar la funcion que el spec sugeria?
Porque asumir la semantica de una funcion sin verificarla contra la BD real fallo: resolveRtProjectionFks devuelve tambien rt__ ajenas que apuntan al base por columnas secundarias. La leccion: en codigo destructivo, verificar la semantica real (introspeccion) antes de anclar una exclusion en ella. El caso Availability enganaba porque ahi las 5 proyecciones son propias.
¿Por que el unit no alcanzaba como evidencia del fix?
El defecto vive en el casing real de columnas y en el fallo silencioso del scan de Prisma; un mock no lo reproduce y daria falso verde. El guard autoritativo es integracion contra BD real (UPU). El unit quedo como complemento del contrato, no como prueba de correctitud.
¿Que hace fail-safe a la exclusion?
Si la introspeccion falla, la funcion devuelve un set vacio: no se excluye nada y el gate mantiene el bloqueo. Un error nunca deriva en un borrado indebido, a lo sumo en un bloqueo de mas. Ademas la exclusion (PK==FK) es un subconjunto de lo que el loop limpia, asi que ninguna capa excluida queda huerfana.
Caveat a futuro: ¿cuando podria fallar el criterio PK==FK?
Asume una proyeccion RT 1:1 con PRIMARY KEY simple. Una rt__ con PK compuesta donde la FK al base fuera solo parte del PK quedaria (mal) excluida. Hoy no existe en up1 (todas las proyecciones son PK simple); si se introdujeran proyecciones con PK compuesta, habria que exigir que la PK sea exactamente esa unica columna.
