HU-3 — asNewVersion en createInstance

El sistema ya sabe clonar un objeto (HU-1 prefillFrom). HU-3 pone una capa de versionamiento encima de esa clonación: cuando creas un objeto pasando asNewVersion: true, no nace un duplicado suelto sino la siguiente versión de un objeto existente — con su número de versión incrementado, su enlace al predecesor, su estado inicial leído del workflow, y una auditoría que recuerda de qué versión salió. Este teaching te deja el mapa del terreno antes de tocar código: sobre qué bases nos paramos, qué hay alrededor, y por dónde va el plan.

TL;DR — Qué hay: createInstance ya acepta prefillFrom (clona campos de un source) pero no es transaccional ni sabe de versiones. Qué se hará: agregar un flag asNewVersion que, sobre el prefill, bumpea el número de versión, enlaza al predecesor, setea el estado inicial leyendo el FK del workflow y audita con versionSourceId — con los writes (y solo los writes) dentro de un $transaction Serializable. Por qué: versionar es una necesidad transversal de la plataforma; resolverla como flag declarativo en createInstance evita un resolver custom por cada objeto versionable.

Conceptos clave (las bases)

El vocabulario sobre el que se apoya HU-3. Todos estos "ladrillos" ya existen en el sistema gracias a las HU previas del épico — HU-3 los combina, no los inventa.

prefillFrom (HU-1)

Copia los campos de un objeto source al crear uno nuevo (lo explícito pisa lo copiado). Viaja dentro de data: JSON!, no como input tipado.

versioningConfig (HU-2/HU-4)

Snapshot en el registry (core_ObjectDefinition.versioningConfig) con el bloque versioning: linkageField, versionField, versionStrategy, initialStateField.

linkageField

Campo que enlaza una versión con su predecesora (= source.id). Es lo que después permite reconstruir la cadena de versiones.

allowsVersioning

Flag en WorkflowStatus. Solo desde un estado con allowsVersioning=true se puede versionar (ej: un Activity PUBlicado).

workflow.initialStatusId

FK único (HU-0h, Opción C) que dice en qué estado nace una versión nueva. Cardinalidad 1 → no existe el caso "múltiples estados iniciales".

$transaction Serializable

Aislamiento máximo de Prisma/Postgres. Garantiza que crear-la-versión + enlazar + auditar sea atómico (todo o nada). Único precedente: createWorkflowValidated.

Cómo funciona hoy createInstance

Estado actual (instance.resolver.js:2177-2869). Dos cosas importan para HU-3: (1) prefillFrom se extrae de data antes de validar; (2) no hay $transaction — el create y el deepClone de hijos corren secuenciales, sin rollback si algo falla a mitad.

// createInstance — wrapper de auth + event publish
createInstance: withEventPublish('create', withObjectAuth('create', async (_, { objectType, data }, context) => {
  const { prisma, tenantId } = context;

  // prefillFrom viaja DENTRO de data (no es input tipado en el SDL)
  const runtimePrefillFrom = data?.prefillFrom || null;
  if (runtimePrefillFrom !== null) delete data.prefillFrom;

  const prefillFrom = await resolveEffectivePrefillFrom({ prisma, objectType, prefillFrom: runtimePrefillFrom });
  data = await applyPrefillFromSource({ prisma, objectType, data, prefillFrom });

  // ... validaciones, FK, formula fields ...
  const created = await prisma[modelName].create({ data: prismaData, include });  // NO transaccional
  await logInstanceOperation(...);                 // audit (swallow-on-error)
  // ... deepClone hijos -> cloneMap ...
  return { id, data, extended, cloneMap };
}))

Flujo propuesto de asNewVersion

La idea de diseño (a validar al ejecutar): todo lo que lee/valida queda FUERA del transaction; solo los writes entran. Así no hay que threadear tx a los 5 helpers internos.

flowchart TB
  A[createInstance asNewVersion=true] --> B{prefillFrom presente?}
  B -- no --> E1[throw AS_NEW_VERSION_REQUIRES_PREFILL]
  B -- si --> C{objeto tiene bloque versioning?}
  C -- no --> E2[throw OBJECT_NOT_VERSIONABLE]
  C -- si --> D[leer source + currentStatus + workflow]
  D --> F{currentStatus.allowsVersioning?}
  F -- no --> E3[throw SOURCE_NOT_VERSIONABLE]
  F -- si --> G{workflow.initialStatusId seteado?}
  G -- no --> E4[throw WORKFLOW_HAS_NO_INITIAL_STATUS]
  G -- si --> H[preparar data: version+1, linkageField=source.id, currentStatusId=initialStatusId]
  H --> T[/$transaction Serializable/]
  T --> W1[create version]
  T --> W2[clone hijos]
  T --> W3[audit Create + versionSourceId]
  T --> R[return created]

La condición exacta

Una creación procede como nueva versión SI Y SOLO SI:
(a) asNewVersion === true y viene prefillFrom
(b) el objeto declara bloque versioning en el registry
(c) el currentStatus del source tiene allowsVersioning === true
(d) el workflow del source tiene initialStatusId seteado
Cada cláusula que falla tiene su error nombrado: (a)→AS_NEW_VERSION_REQUIRES_PREFILL, (b)→OBJECT_NOT_VERSIONABLE, (c)→SOURCE_NOT_VERSIONABLE, (d)→WORKFLOW_HAS_NO_INITIAL_STATUS.

Invariante de atomicidad

Las lecturas y validaciones ocurren ANTES del transaction; solo los writes (create + clone + audit) viven dentro del $transaction Serializable.
Corolario: cualquier await que escriba fuera del bloque rompe la atomicidad. Al refactorizar, todo write de la versión va dentro — ni uno fuera.

Nota de diseño: setear el estado inicial de una versión es creación, no transición → no aplica RULE-cd-004 (que gobierna transitionActivity).

Clonar (HU-1) vs Versionar (HU-3) — lo de al lado

HU-3 se apoya en HU-1, pero hacen cosas distintas. Entender el límite evita confundir un duplicado con una versión.

Clonar — prefillFrom (HU-1)

Crea un objeto independiente copiando campos de otro.

+ No exige config de versioning ni estado especial.

− No enlaza al origen, no incrementa versión, no audita linaje.

Versionar — asNewVersion (HU-3)

Crea la siguiente versión de un objeto: prefill + bump + enlace + estado inicial + audit.

+ Linaje reconstruible (linkageField), auditoría con versionSourceId.

− Exige bloque versioning, allowsVersioning y FK de entrada del workflow.

Q&A de estudio

¿Por qué asNewVersion requiere obligatoriamente prefillFrom?
Porque una versión nueva nace copiando el contenido de la versión anterior. Sin prefill no habría de dónde heredar los campos; versionar es, conceptualmente, "clonar + marcar como siguiente eslabón". De ahí el error AS_NEW_VERSION_REQUIRES_PREFILL.
¿Por qué solo los writes van dentro del $transaction y no toda la función?
Para no threadear el objeto tx a los ~5 helpers de validación que hoy usan el prisma global. Las lecturas/validaciones no mutan estado, así que pueden correr antes; solo create + clone + audit necesitan atomicidad. Es el mismo recorte que hace createWorkflowValidated.
¿Setear el estado inicial de la versión viola RULE-cd-004?
No. RULE-cd-004 gobierna las transiciones de estado (transitionActivity). Aquí el estado inicial se asigna en el momento de crear el objeto — es creación, no transición. Por eso se lee directo de workflow.initialStatusId sin pasar por la máquina de transiciones.
¿Por qué no existe un error WORKFLOW_HAS_MULTIPLE_*?
Porque initialStatusId es un FK de cardinalidad 1 (Opción C, HU-0h): un workflow tiene a lo sumo un estado inicial. Estructuralmente no puede haber "múltiples", así que ese caso de error no aplica.
