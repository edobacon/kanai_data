La historia (Session 1)

Una session, tres tasks en orden de riesgo, cerrada con un gate ⚑ fuerte y dual-judge.

Intake — barrido de impacto (H1)

Antes de tocar el tipo, se grepearon los consumidores de progression. Hallazgo que destrabó todo: los resolvers son pass-through field-agnostic (no validan el valor) → cambiar el tipo no los rompe. El único consumidor problemático dentro del mod era el seed (tenía 'Credits', fuera del enum).

T1 — cerrar el enum

progression → enum + default Sequential + labels i18n; widget de layout text→select en create/edit, copiando exactamente periodType. 33 tests del resolver verdes.

T2 — el flag isCurrent

Boolean not_null default true (molde appearsInDiploma), label "Vigente", columna filtrable en el RecordList, checkbox editable. Suite completa 748/748.

T3 — seed + análisis + gate

Seed migrado a Sequential; impacto confirmado; MCP flagged como propagación. En el gate, dual-judge (2 jueces ciegos) detectó que isCurrent faltaba en el Activity view → se fixeó y re-verificó. Gate cerró en standby porque el sync era DB-gated.

Post-sync — verificación y cierre

El dev corrió el sync en UPU. Se verificó contra el schema regenerado (prisma/UPU/schema.prisma + typeDefs): isCurrent Boolean? @default(true) + progression String?. Se cerró el ticket con evidencia.

Knowledge capturado

Lecciones (consolidadas)

Dos lecciones que conectan directo con la evolución de hipótesis de arriba: una nació de H1.1 (el seed), la otra del hallazgo post-sync sobre H1.

¿Por qué "cerrar un enum" no fue tan simple como editar un JSON?
Porque el campo tenía data viva y consumidores. El barrido de impacto (H1) reveló que el seed guardaba un valor inválido y que el layout lo renderizaba como texto libre. La lección: ante un cambio de tipo sobre un campo existente, el grep de consumidores ANTES de tocar es lo que evita el sync roto — no el cambio en sí.
¿El enum realmente "rechaza" valores inválidos en up1?
Depende de la capa. Para campos de RecordType-extension (rt__*) el codegen NO genera tipo enum → el backend los guarda como String y acepta cualquier valor. El rechazo vive en la UI (select) y en el contrato del MCP (z.enum). Si se necesita enforcement duro a nivel API, hay que un cambio de codegen (aplica igual a periodType) — no se asume que declarar enum en el JSON basta.
¿Cuándo parar y pasar el control al dev?
En la frontera DB-gated. El código mod-only se completó y committeó autónomamente, pero el sync sobre UPU (que toca datos) lo corrió el dev. Super autopilot decide y documenta, pero pausa (standby) en operaciones de DB y en push — ahí el humano tiene la última palabra.
