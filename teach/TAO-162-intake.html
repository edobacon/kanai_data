Widgetbook como app separada + catálogo web publicado por PR

HU-00-12 · GH-15 · TAO-162 · módulo EP-00 · implement. Saca el catálogo de componentes fuera del build de producto: app/widgetbook/ es una app Flutter aparte que reusa el design_system de la app, muestra cada componente con controles de dispositivo, escala de texto y movimiento, y publica su build web como artifact en cada PR que toca app/. Es el habilitador de la revisión visual de EP-01 (DEC-193).

Resultado

TL;DR — Qué hay: app/widgetbook/ no existe todavía; ya existen el catálogo de comandos raíz (scripts/dev/catalog.mjs) y el gate quality-gate en ci-pr.yml. Qué se hará: app + controles + caso de uso con fixture compartida; comandos dev:catalog/docs:catalog; job de CI que publica el build web del catálogo y verifica que no lleve secretos. Por qué: revisar componentes y estados sin meter Widgetbook en el build productivo.
Widgetbook. App Flutter que cataloga componentes y estados con controles (dispositivo, orientación, escala de texto, tema, movimiento); sus anotaciones @UseCase arman el árbol del catálogo.
Fixtures compartidas. Datos de ejemplo en una única ubicación (app/lib/design_system/fixtures/), importables por widget tests, golden tests y el caso de uso del catálogo. Sin duplicar.
Reuso del design_system. El catálogo monta el MISMO ThemeData claro que la app (fuente única con app/lib/main.dart); el oscuro es selector técnico oculto (DEC-196).
Catálogo de comandos raíz. scripts/dev/catalog.mjs declara COMMANDS y cli.mjs los despacha; los nuevos comandos se suman ahí, con el contrato común de fallo.

Verificación

  • S1: fvm flutter run -d chrome dentro de app/widgetbook/ abre el catálogo con el caso de uso y los controles operativos; el widget test de app/ que usa la misma fixture pasa.
  • S2: pnpm dev:catalog y pnpm docs:catalog abren el mismo catálogo con hot reload; pnpm check verde con el paquete anidado; fvm flutter pub deps en app/ no lista widgetbook.
  • S3: un PR que toca app/ publica un artifact que se descarga, se sirve localmente y abre en el navegador; la verificación de secretos sale 0; el job figura en quality-gate. Un PR solo de docs/ deja el job skipped y el gate verde.
  • S1 (T2): app + controles + átomo @UseCase + widget test con la misma fixture.
  • S2 (T1): comandos raíz + documentación en docs/development/commands.md.
  • S3 (T1): job de CI + artifact del build web + verificación de secretos.

Decisiones

Widgetbook NO entra al build productivo. fvm flutter pub deps en app/ no debe listarlo; app/widgetbook/ queda excluido del format/analyze/custom_lint de app/ sin dejar de analizarse por su cuenta (REQ-08).
El artifact no lleva secretos. Antes de subir el build web, el job verifica que no haya .env, tokens ni endpoints de ambientes (REQ-07).
Reusar, no reinventar. El comando se suma al catálogo raíz existente y el tema sale de la fuente única compartida con app/lib/main.dart (REQ-05/REQ-09). Toolchain por fvm (app/.fvmrc).
Sonda de intake: la única tarjeta (privilegios de rol) se resolvió no aplica — el ticket no crea ni modifica tablas ni el contrato; no hay impacto de schema.

Aprendizajes

  • app/widgetbook/ no existe: es lo que este ticket crea.
  • El catálogo de comandos raíz ya está (scripts/dev/catalog.mjs, COMMANDS en la línea 21); faltan dev:catalog/docs:catalog.
  • El gate obligatorio quality-gate (ci-pr.yml) ya incluye en su needs a dev-commands, build-smoke y docs.
  • El toolchain Flutter está fijado por app/.fvmrc: Flutter se invoca con fvm, como el resto de los comandos y jobs.
