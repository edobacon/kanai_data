HU-4 — Config versioning declarativo en el JSON del object

En up1 (la plataforma educativa multi-tenant) los objetos de negocio se definen en archivos JSON; un proceso llamado codegen — el generador que traduce esos JSON a schema Prisma y al registro en DB — los lee y materializa. Esta historia agrega una capacidad nueva: declarar un bloque versioning dentro de metadata de un object para activar el versionamiento sin escribir código. El trabajo concreto de HU-4 es la capa de validación de ese bloque en el codegen (la persistencia ya existe — lo vemos abajo, es la sorpresa principal de este intake).

TL;DR — Qué hay: los objects JSON pasan por un codegen que ya sabe persistir metadata.versioning al registro (lo dejó HU-0j). Qué se hará: agregar un helper de validación (validate-versioning.js) que verifica estructura, exige que linkageField sea FK reflexivo, emite warning para campos de política obsoletos y error para estrategias fuera de SP3. Por qué: que un dev de mod active versionamiento declarativamente, con feedback de codegen claro si el bloque está mal — sin tocar código del core.

El entorno: de qué depende y qué lo limita

HU-4 no se para sola. Antes de empezar conviene saber qué la rodea: dos dependencias ya cerradas que habilitan el terreno, y una restricción de alcance que define qué NO se hace todavía.

✓ Dependencias satisfechas — HU-0j (TICKET-033) ya creó la columna versioningConfig en core_ObjectDefinition y la función syncVersioningConfigToRegistry que persiste el bloque. HU-0e (TICKET-033) habilitó el FK reflexivo (un campo que referencia a su propio object). Ambas en status: closed.

⚠ La política NO vive en este bloque — quién puede versionar y desde qué estado es responsabilidad de WorkflowStatus.allowsVersioning y del FK de entrada del Workflow, no del bloque versioning. Por eso allowedFromStates/initialStateValue declarados aquí generan warning.

✗ Rama protegida — el repo de código está hoy en develop (rama protegida) y no existe aún UPONE-1206. Por RULE-dev-004 (regla de trabajo core: todo layer:core de la épica va en una sola rama UPONE-1206) esto se resuelve en la transición a execute, antes de tocar código.

Las bases: conceptos que hay que tener claros

Cinco ladrillos conceptuales sostienen el caso. Si los entiendes, el resto del intake se lee solo.

codegen

generatePrismaSchema.js — lee todos los object JSON, valida sus bloques de metadata, genera el schema Prisma y sincroniza el registro en DB. Es el punto donde se inyecta la validación de HU-4.

bloque versioning

Sub-objeto bajo metadata que declara cómo se versiona un object: qué campo enlaza versiones (linkageField), cuál guarda el número (versionField) y con qué estrategia (versionStrategy).

FK reflexivo

Foreign key que apunta al MISMO object (ej. previousVersionId en Activity → references Activity). Es lo que encadena una versión con su anterior. HU-4 valida que linkageField sea exactamente esto.

registry (versioningConfig)

Columna JSON en core_ObjectDefinition donde se persiste el bloque para lectura en runtime sin re-leer el JSON. Shape: { versioning, prefillFrom }. Poblada por HU-0j.

patrón de validación de metadata

Convención del codegen: un helper validate-<capacidad>.js que retorna string[] de errores; un wrapper que hace throw si hay errores (aborta codegen). Análogo más reciente: validate-prefill-from.js.

versionStrategy

Cómo se calcula el número de versión. En SP3 sólo increment (entero auto-incremental). user-provided y semver están fuera de alcance (épica 1206) → diferidos a SP4.

Cómo funciona hoy y dónde entra HU-4

El codegen ya tiene una secuencia de validadores que corren al inicio (polymorphicChildren, prefillFrom) y, más adelante, una fase de sincronización al registro. HU-4 inserta un validador nuevo en la cadena de validación (en ámbar abajo); la persistencia de la derecha ya existe — sólo hay que confirmar que sigue funcionando con el bloque validado. 

flowchart LR
  J[object JSON\nmetadata.versioning] --> V1[validatePolymorphicChildren]
  V1 --> V2[validatePrefillFrom]
  V2 --> V3[validateVersioning\nNUEVO · HU-4]
  V3 -- bloque malformado --> ERR[throw → aborta codegen]
  V3 -- bloque válido --> GEN[genera schema Prisma]
  GEN --> SYNC[syncVersioningConfigToRegistry\nYA EXISTE · HU-0j]
  SYNC --> DB[(core_ObjectDefinition\nversioningConfig)]

El bloque, concreto

Así se ve una declaración válida. Los tres primeros campos son requeridos; los dos últimos opcionales con default. Nota un detalle que importa para la validación: el campo de versión en el JSON se declara "type": "integer" (no "Int" — "Int" es el tipo Prisma resultante). 

// objects/business/Base/activity.json → metadata.versioning
{
  "linkageField": "previousVersionId",   // FK reflexivo a Activity
  "versionField": "version",             // type:"integer" para increment
  "versionStrategy": "increment",        // única strategy en SP3
  "auditSourceField": "versionSourceId",  // opcional (default versionSourceId)
  "initialStateField": "currentStatusId" // opcional (default currentStatusId)
}

El invariante que hay que respetar

El bloque versioning describe la mecánica del versionamiento, nunca la política.
Corolario: campos de mecánica (linkage, versionField, strategy, audit, initialState) son válidos aquí; campos de política (allowedFromStates, initialStateValue) son warning — su hogar es WorkflowStatus/Workflow. Esta línea divide qué se acepta, qué se advierte y qué se rechaza.

Alcance de las estrategias

De las tres estrategias posibles, sólo una entra en este sprint. Las otras dos se rechazan con error explícito — el validador debe decir por qué (fuera de alcance, no "valor inválido").

increment — SP3 (esta HU) user-provided — SP4 (error en SP3) semver — SP4 (error en SP3)

Hacia adelante: el plan

El trabajo se reparte en cuatro sessions. La crítica es S2 (gate ⚑ fuerte): es donde el cross-ref del FK reflexivo se topa con la realidad de que previousVersionId hoy es un string plano, y donde se confirma que la persistencia existente sigue poblando el registry.

S1 · Validación estructural (T2)

Requeridos/opcionales/tipos del bloque. Malformados rechazados, válidos aceptados.

S2 · Cross-ref reflexivo + persistencia (T2, ⚑ fuerte)

linkageField debe ser FK reflexivo; confirmar persistencia vía syncVersioningConfigToRegistry.

S3 · Warnings y errores de estrategia (T1)

Q&A — ¿entendiste el caso?

¿De qué se trata el caso?
Activar el versionamiento de un object declarando un bloque versioning en su JSON, y que el codegen valide ese bloque (estructura, FK reflexivo, estrategia) además de persistirlo al registro. El foco de HU-4 es la validación, porque la persistencia ya la entregó HU-0j.
¿Qué se va a hacer y por qué importa?
Crear un helper validate-versioning.js (patrón validate-prefill-from.js) y cablearlo en el codegen para abortar con error claro si el bloque está mal. Importa porque sin validación un bloque mal declarado fallaría en runtime de forma opaca; con ella, el dev de mod recibe feedback en build-time.
¿Qué quedó abierto y qué verificar primero?
No quedan hipótesis abiertas — H1/H2/H3 se confirmaron contra el código en intake. Lo más crítico de verificar en ejecución es S2: que el cross-ref reflexivo de linkageField funcione y que el bloque efectivamente quede persistido en versioningConfig tras el sync.
¿Qué decisión crítica se tomó en el intake?
D9 (acotada a la épica 1206): versionStrategy en SP3 es sólo increment. user-provided (requiere UI de input + ordering por linaje) y semver (requiere parsing) son trabajo de SP4. El intake fue por lo demás lineal: las hipótesis se validaron sin alternativas comparables que requirieran matriz de decisión.
