Nombre de vista declarable por aplicacion

En up1, el texto que ves en el menu de una app para una vista de objeto no lo elige la app: lo elige el objeto. Dos apps distintas que muestran el mismo objeto Base estan obligadas a llamarlo igual. Este caso nace de un choque real: Curriculum Design y Engagement declaran ambos Activity y Offering en el mismo tenant, y cada dominio necesita nombrarlos distinto. Antes de tocar nada conviene entender por que el nombre esta pegado al objeto, que lo rodea (i18n, PLAT-15, la frontera core/mod) y como se propone despegarlo.

TL;DR — Hoy el nombre de una vista de menu se resuelve por objeto (object.<Objeto>), asi que dos apps sobre el mismo objeto comparten texto a la fuerza. La propuesta: un labelKey opcional por entrada de nav, que cada mod declara en su propio namespace i18n y que gana sobre la clave global del objeto. Es aditivo, opt-in y compatible hacia atras. El camino ya se recorrio en un spike; este intake fija el mapa y el plan, no cierra decisiones.

Las bases: como se nombra una vista hoy

Estos son los ladrillos sobre los que se apoya el caso. Sin ellos el resto no se entiende.

NavTab

Una pestaña de navegacion resuelta en el servidor (PLAT-15). Tiene kind (object o dashboards), object, layouts. Hoy NO tiene un campo de nombre.

Clave por objeto

El menu resuelve el texto con la clave i18n object.<Objeto>. La key depende del objeto, no de la app: ahi esta el acople.

Namespace i18n

Cada workspace publica sus traducciones bajo {workspace}/{stem}. Es la propiedad que permite que dos mods no se pisen si usan keys distintas.

normalizeTab

El resolver reconstruye cada tab campo por campo desde la config del mod. Cualquier clave que no reconozca la descarta en silencio.

defaultObjects vs navByRole

Dos sistemas de tabs mutuamente excluyentes: vistas compartidas por todos los roles, y vistas por rol interno del mod. Ambos pasan por el mismo normalizeTab.

Fuente vs copia

El resolver y el tipo GraphQL viven en suite/ (fuente) y tienen copias generadas en object-manager/. El sync propaga; nunca se editan las copias a mano.

Donde se pierde el nombre hoy

Dos puntos concretos del codigo actual explican el problema. Primero, la normalizacion server-side reconstruye el tab y no copia nada que no conozca. Segundo, la etiqueta se resuelve por objeto y, si la clave no existe, cae al nombre tecnico de la tabla. 

// suite/logic/app.resolver.js:37-44 — normalizeTab descarta claves extra
if (typeof entry.object === 'string') {
  return { kind: 'object', object: entry.object,
           layouts: Array.isArray(entry.layouts) ? entry.layouts : null,
           dashboards: null };  // labelKey no se copia -> se pierde
}

// suite/composables/useObjectManager.ts:627-633 — la etiqueta es por objeto
const translationKey = objectGroup.isDashboards
  ? 'object.Dashboards'
  : `object.${objectGroup.objectName}`;   // mismo objeto -> mismo texto
const label = translateWithFallback(translationKey, objectGroup.objectName);
// si la clave no existe -> cae al nombre tecnico del objeto (H6)

El entorno: que rodea a este cambio

ℹ PLAT-15 (UPONE-1513) — construyo el sistema de vistas por app (defaultObjects/navByRole, resolucion server-side de navTabs). Este caso extiende ese sistema con un campo mas; se apoya en una forma existente en vez de inventar otra.
ℹ UPONE-1504 — la etiqueta de negocio del objeto (cascada por idioma) es un segundo sistema de nombres, tambien por objeto y no por app. No resuelve este caso, y unificar los dos es una linea de trabajo aparte (deuda a registrar, no a saldar aqui).
⚠ Por que el mod no lo resuelve solo — declarar la clave object.Offering en el propio mod pierde por el orden de fusion de catalogos (los mods se cargan alfabeticamente; uengagement va despues de curriculum-design). Por eso el nombre por-vista tiene que resolverse con una key distinta, no re-declarando la global.
✗ Frontera core/mod — esto es una Core Extension, Change Type 3 (capacidad opcional nueva). Toca suite (core). La aprobacion de core es gate de merge, no de inicio: se ejecuta y se presenta a core en el PR.

Dos formas de declarar el nombre

La propuesta del equipo (a validar por core) es la clave de traduccion. Se contrasta con el literal para entender por que se prefiere. No es una decision cerrada: es el marco para la revision de core.

labelKey (clave de traduccion)

La entrada de nav declara una clave i18n; la resolucion la prefiere sobre la global.

+ Traducible en los tres idiomas; cada mod la declara en su namespace, por eso no se pisan.

+ La ruta de navegacion hereda el nombre gratis.

− Suma un segundo lugar donde vive el nombre de una vista: hay que documentarlo bien.

Texto literal en la config

La entrada lleva el texto directo en vez de una clave.

+ Mas simple de escribir y de leer.

− No es traducible; mete texto de interfaz en configuracion, contra la cascada i18n y el DoD de paridad en tres idiomas.

La propiedad que hace correcto el diseno

El nombre de una vista debe poder declararse por app sin alterar el nombre que ve otra app sobre el mismo objeto.
Corolario: el criterio central de aceptacion no es "se ve el nombre nuevo", es "la otra app no cambia". Eso no se prueba mirando una sola app: la verificacion runtime necesita dos apps del mismo tenant, una que declara y otra que no.

Hacia adelante: el plan, a nivel orientacion

Server primero, cliente despues, verificacion al final. La secuencia importa: confirmar que el campo viaja por la API antes de tocar el cliente evita el diagnostico ciego que sufrio el spike.

Session 1 Propagacion en el servidor

Preservar labelKey en normalizeTab, declararlo en el tipo NavTab y en el esquema del objeto de app. Cerrar con la API introspeccionada: el servidor conoce el campo.

Session 2 Consumo en el cliente

Pedir el campo en la query, sumarlo a la interfaz, y preferirlo en la resolucion con cascada de fallback (labelKey → clave del objeto → nombre tecnico). El tab de dashboards ignora el campo.

Session 3 Runtime + no regresion + doc

Correr sync, verificar dos apps que comparten un objeto, cubrir vistas por rol interno y clave inexistente, documentar la capacidad. Sin drift.

Q&A de estudio

Por que dos apps sobre el mismo objeto comparten nombre hoy?
Porque la etiqueta del menu se resuelve con la clave object.<Objeto>, indexada por objeto y no por app. La misma clave devuelve el mismo texto sin importar que app la pida.
Cuales son los dos eslabones faciles de olvidar?
El tipo GraphQL (NavTab): sin declarar el campo, la API lo descarta. Y la seleccion de campos del cliente: sin pedirlo en la query, no llega. Si faltan, el sintoma es identico a "el fix no funciona", sin ningun error.
Que gap queda abierto para execute y no se pudo cerrar en intake?
Correr sync end-to-end (H3/H7): el intake es read-only y no ejecuta sync ni escribe en BD. El spike parcheo las copias de object-manager a mano; en la implementacion real hay que regenerarlas por sync y verificar sin drift. Tambien queda por validar en runtime el sistema de vistas por rol interno (H5).
Que descubrio el intake que el papel no tenia?
Que el esquema del objeto de app (up1_suite_app.json) va por detras del resolver: la variante {object, layouts} no esta declarada para vistas compartidas y navByRole declara additionalProperties: false. Declarar labelKey en el esquema es algo mas que "opcional cosmetico" (H9).
