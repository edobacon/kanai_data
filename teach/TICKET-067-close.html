Contexto

Resultado

Lecciones

⚠ La lección que originó este ticket (gap de detección) — un TC con Affects UI=yes NO se cierra por override si toca un path de runtime no cubierto por tests. La verificación a nivel-datos (Prisma directo) prueba el backstop de DB, no el camino del usuario. En 062 el override del smoke UI dejó pasar DOS bugs (display + payload). Aquí se cerró con smoke real del dev + unit test del helper.
ℹ Leer el flujo completo antes de fijar el lugar del fix — el culpable estaba en la inyección de initialData, no en el `else` del field-loop donde "parecía". Asumir el lugar habría tocado el código equivocado.
✓ El fix es transversal — al filtrar la inyección (no solo el prefilledModal), cualquier create con `initialData` sobre-fetcheado queda blindado, no solo el clone de academicProgram.

Q&A de estudio

¿Por qué el allowlist `[ownerType,ownerId,recordType]` y no solo baseFields?
Esos son campos backend-required que el form NO muestra pero el clone de objetos polimórficos (CurricularSection/modality) provee via canCreateInitialData. Normalmente son columnas reales (en baseFields), pero el allowlist es red de seguridad para que el filtro nunca los dropee aunque algún codegen no los liste.
¿El fix afecta el versionado de activity (que dio "ya existe")?
No. El versionado usa create inmediato (useCreateRowAction), NO pasa por handleSubmit. El error de versionado es un unique-violation (previousVersionId, version) en activity — preexistente, otro objeto/épica, anotado como D1 fuera de scope.
