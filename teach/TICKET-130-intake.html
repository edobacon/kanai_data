Teach intake · TICKET-130 · El delta bulk del render de bloqueo (UPONE-1557) up1 · 2026-08-12

Un bloqueo legitimo del borrado via deleteBulkInstances se muestra como pantalla de error de carga en vez de un aviso

Este es el delta que dejo abierto UPONE-1600 sobre el frente frontend de UPONE-1557, en el core layout-engine (RecordList). UPONE-1600 llevo a paridad el borrado gobernado individual (customDeleteMutation): un rechazo de negocio sale como toast y la lista queda intacta. Pero el path que rutea por deleteBulkInstances (la rama else de handleCriticalDeleteConfirm, cuando el objeto no declara customDeleteMutation) NO paso por ese fix: cuando el motor de cascada devuelve un bloqueo legitimo, sus errores se escriben en error.value y la lista entera se reemplaza por la pantalla de error de carga. El objetivo es llevar ESE path a la misma paridad.

TL;DR — La rama else de handleCriticalDeleteConfirm rutea el delete critico por deleteBulkInstances y, si el payload trae errors, escribe error.value (RecordList.vue:6485-6487) — el MISMO ref que gobierna el <ErrorState> full-view de CARGA. El fix discrimina por errors[].type (que el frontend ya pide y el backend ya puebla con CONSTRAINT_VIOLATION) y enruta el rechazo de negocio al mismo showWarning del path individual de 1600, sin tocar error.value. Es fix frontend puro, reusa graphqlErrors.ts; cero cambio de backend. Como es UI, el cierre exige verificacion runtime real (DET-36).

Conceptos base

Cinco piezas sostienen el caso. La clave: hay UN solo ref de error (error.value) que sirve para dos cosas distintas (carga de la lista y resultado del borrado), y en la rama deleteBulkInstances nace el sintoma visible que 1600 no cubrio.

rama else / deleteBulkInstances

Cuando el objeto NO declara customDeleteMutation, el delete critico single rutea por el motor de cascada (deleteBulkInstances, un id). Si el motor bloquea por Restrict, devuelve errors[] en el payload. Es el path que este ticket corrige.

error.value / <ErrorState>

El ref reactivo que gobierna el <ErrorState> full-view de la lista (RecordList.vue:60, v-if="error"). Pensado para fallos de CARGA (fetch/filtro). Si se le escribe cualquier cosa, la lista entera se reemplaza por la pantalla de error.

errors[].type (el discriminador)

El payload de deleteBulkInstances trae errors { id field message type } y el frontend YA lo pide (RecordList.vue:1787-1791). El backend puebla type: CONSTRAINT_VIOLATION para el rechazo por referencia. Con eso alcanza para discriminar en el front, sin tocar backend.

graphqlErrors.ts (reuso de 1600)

Util que introdujo UPONE-1600 (resolveBusinessErrorCode, readErrorExtensions) para clasificar el rechazo de negocio del path individual. El fix lo reusa/extiende para el bulk, sin duplicar logica (DET-11/DET-32).

el path individual de 1600 (oraculo)

En handleCriticalDeleteConfirm:6514-6517, el catch del path customMutation ya discrimina y usa showWarning. Es el comportamiento CORRECTO de referencia: el bulk se lleva a esa paridad.

Las capas encadenadas del sintoma

El diagrama sigue un delete critico single de un objeto sin customDeleteMutation, bloqueado por Restrict. El backend bloquea BIEN (nodo verde) y devuelve errors[] con type: CONSTRAINT_VIOLATION en el payload. El nodo rojo es el defecto: la rama else escribe esos mensajes en el ref de carga y nuke la vista.

Dos cosas del mapa. Primero: el bloqueo del backend (nodo B) es dominio esperado; el fix no lo toca. Segundo: la eleccion es entre las dos ramas del nodo C; el fix solo cambia esa rama para que el resultado sea el nodo E (paridad con el path individual de 1600), sin tocar el path de carga real de la lista.

Invariante que el fix restaura

El <ErrorState> full-view es para fallos de CARGA de la lista. El resultado de una accion (borrar) se comunica con un toast, sin destruir la vista.
Corolario: escribir el error de un borrado en error.value confunde dos dominios distintos (carga vs accion). El path individual arreglado por 1600 ya respeta este invariante; la rama deleteBulkInstances todavia lo viola por reusar el ref equivocado.

El defecto, en codigo

En handleCriticalDeleteConfirm (RecordList.vue:6445), la rama else escribe los errores del payload en error.value. El fix discrimina por type y usa un toast (como el path individual de 1600), dejando error.value intacto para el rechazo de negocio. 

// RecordList.vue:6485-6487 — rama else (deleteBulkInstances), HOY
const bulkErrors = bulkResult?.data?.deleteBulkInstances?.errors || [];
if (bulkErrors.length > 0) {
  error.value = bulkErrors.map((e) => e.message).join(' '); // nuke la vista full-view
  return;
}

// despues: discriminar por type -> toast para el rechazo de negocio
if (bulkErrors.length > 0) {
  const business = bulkErrors.filter(isBusinessType); // type CONSTRAINT_VIOLATION, etc.
  if (business.length) { showWarning(business.map((e) => e.message).join(' ')); // lista intacta }
  else { error.value = bulkErrors.map((e) => e.message).join(' '); }
  return;
}

Opcion A (frontend, elegida) frente a Opcion B (backend, descartada)

El comentario que dejo 1600 en el codigo sugeria "agregar code a ValidationError en object-manager". Eso es la opcion B. Pero el payload bulk ya trae type, asi que la opcion A (frontend puro) alcanza y evita tocar un contrato compartido.

A — discriminar por type en el frontend (elegida)

Enrutar el rechazo de negocio del bulk a showWarning segun errors[].type, sin tocar error.value.

+ Cero cambio de backend: el type ya viaja al cliente

+ Reusa graphqlErrors.ts de 1600; alineado con el path individual

+ Blast radius minimo (una rama); reversible

− Depende de que el backend siga poblando type (hoy lo hace)

B — agregar code a ValidationError (backend)

Agregar y poblar code en el type ValidationError para usar resolveBusinessErrorCode igual que el path individual.

− Cambia un type GraphQL compartido por create/update/bulk de TODOS los mods

− Cruza a object-manager: mayor blast radius y coordinacion core

− Innecesario: el type del payload ya alcanza para discriminar

Malla de seguridad y restricciones

⚠ Cambio quirurgico sobre la rama else / deleteBulkInstances — Debe sobrevivir intacto: (1) el error de CARGA sigue mostrando el <ErrorState> full-view (el path de error.value para fetch/filtro NO se toca); (2) el path individual customMutation arreglado por 1600 sigue con su toast; (3) el delete critico exitoso sigue con toast de exito + fetchData(true); (4) el multi-select deleteSelectedRows conserva su modal bulkDeleteErrors.
ℹ El bloqueo del backend es correcto — no se toca — El motor de cascada rechaza el hard-delete cuando hay una referencia real (Restrict). Es dominio esperado. El fix es frontend puro: NO se agrega code a ValidationError (opcion B descartada), porque el type del payload ya alcanza.
✗ Verificacion runtime real, no solo unit (DET-36) — Como es UI config-driven / DB-gated, el cierre exige evidencia runtime: OM + suite + tenant sembrado con un objeto bloqueable por Restrict via bulk engine; borrar la fila y ver el toast con la lista intacta. Si no es reproducible en el entorno, registrar smoke-not-reproducible con razon auditada. Preguntas de estudio

Si UPONE-1600 arreglo el render del bloqueo, por que hace falta este ticket?
Porque 1600 arreglo SOLO el path individual (customMutation), que lanza y trae extensions.code. El path que rutea por deleteBulkInstances (rama else) no lanza: devuelve errors[] en el payload y sigue escribiendo error.value (RecordList.vue:6485-6487), reemplazando la lista. Es el delta que 1600 dejo anotado en el propio codigo.
Por que el fix no necesita tocar el backend?
Porque el discriminador ya existe en el payload: el selection set pide errors { id field message type } (RecordList.vue:1787-1791) y el backend puebla type: CONSTRAINT_VIOLATION para el rechazo por referencia (referenceValidationService.js:331). Agregar code a ValidationError (opcion B) seria un cambio de contrato compartido innecesario.
Que NO entra en este ticket?
Tres cosas: (1) el frente BACKEND de 1557 (false-RESTRICT por proyeccion RT propia) es TICKET-122, otra causa raiz; (2) el path individual, ya resuelto por 1600; (3) el multi-select deleteSelectedRows (RecordList.vue:6551), que tambien setea error.value=stats.summary junto a su modal — queda como backlog BL-1 (DET-16), para mantener el delta atomico.
Por que no basta con un unit de componente para cerrar?
Porque el comportamiento es config-driven (objeto con cascada Restrict) y DB-gated (el bloqueo depende de una referencia real). Un unit afirma la logica de la rama, pero el cierre exige verificacion runtime real (DET-36): levantar OM + suite + tenant sembrado y ver el toast con la lista intacta al bloquear el delete. El unit es guard barato, no reemplazo.
