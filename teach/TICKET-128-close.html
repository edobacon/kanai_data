RecordDetail: la hidratacion no es edicion del usuario

Un formulario de detalle que autopoblaba un campo al abrirse quedaba marcado como "con cambios" y con el campo requerido en rojo, sin que el usuario tocara nada. El caso ensena a distinguir, en el motor de detalle comun (core layout), lo que hace el sistema al hidratar de lo que hace una edicion real, y a arreglarlo en un unico punto de core que cubre a todos los mods.

TL;DR — autoPopulate.triggerOnMount hace element.update() al montar; update() ensucia (dirty) y valida el campo. El fix limpia dirty + validacion solo en el montaje (clean() + resetValidators(), dos veces por el watcher flush:'pre'), sin tocar el valor ni el submit. Un unico punto de core cubre los 43 campos autoPopulate on-mount de 3 mods. La review de PR cazo un bug fino (el callback de watch reenviaba el valor observado como flag) que ni el smoke ni el unit habian atrapado.

Que se realizo

✓ Fix (core layout) — Helper puro applyAutoPopulateValue(element, value, {isInitialMount, scheduleDeferred}): escribe el valor siempre, y solo en el montaje resetea dirty+validacion del campo. Cableado en los dos sitios de update() de executePopulation. Guard de modo view/RecordList agregado a handleCancelAttempt (espejo de handleCloseAttempt).
ℹ Verificacion — Unit del helper 9/9; area RecordDetail 33/33. Runtime (tenant UPU) antes/despues en el caso ALTA (Curriculum) y cross-mod (up1-manager): sin falso dirty ni rojo al montar, valor preservado, populate intacto (items 139/21/32/2), submit sigue validando, edicion real marca dirty.
⚠ No se hizo (por diseno) — No se porto la rama vieja Feat/UPONE-912 (498 commits de divergencia; su snapshot resuelve otro disparador: tags). No se toco el contrato dual-populate del mod (Opcion D, follow-up). No se toco ningun mod.

Conceptos clave

dirty (form / element)

Vueform marca dirty en un watcher del valor: cualquier update() lo dispara. El core usa form.dirty para el modal "cambios sin guardar".

clean() vs resetValidators()

clean() baja solo dirty. El rojo (validacion) requiere resetValidators(), que limpia invalid/validated/mensajes. Ninguno toca el valor.

triggerOnMount

autoPopulate que corre al montar el formulario (hidratacion), sin edicion del usuario. Es el disparador del falso positivo.

flush: 'pre'

El watcher que ensucia corre despues de la llamada actual y antes del render; por eso el reset debe repetirse en nextTick o se revierte.

Invariante

La hidratacion inicial no es una edicion del usuario: no debe marcar el formulario como modificado ni validar campos antes de que el usuario interactue.
Corolario: el reset se aplica SOLO en el path on-mount. Un populate disparado por un watcher (el usuario edito un campo observado) SI es edicion y debe comportarse normal.

Evolucion de hipotesis

Un sintoma, tres mecanismos

El "cambios sin guardar" + el campo en rojo + el cancelar-en-ver se descompusieron en H1 (falso dirty), H2 (rojo por validacion on-mount) y H4 (guard de view ausente). No habia una unica causa.

La rama vieja evidencia intencion, no solucion completa

H5: el fix de UPONE-912 (snapshot de dirty) arregla el falso dirty por tags, pero NO el rojo ni el cancelar-en-ver. Se toma como base conceptual, no se mergea.

Runtime revela la API exacta

H6/H7 confirmadas en vivo: clean() no alcanza para el rojo; hace falta resetValidators(), y ambos dos veces (watcher flush:pre).

El blast radius es genual de core

43 campos autoPopulate on-mount en 3 mods, todos por el mismo executePopulation: se arregla en un punto, sin tocar mods.

La review caza lo que el test no

F-1: el callback de watch reenviaba newValue como isInitialMount. El unit pasaba false explicito; el call site real pasaba el valor observado. Corregido envolviendo el callback.

El caso que casi se escapa (F-1)

Contexto

Se agrego isInitialMount a executePopulation, usada tambien como callback directo de watch.

Problema

Vue invoca el callback con (newValue, ...); ese newValue caia en isInitialMount. Editar un watchField reseteaba la validacion del dependiente.

Resultado

Envolver el callback (() => executePopulation(false)). El unit y el smoke no lo cazaron; la review de PR si.

El fix, en codigo

// El reset corre dos veces (ahora + nextTick) por el watcher flush:'pre'.
function resetElementAfterAutoPopulate(element, scheduleDeferred) {
  if (!element) return;
  const reset = () => { element.clean?.(); element.resetValidators?.(); };
  reset(); scheduleDeferred(reset);
}

// on-mount: escribe el valor Y resetea. watcher de edicion: escribe, NO resetea.
function applyAutoPopulateValue(element, value, { isInitialMount, scheduleDeferred }) {
  if (!element) return;
  element.update?.(value);
  if (isInitialMount) resetElementAfterAutoPopulate(element, scheduleDeferred);
}

// El pitfall F-1: envolver el callback de watch para NO reenviar newValue como flag.
watch(() => vueformInstance.el$(watchField)?.value, () => executePopulation(false));

Lessons (Q&A)

Por que el unit verde no evito el bug F-1?
El unit probaba el helper con isInitialMount=false explicito, pero el cableado real de produccion (el callback de watch) nunca pasaba false: pasaba el valor observado. Un test que no refleja la aridad del call site consagra el bug. Leccion: verificar la aridad real del call site, no solo el contrato en aislamiento.
Por que un solo clean() no alcanzaba?
Dos razones distintas: (1) el rojo es estado de validacion, no de dirty, asi que necesita resetValidators() aparte; (2) el watcher que ensucia corre en flush:'pre' y revierte un unico clean(), por eso se repite en nextTick. Ambos se confirmaron en runtime, no por lectura.
Por que arreglar en core y no en el mod?
El '' que enrojece nace en el composable del mod, pero el mecanismo (update on-mount ensucia+valida) es del motor de detalle comun. Arreglarlo en executePopulation cubre los 43 campos autoPopulate on-mount de los 3 mods de una vez, sin acoplar el fix a un mod.
Que garantiza que el submit sigue validando?
resetValidators() limpia el estado prematuro pero no desactiva la validacion futura: al guardar, el required vacio vuelve a bloquear. Verificado en runtime con validate() → invalid:true.

Knowledge promovido

RULE-layout-044 — Un callback de watch(source, fn) recibe (newValue, oldValue): envolverlo si el primer parametro de fn no debe ser el valor observado. Nace del hallazgo F-1.
