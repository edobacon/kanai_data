Librería UI: átomos + formularios

JOR-006 construye la segunda tanda de la librería de UI compartida del frontend (front/jormat-front, Next.js 14 + Tailwind v3): un conjunto de átomos — los componentes visuales más pequeños y reusables (input, select, switch, card, dialog) — más dos composites de formulario (FormField / FormSection) que estandarizan cómo se valida y cómo se muestran los errores. El caso es interesante porque el intake original asumió 8 átomos desde cero, pero al investigar el repo encontramos que varios ya existen: el verdadero trabajo es completar el set, no reconstruirlo.

TL;DR — Qué hay: Button, Badge y Tooltip ya están entregados y testeados (JOR-005/024/025). Qué se hará: agregar 5 átomos nuevos (Input, Select, Switch, Card, Dialog), extender Badge con variantes semánticas, y crear FormField/FormSection con react-hook-form + zod — todo con story + test + chequeo de accesibilidad. Por qué importa: JOR-007 (DataTable, organismos), JOR-008 (toasts/modales) y JOR-011 (RBAC) dependen de estos átomos — es infraestructura que desbloquea media FASE B.

Las bases — conceptos sobre los que se apoya el caso

Antes de tocar nada, hay cinco ladrillos que el dev necesita tener claros. No son teoría: cada uno es un patrón que el código existente ya usa, y que los componentes nuevos deben respetar para no romper la consistencia. Los dos primeros son sobre cómo se construye un átomo; los tres siguientes, sobre cómo funcionan los formularios (el corazón de FormField).

Átomo shadcn/ui

Componente UI mínimo y reusable. shadcn no es una librería de npm: copia el código del componente a src/components/ui/ para que sea editable. Muchos envuelven una primitiva de Radix (lógica de accesibilidad sin estilo); otros son HTML puro (Card).

CVA + cn()

class-variance-authority define las variantes visuales de un componente (variant/size) como mapas de clases Tailwind. cn() (en @/lib/utils) fusiona clases resolviendo conflictos. Tipado vía VariantProps<typeof xVariants> — sin any (RULE-global-001 C2).

carpeta-por-componente

Convención fijada por JOR-024/025: cada componente vive en su carpeta con x.tsx + x.stories.tsx + x.test.tsx + index.ts (barrel). Los nuevos átomos siguen esto al pie de la letra.

RHF + zodResolver

react-hook-form (RHF) gestiona el estado del formulario (valores, errores, submit). zod define el schema de validación; @hookform/resolvers/zod conecta ambos: RHF valida cada campo contra el schema zod automáticamente.

Contrato de error {code,message}

El backend (NestJS, Exception Filter de la task A0.9) normaliza toda excepción a { code: string, message: string } + status HTTP. Ej: {code:'MICROCHIP_DUPLICATE'}. FormField mapea ese code al campo correcto.

stories-como-test

Vitest 4 corre dos proyectos: jsdom (tests unitarios *.test.tsx) y Storybook en browser mode (Playwright/Chromium) donde las stories con play() son tests reales. El addon-a11y chequea accesibilidad por story.

Cómo fluye un formulario (la base de FormField)

El diagrama traza el ciclo de vida de un submit y es la base de por qué FormField existe. Mirar dos bifurcaciones: la validación local (zod, antes de salir del browser) y el manejo del error de backend. La clave educativa: un error con code que mapea a un campo (ej. "microchip duplicado") debe pintar ese campo en rojo vía setError(field); un error genérico va a un toast. FormField es la pieza que renderiza el estado aria-invalid + el mensaje cuando RHF marca el campo inválido — por cualquiera de las dos vías.

Restricciones que rodean el cambio

⚠ RULE-global-003 — no tocar lo entregado — Button y Tooltip ya cumplen el alcance literal de JOR-006. No se reconstruyen ni se "mejoran" de paso (success/loading en Button quedan fuera de alcance). La excepción razonada es Badge: extender variantes es completar el átomo según su ticket dedicado, no alterar comportamiento previo — el gate de S3 verifica que las variantes viejas sigan intactas (regression).
✗ Docker hornea node_modules — jormat-front corre en un contenedor con node_modules horneado en la imagen; docker-compose solo monta src/. Agregar deps (react-select, react-switch, react-label) exige que el dev haga ./run.sh build para que el runtime las vea. La verificación de build/test del gate la corro en el host (suficiente para DET-13 — cierre con evidencia); el dev rebuild su contenedor aparte.
ℹ Fuera de alcance — DataTable, FilterBar, KPICard, PageLayout y las vistas de negocio NO son parte de JOR-006 (van en JOR-007 / FASE B). Tampoco Combobox/MultiSelect — el Select de este ticket es el simple (single, con placeholder/opciones/error).

Decisión abierta — qué hacer con Badge

La única decisión con matiz real del intake. Badge ya está entregado pero incompleto frente a lo que pide el ticket. Dos lecturas en tensión; se resuelve en design-feature (en modo super, con racional documentado). El intake deja la pregunta planteada, no cerrada.

A · Extender Badge (additivo)

Agregar variantes success/warning/error/info/neutral al CVA existente. Tokens ya en globals.css.

+ Un solo Badge canónico; cumple el alcance del ticket.

+ No-breaking si las variantes previas quedan intactas.

− Toca un archivo "entregado" — exige test de regresión.

B · Dejar Badge como está

Respetar RULE-global-003 al pie y no tocar el átomo entregado.

+ Cero riesgo sobre lo existente.

− JOR-006 quedaría incompleto (las pills semánticas son alcance explícito).

− Empuja el trabajo a otro ticket sin razón técnica.

Inclinación del intake: opción A — extender es completar, no alterar; el riesgo se acota con un test de regresión de las variantes previas en el gate de S3. La decisión final, con su racional, queda registrada en el spec.
