Cómo quedó: mensaje de unicidad corregido sin tocar core

Se cerró el bug del mensaje engañoso al crear un Curriculum con código duplicado. El arreglo vive solo en el mod curriculum-design: una reescritura del texto que lanza el guard de unicidad. La lección más valiosa no fue el cambio en sí, sino lo que apareció al verificarlo en la UI real — una cadena de error de 3 saltos que el análisis estático no había revelado del todo.

TL;DR
  • Qué se hizo: el guard assertUniqueLineageRoot ahora lanza un mensaje que TERMINA con el formato Prisma Unique constraint failed on the fields: (`code`). Cero cambios en core.
  • Resultado: la UI muestra "Ya existe un registro con ese valor." / "Usa un valor diferente." (verificado con smoke real). Ya no "Este registro fue modificado por otra persona".
  • Lección clave: el verdadero gatekeeper no era el regex del front sino el formatError del object-manager (UPONE-1216), que extrae el campo con un regex anclado al final del mensaje. → RULE-curriculum-design-005.

La historia del caso

Contexto

El guard del mod mostraba "modificado por otra persona" (concurrencia) al duplicar un código. El dev pidió arreglarlo SIN tocar core. El intake propuso enfoque A (extensions + passthrough en core); el dev lo descartó por la restricción → mod-only.

Decisión

El mod emite un texto que core ya sabe mapear. Como no hay canal genérico, se alinea con el mapping de unicidad existente. Texto genérico aceptado (DEC-LOCAL-01) a cambio de cero-core.

Resultado

Funciona en runtime tras un ajuste: el mensaje debe terminar con el formato Prisma para que formatError extraiga el campo. 2 sessions, 4 commits (local), 729/729 tests, smoke UI ✓.

Qué pasó, paso a paso

Intake — re-scope

Enfoque A (extensions + core) descartado por "cero core". Se confirma que core ya tiene un mapping de unicidad con traducción ES.

S1 — cambio + test + sync

Reescritura del mensaje, test de regresión, sync:logic. Tests verdes a nivel-datos.

S2 — primer smoke: FALLA

La UI seguía con el mensaje viejo → el OM (npm start plano) no había recargado. Reinicio de OM.

S2 — segundo smoke: "Unique constraint failed" crudo

El log del OM reveló la causa: formatError trunca el mensaje porque el campo no estaba al final.

S2 — fix de runtime + tercer smoke: ✓

Mensaje reescrito para TERMINAR con el formato Prisma. Re-sync + reinicio. UI: "Ya existe un registro con ese valor.". Cierre.

Por qué el primer mensaje falló

Primer intento (falló en runtime)

...Unique constraint failed on the field `code`. Ya existe... Raices existentes: X.

− El campo (`code`) está a mitad; formatError extrae desde el FINAL → falla → devuelve bare "Unique constraint failed" sin backtick.

− El front no matchea → default "Ocurrió un error inesperado".

Fix (funciona)

...Raices existentes: X. Unique constraint failed on the fields: (`code`)

+ El campo va AL FINAL → formatError lo extrae → forma canónica + extensions.code=UNIQUE_VIOLATION.

+ El front mapea a uniqueness → mensaje ES correcto.

La regla que queda (RULE-curriculum-design-005)

El mensaje de unicidad de un mod DEBE terminar con Unique constraint failed on the fields: (`campo`), sin texto después.
Corolario: el detalle de dominio (code propio, ids en conflicto) va ANTES de esa frase. El acople real del mod es a formatError (object-manager), no al regex del front. Verificar con smoke UI real + reiniciar el OM tras sync:logic.

Lecciones aprendidas

✓ "UI TC no se cierra por override" se ganó su lugar — el test a nivel-datos pasaba, pero el runtime fallaba (dos veces). Solo el smoke real destapó la cadena formatError. No cerrar UI-TCs sin verlos.
⚠ Build verde ≠ runtime nuevo — sync:logic escribe el archivo, pero el OM corre como npm start plano (sin watch) → hay que reiniciarlo para que el cambio surta efecto. Mismo patrón que "Docker hornea node_modules".
ℹ El log del backend es el desempate — cuando el análisis estático y el runtime se contradicen, el log del OM mostró el mensaje exacto thrown + el code INTERNAL_SERVER_ERROR, que llevó directo a formatError. Dejar de teorizar y mirar el log.

Q&A de cierre

¿Qué se hizo finalmente?
Reescribir el string que lanza assertUniqueLineageRoot en el mod para que termine con el formato Prisma de unicidad. Cero cambios en core. Más un test que replica la cadena (formatError + front regex).
¿Cómo evolucionaron las hipótesis?
H1–H5 (del enfoque A) quedaron como evidencia descartada. H6–H9 (mod-only) confirmadas en intake. El descubrimiento clave (no anticipado) fue L4: formatError normaliza/trunca el mensaje — el mod se acopla a él, no al front directamente. Eso obligó a un ajuste del mensaje en S2.
¿Qué se decidió y qué se sacrificó?
DEC-LOCAL-01: mod-only, mensaje genérico ("Ya existe un registro con ese valor.") en vez del texto exacto del dominio. Se gana cero-core y alcance mínimo; se pierde control del texto exacto y se acepta un acople frágil (mitigado con comentario + test). El enfoque A (mod dueño del texto) quedó parqueado (Backlog B1).
¿Qué falta / qué sigue?
Push de los 4 commits del mod (pendiente del OK del dev — en super el push siempre pregunta). Backlog: B1 (enfoque A si más mods necesitan su texto), B2 (el gemelo modalityDefault, hoy cae en genérico no engañoso).
