RBAC por capability para versionar y clonar

En up1 — la plataforma educativa multi-tenant con arquitectura modular — el mod curriculum-design ya expone dos acciones de fila sobre sus objetos: versionar una Activity y clonar una BibliographyReference o una Modalidad. Hoy esas acciones se muestran u ocultan solo según el estado del workflow del objeto (currentstatus.allowsVersioning), igual para todos los usuarios. No hay forma de decir "este usuario sí puede versionar, este otro no". Este ticket agrega esa dimensión: un permiso RBAC por objeto que gobierna quién ve y quién puede ejecutar versionar/clonar, siguiendo la filosofía declarativa de up1 (capabilities custom por mod, core genérico).

TL;DR — Qué hay: versionar/clonar se gatean solo por estado, sin control por usuario. Qué se hará: declarar capabilities object-level (activity:version, bibliographyreference:clone, curricularsection:clone), gatear los row actions con requiredCapability (UI) y agregar un check server-side en createInstance (backend) que enforce solo si el mod lo declara en su metadata. Por qué: que cada mod decida soberanamente qué usuario, según qué permiso, tiene disponible cada acción — defensa en profundidad (UI + backend) sin imponer política desde el core.

Las bases — el RBAC de up1, hoy

Antes de tocar nada conviene tener el glosario del modelo de permisos sobre el que se apoya el cambio. up1 usa un RBAC estilo Moodle: capabilities con nombre-string, asignadas a roles, consultables desde el frontend. Estos cinco ladrillos son todo lo que necesitas para entender el resto del teaching.

capability

Permiso atómico identificado por un string (objeto:accion, ej. activity:version). Vive en la tabla core_Capability y se asigna a roles. El backend acumula las del usuario; el frontend las consulta.

capabilities.json

Archivo declarativo por mod que crea capabilities custom más allá del CRUD. curriculum-design ya declara activity:audit, approve, publish. El sync las inserta en DB.

requiredCapability

Clave que un row action declara en su layout JSON. El motor isActionVisible oculta la acción si el usuario no tiene esa capability — gating de UI 100% declarativo, sin código core.

createInstance / withObjectAuth

El resolver genérico del core que crea objetos. Versionar y clonar comparten este resolver (distinguidos por flags asNewVersion / prefillFrom.source); hoy ambos exigen solo el permiso genérico create.

RULE-mods-037

Regla del proyecto: las capabilities object-level se nombran sin prefijo mod/ (activity:version, no mod/...:version). Gobierna el naming de las nuevas capabilities.

opt-in declarativo

Modo de enforcement elegido: el core lee una capability declarada en el metadata del objeto y la aplica solo si está presente. Sin declaración → permite (comportamiento actual). La mecánica es genérica (core), la política es del mod.

El cambio en 3 capas — dónde vive cada cosa

El hallazgo clave del intake es que el cambio NO es monolítico: se reparte en tres capas con dueños distintos. Dos son 100% declarativas (viven en el mod, cero código core); la tercera obliga a tocar el core. Entender este reparto orienta el plan de sessions: lo declarativo es barato y reversible, el enforcement backend es el corazón de riesgo. Cómo se ve hoy en el código

Para fijar el "antes": así se declara hoy un gating en un row action (carril vivo requiredCapability, usado en mods reales como hw-assessment-list.json) y así luce la única autorización que el backend exige hoy a versionar/clonar. 

// front · layout JSON de un row action (carril vivo: requiredCapability)
{
  "key": "version",
  "label": "Crear nueva versión",
  "requiredCapability": "activity:version",   // ← lo que agrega este ticket
  "visibilityConditions": [ /* allowsVersioning, ya existente */ ]
}

// back · object-manager/instance.resolver.js — autorización actual
// versionar y clonar comparten createInstance con el MISMO permiso genérico:
withObjectAuth('create', createInstance)   // no distingue version/clone de un alta normal

El invariante que rige el diseño

Toda la decisión de cómo implementar el enforcement backend se subordina a un principio de la filosofía up1: la soberanía del mod sobre su política. El core no impone seguridad; ofrece un mecanismo y el mod decide si lo usa.

El core enforce una capability si y solo si el mod la declaró en el metadata del objeto. Sin declaración, permite.
Corolario: un versionado/clonado sin protección es una decisión válida de negocio del mod — NO un hueco que el core deba cerrar a la fuerza. Por eso la ausencia de declaración no genera warning ni error del validador.

El entorno — qué rodea este cambio

Tres piezas del contexto lateral que condicionan la ejecución y que conviene tener presentes antes de codear.

⚠ TICKET-044 activo sobre el mismo Jira (UPONE-1216) — este ticket asume que los row actions de versionar/clonar ya están declarados por TICKET-044 (HU-10). Aquí solo se agrega el requiredCapability encima. Hay que coordinar para no pisarse.
ℹ Reparto de branches (RULE-dev-004) — el trabajo de mod (mods/curriculum-design/) va a la rama UPONE-1038; el trabajo de core (object-manager, layout) va a UPONE-1206. Un mismo ticket toca ambas ramas.
✗ Cobertura dual del check (caveat de propagación, L1) — el clone de Modalidad (un RecordType) pasa por un bloque separado del resolver (~L2357+), distinto del clone del objeto base. El check de permiso debe cubrir AMBOS spots o el clone de Modalidad se escapa del enforcement.

Hacia dónde vamos — orientación del plan

A nivel orientación (el detalle de tasks lo fija design-feature), el trabajo recorre de lo más declarativo y barato a lo más sensible del core. Este orden permite validar el carril feliz de UI antes de comprometer el enforcement server-side.

1 · Declarar capabilities (mod)

Agregar activity:version, bibliographyreference:clone, curricularsection:clone a capabilities.json + asignarlas a roles. 100% declarativo.

2 · Gatear row actions (mod)

Agregar requiredCapability a los row actions de versionar/clonar en los layouts. El motor de UI ya lo soporta.

3 · Mecanismo genérico de enforcement (core)

Enseñar a createInstance a leer metadata.*.requiredCapability y enforcearla si está presente — cubriendo objeto base y bloque RecordType.

4 · Validar end-to-end

UI con/sin capability, rechazo backend de mutación directa, y regresión de que el gating por estado se preserva.

Q&A para fijar el modelo mental

¿Por qué hace falta tocar el core si el frontend ya sabe ocultar el botón por capability?
Porque ocultar el botón es solo defensa de UI: un usuario podría invocar la mutación createInstance directo (vía API/GraphQL) saltándose el frontend. La decisión fue defensa en profundidad (UI + backend), así que el check server-side es necesario. Y como createInstance es un resolver genérico del core que los mods no aportan, ese check vive inevitablemente en el core.
Si el enforcement vive en el core, ¿no rompe a todos los objetos que usan createInstance?
No, gracias al modo opt-in declarativo. El core solo enforce si el objeto declara requiredCapability en su metadata. Los ~14 call-sites de creación scratch (enrollment, recurrence, calendar, import, bulk, AI agent, n8n…) no declaran nada → quedan idénticos a hoy. El blast radius real se limita a curriculum-design.
¿Por qué object-level (activity:version) y no RT-level (curricularsection:modality:version)?
Porque las capabilities object-level se auto-asignan a los roles default (Admin/Consultor/Colaborador) en el generador, mientras que las RT-level y field-level NO se auto-asignan y requerirían asignación explícita en seed. Object-level es más simple y curricularsection:clone ya cubre todos los RecordTypes incluida Modalidad.
¿Qué pasa si el backend rechaza el permiso a mitad de un versionado? ¿Queda estado inconsistente?
No. El throw de permiso ocurre ANTES de finalizeCreate (escrituras a DB), ANTES del audit log, y withEventPublish publica DESPUÉS del resolver. Es decir: sin escrituras, sin eventos, sin audit. El rechazo es atómico y seguro.
