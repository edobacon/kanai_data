Curriculum Mapping · MCP sync

up1 tiene un servidor MCP (paquete up1-mcp, un producto aparte de la plataforma) que deja operar up1 de forma conversacional: el asistente consulta y gestiona el diseño curricular y engagement con los permisos del usuario real. Hoy expone dos dominios (diseño curricular y engagement) pero no expone curriculum mapping: los esquemas de niveles, las escalas de cobertura y la matriz de competencias no se pueden ni siquiera consultar desde el asistente. Este ticket es la deuda de sincronización de ese dominio con el MCP. El alcance ya está acotado a solo lectura del subconjunto estable. Este documento arma el mapa mental antes de ejecutar: sobre qué bases se apoya el MCP, qué rodea al caso en el sprint, y qué vamos a hacer.

TL;DR — Qué hay: el MCP compone dominios como "packs" (una carpeta por mod); agregar un dominio es agregar un pack y una línea al manifiesto, y el CRUD genérico opera cualquier objeto del allowlist sin escribir código de operación. Qué se hará: agregar el pack curriculum-mapping con LevelScheme, CoverageScheme y la matriz (CompetencyNode) en lectura, más su verificación real y su documentación. Por qué: entrega valor consultable sobre terreno estable (F1) sin retrabajo cuando el backend de la matriz termine de estabilizarse en este mismo sprint.

Glosario: sobre qué bases nos paramos

El vocabulario del MCP y del dominio a exponer. Sin estos ladrillos, el resto del documento no se entiende.

Mod pack

Unidad autocontenida en src/mods/<id>/ que declara su allowlist de objetos, contratos, tools y ruteo. El núcleo del MCP es mod-agnóstico: sumar un dominio no lo toca.

Manifiesto

src/mods/index.ts: array MODS, append-only, una línea por mod. Es el único archivo compartido entre equipos; de él se derivan allowlist, contratos, tools y self-doc en runtime.

Allowlist

Unión de los objects de todos los packs (allowedObjectTypes()). El MCP solo toca objetos del allowlist; lo que no está en él no existe para el MCP, ni para el CRUD genérico.

Contrato de objeto

Config por objeto (src/contracts/registry.ts): requeridos, enums, campos readonly, resolución de referencias por nombre. El CRUD genérico lo aplica; declararlo basta para consultar.

CRUD genérico

Tools a nivel server (list_objects, get_object, query_records, ...) que operan cualquier objeto del allowlist con contrato. Para lectura, exigen solo la capability objeto:view.

Permisos como frontera

Doble defensa: up1 enforza RBAC server-side y el MCP lee las capabilities del usuario real (getMyPermissions) y no ejecuta lo que ese usuario no podría hacer en la plataforma.

LevelScheme / CoverageScheme

Los dos esquemas estables (F1) del dominio: la escala de logro (niveles) y la escala de cobertura curricular (Introduce / Reinforce / Master). Terreno que no se mueve en el sprint.

CompetencyNode (la matriz)

El árbol de competencias: en la raíz la matriz, de ella cuelgan competencias y subcompetencias (recordTypes Matrix / Competency / SubCompetency). Este ticket la expone en lectura.

RecordType

Discriminador dentro de un objeto: en una misma tabla base conviven varias formas (Scheme/Level, Matrix/Competency/SubCompetency). Leer "la matriz" es filtrar por recordType = Matrix.

El invariante que ordena todo el trabajo

Sin el objeto en el allowlist, ninguna operación del MCP es posible — ni siquiera consultar.
Corolario: el primer paso siempre es habilitar el dominio (declarar el pack y sus objetos). Recién ahí el CRUD genérico puede leerlos. Por eso "habilitar" es el primer commit natural, antes que cualquier operación de dominio.

Cómo viaja una lectura genérica por el MCP

El camino que recorre una consulta desde el asistente hasta up1. Las dos barreras (allowlist y permiso) son la frontera del MCP: por eso una vez habilitado el dominio, la lectura "sale gratis" y sigue estando gobernada.

Por qué la matriz es lectura (y no escritura) en este ticket

La matriz (CompetencyNode, recordType Matrix) tiene un ciclo de vida gobernado con capabilities dedicadas por arista (approve, publish, deprecate, ...). Escribirla no es un CRUD: es gobernanza. Ese peso, sumado a que sus partes diferidas se construyen en este mismo sprint (UPONE-1633), es la razón de acotar el ticket a lectura.

La forma de un pack (el molde a copiar)

Un ModPack declara qué objetos expone y con qué contrato. Para lectura, esto es casi todo el trabajo: no hace falta escribir tools de operación. Es la Receta 3 (pack nuevo) apoyada en la Receta 1 (CRUD por config).

// src/mods/curriculum-mapping/index.ts  (esqueleto conceptual — el detalle lo fija design)
export const curriculumMappingPack: ModPack = {
  id: 'curriculum-mapping',
  label: 'Mapeo curricular',
  routingHints: ['esquema de niveles', 'cobertura', 'matriz de competencias'],
  objects: [

  about() { return '...'; },
  domainDoc: { whatIsIt: '...', whatYouCanDo: ['...'] },
  registerTools() { /* lectura: nada, o solo lo que el generico no cubra */ },
};

Los dos caminos de extensión (concepto, no decisión cerrada)

El MCP ofrece dos recetas para incorporar un objeto. Entender cuándo aplica cada una es clave para dimensionar cualquier ampliación futura del dominio.

Receta 1 — CRUD genérico (config)

Declarar el objeto en el allowlist del pack + su contrato. El CRUD genérico lo opera aplicando requeridos/enums/readonly y el permiso objeto:acción.

+ Cero código de operación; cubre toda la lectura de este ticket.

− No sirve para objetos con reglas de negocio que el genérico no cubre.

Receta 2 — Tool de dominio

Operación dedicada (como el perfil de egreso) con auth, permisos, esquema de entrada, preview→commit y resolución semántica.

+ Obligatoria para escritura gobernada (mutations validadas, ciclos de estado).

− Fuera de alcance aquí: la escritura del dominio queda para un ticket posterior.

El plan, a nivel orientación

Tres sesiones previstas. El detalle (tasks, criterios de gate) lo fija el diseño; esto es el mapa del camino, no la ejecución.

S1 · Habilitar el dominio

Pack nuevo curriculum-mapping (allowlist + contratos + self-doc) y una línea en el manifiesto. Sin esto, nada más es posible (el invariante).

S2 · Verificación real (gate fuerte)

Con un usuario autenticado: consultar cada objeto contra la plataforma (filtrando la matriz por recordType), y comprobar que un rol sin la capability es rechazado. Valida empíricamente las hipótesis clave.

S3 · Tests + documentación + frontera

Tests de lógica pura, catálogo y documentación de capacidades (TOOLS / manifest / CAPABILITIES / ROADMAP), y dejar escrita la frontera de lo que quedó fuera para que el siguiente sepa dónde retomar.

Preguntas abiertas y de autoevaluación

Las primeras dos siguen abiertas al entrar a execute (son decisiones a resolver); el resto son para verificar que las bases quedaron claras.

¿Pack nuevo o sumar los objetos al pack de curriculum-design? (abierta — la resuelve design)
La Receta 3 favorece un pack nuevo autocontenido (más limpio, una línea en el manifiesto). Sumarlo al pack existente es menos archivos. No hay conflicto de clave en el registry porque curriculum-mapping no comparte objectTypes con curriculum-design. El esqueleto asume pack nuevo.
¿Qué partes de la matriz cambian con UPONE-1633? (abierta — coordinación)
No es verificable solo por código: requiere hablar con el dueño de 1633. Como el alcance es lectura y la salida se proyecta por publicFields, agregar campos o recordTypes es aditivo-safe, así que el riesgo de retrabajo es bajo; aun así conviene confirmar el subconjunto antes de fijarlo.
¿Por qué basta declarar el objeto para poder consultarlo, sin escribir código?
Porque el CRUD genérico opera cualquier objeto del allowlist que tenga contrato, aplicando el contrato y el permiso objeto:view. El allowlist es la unión de los objects de todos los packs; agregar el pack suma sus objetos al allowlist en runtime. Es la Receta 1.
¿Qué protege que el MCP no se vuelva una puerta lateral que evade reglas?
Dos barreras: el guard del allowlist (objeto no habilitado → rechazado) y la verificación de permisos del usuario real (sin objeto:view → PERMISSION_DENIED), además del RBAC server-side de up1. Para escritura se suma que las mutations validadas bloquean el CRUD genérico y obligan a pasar por la tool de dominio.
¿Por qué "leer la matriz" no es solo listar CompetencyNode?
Porque en la misma tabla base conviven Matrix, Competency y SubCompetency. Un listado plano los devuelve mezclados; para "la matriz" se filtra por recordType = Matrix (vía query_records con un filtro). Lo mismo aplica a Scheme/Level en los esquemas.
