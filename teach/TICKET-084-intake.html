Registro del mod + cobertura MCP de los 3 objetos de malla

Los tres objetos que modelan la malla curricular — planEntry (la entrada de plan: una asignatura o bloque dentro de un currículo), requirementCategory (categoría de créditos que agrupa entradas) y requirement (el motor de reglas, un Composite con 3 RecordTypes) — ya existen: los crearon los tickets MC-02 (TICKET-082) y MC-03 (TICKET-083). Pero existir no es lo mismo que estar operables. MC-04 los hace operables en dos frentes que viven en repos distintos: la UI (registro en el mod curriculum-design) y la vía conversacional/programática (el adaptador up1-mcp, que opera up1 como el usuario real vía Elric). Cerrar esto cierra la "Épica A" del sprint: el modelo de malla queda completo y consumible.

TL;DR — Qué hay: 3 objetos creados por MC-02/03, pero sin registrar (sin capabilities CRUD en el mod) y sin exponer (no están en el allowlist ni tienen contrato en el MCP). Qué se hará: (1) registrar CRUD + reconciliar layouts + verificar lang en el mod; (2) declarar 3 ObjectContract + ampliar el allowlist + extender el resolver de FK para el ownerId polimórfico en el MCP; (3) smoke real vía GraphQL. Por qué: habilita el componente de malla (MC-05/06) y a Elric para operar estos objetos. El trabajo es casi todo declarativo — el único código real es ~20 líneas para la FK polimórfica.

Las bases — el vocabulario del caso

Para diseñar bien este ticket hay que entender sobre qué piso nos paramos. Estos cinco ladrillos son el conocimiento fundacional: tres del lado del mod (cómo un objeto se vuelve "operable" en la UI de up1) y dos del lado del MCP (cómo se expone un objeto a Elric sin escribir código nuevo).

capabilities.json (mod)

Declara los permisos RBAC del mod. El registro CRUD de un objeto es object-level RBAC: entradas <obj>:view|create|modify|delete sin prefijo mod/ (RULE-mods-037 — la regla que estandariza permisos por objeto). Hoy NO existe ninguna para los 3 objetos.

layouts (mod)

JSON por objeto que define cómo la suite renderiza listas y detalles. Sufijos: _list (RecordList, también controla el menú), _view/_create/_edit (RecordDetail). La ausencia de _list = el objeto no aparece como menú propio.

lang/es_CL (mod)

Traducciones de labels de columnas + valores de enum. MC-02/03 ya los dejaron completos para los 3 objetos — MC-04 solo verifica cobertura, no crea.

ObjectContract (MCP)

Entrada declarativa en registry.ts que describe un objeto al MCP: campos obligatorios, enums con etiquetas, FK, validaciones espejo. Agregar un objeto = agregar una entrada; el núcleo genérico no cambia. BibliographyReference es el molde mínimo.

allowlist (MCP)

Unión de los objects de cada mod pack (allowedObjectTypes()). El CRUD genérico (create_object, etc.) se rehúsa a tocar un objeto que no esté aquí. Es el guard de exposición.

resolveReference (MCP)

Resuelve una FK escrita por el usuario como nombre/código → id real. Config-driven: si el FieldDoc declara fk, se resuelve solo. Limitación clave: el target (doc.fk) es estático.

Cómo funciona hoy — el contrato deriva todo

Lo elegante del MCP es que una sola entrada declarativa alimenta varias capacidades. Cuando declaras un ObjectContract, las tools describe_object y get_create_guide derivan su salida del contrato (enums + FKs + guía), y create_object aplica las validaciones espejo y resuelve las FK por nombre — todo sin escribir una tool nueva. Por eso REQ-03/04/05 son baratos: el flujo abajo ya existe; solo le agregamos 3 entradas. Mira cómo un mismo contrato se ramifica en describe / create / resolve.

Dos cosas que el diagrama deja ver y conviene notar antes de diseñar. Primero: el ObjectContract es el único punto de entrada — no hay lógica dispersa, todo cuelga de esa entrada declarativa. Segundo, y es la sorpresa del caso: la rama polimorfica ownerId termina en un gap. Eso es lo que nos lleva al entorno del caso y, después, a la única pregunta realmente abierta.

El entorno — qué rodea el caso

MC-04 no nace en el vacío: hereda decisiones de los dos tickets que lo preceden y vive a caballo entre dos repos. Entender ese contexto lateral evita re-hacer lo ya decidido y evita romper el aislamiento entre repos.

⚠ Cross-repo (DET-19) — El ticket toca DOS repos git independientes: el mod up1/mods/curriculum-design/ (rama UPONE-1267-sp5) y el adaptador standalone uplanner/mcp/ (su propia rama UPONE-1267-sp5, default main). Los commits usan el id externo UPONE-1347, no TICKET-084. El acoplamiento mod→MCP lo gobierna RULE-mcp-015 (cualquier objeto desarrollado en el mod se cubre en el MCP en el mismo sprint).
ℹ Decisiones heredadas de MC-02/03 que MC-04 debe respetar — MC-02 decidió que planEntry se crea vía el componente de malla, no como menú suelto (por eso solo tiene _view, sin _list). MC-03 decidió que requirement es no-menú (9 layouts de detalle por RecordType, ningún _list). El enunciado de REQ-01 dice genéricamente "RecordList/RecordDetail" — no hay que tomarlo literal y re-introducir listas que esos tickets omitieron a propósito (DET-16, propagación: respetar lo ya decidido).
ℹ Dónde estamos parados respecto al modelo — La malla en la UI consume el GraphQL nativo del mod (no necesita el MCP). El MCP es la vía conversacional/programática (Elric). Son dos consumidores independientes del mismo modelo — por eso el ticket tiene dos mitades que casi no se tocan.

La pregunta abierta a explorar — la FK polimórfica de requirement.ownerId

Aquí está la única tensión de diseño del ticket, y conviene llevarla resuelta al spec. requirement tiene un dueño polimórfico: ownerType (curriculum / activity / offering) decide a qué objeto apunta ownerId. El resolver actual (resolveContractInputs) solo sabe resolver FK con target fijo (doc.fk es un string). MC-03 zanjó esto como "convención documentada" (no resolver), pero REQ-05 de MC-04 pide explícitamente que ownerId se resuelva por nombre condicionado a ownerType. Las dos lecturas en juego:

A · Extender el resolver (config-driven)

Agregar soporte para una FK cuyo target sale de otro campo: un FieldDoc tipo polymorphicFkFrom: "ownerType" que mapea cada valor de enum → objectType, y resolveContractInputs resuelve dinámicamente.

+ Cumple REQ-05 al pie de la letra: ownerId="EST200" resuelve al id real.

+ ~20 líneas, sigue siendo config-driven (encaja con la filosofía del registry).

− Es el único código no-declarativo del ticket → concentra el riesgo (por eso S2 es ⚑ fuerte).

B · Convención documentada (heredar MC-03)

Declarar ownerId sin fk (passthrough): el usuario debe pasar un id ya resuelto; las FK estáticas (planId, categoryId…) sí se resuelven por nombre.

+ Cero código: 100% declarativo, riesgo mínimo.

− No cumple el enunciado literal de REQ-05 (que dice "resueltas por nombre/código, ownerId condicional a ownerType").

− Peor ergonomía para Elric (pedir un id crudo rompe el patrón "habla en lenguaje de negocio").

La orientación (a confirmar en design-feature): A, porque REQ-05 está confirmed y nombra explícitamente el caso polimórfico, y porque la extensión es pequeña y respeta la naturaleza config-driven del registry. B queda como fallback si la extensión resulta más invasiva de lo previsto. Esto es lo primero que el spec debe cerrar.

Q&A de estudio — ¿entendiste el caso?

¿De qué se trata el caso, en una frase?
Tomar 3 objetos de malla que ya existen pero están "mudos" (sin permisos CRUD en el mod, sin contrato en el MCP) y hacerlos operables en la UI y conversacionalmente, cerrando la Épica A del sprint.
¿Por qué el trabajo es tan barato si toca dos repos?
Porque es casi todo declarativo: en el mod son entradas JSON (capabilities/layouts/lang) y en el MCP son 3 entradas de config en registry.ts que el núcleo genérico ya sabe consumir (describe/create/resolve derivan solas). El único código real son ~20 líneas para resolver la FK polimórfica.
¿Cuál es la pregunta abierta más crítica a verificar primero?
Cómo resolver requirement.ownerId (FK polimórfica): extender el resolver config-driven (opción A, orientación recomendada por REQ-05) vs dejarlo como convención documentada (opción B, heredada de MC-03). Es lo primero que el spec debe cerrar porque concentra todo el riesgo del ticket.
¿Qué NO hay que hacer aunque REQ-01 lo sugiera?
No re-introducir layouts _list para los 3 objetos. MC-02 (planEntry vía malla) y MC-03 (requirement no-menú) los omitieron a propósito; "RecordList/RecordDetail" en REQ-01 es genérico, no literal (DET-16).
¿Qué quedó fuera de alcance (drop)?
Las tools cd_* de dominio ergonómicas para estos objetos → SP6. El CRUD genérico ya cubre las operaciones; las tools de conveniencia no son necesarias para cerrar la Épica A.
