Cierre: qué se hizo en la vista de crear factura

Este documento mira hacia atrás: qué se implementó, qué decisiones se cerraron y qué quedó aprendido. Las bases y el contexto están en el teach-intake — acá no se repiten. El ticket alineó la sección de cliente/receptor y el campo Fecha de la vista de crear factura a la maqueta, en 2 sessions, 100% frontend.

TL;DR — Se construyó un DatePicker propio (con date-fns, cero dependencias nuevas) para el campo Fecha; se unificaron los dos inputs de RUT en un único select-suggest que al elegir un cliente puebla los 5 datos del receptor; y se implementó "Actualizar receptor" (re-fetch por RUT). 1477 tests verdes, cobertura global ≥90, sin romper el autocompletado previo (JOR-058).

Qué se hizo, por session

Dos sessions, cada una cerrada con tests verdes y cobertura ≥90. El orden aisló la decisión de dependencias en S1.

S1 — DatePicker propio

Se creó ui/date-picker/ (componente + test + story + barrel): un calendario en popover construido con date-fns, con cierre por click-fuera/Escape, integrado a react-hook-form vía Controller. Se reemplazó el <input type=date> del campo Fecha. Se adaptó 1 test que asertaba el input nativo. Commit 25cbbd3.

S2 — Cliente y receptor

Se extendió el schema del receptor a 5 campos (opcionales); se unificaron los dos inputs de RUT en un único select-suggest que al elegir puebla los 5 datos y se muestran en "Datos del cliente"; y "Actualizar receptor" pasó de stub a re-fetch por RUT (con AbortSignal). Se adaptaron los tests del autocompletado JOR-058 y del guard. Commit 2d35c52.

Cómo evolucionaron las hipótesis

✓ H1 confirmada — el poblado y el refresh eran cableado front puro: el endpoint y el clienteSchema ya tenían los 5 campos; solo faltaba extender el schema del receptor y poblar en el onSelect/handler. Se confirmó en 4 capas.
H2 resuelta en ejecución — la duda de dependencias (¿shadcn con react-day-picker/cmdk?) se cerró por el camino de mínimas deps: se construyó todo con date-fns + el listbox que ya existía. Cero deps nuevas, sin rebuild de imagen.
H3 confirmada — el DatePicker quedó como primitiva reusable en ui/date-picker/, sin bloquear contra el spec de la librería UI (JOR-006).

Decisiones que quedaron cerradas

Cero dependencias nuevas

DatePicker con date-fns + popover propio (patrón del listbox existente). Respeta "solo aditivo" y evita rebuild. El DET-32 quedó registrado como mixed (build el picker, reduce el select y el schema).

Un único campo RUT

Se eliminó el input de RUT suelto y el de razón social; el select-suggest es la única entrada, alineado a la maqueta 03. Los datos completos viven en "Datos del cliente".

Schema aditivo

telefono/ciudad/direccion se agregaron como opcionales al receptor para no romper el listado (vista 02) ni el refine de emisión.

Smoke no reproducible

La vista completa necesita Docker + CIAM/MSAL; el smoke en navegador quedó como smoke-not-reproducible (auditado), con el render jsdom del flujo como evidencia más fuerte disponible.

Lecciones (lessons learned)

Tests atados al widget nativo son frágiles — varios tests asertaban input[type=date] o el placeholder del RUT; al cambiar el widget hubo que adaptarlos. Conviene asertar rol/comportamiento, no el elemento nativo (ya cubierto por RULE-frontend-002).
Campo RHF ≠ state local de UI — el buscador select-suggest es state local, no ensucia el form; los tests del guard de cambios deben ensuciar vía un campo registrado (se usó O.C.). Distinción clave al escribir tests de "unsaved changes".
Reuso > build paga — el listbox del autocompletado previo (JOR-058) se reutilizó para el select-suggest; el DET-32 evitó introducir cmdk/react-day-picker sin necesidad.
Hecho: DatePicker + RUT único + refresh Follow-up: catalogar DatePicker en la librería UI (JOR-006) Follow-up: smoke real cuando haya entorno Docker/MSAL

Q&A de cierre

¿Qué cambió para el usuario?
Un solo campo Rut/Razón social con autocompletado; al elegir un cliente ve todos sus datos (teléfono, ciudad, dirección incluidos); un selector de fecha propio; y un botón "Actualizar receptor" que ahora sí recarga los datos.
¿Por qué no se usó el DatePicker estándar de shadcn?
Habría requerido 2-3 dependencias nuevas (react-day-picker, cmdk, popover) y rebuild de imagen. Con date-fns (ya instalada) y el patrón de popover que la vista ya usaba, se logró el mismo resultado sin deps. Decisión registrada en DET-32.
¿Cómo se garantizó no romper lo anterior?
La suite completa quedó en 1477/1477 verde con cobertura global ≥90; los tests del autocompletado JOR-058 se preservaron (adaptando solo selectores, no comportamiento). El schema se extendió con campos opcionales para no afectar el listado ni la emisión.
¿Qué quedó pendiente?
Dos follow-ups no bloqueantes: catalogar el DatePicker en la librería UI (JOR-006) y correr un smoke real de la vista cuando haya entorno Docker/MSAL disponible.
