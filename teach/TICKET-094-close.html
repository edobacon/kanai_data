Lecciones (promovidas a reglas)

Dos aprendizajes del ejecutar que se convirtieron en reglas del módulo para el próximo custom element. Conectan directo con la evolución de H2 (cómo escribir el element) y con la mecánica de i18n del storybook.

⚠ RULE-curriculum-design-019 — Un custom element WRITABLE va con setup(props,{element}) + element.update() + useI18n().t, NUNCA con Options-API methods/data. Con methods, vue-tsc lanza TS2349 "not callable" en TODO el template (pasó en S1: 5 errores que se evaporaron al migrar a setup()). RichTextRenderer/ActivityStatusBadge no fallan porque son read-only (solo computed).
ℹ RULE-curriculum-design-020 — El i18n de un componente va ANIDADO bajo su clave en es_CL.json (como richTextRenderer), no en un es_CL@comp.json de claves planas: el storybook preview hace Object.assign flat sobre todos los lang → las claves planas colisionarían entre componentes.
✓ Patrón de prueba a11y del mod — Como el SFC Vueform no se monta en vitest, los tests construyen el DOM espejo (radiogroup / listbox) y corren axe-core. El indicador de selección del ColorPicker se hizo SVG aria-hidden (no texto) para no disparar color-contrast sobre swatches claros.

Q&A de cierre

¿Por qué el layout view no usa los pickers?
DEC-LOCAL-03: los pickers son interactivos (submits:true, grilla clickeable) y no tienen modo read-only. Meter una grilla seleccionable en una pantalla de solo-lectura es UX incorrecta. view muestra el valor como texto; la selección visual (el core del request) vive en create/edit. Un render read-only dedicado (chip de color + glifo) sería un follow-up.
¿Cómo se entera el dev de que funciona en la suite real?
El smoke runtime es DB-gated: los layouts viven en la DB del tenant y se aplican con npm run sync. La verificación de código (JSON válido, suite 836/836, axe 0, eslint 0, tsc 0) está hecha; el render real en la suite lo corre el dev tras el sync, igual que MC-02/MC-02-fix. Storybook cubre la verificación visual aislada de ambos pickers.
¿Qué quedó fuera de alcance?
Color hex libre (solo swatches de tokens, DEC-LOCAL-01); reusar los pickers en otros objetos (solo cableados en requirementCategory); render read-only del view; LLM-e2e de keyboard interaction (diferido como en el resto del mod). Nada de esto bloquea: el valor central — elegir color/ícono visualmente — está entregado.
Si mañana creo un tercer picker, ¿qué leo primero?
RULE-curriculum-design-019 (cómo escribir el element writable sin romper el tipado), RULE-020 (dónde poner el i18n), y las guías docs/guides/color-picker.md / icon-picker.md como plantilla (incluyen la sección Accesibilidad que RULE-002 exige).
