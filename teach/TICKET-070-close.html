Lo que sostiene la solución

El adapter es thin: arma el alias, normaliza el payload (strip de discriminador + vacíos) y delega. Ninguna lógica de negocio, ningún prisma.create propio.
Corolario: el día que el split base→alias viva en createInstance de core (backlog B1, camino B), esta mutation se vuelve redundante y se retira — el form vuelve a submitear a la base.

Lecciones

La lección de proceso (la más importante): por qué TC-2 dio "verde" y el Minor seguía roto
La prueba a nivel API de Minor mandó solo los campos comunes — pero el formulario único multi-RecordType manda los campos de TODOS los tipos (con conditions), así que al elegir Minor envía progression/totalCredits/… como null. Verificar a nivel payload NO replicó el camino del usuario. Regla práctica: para un form multi-RT, el repro DEBE incluir los campos ocultos por conditions. Y para una TC que afecta UI, el smoke real del browser no es opcional — fue el dev quien lo cazó (L3).
¿Por qué el strip de campos vacíos es correcto y no "lógica de negocio"?
En un CREATE, un campo vacío (null/'') = "no provisto". Dropearlo es higiene de datos genérica (no sabe de RecordTypes, no decide nada de dominio). Conserva false y 0 (valores significativos). El adapter sigue siendo thin.
¿Por qué enumerar campos en el customEndpoint si queríamos que "escale solo"?
El engine de layout no soporta pasar el form entero (source: "formData" whole-object). Con inputVariable: "data" + campos enumerados se logra un data: JSON! equivalente, pero un campo nuevo exige una línea en el layout. La generalidad sobre recordType sí se conserva (tipos nuevos no tocan nada). Es otro argumento para mover el split a core (B).
