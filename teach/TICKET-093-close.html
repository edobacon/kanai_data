La decisión que ahorró tocar el backend

Contexto

El request pedía declarar metadata.directChildren en Curriculum.json como parte del embedding.

Decisión

Grep de directChildren: 0 usos en layout/src/suite/src; solo en object-manager (deepClone/versioning). Se descartó (DET-32 → drop): no participa del embedding y tocaría backend.

Resultado

Fix mínimo, mod-only, cero backend. Curriculum.json intacto. El embedding lo da el record-list del layout.

Lecciones

✓ L1. En up1, metadata.directChildren la consume solo el object-manager (deepClone/versioning + codegen). El embedding de hijos como pestañas se logra con el campo record-list + filters {{parentId}} del layout de detalle. No confundir las dos capas.
⚠ L2 (propagación). Curriculum declara metadata.versioning pero no directChildren → versionar/clonar un Currículo no cascadea sus hijos planEntry/requirementCategory. Gap latente para el ticket de versioning (UPONE-1270), fuera de este fix.
ℹ L3. Verificar el supuesto del request con un grep antes de implementarlo evitó un cambio de backend innecesario. El request es una hipótesis de cómo arreglar, no un contrato de implementación (DET-32 permite drop de un item aunque venga "confirmado").

Invariante

Embedding de hijos como pestaña = campo record-list + filters {{parentId}} en el layout de detalle del padre. La metadata del objeto (directChildren/polymorphicChildren) es ortogonal: gobierna clone/versioning en el backend.
Corolario: para mover un objeto "del menú a una pestaña" basta borrar su _list y agregar un record-list filtrado al detalle del padre — sin tocar el objeto ni el backend.

Q&A de estudio

¿Cómo se garantizó "cero backend"?
El diff (`git diff --name-only`) toca solo config/layouts/ (4 archivos) y un test. Ningún objeto (Curriculum.json etc.), resolver ni seed. El dual-judge lo verificó como dimensión.
¿Qué quedó pendiente / DB-gated?
El smoke visual: los layouts viven en la DB del tenant y se aplican con npm run sync. Los TC-01..05 (menú sin los objetos, pestañas con datos, CRUD de líneas) los verifica el dev tras el sync. La verificación de código (JSON válido + suite 788/788 + dual-judge) ya pasó.
¿Por qué la pestaña "Malla curricular" puede verse vacía?
Filtra planEntry por planId; solo los currículos de recordType=Plan tienen entradas. Para un Minor la pestaña aparece pero vacía — aceptable en SP5. Condicionar su visibilidad por recordType sería un follow-up.
