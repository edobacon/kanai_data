Selección visual de color e ícono para las líneas de formación

Una línea de formación (objeto requirementCategory, creado en el sprint MC-02 / TICKET-082) agrupa requisitos de créditos de una malla y se presenta con un color y un ícono. Hoy esos dos campos son cajas de texto: el usuario debe escribir a mano var(--up1-color-primary) o bi-mortarboard. Eso es frágil y poco descubrible. Este ticket entrega lo que MC-02 dejó pendiente: dos selectores visuales — pinchar un swatch de color del tema y pinchar un ícono de un catálogo con búsqueda — implementados como elements custom de Vueform dentro del mod curriculum-design.

TL;DR — Qué hay: los campos color e icon de requirementCategory son type:text en los layouts create/edit/view (MC-02). Qué se hará: crear dos Vueform elements custom en modsComponents/ — ColorPickerElement (grilla de swatches de los tokens --up1-color-*) e IconPickerElement (grilla de bootstrap-icons con búsqueda) — y reemplazar type:text por type:color-picker / icon-picker en los layouts. Incluye lang, storybook y tests a11y. Por qué: el valor sigue siendo el mismo string (token/hex y bi-*) — cero cambio de objeto/schema/backend — pero la captura pasa de "escribir un código" a "elegir visualmente".

Las bases — el vocabulario del caso

Seis ladrillos. Todo el cambio gira sobre cómo un element de Vueform (un widget de formulario reusable) se registra por su type y se cablea en un layout sin tocar el backend.

requirementCategory

"Línea de formación". Tiene color e icon como string nullable (FK curriculumId → Currículo). El valor que estos pickers producen/leen.

Vueform element

Widget de formulario declarado con defineElement({ name, ... }). El motor de layouts lo instancia por su type. Lee/escribe su dato vía this.value.

type (registro)

String que un layout usa para pedir un element ("type": "color-picker"). Se deriva del name PascalCase+Element → kebab-case. Auto-registrado por glob.

layout

JSON en mods/curriculum-design/config/layouts/. default_requirementCategory_{create,edit,view}.json definen los campos del formulario. Aquí cambia type:text → picker.

design tokens

Variables CSS --up1-color-* (layout/src/styles/design-tokens/colors.css): primary, success, danger, warning, info, purple, rose, gray. Los swatches del ColorPicker.

bootstrap-icons

Dependencia del mod (^1.13.1). 2078 íconos como clases bi bi-*; el manifest font/bootstrap-icons.json da la lista de nombres. El catálogo del IconPicker.

Cómo se registra y se cablea — el patrón que ya existe al lado

No inventamos el mecanismo: el mod ya tiene tres elements custom — ActivityStatusBadge, CompositeSectionTree y RichTextRenderer (el más simple para imitar). El vueform.config.ts del mod hace import.meta.glob(['./modsComponents/*/*.vue']) y registra todos automáticamente: basta crear el .vue en su carpeta, sin tocar ningún registry. El npm run sync copia esos .vue al vueform.config.ts del layout para que la suite real los conozca. El diagrama muestra el camino del dato.

El eje que define el alcance: construir el widget vs reusar primitivas

La RULE-curriculum-design-015 (reusar Vueform search+create, no construir desde cero) y la RULE-curriculum-design-002 (WAI-ARIA APG obligatorio en elements compuestos) enmarcan la pregunta: ¿cuánto construimos a mano? La respuesta es un punto medio — apoyarse en las primitivas (tokens, manifest de íconos, atoms del mod) y construir solo la grilla seleccionable accesible. Esto se cerrará formalmente en el gate de necesidad/reuso (DET-32) durante el design.

reusar las primitivas ✓

Tokens --up1-color-* + manifest bootstrap-icons.json + patrón defineElement existente.

+ Los swatches/íconos salen de la fuente de verdad del tema, no de una lista duplicada a mano.

+ Cero dependencias nuevas: bootstrap-icons ya está instalado.

librería externa de picker ✗

Un color/icon-picker de npm con su propio markup.

− Su a11y no necesariamente cumple WAI-ARIA APG (RULE-002) ni su look el tema up1.

− Dependencia nueva en el mod por un widget que es ~1 grilla seleccionable. YAGNI.

Restricciones que enmarcan el trabajo

⚠ a11y no es opcional. RULE-curriculum-design-002 (nivel must) exige WAI-ARIA APG: el ColorPicker es un radiogroup (roving tabindex, aria-checked); el IconPicker es grid/listbox + campo de búsqueda etiquetado. Tests con axe-core (patrón tests/integration/activity-status-badge-a11y.test.ts), no jest-axe.
ℹ Cero backend. color/icon ya son string nullable en requirementCategory.json. El valor que el picker emite es el mismo string que hoy se escribe a mano → no se toca objeto, schema, resolver ni seed.
ℹ DB-gated. Los layouts viven en la DB del tenant y se aplican con npm run sync. La verificación de código es: JSON válido + suite del mod (vitest) sin regresión + axe sin violaciones + storybook. El smoke visual en la suite lo corre el dev tras el sync (precedente MC-02 / MC-02-fix).

Hacia adelante — el plan

Tres sesiones. Cada picker es una unidad cohesiva (componente + lang + story + tests) y se ejecuta en serie; el cableado de layouts cierra al final porque depende de ambos types. El detalle (REQ, task contracts) lo fija el design-feature.

S1 (T2 ⚑) — ColorPickerElement

Element radiogroup de swatches de tokens --up1-color-* + lang + storybook + tests unit/a11y. Emite/hidrata string token o hex.

S2 (T2 ⚑) — IconPickerElement

Element grid + búsqueda sobre el catálogo bootstrap-icons + lang + storybook + tests unit/a11y. Emite/hidrata bi-*.

S3 (T1) — Cablear layouts

Cambiar type:text → color-picker/icon-picker en create/edit/view de requirementCategory + regresión. Smoke runtime DB-gated diferido al dev.

Q&A de estudio

¿Cómo se registra un nuevo element type sin tocar ningún registry?
El vueform.config.ts del mod hace import.meta.glob(['./modsComponents/*/*.vue']) y mapea cada módulo a elements. El type sale del name del defineElement: ColorPickerElement → color-picker. Basta crear el .vue en modsComponents/ColorPicker/; el npm run sync lo propaga al layout/suite. Convención verificada en los 3 elements existentes.
¿Por qué no cambia nada del backend ni del objeto?
Porque el contrato del dato no cambia: color e icon siguen siendo string nullable (token var(--up1-color-*)/hex y bi-*). El picker es solo la forma de capturar ese string. Por eso es creates_data:false y todo el cambio cabe en mods/curriculum-design/ (componentes + layouts), layer:mod.
¿Qué hace que la a11y sea la parte no trivial?
RULE-curriculum-design-002 (must) obliga WAI-ARIA APG en elements compuestos. Una grilla de colores/íconos no es un <input>: necesita rol semántico (radiogroup para color, grid/listbox para íconos), navegación por teclado (roving tabindex, flechas), estado aria-checked/aria-selected y, para el ColorPicker, contraste suficiente de los swatches. Cada picker lleva un test axe-core wcag2aa/wcag21aa con 0 violaciones.
¿Por qué este ticket va después del embedding (TICKET-093) y no antes?
Ambos tocan los layouts create/edit de requirementCategory. TICKET-093 (MC-02-fix) reorganizó dónde se ven esos layouts (pestañas dentro del Currículo). Hacer los pickers después evita conflictos de edición sobre los mismos JSON y parte de una base ya consolidada. Por eso depends_on: [TICKET-082, TICKET-093] — ambos cerrados.
