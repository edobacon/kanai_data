false-Restrict por casing + hardening del motor de delete cascade

Este ticket corrige defectos encontrados al revisar como PR el trabajo de TICKET-104 / UPONE-1382 — el motor de hard delete en cascada (borrar un objeto y arrastrar consigo a sus hijos poseidos, en una sola operacion). El motor vive en object-manager/src/graphql/resolvers/helpers/deleteImpactPlan.js, aun en su rama feat/UPONE-1382-hard-delete-cascade (sin mergear a develop). El defecto central: al intentar borrar un Curriculum (un Plan) que tiene alguna requirementCategory, el motor bloquea el borrado por error — cree que la categoria es una referencia externa cuando en realidad es un hijo que deberia arrastrarse en la cascada. La causa es sutil: una comparacion de strings sensible a mayusculas/minusculas.

TL;DR — Que hay: el motor de delete cascade marca un falso Restrict (bloqueo) al borrar un Plan con requirementCategory, porque compara la clave del subarbol con distinto casing (requirementCategory:id vs RequirementCategory:id). Los unit tests estan verdes porque cargan un nombre PascalCase que no existe en el JSON real. Que se hara: normalizar la comparacion de claves (no comparar PascalName crudo), corregir los tests para que carguen el object real del JSON, agregar integration contra BD real + smoke por la UI, hacer hardening (perf, dead code, ids DET-19), completar i18n en/pt y registrar el KB de la review. Por que importa: vive en core (blast radius amplio, exige revision del equipo core) y un usuario no puede borrar un Plan con categorias — funcionalidad rota.

Lo que rodea el caso

Antes de tocar el motor conviene entender el entorno: no es un fix aislado de un mod, es un cambio en codigo compartido de core con reglas y precedentes que aplican. Estos tres avisos condicionan como se ejecuta el fix.

✗ Es core, no mod — deleteImpactPlan.js alimenta deleteBulkInstances/deleteInstance para todos los objetos, no solo curriculum-design. Por RULE-dev-004 (regla del proyecto: el codigo core de una epica va en una rama unica y se mergea a develop solo tras revision del equipo core) el diff debe pasar por revision del equipo core antes del merge. La quality review del mod no alcanza.
⚠ Los unit verdes mienten — memoria de proyecto: "unit tests mockeados consagran bugs de runtime en codigo de datos". Aca es exacto: el prisma mockeado con un object PascalCase inventado deja el test verde mientras el runtime real (con el JSON en minuscula) falla. Por eso el fix EXIGE integration contra BD real, no basta corregir el unit.
ℹ Diseno defensivo previo — el motor ya cita bug-curriculum-design-003 (Curriculum no declara directChildren para todos sus hijos) como base de su logica. El false-Restrict de esta review es un bug nuevo, candidato a registrarse formalmente (backlog B1).

Conceptos clave (las bases)

Seis ladrillos para entender el mecanismo. Los primeros tres son del dominio de borrado; los ultimos tres son la mecanica de nombres donde vive el bug.

cascade vs Restrict

Al borrar un objeto, un hijo poseido se borra en cascade. Si algo externo lo referencia, el motor marca Restrict y bloquea con un mensaje "esta en uso por N...".

deleteImpactPlan

El motor (helper de object-manager) que, dado un objeto, arma el plan: nodos (que se borra), edges (relaciones), restrictions (que bloquea) y deleteOrder. Read-only; el delete real lo consume.

requirementCategory

Hijo directo de un Curriculum (FK curriculumId). Es poseido exclusivo: al borrar el Plan deberia caer en cascade, no bloquear.

subtreeKeys

El set de claves objectType:id de todos los nodos del plan. Sirve para decidir si una FK entrante apunta dentro del subarbol (hijo) o fuera (referencia externa → Restrict).

metadata object

El campo object que un JSON declara para un hijo. Curriculum.json lo declara en minuscula: "object": "requirementCategory".

PascalName

El nombre del modelo Prisma capitalizado (requirementCategory → RequirementCategory) que el escaneo de FK entrantes usa para reportar el objeto referenciante.

Como camina el motor (y donde rompe)

El flujo tiene dos mitades. La primera (walkDirectChildren) arma los nodos del subarbol usando el object de la metadata verbatim — asi las claves quedan en minuscula. La segunda (detectRestrictions → findIncomingReferences) busca quien referencia a cada nodo y, para decidir si es externo, compara contra subtreeKeys usando el PascalName. El punto rojo es donde los dos casings se cruzan sin matchear.

El mecanismo, en el codigo real

Tres puntos de deleteImpactPlan.js (lineas confirmadas contra la rama el 2026-07-15). La clave se construye con object crudo; el filtro compara con PascalName. Nunca coinciden cuando el JSON declara el hijo en minuscula. 

// :473  walkDirectChildren — la clave usa `object` verbatim (minuscula del JSON)
const key = `${object}:${child.id}`;   // => "requirementCategory:RC1"

// :722  findIncomingReferences — el objeto referenciante se reporta capitalizado
const PascalName = modelName.charAt(0).toUpperCase() + modelName.slice(1); // "RequirementCategory"

// :669-671  filterExternal — compara PascalName:id contra el set de claves minuscula
const filterExternal = (referencingObjectPascal, ids) => {
  if (!subtreeKeys) return ids;
  return ids.filter((id) => !subtreeKeys.has(`${referencingObjectPascal}:${id}`)); // "RequirementCategory:RC1" ∉ {"requirementCategory:RC1"}
};

Cuando el motor marca "referencia externa"

La regla que deberia gobernar el Restrict, y por que hoy da un falso positivo:

una FK entrante es referencia externa (→ Restrict) SI Y SOLO SI:
(a) apunta a un nodo del plan, Y
(b) ese nodo NO pertenece al subarbol que se va a borrar
El bug: la clausula (b) se evalua con subtreeKeys.has(PascalName:id), pero el set contiene object:id (minuscula). El casing hace que (b) de true siempre para hijos declarados en minuscula → falso Restrict.

Invariante a preservar

Un nodo que pertenece al subarbol del plan nunca debe contarse como referencia externa, independiente del casing con que la metadata declare su nombre.
Corolario: la comparacion de pertenencia al subarbol debe ser sobre identidad normalizada (objectType:id resuelto por introspeccion), no sobre strings crudos que dependen de como cada JSON escribio el nombre.

Preguntas abiertas a verificar

El intake dejo dos hipotesis confirmadas (H1 el false-Restrict, H2 el falso verde del unit) y una parcial. Estas son las preguntas que el execute debe cerrar con evidencia, no asumir.

¿La causa raiz es exclusiva de requirementCategory o es general? (H3, parcial)
El mecanismo (comparar PascalName crudo contra la clave de metadata) es general. Hoy solo requirementCategory lo gatilla: planEntry usa FK planId (no curriculumId) y requirement usa ownerType minuscula que no matchea el scan. Se confirma empiricamente al normalizar + correr TC-3 (integration con planEntry): debe seguir sin regresionar.
¿Por que dos tests distintos usan PascalCase inexistente?
El caso T4 (:275) y el test de historyKey (:550) declaran object: 'RequirementCategory'. Ambos hay que corregirlos al casing real del JSON (requirementCategory) en S1.T2, o el fix queda sin cobertura real.
¿La asimetria preview vs delete real es un hueco? (C5)
No es hueco de integridad: deleteImpactPreview corre el motor para cualquier objeto, mientras el delete generico gatea por hijos declarados y confia en el FK constraint de la BD. Pero UI y backend pueden divergir en el mensaje. Es una decision a registrar (B5), no un fix.
