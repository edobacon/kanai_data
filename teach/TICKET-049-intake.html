Derived genérico en codegen — remap declarativo de FKs internas entre hijos clonados

Cuando un usuario crea una nueva versión de un objeto (ej. una Activity en el módulo curriculum-design), el motor de object-manager clona en cascada a sus hijos polimórficos — las CurricularSection. Pero hay un detalle que el motor no resuelve solo: algunos hijos tienen foreign keys (FK) que apuntan a otros hijos — un CurricularLink referencia dos CurricularSection vía sourceSectionId/targetSectionId. Tras clonar, esas FK siguen apuntando a las secciones viejas. Hoy eso se arregla con un hook escrito a mano por módulo. Este ticket convierte ese arreglo en una capacidad declarativa del motor, para que cualquier objeto futuro lo obtenga gratis.

TL;DR — Qué hay: el motor de clonado de versionado remapea el dueño y el self-ref de los hijos, pero las FK entre hijos las remapea un hook + flow n8n escrito a mano en curriculum-design (~93 líneas). Qué se hará: generalizar ese remap a un bloque declarativo polymorphicChildrenDerived persistido por el codegen + una fase derived genérica en el motor, y retirar el hook + flow por-módulo. Por qué: elimina deuda técnica por-mod y habilita a cualquier objeto futuro a remapear sus FK internas sin código a medida.

Conceptos clave (las bases)

Seis ladrillos conceptuales sobre los que se apoya todo el caso. Los tres primeros son el mecanismo de clonado que ya existe; los tres últimos, el arreglo por-módulo que vamos a generalizar. Si entiendes estos seis, entiendes el problema completo.

deepClonePolymorphicChildren

La función del motor (deep-clone-polymorphic.js) que, al versionar, clona en cascada a los hijos polimórficos de un objeto. Invocada dentro de finalizeCreate del resolver de instancias.

cloneMap / buildRemapAPI

El índice Map<oldId → {newId, type}> que el clonado va construyendo. buildRemapAPI lo envuelve con has/remap/typeOf/toObject — es la pieza que sabe a qué id nuevo corresponde cada id viejo.

polymorphicChildren

Bloque de metadata por objeto que declara qué hijos clonar y cómo ({name, object, via, ownerTypeValue, recursiveBy}). El motor remapea el dueño y el self-ref, pero no las FK entre hijos.

FK interna entre hijos (FK derivada)

Una FK de un hijo clonado que apunta a otro hijo clonado del mismo árbol. Ej: CurricularLink.sourceSectionId → una CurricularSection. Tras clonar, queda apuntando a la sección vieja: hay que remapearla con el cloneMap.

versioningConfig

Columna de core_ObjectDefinition que el codegen llena con {versioning, prefillFrom} vía syncVersioningConfigToRegistry. Es el lugar natural donde persistir el nuevo bloque declarativo.

hook + flow n8n (lo que se retira)

El arreglo actual: el resolver activity.versioning-hook.resolver.js (mutación GraphQL) + un flow n8n (versioning-remap.json) que escucha el evento :create y llama a esa mutación. Funcionan en par.

Cómo funciona el versionado HOY

El flujo de abajo muestra el camino actual cuando se versiona una Activity. Mira las dos mitades: la izquierda (motor genérico, in-process) ya remapea dueño + self-ref y publica un evento con el _cloneMap adjunto. La derecha (arreglo por-módulo, asíncrono) es lo que este ticket absorbe al motor: hoy un flow n8n filtra el evento y llama a una mutación GraphQL que remapea las FK de los links.

El remap actual vs. el bloque declarativo propuesto

Arriba, el núcleo del hook por-módulo (activity.versioning-hook.resolver.js:52-76): por cada link resuelve los ids nuevos y, si alguna FK cae fuera del cloneMap (un link cross-owner), hace skip + warn en vez de crear un link huérfano — esa defensa existe porque no hay constraint de FK en la DB. Abajo, la forma declarativa que reemplazaría esas 93 líneas: el objeto solo declara qué hijo derivado tiene qué FK y a qué tipo apunta. 

// HOY — lógica imperativa por-módulo (curriculum-design)
for (const link of sourceLinks) {
  const newSourceId = resolveNewId(link.sourceSectionId);
  const newTargetId = resolveNewId(link.targetSectionId);
  if (!newSourceId || !newTargetId) {       // FK fuera del cloneMap (cross-owner)
    console.warn('[versioning-hook] link fuera del cloneMap → skip');
    skipped += 1; continue;            // defensivo: no crear huérfano
  }
  await prisma.curricularLink.create({ data: { sourceSectionId: newSourceId, targetSectionId: newTargetId, ... } });
}

// PROPUESTO — declarativo en metadata del objeto (genérico)
"polymorphicChildrenDerived": [
  { "object": "CurricularLink", "via": "sourceSectionId,targetSectionId", "remapTo": "sections" }
]

Pregunta abierta a explorar en design (H4)

Hay una decisión arquitectónica que el intake dejó deliberadamente abierta y que design-feature debe cerrar al inicio de la session del motor: ¿dónde corre la fase derived? Las dos lecturas de abajo no son un veredicto cerrado — son el trade-off que aún se evalúa. El dato técnico que inclina la balanza ya está confirmado: el cloneMap ya está en scope dentro de finalizeCreate, justo después de clonar.

A · Síncrono in-engine

La fase derived corre dentro de finalizeCreate, reusando el cloneMap ya disponible.

+ Elimina la dependencia n8n + GraphQL por-mod; sin lag eventual; transaccional.

− Toca el motor core (mayor superficie de regresión a cubrir con tests).

B · Hook genérico asíncrono

Conservar el patrón evento → consumer, pero genérico (un solo flow para todos los objetos, dirigido por la config).

+ Cambio acotado al motor; mantiene el desacople por eventos.

− Mantiene la infra n8n + GraphQL y el lag eventual; más piezas móviles que migrar.

Restricciones del entorno

⚠ Multi-repo — object-manager y mods/curriculum-design son submódulos git distintos. La migración (declarar el bloque + retirar hook/flow) toca ambos: los commits se reparten por repo.
✗ Rama protegida — al arrancar execute, el repo de código está en develop (protegida) con working tree sucio. Antes de tocar código hay que pasar a la rama de ticket UPONE-1206 (guarda de inicio DET-30); no se toca el estado sucio preexistente.
ℹ RULE-platform-007 — el codegen consume las relaciones FK en lowercase sin el sufijo Id (accessor Prisma). La fase derived opera sobre el campo escalar sourceSectionId directo (como el hook), no sobre el accessor — sin impacto si se respeta el escalar.

¿De qué se trata el caso?
El motor de versionado clona hijos polimórficos y remapea dueño + self-ref, pero no las FK entre hijos (ej. un link que referencia dos secciones clonadas). Hoy eso lo arregla un hook + flow por-módulo. El ticket lo generaliza a una capacidad declarativa del motor.
¿Qué se va a hacer y por qué importa?
Añadir un bloque declarativo polymorphicChildrenDerived (persistido por el codegen) + una fase derived genérica en el motor que remapea las FK vía cloneMap, y retirar el hook + flow de curriculum-design. Importa porque elimina deuda por-mod y cualquier objeto futuro obtiene el remap sin código a medida.
¿Qué hipótesis quedó abierta y cuál es la más crítica de verificar primero?
H4: si la fase derived corre síncrona in-engine (recomendación del intake, reusando el cloneMap en scope) o se mantiene asíncrona vía un hook genérico. Es lo primero a cerrar en S3 porque condiciona si la migración (S4) retira o conserva el flow n8n.
¿Qué se confirmó en el intake que cambia el approach?
Que el cloneMap ya está en scope dentro de finalizeCreate justo tras clonar (habilita el camino síncrono), que versioningConfig ya existe como punto de persistencia (no hace falta columna nueva), y que buildRemapAPI ya expone todo lo necesario (no hay que ampliar la API del map).
