Evolución de hipótesis

El intake abrio con 2 hipotesis, ambas se asumieron confirmadas. Ninguna se refuto en execute; la segunda (H2, RBAC) era la critica a verificar empiricamente y se confirmo con matices.

H1 — walk simple basta (sin CTE) ✓ confirmada

El walk en memoria (atras + BFS adelante) resolvio el linaje sin necesidad de CTE recursivo. Validado para linajes chicos (H1 / DEC-LOCAL-02). El guard de ciclo via Set resulto necesario y se probo con datos ciclicos.

H2 — RBAC con el patron existente ✓ confirmada (con matiz)

Se uso withObjectAuth('view') (gate por tipo) + getBusinessContextFilter (recorte por fila, como listInstances). Matiz que emergio: getVersionChain queda "en el medio" — getInstance no filtra por fila, listInstances si; se eligio el de listInstances por devolver coleccion.

Decisiones clave

Cuatro decisiones de fondo (todas en Decisions del spec). La dominante es el tipo de retorno: condiciona el contrato GraphQL que consumira la UI.

El corazón del resolver

El walk bidireccional con guard de ciclo + la query final que combina RBAC y orden. Nota el patron de resolucion del accesor de Prisma (PascalCase→camelCase) que se adopto de createInstance tras descubrir que getInstance minusculiza sin fallback (L1).

// walk atras hasta la raiz + BFS adelante, guard de ciclo via Set
const ids = new Set([start.id]);
let cursor = start;
while (cursor && cursor[linkageField] != null) {
  const prev = await model.findUnique({ where: { id: cursor[linkageField] } });
  if (!prev || ids.has(prev.id)) break;
  ids.add(prev.id); cursor = prev;
}
// ... BFS adelante por hijos ...
// RBAC por fila + orden en una sola query
const businessFilter = await getBusinessContextFilter(user, objectType, prisma, selectedRole);
const where = { id: { in: [...ids] } };
if (Object.keys(businessFilter).length) where.AND = [businessFilter];
const visible = await model.findMany({ where, orderBy: { [versionField]: 'asc' } });

La semántica que hay que recordar

isLatest y versionNumber se computan sobre el set visible tras RBAC, no sobre el linaje físico.
Corolario: si el rol no puede ver la cabeza real del linaje, isLatest marca la cabeza visible. Es intencional (DEC-LOCAL-03 + Risks del spec), alineado al pseudo-codigo del diseño. Un consumidor que necesite la cabeza absoluta no debe inferirla de getVersionChain bajo un rol restringido.

Lessons learned

Lo mas reutilizable del caso. La primera conecta con la evolucion de H2 (RBAC): el patron de acceso a modelos no es uniforme en el modulo, y eso impacta cualquier resolver generico nuevo.

Acceso a modelos no es uniforme (L1)

getInstance minusculiza sin fallback; createInstance prueba PascalCase→camelCase. El client real expone PascalCase. Para un resolver generico nuevo, usar el patron robusto de createInstance.

Tests con storage mockeado pueden ser tautologicos (L2)

Un override de findMany que aplica el recorte en el test no prueba que el resolver construya el where. Asercion directa sobre los args de la llamada real cierra el hueco.

Separar gate-por-tipo de filtro-por-fila (L3)

El unit del resolver cubre el recorte por fila; el gate por tipo (withObjectAuth) es responsabilidad del modulo auth y se testea alli. No duplicar.

¿Por qué esas decisiones y no otras?
Tipo de retorno nuevo (VersionChainItem) para no contaminar InstanceResult compartido. Walk en memoria (no CTE) porque los linajes son chicos (H1). RBAC por fila con getBusinessContextFilter porque la query devuelve coleccion (como listInstances), no una sola instancia. versionNumber posicional siguiendo el pseudo-codigo del diseño.
