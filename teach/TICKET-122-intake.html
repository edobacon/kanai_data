Teach intake · TICKET-122 · Bulk delete no debe contar la proyeccion RT propia up1 · 2026-08-07

El borrado en bloque cuenta la proyeccion RT del propio objeto como referencia externa

Este es el frente backend del bug de hard-delete UPONE-1557, en el core object-manager. Al intentar borrar en bloque (deleteBulkInstances) filas de un objeto base que tiene extensiones RecordType, la operacion se rechaza con CONSTRAINT_VIOLATION aunque no exista ninguna referencia externa real. El motivo: la validacion previa de referencias cuenta las tablas de proyeccion del propio objeto (rt__<Rt>__<base>, unidas por la FK <base>Id) como si fueran referencias entrantes de otro objeto. El borrado individual (deleteInstance) ya lo resuelve bien; el objetivo de este ticket es llevar el bulk a paridad con el singular, con una exclusion quirurgica y verificada contra base de datos real.

TL;DR — validateBulkDelete corre ANTES de la limpieza de proyecciones y trata la FK <base>Id de las tablas rt__*__<base> del propio objeto como referencia externa, asi que el id nunca llega al codigo que ya sabe borrar esas capas. El fix (Opcion A) agrega esas proyecciones propias a la lista de exclusion de discoverFKRelationshipsFromPrisma, anclado en la introspeccion real de la FK (resolveRtProjectionFks), no en un patron de string rt__. El caso es traicionero por un falso verde de tests: el unico test que cubre el escenario esquiva el bug por casing de la FK. Por eso el orden es tests-first y la verificacion es integracion contra BD real.

Conceptos base

Cinco piezas del motor de borrado de object-manager sostienen el caso. Sin ellas, el fix parece "agregar un if" cuando en realidad toca la frontera entre dos motores de deteccion de referencias que hoy no coinciden.

Proyeccion RecordType (rt__)

Tabla rt__<Rt>__<base> que es una capa del MISMO registro logico que la fila base, no un objeto externo. Se une a la base por la FK de convencion <base>Id (ej. availabilityId). Ejemplos: rt__InstructorAvailability__availability, rt__StudentAvailability__availability.

validateBulkDelete

Gate previo del borrado en bloque (referenceValidationService.js). Usa discoverFKRelationshipsFromPrisma con cache de FK para buscar quien referencia al objeto. Es rapido, pero su lista de exclusion no cubre las proyecciones rt__ propias: ahi nace el bug.

resolveRtProjectionFks

Helper de instance.resolver.js que introspecta la FK real de cada proyeccion del objeto (por casing verdadero, no adivinando ${base}Id). Ya se usa en el loop de borrado para limpiar las capas rt__. Es la fuente de verdad para la exclusion del fix.

deleteImpactPreview (el motor)

El OTRO motor (deleteImpactPlan.js): construye el plan de impacto para el preview. Excluye BIEN las proyecciones propias (por eso el preview reporta restrictions: []). Tiene semantica completa pero sin cache. La divergencia preview↔ejecucion es el problema de fondo.

CONSTRAINT_VIOLATION vs DELETE_RESTRICTED

Dos codigos de bloqueo distintos: CONSTRAINT_VIOLATION lo emite validateBulkDelete (path generico, objetos sin hijos); DELETE_RESTRICTED lo emite el motor de cascada (objetos con hijos). Todos los tests de RESTRICT existentes usan el segundo camino, por eso el primero quedo sin cobertura.

Como recorre hoy un borrado bulk de un base con proyeccion RT

El diagrama sigue el camino de deleteBulkInstances('Availability', ids). El punto critico es el rombo del centro (validateBulkDelete): hoy encuentra la FK availabilityId de las tablas rt__*__availability del propio objeto, las cuenta como referencia externa, y manda TODOS los ids a blockedResults. Por eso nunca llegan al ultimo nodo, que es precisamente el que ya sabe limpiar esas capas (resolveRtProjectionFks + deleteMany).

Dos cosas se desprenden del mapa. Primero: la ironia es que el codigo que arreglaria el borrado (nodo F) YA existe y funciona en el path singular; el bug es solo que el gate del nodo C corre antes y no deja pasar el id. Segundo: el fix NO agrega logica de borrado nueva, solo corrige el criterio de exclusion del nodo C para que la proyeccion propia deje de contar como referencia.

Invariante que el fix restaura

Una proyeccion rt__*__base es una capa del mismo registro, no una referencia externa. El borrado bulk debe comportarse como el singular.
Corolario: la evidencia de correctitud no es teorica — deleteInstance (singular) ya borra estos objetos en produccion sin contar la proyeccion como referencia. El fix solo alinea dos caminos que deberian coincidir; no es un cambio especulativo.

Dos motores de deteccion de referencias que no coinciden

El sistema tiene DOS implementaciones de "quien referencia a este objeto", por diseno: el preview usa el motor completo (sin cache); la ejecucion bulk usa validateBulkDelete (con cache de FK, para escalar en borrados masivos). Por eso el preview dice cascade y el borrado real falla. La fila destacada es donde vive el defecto de este ticket.

El defecto, en codigo

En discoverFKRelationshipsFromPrisma (referenceValidationService.js:75-89) la lista de exclusion cubre el propio objeto, las tablas ext__ y las core_, pero NO las proyecciones rt__ del objeto que se borra. El fix (Opcion A) agrega esa exclusion, anclada en el set exacto que devuelve resolveRtProjectionFks. 

// referenceValidationService.js:75-89 (exclusion HOY — incompleta)
if (modelName === selfModel) continue;        // self
if (modelName.startsWith('ext__')) continue;   // extensiones
if (modelName.startsWith('core_')) continue;   // core
// FALTA: las proyecciones rt__*__base del propio objeto

// despues (Opcion A): excluir las proyecciones propias por introspeccion real
const ownProjectionFks = resolveRtProjectionFks(prisma, selfModel); // {model, fkColumn}[]
if (ownProjectionFks.some(p => p.model === modelName)) continue;

Opcion A (elegida) frente a Opcion B (descartada)

La decision critica del intake fue el enfoque del fix. "Mayor" no es "mejor": B parece mas consistente (una sola deteccion) pero pierde donde importa.

A — exclusion quirurgica (elegida)

Excluir las proyecciones RT propias en validateBulkDelete, por introspeccion de la FK real.

+ Mantiene el cache FK (no degrada el bulk masivo)

+ Blast radius minimo, reversible, casing-agnostico

+ Solo lleva el bulk a paridad con el singular ya probado

− No cierra la divergencia amplia preview↔ejecucion (queda como B' follow-up)

B — apuntar el bulk al motor del preview

Reemplazar validateBulkDelete por el motor del preview en el path de ejecucion.

− Regresion de performance en el caso que disparo el bug (bulk ~31k, sin cache)

− Cambia la semantica de bloqueo para muchos objetos a la vez

− Riesgoso (~3-5 dias); contradice la decision de diseno de deleteImpactPlan.js:706-707

Malla de seguridad y restricciones

✗ El falso verde de tests — Existe un test del caso "base sin hijos + proyeccion RT en bulk" (OrgUnit, hard-delete-cascade.integration.test.js:740) y pasa. Pero pasa por coincidencia de casing: su FK OrgUnitId (mayuscula) esquiva el scan que arma orgUnitId (minuscula) — Prisma lanza "unknown field", el catch lo traga y el modelo se salta. El unico casing que rompe (minuscula, la convencion, como availabilityId) es el que ningun test ejercita.
⚠ Que NO se puede romper con la Opcion A — La exclusion debe ser quirurgica: (1) una FK externa real debe seguir bloqueando; (2) un custom field de tipo reference debe seguir bloqueando; (3) no sobre-excluir: solo la rt__ del objeto que se borra, NO una rt__ de OTRO objeto que legitimamente lo referencia. De ahi la insistencia en anclar en resolveRtProjectionFks (introspeccion) y no en un patron de string rt__ suelto.
ℹ Verificacion contra BD real (no unit mockeado) — El defecto vive en la introspeccion de modelos Prisma reales + casing de columnas. Un unit con Prisma mockeado puede volver a consagrar el bug (el mock no reproduce el casing ni el fallo silencioso del select). El guard autoritativo es integracion contra el tenant real (UPU); el unit directo es complemento barato, no reemplazo. Reglas del ticket: DET-7 (regression obligatoria), DET-13 (cierre por evidencia), DET-33 (verificar el self-report), DET-40 (auditoria de reemplazo: enumerar 1:1 lo que hace el path viejo y que el nuevo lo replique).

Preguntas de estudio

Por que el preview dice "cascade / sin restricciones" y el borrado real falla?
Porque son dos motores distintos. El preview corre el motor completo (deleteImpactPlan.js), que excluye bien las proyecciones propias. El borrado bulk usa validateBulkDelete, que no las excluye. La divergencia es por diseno (el bulk conserva un cache de FK para escalar), y el que esta mal es validateBulkDelete, no el preview.
Si el path generico ya sabe limpiar las capas rt__, por que el bulk falla?
Porque validateBulkDelete corre ANTES de esa limpieza. Cuenta la FK de la proyeccion propia como referencia externa y manda el id a blockedResults, asi que el id nunca llega al loop de borrado (linea 6049) que ya sabe borrar la capa rt__ y luego la base. El singular no tiene ese pre-gate, por eso funciona.
Por que anclar la exclusion en resolveRtProjectionFks y no en el prefijo "rt__"?
Para no sobre-excluir. Una tabla rt__ de OTRO objeto podria referenciar legitimamente al base que se borra, y ese bloqueo debe sobrevivir. resolveRtProjectionFks devuelve el set exacto de proyecciones del PROPIO objeto por introspeccion de la FK real, cubriendo ademas cualquier casing (minuscula o capitalizada). Un match por string rt__ suelto excluiria de mas.
Por que el orden es tests-first y no "arreglar y despues testear"?
Porque validateBulkDelete no tiene tests directos y protege bloqueos legitimos (FK externa real, custom fields) que deben sobrevivir. Primero se ponen en VERDE, sobre el codigo actual, los tests de la malla de seguridad (bloqueo por FK externa real, precision del match, single sin regresion); recien despues se escribe el test ROJO que reproduce el bug (FK de proyeccion minuscula). El fix se implementa sobre una malla ya verde, no a ciegas.
