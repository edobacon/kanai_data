Cómo leer este teach: cuenta el caso ya resuelto. Si solo lees el TL;DR y "La historia / variaciones del plan", tienes el núcleo — porque la lección principal de este ticket NO fue el código, sino cómo un blocker descubierto en ejecución reescribió el plan dos veces.

TL;DR

El "Sílabo" se entregó como el mismo Offering de engagement, anclado a una asignatura (Activity{recordType: Course}) + su período (termId) + un discriminador recordType propio. Vista completa (lista filtrada, detalle, crear, editar) en Curriculum Design. El giro: el plan original (derivar el tipo de Activity, sin tocar el Offering) chocó con un límite del frontend (la lista no podía filtrar a 2 saltos), se difirió, se evaluaron 3 opciones, y se resolvió reintroduciendo recordType en el Offering desde CD — el mismo patrón que CD ya usaba para Activity.

1. ¿Qué se hizo? (estado final)

  • Modelo: el Offering compartido ganó termId (FK→Term, nullable) y recordType (enum [ServiceOffer, Syllabus], not_null, static_default ServiceOffer), ambos aportados por curriculum-design/objects/Offering.json (deep-merge del sync, sin tocar archivos de engagement).
  • Backend: createSyllabusOffering (valida Course, unicidad scoped, setea recordType: Syllabus) + query syllabusOfferings (where 2-hop, queda como API programática).
  • Vista: 4 layouts del sílabo — lista (filtro recordType=Syllabus), detalle, crear (picker de asignatura Course + período), editar; registrados en el nav vía app.json.defaultObjects. + filtro recordType=Course en la lista de Activity de CD (cerró un leak preexistente de 15 Activities de engagement).
  • i18n + seed: lang es/en/pt (status + recordType); seed idempotente (Activity Course + ActivityLine + 2 Terms + 3 sílabos).
  • Verificado: sync+db push backfill-safe (30 ServiceOffer + 3 Syllabus, sin data-loss); vitest 8/8; regresión engagement OK; smoke UI autenticado (Playwright) de lista/detalle/crear/editar + Activity.

2. ¿Por qué así? (lectura post-hoc)

Por qué mirarla: la solución final NO fue la del plan. Entender por qué es la lección reutilizable para cualquier objeto compartido entre mods.

El "tipo" de una oferta vive conceptualmente en su Activity (Course/Service), a 2 saltos del Offering. El plan original (Opción B / DEC-LOCAL-01) derivaba el tipo de ahí — limpio en backend. Pero el frontend de listas (RecordList) solo consume listInstances y filtra a 1 salto (learn L6): no podía expresar "offerings cuya Activity es Course". La salida correcta resultó ser la que el codebase ya usaba para Activity: poner el discriminador como campo propio del objeto listado (recordType), declarado desde CD. No es denormalización gratuita — es el patrón idiomático de up1 (CD ya declara Activity.recordType cubriendo Course+Service; engagement lo consume).

6. Lecciones (para tickets futuros)

  • Verificar la capa de consumo del frontend, no solo el backend. El plan de S2 asumió que la lista consumiría una query custom; el blocker L6 solo apareció al mirar RecordList.vue. Para features de UI sobre objetos compartidos, validar cómo el componente obtiene los datos antes de diseñar el backend.
  • El discriminador de tipo va en el objeto que se lista. Patrón idiomático up1 (Activity.recordType). Para filtrar una lista por tipo, el campo debe estar a 1 salto — en el propio objeto.
  • FK display: RecordList resuelve relationDisplayFields por objeto/referencia; RecordDetail por nombre de campo. Declarar ambas claves evita el bug B6 (timestamp en vez del valor).
  • El nav de un app sale de app.json.defaultObjects (no de showInNav), y el orden de tabs es alfabético por nombre de layout (sin campo de orden — B7).
