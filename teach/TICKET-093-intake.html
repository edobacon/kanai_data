Embeber la malla y las líneas de formación dentro del Plan de estudios

En up1 un Currículo (objeto Curriculum, variante Plan) es el contenedor de una malla curricular. En el sprint MC-02 (TICKET-082) se crearon sus dos hijos: las líneas de formación (objeto requirementCategory) y las entradas de la malla (objeto planEntry). El problema que este ticket corrige: esos dos hijos quedaron colgando como objetos sueltos en el menú lateral, desconectados visualmente de su Plan padre. La meta es que se vean dentro del detalle del Plan, como pestañas — exactamente como las secciones de un Programa de asignatura (Activity) se ven dentro del Programa.

TL;DR — Qué hay: planEntry y requirementCategory aparecen como entradas sueltas del menú porque MC-02 les dio layouts default_<Obj>_list top-level. Qué se hará: borrar esos 2 layouts list (los saca del menú) y embeberlos como pestañas dentro de default_Curriculum_view y default_Curriculum_edit, reusando el patrón record-list de default_Activity_view. Por qué: son hijos del Currículo (FK curriculumId/planId) y deben leerse en su contexto, no como objetos de primer nivel. Cambio 100% de capa de layouts: cero backend.

Las bases — el vocabulario del caso

Antes de tocar nada conviene fijar 6 ladrillos. Todo el cambio gira alrededor de cómo un layout de detalle embebe un record-list filtrado por la FK del hijo al padre.

Curriculum (Plan)

Contenedor curricular. La variante Plan tiene semántica temporal (créditos, períodos). Es el padre de la malla.

requirementCategory

"Línea de formación". Agrupa requisitos de créditos. FK curriculumId → Curriculum.

planEntry

Entrada de la malla (asignatura en un período). FK planId → Curriculum, categoryId → línea, activityId → programa.

layout

JSON declarativo en mods/curriculum-design/config/layouts/ que el motor de la suite renderiza. Tipos: _list, _view, _edit, _create.

record-list embebido

Campo de tipo record-list dentro del schema de un layout de detalle, con filters por {{parentId}}. Es lo que dibuja la pestaña con la lista del hijo.

directChildren

Metadata del objeto padre. Solo la lee el backend (deepClone/versioning), no el motor de layouts — clave para este caso (ver más abajo).

Cómo encaja — el patrón de embedding que ya existe al lado

No inventamos nada: el hermano Activity (Programa de asignatura) ya embebe 7 listas de CurricularSection como pestañas en su default_Activity_view. El diagrama muestra el mecanismo: el layout de detalle del padre declara tabs, y cada pestaña apunta a un campo record-list del schema que filtra los hijos por la FK. Copiamos ese patrón al Currículo.

La decisión que define el alcance: ¿qué hace que el hijo aparezca como pestaña?

El request original sugería declarar metadata.directChildren en Curriculum.json. Antes de hacerlo verificamos con un grep quién consume esa metadata. El resultado cambia el approach: el embedding lo hace el record-list del layout, no directChildren. Esto importa porque tocar Curriculum.json sería un cambio de backend (y el request pide cero backend).

record-list en el layout ✓

Campo record-list + filters por {{parentId}} en default_Curriculum_view/_edit.

+ Es lo que el motor de layouts realmente renderiza (probado en Activity).

+ Cero backend: solo archivos de config/layouts/.

metadata.directChildren ✗ (para esto)

Bloque declarativo en Curriculum.json.

− Grep: 0 usos en layout/src y suite/src; solo en object-manager (deepClone/versioning).

− No mueve la aguja del embedding y sí toca backend → fuera de alcance (DET-32 → drop).

Restricciones que enmarcan el trabajo

⚠ Cero backend. Solo se tocan archivos de mods/curriculum-design/config/layouts/. No se modifican objetos, resolvers ni seed. Curriculum.json queda intacto.
ℹ DB-gated. Los layouts viven en la DB del tenant y se aplican con npm run sync. La verificación de código es JSON válido + suite del mod sin regresión; el smoke visual en la suite lo corre el dev tras el sync.
ℹ No se borra todo. Solo los 2 _list de los hijos. default_Curriculum_list se conserva (los currículos SÍ van en el menú) y los _view/_edit/_create de los hijos también (los abre la lista embebida).

Hacia adelante — el plan

Una sola sesión (tier T2, con dual-judge). El orden es: primero sacar del menú, luego embeber en las dos vistas de detalle.

S1.T1 — Remover del menú

Borrar default_planEntry_list.json y default_requirementCategory_list.json.

S1.T2 — Embeber pestañas

Agregar tabs (General + Líneas de formación + Malla curricular) con record-lists filtradas a default_Curriculum_view y default_Curriculum_edit.

S1.GATE — Validar

JSON válido + suite del mod sin regresión + dual-judge APPROVED. Smoke runtime DB-gated diferido al dev.

Q&A de estudio

¿Por qué los dos objetos aparecían en el menú?
Porque MC-02 les creó layouts default_<Obj>_list top-level. En este mod, un objeto con un layout _list registrado se vuelve una entrada del menú de objetos. Al borrar esos 2 layouts, los objetos dejan de listarse — pero siguen existiendo (sus _view/_edit/_create permanecen).
¿Hace falta declarar directChildren en Curriculum.json?
No para el embedding. El grep prueba que directChildren solo lo consume el object-manager (deepClone/versioning), no el motor de layouts ni la suite. El embedding lo logra el campo record-list del layout. Declararlo tocaría backend (contra "cero backend") y expandiría el scope a versioning. Por eso queda fuera (DET-32 → drop), con nota de propagación: si en el futuro se quiere que versionar un Currículo clone sus hijos, eso es trabajo del ticket de versioning.
¿Se pierde la capacidad de crear líneas de formación al sacarlas del menú?
No. La pestaña embebida de "Líneas de formación" conserva las acciones de crear/editar/borrar apuntando a los layouts existentes (_create/_edit/_view). El único matiz: el create abre el layout actual donde curriculumId es un picker required sin prefill automático — el usuario elige el currículo. El prefill desde el padre es un nice-to-have fuera de alcance.
¿Cómo se verifica si los layouts viven en la DB?
A nivel de código: el JSON parsea y la suite del mod (vitest) no regresiona. A nivel runtime: el dev corre npm run sync (aplica los layouts al tenant) y abre el detalle de un Currículo en la suite. Por eso los TC de UI están marcados DB-gated.
