Sanear el seed de progression del Plan (Credits a Sequential)

Este caso corrige un dato invalido en el seed canonico del mod curriculum-design: las 20 filas de tipo Plan en _data-curriculum.js tienen el campo progression con el literal "Credits", valor que no existe en el enum cerrado del modelo (rt__Plan__curriculum.json, que solo admite Sequential o Modular). El efecto se nota por una regla de visibilidad condicional introducida en UPONE-1538 (el Jira padre del caso, el mismo al que este ticket queda atado): el campo totalPeriods solo se muestra cuando progression es Sequential, asi que los 20 planes con el dato invalido pierden ese campo en la UI aunque el dato exista. El fix es puramente de datos, sin cambio de codigo ni de esquema, y se aplica reescribiendo la fuente del seed para que el proximo re-seed alinee la base de datos.

TL;DR — El seed trae progression: "Credits" en 20 filas de Plan, un valor invalido para el enum del modelo. La correccion univoca es Sequential: los 20 planes tienen forma secuencial (definen totalPeriods + periodType: "Semester") y el default del modelo ya es Sequential. Se corrige en la fuente y se propaga con un re-seed; ningun consumer del mod hace switch sobre "Credits", asi que no hay riesgo de romper logica existente. El plan de sessions es de 1 sola session (T1).

Conceptos base

Cuatro piezas del dominio sostienen este caso. Sin ellas, el fix parece "cambiar un texto" cuando en realidad toca la integridad de un modelo cerrado y el mecanismo que lo repuebla en cada sync.

Enum cerrado

Campo cuyo modelo de objetos (JSON en objects/RecordTypes/) declara una lista fija de valores permitidos. Cualquier valor fuera de esa lista es dato invalido para el modelo, aunque la base de datos lo acepte como texto libre (no hay constraint SQL que lo bloquee).

RecordType (RT)

Variante especializada de un objeto base, nombrada rt__<base>. Aqui, rt__Plan__curriculum.json es el RT que define progression como enum ["Sequential","Modular"] con default Sequential.

Seed idempotente-restaurador

Seed que, en cada corrida de la fase seed de npm run sync, busca cada fila por su clave de negocio (aqui institutionId + code) y la reescribe al estado que define el archivo fuente, revirtiendo cualquier edicion manual hecha directo en la base.

Regla de visibilidad condicional

Patron de layout donde un campo se muestra u oculta segun el valor de otro campo del mismo registro. UPONE-1538 la aplico a totalPeriods, visible solo cuando progression == "Sequential".

Como llega el dato hasta la UI hoy

El diagrama sigue el mismo camino que toma cualquier valor de progression, desde el archivo fuente hasta la decision de mostrar u ocultar totalPeriods. El punto critico es el rombo del centro: hoy evalua "Credits" en 20 planes, y como "Credits" nunca es igual a "Sequential", esos planes caen siempre por la rama de "oculto", sin importar que totalPeriods tenga un valor real cargado. 

flowchart LR
  A["_data-curriculum.js (fuente)"] --> B["fase seed de npm run sync"]
  B --> C[("rt__Plan__curriculum (DB)")]
  C --> D{"progression == Sequential ?"}
  D -- "si" --> E["totalPeriods visible en la UI"]

Dos cosas se desprenden de este mapa. Primero, corregir solo el nodo C (la base) no alcanza: el proximo paso por B lo vuelve a sobrescribir con lo que diga A. Segundo, el nodo D es codigo que ya existe y no se toca en este ticket, la unica pieza a corregir es el dato que entra por A.

La condicion exacta de UPONE-1538

totalPeriods es visible en la UI SI Y SOLO SI:
(a) el Plan tiene progression === "Sequential"

Invariante del modelo

progression solo admite Sequential o Modular. No hay un tercer valor.
Corolario: un dato fuera del enum, como "Credits", no rompe ninguna query (nada en el mod hace switch sobre ese literal), pero rompe silenciosamente cualquier regla de UI que compare contra los valores validos del enum, como paso con UPONE-1538.

El cambio en la fuente

20 filas identicas en su estructura, todas con el mismo literal equivocado. El cambio es mecanico: reemplazar el valor del enum, sin tocar totalPeriods, periodType ni ningun otro campo de la fila. 

// mods/curriculum-design/seed/_data-curriculum.js:29-48 (antes, x20 filas)
{ recordType: 'Plan', code: 'PLAN-XXX', plan: {
  progression: "Credits", // valor fuera del enum
  totalPeriods: 10, periodType: "Semester"
}}

// despues
{ recordType: 'Plan', code: 'PLAN-XXX', plan: {
  progression: "Sequential",
  totalPeriods: 10, periodType: "Semester"
}}

Por que no se agrego un tercer valor de enum

El literal "Credits" podria delatar la intencion original de una tercera modalidad ("por creditos"), distinta de Sequential y Modular. Esa lectura se evaluo y se descarto durante el intake: el modelo actual solo admite dos valores, y los 20 planes del seed calzan exactamente con la forma de Sequential (definen totalPeriods + periodType). La tabla resume por que Sequential es la opcion de este ticket y agregar un tercer valor queda fuera de alcance.

Preguntas de estudio

Por que no alcanza con corregir directamente la fila en la base de datos de UPU?
Porque el seed es idempotente-restaurador por (institutionId, code) (ver glosario arriba): en cada fase seed de npm run sync vuelve a escribir el estado canonico definido en _data-curriculum.js. Si el dato invalido sigue en el archivo, el proximo sync lo repone. La correccion tiene que vivir en la fuente, no en la base.
El re-seed va a revertir cambios manuales del smoke de TICKET-119. Es una regresion?
No. Los planes Biologia 2026 y Ciencia de Datos 2026 se setearon a mano solo para probar la regla de UPONE-1538 durante ese smoke, antes de que existiera este fix. El re-seed los devuelve al estado canonico (Sequential), que es exactamente el comportamiento esperado de un seed restaurador y ya quedo documentado en la seccion Regression del ticket.
Hay algun consumer del mod que dependa del valor invalido "Credits"?
No. La unica aparicion de "Credits" como valor de progression en todo mods/curriculum-design son las 20 filas del propio seed. Ningun resolver, componente ni condicion de layout hace un switch sobre ese literal, asi que corregir el dato es autosuficiente: no hace falta tocar codigo.
