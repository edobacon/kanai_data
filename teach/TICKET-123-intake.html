Teach intake · TICKET-123 · Un bloqueo legitimo de delete debe ser aviso, no error de carga up1 · 2026-08-07

Un rechazo de dominio en el borrado se muestra como pantalla de error de carga en vez de un aviso

Este es el frente frontend del bug de hard-delete UPONE-1557, en el core layout-engine (RecordList). Cuando un borrado gobernado (customDeleteMutation) es rechazado por el servidor con un error de dominio legitimo (por ejemplo, un esquema de niveles que una matriz esta usando), la lista entera se reemplaza por la pantalla roja de error de carga con un texto generico ("Ocurrio un error inesperado"). El mensaje util del backend ("inactivalo en su lugar") nunca se ve, y el usuario pierde la vista. El path de rowAction type: mutation ya lo hace bien (toast, vista intacta); el objetivo es llevar el custom delete a esa paridad.

TL;DR — El catch del custom delete escribe el error en error.value, el MISMO ref que gobierna el <ErrorState> full-view de CARGA de la lista. Ademas useFriendlyErrors no reconoce el mensaje del backend (cae al generico). El fix (Opcion A1) cambia SOLO la rama customMutation del catch: mostrar el mensaje del servidor como toast (showWarning) sin tocar error.value — espejando useRowMutation, que ya funciona. El bloqueo del backend es correcto; lo unico roto es como se muestra. Como es UI, el cierre exige verificacion runtime real (DET-36), no solo unit de componente.

Conceptos base

Cinco piezas del render de errores de RecordList sostienen el caso. La clave es entender que hay UN solo ref de error (error.value) que hoy sirve para dos cosas distintas (carga de la lista y resultado del borrado), y ahi nace el bug visible.

customDeleteMutation

Config de layout que reemplaza el borrado estandar por una mutation GraphQL gobernada por el mod (ej. deleteLevelSchemeValidated). Su resolver puede rechazar por dominio (ej. "esquema en uso"). Aplica a todo consumer: levelScheme, coverageScheme, objectDefinition, etc.

error.value / <ErrorState>

El ref reactivo que gobierna el <ErrorState> full-view de la lista (RecordList.vue:60, v-if="error"). Esta pensado para fallos de CARGA (fetch/filtro). Si se le escribe cualquier cosa, la lista entera se reemplaza por la pantalla de error.

useFriendlyErrors

Composable que traduce errores a texto amigable matcheando por TEXTO contra ~40 patrones (en ingles). Si nada matchea, cae a DEFAULT_ERROR ("Ocurrio un error inesperado"). No tiene patron para el mensaje personalizado del backend en español.

useRowMutation (el oraculo)

Composable de las rowActions type: mutation. En useRowMutation.ts:151 muestra el error como toast sin tocar la vista. Es el comportamiento CORRECTO de referencia: el fix lleva el custom delete a esta paridad.

personalisedError (backend)

Helper del mod que lanza un Error plano con .code custom. Apollo NO promueve ese .code a extensions.code: lo serializa como INTERNAL_SERVER_ERROR. Al front solo le llega el .message en español (que igual es user-ready).

Las tres capas encadenadas del sintoma

El diagrama sigue un borrado de LS-100 (un esquema en uso). El nodo rojo es el fix: el catch escribe en el ref de carga y nuke la vista.

Segundo: la eleccion es entre las dos ramas del nodo D; el fix solo cambia esa rama para que el resultado sea el nodo F (paridad con useRowMutation), sin tocar el path de carga real de la lista.

Invariante que el fix restaura

El <ErrorState> full-view es para fallos de CARGA de la lista. El resultado de una accion (borrar) se comunica con un toast, sin destruir la vista.
Corolario: escribir el error de un borrado en error.value confunde dos dominios distintos (carga vs accion). El path de rowAction mutation ya respeta este invariante; el custom delete lo viola por reusar el ref equivocado.

El defecto, en codigo

En handleCriticalDeleteConfirm (RecordList.vue:6416), el catch de la rama customMutation escribe en error.value. El fix A1 usa un toast (como useRowMutation) y deja error.value intacto. 

// RecordList.vue:6416 — rama customMutation del catch (HOY)
} catch (err) {
  error.value = 'Error deleting record: ' + err.message; // nuke la vista full-view
}

// despues (A1): toast passthrough, sin tocar el ref de carga
} catch (err) {
  showWarning(err.message); // msg del backend, user-ready; lista intacta
}

Opcion A1 (elegida) frente a Opcion A2 (descartada)

La decision critica del intake fue el enfoque. A2 (implementar la convencion _PERSONALISED_ERROR end-to-end) parece "el fix mayor", pero NO es un cambio de front puro y su blast radius es enorme.

A1 — toast en la rama custom delete (elegida)

Mostrar el mensaje del backend como toast en el catch de customMutation, sin tocar error.value.

+ Blast radius minimo (una funcion); no toca useFriendlyErrors ni el backend

+ Aplica a TODOS los consumers de customDeleteMutation, sin trabajo per-objeto

+ Paridad con useRowMutation (ya funciona); reversible

− Acopla el toast al texto es del backend (aceptable: el mensaje esta diseñado para mostrarse)

A2 — convencion _PERSONALISED_ERROR end-to-end

Que useFriendlyErrors reconozca el error personalizado y haga passthrough en toda la plataforma.

− NO es cambio de front: el code se pierde en extensions; requiere cambiar el backend de cada mod

− Toca un composable compartido (~40 patrones) + backend transversal; riesgo de regresion amplio

− Esfuerzo alto (5+ SP); queda como A2' follow-up de deuda tecnica

Malla de seguridad y restricciones

⚠ Cambio quirurgico sobre la rama customMutation del catch — Debe sobrevivir intacto: (1) el error de CARGA sigue mostrando el <ErrorState> full-view (el path de error.value para fetch/filtro NO se toca); (2) el custom delete exitoso sigue con toast de exito + fetchData(true); (3) el bulk delete conserva su modal bulkDeleteErrors; (4) otros consumers de customDeleteMutation (ej. deleteObjectDefinition) siguen operando, ahora con toast.
ℹ El bloqueo del backend es correcto — no se toca — El guard R9 (assertSchemeNotInUse) rechaza el hard-delete de una escala en uso por una matriz. Es comportamiento de dominio esperado. Una escala LIBRE se borra sin problema. El defecto 2.2 (el code se pierde en extensions) es transversal pero NO se aborda aqui: A1 no lo necesita porque el .message ya es user-ready. Cerrarlo entero es A2' (follow-up).
✗ Verificacion runtime real, no solo unit (DET-36) — Como es UI config-driven / DB-gated, el cierre exige evidencia runtime: OM + suite + tenant UPU sembrado (con la matriz MAT-GEN apuntando a LS-100), borrar LS-100 y ver el toast "...inactivalo..." con la lista intacta. Reglas del ticket: DET-7 (regression), DET-13 (cierre por evidencia), DET-33 (verificar self-report), DET-36 (verificacion runtime/UI).

Preguntas de estudio

Por que un delete fallido reemplaza toda la lista y no muestra un simple aviso?
Porque el catch del custom delete escribe en error.value, que es el mismo ref reactivo que gobierna el <ErrorState> full-view de CARGA (v-if="error", RecordList.vue:60). Ese ref esta pensado para fallos de fetch/filtro; al escribirle el resultado de una accion, la vista entera se monta como error. Ademas el texto pasa por useFriendlyErrors, que no reconoce el mensaje y devuelve el generico.
El bloqueo del backend es un bug que hay que arreglar?
No. El guard R9 rechaza correctamente el hard-delete de un esquema en uso por una matriz; es comportamiento de dominio esperado (una escala libre si se borra). Lo unico roto es COMO se muestra ese rechazo en el front. Separar "que se bloquea" (correcto) de "como se renderiza" (roto) es la clave del caso, igual que en el bug hermano TICKET-122.
Por que A1 y no A2 (la convencion _PERSONALISED_ERROR)?
A2 no es un cambio de front puro: el code personalizado se pierde en extensions (llega como INTERNAL_SERVER_ERROR), asi que keyear por extensions.code exige cambiar el backend de cada mod. A2 toca un composable compartido por toda la plataforma + backend transversal, con riesgo de regresion sobre ~40 patrones. A1 arregla ambos sintomas visibles con una funcion y aplica a todos los consumers. A2' queda como follow-up de deuda tecnica.
Por que no basta con un unit de componente para cerrar?
Porque el comportamiento es config-driven (layout con customDeleteMutation) y DB-gated (el rechazo "en uso" es una query cross-tabla que solo el backend conoce). Un unit puede afirmar la logica del catch, pero el cierre exige verificacion runtime real (DET-36): levantar OM + suite + tenant UPU sembrado y ver el toast con la lista intacta al borrar LS-100. El unit es guard barato, no reemplazo.
