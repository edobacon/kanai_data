Los dos cambios, en codigo

El mecanismo difiere por la forma del error en cada path: el single recibe un error LANZADO (se clasifica por extensions.code), el bulk recibe un payload con errors[] de type plano (se clasifica con el helper nuevo). El multi-seleccion no necesita clasificar: todos sus errores ya van al modal, asi que basta con no marcar la vista como fallida. 

// S2 — path critico single (rama else / deleteBulkInstances)
const bulkErrors = bulkResult?.data?.deleteBulkInstances?.errors || [];
if (bulkErrors.length > 0) {
  const bulkMessage = bulkErrors.map(e => e.message).join(' ');
  if (isBusinessBulkDeleteError(bulkErrors)) showWarning(bulkMessage); // aviso, lista viva
  else error.value = bulkMessage;                              // no-dominio: full-view legitimo
  return;
}

// S3 — path multi-seleccion (deleteSelectedRows), branch de errores
if (errors.length > 0) {
  bulkDeleteErrors.value = errors;   // el modal ya renderea estos errores por-registro
  // (se elimino: error.value = `${stats.summary}` — solo alimentaba el full-view)
}

El invariante que el fix protege

error.value es solo para fallas que invalidan la pantalla (carga/fetch/filtro, o una excepcion de transporte). Un rechazo de negocio del borrado NUNCA debe escribirlo.
Corolario: cualquier camino que quiera avisar de un rechazo de dominio usa toast o el modal existente; escribir error.value equivale a declarar la vista rota y desmonta el contenido de datos por la cadena v-if="error".

Lecciones para quien retome un caso parecido

Un ref compartido entre "carga" y "accion" es una trampa de render
(de H1 confirmada) El bug no estaba en el manejo del error del borrado, sino en que reusaba error.value, el ref que la plantilla trata como "la pantalla fallo". Antes de rutear un error a un ref existente, preguntar que v-if gobierna ese ref: puede desmontar mucho mas de lo que crees.
Discriminar por lo que el payload ya trae, antes de cambiar el contrato
(de H2 confirmada) El backend ya poblaba type y el frontend ya lo pedia; agregar un code a ValidationError habria sido un cambio de contrato compartido por create/update/bulk de todos los mods. La opcion barata (clasificar en el cliente) resolvio el caso sin blast radius.
El mismo bug puede tener severidad distinta segun el flujo que lo rodea
(de H3 confirmada) En el path single el return deja error.value truthy de forma permanente. En el multi-seleccion un fetchData posterior lo limpia, asi que el full-view es transitorio. La raiz es la misma, pero reconocer el matiz evita sobre-diagnosticar y guia a un fix aun mas chico (quitar una linea).
Cuando el fix es de 1 linea sin seam testeable, la honestidad es documentar el limite
La cobertura del multi-seleccion se apoya en inspeccion estatica + regression + smoke (cuando el entorno lo permita), no en un unit nuevo. Forzar un mount del componente gigante habria sido sobre-ingenieria fragil; se dejo registrado el limite en vez de fabricar un test que no prueba el runtime.
