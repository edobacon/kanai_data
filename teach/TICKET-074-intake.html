Versionar objetos versionables SIN workflow

La plataforma up1 sabe versionar objetos (crear la "v2" de un registro encadenada a su origen). Pero el motor de versionado de core fue escrito asumiendo que todo objeto versionable tiene un workflow (una máquina de estados con FK a WorkflowStatus). Llegó Curriculum —el primer objeto versionable que modela su estado como un enum simple, sin workflow— y al versionarlo el sistema crashea. Este ticket hace opcional esa asunción en una función pura de core, y aprovecha el crash destrabado para observar en profundidad qué más le falta al versionado de curriculum (la pista: su extensión de RecordType).

TL;DR — Qué hay: versionar un Curriculum lanza INTERNAL_SERVER_ERROR porque prepareVersionData (core) asume workflow siempre. Qué se hará: gatear toda la lógica de workflow a needsWorkflow = !!initialStateField (~15 líneas, función pura, backward-compatible con activity) + test unitario. Por qué: versionar objetos de estado-simple es una capacidad legítima de la plataforma (curriculum hoy, academicProgram mañana), no un caso especial. Bonus: una vez sin crash, observar si la v2 arrastra su extensión rt__Plan__curriculum (frente #2, posible backlog de core).

Conceptos clave (las bases)

Antes de tocar nada, estos son los ladrillos del versionado en up1. Los tres primeros son el piso del cambio; los tres últimos son el entorno que rodea al caso y que vamos a observar (no tocar) en este ticket.

Versionado config-driven

Cada objeto declara un bloque versioning en su metadata; el createInstance genérico de core lo interpreta al recibir asNewVersion:true. Origen: SP3 / UPONE-1209.

prepareVersionData

El helper de core (helpers/version-from-source.js) que, antes de escribir, lee el source, valida la política de versionado y arma el payload de la nueva versión (bump de version + linkage + estado inicial). Es donde vive el bug.

Workflow vs enum simple

activity tiene workflow real: FK currentStatusId → WorkflowStatus. Curriculum modela el estado como enum (status ∈ Draft/Active/Archived), sin FK ni relación. Decisión de modelado de UPONE-1268, igual que AcademicProgram.

initialStateField

Campo opcional del versioning que declara DÓNDE (qué FK de estado) escribir el estado inicial del workflow en la nueva versión. activity lo declara (currentStatusId); curriculum NO. Es la señal natural de "este objeto tiene workflow".

Extensión RecordType (rt__)

Fila 1:1 del MISMO registro donde viven los campos específicos del RecordType: rt__Plan__curriculum guarda progression, totalCredits… El create genérico separa base/extensión SOLO si recibe el alias rt__. Es el "frente #2" a observar.

deepClone de hijos

Mecanismo que copia los registros HIJOS (separados) del source a la nueva versión (ej. planEntry, sections). Distinto de la extensión RT (que es 1:1). Ya corre atómico en el path de versión. Lo cablea TICKET-072 para el path de clone.

El flujo: dónde crashea y dónde se arregla

El versionado config-driven funciona: core lee versioning genéricamente. El bloqueo está 100% dentro del cuerpo de prepareVersionData, que incluye relaciones de workflow en el findUnique que Curriculum no tiene. El fix introduce una sola bifurcación (needsWorkflow) y todo lo demás queda igual.

El cambio, en código

Estado actual (asume workflow SIEMPRE) — las 4 líneas que crashean con curriculum: 

// version-from-source.js — HOY
const source = await modelClient.findUnique({
  where: { id: resolvedId },
  include: { currentstatus: true, workflow: true },  // (1) Curriculum no tiene estas relaciones -> Prisma falla
});
if (!source.currentstatus?.allowsVersioning) throw ...;  // (2) asume estado de workflow
if (!source.workflow?.initialStatusId)        throw ...;  // (3) asume workflow con estado inicial
return { ...data, [versionField]: max+1, [linkageField]: source.id,
         [initialStateField]: source.workflow.initialStatusId };  // (4) setea estado de workflow

Propuesto (Alternativa A) — todo lo de workflow gateado a needsWorkflow: 

const needsWorkflow = !!initialStateField;  // unico discriminante
const source = await modelClient.findUnique({
  where: { id: resolvedId },
  include: needsWorkflow ? { currentstatus: true, workflow: true } : undefined,
});
if (needsWorkflow) {
  if (!source.currentstatus?.allowsVersioning) throw ...;
  if (!source.workflow?.initialStatusId)        throw ...;
}
const result = { ...data, [versionField]: max+1, [linkageField]: source.id };
if (needsWorkflow) result[initialStateField] = source.workflow.initialStatusId;
return result;  // curriculum: estado lo resuelve static_default "Draft"

Por qué fix en core (A) y no resolver en el mod (B)

Hubo dos approaches viables (y una tercera descartada: darle workflow a curriculum, que contradiría el modelado de UPONE-1268). Se eligió A. Entender por qué ayuda a no "parchear en el mod" la próxima vez que aparezca un objeto sin workflow.

A — workflow opcional en core (elegida)

Gatear la lógica de workflow a initialStateField en prepareVersionData.

+ Generaliza la plataforma (curriculum, academicProgram, futuros).

+ Backward-compatible: activity intacto.

+ Un solo path de versionado, función pura testeable.

− Es core → rama de épica + review del team (RULE-dev-004).

B — resolver custom en el mod (puente táctico)

Mutation versionCurriculum en el mod que replica el versionado simple y rutea por el create RT-aware.

+ Entra sin tocar core.

+ Resolvería de paso el frente #2 (extensión RT).

− Duplica el walk de linaje de core (deuda).

− Se aparta del patrón único de versionado.

Avisos para quien ejecuta

⚠ Es core, no mod-only — el cambio vive en object-manager. Por RULE-dev-004 / core_work_policy va en la rama de épica UPONE-1261-academic-program (NO develop; el git hook lo rechaza) y mergea a develop gated por review del team up1.
✗ El fix NO cierra "versionar curriculum" — destraba el crash, pero la v2 podría NO arrastrar su extensión rt__Plan__curriculum (progression, totalCredits): el path de versión usa objectType=Curriculum base (no recibe el alias rt__), y con alias el guard de version-from-source.js:40 lo rechaza (path RT no-atómico, TICKET-056). Eso es el frente #2 — pregunta abierta de S2.

Q&A de estudio

¿De qué se trata el caso?
Versionar un Curriculum crashea (INTERNAL_SERVER_ERROR) porque el helper de core prepareVersionData asume que todo objeto versionable tiene workflow, y Curriculum modela su estado como enum simple. Es el primer objeto versionable sin workflow de la plataforma.
¿Qué se va a hacer y por qué importa?
Hacer opcional la lógica de workflow en prepareVersionData gateándola a needsWorkflow = !!initialStateField (~15 líneas, función pura). Importa porque versionar objetos de estado-simple es una capacidad legítima de la plataforma (curriculum hoy, academicProgram mañana), no un parche puntual; y es backward-compatible (activity no cambia).
¿Qué hipótesis quedó abierta y cuál es la más crítica?
H4 (frente #2): la v2 de curriculum probablemente NO arrastra su extensión rt__Plan__curriculum atómicamente en el path asNewVersion. Es la más crítica de verificar en S2 porque determina si "versionar curriculum" queda realmente entregado o si hay que abrir un backlog de core (path RT atómico, TICKET-056).
¿Qué decisión crítica se tomó en el intake y por qué esa?
Alternativa A (fix en core, workflow opcional) sobre B (resolver custom en el mod) y C (darle workflow a curriculum, descartada). A generaliza la plataforma y mantiene un solo path de versionado; B duplicaría el walk de linaje y se apartaría del patrón; C contradice el modelado de UPONE-1268. El costo de A (es core → review del team) se aceptó por su valor estratégico.
