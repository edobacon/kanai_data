Lecciones y evolución de hipótesis

¿Cómo evolucionaron las hipótesis del intake?
Las 7 quedaron confirmadas. H6 (el override de create no rompe otros objetos) se confirmó porque el patrón delegate-to-generic ya estaba probado en update. H7 (constraint de colisión del scanner) emergió en intake y se validó empíricamente: el sync registró los 7 resolvers sin colisión. Ninguna se refutó.
Lección 1 — validación runtime vs backstop de constraint
Workflow.isDefault YA tenía validación runtime en createWorkflowValidated, pero el CRUD generic la bypassa. El índice parcial (I4) es el backstop universal que cubre TODOS los paths. Patrón reutilizable: validación amigable en la mutation validated + constraint/índice como red dura.
Lección 2 — single-source vía paridad testeada cuando el import no es posible
El sync separa los destinos (modsComponents→frontend, logic→backend), así que un import cross-layer rompe el bundle. La "fuente única" se garantizó con un test de paridad que falla si front y back divergen — no con un import compartido.
Lección 3 — al agregar un loader al seed o layouts, actualizar sus tests
La regresión destapó 2 tests stale de TICKET-059: el dispatch test no mockeaba el nuevo loader (corría la fn real contra prisma vacío) y el inventario de layouts tenía el conteo viejo. Al sumar un paso al seed o un layout, actualizar los tests de dispatch/inventario en el mismo cambio.
¿Por qué el enforcement vive en el resolver y no en el contrato MCP?
Porque el resolver está aguas abajo de TODOS los clientes. El contrato MCP solo declara/expone la regla; aunque no esté registrado (B2 diferido), el mod ya rechaza los datos inválidos. Así el mod queda MCP-ready sin depender del repo `mcp`.
