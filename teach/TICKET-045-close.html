HU-11 — cierre: qué se hizo, qué se decidió, qué aprendimos

HU-11 parecía un ticket de configuración pura (~0.5 SP): agregar una pestaña "Versiones" al detalle de un Programa de asignatura. Terminó tocando layout core (rama UPONE-1206 + revisión team) porque la navegación entre versiones destapó dos bugs del motor. Esta nota es para el dev que retoma: el resultado final, las decisiones de scope, y las dos trampas de core que ahora están resueltas pero conviene conocer.

TL;DR — Se entregó la pestaña Versiones en default_Activity_view.json: lista la cadena completa de versiones (filtrada por code), con i18n es/en/pt y la rowAction "Crear nueva versión" (reuso de HU-10). Clickear una versión navega a su ficha completa. Eso último requirió 2 fixes de layout core: (1) RecordListElement ahora rutea la navegación de listas embebidas (antes el evento se tragaba), y (2) un :key en la página de detalle Suite fuerza recarga al cambiar de registro. Validado en vivo con un programa de 3 versiones.

Los 2 bugs de layout core (resueltos)

Bug 1 — la navegación no se disparaba. El request-action: navigate-to-relation de un record-list EMBEBIDO llegaba a RecordListElement.handleAction (puente Vueform) que solo hacía element.fire('action') — un evento Vueform que nadie ruteaba. Fix: handleAction ahora navega vía router en navigate-to-relation (gateado; solo aplica a openMode:route).
Bug 2 — el destino no recargaba. Al navegar entre dos registros del mismo objeto/layout (cambia solo instance_id), Vue reusa el componente; RecordDetail.vue:4567 solo refetchea if (!schema.value) — y como el schema ya existe, no recargaba (vista stale). Fix: :key en el LayoutOrchestrator de la página Suite de detalle → remount + fetch fresco.
Ambos componen: el click ahora dispara la navegación (Bug 1) y el destino recarga los datos de la versión elegida (Bug 2). Validado: estando en v3, clic en v1 → URL cambia + ficha muestra v1 (VERSION 1, v2022-actual, Publicado).

Invariante aprendido

Las listas embebidas en RecordDetail soportan modal nativamente; route requiere cableado de core.
Corolario: si un mod pone openMode:route en una lista embebida, hoy funciona gracias al fix de RecordListElement; antes se tragaba silenciosamente. Para record-DETAIL embebidos el gap sigue (mismo patrón, ver RecordDetailElement.vue:69).

Lecciones para el próximo

El discovery de S1 sobre-simplificó. "Filtrar por linkageField" era impreciso (es un puntero, no clave de grupo) y "autor/fecha" no eran satisfacibles config-only. Verificar a nivel campo/schema antes de prometer columnas.
Un ticket "config-only" puede escalar a core. La UX de navegación destapó deuda del motor. Validar en vivo TEMPRANO (no solo por code-trace) cuando hay interacción de usuario.
Fix de bajo blast radius preferido. Se eligió `:key` en la página + gate en `handleAction` (aditivo, opt-in por openMode) sobre tocar el guard compartido de RecordDetail (app-wide). El reviewer aislado confirmó scope/rama.

Q&A de estudio

¿Por qué la tab Versiones filtra por code y no por previousVersionId?
code es estable entre versiones del mismo programa; un filtro EQUALS devuelve la cadena completa. previousVersionId es un FK reflexivo al anterior (linked-list) → un EQUALS solo daría el sucesor inmediato.
¿Qué pasaba al clickear una versión antes del fix?
Nada visible: en route el evento se tragaba en el puente Vueform (Bug 1); aunque navegara, el destino no recargaba por el guard !schema.value (Bug 2). Por eso "no resultaba".
¿Por qué no se usó modal, que ya funcionaba?
El dev pidió explícitamente la vista completa del activity (página), como abrirlo normalmente — no un overlay. Eso obligó a arreglar el route en core.
¿Qué quedó fuera (backlog)?
B-1 badge/highlight; B-3 editar inline (override read-only embebido, core); B-5 columna Fecha (createdAt no expuesto como columna de lista); B-6 onBeforeRouteLeave (guard de ediciones sin guardar, gap pre-existente).
