Cómo un custom Vueform element recibe (de verdad) su valor cargado

El cierre de este ticket vale más por cómo se resolvió que por el diff. La hipótesis del intake (onMounted re-read) era razonable y estaba equivocada. Tres intentos fallidos después, el fix real fue una línea conceptual: declarar y leer la prop default. Esto es la base para todo futuro custom element de este tipo.

TL;DR — Qué se entregó: los pickers hidratan al editar y se muestran read-only (chip/glifo) al ver; las líneas de formación abren en modal y sin botón eliminar. El fix clave: Vueform entrega el valor persistido del registro a un custom element por props.default, NO por element.value ni el proxy element.el$.value. El read-only en view exige disabled:true explícito en el layout (Vueform no lo deriva de mode:"view"). Meta-lección: el wiring de un custom Vueform element NO lo atrapa el unit test → solo el smoke runtime.

El rastro de hipótesis (y por qué cada una cayó)

Cada intento pasaba vitest (875 tests) y el dual-judge, pero fallaba en el smoke. El motivo: los tests prueban helpers puros con objetos planos, nunca el element real de Vueform. La verdad de terreno solo apareció en el browser.

La pista decisiva fue la asimetría: en r1 el view ya era read-only (isDisabled se resolvía) pero el valor seguía vacío. Si el disabled llegaba y el value no, el value venía por otra vía. Esa vía era props.default — el mismo patrón que usa EnumValuesEditorElement (initEntries(props.default)), el único custom element writable que ya hidrataba en el codebase.

El fix real

Hidratación = props.default — declarar default: { type: String, default: '' } en props y leerlo como fuente primaria: readValue = () => (props.default || readLoadedValue(proxy())), usado en el init del ref local Y como getter de un watch(..., { immediate:true }).
Read-only en view = disabled:true en el layout — Vueform deriva element.isDisabled solo del disabled del field (o validación), no de mode:"view". Sin el disabled:true en default_requirementCategory_view.json, el field queda editable en la vista. Con él, el mismo componente cae al branch isReadonly (chip/glifo + role=img/aria-label, alineado con min-height: var(--vf-min-height)).
Extra de UX — las líneas de formación ahora abren en modal (openMode:"modal") y sin eliminar (canDelete:false) en los embeds requirementCategoriesList de Curriculum view+edit. Y el ícono guardado fuera del set curado se prepone como primer elemento y queda seleccionado.

Q&A de estudio

¿Por qué element.value no sirve para leer el valor cargado en setup?
En el 2º arg de setup, context.element es el retorno de GenericElement.setup: un objeto de Refs/computed SIN unwrap. element.value es el objeto Ref (identidad estable), no el string; un watch(() => element.value) observa esa identidad y nunca dispara. Vueform inyecta el valor del registro por la prop default, que sí está disponible y es reactiva.
¿Por qué el dual-judge y vitest no atraparon que estaba roto?
Los tests del mod ejercen los helpers puros (readLoadedValue, resolveDisabled) con objetos planos que simulan el element — nunca montan el SFC ni el element real de Vueform. El dual-judge revisa código, no runtime. El comportamiento de carga del modal solo existe en el browser con datos → por eso el smoke DB-gated es la aceptación central, y los TC de hidratación/render se marcan smoke + Affects UI.
¿Por qué el view mostraba la grilla editable aunque era "ver"?
Porque se asumió que element.isDisabled era true en mode:"view". Vueform NO lo deriva del mode (su computed solo mira el disabled del schema o la validación). El fix: disabled:true explícito por field en el layout view.
¿Quedó código de los intentos fallidos?
Sí, como fallback defensivo y testeado: resolveElementProxy/unwrapMaybeRef alimentan la rama secundaria de readValue (props.default || readLoadedValue(proxy())) y resolveDisabled(proxy()). No es ruido: props.default es la vía primaria, el resto es red de seguridad. Candidato a simplificación futura si se confirma que props.default es universal.
