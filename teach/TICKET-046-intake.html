Documentar como adoptar clonar/versionar — sin leer el core

Durante todo el sprint SP3 (epica UPONE-1206) se construyo, ladrillo a ladrillo, la capacidad de clonar y versionar objetos en uP1. Once historias (HU-1 a HU-11) entregaron el motor: el primitivo de clonado, la capa de versionamiento, la persistencia de config, las row actions. Este ticket no entrega codigo nuevo — entrega la documentacion que permite que un dev de cualquier mod active esa capacidad para su propio objeto sin tener que leer el codigo del core. El entregable mas concreto es un "test de adopcion simulada": una receta paso a paso que un dev externo pueda seguir en menos de 30 / 60 minutos.

TL;DR — Que hay: el motor de clonar/versionar ya esta entregado (HU-1..HU-11, todas cerradas). Dos docs ya existen (prefill-capability.md, versioning-capability.md parcial) y una tercera de codegen (codegen-polymorphic-children.md). Que se hara: expandir versioning-capability.md al runtime + receta, crear config-storage.md, polymorphic-children.md (adopcion) y layout/docs/row-actions.md, extender PATTERNS.md con el ejemplo Activity end-to-end, y escribir el test de adopcion simulada con sus trampas. Por que: sin esta guia, adoptar la capacidad obliga a leer ~6 helpers del resolver y el codegen. El objetivo de negocio (HU-12) es que la capacidad sea auto-servicio para otros mods.

Las bases: los 4 ladrillos de la capacidad

Para documentar la capacidad hay que entenderla primero. Se construyo como 4 "ladrillos" apilados: cada uno se apoya en el anterior. Un ladrillo aqui es una pieza funcional minima entregada por una HU (historia de usuario). El primero es transversal (sirve a cualquier objeto); los siguientes agregan la semantica de versionamiento. Las cuatro tarjetas de abajo son ese stack, de base a cima:

Ladrillo 1 — prefillFrom (HU-1/HU-2)

Clonacion declarativa: pre-llenar una instancia nueva con los campos de otra (source). Sin linaje, sin bump. Es el primitivo transversal — cualquier objeto lo puede usar. Gated por source: si nadie pide clonar, no se activa.

Ladrillo 2 — asNewVersion (HU-3/HU-4)

Versionamiento sobre el prefill: ademas de clonar, hace bump del versionField, setea el linkageField (FK reflexivo al source) y resetea al estado inicial del workflow. Requiere prefillFrom.source.

Ladrillo 3 — getVersionChain (HU-5)

Query que reconstruye el linaje completo de versiones desde cualquier instancia (backward por linkageField + forward BFS), ordenado por version. Es como se lee la "historia" de un objeto versionado.

Ladrillo 4 — row action type:create (HU-7)

Primitivo declarativo de layout: un boton en la lista/detalle que dispara createInstance con prefillFrom+asNewVersion. Su visibilidad se gobierna por visibilityConditions sobre relaciones hidratadas.

Piezas de soporte alrededor del stack: config-storage (HU-0j) persiste la config declarativa del JSON a la columna core_ObjectDefinition.versioningConfig para que el runtime no re-lea el JSON; polymorphicChildren (HU-0d) permite que el clonado arrastre hijos polimorficos (ej. las secciones de una Activity).

El invariante que organiza el diseño

Si el dev se lleva una sola idea del intake, que sea esta. Toda la documentacion se ordena alrededor de una linea divisoria entre mecanica (el como se versiona) y politica (el quien puede y desde donde). Confundirlas es la fuente #1 de errores de adopcion:

La mecanica vive en metadata.versioning del JSON del objeto. La politica vive en la DB: WorkflowStatus.allowsVersioning (flag por estado) + Workflow.initialStatusId (FK del estado inicial).
Corolario: declarar politica (allowedFromStates, initialStateValue) dentro de versioning NO es error — genera un warning de codegen y se ignora. Y al reves: declarar la mecanica perfecta pero olvidar setear initialStatusId en el seed hace fallar el versionado en runtime con WORKFLOW_HAS_NO_INITIAL_STATUS.

Como funciona hoy: del JSON al runtime

El flujo abajo muestra el viaje de la config: el dev la declara una vez en el JSON, el codegen la valida en build-time y la persiste al registry, y el resolver la consume en cada createInstance. Mirar primero el nodo codegen (es donde fallan las adopciones mal declaradas) y el nodo resolver (donde se decide si clonar, versionar o nada).

Versionar vs Clonar — la distincion que el ticket exige documentar

El criterio de aceptacion pide una seccion "Versionar vs Clonar". No son lo mismo y la confusion lleva a adoptar mal. Las dos caras: clonar es transversal (cualquier mod, sin semantica de dominio); versionar es del dominio CD (agrega linaje, numeracion y reset de estado).

Clonar (transversal)

Pre-llenar una instancia nueva desde otra. Usa solo prefillFrom.

+ Sirve a cualquier objeto, sin tocar workflow ni estados.

+ Puede arrastrar hijos (deepClone).

− Sin linaje, sin numero de version, sin reset de estado. El clon es independiente.

Versionar (dominio CD)

Clonar + linaje. Usa prefillFrom + asNewVersion.

+ Encadena versiones (linkageField), numera (versionField), resetea al estado inicial.

− Exige politica en la DB: allowsVersioning en el estado + initialStatusId en el workflow.

− Falla con error explicito si la politica no esta seteada (es una feature, no un bug).

El shape declarativo (lo que el dev escribe una vez)

Para aterrizar las bases, asi se ve la declaracion real en el JSON de un objeto adoptado (Activity). Todo lo demas (codegen, persistencia, runtime) es automatico a partir de esto. Notar que versioning y prefillFrom viven bajo metadata — fuera de ahi el sync los descarta en silencio (trampa conocida #2). 

// objects/activity.json (extracto)
"metadata": {
  "versioning": {
    "linkageField": "previousVersionId",  // FK reflexivo al source
    "versionField": "version",            // Int auto-incremental
    "versionStrategy": "increment"         // unica estrategia en SP3
  },
  "prefillFrom": {
    "exclude": ["currentStatusId", "previousVersionId", "versionLabel"],
    "deepClone": ["sections"]                // arrastra hijos polimorficos
  },
  "polymorphicChildren": [{ "name": "sections", "object": "CurricularSection", /* ... */ }]
}

Q&A de estudio — ¿entendiste el caso?

¿De que se trata el caso?
De documentar (no implementar) la capacidad de clonar/versionar objetos que SP3 ya construyo, de modo que un dev de cualquier mod pueda adoptarla para su objeto sin leer el codigo del core. El entregable estrella es un test de adopcion simulada: una receta seguible en <30/<60 min.
¿Que se va a hacer a alto nivel y por que importa?
Escribir/expandir ~5 docs (versioning, config-storage, polymorphic-children, row-actions, PATTERNS) + un test de adopcion. Importa porque el objetivo de negocio de HU-12 es que la capacidad sea auto-servicio: sin docs, adoptarla obliga a leer 6+ helpers y el codegen, lo que la hace inaccesible para otros mods.
¿Que preguntas quedaron abiertas y cual es la mas critica?
La mas critica (resuelta ya en el intake): el test de adopcion no puede correr en vivo porque Syllabus/CompetencyMap/CurriculumPlan no existen como objetos y no hay directChildren de ejemplo en el mod CD. Decision: el test es un walkthrough verificado contra el codigo, usando un ejemplo generico (Invoice/LineItem) para camino A y Activity real para camino B.
¿Que decisiones criticas se tomaron en el intake?
(1) Fusionar S3+S4 del plan original en un unico test simulado con gate auto (no ⚑ fuerte en vivo). (2) polymorphic-children.md sera adopcion-focused y cross-linkeara a la codegen-polymorphic-children.md existente en vez de duplicar. (3) Reflejar que el hook de remap de derived children dejo de ser per-mod: se generalizo al core (applyDerivedRemap + polymorphicChildrenDerived, TICKET-049) — la nota "derived generico → SP4" del ticket quedo obsoleta.
