HU-9 · Campo versionSourceId en changeLog

El mod curriculum-design tiene un audit log inmutable que registra cada cambio sobre objetos auditables (Activity y sus hijos). Este caso agrega trazabilidad de linaje de versionamiento: saber de que objeto se versiono un Activity cuando se crea por clonacion. La parte interesante no es el campo (es trivial), sino por que se hace con un campo nuevo y no tocando lo que ya existe — y ese "por que" vive en un contrato cerrado en produccion que conviene entender antes de tocar nada.

TL;DR (autopilot super)

¿Que hay? Un audit log (changeLog.json + el resolver recordAuditEvent) con enums fijos (action 7 valores, source 6) y el patron L40 (sourceRefId/Name/Type). Ese contrato quedo cerrado verbatim en UPONE-1098 — tocarlo rompe produccion.

¿Que se hara? Agregar UN campo aditivo nullable versionSourceId: String?. El resolver lo lee de data._versionSourceId, valida que el origen exista y sea del mismo entityType, y lo persiste. Luego codegen → migracion additive → sync. Dos sessions: S1 implementa todo, S2 cierra.

¿Por que? Para auditar el origen de un versionamiento. El Jira original lo pedia metiendo Clone al enum y renombrando sourceRefId — rechazado (rompe el contrato). Distinguir un Create-de-version se hace via versionSourceId != null.

▼ Las bases — sobre que nos paramos

Conceptos clave del audit log

Cuatro terminos que vas a encontrar en el spec y el codigo. Si los entendes, el resto del cambio es mecanico.

changeLog (audit log)

Log inmutable, append-only de cambios sobre objetos auditables (Activity, CurricularSection, CurricularLink). Su unico escritor es el resolver recordAuditEvent, invocado por un workflow n8n. No expone update/delete publicos.

Patron L40 — sourceRefId/Name/Type

Cuando se edita un hijo polimorfico de Activity (Modalidad, Sesion, etc.), el row se consolida al Activity padre y el hijo que cambio queda referenciado en la tripleta sourceRef*. Es trazabilidad del hijo dentro de una edicion.

Campos meta del payload (prefijo _)

El resolver recibe en input.data campos internos con prefijo _ (_sourceRefId, _changeRequestId, _source) que son instrucciones de auditoria, NO campos del modelo. El prefijo _ ademas los excluye del diff. _versionSourceId sigue esa convencion.

codegen → migracion → sync

El flujo canonico de UP1 para cambios de modelo: changeLog.json (fuente de verdad) → npm run codegen (genera Prisma + GraphQL) → prisma migrate → npm run sync (propaga a core). Sin atajos quirurgicos (ALTER TABLE manual prohibido).

Como funciona el audit log HOY

Una mutation sobre un objeto auditable termina, varios saltos despues, en una fila del changeLog. El campo nuevo se suma al final de esta cadena, sin alterarla.

flowchart LR
  A[createActivity / updateActivity] --> B[decorator withEventPublish]
  B --> C[(Redis Pub/Sub)]
  C --> D[n8n audit-capture]
  D --> E[recordAuditEvent]
  E --> F[(changeLog rows)]

sourceRefId (existe) vs versionSourceId (nuevo)

La trampa de este ticket es confundir los dos campos. Resuelven cosas distintas y NO deben colisionar. Esta es la distincion que evita el error mas probable.

sourceRefId (patron L40, ya en produccion)

Referencia al hijo polimorfico que cambio dentro de una edicion consolidada al Activity padre.

+ Trazabilidad intra-edicion (que Modalidad/Sesion cambio).

− Contrato cerrado en UPONE-1098 — no se toca.

versionSourceId (nuevo, este ticket)

ID del objeto origen de un versionamiento completo (de que Activity se clono este).

+ Trazabilidad de linaje. Distingue Create-de-version via != null.

− Solo se pobla en el Create derivado (null el resto).

Autoevaluacion

¿Por que no agregar simplemente Clone al enum action?
Porque el enum action (7 valores) es contrato verbatim de UPONE-1098 (AC2). Cambiarlo invalida un cierre formal y obliga a migrar datos historicos. Un Create-de-version se distingue por versionSourceId != null, no por un valor de enum nuevo.
¿Cual es la diferencia entre sourceRefId y versionSourceId?
sourceRefId (L40) referencia al hijo polimorfico que cambio dentro de una edicion consolidada al Activity padre. versionSourceId referencia al objeto origen de un versionamiento completo. Conceptos distintos — por eso campo nuevo y no reuso.
¿De donde lee el resolver el valor del campo?
De input.data._versionSourceId — convencion de campos meta del payload con prefijo _ (igual que _sourceRefId). No requiere cambio del schema GraphQL porque data es JSON arbitrario.
¿Que pasa si el origen referenciado no existe?
El resolver devuelve un error no-fatal AUDIT_INVALID_VERSION_SOURCE en errors[] (sin throw, patron append-only) y NO persiste la fila. n8n decide retry/dead-letter. Si el entityType no es mapeable a un accessor Prisma, se persiste sin validar (degradacion grafil).
