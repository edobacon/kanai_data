Malla — Agregar y editar asignaturas (obligatorias + electivas)

MC-06 fue el feature frontend más grande del Sprint 6: modales de alta y edición sobre la malla curricular, con dos flujos diferenciados (obligatoria y electiva) y un sistema de tagging de bloques requirement-Group. Este documento cuenta qué se hizo en cada session, cómo evolucionaron las hipótesis abiertas del intake, qué decisiones se tomaron en ejecución y qué aprendieron el equipo y el proceso automático.

TL;DR — 5 sessions, 23 archivos, +4 639 líneas, 1 040 tests verdes, 15 commits locales. El flujo Must (obligatorias) quedó completo en S2; las electivas y la edición en S3-S5. El dual-judge (DET-35) capturó dos bugs críticos que los tests unitarios no veían: objectType incorrecto al crear un bloque (S4) y 5 errores de tipo en el modal de edición (S5). Tres ítems de backlog quedan abiertos (B1/B2/B3, todos Should/Could).

Lessons learned

Lo mas valioso para el dev que trabaje sobre este modulo o el platform en el futuro.

¿Por que createInstance de un RecordType necesita el objectType completo y no el nombre base?

El platform usa el objectType para resolver el archivo de schema del RecordType (patron rt__{RT}__{base}, ej. rt__Group__requirement). Con ese archivo crea la fila completa del RT incluyendo los campos especificos del subtipo (combinator, minToSatisfy). Si pasas solo el nombre base ('requirement'), el platform resuelve el schema base y no sabe de esos campos especificos: el create falla silenciosamente o crea una fila incompleta.

Asimetria importante: listInstances si acepta el nombre base mas un filtro recordType=Group. Create y list usan convenciones distintas.

Donde lo atrapo DKC: S4, dual-judge. El Juez B reporto FAIL en F1; el Juez A reporto PASS. El orquestador resolvio el tie-break contrastando con el spec (Technical reference L474) y el schema real. Los 999 tests unitarios no lo veian porque solo testean los builders de payloads, no el createInstance real.

¿Por que los tests en verde no son suficiente para un gate de session que toca UI?

Vitest corre con esbuild, que transpila TypeScript sin realizar typechecking. Eso significa que errores de tipo (tipo incorrecto en prop, Pick con campos inexistentes, size invalido) pasan sin error en tiempo de transpilacion y los tests siguen verdes.

En S5, el orquestador corrio vue-tsc como parte del DET-33 (verificacion del self-report) y encontro 5 errores que el dev no habia ejecutado: size='xs' invalido en el Modal, y 4 mismatches de Pick<MeshEntry,...> con campos inexistentes.

Practica recomendada: ejecutar vue-tsc --noEmit (o equivalente del proyecto) en el gate de toda session que produzca componentes Vue, ademas del vitest run habitual.

¿Como extraer la logica de un SFC a un archivo .ts puro para poder testearla en env node?

El vitest del mod curriculum-design corre en environment: 'node' sin @vitejs/plugin-vue (los SFC estan aliasados a stubs). Eso significa que no puedes importar ni montar un .vue directamente en el test.

El patron del mod es: extraer toda la logica (calculos, validators, derivaciones) a un archivo *.logic.ts que solo importa tipos y utilidades (sin Vue). El SFC importa desde ese archivo y aplica la logica a sus refs. Los tests (*.logic.spec.ts) importan directamente el .ts sin necesidad de montar el componente.

Cuidado: en S2 el SFC de AddEntryModal reimplemento la logica inline sin usar el addEntryModal.logic.ts recien creado. El dual-judge lo detecto como dead code. Siempre verificar que el SFC importa y usa el modulo .ts externo.

¿Por que create:true de Vueform es seguro dentro del modal casero?

BUG-platform-011 indica que el ModalStackManager de Vueform no se expone al contexto de los mods. La preocupacion era que create:true invocara ese manager al crear una nueva opcion.

El spike de S3.T1 leyo el source de Vueform (@vueform/multiselect/.../useOptions.js:110-111) y verifico que createdOption es un computed local del multiselect y que handleTag solo dispara el event bus interno de Vueform. El ModalStackManager no esta involucrado.

La story SpikeS3T1SelectSuggestElectiva en CurriculumMesh.stories.ts sirve como evidencia reproducible de que el flujo create funciona en el modal casero.

¿Que campos son obligatorios al crear un bloque requirement(Group) para un curriculum?

Segun el schema dynamic.js:764-781 + :2133-2152 y el precedente en seed/_data-requirement.js:115, los campos requeridos son:

  • objectType: 'rt__Group__requirement' (NO 'requirement')
  • ownerType: 'curriculum'
  • ownerId: planId
  • parentId: null
  • recordType: 'Group'
  • effect: 'ProgressGate' (requerido, precedente en MC-03)
  • combinator: 'OR'
  • minToSatisfy (auto-derivado del conteo de cursos)
  • isHardRule: false
  • label (nombre del bloque electivo)

Para listar bloques existentes se usa listInstances(name:'requirement', filters:[{recordType EQUALS 'Group'}, {ownerType EQUALS 'curriculum'}, {ownerId EQUALS planId}]). Notar que combinator y minToSatisfy no se usan como filtros EQUALS porque son campos del blob data, no del schema base.

¿Como maneja el seam la logica de Rol Obligatoria ↔ Electiva en la edicion?

La regla central es: isElective = blockId != null (evaluado por el read enrichment del backend en curriculum-read.resolver.js:185-225). El modal de edicion no guarda un campo "tipo" separado: solo gestiona blockId.

La logica pura (applyRoleChange en curriculumMesh.logic.ts) implementa:

  • Rol → Electiva: setea blockId al bloque seleccionado
  • Rol → Obligatoria: limpia blockId (null)
  • Cambiar categoria (categoryId): no toca blockId — electividad y categoria son ortogonales

El adapter (CurriculumMeshElement.vue) ejecuta updateInstance(objectType:'planEntry', id, data:payload) — objectType base (sin rt__) porque planEntry no es un RecordType.

Pendiente (backlog abierto)

B1 (Should) — Precarga visual de cursos del bloque existente
Al elegir un bloque existente, el picker deberia preseleccionar los cursos que ya contiene (REQ-07 parcial). Requiere un query adicional de planEntries del bloque y una prop preselectedIds en ActivityPicker. La exclusion de duplicados de S2 ya evita problemas de datos; es solo UX.
B3 (Should) — Fidelidad del campo creditos en edicion
El modal de edicion abre con el credito efectivo resuelto (nunca null) en vez del override crudo. Un entry sin override muestra los creditos heredados como si fueran un override explicitamente seteado. Sin corrupcion de datos (patch parcial correcto), solo UX confuso. Requiere plumbing de planEntry.credits raw hasta MeshCard.
B2 (Could) — Rollback de bloque huerfano en error parcial
Si se crea el requirement Group pero falla el tag de alguna planEntry, el bloque queda sin entries. GraphQL del platform no provee transacciones cross-mutation; evaluar cleanup explicito o advertencia al usuario.
Tests verdes != integracion correcta. Vitest/esbuild no typechequea y los unit tests solo cubren los builders puros.
Corolario: en todo gate de session que toque UI o que llame a createInstance de un RecordType, correr vue-tsc y contrastar el objectType con el schema real — el dual-judge DET-35 es el seguro de red, pero correr el typechecker al cierre de cada tarea es mas barato.
