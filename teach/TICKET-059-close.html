Lecciones aprendidas

✓ Diff antes de forzar — ante un db push con data-loss, prisma migrate diff separa lo aditivo (tuyo) de lo destructivo (drift ajeno). Aplicar solo lo tuyo evita pérdida de datos y no enmascara el problema sistémico.
⚠ Los artefactos generados del object-manager SÍ se necesitan en runtime — revertirlos para "limpieza" deja al GraphQL sin el tipo y rompe la UI. La fuente canónica es el mod; los generados (dynamic.js, schema, client) deben regenerarse y quedar, no revertirse.
ℹ Restart del backend tras cambios de objeto — el GraphQL (object-manager vía nodemon) necesita recargar typedefs; sin eso el suite reporta "Error al cargar <objeto>" aunque la DB esté correcta. nodemon recarga al tocar src/.
✗ El drift de BASEMODEL persiste para el equipo — no se resolvió de fondo (excede este ticket). Cualquier cambio de schema seguirá chocando con db push hasta regenerar baseline. No usar --accept-data-loss.

Q&A para quien retome o agregue otro objeto

¿Cómo agrego un objeto CRUD-plano nuevo al mod?
Copia el patrón de AcademicProgram/BibliographyReference: objects/<Obj>.json (PascalCase), 4 layouts default_<Obj>_*, lang/es_CL@<Obj>.json, alta en defaultObjects de app.json, y un seed/_data-*.js enganchado en seed.js. Luego sync + restart del backend.
¿Por qué el seed usa FK directo (*Id) y no connect?
Es la convención real del mod (ver _data-univalle.js). Prisma acepta ambas; se siguió la del mod por consistencia. El seed es idempotente: busca por [institutionId, code] antes de crear.
¿Qué falta para una v2?
Relación a workflow (workflowId + currentStatusId), el objeto hijo curriculumPlan + versionado, y el filtro de OrgUnit por recordType en el select (Backlog B1). Todo aditivo sobre esta base.
¿La tabla quedó aplicada de forma "oficial"?
Se aplicó el DDL aditivo directo a UPU (no vía db push completo, que está bloqueado por drift). Cuando el equipo regenere el baseline, el sync normal reconciliará todo; el objeto ya está en la fuente (mod) y en los generados.
