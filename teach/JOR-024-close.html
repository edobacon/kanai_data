Knowledge promovido

Los 5 learns del ticket se consolidaron en una rule nueva — son convenciones del stack, no detalles del caso:

RULE-frontend-002 — Convenciones de autoria de test+story por componente (vitest dual-project + storybook-nextjs-vite). Complementa RULE-frontend-001 (donde van los archivos) diciendo COMO escribirlos.
// los 5 patrones que la rule codifica:
1. radix-portal en test jsdom -> defaultOpen; en story -> play() abre overlay (a11y); contenido en screen, no canvas
2. story con hooks de App Router -> parameters.nextjs.appDirectory: true (+ navigation.pathname)
3. mover componente a sub-carpeta -> imports relativos a sibling suben un nivel (./x -> ../x); alias @/ no se afecta
4. story de componente con prop requerida -> args: { children: null } aunque uses render (TS la exige)
5. cache storybook flaky -> rm -rf node_modules/.cache/storybook .vite antes del full vitest run
El refactor mantuvo zero-behavior-change: los 59 tests del baseline siguen verdes, sin reescribir su logica.
Corolario: mover composites con barrel = nombre del componente hace el cambio transparente para los consumidores; relocar tests entre archivos preserva sus aserciones (solo cambia la ruta de import).

Lessons learned (Q&A para el proximo refactor de frontend)

¿Como ordenar un refactor de movimientos masivos?
Por riesgo creciente: primero lo aditivo (agregar tests/stories, riesgo ~0), despues los movimientos (riesgo de imports), cerrando con validacion completa. Cuando llegas a mover, ya tenes la suite verde como red.
¿Como minimizar el riesgo de romper imports al mover a carpeta?
Nombrar la carpeta igual que el componente y poner un index.ts barrel: los imports existentes (`./Breadcrumb`, `@/shell/AppShell`) resuelven a la carpeta sin cambios. Solo los imports relativos a un sibling dentro del componente movido (NavGroup→NavItem) necesitan subir un nivel.
¿Donde testear un componente radix que monta en portal?
El test jsdom con `defaultOpen` valida el contenido montado de forma deterministica; la story (chromium) abre el overlay en `play()` para el escaneo de a11y. La division test/story del stack se aprovecha exactamente para esto.
¿Que valido el reviewer aislado al cierre?
En contexto limpio (sin haber visto la ejecucion): que cada cambio corresponde al spec, que los imports/barrels resuelven, que ningun archivo cae fuera de execute_scope, que no quedan huerfanos, y que el trabajo esta en rama de ticket. Recomendacion: approve.
