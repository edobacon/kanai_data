HU-6 · createdVia en eventos + n8n persiste versionSourceId

Cuando se crea una instancia en object-manager, se publica un evento (BullMQ → n8n) que un flow de auditoria consume para escribir un registro en ChangeLog. HU-6 quiere que ese evento lleve el origen de la creacion — createdVia: "scratch" | "prefill" | "version" — y, cuando es una version, el id del registro del que se versiono (versionSourceId), para trazabilidad. Todo de forma aditiva: sin romper a otros mods ni pisar la consolidacion L40.

TL;DR — Qué hay: el lado de auditoria ya esta cableado por HU-9 (TICKET-035): recordAuditEvent extrae versionSourceId de input.data._versionSourceId, lo valida y lo persiste en ChangeLog; sourceRefId (L40) es ortogonal. Qué se hará: hacer que createInstance emita la metadata — derivar createdVia + _versionSourceId y adjuntarlos al registro devuelto, que fluye al payload del evento via withEventPublish. Por qué importa: el alcance es mas chico de lo que parecia — el flow n8n NO necesita editarse (el campo viaja dentro de data, que el flow ya mapea). Cierra la trazabilidad de origen sin tocar contratos de terceros.

Las bases: conceptos del dominio

Cinco piezas. La clave es entender que el payload del evento transporta el registro creado, y que la auditoria lee metadata con prefijo _ dentro de ese registro.

withEventPublish

Decorador (src/events/decorators/withEventPublish.js) que envuelve mutations. Tras crear, publica al canal BullMQ core:* un payload cuyo data es lo que el resolver devuelve + _triggeredBy. No hay hook de campos extra: lo que el resolver retorna, viaja.

Convencion meta _

Campos de metadata viajan con prefijo guion-bajo dentro del payload (_triggeredBy, _previousData). HU-9 sumo _versionSourceId leido por el audit. HU-6 emite _versionSourceId + _createdVia con la misma convencion.

createdVia

Origen de la creacion: version si asNewVersion===true; prefill si hubo prefillFrom.source sin versionar; scratch si ninguno. Es metadata de trazabilidad en el payload.

versionSourceId vs sourceRefId (L40)

versionSourceId = id del registro del que se versiono (solo cuando version). sourceRefId/Name/Type (L40) = consolidacion de un hijo polimorfico (CurricularSection) a su Activity padre. Ortogonales: HU-6 no debe tocar L40.

Flow audit-capture.json (n8n)

Unico consumer del canal core:*. Filtra por whitelist (Activity|CurricularSection|CurricularLink), hace unwrap del envelope (record = envelope.data.data = el registro creado) y llama recordAuditEvent(input) con data: record. Como _versionSourceId vive dentro de record, llega solo — el JSON del flow NO cambia.

Estado actual: el extractor que HU-9 ya dejó

Este es el codigo del lado consumidor (auditCapture.resolver.js) que define donde debe viajar el campo: dentro de input.data. Por eso HU-6 lo adjunta al registro devuelto por createInstance, no a un nivel superior del payload. 

// auditCapture.resolver.js (HU-9) — ya existe; define el contrato de lectura
function extractVersionSourceId(input) {
  const raw = input?.data?._versionSourceId;   // <-- viaja DENTRO de data
  if (raw == null) return null;
  return String(raw);
}
// luego: valida que el origen exista y persiste ChangeLog.versionSourceId

El invariante que protege la auditoría existente

HU-6 es puramente aditivo: agrega createdVia/versionSourceId al payload y NO toca sourceRefId/Name/Type (L40).
