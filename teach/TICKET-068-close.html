Lessons learned

¿Dónde va el seed de datos de un objeto de un mod en up1?
En mods/<mod>/seed/ (un seed.js entrypoint que importa _data-*.js), que corre durante npm run sync — NO en object-manager/prisma/{tenant}/seed.js (ese es el seed core). Confundirlos infla el scope a object-manager innecesariamente. El primer borrador del spec lo ubicó mal; el dev lo corrigió. (L3)
¿Por qué el GraphQL seguía sirviendo v1 tras el reset, y cómo se arregló?
El server corría bajo nodemon. Un nodemon-reload (incluso con respawn del proceso, PID nuevo) no recargó el schema por-tenant — siguió sirviendo v1 pese a que TODAS las fuentes persistentes (prisma schema, dynamic.js, business/Base, core_ObjectDefinition, core_FieldDefinition, filas DB) eran v2. El fix fue un cold restart real: matar nodemon + el listener, esperar el puerto libre, levantar fresco. Regla: tras reset-tenant/codegen, cold restart del OM, no touch-reload. (L4)
¿Por qué "reformar el objeto" terminó siendo no tocar nada?
La cascada DET-32 (necesidad/reuso) mostró que el v2 + rt__Plan/rt__Minor ya cubrían el scope, y que los campos v1 (publicId/versionCode/isCurrent/careerId/modality) estaban superseded (drop) porque no había data viva que preservar. El Request decía "reformar", pero la respuesta correcta fue confirmar que el canónico ya era el destino. Verdicto: build (seed) / reuse (objeto) / drop (legacy).
¿Por qué owner=AcademicProgram y no Institution?
El borrador asumió que AcademicProgram no estaba seedeado en UPU. Falso: el mod lo siembra (_data-academicprogram.js, ej. UV-ICIV). Para un Plan, AcademicProgram es el owner program-centric correcto (intención v2). El Minor, al ser compartido, cuelga de la Institution. Lección: verificar el seed del mod, no solo la lista de tipos del seed core.
