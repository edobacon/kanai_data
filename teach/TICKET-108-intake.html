Validacion pre-push local obligatoria en curriculum-design

Hoy cualquiera puede pushear directo a develop/master y no hay ninguna revision automatica de calidad antes de subir codigo. Vamos a poner una revision obligatoria previa al push dentro del repo del mod curriculum-design: un git hook pre-push versionado que bloquea el push directo a ramas protegidas y corre lint + typecheck antes de dejarte subir. Este documento te da el piso (como funcionan los git hooks y husky), el entorno (por que "solo local" por ahora y que viene despues) y el plan. No cuenta resultados: eso es del teach-close.

TL;DR — Que hay: cero automatizacion pre-push en el mod. Que se hara: un hook pre-push (husky) que (1) bloquea push a develop/master/main, (2) linta los archivos cambiados y (3) typecheckea el mod completo; auto-instalado al correr npm install. Por que: que todo dev pase por una revision de calidad y el trabajo entre por PR. Etapa 1 = solo local (sin acceso a Bitbucket cloud); el bloqueo no evadible es etapa 2.

Conceptos clave (el piso)

git hook

Script que git ejecuta automaticamente en un evento (commit, push, merge). Vive en .git/hooks, que no se versiona por defecto, asi que un hook "a mano" no se propaga a otros devs.

pre-push

Hook que corre antes de enviar commits al remoto. Git le pasa por stdin las lineas <local_ref> <local_sha> <remote_ref> <remote_sha>: de ahi sabemos a que rama vas a pushear y que rango de commits.

husky

Herramienta que versiona los hooks en el repo (carpeta .husky/) y los auto-instala via el script prepare: al correr npm install, setea core.hooksPath a .husky/_.

core.hooksPath

Config de git que redirige de donde se leen los hooks. husky lo apunta a su carpeta; asi el hook versionado reemplaza al de .git/hooks.

lint / typecheck

El mod ya tiene npm run lint (eslint) y npm run typecheck (vue-tsc). Los binarios estan hoisted en up1/node_modules (por eso los scripts usan ../../node_modules/.bin).

--no-verify

Flag de git push que saltea todos los hooks de cliente. Es la razon por la que un hook local es guia, no seguridad: cualquiera puede evadirlo.

Como decidira el hook (orientacion)

flowchart TB
  A[git push] --> B{ rama destino develop / master / main ? }
  B -- si --> R[Rechaza: usa un PR - exit 1]
  B -- no --> C[Lint de archivos cambiados vs origin]
  C -- error --> R2[Aborta push]
  C -- ok --> D[Typecheck del mod completo]
  D -- error --> R2
  D -- ok --> E[Push procede]

El orden importa: primero la guarda de rama (barata), despues las validaciones pesadas. Si vas a una rama protegida, ni corre lint/typecheck.

El hook que vamos a escribir (esqueleto)

husky v9: el archivo es shell plano. Lee stdin para la rama destino y el rango de diff. Detalle final en el spec (S1.T2).

# .husky/pre-push (etapa 1 local)
PROTECTED="develop master main"
while read -r local_ref local_sha remote_ref remote_sha; do
  target=${remote_ref#refs/heads/}
  for p in $PROTECTED; do
    [ "$target" = "$p" ] && { echo "push directo bloqueado, usa un PR"; block=1; }
  done
  # rango para lint: remote_sha..local_sha (o merge-base con origin/develop si rama nueva)
done
[ "$block" = 1 ] && exit 1
eslint $archivos_cambiados_lintables   # solo lo que cambio
npm run typecheck                       # mod completo

El entorno: por que "solo local" ahora (y que viene despues)

Hay dos capas de enforcement posibles. Esta etapa hace la local; la server queda documentada como follow-up (no tenemos acceso admin a Bitbucket ahora).

Etapa 1 — local (este ticket)

Git hook pre-push versionado + husky, dentro del repo del mod.

+ Feedback inmediato en la maquina del dev, sin infra.

+ Versionado y auto-instalado (se propaga a todos).

− Evadible con --no-verify; solo existe tras el install.

Etapa 2 — server (follow-up)

Bitbucket Branch permissions (PR-only) + Pipelines corriendo lint/typecheck como merge check.

+ No evadible; es la seguridad real.

− Requiere acceso admin a Bitbucket (no lo tenemos hoy).

− Exige desacoplar el mod de ../../node_modules (Pipelines clona solo el mod).

ℹ El mod vive en dos mundos a la vez — curriculum-design es un repo git propio (remote bitbucket.org:uplanner/curriculum-design) y a la vez un workspace de up1. Por eso hereda los binarios de up1/node_modules. Instalar husky en el mod afecta solo el .git del mod, no el repo up1 ni a otros equipos.
⚠ Riesgo a verificar en ejecucion — en monorepos con workspaces, el prepare de un workspace no siempre dispara con un npm install hecho solo en el root. El instalador de up1 corre npm install con cwd dentro del mod (eso si lo dispara), pero hay que confirmarlo empiricamente antes de darlo por hecho.

El limite que no hay que olvidar

Un hook de cliente es una guia, no un candado.
Corolario: git push --no-verify lo saltea, y un clon sin npm install no lo tiene. El "solo por PR" real recien llega con Bitbucket Branch permissions (etapa 2). Presentarlo como seguridad seria falsa sensacion de proteccion.

Q&A de estudio

¿Por que el lint corre solo sobre archivos cambiados pero el typecheck sobre todo el mod?
Decision del dev: el lint acotado hace el push mas rapido y valida el codigo que efectivamente subes. El typecheck (vue-tsc) no tiene un modo por-archivo confiable (el sistema de tipos es global), asi que corre completo.
¿Por que husky y no un hook a mano en .git/hooks?
Porque .git/hooks no se versiona: un hook a mano vive solo en tu maquina y no se propaga a otros devs. husky versiona el hook en el repo y lo auto-instala, que es lo que hace posible el "obligatorio para todo dev".
¿Como sabe el hook a que rama vas a pushear?
Git le pasa por stdin las lineas <local_ref> <local_sha> <remote_ref> <remote_sha>. Del remote_ref se saca el nombre de la rama destino (quitando refs/heads/) y se compara con la lista de protegidas.
¿Por que no cerramos el "solo por PR" de verdad en esta etapa?
Porque el bloqueo real (no evadible) se configura en Bitbucket (server-side) y no tenemos acceso admin ahora. Lo local es un recordatorio util pero evadible con --no-verify. La etapa 2 queda documentada como follow-up.
