Borrado por RecordType: como quedo resuelto

Cierre de UPONE-1479. El borrado por el nombre de un RecordType ahora se comporta igual que por el objeto base: cascadea hijos, respeta soft-delete y Restrict, y audita por nodo, en los dos entrypoints. Este documento mira hacia atras: que se hizo, que decisiones se tomaron, como evolucionaron las hipotesis y que lecciones quedaron.

TL;DR — Que se realizo: se resolvio el nombre RT a su base al inicio de deleteInstance y deleteBulkInstances y se retiraron las dos ramas RT paralelas (Opcion B). El camino generico limpia las proyecciones rt__/ext__ resolviendo la FK por introspeccion. Como se valido: 8 red tests RT (bulk+single) rojos->verdes, suite unit completa 110/110 (2395 tests), integration 17/17 contra UPU real. Estado: codigo commiteado en la rama de trabajo; pendiente el gate humano de revision del team core (RULE-dev-004) + merge a develop.

La historia del caso

Cinco momentos. Lo interesante: casi ningun problema lo cazo el fix inicial; cada capa de verificacion (dual-judge, commit del dev, pipeline) destapo algo que la anterior no.

S1 — red tests + fix Opcion B

Se escribieron 8 red tests RT (hard/soft/Restrict/DataLog, bulk+single) que fallaban por los huerfanos; el fix (RT->base + retiro de las ramas RT) los puso verdes.

S1.GATE — el dual-judge caza el evento

Los 15 tests pasaban, pero el review adversarial detecto que el bulk pasaba a emitir el evento delete con el nombre base y el single con el RT. Fix: preservar rawObjectType.

Commit del dev — FK por introspeccion

La limpieza de proyecciones ensamblaba ${base}Id, que falla por casing (OrgUnitId vs availabilityId). Se reemplazo por introspeccion de information_schema + 2 tests OrgUnit.

Re-review — el escape del LIKE roto

El dual-judge del delta vio que LIKE 'rt\_\_%' no filtra (los \ se pierden en el template literal JS). Se cambio a LEFT(table_name,4)='rt__'.

Pipeline — 2 unit obsoletos

La regresion local (5 suites) no incluia recordType.resolver.test.js, que asertaba la rama RT retirada. El pipeline (110 suites) lo cazo; se realinearon al nuevo contrato.

Evolucion de hipotesis y lecciones

Como evolucionaron las hipotesis del intake?
Las 4 (H1 bulk-hard, H2 bulk-soft-latente, H3 single-misma-causa, H4 Opcion-B-viable) se confirmaron contra codigo y se sostuvieron en execute. La unica sorpresa fue un 5to frente que el intake no anticipo: la limpieza de proyecciones por ${base}Id era un bug pre-existente de casing, latente hasta que el red test de RT-sin-hijos (OrgUnit) lo destapo.
Leccion 1 — el RT es un alias, no un tipo con metadata propia
La metadata que gobierna el borrado (hijos, soft-delete) vive en el objeto base. Resolver el alias a base ANTES de leer metadata o aplicar politica. Capturado en RULE-core-043.
Leccion 2 — el casing de la FK de una proyeccion no se infiere del nombre
OrgUnit->OrgUnitId pero Availability->availabilityId. Resolver por introspeccion (information_schema / core_FieldDefinition), nunca por string. Y en $queryRaw, cuidado con LIKE y backslashes en template literals. Capturado en RULE-core-044.
Leccion 3 — al reenrutar una rama, verificar ancho
Auditar TODOS los sinks que leen el input original (eventos, DataLog, decorators que leen args) y correr la suite unit COMPLETA, no solo el area tematica: los tests de estado de BD no cazan divergencias de evento, y unit mockeados en otro archivo consagran los internals retirados. Capturado en RULE-core-045.
Que gate humano queda pendiente?
Revision del team core (RULE-dev-004, porque toca deleteBulkInstances/deleteInstance compartidos) + push + merge a develop. El codigo esta commiteado local en feat/UPONE-1479-recordtype-delete-cascade.

Lo que queda garantizado

Borrar un registro produce el mismo resultado por el nombre base o por el del RecordType, en ambos entrypoints.
El objectType de entrada es un alias de presentacion; nunca cambia la politica de borrado (cascada, Restrict, soft-delete, DataLog) del objeto real.
