Reubicacion del acceso al Catalogo bibliografico

El acceso al catalogo de Referencias bibliograficas dejo de vivir en el menu general del modulo curriculum-design y paso a un boton en la barra del listado de Programas de asignatura, que lo abre en un modal. El cambio fue 100% configuracion de layout del mod (dos archivos JSON, mas un tercero descubierto en runtime) propagada por npm run sync: cero codigo nuevo. Este teach mira hacia atras: como se ejecuto, que hipotesis del intake resulto falsa y por que, que decidio el dev sobre la forma de despliegue, y que aprendizaje quedo promovido a regla.

TL;DR — Se agrego un modalActionButton ("Catalogo bibliografico", gateado por bibliographyreference:view) en default_Activity_list.json y se retiro la entrada del menu. Sorpresa del smoke: quitar el objeto de defaultObjects no oculto la entrada (la hipotesis H2 del intake era falsa); el toggle real fue showInNav: false. Ese aprendizaje quedo como RULE-mods-055. El dev evaluo mostrar el catalogo como ruta full-page, confirmamos que eso requiere cambio en core, y acepto el modal (la ruta quedo como backlog could B1). Como se ejecuto (Session 1, tier T3)

Fue una sola session, pero con un giro en el medio. El orden de acciones importa para entender por que el cambio final tiene tres archivos y no dos:

1 · Config declarativa

Se quito "BibliographyReference" de defaultObjects en config/app.json y se agrego el bloque modalActionButtons + layoutNameMap dentro de layoutConfig de default_Activity_list.json, apuntando a default_BibliographyReference_list como RecordList en modal, con requiredPermission: bibliographyreference:view. Se agrego la key i18n del boton con fallback al label nativo.

2 · Tests + docs, luego sync

Se extendio layouts-declared.test.ts con 5 casos que trazan a REQ-01/02 mas la regresion del RT rt__Bibliography__curricularsection, se revisaron los docs del mod (sin refs stale), y se corrio npm run sync para propagar la config a suite.

3 · Smoke UI y el descubrimiento

Al verificar en runtime (tenant UPU) aparecio el problema: el boton y el modal funcionaban, pero la entrada de "Referencia bibliografica" seguia en el menu pese a haberla quitado de defaultObjects. Se diagnostico en useObjectManager.ts y se corrigio con showInNav: false en el layout del catalogo. Recien ahi el menu quedo limpio.

4 · Gate: iterate y luego continue

El dual-judge aprobo (ambos jueces convergieron). En el gate el dev pidio evaluar mostrar el catalogo como vista en ruta en vez de modal, porque el modal anida sub-modales (view/edit/crear). Se exploro, se confirmo que la ruta requiere cambio en core (no config-only), y el dev acepto el modal para este ticket. La decision continue supersede al iterate transitorio.

5 · Unificacion de copy

El boton decia "Referencias bibliograficas" pero el encabezado interno del listado decia "Catalogo bibliografico". El dev eligio unificar a "Catalogo bibliografico" (label + modalTitle + key i18n es/pt), verificado en runtime. Todo quedo en el commit local f4b37f6.

La hipotesis que el runtime tumbo

Contexto

El intake asumio (H2) que quitar el objeto de defaultObjects lo sacaba del menu, verificado "multi-capa" contra el consumer. Config + BD daban verde.

Decision

No cerrar con config+BD: correr smoke UI real (gate DET-36, T3). El smoke mostro la entrada todavia en el nav.

Resultado

Causa raiz: tras el sync todo layout del mod es explicito (applicationId = app), asi que aparece siempre; defaultObjects solo ordena. El toggle real es showInNav: false.

⚠ Leccion de metodo — una hipotesis "confirmada multi-capa" leyendo codigo estatico igual puede ser falsa. Para UI config-driven, la unica confirmacion valida es el render real. El gate T3 (smoke obligatorio) fue lo que evito cerrar en falso.

Modal vs vista en ruta: por que quedo el modal

Modal (elegido ✓)

El boton abre default_BibliographyReference_list en un modal via modalActionButtons, el mismo patron del precedente engagement_Activity_service_list.

+ 100% config del mod, cero codigo core, reversible.

+ Ya implementado y verificado en runtime.

− El catalogo abre sub-modales (view/edit/crear referencia): el anidamiento se acumula.

Vista en ruta (descartado para este ticket)

El boton navegaria a /{tenant}/{object}/RecordList/{layoutId} como pagina completa, sin anidar modales.

+ Mejor UX cuando el catalogo se opera a fondo.

− modalActionButtons es modal-only por diseno; se necesitaria openMode: 'route' en el tipo core + handler en suite.

− Cruza a core (RULE-dev-004): rama + revision del team. Fuera de un ticket config-only.

El dev priorizo entregar el acceso ya (mod-only, verificado) por sobre la UX ideal. La capacidad boton→ruta quedo capturada como backlog B1 (prioridad could), reusable para todos los mods.

Lo que queda como regla

Para ocultar un layout de mod del nav se usa showInNav: false en su layoutConfig. Quitarlo de defaultObjects solo reordena, no oculta.
Corolario: tras el sync todo layout del mod es explicito para la app, asi que aparece incondicionalmente. Un modal/ruta que abre el layout por layoutId directo sigue funcionando aunque showInNav sea false. Promovido a RULE-mods-055 (must), cross-link a rule-mods-010 y rule-mods-020.

Autoevaluacion

Si otro mod quiere sacar un objeto del menu general, ¿que hago?
Poner showInNav: false en el layoutConfig del default_{Object}_list.json del mod. Quitarlo de defaultObjects es opcional (coherencia semantica), pero por si solo no oculta nada tras el sync. Verificar siempre con smoke, no con BD.
¿Por que este ticket toco 3 archivos si el plan hablaba de 2?
El plan (app.json + default_Activity_list.json) asumia que defaultObjects controlaba la visibilidad. El smoke refuto eso, y aparecio el tercer archivo: default_BibliographyReference_list.json con showInNav: false. Es el failed approach documentado del ticket.
¿Cuando un boton de listado deberia ser modal y cuando ruta?
Hoy, en config-only, solo hay modal (modalActionButtons). Si el layout destino abre sub-modales o se opera a fondo, la ruta es mejor UX, pero requiere el cambio core del backlog B1 (openMode: 'route'). Sin ese cambio, aceptar el modal es lo correcto para no bloquear la entrega.
¿Por que no basto con la revision "multi-capa" del intake?
Porque leer el consumer estaticamente no captura que el sync reescribe applicationId en todos los layouts del mod. La capa que faltaba era la de runtime post-sync. Regla practica: para UI config-driven, el smoke es una capa de verificacion, no un lujo.
