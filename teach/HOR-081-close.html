Teaching v2 — como se construyo (y por que)

TL;DR — Convertimos el teaching de DKC de prosa markdown a HTML didactico self-contained renderizado en un iframe de HC (como los drafts), forward-only: HC detecta el formato por existencia de archivo (teach-{kind}.html ⇒ v2 iframe; si no ⇒ markdown v1 intacto). Libs (Tailwind+Mermaid) servidas localmente desde HC, sin CDN. Este archivo que estas leyendo ES el primer teach v2 de produccion — dogfood del pipeline completo.

Que se hizo

5 sessions cross-repo (deckard + horadric-cube): el template base con catalogo de 14 bloques + una rule del catalogo (S1); vendoring de libs + ruta /vendor + deteccion forward-only en el server (S2); el tab Teaching renderizando el iframe v2 con "Abrir en pestaña" + fallback v1 (S3); el validador HTML-aware + reescritura de los steps teach-intake/close + alineacion de las 5 capas de DET-21/22 (S4); y este dogfood (S5).

El flujo, session por session

No es un indice de las sessions — es la narracion de que se hizo y en que orden, para que entiendas el camino que llevo de "el teaching es tedioso" a "el teaching es un HTML didactico renderizado". Cada session dejo el sistema funcional y se construyo sobre la anterior.

S1 · deckard — el molde y su catalogo

Arrancamos por lo que todo lo demas consume: el template base. Tomamos el draft v2 aprobado y lo convertimos en teach-base.html — un molde con los 14 bloques didacticos, cada uno marcado con data-dkc-block y con un comentario de "cuando usarlo". Las libs se referencian por URL local (placeholder a resolver en S2). Para que el catalogo no se vuelva caos al crecer, escribimos RULE-workflow-teach-html-catalog-010: donde vive el catalogo y la regla de ampliacion forward-only. El reviewer pidio un detalle: borrar las etiquetas de guia (blk-tag) al generar teaches reales — quedo documentado en el instructivo del molde.

S2 · horadric-cube server — servir las libs y detectar el formato

Con el molde listo, el server tenia que (a) entregar las libs sin CDN y (b) decidir que teach mostrar. Agregamos @tailwindcss/browser como dependencia y creamos la ruta /vendor/* que sirve Tailwind y Mermaid desde node_modules (descubrimos que el ESM de Mermaid importa chunks relativos → servimos el subtree completo). Luego enseñamos a teaches.ts a mirar si existe teach-{kind}.html: si esta, devuelve format: html + la URL servida; si no, sigue el camino markdown de siempre. Lo cubrimos con tests (deteccion, precedencia, path-traversal, serving offline): 196 verdes, sin tocar el v1.

S3 · horadric-cube viewer — pintar el iframe

Ya con el server devolviendo format, el tab Teaching tenia que ramificar: si es html, montar un <iframe> (mismo sandbox que los drafts) con un boton "Abrir en pestaña"; si no, el render markdown de siempre. Levantamos el server real y lo miramos en el browser — ahi cazamos que en dev faltaba proxear /vendor en vite (en prod no pasa, el server es uno solo). Con eso resuelto, el smoke confirmo en vivo los 4 casos: el iframe pintando Tailwind+Mermaid offline, el v1 intacto, y "Abrir en pestaña" funcionando.

S4 · deckard workflow — cerrar el contrato

El render ya funcionaba, pero el contrato del workflow seguia hablando de markdown. Hicimos que el validador (dkc-validate Teach) reconozca el HTML — cuenta los data-dkc-block en vez de los fences dkc:*. Reescribimos los steps teach-intake/teach-close para que generen HTML desde el catalogo, y actualizamos DET-21/22 en sus 5 capas. Aca el reviewer aislado fue clave: detecto que 2 de esas capas (el c-validator y los a-hooks) habian quedado apuntando a .md — habrian roto cualquier ticket v2. Las corregimos antes de avanzar.

S5 · dogfood — probarlo con su propia medicina

La mejor prueba de que el pipeline cierra: que este mismo teach-close se generara como v2 real. Lo escribimos eligiendo bloques del catalogo, lo pasamos por el validador nuevo (0 errores) y corrimos la regresion final cross-repo (267 tests, type-check, v1 sin tocar). Si lo estas leyendo en el iframe de HC, el ciclo completo — autorar → detectar → servir → renderizar → validar — funciono de punta a punta.

Lessons learned

¿Por que HTML+iframe y no enriquecer el render Vue?
El dev priorizo libertad de composicion (catalogo ampliable, distinto por caso) sobre integracion. El HTML la da; Vue acotaba a componentes fijos. La objecion CDN se neutralizo sirviendo libs localmente.
¿Que catch dio el smoke visual?
En dev, vite proxea /api pero el iframe pide /vendor relativo → habia que agregar /vendor al proxy. En prod (server unico) no aplica. Solo se vio levantando el server real.
¿Cual fue el valor del reviewer aislado?
Cazo 2 gaps de la capa 5 (c-validator + a-hooks en .md) que el ejecutor no vio. Las capas 1-4 estaban bien; la 5 no. Es el patron que RULE-workflow-det-introduction-001 previene.
