Lecciones y findings

ℹ db push, no migration files — el platform materializa cambios de schema por-tenant con prisma db push via el sync del object-manager, no con migration files. (de H1, al ejecutar S1.T5)
⚠ Entanglement del codegen — npm run sync regenera TODOS los schemas de tenant; los stale arrastran cambios de otros tickets aun no propagados. Para un commit scoped hubo que revertir los schemas entangled y commitear solo los limpios (UPU/BASEMODEL) + el object source + dynamic.js. (de S1.T5 → B2)
⚠ execute_scope subespecificado — el campo listaba solo mods/curriculum-design/, pero la propagacion via codegen toca object-manager (anticipado por la Classification del ticket + REQ-IMPLEMENT-03). Para tickets de mod con cambio de modelo, execute_scope deberia incluir los artefactos generados de object-manager. (finding de cierre)
✗ Blocker preexistente (otro ticket) — el db push falla en varios tenants por Activity.workflowId/currentStatusId required con NULLs existentes (versionamiento de Activity). Mismo origen que la falla de fixtures-vs-seed (activity.version). No es de este ticket → B3. (de S1.T5)

Invariante que queda

Para extender un contrato de auditoria cerrado, agregar un campo aditivo nullable casi siempre gana a mutar un enum o renombrar un campo compartido.
Corolario: la semantica especial (Create-de-version) se expresa con la presencia del campo (!= null), no contaminando un enum que otros consumers ya dependen.
