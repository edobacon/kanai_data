Detalle y clonado de Curriculum no muestran los campos del RecordType

Un plan de estudios (objeto Curriculum de tipo Plan) se crea pidiendo datos extra que el tipo exige —créditos totales, períodos, progresión—, pero al abrir el detalle esos datos no aparecen, y al clonar tampoco se prellenan. El dato sí está guardado; el problema es de lectura. Este teaching te deja parado en el problema antes de diseñar la solución: el piso (cómo modela up1 los campos por tipo), el entorno (qué ya se resolvió y qué queda fuera) y el plan (qué vamos a tocar, mod-only).

TL;DR — Los 4 campos del tipo Plan (progression, totalCredits, totalPeriods, periodType) no son columnas de la tabla base curriculum: viven en una tabla satélite 1:1 llamada rt__Plan__curriculum. El backend solo resuelve esa satélite cuando se le pasa el alias rt__Plan__curriculum; con la base "Curriculum" la ignora. El crear y el editar ya rutean por el alias (resuelto en TICKET-074); falta el leer (detalle, precarga de edit) y el prefill del clon. Lo arreglamos mod-only interceptando dos resolvers de lectura (getInstance, listInstances) en el mod curriculum-design, sin tocar core ni el front.

Las bases — cómo modela up1 los campos por tipo

up1 tiene objetos con RecordType: un mismo objeto base (ej. Curriculum) tiene subtipos (Plan, Minor) que agregan campos propios. Esos campos del subtipo NO viven en la tabla base; viven en una tabla de extensión 1:1 nombrada rt__<Tipo>__<base>. Para un Plan eso es rt__Plan__curriculum, con FK/PK curriculumId y relación curriculum → Curriculum. Hay un tercer tipo de tabla, ext__uplanner__curriculum, que NO es lo mismo: esa guarda custom fields genéricos, no los del RecordType. Confundirlas es el corazón del bug.

RecordType (discriminador)

El campo recordType (enum: Plan/Minor) del registro base dice de qué subtipo es. Es la pista para saber qué extensión cargar.

Alias rt__Plan__curriculum

El "objectType" que activa en el backend el branch que hace el split base/extensión. El front rara vez lo conoce de antemano en lectura.

Extensión vs ext__

rt__Plan__curriculum = campos del tipo (progression, totalCredits…). ext__uplanner__curriculum = custom fields genéricos. El read base solo trae la segunda.

Segundo: la asimetría es exactamente "escritura ya curada / lectura aún cruda", así que el fix es el espejo de lo que ya se hizo para crear y editar. Eso nos lleva al entorno: qué piezas vecinas ya existen y de cuáles nos apoyamos.

El entorno — qué nos rodea

✓ Ya resuelto (de qué nos apoyamos) — Crear (createCurriculumWithRecordType) y editar-guardar (updateCurriculumWithRecordType, TICKET-074) ya rutean por el alias vía customEndpoint del layout. El mecanismo de override mod→core ya está probado: resolverIndex.js hace ...dynamicResolvers.queries/mutations al final, así que un resolver del mod gana sobre el de core.
ℹ Por qué leer es distinto a escribir — Crear/editar usan "mutation nueva + customEndpoint" porque el botón Guardar dispara una mutation. La lectura del detalle no tiene ese hook: el front llama getInstance genérico (RecordDetail.vue solo hace caso especial para ReportTemplate). Por eso ver se resuelve con un override de Query.getInstance, no con una query nueva.
⚠ Restricción mod-only — No se toca core (object-manager) ni el front (layout). Todo vive en mods/curriculum-design/logic/. Y ojo con el constraint "un campo por archivo": dos *.resolver.js del mod no pueden exportar el mismo campo (el último pisa). getInstance/listInstances aún no están overrideados → van en un file nuevo de lectura.
✗ Fuera de alcance — versionar — Que la v2 de un Plan arrastre su extensión rt__Plan__curriculum está confirmado roto (TICKET-074 S2/TC-5: v1 totalCredits=240 → v2 NULL), pero es trabajo de core (path RT atómico en el versionado), frente B1 / pendiente de formalizar. NO entra en este ticket.

El invariante a restaurar

Toda operación sobre un Curriculum tipado debe resolver su extensión de RecordType, sin importar si entra por la base o por el alias.
Corolario: si la escritura lo cumple (crea/edita por alias) pero la lectura no (ve/lista por base), el dato existe pero es invisible — exactamente el síntoma reportado. El fix cierra esa brecha en el lado lectura.

El patrón que vamos a usar es el mismo que ya emplea polymorphicUpdate.resolver.js en el mod: "detecto mi caso, si no delego al genérico". El esqueleto del override de lectura se ve así (la idea, no el código final): 

// curriculum-read.resolver.js (mod) — override de Query.getInstance
export const curriculumReadQuery = {
  getInstance: async (parent, args, context) => {
    if (args.objectType === 'Curriculum') {
      // lee recordType del registro y delega por el alias rt__<tipo>__curriculum
      // el branch RT del genérico ya hace include {curriculum} + flatten
      return generic.getInstance(parent, { ...args, objectType: alias }, context);
    }
    return generic.getInstance(parent, args, context); // resto: sin tocar
  }
};

Dato verificado que sostiene este approach: el schema casa exacto (la satélite tiene relación curriculum y FK curriculumId; el branch RT del genérico busca where:{curriculum:{id}}), y el split es data-driven, así que sirve Plan y Minor sin hardcodear. El RBAC del alias (rt__Plan__curriculum:view) ya quedó probado por simetría con el edit (TICKET-074 TC-6 pasó con el delegate-con-alias en modify). Igual lo re-verificamos en runtime en la primera session.

Q&A de estudio

¿Por qué los campos del Plan no se ven si el create los guarda bien?
Porque viven en rt__Plan__curriculum, no en la tabla base. El create rutea por el alias (resuelve la extensión), pero el detalle lee por la base "Curriculum" y el branch base del getInstance solo incluye ext__uplanner__curriculum (custom fields), nunca la extensión del RecordType.
¿Por qué el clon no prellena los campos si el modal de create funciona?
El clon (prefilledModal) se prellena desde la fila del listado, y listInstances con name="Curriculum" no entra al branch RT → la fila no trae rt__ anidado. El código de prefill ya sabe copiar rt__*, pero no hay nada que copiar. Por eso el fix también enriquece listInstances.
¿Por qué override de getInstance y no una mutation nueva como en create/edit?
Porque el front no tiene "customEndpoint de lectura": RecordDetail.fetchInstanceData usa el getInstance genérico para todo (salvo un caso hardcodeado). No hay hook para enrutar una query nueva, así que la única vía mod-only es interceptar el resolver genérico.
¿Versionar entra en este ticket?
No. Que la v2 arrastre la extensión es un bug de core (path RT atómico en el versionado), confirmado en TICKET-074 y diferido al frente B1. Este ticket es solo el lado lectura (ver/editar-precarga/clonar), mod-only.
