Cierre — curriculum (Plan) · Clonar y versionar

Qué quedó hecho, qué se descubrió en el camino, y qué aprendimos. El caso entregó clonar y la unicidad por linaje del objeto Curriculum, verificados end-to-end. Pero el camino dejó tres hallazgos que valen más que el código: un bypass del guard que solo el E2E real atrapó, una limitación de core que refuta una hipótesis del intake, y un mensaje de error mal mapeado. Este teach mira hacia atrás: lo ejecutado, la evolución de las hipótesis, y las lecciones para quien retome.

Fixes extra: bypass del guard por el path UI (atrapado por E2E), y mensaje de error genérico (B4). 3 sessions, regresión 571/571.

La lección principal — el bypass que solo el E2E atrapó

Contexto

El guard se puso en el override de createInstance (DEC-LOCAL-01), asumiendo que cubría todos los paths. Los 13 tests de integración (que llaman al validador directo) pasaban.

Descubrimiento

El E2E real: clonar con code duplicado creó una raíz duplicada. La UI crea por createCurriculumWithRecordType que llama generic.createInstance DIRECTO → bypassa el override.

Resultado

Fix: el guard se movió a fuente única (helper) e invoca en AMBOS entry points. Re-verificado: clon dup rechazado, 0 duplicados. Lección: el unit/integration del validador NO prueba el ruteo — el E2E sí.

Lecciones y pendientes

✓ Lección L5 — un guard de dominio debe correr donde TODOS los clientes convergen; verificá el ruteo real (qué mutation llama cada cliente), no solo que el validador exista. El E2E real es el que atrapa bypasses de ruteo.
✓ Lección L3/OQ-1 — detectar "raíz" por previousVersionId==null era incorrecto: en el path de versión, core setea previousVersionId DESPUÉS del override. La señal correcta es el flag asNewVersion (leído igual que core, estricto).
⚠ Pendiente B2 (core) — Versionar curriculum requiere gatear la lógica de workflow de version-from-source.js a la presencia de initialStateField (curriculum no lo declara). Rama de épica core. El rowAction queda visible (decisión dev) y errorea hasta el fix.
⚠ Pendiente B3 — el clon nace status=Active, no Draft (el prefilledModal arrastra el status del source; prefillFrom.exclude no afecta el prefill client-side). Decidir si Draft es requisito duro.
ℹ B4 resuelto — el mensaje "modificado por otra persona" salía porque el texto del error contenía "versiones...Conflicto" (matcheaba el regex de concurrencia). Fix: patrón por código en useFriendlyErrors.ts (rama aislada, layout estaba ocupado por UPONE-1271).
ℹ B1 — clone profundo (arrastrar planEntry) sigue diferido al sprint con la malla.

Q&A para quien retome

¿Dónde vive el guard de unicidad por linaje y por qué en dos lugares?
En logic/helpers/lineageUniqueness.js (validateCurriculumCreate, fuente única). Se invoca desde (1) el override de createInstance en sectionValidation.resolver.js (cubre GraphQL directo + MCP) y (2) createWithRecordType en curriculum-create.resolver.js (cubre la UI, que llama generic.createInstance directo y bypassa el override). Los dos, porque son dos entry points de create distintos.
¿Por qué versionar no funciona y qué se necesita?
Core prepareVersionData (object-manager) hace include:{currentstatus,workflow} y exige allowsVersioning/initialStatusId — asume workflow. Curriculum es workflow-less. Fix (B2, core): gatear esa lógica a la presencia de initialStateField en el versioning config. Backward-compatible (activity lo declara, sigue igual).
¿Cómo se verificó que el enforcement es real y no solo UX?
E2E con Playwright + verificación directa en la DB UPU (core_Curriculum): clonar con code duplicado deja 1 sola raíz (rechazado); clonar con code nuevo crea la raíz. Más 13 tests de integración (incl. el path UI que tenía el bypass) y verificación por código de que el MCP rutea por createInstance.
¿Qué tooling de DKC quedó flaggeado como follow-up?
Dos: (1) el drift-checker de object-manager (detect-schema-drift.js) ignora objects/business/RecordTypes/ → falsos positivos en RT objects; (2) dkc-mutate con stryker-vitest-runner 8.7.1 vs vitest 3.2.4 (version-skew). Ambos con task chips.
