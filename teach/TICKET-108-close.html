Cierre: validacion pre-push local en curriculum-design (etapa 1)

Se instalo un hook .husky/pre-push versionado y auto-instalado (husky) en el mod curriculum-design. La guarda de rama (bloquear push directo a develop/master/main) quedo bloqueante; lint y typecheck quedaron en modo advisory (warn-only). La leccion central del caso apareció en runtime: el diseño chocó con un baseline que no pasa ni lint ni typecheck.

TL;DR — El hook se entregó y validó por runtime (6 TCs). Validar de verdad (DET-33) reveló que el mod no pasa typecheck (~130 errores) ni eslint (roto repo-wide por conflicto de ajv). En vez de bloquear todo push, se decidió (DEC-LOCAL-04) dejar lint/typecheck advisory y sanear el baseline en un follow-up (UPONE-1446).

  • S1.T2 — .husky/pre-push (POSIX sh): guarda de rama + lint changed-files por rango de refs + typecheck del mod + mensajes accionables + escape hatch.
  • S1.T3 — validacion runtime (DET-33). Aquí se descubrió el baseline rojo. Se adaptó el diseño a warn-only y se revalidaron los 6 TCs con evidencia real.
  • S1.T4 — docs/pre-push-hook.md: qué valida, instalacion, escape hatch, límites, follow-ups.
  • S1.GATE — quality review pass, commit 3b4b62b (mod, no pusheado), gate continue.

La decisión de cierre

Lessons learned

¿Por qué no bastaba leer el script del hook para cerrar?
Porque un hook "se ve bien" pero su valor es el comportamiento en runtime. Ejecutar los 6 pushes reales (DET-33) fue lo único que reveló que typecheck/eslint no pasan; sin eso, el ticket habría cerrado con un hook que bloquea a todo el equipo.
Lección de monorepo: instalar en un workspace toca el lock del root
El npm install dentro del mod reescribió el package-lock.json del root de up1 (workspaces comparten lock). La vía correcta para agregar una dep a un workspace es instalar desde el root. Quedó como nota de higiene.
Diagnóstico honesto vs supuesto: "3 errores" eran 130
Un tail del output mostró 3 errores y se reportaron como el total. El typecheck real tenía 130. Lección: contar/agrupar el output completo antes de dimensionar (DET-4: no confundir el síntoma visible con el alcance real).
Cuándo degradar un gate a advisory
Cuando la herramienta que el gate invoca está rota o el baseline no pasa, un gate bloqueante paraliza al equipo. Degradar a warn-only + follow-up explícito entrega valor (la guarda de rama) sin fingir un baseline sano, y deja el camino para promover a bloqueante.
Invariante del caso
Un quality gate no puede ser más estricto que el baseline que valida. Si el baseline está rojo, el gate se degrada a advisory y se abre el trabajo de saneamiento; no se cierra el gate sobre un baseline que no pasa.
