Malla curricular — Ver, modo edición y resumen

Este caso (MC-05, ticket Jira UPONE-1348) construye la vista de la malla curricular de un plan de estudio: las asignaturas ordenadas en columnas por período (semestre), con una barra de resumen del plan y la edición habilitada sólo cuando el plan lo permite. Es la vista base del módulo de malla — sobre ella se montarán después agregar/editar asignaturas (MC-06) y filtros (MC-08). Hoy esa vista no existe; lo que sí existe ya, gracias al ticket previo MC-02, son los datos que la malla va a pintar.

TL;DR — Qué hay: MC-02 dejó los objetos planEntry y requirementCategory + seed; no hay todavía una pantalla que los muestre como malla. Qué se hará: un componente de frontend en modsComponents/ del mod curriculum-design que reusa el patrón del precedente CompositeSectionTree, carga por GraphQL, agrupa por período y deriva el badge "electivo". Por qué: es la vista sobre la que el resto del sprint construye (MC-06 edita, MC-08 filtra).

Las bases — sobre qué se apoya el caso

Antes de tocar nada conviene fijar el vocabulario del módulo. Estos seis conceptos son el piso sobre el que se para todo MC-05. Los tres primeros son del cómo se organiza el código del mod; los tres últimos son del dato que la malla lee.

mod curriculum-design

Extensión modular de up1 (vive en mods/) para diseño curricular. Su código fuente se sincroniza a los workspaces core con npm run sync; nunca se edita el destino sincronizado.

modsComponents/

Carpeta del mod donde se autoran los componentes Vue. Es el lugar correcto del componente de malla. Sincroniza a layout/ (core) — el archivo de core es generado, no se toca a mano.

CompositeSectionTree

Componente precedente del mod (full-page Vueform element + carga GraphQL + lógica extraída a .ts). Es el patrón a reusar: misma estructura, no reinventar.

planEntry / requirementCategory

Objetos creados por MC-02 (TICKET-082). Un planEntry es una asignatura ubicada en un período del plan. La malla los lee (sólo lectura en MC-05).

blockId (electivo)

Campo del planEntry. Si blockId != null la asignatura pertenece a un bloque electivo → la tarjeta muestra badge "electivo". El badge se deriva, no se guarda.

LayoutOrchestrator / layoutType

El punto único de renderizado de up1 (core). Registrar un layoutType nuevo ahí tocaría core. En MC-05 está prohibido: el acceso se declara por config del mod.

El entorno — qué rodea el caso y qué lo limita

MC-05 no nace en el vacío: se apoya en el trabajo de MC-02, sigue un patrón ya probado en el mod, y choca con una frontera dura del sprint. Estos tres avisos son lo que hay que tener presente antes de diseñar la solución.

✗ Frontera crítica — mod-only. NO registrar un layoutType nuevo en el LayoutOrchestrator de core (auditoría §1.6). El entrypoint va por config del mod: una pestaña en default_Curriculum_view.json y una acción "Malla curricular" en default_Curriculum_list.json. Tocar core saca el ticket de alcance (SP5 es sin core) y obliga a escalar.
ℹ Reuso fuerte. No se construye desde cero: se calca CompositeSectionTree (full-page Vueform element + useTenantApolloClient + listInstances, lógica pura en .ts). Esto es lo que recomienda RULE-curriculum-design-014 y reduce el riesgo a "adaptar", no "inventar".
⚠ Gotcha conocido (memoria up1). El listado del mod a veces requiere recargar tras el primer render para que la acción/pestaña aparezca. Tenerlo presente al validar el entrypoint — no confundirlo con un bug del componente.

El invariante que ordena todo el ticket

El componente se autora en el mod y el acceso se declara por config del mod — jamás registrando un layoutType nuevo en el core.
Corolario: si en algún momento la solución "más fácil" pide tocar layout/ o el LayoutOrchestrator, es señal de que el approach se desvió — parar y reconsiderar, no escalar a core.

La forma del dato y la transformación central

La lógica de MC-05 es, en el fondo, una agrupación: tomar la lista plana de planEntry y partirla en columnas por period, derivando el badge electivo de blockId. Esa lógica pura es lo que va a un .ts testeable (sin Vue), para que las pruebas muerdan el cálculo y no el render. 

// planEntry (lo que entrega GraphQL — sólo lectura en MC-05)
type PlanEntry = { id: string; subjectCode: string; credits: number;
                   period: number; formationLineColor?: string; blockId?: string | null }

// transformación central: lista plana -> columnas por período + badge derivado
function groupByPeriod(entries: PlanEntry[], totalPeriods: number) {
  const columns = Array.from({ length: totalPeriods }, () => [] as CardVM[])
  for (const e of entries) {
    columns[e.period - 1]?.push({ ...e, isElective: e.blockId != null }) // badge = derivado
  }
  return columns
}

Hacia adelante — el plan (orientación)

El ticket está calibrado en 5 SP y previsto en cinco tareas con rollback. No es el detalle final (eso lo fija el SPEC formal en design-feature), pero da la forma del recorrido: primero el render y la lógica testeable, luego el entrypoint, después el resumen, y al final el gating de edición.

T1 — Componente de malla + carga GraphQL (REQ-01)

Grid por período, tarjetas (código, créditos, color de línea, badge electivo). Reusa CompositeSectionTree.

T2 — Lógica pura a .ts + .spec.ts

Agrupación por período y derivación del badge, fuera del componente Vue, con tests unitarios.

T3 — Entrypoint por config del mod (REQ-02)

Pestaña en default_Curriculum_view.json + acción en default_Curriculum_list.json. Sin layoutType en core.

T4 — Barra de resumen (REQ-03)

Créditos diseño/requeridos, n.º períodos, n.º asignaturas, carga máx. por período. Cálculo desde planEntry + totalCredits/totalPeriods.

T5 — Gating de modo edición (REQ-04) + stories

Acciones visibles sólo en modo edición + status editable (Draft); en sólo lectura, ocultas.

Q&A — ¿entendiste el caso?

¿De qué se trata el caso?
De construir la vista de lectura de la malla curricular de un plan: las asignaturas (planEntry) agrupadas en columnas por período, con tarjetas que muestran código, créditos, color de línea de formación y badge "electivo", más una barra de resumen del plan y la edición habilitada sólo cuando el plan está en estado editable.
¿Qué se va a hacer a alto nivel y por qué importa?
Un componente de frontend nuevo en modsComponents/ del mod curriculum-design, reusando el patrón CompositeSectionTree (Vueform element + GraphQL + lógica en .ts). Importa porque es la vista base del sprint: MC-06 (agregar/editar asignaturas) y MC-08 (filtros) se montan encima.
¿Cuál es la restricción que no se puede violar?
Mod-only: el acceso se declara por config del mod (pestaña del RecordDetail + acción del RecordList), nunca registrando un layoutType nuevo en el LayoutOrchestrator de core. SP5 es un sprint sin core; tocarlo obliga a escalar.
¿Quedaron hipótesis abiertas? ¿Hubo decisiones críticas?
No. El intake fue lineal: los 4 REQ están confirmados contra el mockup y los handoffs, y la única hipótesis (entrypoint vía config evita core) quedó confirmada por la auditoría §1.6. No hubo alternativas que ponderar, así que no hay matriz de decisiones.
¿Por qué la lógica de agrupación va a un .ts separado?
Para que sea testeable sin montar Vue: la agrupación por período y la derivación del badge son funciones puras (entrada → salida), y las pruebas unitarias (TC-01..TC-03) muerden ese cálculo directamente. Es el mismo split que usa CompositeSectionTree.
