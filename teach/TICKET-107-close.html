La historia

Este ticket nacio al revisar como PR el trabajo de TICKET-104 (UPONE-1382), el motor de hard delete en cascada, todavia sin mergear a develop. La revision encontro un defecto bloqueante: borrar un Curriculum (un Plan) que tuviera al menos una requirementCategory quedaba bloqueado por un Restrict falso, aunque la categoria es un hijo poseido que deberia caer en cascada, no bloquear el borrado.

La causa resulto sutil: el motor construye las claves del subarbol con el object de la metadata tal cual lo declara cada JSON (en minuscula para requirementCategory), pero al escanear referencias entrantes compara esa pertenencia contra el PascalName del modelo Prisma. El casing nunca coincidia, asi que la categoria se contaba como referencia externa. Dos unit tests estaban en verde porque cargaban un object en PascalCase que no existe en el JSON real: el mock ocultaba el bug que el runtime si sufria.

La decision principal fue normalizar la comparacion de claves del subarbol (objectType:id resuelto a un casing canonico), no parchear el JSON a PascalCase. Un parche de solo-JSON arreglaba el sintoma puntual, pero dejaba la comparacion fragil para el proximo hijo declarado en minuscula; normalizar cierra la causa raiz para todo hijo, presente y futuro, a costa de tocar codigo core con revision del equipo core pendiente (RULE-dev-004).

La sesion 1 aplico el fix, corrigio los tests falsos verdes y lo respaldo con integration contra la BD real de UPU mas un smoke por el path real de RecordList; un dual-judge (dos jueces ciegos) aprobo el cambio tras resolver empiricamente su unica disputa. Las sesiones 2 y 3 hicieron hardening de cero cambio de comportamiento y completaron i18n mas el mantenimiento del KB de la revision.

Con el fix y el KB cerrados, el dev abrio una cuarta sesion como una auditoria mas amplia: actualizar la documentacion de up1 para reflejar los tres tickets de SP6 (DataLog, transiciones y versionado, y este motor de cascada). El alcance crecio mas alla del pedido original de 107, pero el dev definio este ticket como el contenedor natural de la continuacion de 104.

Lessons learned

¿Por que unit tests en verde no bastan para codigo de datos?
(de H2 confirmada) porque un mock puede cargar un casing o un string que no existe en la fuente real, el JSON del objeto. El test queda verde mientras el runtime real, con el dato real, falla. Para delete, persistencia con proyecciones, casing o FK, exigir integration contra BD real, no basta el unit mockeado.
¿Como se debe resolver el nombre de un modelo o de una FK en codigo core?
Por introspeccion del schema, nunca comparando strings crudos entre convenciones distintas (el PascalName del modelo Prisma contra el object de la metadata JSON). Esa comparacion cruda fue exactamente la causa raiz de H1; RULE-core-031 lo deja como regla global del proyecto.
¿Que aprendio el equipo sobre como escribir la documentacion?
Que debe describir el estado ACTUAL en prosa limpia, sin mencionar artefactos internos de gestion (ids de ticket, spec o regla internos). Anexar capas tipo changelog en vez de reescribir el estado actual vuelve la doc confusa para quien la lee despues. Esta leccion vino del feedback del dev en S4, tras la primera pasada de la auditoria.
