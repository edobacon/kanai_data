HU-10 — Cierre: del "solo config" a un fix de engine de versionado

El intake apostó a que esto era configuración declarativa sobre un primitivo ya construido, sin código nuevo. Para los row actions (versionar Activity, duplicar BibliographyReference/Modalidad/CustomSection) la apuesta se cumplió. Pero el smoke E2E del objetivo —probar el versionado de verdad— destapó que el engine de versionado/clonado (de tickets previos) tenía dos defectos que rompían el caso real, y el alcance creció hacia el core. Este teach captura esa evolución: qué se entregó, qué hipótesis del intake se rompió, y los gotchas que un dev futuro necesita para no repetir el camino largo.

TL;DR — Entregado: Activity versionable + 3 objetos clonables (BibliographyReference directo→ver; Modalidad y CustomSection vía prefilledModal); toasts e i18n; modal de confirmación previa al versionado; campo version bloqueado en edición. Fixes de engine (UPONE-1219): (1) el deep-clone de hijos clonaba solo la fila base y perdía la proyección RT de cada hijo (FINDING-V1) → syllabus versionado vacío; (2) el incremento de versión era source.version+1 ingenuo → versionar dos veces desde v1 daba v2 dos veces → ahora max(linaje)+1. Lección madre: "no escribo código, solo configuro" es válido para la capa de UX, pero activar un primitivo end-to-end ejercita el engine debajo — y ahí aparecieron los bugs reales.

✓ Confirmado — La capa de UX fue config pura: row actions en JSON de layout + prefillFrom en objetos + i18n. Cero código nuevo en esa capa (REQ-01..REQ-07).

Gotchas que costaron el camino largo

⚠ deep-clone solo toca el modelo base — deepClonePolymorphicChildren clonaba CurricularSection pero NO rt__<RT>__curricularsection. Regla: clonar un objeto RT-projected = base + proyección + ext. El clone individual sí lo hacía; el deep-clone de hijos no. (FINDING-V1, L8)
⚠ versión = max(linaje)+1, no source.version+1 — el bump ingenuo colisiona al versionar dos veces desde la misma fuente. Hay que recorrer el linaje (atrás a la raíz + BFS de hijos) y tomar el máximo.
⚠ i18n: editás en layout/lang pero el runtime lee suite/lang — el plugin hace import.meta.glob('../lang/**') sobre suite/lang (copia generada). Sin correr suite/scripts/sync-i18n.js la clave sale cruda. (L7)
✗ Para bloquear un input de texto, usá disabled, no readOnly — Vueform honra disabled (el codebase setea field.disabled=true); readOnly solo aplica a textareas JSON. Bonus: disabled excluye el campo del submit.
ℹ Backend i18n: devolver code, no idioma — formatError retorna code: UNIQUE_VIOLATION + msg técnico canónico; el cliente traduce (form vía friendlyErrors.uniqueness, row action vía rowAction.create.error.*). El server no decide el idioma de la UI.
ℹ Postgres trata NULL como distinto en UNIQUE — @@unique([previousVersionId, version]) NO rechaza las dos raíces (previousVersionId=null, version=1): coexisten. Solo exige unicidad entre hijos del mismo padre no-null. Es exactamente "único entre los del mismo padre".

Study Q&A

¿Por qué el versionado producía un syllabus vacío de contenido?
El deep-clone de hijos clonaba solo la fila base de CurricularSection (name/recordType/position) pero no su proyección rt__<RT>__curricularsection (deliveryMode, week, citas, pesos…). Los 41 hijos quedaban como cáscaras. Fix: tras crear cada hijo base, clonar también su fila RT + ext (helper cloneChildProjections).
¿Qué pasa si versiono dos veces la misma Activity v1?
Antes: v2 las dos veces (colisión, source.version+1). Ahora: v2 y luego v3, porque el incremento usa max(versión del linaje)+1 recorriendo todo el árbol de versiones.
Agregué una clave i18n y sale cruda en la app. ¿Qué falta?
Editaste layout/lang (fuente) pero el runtime lee suite/lang (copia). Corré node suite/scripts/sync-i18n.js y recargá. El sync mergea claves nuevas (falla ante conflicto, no borra removidas).
¿Cómo bloqueo un campo en un layout de RecordDetail?
disabled: true en el schema del campo (Vueform). readOnly no aplica a inputs text en este codebase. disabled además lo excluye del submit.
¿La unicidad de versión por padre está enforced en la DB?
Declarada (uniqueConstraints: [["previousVersionId","version"]] en activity.json → codegen emite @@unique), pero NO aplicada aún a la DB viva (necesita migración + navegar drift de UPU). El incremento por linaje ya evita duplicados en flujo normal; el constraint es la red de concurrencia, a aplicar en deploy.
