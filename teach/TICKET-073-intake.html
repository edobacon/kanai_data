Corregir el mensaje de unicidad por linaje sin tocar core

Cuando un usuario intenta crear un segundo plan de estudio (un Curriculum) con un código ya usado en su institución, la app debería avisarle "ese código ya existe". En vez de eso, hoy muestra "Este registro fue modificado por otra persona" — un mensaje de concurrencia que no tiene nada que ver. Este ticket arregla ese mensaje engañoso. La parte interesante no es el qué (cambiar un texto), sino el dónde: el dev pidió expresamente que el arreglo viva solo en el mod curriculum-design, sin tocar el core (layout). Ese constraint es lo que define todo el enfoque.

TL;DR
  • Qué hay: el guard de unicidad por linaje del mod lanza un error cuyo texto contiene "versiones…Conflicto", y el core (useFriendlyErrors) lo confunde con un error de concurrencia → mensaje engañoso al usuario.
  • Qué se hará: reescribir solo el string que lanza el mod para que coincida con un patrón que el core ya reconoce (el de unicidad), que tiene traducción al español. Cero archivos de core.
  • Por qué: el dev impuso "solo el mod, cero core". El core no tiene un canal genérico para que un mod fije su propio texto, así que la única vía mod-only es hablar el idioma que el core ya entiende.

Conceptos clave (las bases)

Para entender el caso necesitás cuatro ladrillos: el guard que lanza el error, el componente de core que traduce errores técnicos a mensajes amables, el mecanismo de sync mod→core, y la regla de negocio de unicidad por linaje. Los tres primeros son del sistema; el último es del dominio educativo.

Unicidad por linaje

Regla de negocio (UPONE-1270): dos planes distintos no pueden compartir (institutionId, code). El code SÍ se comparte entre versiones de un mismo plan (las une), por eso no puede ser un unique de fila — se valida por dominio en el mod, solo para "raíces" de linaje.

El guard del mod

assertUniqueLineageRoot en lineageUniqueness.js: si detecta una raíz duplicada, hace throw new Error('CURRICULUM_LINEAGE_DUPLICATE: …'). El texto del error es lo único que controla el mod.

useFriendlyErrors (core)

Composable de layout que traduce errores técnicos a mensajes para el usuario. Itera un array ERROR_PATTERNS (orden = prioridad, el primero que matchea gana) contra el string del error. NO mira extensions, solo el texto.

Sync mod → core

La fuente del mod vive en mods/curriculum-design/logic/. npm run sync la copia al destino en object-manager/. Siempre se edita la fuente, nunca el destino sincronizado.

Cómo viaja el error hoy (y por qué se rompe)

El error nace en el mod (backend), atraviesa GraphQL sin perder su mensaje, y al llegar al front lo procesa useFriendlyErrors. El nudo está en el último paso: el texto del mod ("…versiones…Conflicto…") matchea el patrón de concurrencia (/version.*conflict/i) antes que cualquier otro, y por eso el usuario ve el mensaje equivocado. Clave: el patrón de unicidad está ANTES en el array, así que si el texto lo dispara, gana por orden de prioridad.

La restricción que define el enfoque

⚠ DEC-LOCAL-01 — "solo el mod, cero core" — El dev priorizó NO tocar layout/object-manager por sobre que el mod gobierne el texto exacto. Esto descartó el enfoque A (que requería un cambio en core) y dejó una sola vía: que el mod emita un texto que el core ya sabe mapear.
✗ Acople frágil aceptado — El nuevo mensaje depende del regex uniqueness de useFriendlyErrors.ts:191. Si alguien en core renombra o borra ese patrón, el mapping se rompe en silencio (sin error, solo vuelve el mensaje genérico). Mitigación: comentario explicativo en el helper + un test de regresión que ancla la forma del mensaje.
ℹ El mod no podrá fijar su texto exacto — La UI mostrará el mensaje genérico de core ("Ya existe un registro con ese valor."), NO "Ya existe un currículo con ese código en esta institución". Ese es el trade-off consciente de hacerlo mod-only.

Las dos formas de resolverlo

Hay dos maneras de que "lo maneje el mod". Importan ambas porque explican por qué el alcance quedó donde quedó: el enfoque A es técnicamente superior (el mod dueño de su texto) pero exige tocar core; el mod-only respeta el constraint del dev a costa de un texto genérico. El dev eligió mod-only. A queda parqueado en el backlog (B1).

A — extensions GraphQL (parqueado)

El mod lanza GraphQLError con extensions.userMessage; core gana un passthrough genérico que respeta ese texto.

+ El mod gobierna el texto exacto; reusable por cualquier mod.

− Exige tocar core (useFriendlyErrors + RecordDetail.vue) → viola "cero core".

mod-only — alinear al patrón de core ✓ elegido

El mod emite un string que matchea el patrón uniqueness que core ya tiene y ya traduce al español.

+ Cero cambios en core; un solo archivo del mod + su test.

− Texto genérico (no menciona currículo/código); acopla el mod al regex de core.

El cambio, en concreto

Una sola reescritura del string en assertUniqueLineageRoot. Hay que conservar CURRICULUM_LINEAGE_DUPLICATE (los tests asertan toThrow(/CURRICULUM_LINEAGE_DUPLICATE/)) e incluir la frase "Unique constraint failed … `code`" que dispara el patrón de unicidad de core. 

// HOY (matchea concurrency → mensaje engañoso):
throw new Error(`${ERR.CURRICULUM_LINEAGE_DUPLICATE}: ya existe un Curriculo raiz … las versiones … Conflicto con: …`);

// PROPUESTO (matchea uniqueness → "Ya existe un registro con ese valor."):
throw new Error(`${ERR.CURRICULUM_LINEAGE_DUPLICATE}: Unique constraint failed on the field \`code\`. ` +
  `Ya existe un curriculo raiz con el codigo "${code}" en la institucion (${institutionId}).`);
// + comentario explicando el acople intencional al regex de core (no "limpiar" el texto inglés)

Por qué esto funciona sin tocar core

El patrón uniqueness está ANTES que concurrency en ERROR_PATTERNS.
Corolario: como translateError devuelve el primer patrón que matchea, basta con que el mensaje dispare uniqueness — gana aunque el texto también contuviera "version/conflict". Y core ya tiene la traducción ES de friendlyErrors.uniqueness, así que el usuario ve español correcto.

Q&A de estudio

¿De qué se trata el caso?
Al crear un Curriculum (plan de estudio) con un código ya usado en la institución, la app muestra un mensaje de concurrencia ("modificado por otra persona") en vez de avisar que el código ya existe. Hay que corregir ese mensaje, tocando solo el mod.
¿Qué se va a hacer y por qué importa?
Reescribir el string que lanza el guard del mod para que matchee el patrón de unicidad que core ya reconoce y traduce. Importa porque el usuario hoy recibe una instrucción inútil ("refresca y reintenta") ante un problema que es de su input (código repetido).
¿Qué quedó abierto y qué verificar primero?
No quedan hipótesis abiertas (H6–H9 confirmadas en intake). Lo más crítico a verificar empíricamente es H8 en S2: que el toast correcto efectivamente aparezca en la UI real (no solo a nivel de match de regex). Por eso S2 es ⚑ fuerte.
¿Qué decisión crítica se tomó y por qué?
DEC-LOCAL-01: hacerlo mod-only, sacrificando que el mod fije su texto exacto. Se eligió por instrucción explícita del dev ("cero core"). El enfoque A (mod dueño del texto vía extensions + passthrough en core) es mejor a futuro pero exige tocar core → parqueado en backlog B1.
