Perfil local de DKC — reducir contexto y superficie de tools sin degradar Claude Code

Este teach-close es el complemento del teach-intake del ticket HOR-103: si el intake describía el landscape antes de ejecutar (el problema, las hipótesis, el plan), este close documenta lo que realmente ocurrió. El ticket implementó tres mejoras en tres sessions secuenciales para acercar DKC — el sistema spec-driven de gestión de conocimiento y flujo de trabajo — a un host LLM local con ventana reducida, sin tocar el comportamiento del host actual (Claude Code). Las dos hipótesis que el intake dejaba abiertas quedaron confirmadas con evidencia empírica en S1. Las tres sessions cerraron limpias. Lo que sigue es la historia completa para que puedas retomar el caso, extender el trabajo o aplicar los patrones en otro módulo.

TL;DR resultado clave S1 → S2 → S3 default vs local hipótesis confirmadas decisiones lecciones para retomar
TL;DR — En tres sessions, HOR-103 añadió un perfil dual a DKC: activar DKC_PROFILE=local baja el baseline de contexto de 39,580 a 28,938 tokens (−27%), dejando al sistema dentro del presupuesto de un host local con ventana de 128K. El perfil default de Claude Code quedó byte-idéntico: 39,580 tokens, validators verdes, sin ningún cambio de comportamiento. La superficie de 78 tools quedó documentada por step en el frontmatter (tools:), con un validator de coherencia que detecta drift automáticamente. Todo lo que depende de tener un host local instalado quedó en backlog bloqueado-por-host.

Evolución de hipótesis — propuesta → confirmada

El intake tenía dos hipótesis abiertas, ambas marcadas como "propuesta". Las dos se verificaron en S1.GATE con medición empírica. H1 es la dominante — todo el ticket dependía de que se cumpliera. H2 es consecuencia directa de H1 y se obtiene de la misma medición. Ambas cerraron en la primera session.

H1 (DOMINANTE) — El perfil dual reduce contexto en local sin tocar el default → CONFIRMADA

Enunciado original (intake): DKC_PROFILE=local activo → baseline local baja del target de 32K; perfil default (variable no seteada) → baseline idéntico a hoy (39.6K).

Evidencia (S1.GATE): dkc-measure-context-base --json sin variable → 39,580 tok (idéntico). Con DKC_PROFILE=local → 28,938 tok (< 32K). git diff --stat prompts/_style.md vacío — el íntegro byte-idéntico.

Cómo cerró: el mecanismo condicional en dkc-measure-context-base (CLI --local + variable de entorno, con precedencia CLI-sobre-env) funcionó exactamente como se diseñó. El switch no toca ninguna ruta del perfil default.

Evolución respecto al intake: el intake planteaba H1 como "propuesta" y condición bloqueante del gate de S1. Cerró en S1.GATE con evidencia dura — no hubo iteración ni ajuste del mecanismo.

H2 (derivada) — _style point-of-use baja el baseline local por debajo de 32K → CONFIRMADA

Enunciado original (intake): _style.md (12,223 tok) movido a point-of-use baja el baseline del perfil local de 39.6K a menos de 32K — un delta de al menos 7.6K tokens.

Evidencia (S1.GATE): _style 12,223 tok → condensado 1,581 tok. Baseline local: 28,938 tok (margen de 3K respecto al objetivo de 32K). Delta real: 10,642 tok (más holgado que los 7.6K estimados).

Cómo cerró: la reducción fue mayor de lo esperado. El condensado resultó más compacto que el lower-bound que el intake estimaba. La heurística chars/3.7 de dkc-measure-context-base (el instrumento de medición basado en ese ratio de caracteres por token) fue suficientemente precisa para el gate.

Incertidumbre resuelta: el intake señalaba que la reducción real dependía de cuántos principios declara cada step. La solución encontrada disolvió esa incertidumbre: como el condensado se surfacea entero (no granular por step), la varianza desapareció. Se simplificó el modelo a costa de un margen algo menor, pero el target se cumplió con holgura.

Evolución respecto al intake: H2 era "derivada de H1" — si H1 pasaba, H2 se obtenía de la misma medición. Así ocurrió exactamente. No requirió steps adicionales.

Lo notable de la evolución de hipótesis es que ambas cerraron en la misma session y con la misma evidencia. Eso no es habitual — normalmente H2 requiere observación adicional. En este caso, la arquitectura del mecanismo (condensado que se surfacea entero, no granular) colapsó la verificación de ambas en una sola medición. Esa simplificación es en sí misma una de las lecciones del ticket. Las decisiones que llevaron a esa arquitectura se detallan a continuación.

Tres decisiones que fijaron el diseño

Estas son las tres decisiones más importantes del ticket — las que podrían parecer raras si abres el código sin contexto. Cada una tenía alternativas viables que se descartaron por razones concretas.

Switch del perfil = env var

Elegida: variable de entorno DKC_PROFILE. Documentada en prompts/agent-tiers.md.

Descartada: config.yaml de proyecto — granularidad incorrecta. El dev alterna Claude Code ↔ local sesión a sesión en el mismo PC y proyecto; una config de proyecto no captura esa variación.

Runtime, coexiste Claude↔local en el mismo PC sin tocar archivos del proyecto.

Mecanismo de _style = condensado completo

Elegida: prompts/_style-condensed.md se surfacea entero bajo perfil local. Host-agnóstico, cero cambios al server MCP.

Descartada: granularidad style: por step (paridad con el mecanismo de DETs seleccionadas por step). El íntegro de _style.md son 12 principios (no 1,280 líneas como las DETs) — el condensado a 1.5K cabe entero y evita tocar ~28 frontmatters.

Paridad en el patrón (condensado point-of-use), no en el mecanismo de selección.

Tools surface = enfoque C (frontmatter)

Elegida: frontmatter tools: por step generado desde grep dkc_ real + validator de coherencia.

Descartado B: fachadas de tools — rompe HC server, validators, convención dkc.md. Descartado A: tool-set dinámico server-side — depende de host local inexistente → Backlog.

Host-agnóstico hoy; habilita enfoque A cuando llegue el host local.

Las tres decisiones tienen un hilo común: cada una rechazó la opción que requería más precondiciones no cumplidas (un host local, cambios al server, granularidad innecesaria) a favor de la opción host-agnóstica con menor riesgo de regresión. Lo que esas decisiones producen — y lo que vale la pena recordar si abres código similar — son tres lecciones.

Lecciones aprendidas (R5)

Las tres lecciones del ticket están conectadas con las hipótesis: L1 y L2 surgieron de la confirmación de H2 (cómo funciona realmente el mecanismo de _style); L3 surgió de implementar el generador de S2. Se presentan con el marcador de la hipótesis que las originó para que puedas trazar la cadena.

L1 — (de H2 confirmada) Paridad en el patrón, no en el mecanismo de selección
El condensado de _style (~2K, 1,581 tok) es lo suficientemente compacto para surfacearse entero bajo perfil local — no necesita la granularidad style: por step que tienen las DETs (cuyo íntegro son 1,280 líneas). Cuando el intake planteó H2 asumía incertidumbre sobre cuántos principios declararía cada step; la solución colapsó esa incertidumbre eligiendo no tener granularidad. Si en el futuro _style.md crece hasta el orden de magnitud de las DETs, este patrón debería revisarse — el mecanismo granular existe y está probado (HOR-085).
Aplicable a: cualquier archivo de prompts que se esté pensando reducir. Si el condensado cabe en <3K, surfacea entero. Si no, granularidad por step.
L2 — (de H1 confirmada) El wiring del perfil NO va en el archivo íntegro
Añadir el blockquote de wiring directamente en _style.md rompería REQ-PRESERVE-02 (+139 tokens en el íntegro → baseline default sube). La discoverability del switch vive en _style-condensed.md (header autodescriptivo que explica la relación con el íntegro) y en agent-tiers.md (el punto único del switch). Esto sigue el mismo principio que el íntegro de las DETs — prompts/deterministic-rules.md no se auto-anota "te condensan en dets_catalog.py": el wiring vive en el condensado, no en el original.
Aplicable a: cualquier par íntegro/condensado en DKC. El íntegro es fuente de verdad de contenido; la instrucción de cómo usarlo vive en el condensado y en el punto de configuración.
L3 — (de implementación S2) Generador y validador comparten la misma lógica grep
dkc-validate-tools opera en dos modos con la misma lógica grep interna: --fix (genera y escribe el campo tools:) y validate (verifica coherencia). Al compartir la lógica, es imposible por construcción que el campo declarado y el campo real diverjan — si modificas el cuerpo del step y corres el comando, el campo se recalcula desde el mismo grep que el validador usa. No hay dos fuentes de verdad que sincronizar manualmente. Este patrón es reutilizable para cualquier campo de frontmatter que deba derivarse del uso real en el cuerpo del archivo (ej. un campo futuro reads: que registre los archivos que el step lee).
Aplicable a: campos derivados-de-uso en frontmatter de steps o cualquier otro tipo de archivo donde el campo refleja qué hay en el cuerpo. "Generar desde uso real, no a mano" debe ser la regla por construcción.

Las tres lecciones convergen en una idea: las reducciones más robustas son las que hacen que el estado incorrecto sea imposible por construcción — ya sea que el mecanismo no distinga perfiles cuando no debe (L1, L2), o que el campo declarado no pueda desincronizarse del uso real (L3). Con las lecciones claras, lo que sigue es el path sugerido para quien retome el caso.

Para retomar el caso

Este bloque está escrito para un dev que llega al código después — ya sea a depurar, a extender el perfil local, o a activar el enfoque A cuando exista el host local. El orden es el de lectura útil, no el de implementación original.

Paso 1 — Entender el switch del perfil

Por qué primero: todo lo demás depende de cómo funciona DKC_PROFILE.
Refs: prompts/agent-tiers.md (sección "Perfil de contexto — DKC_PROFILE"), commands/dkc-measure-context-base (líneas del bloque condicional de perfil), prompts/_style-condensed.md (el condensado que se activa bajo perfil local).

Paso 2 — Verificar el estado actual

Por qué: confirmar que el baseline sigue en los valores documentados antes de hacer cualquier cambio.
Comando: ./commands/dkc-measure-context-base --json (default) y ./commands/dkc-measure-context-base --local --json (local).
Valores esperados: default 39,580 tok · local 28,938 tok. Cualquier desviación indica que algo cambió en prompts/_style.md o en las DETs.

Paso 3 — Verificar coherencia de tools

Por qué: los frontmatters de steps pueden desincronizarse si se modifican steps sin correr el generador.
Comando: ./commands/dkc-validate-tools (debe reportar "OK: 35 steps coherentes").
Si hay drift, correr ./commands/dkc-validate-tools --fix para regenerar desde uso real.

Paso 4 — Para activar el enfoque A (Backlog B1)

Cuándo: cuando exista un host local que soporte filtrado dinámico del tool-set.
Base ya disponible: el campo tools: en cada step es exactamente la entrada que el servidor necesita para filtrar el tool-set expuesto. La lógica de lectura del frontmatter ya existe en el server MCP.
Ref: spec SPEC-workflow-local-only-readiness-102 (sección DEC-LOCAL-02 y Backlog B1).
