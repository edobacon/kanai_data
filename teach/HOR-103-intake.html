Perfil local de DKC — reducir contexto y superficie de tools sin degradar Claude Code

Este ticket (HOR-103) implementa las tres mejoras host-agnósticas diseñadas en la exploración HOR-102 para acercar DKC — el sistema spec-driven de gestión de conocimiento y flujo de trabajo — a un host LLM local con ventana de ~128K tokens y tool-calling débil, sin degradar en ningún punto el host actual (Claude Code, ~1M de ventana). El trabajo está partido en tres sessions secuenciales con gate de verificación en cada una. Este teach-intake es el mapa conceptual que necesitas leer antes de empezar a ejecutar: qué existe hoy, qué se va a hacer, qué decisiones se tomaron en el diseño y qué hipótesis quedan abiertas para verificar en vivo.

TL;DR restricciones glosario perfil default vs local decisiones hipótesis plan de sessions invariante
TL;DR — El baseline puro de contexto de DKC es hoy 39.6K tokens: DETs (las reglas determinísticas del flujo, 27.4K) más _style.md (la guía de estilo de prompts, 12.2K). El único componente grande sin mecanismo de reducción es _style.md — 31% del baseline — y hoy ningún step lo declara en su frontmatter. La superficie de tools es 78, de las cuales solo 18 se usan en algún step del flujo. Este ticket añade un perfil dual opt-in: activar DKC_PROFILE=local activa la carga reducida; sin esa variable, el comportamiento de hoy queda idéntico. La hipótesis dominante que se verifica primero en S1 es si el mecanismo de point-of-use de _style baja el baseline local por debajo de 32K sin tocar el default.

Restricciones del ticket

Restricción dura (DEC-LOCAL-03) — El perfil default (Claude Code, ~1M de ventana) NO se toca. Toda reducción es condicional a DKC_PROFILE=local. Si el baseline del perfil default cambia un solo token, la session falla el gate.
Dependencia secuencial — S2 (tools: por step) y S3 (doc del perfil local) dependen del switch DKC_PROFILE que se define en S1. No hay tasks paralelizables inter-session.
Fuera de scope — Enfoque B (fachadas de tools que colapsan la interfaz), enfoque A (tool-set dinámico server-side), validación contra un host local real, y cualquier cambio al server MCP para multi-provider. Todo eso queda en Backlog bloqueado-por-host.
Autopilot: super — Este ticket corre en modo autopilot super, lo que activa DET-30 (red de seguridad autopilot): guard de rama protegida, validación de cierre reforzada, teach obligatorio (no skip), intake exhaustivo. Los commits se generan automáticamente por session pero el push siempre requiere aprobación humana.

Antes de entrar al contenido, estos son los términos del dominio que aparecen a lo largo del teach. Si ya conoces DKC puedes saltar esta sección; si llegas frío, lee los seis conceptos en orden.

Glosario

DETs (reglas determinísticas)

Las 30 reglas no-negociables del workflow DKC (DET-1 a DET-30). Viven en prompts/deterministic-rules.md (texto íntegro, 27.4K tokens) y en server/src/deckard_cain/dets_catalog.py (condensado Lean-B). Son el componente más pesado del baseline.

_style.md

La guía de estilo de prompts de DKC — 12 principios que rigen cómo se redactan los steps y el output del LLM. Pesa 12.2K tokens (31% del baseline puro) y hoy es el único componente grande sin mecanismo de reducción. Vive en prompts/_style.md.

Baseline puro

El contexto mínimo que DKC carga antes de ejecutar cualquier step: solo DETs + _style.md. Se mide con commands/dkc-measure-context-base (heurística chars/3.7). Hoy es 39.6K tokens (27.4K DETs + 12.2K style).

Point-of-use (re-surfacing)

Patrón introducido en HOR-085 para las DETs: en lugar de cargar el texto íntegro de una regla, el step declara en su frontmatter (dets:) cuáles necesita y el sistema las re-surfacea condensadas solo para ese turno. Este ticket aplica el mismo patrón a _style.md.

Perfil dual (DEC-LOCAL-03)

La decisión arquitectónica central del spec HOR-102: las reducciones no son globales. Con DKC_PROFILE=local activo → carga reducida. Sin la variable (o cualquier otro valor) → comportamiento actual de Claude Code, sin ningún cambio. Un solo codebase sirve a ambos hosts.

Superficie de tools

El conjunto de tools MCP (dkc_*) expuesto al LLM. Hoy son 78 tools en total; la unión de lo que usan todos los steps del flujo es 18; el máximo por step es 11 (task-loop). 60 tools nunca se usan. El enfoque C (frontmatter tools: por step) documenta la superficie mínima real sin cambiar el server.

Con el glosario claro, la siguiente sección compara directamente cómo se comporta el sistema hoy (perfil default) versus cómo se comportará bajo DKC_PROFILE=local. Esta comparativa es el corazón del cambio propuesto.

Perfil default vs perfil local

Perfil default — Claude Code (hoy, sin cambios)

Ventana ~1M tokens. Baseline puro: 39.6K tokens por turno (DETs 27.4K + _style.md 12.2K completo).

_style.md se carga íntegro. No hay declaración de tools: por step.

+ Comportamiento actual íntegro, sin degradación.

+ El dev no tiene que cambiar nada — es el default cuando DKC_PROFILE no está seteado.

− Incompatible con ventana de 128K: solo el baseline ya ocupa el 31% de la ventana objetivo.

Perfil local — DKC_PROFILE=local (objetivo)

Ventana objetivo ~128K. Baseline puro objetivo: < 32K tokens (target medido post-S1).

_style.md se re-surfacea point-of-use (solo principios declarados por el step). tools: por step permite acotarla cuando el host soporte filtrado.

+ Cabe en ventana local. Reducción de al menos 7.6K tokens en baseline (si el patrón DETs se replica).

+ Host-agnóstico: no asume nada del host local que aún no existe.

− El ahorro real en tools llega completo solo cuando el host soporte filtrado server-side (enfoque A, en Backlog).

Lo interesante de esta comparativa es que el perfil local no elimina nada: mueve la carga de _style.md de "siempre íntegro" a "on-demand por principio". El contenido íntegro sigue accesible. Eso implica que la reducción es reversible: si un step necesita un principio no declarado, sigue pudiendo consultarlo. Con eso en mente, veamos las decisiones críticas que fijaron el diseño.

Decisiones del intake

Cuatro decisiones críticas tomadas durante el diseño (HOR-102) y ratificadas al activar este ticket. La columna "Alternativas descartadas" explica por qué no se eligieron las otras opciones.

Decisión Elegida Alternativas descartadas Driver clave
DEC-LOCAL-03 — Perfil dual Opt-in via DKC_PROFILE=local Reducción global (viola no-degradar CC) · Dos forks del prompt-set (divergencia doble de mantenimiento) Restricción dura del dev: no degradar Claude Code
DEC-LOCAL-01 — Reducir _style.md Point-of-use (paridad con DETs / HOR-085) Split por sección + lazy-load (mismo efecto, más trabajo) · Condensado único estilo Lean-B (pierde granularidad por step) Reusar patrón probado; evitar inventar mecanismo nuevo
Switch del perfil Variable de entorno DKC_PROFILE + doc en prompts/agent-tiers.md config.yaml de proyecto (granularidad incorrecta: es config de proyecto, no de sesión) El dev alterna Claude Code ↔ local sesión a sesión en el mismo PC/proyecto
DEC-LOCAL-02 — Tools surface Enfoque C: frontmatter tools: por step + doc (habilita A futuro) B fachadas (rompe HC server, validators, DET-16) · A tool-set dinámico (depende de host no existente) Host-agnóstico ahora, path a A cuando llegue el host

La decisión más sorprendente de la tabla es el rechazo al enfoque B (fachadas de tools): intuitivamente parece la solución más directa para acotar la superficie, pero rompería consumidores existentes — HC server, validators, la convención dkc.md — lo que generaría deuda técnica mayor que el ahorro. El enfoque C es deliberadamente conservador: documenta sin cambiar la interfaz, y deja el filtrado real para cuando haya un host que lo soporte. Con las decisiones fijas, lo que queda abierto son dos hipótesis que se verifican durante la ejecución.

Hipótesis abiertas

El mapa tiene 2 hipótesis abiertas. H1 es la dominante — todo el ticket se subordina a si se cumple. H2 es una consecuencia derivada de H1. Ambas se verifican en S1 con medición empírica; H1 debe pasar antes de cerrar el gate de S1.

H1 (DOMINANTE) — El perfil dual reduce contexto en local sin tocar el default

Enunciado: DKC_PROFILE=local activo → baseline local baja del target de 32K; con perfil default (variable no seteada) → baseline idéntico a hoy (39.6K tokens medidos con dkc-measure-context-base --json).

Por qué es dominante: el invariante del ticket es "no degradar el default". Si el mecanismo point-of-use toca el baseline del perfil default (aunque sea un solo token), el ticket debe hacer rollback. Todo lo demás (tools, doc) se construye sobre este resultado.

Cómo verificar: correr dkc-measure-context-base --json dos veces — sin DKC_PROFILE y con DKC_PROFILE=local. El primero debe reportar 39.6K (±marginal). El segundo debe estar bajo 32K.

Status: abierta (propuesta). Se verifica en S1.GATE como condición bloqueante.

H2 (derivada) — _style point-of-use baja el baseline local por debajo de 32K

Enunciado: _style.md (12.2K tokens) movido a point-of-use baja el baseline del perfil local de 39.6K a menos de 32K — un delta de al menos 7.6K tokens.

Base de la hipótesis: en HOR-085, el mismo patrón (DETs condensadas en lugar de texto íntegro de deterministic-rules.md) produjo la reducción de 27.4K del texto íntegro a la fracción que re-surfacea cada step. Si _style.md sigue la misma mecánica, la reducción debería ser comparable.

Incertidumbre: la reducción real depende de cuántos principios declara cada step. Si un step promedio declara muchos principios, el re-surfacing puede ser mayor que el texto original condensado. La medición post-S1.T2 resolverá esto con evidencia empírica.

Status: abierta (derivada de H1). Depende de H1; se verifica con la misma medición.

Lo que distingue H1 de H2 es el orden de verificación: H1 primero porque es el gate que desbloquea el resto. Si H1 falla (el mecanismo no es condicional al perfil y toca el default), S1 hace rollback y el ticket escala; no tiene sentido medir H2 sin H1 verificada. Si H1 pasa, H2 se obtiene automáticamente de la misma medición. A continuación, el plan de sessions que estructura esa verificación.

Plan de sessions (S1 → S2 → S3)

S1 — Reducir _style.md via point-of-use + definir el switch del perfil gate: fuerte T2

Objetivo: medir baseline actual → crear prompts/_style-condensed.md (catálogo markdown de los 12 principios, paridad con dets_catalog.py) → añadir frontmatter style: por step → documentar el switch DKC_PROFILE en prompts/agent-tiers.md → verificar que el baseline default queda en 39.6K y el baseline local cae bajo 32K.

Gate: baseline local < 32K medido y baseline default idéntico (39.6K) y validators verdes. Cualquier desviación en el default bloquea el continue.

S2 — Frontmatter tools: por step + validator de coherencia gate: auto T2

Objetivo: poblar tools: en los ~28 steps de prompts/steps/ generado desde grep dkc_ real (no a mano para evitar drift) → implementar validator de coherencia que compara tools: declaradas vs referenciadas en el cuerpo del step.

Depende de: S1 completada (el switch DKC_PROFILE ya definido). Gate auto: todos los steps con tools: y validator pasa sin drift.

S3 — Perfil local consolidado: doc + medición final gate: fuerte T1

Objetivo: documentar el perfil local completo en prompts/agent-tiers.md (palancas disponibles, cómo activarlas, target medido) → correr medición final que demuestra el baseline mínimo alcanzable → nota de replicación para quien quiera replicar Lean-B en un frontend local.

Depende de: S1 y S2 completadas. Gate fuerte: perfil documentado + medición con número que demuestra el baseline mínimo del perfil local.

El orden de sessions no es arbitrario: S1 es la más riesgosa porque toca _style.md — el archivo con más influencia sobre el comportamiento del LLM principal — y define el switch sobre el que S2 y S3 se apoyan. Interrumpir en S1.GATE si la medición falla es más barato que descubrir la incoherencia en S3. Esa secuencialidad es la razón por la que el plan de paralelización quedó como "not-applicable" en el ticket. El único invariante que sostiene todo el diseño se resume a continuación.

Invariante

El perfil default de Claude Code nunca se degrada. Sin DKC_PROFILE=local, el baseline es 39.6K y los validators pasan idéntico a hoy.
Corolario: cada task que reduce algo bajo el perfil local debe incluir una verificación explícita del perfil default. Si esa verificación no está en el plan de la task, la task no cumple DET-8 (rollback documentado) — el reviewer debe bloquearlo.
