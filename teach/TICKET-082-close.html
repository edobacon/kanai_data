Lessons learned (reusables para el mod)

L1 · Un mod NO puede registrar field resolvers de tipo GraphQL
El scanner (resolverIndex.js: loadResolversFromDirectory) solo recolecta exports con "query"/"mutation" en el nombre → los compone en Query/Mutation. Corolario: campos derivados de lectura se entregan enriqueciendo item.data en el override de getInstance/listInstances (patrón curriculum-read), nunca con extend type + resolver de campo.
L2 · El codegen no honra metadata.indexes; la nullability la decide required[]
Los índices del JSON no llegan al schema (igual que CurricularSection) → se crean vía seed/_data-indexes.js (ensureIndexes, CREATE INDEX IF NOT EXISTS). Y not_null: true NO basta para no-nullable: el campo debe estar en required[] (verificado: kind salió planEntryKind?, period en required salió Int).
L3 · planEntry/requirementCategory son hijos del Curriculum, no objetos de menú
Lo que pone un objeto en el menú es tener un default_<Obj>_list top-level (CurricularSection no lo tiene → no aparece). Los hijos se embeben en el view/edit del padre vía tabs + elementos record-list con filters sobre {{parentId}} + directChildren en la metadata. Esta corrección de placement se ejecuta en un ticket nuevo (el núcleo de datos de MC-02 ya estaba completo y aprobado).

Q&A para quien retoma

¿Por qué los campos derivados no son columnas ni field resolvers?
REQ-04 prohíbe persistir isElective; y un mod no puede registrar field resolvers de tipo GraphQL (L1). Se enriquecen en lectura (override getInstance/listInstances por objectType, batch findMany). effectiveCredits = credits ?? Activity.credits; isElective = blockId != null; currentCredits = Σ efectivos.
¿Dónde está el guard de borrado y por qué A+B?
A: FK planEntry.categoryId onDelete: Restrict (DB bloquea — backstop, cubre bypass directo/MCP). B: requirementCategoryDelete.resolver.js (único override de deleteInstance del mod) cuenta entries y lanza "reasigna primero" (REQ-09 exige el mensaje). El guard B corre primero; la DB es el backstop.
¿Cómo se entregaron los índices si el codegen los ignora?
Vía seed/_data-indexes.js (ensureIndexes) — el workaround del mod que crea índices con SQL en cada sync (mismo patrón que ChangeLog/WorkflowTransitionHistory). Se agregaron 5: planEntry (planId, categoryId, blockId, compuesto) + requirementCategory (curriculumId).
¿Qué falta para que la malla se vea como la maqueta?
El ticket de seguimiento (placement, L3): mover ambos objetos a hijos del Curriculum (tabs Líneas de formación + Malla curricular embebidas), y el componente visual de la malla (grilla por período coloreada por línea) es MC-05/06.
