Las bases — vocabulario que conviene tener firme

Todo lo que sigue se apoya en estos conceptos. Si alguno no esta claro, el resto del ticket se lee en falso.

Token semantico

Variable CSS nombrada por su rol (--primary, --background), no por su color. La UI usa el rol; el modo (claro/oscuro) cambia el valor detras. Es lo que permite un solo set de componentes para ambos temas.

Convencion shadcn (HSL)

shadcn/ui guarda el color como HSL sin envoltura: --primary: 142 76% 36%, y en Tailwind lo consume como hsl(var(--primary)). Es la convencion que adopta el proyecto (ver components.json).

Estrategia .dark (class)

El modo oscuro se activa poniendo la clase .dark en <html>. Tailwind necesita darkMode: ['class'] para que el .dark redefina los tokens. Sin esa linea, el switch no hace nada.

FOUC / flash de tema

Si el tema se decide despues de pintar, el usuario ve un parpadeo (claro→oscuro). Se evita con un script inline en <head> que setea la clase antes del primer render, leyendo localStorage / prefers-color-scheme.

design-tokens.md

La fuente canonica de valores (en jormat_docs/ongoing/): roles de color HSL listos para implementar, radios, sombras, tipografia. Este ticket lo aterriza a codigo; no inventa valores.

DET-18 (gate de draft)

Regla DKC: si el ticket crea algo visual (creates_visual: true), antes del spec se produce un draft aprobable (preview de los tokens y el toggle). Por eso este ticket pasa por design-draft antes de design-feature.

Como funciona el estilo HOY

El scaffold (cerrado en JOR-002) dejo globals.css con un set provisional: tokens --color-* en formato RGB (consumidos via rgb(var(--color-x))) y una paleta brand verde-claro en tailwind.config.js. No hay modo oscuro tokenizado ni convencion shadcn. Esto es lo que vamos a complementar (no borrar): 

/* globals.css — estado actual (scaffold, se conserva) */
:root {
  --color-primary: 77 194 71;      /* RGB, no HSL · verde #4dc247 */
  --color-surface: 255 255 255;
  --color-text: 17 24 39;
}
/* tailwind.config.js — paleta legacy (la usa el shell mock) */
brand: { 400: '#4dc247', 600: '#2f8a2d' }, muted: '#5a5f70'

// JOR-003 AGREGA (sin remover lo de arriba):
:root { --primary: 142 76% 36%; /* HSL shadcn · green-600 #16A34A */ ... }
.dark { --primary: 142 70% 45%; ... }

Q&A para verificar que agarraste el caso

¿Por que el ThemeToggle no va a verse en la app corriendo al cerrar este ticket?
Porque colocarlo en el TopBar y tematizar el shell es scope de JOR-005, y RULE-global-003 prohibe tocar el shell entregado aqui. El toggle existe, funciona y se prueba en Storybook; su lugar en el header lo pone JOR-005.
¿Que pasa si me olvido de darkMode: ['class'] en Tailwind?
El bloque .dark redefine las variables CSS, pero Tailwind no generaria las variantes y, mas importante, el contrato de tema quedaria a medias. La clase .dark en <html> seguiria cambiando los valores de las vars consumidas con hsl(var(--x)), pero cualquier uso de dark: utilities no funcionaria. Es la linea que habilita la estrategia por clase.
¿Cual es la colision de muted y por que no se resuelve en este ticket?
El legacy define muted: '#5a5f70' (gris) y lo usa el Sidebar 5 veces como text-muted. shadcn espera muted como fill claro (#F3F4F6) + muted-foreground. Cambiar la key rompe el Sidebar (RULE-003). Solucion: agregar muted-foreground flat, conservar el legacy, y dejar un backlog must para que JOR-005 — que de todos modos retematiza el shell — reconcilie. El orden del plan (A2 antes que A3) hace que se resuelva antes de que los atomos necesiten bg-muted.
¿De donde salen los valores de color? ¿Los invento el ticket?
No. Salen de jormat_docs/ongoing/design-tokens.md (fuente canonica). El ticket aterriza esos valores a globals.css y al binding de Tailwind; las dos decisiones abiertas del doc (adoptar green de Tailwind como primary, y tipografia Inter) se resuelven aqui con su racional.
