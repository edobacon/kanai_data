No-negativos en campos numéricos del mod, y el typechecking preexistente

Este ticket (external UPONE-1378, mod curriculum-design) cierra un hueco de integridad de datos: hoy varios campos numéricos de negocio de la malla (créditos, períodos, pesos, horas, semanas, duraciones, totales) aceptan valores negativos por cualquier canal (UI, MCP, n8n, bulk), lo que rompe cálculos de plan y de sílabo. La buena noticia: no hay que construir nada nuevo para validarlo, el motor ya existe en el core. El ticket suma además un apartado de deuda técnica: resolver los errores de tipado (vue-tsc) que arrastra el mod. Este documento te deja parado sobre las bases, el entorno y el plan antes de que diseñes o ejecutes.

TL;DR — Qué hay: 9 campos numéricos del mod (7 tipos de magnitud en 6 archivos) sin guardarraíl de no-negatividad, y un set de errores de tipado preexistentes. Qué se hará: S1, declarar "minimum": 0 en el JSON del mod (el validador del core lo enforcea solo) + codegen + sync + tests; S2, re-baselinear vue-tsc y limpiar los errores propios del mod + gatearlo en CI. Por qué: datos inválidos silenciosos corrompen la malla, y el tipado sin gate vuelve a romperse.

Conceptos clave (las bases)

Seis ladrillos que hacen entendible por qué este ticket es casi todo declarativo. El más importante es el primero (validador del core): entenderlo explica por qué no escribimos lógica de validación.

Validador del core (validateBaseFieldFormats)

Función en object-manager/src/graphql/resolvers/jsonFieldValidator.resolver.js:294 que, a nivel API, enforcea minimum/maximum sobre cada campo escalar leyendo su metadata. Ya vive en el core y corre para todo request GraphQL.

core_FieldDefinition.properties

La tabla donde el core guarda las propiedades de cada campo (incluida minimum). La puebla codegen a partir del JSON del objeto. Es el puente entre "lo que escribo en el JSON" y "lo que el validador aplica en runtime".

Schema-driven (JSON como fuente de verdad)

Los objetos se definen en JSON; codegen deriva Prisma + GraphQL + metadata. Por eso agregar una propiedad al JSON es un cambio declarativo, no imperativo.

RecordType (RT) rt__hijo__base

Sub-tipos de un objeto base (ej. rt__Session__curricularsection). Varios de los campos en alcance (weight, week, duration, hours, totales) viven en RTs, no en el objeto base.

vue-tsc / bucket A vs B

Type-checker de Vue/TS. Los errores del mod se dividen en bucket B (propios del mod, los que este ticket resuelve) y bucket A (ruido del symlink components/ → layout/, que es CORE y queda fuera).

RULE-dev-004 (ownership)

La regla de fronteras: el trabajo layer: mod se edita dentro de mods/curriculum-design/ y el sync lo propaga al core. Nunca se edita el core a mano.

Cómo se valida hoy (y por qué basta con declararlo)

El flujo abajo tiene 4 pasos. La clave que reduce el ticket a "config": la propiedad que escribes en el JSON viaja por codegen hasta la metadata que el validador ya lee en cada request. El validador no distingue el canal, por eso cubre MCP, n8n y bulk (los que saltan la validación de Vueform en el front).

Precedente en uso: restrictiondefinition.json y contractrestriction.json del core ya declaran "minimum": 0 exactamente así. No estamos inventando un patrón, lo estamos extendiendo a los campos del mod que faltan.

El cambio, en concreto

Sobre el bloque del campo en el JSON del mod, se agrega una sola propiedad. Ejemplo con activity.credits:

// mods/curriculum-design/objects/activity.json (campo credits)
{
  "name": "credits",
  "type": "number",
  "minimum": 0          // ← unica linea nueva
}

Se repite para los 7 campos en alcance. Luego npm run codegen (puebla la metadata) y npm run sync (propaga el JSON del mod al core). No hay migración de columna: es validación, el tipo Prisma no cambia.

El entorno: fronteras, exclusiones y una deuda

ℹ Ownership (RULE-dev-004): todo se edita en mods/curriculum-design/. El sync escribe el destino en object-manager/objects/business/Base/: ese destino no se toca a mano. layer: mod se mantiene, cero edición directa de core.
⚠ Excluidos a propósito: version (Activity, Curriculum) y position (planEntry, requirement, CurricularSection, CurricularLink) los pone el sistema (versioning y orden Composite), nunca van negativos. Ponerles guardarraíl sería ruido sobre campos que el usuario no edita.
↩ En P1, no aquí: los RT de requirement (minToSatisfy, creditsRequired, value, thresholdMinGrade) ya recibieron minimum: 0 en TICKET-101 (REQ-09). Este ticket barre el resto. Comparten el external UPONE-1378 pero tocan archivos distintos: sin conflicto.
✗ Deuda de otro repo (BL-1): Offering (maxCapacity, usedCapacity) lo declara uengagement-up1, no este mod. Queda como propagación (DET-16) fuera de alcance, prioridad could con owner uengagement-up1.

El invariante que perseguimos

Ningún campo numérico de input de negocio de la malla acepta valores negativos, sin importar el canal.
Corolario: la garantía vive en el backend (validador del core), no en el front. Un cliente que saltee Vueform (MCP, n8n, bulk) igual queda cubierto. Los campos system-managed quedan fuera por diseño.

El plan: dos sessions

S1 es el corazón del request y es de bajo riesgo técnico (declarativo). S2 es el apartado de deuda, y arranca con una incógnita honesta: el análisis de errores de tipado es del 2026-07-22 y ya envejeció, así que su primera task re-mide el terreno antes de tocar nada.

S1 · No-negativos (T3, gate fuerte)

"minimum": 0 en los 7 campos → codegen → sync (drift 0) → tests de integración por API (negativo rechaza, ≥0 acepta) + smoke en UPU. Independiente de S2.

S2.T1 · Re-baseline de vue-tsc (empírico, bloquea el resto)

Correr vue-tsc --noEmit hoy, regenerar el set real de errores propios (bucket B), excluir el ruido del symlink (bucket A). El conteo "58 errores / 4 clusters" de julio ya no es confiable.

S2.T2+ · Limpieza + gate

Resolver los errores propios sin supresión masiva, y decidir dónde gatear el typecheck (el mod no tiene bitbucket-pipelines.yml propio: hay que ver el pipeline raíz).

Q&A de estudio

¿De qué se trata el caso?
De impedir que campos numéricos de negocio de la malla (créditos, períodos, pesos, horas, semanas, duraciones, totales) acepten valores negativos, más un apartado anexo de limpieza de errores de tipado (vue-tsc) que el mod arrastra.
¿Qué se va a hacer y por qué importa?
S1: declarar "minimum": 0 en el JSON del mod para 9 campos (6 archivos) (el validador del core lo aplica en todos los canales) + codegen + sync + tests. Importa porque un valor negativo silencioso corrompe cálculos de plan y sílabo. S2: re-baselinear y limpiar el tipado + gatearlo en CI, para que la deuda no reaparezca.
¿Qué hipótesis quedaron abiertas y cuál es la más crítica?
Dos, ambas en S2. H6 (la más crítica): el análisis de clusters de tipado es de julio y ya drifteó (un composable desapareció, otro resultó ser de layout), así que el alcance real de S2 solo se conoce tras el re-baseline empírico. H7: el mod no tiene pipeline propio, hay que decidir dónde gatear el typecheck. S1 no tiene hipótesis abiertas.
¿Qué decisiones críticas se tomaron en el intake y por qué?
DEC-INTAKE-01: mantener S1 + S2 en un solo spec (en vez de partir S2 a un ticket propio), con re-baseline de vue-tsc como primera task de S2.
