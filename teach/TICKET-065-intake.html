curriculum (Plan) · Clonar y versionar (superficial v1)

Este caso agrega dos acciones al objeto curriculum (el "Plan" de estudio, entregado por el ticket previo UPONE-1268) del mod curriculum-design de up1: Clonar (sacar una copia independiente) y Versionar (encadenar una nueva versión de la misma entidad). Suenan parecidas pero son semánticamente opuestas, y la diferencia obliga a una regla de unicidad fina que la base de datos no puede expresar sola. Antes de tocar código conviene entender sobre qué nos paramos (el patrón de versionado que ya usa activity), qué nos rodea (la dependencia de UPONE-1268 y la malla planEntry que aún no existe) y hacia dónde vamos (3 sessions, sin tocar core).

TL;DR — Qué hay: el objeto curriculum ya existe con versionado (UPONE-1268), copiando el patrón de activity. Qué se hará: habilitar Clonar (copia independiente, code nuevo, sin previousVersionId) y Versionar (mismo code, encadena previousVersionId), más una validación de unicidad por linaje en el resolver del create. Por qué importa: sin esa regla, clonar con un code ya usado crearía "dos v1" del mismo plan y rompería la identidad de los linajes. Alcance v1 = superficial (solo el Plan, sin arrastrar la malla); el clone profundo se difiere.

Las bases — glosario del caso

Cinco conceptos sostienen todo lo demás. Los dos primeros son del dominio up1 (cómo se modela un plan y su evolución); los tres siguientes son los mecanismos que vamos a reutilizar o extender. Si entiendes estas tarjetas, el resto del teaching encaja.

curriculum (Plan)

El objeto que representa un plan de estudio en el mod curriculum-design. Tiene un code (identificador de negocio), un version y un estado de workflow (nace Draft).

Linaje y previousVersionId

Una cadena de versiones de la misma entidad. La raíz tiene previousVersionId = null; cada versión nueva apunta a la anterior. Todas comparten el mismo code.

prefillFrom + asNewVersion

El mecanismo declarativo (en el JSON del objeto) que ya usa activity: prellena un create desde un registro fuente. Con asNewVersion: true incrementa version y encadena previousVersionId.

prefilledModal

Primitivo de UI (TICKET-052): abre un modal de create prellenado con los escalares de la fuente excepto los uniqueFields (quedan vacíos). No crea nada hasta que el usuario guarda. Copia solo escalares, no hijos.

Unicidad por linaje

La regla de dominio del caso: dos planes distintos (dos raíces) no pueden compartir (institutionId, code). Vive en el resolver del create, no en la DB.

Resolver de dominio

Función backend en logic/ del mod por donde pasan las escrituras de gobernanza (RULE-curriculum-design-003). Es donde colgamos la validación de linaje.

Cómo se encadena una cadena de versiones

Esta es la mecánica que activity ya implementó (TICKET-044, version-only) y que reusamos. Una raíz v1 queda intacta; versionar produce v2 en Draft apuntando a v1, con el mismo code. Clonar, en cambio, abre otra cadena: una raíz nueva con code distinto.

Clonar ≠ Versionar (el corazón del caso)

Las dos acciones parten del mismo gesto (copiar desde una fuente) pero producen entidades de naturaleza distinta. Versionar mantiene la identidad del plan (es la misma cosa, evolucionada); clonar crea una entidad nueva. Esta distinción es la que la regla de unicidad necesita distinguir más abajo.

Versionar

Nueva versión encadenada de la misma entidad.

+ Mantiene el code; incrementa version; setea previousVersionId → v_anterior.

+ Mecánica: prefillFrom + asNewVersion: true.

− No es una raíz → la regla de unicidad no le aplica.

Clonar

Copia independiente: un plan nuevo que arranca en v1 de su propia cadena.

+ Nuevo id, nace Draft, sin previousVersionId, code nuevo.

+ Mecánica: prefilledModal + uniqueFields: ["code"] (modal con code vacío). Excluir code/version/previousVersionId del prefill.

− ES una raíz → la regla de unicidad por linaje sí le aplica.

La regla de unicidad por linaje (condición exacta)

Aquí está el branching que el resolver del create tiene que implementar — y el que la session 2 verificará con tests y mutation testing. Léelo con cuidado: la condición es parcial (solo dispara para raíces). Esa parcialidad es justo lo que la unicidad declarativa de la DB (uniqueScopedBy) no sabe expresar, y la razón por la que la regla vive en el resolver y no en el JSON.

El create de un curriculum se RECHAZA SI Y SOLO SI:
(a) es una raíz (previousVersionId == null) Y
(b) ya existe otra raíz con el mismo (institutionId, code).
Versionar nunca cumple (a) → nunca choca. Clonar con code nuevo no cumple (b) → pasa. Clonar con code ya usado por otra raíz cumple ambas → rechaza.

El invariante que obliga todo esto

El code se comparte entre versiones de un mismo plan → no puede ser @@unique a nivel de fila.
Corolario: el code vacío del modal de clone es solo UX; el enforcement real lo da el resolver de linaje. La integridad de la cadena la sostiene @@unique([previousVersionId, version]) (igual que activity), que es algo distinto a la unicidad de negocio.

Q&A de estudio

¿Por qué la unicidad va en el resolver y no como @@unique o uniqueScopedBy en el JSON?
Porque la condición es parcial: solo aplica a raíces (previousVersionId == null). Las versiones de un mismo plan comparten code a propósito, así que un unique de fila las bloquearía. uniqueScopedBy es declarativo y no soporta la cláusula "solo cuando es raíz". El resolver sí puede expresar el branching (D-D, opción 1; patrón de TICKET-061).
¿Qué distingue, en datos, un clon de una versión recién creada?
La versión mantiene el code de la fuente, incrementa version y setea previousVersionId al registro anterior (no es raíz). El clon tiene code nuevo, version de arranque y previousVersionId = null (es raíz). Por eso la regla de unicidad solo "ve" a los clones.
¿Por qué el clone profundo (arrastrar planEntry) no está en este ticket?
Porque planEntry (la malla) no existe todavía — llega el próximo sprint. Sin hijos que clonar, el deep clone no es testeable ni tiene contrato cerrado (YAGNI). Su diseño ya quedó resuelto (D-E, opción A: extender prefilledModal para disparar deepClone server-side en una transacción) y espera en el Backlog B1.
¿Por qué prefilledModal es seguro para el v1 superficial?
Porque copia solo escalares (typeof v !== 'object') y excluye relaciones/hijos (RecordList.vue:2706 excluye parentId/sourceId/position). En v1 no hay malla, así que "no clonar hijos" es exactamente el comportamiento deseado.
