Programa académico — un objeto nuevo para curriculum-design

Este ticket (externo UPONE-1260) agrega un objeto de negocio nuevo al mod curriculum-design de up1: el programa académico (la carrera — ej. "Ingeniería Civil"). Hoy el mod ya tiene Activity (el programa de asignatura, distinto: es el syllabus de un curso). Lo que se pide es: definir el objeto, que aparezca en el menú de objetos junto a Activity, configurar sus 4 vistas (lista/detalle/crear/editar) y dejar datos precargados (seed). Con un recorte explícito del ticket: en v1 NO hay relación a workflow — es un CRUD plano, sin estados.

TL;DR — Qué hay: un mod (curriculum-design) donde los objetos se definen en JSON; un codegen que genera Prisma + GraphQL desde esos JSON; y un menú que se arma solo desde defaultObjects + layouts. Qué se hará: agregar AcademicProgram.json (CRUD plano, sin workflow), 4 layouts, i18n y seed; correr npm run sync. Por qué: el modelo de objetos de negocio (Learning Assurance) define la carrera como entidad raíz; este es su primer incremento, deliberadamente mínimo (sin workflow) para entregar valor visible rápido y de forma reversible.

Conceptos clave (las bases)

Antes de tocar nada conviene tener claros seis ladrillos del dominio. Los dos primeros son el corazón: distinguir AcademicProgram de Activity (se confunden por el nombre), y entender que en este mod un "objeto" es un archivo JSON, no una clase de código.

AcademicProgram

La carrera / programa académico (ej. "Ingeniería Civil"). Entidad raíz que en el modelo completo agrupa planes de estudio. Es lo que creamos.

Activity

El programa de asignatura (el syllabus de un curso). Ya existe en el mod. NO es lo mismo que la carrera — una asignatura puede aparecer en varias carreras.

Objeto del mod (JSON)

Un archivo en objects/*.json con metadata (labels, constraints) y properties (campos). Es la fuente de verdad del modelo.

codegen / sync

npm run sync (desde object-manager) lee los JSON, genera el schema Prisma + GraphQL, migra la BD y corre los seeds. Sin esto, el objeto no existe en runtime.

Layout

JSON en config/layouts/ que describe una vista (list/view/create/edit) de un objeto. El layout-engine lo renderiza; no escribimos componentes Vue.

defaultObjects

Array en config/app.json. Lo que listamos ahí es lo que aparece en el menú de objetos (ObjectNavBar). Así Activity está en el menú hoy.

Cómo encaja un objeto en el sistema

El flujo de abajo muestra el camino completo de un objeto del mod, desde el JSON que escribimos hasta que el usuario lo ve en el menú. Lo importante: una sola fuente (el JSON) alimenta tres salidas (modelo de datos, API y UI). Por eso "agregar un objeto" no requiere tocar código de la suite ni del object-manager — solo declarar JSON y correr el sync.

Avisos del entorno (lo que rodea el caso)

El riesgo de este ticket no es de lógica de negocio (es CRUD) sino de pipeline. Tres restricciones del entorno que más de un dev de up1 ha aprendido a golpes:

✗ PascalCase o no hay deploy — RULE-platform-006 (norma must): el objeto debe llamarse AcademicProgram (no academicProgram) en title, filenames de layouts, objectName y defaultObjects. Una sola minúscula rompe el codegen en Linux.
⚠ Reiniciar object-manager tras el sync — no hay hot-reload de los typedefs del mod. Si no reinicias, la suite muestra "Error al cargar AcademicProgram" aunque el archivo esté correcto en disco.
ℹ El select de FK no filtra por recordType — los campos governanceUnitId/executionUnitId apuntan a OrgUnit, pero fetchRelationOptions no acepta filtros: el select mostrará TODOS los OrgUnits. Tolerado en v1 (campos opcionales) → quedó como Backlog B1.

La decisión que define v1: sin workflow

La única decisión de peso del intake es cómo manejar el estado del programa. El modelo canónico de Confluence le da a academicProgram dos campos requeridos (workflowId + currentStatusId) que lo conectan a la máquina de estados configurable. El ticket pide explícitamente no incluir eso en v1. Hay un precedente directo en el proyecto: DECISION-005 (cuando Activity difirió workflow en SP1, usó un enum provisional). Lo registramos como alternativa pero se descartó.

Contexto

El objeto canónico exige workflow; el ticket lo recorta para v1. ¿CRUD plano sin estado, o enum provisional tipo Activity (DECISION-005)?

Decisión (approach v1)

CRUD plano: sin workflowId/currentStatusId y sin campo de estado. Confirmado con el dev.

Por qué

Es lo que pide el ticket literal; BibliographyReference prueba que un objeto del mod vive bien sin estado y sin resolver custom. Reversible: agregar workflow después es aditivo.

La definición propuesta

Así se ve el objeto que vamos a crear (campos descriptivos + FKs + enums cerrados, sin workflow). El uniqueConstraints compuesto el codegen lo traduce solo a @@unique en Prisma (verificado en generatePrismaSchema.js). 

// objects/AcademicProgram.json (forma propuesta — plantilla: BibliographyReference)
{
  "title": "AcademicProgram",
  "metadata": {
    "label": "Programa académico",
    "labelPlural": "Programas académicos",
    "defaultLayoutType": "RecordList",
    "uniqueConstraints": [["institutionId", "code"]]
  },
  "properties": {
    "name":    { "type": "string", "not_null": true },
    "code":    { "type": "string", "not_null": true },
    "degree":  { "type": "string", "not_null": true, "enum": ["Bachelor","Master","Doctorate","Technical"] },
    "modality":{ "type": "string", "not_null": true, "enum": ["InPerson","Online","Hybrid"] },
    "nominalDuration": { "type": "number" },
    "institutionId":    { "type": "string", "not_null": true, "isForeignKey": true, "references": "Institution" },
    "governanceUnitId": { "type": "string", "isForeignKey": true, "references": "OrgUnit" },
    "executionUnitId":  { "type": "string", "isForeignKey": true, "references": "OrgUnit" },
    "externalId": { "type": "string" }
  },
  "required": ["name","code","degree","modality","institutionId"]
}

Q&A para arrancar con contexto

¿Por qué AcademicProgram y Activity son objetos distintos si ambos son "programas"?
Porque modelan cosas diferentes: AcademicProgram es la carrera (contenedor de planes de estudio); Activity es el programa de asignatura (el syllabus de un curso). Una misma asignatura puede pertenecer a varias carreras. En v1 son independientes — no hay relación entre ellos todavía.
¿Qué archivos toco y cuáles NO?
Tocas solo el mod curriculum-design: objects/AcademicProgram.json, 4 layouts, lang/es_CL@AcademicProgram.json, config/app.json y el seed. NO editas código de object-manager ni de suite — el codegen genera Prisma/GraphQL y el menú se arma solo desde defaultObjects.
¿Cuál es la hipótesis más crítica y ya está verificada?
H1: "definir JSON + layouts + defaultObjects basta, sin tocar otros repos". Ya está confirmada en intake (multi-capa: useObjectManager arma el menú; generatePrismaSchema genera el modelo; BibliographyReference es la prueba de un CRUD sin workflow). El riesgo residual es de pipeline (PascalCase, restart), no de diseño.
¿Qué decisión crítica se tomó y por qué?
Hacer el objeto CRUD plano sin workflow en v1 (en vez del enum provisional de DECISION-005). Razón: es lo que pide el ticket, es reversible, y no requiere resolver custom. Ver el bloque "decisión clave".
¿El select de unidad organizativa mostrará lo correcto?
No del todo: mostrará todos los OrgUnits sin filtrar por recordType (limitación del layout-engine, H5 refutada). Es aceptable en v1 porque governanceUnit/executionUnit son opcionales. El filtrado quedó como Backlog B1 (should).
