Detalle/clonado de Curriculum y UX de la lista de planes de estudio

Ticket: TICKET-075 (UPONE-1270) · Spec: SPEC-curriculum-design-fix-recordtype-fields-in-read · Módulo: curriculum-design (mod) · Sessions: 2 · Teach close generado al cerrar.

Cómo leer este teach: este archivo cuenta el caso ya resuelto. Si solo lees TL;DR y La historia, ya tienes el núcleo. El resto profundiza por capas. Pares con el teach-intake: intake = "el terreno antes de tocar"; close = "qué aprendimos".

TL;DR

Al ver el detalle, editar o duplicar un plan de estudio, los datos propios de su tipo (créditos, periodos, progresión) no aparecían. Ahora sí se muestran y se arrastran al duplicar y al crear nuevas versiones. Además, al crear una nueva versión de un plan la pantalla te lleva a la vista de detalle (antes te dejaba en el formulario de edición), y se quitó la opción de borrar planes (un plan se versiona, no se elimina).

La historia

Un plan de estudio tipado (recordType Plan) se crea con datos que el tipo exige: progresión, créditos totales, periodos, tipo de periodo. El síntoma reportado: esos datos se guardaban bien, pero al ver el detalle no aparecían y al duplicar no se prellenaban. El caso importaba porque la creación ya funcionaba — la asimetría confundía al usuario (creo un dato que después "desaparece").

El intake confirmó la causa raíz cruzando capas (DET-5 — la regla de no confirmar una hipótesis desde una sola capa): esos 4 campos no son columnas de la tabla base curriculum; viven en una extensión 1:1 rt__Plan__curriculum. La creación y el guardado ya ruteaban por el alias de esa extensión (trabajo de TICKET-074), pero el read genérico operaba sobre la base "Curriculum" y nunca incluía la extensión. Por eso ver/editar/duplicar llegaban vacíos en esos campos.

La decisión central fue cómo resolver el read. Ver no podía ser "mutation nueva + customEndpoint" como hicieron create/update, porque el front no soporta customEndpoint en lectura. La salida limpia: un override mod-only de getInstance y listInstances que delega al branch de RecordType del resolver genérico (reuso, no replicación — DET-32). Aparecieron dos sorpresas durante execute que ajustaron el plan: (1) el delegate incondicional rompía los planes v2 versionados que no tenían fila de extensión — daba "Record Not Found"; se agregó un fallback al read base. (2) Se descubrió, ya en ejecución, que el versionado no heredaba la extensión; se resolvió mod-only con un post-create hook (scope-expansion aprobada por el dev).

Cerrando el caso, el dev pidió dos ajustes de experiencia sobre la lista de planes (Session 2, config-only): que versionar lleve al detalle y no al edit, y ocultar "Eliminar". Ambos resultaron ser dos valores en el JSON del layout, sin código nuevo — porque los mecanismos (redirectTo: 'view' y canDelete: false) ya existían en el layout-engine.

What was done — síntesis ejecutiva

Mod-only sobre curriculum-design, sin tocar core (object-manager) ni el código del front. S1: nuevo override de lectura logic/curriculum-read.resolver.js (getInstance + listInstances → branch RT con fallback al base) y un post-create hook en logic/sectionValidation.resolver.js que copia la extensión rt__<RT>__curriculum del source a la v2 al versionar; +22 unit tests. S2: dos valores en config/layouts/default_Curriculum_list.json (redirectTo edit→view, canDelete true→false), aplicados a la DB del tenant vía sync. Efecto observable: ver/editar/duplicar/versionar muestran y arrastran los campos del tipo; versionar abre el detalle; la lista ya no ofrece borrar.

Hay 2 snippets core. El primero es el corazón del fix de S1: el override de lectura con el fallback que evitó la regresión. El segundo es el cambio de S2 — config, no código — que muestra lo barato que salió la UX.

1 · Override de lectura con fallback (S1)

Rol: curriculum-read.resolver.js es el único archivo del mod que exporta getInstance/listInstances (un campo por archivo — el loader hace Object.assign y el último pisa). Entender este contrato importa antes de leer el código: el mod gana sobre core porque resolverIndex.js expande los resolvers del mod al final.

después (estado final en el mod)
// getInstance override: solo Curriculum entra al delegate-con-alias; el resto delega tal cual.
if (objectType === 'Curriculum' && recordType) {
  try {
    const viaAlias = await generic.getInstance(parent,
      { objectType: `rt__${recordType}__curriculum`, id }, ctx, info);
    if (viaAlias) return viaAlias;        // trae la extensión RT
  } catch (e) { /* alias lanzó: degradar al base (BUG-2) */ }
  return generic.getInstance(parent, { objectType: 'Curriculum', id }, ctx, info); // fallback: v2 sin extensión no da Record Not Found (L1)
}
return generic.getInstance(parent, args, ctx, info);   // no-Curriculum: delega sin tocar

El failed approach que originó el fallback: el delegate incondicional (sin el bloque try/return base) daba "Record Not Found" en un Plan v2 versionado cuya fila de extensión no existía. El branch RT del genérico hace findFirst sobre la extensión y devuelve null si no está.

2 · UX de la lista (S2) — config, no código

Rol: default_Curriculum_list.json es el layout de la lista; se sincroniza a la tabla up1_layen_layout del tenant. El front lee de esa tabla por request — por eso el cambio no necesita restart de OM, solo el sync.

Lessons learned — para casos futuros

Qué es: lo que el dev futuro debería llevarse.
Cómo te afecta: leerlas en el intake del próximo ticket del módulo ahorra trabajo.
Por qué mirarla: condensa los ejes 2 y 4 desde el cierre.
  • El read del genérico no resuelve extensiones RecordType por la base (de H2 confirmada): si un objeto tiene extensión 1:1 rt__<RT>__<base>, ver/editar/listar por la base llega vacío. Aplicable a cualquier objeto tipado del mod, no solo Curriculum.
  • Delegate-con-alias SIEMPRE necesita fallback al base (de failed approach #1): el branch RT devuelve null cuando la fila de extensión no existe (registros viejos, v2 sin heredar). Sin fallback → "Record Not Found". Vale para cualquier override de lectura que rutee por alias.
  • "Es core" puede ser un falso límite (de H7 revisada): la herencia de la extensión al versionar se resolvió mod-only con un post-create hook. Antes de diferir scope a core, buscar si un hook en el mod lo cubre.
  • Antes de codear una conducta de UI, mirar si es config (de S2): navegación post-acción (redirectTo) y visibilidad de delete (canDelete) son flags del layout-engine. Dos líneas de JSON evitaron código.
  • Verificar el path UI, no solo los datos (de L2): el dato correcto en DB prueba el backstop, no que el usuario lo vea. Cerrar TCs con Affects UI exige confirmación en la suite.

Learning path para retomar el caso

Qué es: orden de lectura para un dev que retome el read del mod o agregue un RecordType.
Cómo te afecta: ruta al caso resuelto, no onboarding general.
Por qué mirarla: el aprendizaje vale más cuando se reusa.

4 steps. El step 1 es no-negociable: sin entender el modelo base/extensión, el resto queda en el aire.

  1. Modelo base + extensión RT — por qué los 4 campos viven en rt__Plan__curriculum y no en la tabla base. Refs: schema model rt__Plan__curriculum, teach-intake. (~10 min)
  2. El override de lectura — logic/curriculum-read.resolver.js: delegate-con-alias + fallback. Por qué un override y no customEndpoint. (~10 min)

  4. UX por config — config/layouts/default_Curriculum_list.json y cómo el sync (PHASE 5) lo lleva a up1_layen_layout. (~5 min)
