6 · Lecciones para tickets futuros

Una regla de negocio vive en varias capas: la UI no la sincroniza al MCP
El layout del suite y el contrato del up1-mcp son capas distintas y el MCP se mantiene a mano, ticket por ticket. Cuando un ticket introduce una regla observable (visibilidad, requeridos, RBAC), preguntar explicitamente si tambien debe reflejarse en el MCP. Idealmente, agregar una task "paridad MCP" al planificar, no descubrirla al cierre.
El smoke revela dependencias del entorno que la revision estatica no ve
El fix era trivial, pero recorrer la UI real destapó el seed corrupto de progression y el gap de RBAC de instituciones. DET-36 (evidencia runtime) valio la pena: sin el smoke esos dos hallazgos no aparecen.
Verificar el persistido, no solo el render
TC-6 no se dio por bueno con "el campo se oculto": se guardo y se leyo la DB (progression=Modular, totalPeriods=8 retenido). Confirmar la escritura por el path real del usuario evita consagrar un bug de runtime.
Paridad != duplicar la UI: mirror del comportamiento, no del mecanismo
La UI oculta el campo; el MCP no tiene UI, asi que la paridad correcta es rechazar la combinacion invalida (Modular + periodos) en la API, resolviendo la progresion actual cuando el update es parcial. Mismo efecto de negocio, mecanismo propio de cada capa.
