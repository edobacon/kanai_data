La maquina de estados debe resolver el alias RecordType a la PK base

Cuando un usuario abre el detalle de una matriz de competencias para operar su ciclo de vida (Borrador, En revision, Aprobada...), el backend deberia devolver las transiciones validas del estado actual. Hoy, en lugar de eso, los resolvers de la maquina de estados (getValidTransitions y previewBulkTransition) revientan con Unknown argument 'id'. Este intake arma el mapa del problema antes de tocar codigo: es la misma clase de defecto que el Caso A de este mismo Jira (previews de borrado), pero en otra superficie: un alias de RecordType que no se resuelve a su PK base.

TL;DR   Que hay: los resolvers de la maquina de estados reciben el alias rt__<Rt>__<base> y leen el registro con where: { id }; la tabla de proyeccion no tiene id (su PK es la FK <base>Id) → Prisma rechaza el argumento. Por que importa: la vista de la matriz no puede leer ni operar sus transiciones; y al partir del objeto base tampoco sirve, porque el estado y la metadata viven en la proyeccion, no en el base. Que se hara: keyear por <baseLower>Id cuando el objeto es RecordType, reutilizando el helper resolveRecordTypeToBaseObject que entrega el Caso A (TICKET-129). Por que asi: es la misma resolucion alias→base que el resto del motor ya aplica; no es logica nueva, es llevar la maquina de estados a paridad.

Las bases — el piso conceptual

Para entender el bug hay que tener claros cuatro ladrillos de como funciona HOY la maquina de estados sobre RecordTypes.

RecordType (alias de presentacion)

Una matriz de competencias no es un objeto propio: es un RecordType de CompetencyNode, listado como rt__Matrix__competencynode. Su metadata y su campo status (con las transitions) viven en la proyeccion; el objeto base CompetencyNode no tiene status.

Tabla de proyeccion sin id

La tabla fisica rt__<Rt>__<base> no tiene columna id: su clave primaria es la FK al objeto base (competencynodeId). Cualquier query que filtre por id sobre ella es invalida.

Maquina de estados

getValidTransitions y previewBulkTransition (en objectDefinition.resolver.js) leen el registro para saber su status actual y calcular a que estados puede pasar. Ambos asumen que el modelo tiene columna id.

La isla sin tratamiento RT

El motor de borrado (instance.resolver.js) ya sabe resolver el alias a base. La maquina de estados, en otro archivo, quedo fuera de ese tratamiento: nunca recibio la resolucion RT-aware.

Como falla hoy — el flujo

El layout puede apuntar al RT o al objeto base, y ninguno de los dos caminos sirve: uno crashea, el otro pierde los datos.

flowchart TB
  U[Vista de matriz pide transiciones del status] --> D{Layout apunta a...}
  D -- rt__Matrix__competencynode --> G[getValidTransitions lee findUnique where id]
  G --> X[La proyeccion no tiene columna id]
  X --> E[Unknown argument id - INTERNAL_SERVER_ERROR]
  D -- CompetencyNode base --> B[findUnique where id no crashea]
  B --> L[Pero status y metadata viven en el RT, no en el base]
  L --> Z[Registro sin datos - no hay workaround por el base]

El entorno — que rodea el caso

ℹ Origen (UPONE-1537) — El crash aparecio armando la vista de edicion de las matrices de competencia (mod curriculum-mapping). El dev reporto: al partir del RT, la metadata y el estado cargan pero la maquina de estados falla; al partir del base, no falla pero se pierden los datos. Esa observacion es la que destapo el defecto de core.
ℹ Hermano de Caso A (mismo Jira UPONE-1608) — El Caso A resuelve el alias RT en los previews de borrado (TICKET-129) y extrae el helper resolveRecordTypeToBaseObject. Este Caso B es la misma causa raiz en la maquina de estados y consume ese helper. Por eso este ticket depende de TICKET-129.
⚠ Antecedente (UPONE-1479) — Ese ticket resolvio la clase de alias en el path de borrado real. Ni el preview (Caso A) ni la maquina de estados (Caso B) recibieron el tratamiento entonces. No es idea nueva: es aplicar una resolucion ya probada donde falto.
✗ Trampa a evitar — Resolver el alias con un startsWith('rt__') o cortando el string a mano. El casing del base no es derivable del nombre: hay que resolverlo por introspeccion (core_ObjectDefinition), igual que el resto del motor. El parser parseRecordTypeParentName ya existe en el mismo archivo, sin usar en estos resolvers.

La regla que gobierna el fix

El nombre de un RecordType es un alias de presentacion: hay que resolverlo a la PK del objeto base antes de leer el registro.
RULE-core-043 (nacida de UPONE-1479). Corolario: todo entrypoint que lea un registro para decidir sobre el (borrar, previsualizar, o transicionar su estado) debe resolver primero. Un resolver que consulta la proyeccion por id esta consultando una columna que no existe.

El patron que ya existe (a reutilizar)

Esto es lo que instance.resolver.js ya hace para keyear un RecordType por su PK real. El fix aplica la misma tecnica en getValidTransitions y previewBulkTransition, consumiendo el helper del Caso A.

// detectar si el objeto es un alias de RecordType y keyear por su PK real
const rtMatch = objectName.match(/^rt__(.+)__(.+)$/);   // -> [_, rtName, baseLower] | null
const pkWhere = rtMatch
  ? { [`${rtMatch[2]}Id`]: coerceId(recordId) }   // RT: <baseLower>Id (ej. competencynodeId)
  : { id: coerceId(recordId) };                    // base: id

const rawRecord = await prisma[modelName].findUnique({ where: pkWhere, ... });

coerceId ya tolera la PK string tipo cuid del RT (Number(cuid) es NaN y devuelve el string), asi sirve para RT y base. El include de la extension ya funciona; el unico punto roto es el where.

Q&A de estudio

Si al partir del objeto base CompetencyNode no crashea, ¿por que no usar eso como workaround?
Porque el status y toda la metadata de la matriz viven en la proyeccion rt__Matrix__competencynode, no en el base. Al leer el base no crashea, pero el registro no tiene el estado ni las transiciones que la vista necesita. No hay atajo por el base: hay que resolver el alias a su PK y leer la proyeccion.
¿Por que este caso entra en el mismo Jira que los previews de borrado (Caso A)?
Porque es la misma causa raiz: un alias de RecordType que no se resuelve a su PK base, y un resolver que asume where: { id }. Difieren en la superficie (borrado vs maquina de estados) y en el archivo, pero comparten el helper de resolucion. En DKC se ejecutan como dos tickets separados (129 y 131) bajo un solo Jira, patron 1 Jira a N.
¿Por que depende de TICKET-129 y no se hace independiente?
Porque el Caso A extrae el helper resolveRecordTypeToBaseObject como unica fuente de verdad de la resolucion alias a base. Este ticket lo consume en vez de duplicar el bloque. Si 131 corriera antes, tendria que crear su propia copia y luego reconciliarla. Por eso 129 primero.
¿Por que la validacion pide BD real y no alcanza con unit tests?
Porque la lectura depende del shape real de la proyeccion (PK competencynodeId, no id) y de la introspeccion del casing. Un Prisma mockeado puede dar verde con datos que no reflejan ese shape y consagrar el bug (RULE-core-034 / RULE-dev-test-real-shape-not-mocked).
