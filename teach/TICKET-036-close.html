La historia del caso

Contexto (lo que creíamos)

El intake asumió firma createInstance(objectType, data) y que prefillFrom sería un 3er argumento GraphQL nuevo, con cambio de SDL.

Decisión (al ver el código)

En S1, al leer el resolver real, apareció que prefillFrom YA existe dentro de data (033/HU-0d, shape {source, deepClone, exclude}, clona hijos). Se pivoteó: extender ese mecanismo, sin arg GraphQL.

Resultado

Helper que pre-llena los campos propios del source; coexiste con deepClone. 11 TCs + 457 de regresión verdes. Spec reorientado y revalidado.

Qué se construyó (el shape final)

Un helper puro y aislado (testeable sin mockear todo el resolver), llamado desde createInstance justo antes de prepareLayoutCreationData para que los campos pre-llenados fluyan por el pipeline normal. 

// helpers/prefill-from-source.js — gated, tenant-safe, aditivo
export async function applyPrefillFromSource({ prisma, objectType, data, prefillFrom }) {
  if (prefillFrom?.source == null) return data;        // REQ-01 gating
  const model = resolvePrefillModel(prisma, objectType);
  if (!model) throw new Error('PREFILL_SOURCE_TYPE_MISMATCH');  // REQ-02
  const source = await prisma[model].findUnique({ where: { id: srcId } }); // REQ-04 tenant-scoped
  if (!source) throw new Error('PREFILL_SOURCE_NOT_FOUND');     // REQ-02
  // REQ-03: explicit pisa source; default exclude + caller exclude
  return { ...prefilledFields, ...data };
}

Lecciones aprendidas

L1 — Leer el código real antes de confiar en el intake

El intake puede traer supuestos desactualizados. prefillFrom ya existía; verificarlo en S1 evitó construir un arg GraphQL en conflicto.

L2/L3 — Conocer el modelo de tenancy y de tipos

Tenancy por client scoped (no columna); el tipo es la tabla. Ambos cambiaron la implementación de REQ-04 y la semántica de los errores.

L4 — Los specs DKC deben vivir dentro de deckard

El symlink specs → external dejaba los specs sin versionar. Se migraron 28 specs a dir real + RULE-dev-005.

L5 — No materializar bloques de session futuros

HC infiere estado por el bloque Gate decision; sessions futuras sin él se ven in_progress. Materializar lazy con open-session.

Q&A de cierre

Si voy a construir HU-2 (prefillFrom declarado en JSON), ¿desde dónde parto?
Desde el mismo objeto data.prefillFrom. HU-1 dejó source + exclude para campos propios; 033 dejó deepClone para hijos. HU-2 leerá la declaración del JSON del objeto y la mapeará a este shape. El helper prefill-from-source.js es el punto de extensión.
¿Qué quedó como deuda/residual?
(1) OQ-1: si se quiere distinguir cross-type de NOT_FOUND con un check explícito de tipo (más costoso) en vez de colapsar a NOT_FOUND. (2) ticket-030 (cerrado) referencia un spec inexistente SPEC-012 — colgante pre-existente, spawneado como tarea aparte.
¿Por qué un helper y no inline en el resolver?
Testeabilidad: el resolver está envuelto en withEventPublish/withObjectAuth y depende de muchas etapas. Un helper puro se testea en aislamiento (11 TCs) — mismo patrón que deep-clone-polymorphic.js de 033.
