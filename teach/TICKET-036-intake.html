HU-1 · prefillFrom en createInstance

up1 está construyendo una capacidad de clonación de objetos (épica Jira UPONE-1206): poder crear una instancia nueva pre-llenada a partir de otra existente. Este ticket entrega el primer ladrillo de esa capacidad — el primitivo más bajo y transversal. La pieza que se toca es createInstance, que en up1 no es "un resolver más": es el único punto de creación CRUD de toda la plataforma (todos los objetos de todos los tenants se crean por ahí). Por eso un cambio aquí parece pequeño en líneas pero es delicado en alcance: lo consumen ≥12 callers repartidos en 4 capas. El trabajo consiste en agregarle un parámetro opcional prefillFrom sin alterar en nada el comportamiento que ven los callers actuales.

TL;DR — Qué hay: createInstance(objectType, data) es el resolver genérico de creación de la plataforma (instance.resolver.js:2145), extensible con args opcionales. Qué se hará: agregarle un 3er argumento opcional prefillFrom: PrefillFromInput que, cuando viene, copia los campos de un objeto fuente del mismo tipo y los combina con los explícitos (lo explícito pisa). Por qué: es el primitivo de clonación reusable — habilita "duplicar objeto" sin escribir un resolver custom por cada tipo, reusando validación, RBAC y hooks que ya existen.

Las restricciones que enmarcan el cambio

Antes de tocar nada conviene tener presentes los tres límites que el intake dejó fijados. No son detalles: son las paredes contra las que se va a chocar cualquier implementación que se desvíe del plan.

✗ Gating estricto, no negociable — createInstance tiene ~64 callers (≥12 confirmados en 4 capas). Si prefillFrom llega null/ausente, el código nuevo NO debe ejecutarse: el caller existente tiene que ver comportamiento idéntico al de hoy. El cambio se "enciende" solo por presencia del parámetro.
⚠ Es código core (RULE-dev-004) — object-manager es un workspace core: lo consumen todos los mods y tenants. RULE-dev-004 (regla de up1 que obliga a agrupar el trabajo core de una épica en una sola rama revisable antes de tocar develop) aplica. El commit va a la rama de la épica; el merge a develop lo decide el team up1, no el cierre del ticket.
ℹ Alcance acotado: solo el parámetro básico — este ticket entrega prefillFrom como argumento explícito de la mutation. El prefillFrom declarado en el JSON del objeto (con deepClone de hijos polimórficos) se construye encima de esto en otros tickets (HU-2 / HU-0d). No es trabajo de hoy.

Las bases: el vocabulario del caso

Estos cinco conceptos son el piso. Sin ellos, el cambio no tiene contexto: explican qué es la pieza que se toca, por qué se puede extender sin romper, y qué reusa.

createInstance

El resolver genérico de creación de objetos. Único punto CRUD de creación de la plataforma — no hay createXxx por tipo. Hace dispatch dinámico vía prisma[objectType]. Firma actual: createInstance(objectType: String!, data: JSON!).

prefillFrom (lo nuevo)

El parámetro opcional que se agrega: { sourceId, includeRelations? }. Cuando viene, lee el objeto sourceId, valida que es del mismo tipo, y pre-llena data con sus campos. Es un "duplicar desde" genérico.

Gating por presencia

Patrón típico de Apollo Server: un argumento nullable cuya ausencia hace que la rama de código nueva se ignore. Es la herramienta que garantiza compatibilidad con los callers existentes.

withObjectAuth / RBAC

El middleware de autorización (withAuth.js:122,129). Lee solo args.objectType para resolver permisos → es insensible a argumentos nuevos. Por eso agregar prefillFrom no altera la autorización.

Etapas compartidas

prepareLayoutCreationData (:2161), validación JSON (:2307) y lookup de objectDefinition (:2313). Son agnósticas al origen de los datos → el data pre-llenado pasa por las mismas que el data explícito. Esto es lo que hace seguro reusar el resolver.

Default exclude

Los campos que NO se copian del source al pre-llenar: id, createdAt, updatedAt, createdBy. Son identidad/auditoría — la instancia nueva debe generarlos frescos, no heredarlos.

El invariante que no se puede romper

Todo el diseño se subordina a una sola garantía. Si el dev que ejecuta se lleva una idea de este teaching, que sea esta — es el criterio contra el que se mide el éxito de la S2 (regression de callers).

Una llamada a createInstance sin prefillFrom debe comportarse exactamente como hoy.
Corolario: el código de prefillFrom vive entero dentro de un guard if (prefillFrom?.sourceId) { … }. Fuera de ese branch, ni una línea cambia. La validación de la S2 no es "los tests nuevos pasan" — es "los 64 callers existentes no notan nada".

El shape: SDL + el guard del resolver

Dos piezas de código son el corazón del cambio. La firma GraphQL (SDL) en typeDefs/static.js:1145-1150 — donde se declara el nuevo input y el 3er argumento opcional. Y el guard en el resolver (instance.resolver.js:2145) — el bloque condicional que materializa el invariante de arriba. El pseudocódigo es la intención de diseño del intake; los nombres exactos (p.ej. cómo se lee el tipo del source) se confirman en S1. 

# SDL — typeDefs/static.js
input PrefillFromInput {
  sourceId: ID!
  includeRelations: Boolean = false
}

type Mutation {
  createInstance(
    objectType: String!,
    data: JSON!,
    prefillFrom: PrefillFromInput   # nuevo, opcional
  ): InstanceResult
}
// resolver — guard gated (pseudocodigo del intake)
async function createInstance(objectType, data, prefillFrom = null) {
  // ... etapas compartidas existentes ...
  if (prefillFrom?.sourceId) {
    const source = await prisma[objectType].findUnique({ where: { id: prefillFrom.sourceId } });
    if (!source) throw new Error('PREFILL_SOURCE_NOT_FOUND');
    if (source._objectType !== objectType) throw new Error('PREFILL_SOURCE_TYPE_MISMATCH');
    const exclude = new Set(['id', 'createdAt', 'updatedAt', 'createdBy']);
    const prefilled = Object.fromEntries(
      Object.entries(source).filter(([k]) => !exclude.has(k))
    );
    data = { ...prefilled, ...data };   // explicit pisa source
  }
  // ... resto del flujo de create (igual al actual) ...
}

El entorno: dos formas de llamar al mismo resolver

La mejor forma de internalizar el gating es ver las dos llamadas lado a lado. Misma firma, mismo resolver, mismas etapas compartidas — la única diferencia es la presencia del 3er argumento. Esto es lo que el dev debe poder explicar antes de tocar código.

Caller existente (los ~64 de hoy)

createInstance(objectType, data)

+ No cambia: prefillFrom es undefined, el guard no entra.

+ RBAC, validación, hooks: idénticos.

− Riesgo si el guard se escribe mal (p.ej. condición que entra con prefillFrom = {} vacío) → rompería a todos. De ahí la regression de S2.

Caller nuevo (clonación)

createInstance(objectType, data, { sourceId })

+ Pre-llena desde el source; data explícito sobreescribe.

+ Errores claros si el source no existe o es de otro tipo.

− includeRelations (GraphQL) vs deepClone (JSON declarativo): el clonado profundo de relaciones es de tickets posteriores; en este solo se define el campo, sin lógica de deep-clone.

Hacia adelante: el plan (3 sessions, ~1 SP)

El ticket está preplanificado en 3 sessions. La crítica es la S2: ahí vive el gate fuerte de regression, que es donde se demuestra que el invariante se respeta. S1 construye, S2 prueba (y defiende a los 64 callers), S3 cierra.

S1 — resolver + SDL (tier T2, gate auto)

Agregar PrefillFromInput + param opcional en el SDL; implementar el guard gated con validación de source y los dos errores. Tests básicos verdes.

S2 — tests exhaustivos + regression (tier T2, gate ⚑ fuerte)

Unit + integration: prefill básico, override explícito, cross-type rechazado, source inexistente. Y la clave: regression de callers existentes — sin prefillFrom, cero cambio.

S3 — cierre (tier T1, gate auto)

Quality review final, commits granulares (DET-27) en la rama de la épica, teach-close. Tests verdes.

Autoevaluación (la barra de éxito del intake)

Si puedes responder estas cuatro sin volver a leer, tienes el mapa mental que el intake buscaba dejar.

¿De qué se trata el caso?
Agregar un parámetro opcional prefillFrom al resolver genérico de creación createInstance, para crear una instancia pre-llenada desde otra del mismo tipo. Es el primer ladrillo (el primitivo transversal) de la capacidad de clonación de objetos de up1 (épica UPONE-1206).
¿Qué se va a hacer a alto nivel y por qué importa?
Extender la firma con prefillFrom: PrefillFromInput (SDL) y un guard gated en el resolver que lee el source, valida existencia + tipo, y combina campos (explícito pisa source, con un exclude de identidad/auditoría). Importa porque createInstance es el único punto CRUD de creación de la plataforma: hacerlo bien da clonación reusable a todos los tipos sin resolvers custom; hacerlo mal rompe los ~64 callers existentes.
¿Qué quedó abierto y qué es lo más crítico de verificar primero?
Lo más crítico: confirmar en S1 cómo se lee el tipo del objeto fuente (el pseudocódigo asume source._objectType, pero el dispatch real es prisma[objectType] — hay que verificar el nombre/forma exacta del campo de tipo en el row). Segundo abierto: la relación entre includeRelations (GraphQL) y el deepClone declarativo del JSON — en este ticket el campo se define pero el deep-clone real es de HU-2/HU-0d.
¿Qué decisiones críticas se tomaron en el intake y por qué?
La decisión de fondo: no escribir un resolver custom de clonación, sino extender el genérico con un arg opcional gated. Por qué: reusa validación, RBAC y hooks ya existentes, y mantiene un único punto CRUD. La alternativa (resolver por tipo) habría duplicado lógica y multiplicado superficie de ataque. El gating por presencia del parámetro es lo que hace viable esa extensión sin riesgo para los callers.

Dónde encaja en la épica de clonación

Este ticket es el ladrillo base. Lo que viene después se apoya en el parámetro que aquí se crea — útil para no sobre-construir hoy.
