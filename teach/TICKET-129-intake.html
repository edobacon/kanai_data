Los previews de impacto de borrado deben resolver el alias RecordType a objeto base

Cuando un usuario abre el modal de confirmacion para borrar filas de un catalogo gobernado por un RecordType (por ejemplo un esquema de niveles), el backend deberia devolver cuantos registros se afectan y que referencias lo bloquean. Hoy, en lugar de eso, los dos previews de impacto (deleteImpactPreview y softDeleteImpactPreview) revientan con un PrismaClientValidationError. Este intake arma el mapa del problema antes de tocar codigo: sobre que bases se apoya, que lo rodea, y por que la correccion es replicar una resolucion que el borrado real ya hace.

TL;DR — Que hay: los previews reciben el alias rt__<Rt>__<base> y consultan la tabla de proyeccion por id, columna que no existe (su PK es la FK <base>Id) → Prisma lanza. Por que importa: no es bloqueante (el front degrada a texto estatico y el borrado real revalida), pero se pierde la barrera de aviso y ensucia el log del OM en cada apertura del modal. Que se hara: resolver el alias al objeto base antes de invocar el motor de impacto, en los dos previews, extrayendo a un helper la resolucion que deleteBulkInstances ya hace (UPONE-1479). Por que asi: la metadata que gobierna el borrado vive en el objeto base, no en la proyeccion; es paridad con el path de borrado, no logica nueva.

Las bases — el piso conceptual

Para entender el bug hay que tener claros cuatro ladrillos de como funciona HOY el motor de borrado de object-manager.

RecordType (alias de presentacion)

Un RecordType es una "vista" tipada de un objeto base. La UI lo lista con el nombre rt__<Rt>__<base>, pero no es una entidad propia: es una proyeccion del objeto base. La metadata que gobierna el borrado (hijos declarados, softDelete) vive en el base, no en el alias.

Tabla de proyeccion sin id

La tabla fisica rt__<Rt>__<base> no tiene columna id: su clave primaria es la FK al objeto base (<base>Id). Cualquier query que filtre por id sobre ella es invalida.

Motor de impacto

buildDeleteImpactPlan / buildSoftDeleteImpactPreview (en helpers/deleteImpactPlan.js) asumen que el tipo recibido es un objeto base: derivan el modelo bajando la primera letra y consultan findMany({ where: { id: { in: [...] } } }).

Preview vs borrado real

El preview corre el motor sin mutar, para alimentar el conteo del modal. El borrado real (deleteBulkInstances) muta. Son dos entrypoints distintos al mismo motor; el real ya sabe resolver el alias, el preview no.

Como falla hoy — el flujo

El mismo input (un alias RT) toma dos caminos segun el entrypoint. El del borrado real resuelve; el del preview no, y por eso choca contra la tabla de proyeccion.

El entorno — que rodea el caso

ℹ Antecedente directo (UPONE-1479 / TICKET-117) — Ese ticket resolvio exactamente esta clase de alias, pero solo en el path de borrado (deleteBulkInstances). Dejo los dos previews sin tocar. Este ticket es el gemelo que los lleva a paridad. No es una idea nueva: es aplicar una resolucion ya probada en un lugar donde falto.
ℹ Consumidor front (best-effort) — layout/src/layouts/RecordList/RecordList.vue pide el preview para el conteo dinamico del modal critico; si falla, cae a un texto estatico. Por eso el usuario no queda bloqueado — pero pierde el aviso de cuantos registros y que referencias van a impedir el borrado.
⚠ Familia, no confundir (UPONE-1557) — La familia de robustez del hard-delete flagueo un follow-up sobre la divergencia semantica entre lo que detecta el preview y lo que detecta la ejecucion. Eso es otra deuda, mayor y fuera de alcance. Este ticket es solo el crash por alias.
✗ Trampa a evitar — Resolver el alias con un startsWith('rt__') o cortando el string a mano. El casing del base no es derivable del nombre: hay que resolverlo por introspeccion (core_ObjectDefinition), igual que hace el path de borrado.

La regla que gobierna el fix

El nombre de un RecordType es un alias de presentacion: hay que resolverlo al objeto base antes de aplicar cualquier politica de borrado.
RULE-core-043 (nacida de UPONE-1479). Corolario: todo entrypoint que decida sobre borrado — real o preview — debe resolver primero. Un preview que mira la proyeccion cruda esta mirando el lugar equivocado.

El patron que ya existe (a extraer y reutilizar)

Esto es lo que deleteBulkInstances hace hoy en instance.resolver.js:6004. El fix lo lleva a un helper compartido y lo aplica en los dos previews — misma tecnica, no logica nueva.

// resuelve el alias rt__<Rt>__<base> al nombre canonico del objeto base
const rtParsed = parseRecordTypeFileName(objectType);   // -> { rtName, baseObjectLower } | null
if (rtParsed) {
  const { baseObjectLower } = rtParsed;
  let resolvedBase = baseObjectLower;
  // introspeccion case-insensitive: recupera el CASING canonico, no se deriva del string
  const baseObjDef = await prisma.core_ObjectDefinition.findFirst({
    where: { name: { equals: baseObjectLower, mode: 'insensitive' } },
    select: { name: true },
  });
  if (baseObjDef?.name) resolvedBase = baseObjDef.name;
  objectType = resolvedBase;   // recien ahora el motor recibe el base
}

Q&A de estudio

¿Por que no basta con resolver el id del RecordType en vez de resolver al objeto base?
Porque la proyeccion no tiene id, y ademas la politica de borrado (hijos declarados, softDelete, conteos, restricciones) vive en el objeto base. Aunque pudieramos consultar la proyeccion, mirariamos el lugar equivocado para decidir el impacto. La resolucion correcta es alias → base, no "arreglar el id".
¿Por que el bug no se nota como un error para el usuario final?
Porque el front trata el preview como best-effort: si falla, muestra un texto estatico en vez del conteo dinamico, y el borrado real revalida y aborta por su cuenta. Lo que se pierde es la barrera de aviso (el usuario confirma a ciegas) y queda ruido de error en el log del backend en cada apertura del modal.
¿Por que la validacion pide BD real y no alcanza con unit tests?
Porque la resolucion depende de introspeccion sobre core_ObjectDefinition y del casing real de columnas de la proyeccion. Un Prisma mockeado puede dar verde con datos que no reflejan el shape real y consagrar el bug (RULE-core-034 / RULE-dev-test-real-shape-not-mocked). El path de borrado ya se prueba asi en integracion.
