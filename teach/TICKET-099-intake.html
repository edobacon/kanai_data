Paridad de la malla curricular desde el MCP

En SP5 (el sprint de "malla curricular") el equipo construyó el componente de UI CurriculumMesh: la vista donde un diseñador curricular arma la malla de un plan de estudios — coloca asignaturas por período, define líneas de formación (categorías de créditos), arma bloques electivos y el árbol de prerrequisitos. Ese poder vive hoy solo en el navegador. Este ticket lo lleva al MCP (up1-mcp, alias "Elric"): el adaptador que permite que un asistente conversacional (Claude / ChatGPT) opere up1 en nombre de un usuario real. El objetivo es paridad operable: que desde una conversación se pueda ver y editar la malla igual que en la UI, sin conocer la forma cruda de los objetos y con aviso previo de las reglas de negocio.

TL;DR — Qué hay: los 3 objetos de la malla ya se operan por MCP con CRUD genérico, pero sin tools dedicadas, sin lectura agregada y sin exponer los guards. Qué se hará: Fase A (exponer guards + editabilidad en los contratos) + Fase B (tools cd_* de malla: leer, agregar/editar/mover/quitar asignaturas, líneas y árbol de requisitos), en 3 sessions. Por qué: hoy el usuario del MCP debe conocer ids y el orden exacto de pasos, y solo se entera de una regla cuando el commit falla — rompe la filosofía "guía antes de enviar".

Las bases — el vocabulario del dominio

Antes de tocar nada conviene fijar seis términos. Los tres primeros son los objetos de datos de la malla (lo que se persiste en up1); los tres siguientes son las piezas del adaptador MCP con las que vamos a trabajar.

planEntry

Una "entrada de plan": coloca una asignatura (activityId) en un período de un plan (planId). Puede llevar categoría de créditos y blockId (bloque electivo).

requirementCategory

La "línea de formación": agrupa entradas por un rango de créditos (min/max) dentro de un plan. Su lectura ya trae derivados (créditos actuales, estado under/ok/over).

requirement

Nodo del árbol de reglas (patrón Composite). Tres tipos: Group (combina hijos, también es el "bloque electivo"), RecordState (exige un curso — prerrequisito) y MetricThreshold (umbral de créditos).

MCP / up1-mcp (Elric)

Servidor que expone up1 a un LLM vía solo GraphQL (nunca DB ni código). Es standalone y stateless: up1 es la fuente de verdad; el MCP nunca modifica up1.

tools cd_*

Las "operaciones de dominio" de curriculum-design en el MCP (ej. cd_create_curriculum). Envuelven el CRUD genérico con resolución por nombre y patrón preview→commit.

ObjectContract

La ficha config-driven de cada objeto en el MCP (campos, enums, FKs, notas). Es la fuente única de la que describe_object y get_create_guide derivan su salida.

Dos cosas a notar. Primero: el paso C (contrato) ya resuelve nombres a ids — esa maquinaria de resolución ya existe y la vamos a reutilizar en todas las tools nuevas. Segundo: el rechazo tardío del guard es exactamente el problema que Fase A ataca — moverlo a describe_object/get_create_guide para que el usuario lo vea antes.

El entorno — dependencias y restricciones que nos rodean

ℹ De dónde viene — Este ticket es el hijo directo de dos precedentes cerrados. MC-04 (TICKET-084) registró los 3 objetos en el MCP con CRUD genérico y difirió a SP6 las tools dedicadas cd_* de malla; este ticket las adelanta a SP5. MC-08 (TICKET-088) construyó lógica de dominio nueva en la UI (pre-check de prerrequisitos, mover asignatura con recálculo de posición, aviso de períodos) que hoy no tiene equivalente por MCP.
✗ Restricción dura — el MCP es standalone — El repo del MCP (uplanner/mcp) es un proyecto git independiente que solo habla GraphQL. La lógica de la UI (los archivos prereqCheck.logic.ts y recalcPeriodPosition.logic.ts del mod) no se puede importar desde el MCP. "Reusar la lógica del mod" significa portar el algoritmo puro (mismas reglas, código propio en el MCP), no un import. Esta es la decisión de arquitectura central del ticket (ver abajo).
⚠ Semántica H2 — no todo prerrequisito bloquea la ubicación — El pre-check estructural de SP5 solo mira si un curso exigido (RecordState con timing "Before"/"Either") está colocado en un período anterior, y si un grupo K-de-N tiene suficientes miembros ubicados antes. Los umbrales de créditos (MetricThreshold) NO condicionan la ubicación — el degree-audit real con notas es SP6. Portar esta semántica exacta importa: alertar de más sería un falso positivo.
◆ Patrón preview→commit — Toda tool de escritura del MCP, sin confirm:true, devuelve un preview sin mutar; con confirm:true ejecuta. Los guards corren en el commit. Este patrón es dónde naturalmente se muestran las advertencias (prereqs faltantes, discrepancia de períodos) — informativas, sin bloquear.

La pregunta de arquitectura: ¿importar o portar la lógica del mod?

REQ-07 (pre-check de prereqs) y REQ-08 (mover con recálculo) piden "reusar la lógica del mod". Hay dos lecturas de "reusar". La restricción de repo standalone (arriba) inclina la balanza, pero conviene tener claras ambas para no volver sobre esto en execute.

A · Importar el archivo del mod

El MCP haría import de prereqCheck.logic.ts directamente.

+ Cero duplicación; una sola fuente del algoritmo.

− Imposible: son repos separados; el MCP no tiene acceso al filesystem del mod ni al build de up1.

B · Portar el algoritmo puro (elegido)

Reimplementar las funciones puras en el MCP con las mismas reglas, con comentario de procedencia.

+ Único camino viable; alineado con el patrón ya usado en validations.ts (reglas frontend-only replicadas).

− Duplicación lógica: si el mod cambia las reglas, hay que reflejarlo aquí. Se mitiga con tests que fijan la semántica.

La sorpresa útil: el MCP ya tiene un precedente de esto. src/contracts/validations.ts replica reglas que up1 solo enforza en el frontend (suma de pesos, rango de créditos). Portar prereqs y recálculo es más de lo mismo, no un patrón nuevo — lo que baja el riesgo de la decisión.

Hacia adelante — el plan en 3 sessions

El trabajo se ordena de barato-y-fundacional a caro-y-derivado. S1 no depende de nada nuevo; S2 y S3 construyen sobre la lectura agregada de S1. Cada session cierra con un gate T2 (validación por tests de contrato + smoke con sesión real).

S1 · Fase A — contratos + lectura

Exponer guards (MC-09, rango, borrado) y editabilidad del plan en describe_object/get_create_guide; nueva tool cd_get_mesh (malla agregada por período + líneas con derivados + totalPeriods). REQ-01, 02, 03, 09.

S2 · Fase B — escritura de entradas

cd_add_plan_entry (orquesta bloque electivo + pre-check de prereqs), cd_update/move/remove_plan_entry (recálculo de posición), cd_manage_formation_line. REQ-04, 05, 06, 07, 08.

S3 · árbol de requisitos + transversal

cd_manage_requirement + cd_get_prereqs, y el principio transversal G11 (nunca ids crudos: resolver por nombre/código, opciones legibles) aplicado a todas las tools. REQ-10, 11.

Alcance — qué entra y qué queda diferido

Fase A + B (este ticket) Fase C — layout de malla por MCP (RecordDetail fase 2) Motor de evaluación de requisitos (SP6)

Q&A — verifica tu mapa mental

¿De qué se trata el caso?
Llevar las capacidades de la malla curricular (el componente CurriculumMesh de la UI de SP5) al adaptador MCP, para que un asistente conversacional pueda ver y editar la malla de un plan con la misma potencia que la UI, sin exigir ids crudos ni conocer el orden interno de operaciones.
¿Qué se va a hacer a alto nivel y por qué importa?
Fase A: exponer los guards de negocio y la editabilidad del plan en los contratos, para "guiar antes de enviar" en vez de fallar en el commit. Fase B: tools cd_* dedicadas que orquestan las operaciones (ej. crear el bloque electivo y la entrada en un solo paso atómico) y reusan el enrichment de lectura. Importa porque hoy el usuario del MCP tiene una experiencia cruda y propensa a error frente a una UI pulida.
¿Cuál es la restricción más crítica a respetar?
Que el MCP es un repo standalone que solo habla GraphQL: no puede importar la lógica de la UI. Toda "reutilización" de prereqCheck.logic.ts y recalcPeriodPosition.logic.ts es un port del algoritmo puro. Y respetar la semántica H2: los umbrales de créditos no condicionan la ubicación en el pre-check estructural.
¿Hubo decisiones cerradas en el intake?
El intake fue mayormente lineal: las 3 hipótesis (guards ya corren y solo falta exponerlos; el enrichment llega gratis; las tools son orquestación sobre mutaciones existentes) quedaron confirmadas contra el MCP en vivo. La única decisión de peso — importar vs portar la lógica del mod — quedó resuelta por la restricción de repo standalone (portar), pero se documenta explícita para no re-litigarla en execute.
