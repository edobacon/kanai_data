HU-10 — Row action "Crear nueva versión" en RecordList de Activity

Este ticket agrega un botón "Crear nueva versión" en cada fila de la lista de Activity (la entidad del mod curriculum-design que modela una actividad curricular). El botón es el punto de entrada visible que el consultor usa para iniciar el ciclo de mejora curricular: clonar la Activity actual como una nueva versión. Lo notable es que no se escribe código nuevo — todo es configuración declarativa sobre un primitivo ya construido en sprints anteriores. El trabajo real es entender bien cómo ese primitivo se configura y dónde viven la hidratación de la relación y la condición de visibilidad.

TL;DR — Qué hay: el primitivo de row action type:"create" (HU-7, ya cerrado en TICKET-042) soporta clonar+versionar; el motor de listas ya sabe hidratar relaciones y resolver visibilidad por dot-notation. Qué se hará: editar default_Activity_list.json para declarar relations: ["currentStatus"] en la raíz + un row action type:"create" (prefillFromCurrent + asNewVersion, redirect a edit, visible sólo si currentStatus.allowsVersioning == true) + 3 traducciones (es_CL/en_CL/pt_BR). Por qué: darle al consultor el disparador del versionamiento sin modal, con feedback por toast, en los estados que el negocio permite versionar.

Conceptos clave (las bases)

Sobre estos cimientos se apoya el cambio. Si no estuviste en sprints anteriores, lee estas seis tarjetas primero — son el vocabulario sin el cual el resto del ticket no se entiende.

RecordList + layout config

La lista de registros de una entidad se renderiza desde un JSON de configuración declarativo (default_<Object>_list.json). No hay un componente Vue por entidad: el motor de layout interpreta el JSON.

Row action type:"create"

Acción por fila construida en HU-7 (TICKET-042). Con prefillFromCurrent clona los datos de la fila y con asNewVersion los guarda como versión nueva, invocando createInstance. redirectTo:"edit" lleva al RecordDetail del nuevo registro.

Hidratación de relations

La query LIST_INSTANCES sólo trae los campos de la entidad. Para acceder a campos de una relación (ej. currentStatus.allowsVersioning) hay que pedir esa relación con relations: [...] en la raíz del config — lo lee useDataFetching.ts:126-135.

visibilityConditions

Bloque declarativo que decide si un elemento se muestra, evaluando condiciones sobre campos del registro — soporta dot-notation hacia relaciones. Implementado en useFieldConditions.ts:38-52.

currentStatus.allowsVersioning

Flag del estado de workflow de la Activity (vía relación currentStatus). El negocio decide en qué estados se puede versionar; este flag es el gate de visibilidad del botón.

i18n por archivo @activity

Las traducciones viven en suite/lang/<locale>@activity.json. El label del botón usa {{$t('createNewVersion')}}, que debe existir en los 3 locales soportados (es_CL/en_CL/pt_BR).

El entorno: dependencias y restricciones

Qué rodea a este cambio sin ser parte de él, y qué reglas lo limitan.

✓ Dependencias ya cerradas — HU-7 (TICKET-042, primitivo type:create) y HU-8 (TICKET-043, adopción del versionamiento en Activity) cerraron el 2026-06-02. HU-10 sólo configura lo que ellos construyeron; no toca layout/ ni el resolver.
ℹ Precedente real — relations en la raíz de un list config ya existe en mods/hello-world-mod/hw-intervention-list.json ("relations": ["hwassessment"]). HU-10 replica el patrón con currentStatus. No es terreno inexplorado.
⚠ relations va en la raíz, NO en el row action — relations no es un campo de RowAction. Si se anida dentro del action, la relación no se hidrata y currentStatus.allowsVersioning resuelve a undefined → el botón nunca aparece. Es el error más probable de este ticket.
⚠ RULE-platform-006 — filename PascalCase — el layout es default_Activity_list.json (objeto en PascalCase). Mantener el nombre exacto; el motor resuelve el layout por convención de nombre.
✗ Sin modal — el versionamiento usa increment directo: el click ejecuta createInstance sin diálogo de confirmación. No agregar modal; el feedback es por toast + redirect.

Flujo del botón (qué pasa al hacer click)

flowchart LR
  A[Fila de Activity en la lista] --> B{ currentStatus.allowsVersioning == true? }
  B -- no --> H[Botón oculto]
  B -- si --> C[Botón Crear nueva versión visible]
  C --> D[click: createInstance prefillFromCurrent + asNewVersion]
  D --> E[Redirect a RecordDetail del nuevo Activity en edit]
  E --> F[Toast: Versión N creada desde versión N-1]

Shape canónico del config (objetivo)

Así queda default_Activity_list.json tras HU-10. Nota dónde vive relations (raíz) vs visibilityConditions (dentro del action):

// mods/curriculum-design/config/layouts/default_Activity_list.json
{
  "name": "default_Activity_list",
  "objectType": "Activity",
  "relations": ["currentStatus"],          // raíz: hidrata la relación
  "rowActions": [{
    "type": "create",
    "prefillFromCurrent": true,
    "asNewVersion": true,
    "label": "{{$t('createNewVersion')}}",
    "redirectTo": "edit",
    "icon": "bi-arrow-clockwise",
    "visibilityConditions": {            // dentro del action: gate de visibilidad
      "operator": "AND",
      "conditions": [
        { "field": "currentStatus.allowsVersioning", "operator": "==", "value": true }
      ]
    }
  }]
}

Q&A de estudio

¿De qué se trata el caso?
Agregar un botón "Crear nueva versión" en cada fila de la lista de Activity, que clona la Activity actual como versión nueva y redirige a editarla. Es puramente configuración de layout JSON + i18n sobre primitivos ya construidos (HU-7, HU-8).
¿Qué se va a hacer y por qué importa?
Declarar relations:["currentStatus"] + un row action type:"create" con visibilidad por currentStatus.allowsVersioning en default_Activity_list.json, más 3 traducciones. Importa porque es el disparador visible del ciclo de mejora curricular para el consultor — sin botón, el versionamiento construido en sprints previos no tiene puerta de entrada en la UI.
¿Qué hipótesis quedaron abiertas y cuál verificar primero?
No quedan hipótesis abiertas: H1 (el primitivo type:create soporta prefill+asNewVersion) y H2 (relations en raíz hidrata la relación para dot-notation) están ambas confirmadas — H1 por la dependencia cerrada TICKET-042, H2 por useDataFetching.ts:126-135 + el precedente hw-intervention-list.json. Lo crítico a verificar empíricamente no es una hipótesis sino el comportamiento E2E en S3.
¿Qué decisiones críticas se tomaron en el intake?
El intake fue esencialmente lineal: shape conocido, certeza confirmada, sin alternativas comparables. La única decisión de diseño no trivial — relations en la raíz del config y NO dentro del row action — viene impuesta por el motor (relations no es campo de RowAction), con precedente real. No hubo trade-off que pesar.
