HU-7 · Row action type: "create" como primitivo declarativo del layout

En layout — la librería de componentes de Uploadr (Atomic Design + LayoutOrchestrator) — las listas de registros (RecordList.vue) muestran row actions: botones por fila declarados en JSON de config (editar, descargar plantilla, ejecutar una mutation…). HU-7 agrega un tipo nuevo de row action — type: "create" — que crea una instancia nueva opcionalmente precargada desde la fila actual (prefillFromCurrent) y opcionalmente como nueva versión (asNewVersion). Con esos dos flags ortogonales se cubren dos casos sin escribir componentes a mano: "Crear nueva versión" (create + asNewVersion) y "Clonar" (create + prefill). Todo de forma aditiva: sin tocar los tipos existentes.

TL;DR — Qué hay: hoy el union de row actions es default | modal | download-template | import-template | mutation, declarado en dos lugares que deben mantenerse en sync (types/recordlist.ts y EnhancedRowAction en useRowActionHandler.ts). El dispatcher es una cadena de if (no switch exhaustivo) → agregar un tipo es aditivo. La visibilidad por flag relacionado ya es posible sin código: la lista hidrata relaciones con relations y visibilityConditions resuelve dot-notation. Qué se hará: declarar CreateRowAction en las 2 definiciones del union, sumar el caso create al dispatcher de RecordList.vue (y al de ChibiList.vue), y un handler que llama createInstance(prefillFrom + asNewVersion). La visibilidad se logra por config (no por código): relations: ["currentStatus"] + currentStatus.allowsVersioning == true. Por qué importa: es un primitivo transversal — cualquier mod podrá ofrecer versionar/clonar declarativamente. El riesgo real está en mantener las 2 definiciones del union sincronizadas y en no tocar los otros tipos.

Las bases: cómo funcionan hoy los row actions

Seis piezas del modelo actual de layout. La clave: un row action es declarativo (JSON), su comportamiento lo resuelve un dispatcher en el componente, y su visibilidad se evalúa contra los datos hidratados de la fila.

Row action (union de tipos)

Cada botón por fila tiene un type. El union vive en layout/src/types/recordlist.ts:68 (default | modal | download-template | import-template | mutation). HU-7 suma create.

La segunda definición del union

EnhancedRowAction en useRowActionHandler.ts:25 reespecifica el mismo union para el handler. Hay que actualizar las dos: si solo se toca una, el tipo nuevo no queda bien tipado y rompe ChibiList/RecordList.

Dispatcher (cadena de if)

RecordList.vue:2205-2306 resuelve la acción con if (action.type === …) encadenados, sin switch exhaustivo ni never-check. Por eso agregar un caso al final es aditivo: no altera los ramos previos. Hay un segundo dispatcher en ChibiList.vue:716-741.

createInstance(prefillFrom + asNewVersion)

La mutation de creación (object-manager) que HU-1/HU-3 extendieron. prefillFrom: { sourceId } precarga; asNewVersion: true la marca como versión. El handler de HU-7 solo orquesta estos dos flags según el row action.

Hidratación por relations

La query de la lista (LIST_INSTANCES) acepta $includeRelations/$relations; useDataFetching.ts:126-135 lee layoutConfig.relations. Poniendo relations: ["currentStatus"] en la raíz del config, cada fila trae su currentStatus embebido.

visibilityConditions + dot-notation

RowAction.visibilityConditions ya existe (recordlist.ts:92); se evalúa en useRowActionHandler.ts:147-165 con getNestedValue (useFieldConditions.ts:38-52) — soporta rutas tipo currentStatus.allowsVersioning. Por eso la visibilidad de HU-7 no necesita código nuevo.

Estado actual: el dispatcher que vamos a extender

Así luce hoy la cadena de if de RecordList.vue (esquemático). HU-7 agrega un eslabón al final — los previos quedan intactos. Entender que no hay default exhaustivo es lo que hace seguro el cambio. 

// RecordList.vue ~2205-2306 — dispatcher actual (cadena de if, sin switch)
if (action.type === 'modal') { /* abre modal */ }
else if (action.type === 'download-template') { /* … */ }
else if (action.type === 'mutation') { /* ejecuta mutation */ }
// … otros tipos …
// ★ HU-7 agrega al final, aditivo:
else if (action.type === 'create') {
  if (action.prefillFromCurrent) {
    const args = { prefillFrom: { sourceId: row.id } };
    if (action.asNewVersion) args.asNewVersion = true;
    return await createInstance(objectType, {}, args);
  }
}

Dos casos, un solo primitivo: versionar vs clonar

La decisión de diseño (D23) fue no crear dos tipos separados ni reusar type: "mutation", sino un primitivo create con dos flags ortogonales. Así un mismo tipo cubre ambos casos por composición de flags.

Crear nueva versión

create + prefillFromCurrent + asNewVersion. Precarga desde la fila y marca la creación como versión del origen. Visible solo si currentStatus.allowsVersioning == true.

Clonar

create + prefillFromCurrent (sin asNewVersion). Precarga desde la fila pero crea una instancia independiente, no una versión. Mismo tipo, un flag menos.

El invariante que mantiene el cambio seguro

type: "create" es puramente aditivo: suma un eslabón al final del dispatcher y un miembro al union (en sus 2 definiciones), y NO modifica los tipos modal/mutation/default/etc.
Corolarios: (1) la visibilidad vive en la raíz del config de la lista (relations), no en el row action — relations no es campo de RowAction. (2) En SP3 la única versionStrategy es increment → sin modal (no se pide valor al usuario); el modal de captura llega con user-provided en SP4. (3) Las 2 definiciones del union deben quedar idénticas: la sincronización es el único punto donde un error rompe el tipado de ambas listas.

Q&A — ¿entendiste el caso?

¿De qué se trata el caso?
De agregar un tipo nuevo de row action al layout — type: "create" — que permite crear una instancia precargada desde la fila actual (prefillFromCurrent) y opcionalmente como nueva versión (asNewVersion). Con esos dos flags se ofrecen "Crear nueva versión" y "Clonar" de forma declarativa (JSON de config), sin escribir componentes ni argsMapping a mano.
¿Qué se va a hacer (alto nivel) y por qué importa?
Declarar CreateRowAction en las dos definiciones del union (recordlist.ts y EnhancedRowAction), agregar el caso create a los dos dispatchers (RecordList.vue y ChibiList.vue) con un handler que llama createInstance(prefillFrom + asNewVersion), y lograr la visibilidad por config (relations + visibilityConditions). Importa porque es un primitivo transversal reusable por cualquier mod, y el descubrimiento clave es que la visibilidad no requiere código nuevo.
¿Qué hipótesis quedaron abiertas y cuál es la más crítica de verificar primero?
Las tres hipótesis del triage quedaron confirmadas en exploración: H1 (las 2 definiciones del union están en sync hoy), H2 (los dispatchers son cadenas de if sin exhaustiveness → aditivo seguro), H3 (relations hidrata currentStatus y dot-notation resuelve allowsVersioning). La más crítica de validar empíricamente durante execute es H3 de punta a punta (S3, gate fuerte): que el botón realmente aparezca solo cuando allowsVersioning == true con datos hidratados reales en storybook.
¿Qué decisiones críticas se tomaron en el intake?
La decisión D23: crear type: "create" como primitivo declarativo con dos flags ortogonales (prefillFromCurrent + asNewVersion), en vez de (a) reusar type: "mutation" o (b) crear dos tipos separados "versionar" y "clonar". El primitivo por composición de flags es más general y evita duplicar lógica. La segunda decisión: poner la visibilidad en la raíz del config de la lista (vía relations), no en el row action, porque relations no es un campo de RowAction y la hidratación es responsabilidad de la lista.
