A1.5 · Login & landing (rediseño pre-auth)

Hoy, cuando un visitante anónimo entra a la plataforma Jormat Evolution, ve una pantalla mínima: un título, una línea de texto y un botón "Iniciar sesión". Ese trozo de UI vive incrustado dentro del AuthGuard — el componente que decide si mostrar la app o pedir login. Este ticket extrae esa pantalla a su propio componente <LoginScreen> y la rediseña con el lenguaje visual de la plataforma (la marca verde, claro/oscuro, estados de carga y error). El objetivo de este teach-intake es darte el mapa completo antes de diseñar: sobre qué bases te paras, qué hay alrededor que no debes romper, y cuál es el plan.

TL;DR — Qué hay: el login pre-auth es un <div> con un <button> dentro de la rama !isAuthenticated del AuthGuard. Qué se hará: extraerlo a un componente de presentación <LoginScreen> con marca green-600, claro/oscuro, responsive y estados (loading "Inicializando…", error, CTA), que reúsa la llamada MSAL ya entregada — más stories + tests. Por qué: la pantalla de entrada debe verse acorde al design system (JOR-003) sin tocar la lógica de autenticación entregada (regla crítica RULE-global-003).

Conceptos clave (las bases)

Cinco ladrillos conceptuales que necesitas para entender el caso. El primero (AuthGuard) es el suelo: todo el ticket gira alrededor de él sin tocar su lógica.

AuthGuard

Componente "portero" (src/auth/AuthGuard.tsx): si el usuario está autenticado renderiza la app (children); si no, muestra la pantalla de login. Es código entregado — su lógica no se reescribe.

MSAL / CIAM

MSAL es la librería de Microsoft (@azure/msal-react) que habla con Azure External ID (CIAM), el servicio de identidad. El login se dispara con loginRedirect (redirige al portal de Azure).

useMsal() · inProgress

Hook que da acceso a la instance de MSAL y a inProgress (un InteractionStatus: si está en None está en reposo; si no, hay un login/token en curso → mostrar "cargando").

Componente de presentación

Un componente "puro" que solo dibuja UI y maneja estados visuales, sin lógica de negocio propia (criterio C1 de RULE-global-001). <LoginScreen> será uno de estos.

Tokens shadcn (JOR-003)

Variables CSS semánticas por rol (--primary, --background, --muted-foreground…) en :root/.dark. primary = green-600. Se usan como utilidades Tailwind (bg-primary, text-foreground).

cn() + lucide-react

Utilidad cn() (src/lib/utils.ts) para componer clases Tailwind sin conflictos; lucide-react es la librería de íconos. Patrón ya usado en ThemeToggle.tsx.

El entorno (qué rodea el caso)

El cambio es chico, pero está rodeado de restricciones y vecinos que importan. Léelos antes de diseñar:

✗ RULE-global-003 (crítica) — la lógica de auth entregada NO se reescribe: MsalProviderWrapper, msalConfig.ts, la cadena useMsal→loginRedirect→initialize. Se permite el cambio aditivo/de presentación: reemplazar el <div> inline por <LoginScreen /> dentro de la misma rama del guard.
✓ Dependencia lista — JOR-003 — los tokens claro/oscuro ya existen (cerrado 2026-06-13). primary=green-600, cn(), lucide-react, Storybook+Vitest (browser mode) y el patrón ThemeToggle están disponibles para reusar. No hay bloqueante.
ℹ Vecinos del plan — JOR-005 (Shell/Sidebar) montará el ThemeToggle y retematizará el nav; JOR-008 (A4.5) manejará el flujo 403→login. Nada de eso es parte de este ticket — solo la pantalla pre-auth.
⚠ Sin asset de logo — public/ está vacío. La marca hoy es texto ("Jormat Evolution" + letra "J"). <LoginScreen> usará marca tipográfica (la "J" en un recuadro bg-primary + wordmark), sin replicar el Sidebar entregado. El branding de la pantalla hosteada por Azure CIAM queda fuera de alcance (es config del portal, no código).

El enfoque: ¿cómo se conecta LoginScreen con MSAL?

La decisión de diseño clave del intake (hipótesis H2). Hay dos formas de que <LoginScreen> dispare el login. El intake se inclina por la opción A (consume useMsal() internamente) porque el Request lo pide explícito ("reúsa useMsal().loginRedirect") y el plan de tests dice "mock de useMsal" — lo cual solo tiene sentido si el componente importa el hook. Se formalizará como DEC-LOCAL en el spec; aquí queda como orientación, no como conclusión cerrada.

A · Consume useMsal() internamente ✓ (enfoque previsto)

<LoginScreen> importa useMsal + loginRequest, lee inProgress y llama loginRedirect en el click; el guard solo hace return <LoginScreen />.

+ Coincide con el Request y con el plan de tests (mock de useMsal).

+ El guard queda más limpio; nada de plumbing de props.

− El test del componente necesita mockear el hook (manejable).

B · Recibe todo por props

El guard lee useMsal y pasa onLogin, isLoading, error como props a un <LoginScreen> 100% tonto.

+ Render testeable sin mock de MSAL.

− Contradice el Request ("reúsa useMsal()") y el plan de tests.

− Más plumbing en el guard (roza el límite de "no tocar la lógica").

Invariante a preservar

La cadena de autenticación entregada queda byte-idéntica en comportamiento: mismo loginRedirect(loginRequest), mismo orden de evaluación del guard, mismo initialize() post-login.
Corolario: el único delta visible es la presentación de la pantalla pre-auth. Si un cambio altera el flujo de auth (no solo su aspecto), está fuera de alcance y viola RULE-global-003.

Q&A de estudio

¿Por qué editar AuthGuard.tsx no viola RULE-global-003 si es código entregado?
Porque solo se reemplaza la presentación de una rama (<div> → <LoginScreen />), no la lógica. El orden de evaluación, el loginRedirect y el initialize() quedan idénticos. Además, execute_scope incluye src/auth/ explícitamente. RULE-003 prohíbe reescribir lógica, permite cambios aditivos/de presentación.
¿Qué estados visuales debe cubrir <LoginScreen>?
Tres: (1) idle con el CTA "Iniciar sesión"; (2) loading cuando inProgress != None ("Inicializando…"); (3) error de config/auth con un mensaje amistoso. Todos en claro y oscuro, responsive.
¿De dónde sale el color de marca y cómo se aplica claro/oscuro?
De los tokens de JOR-003: primary = green-600. Se usa vía utilidades Tailwind por rol (bg-primary, text-foreground, text-muted-foreground). El modo oscuro lo da la clase .dark en <html> (ya gestionada por el ThemeProvider); el componente no maneja tema, solo usa los tokens.
¿Hay preguntas abiertas que bloqueen el diseño?
No. Las tres hipótesis del intake (complejidad simple, consume useMsal internamente, cableado aditivo) están confirmadas con evidencia multi-capa. El único gap menor — no hay logo gráfico — se resuelve con marca tipográfica. Sin gaps activos.
