Lecciones aprendidas

✗ L1 — lint/editor en archivos excluidos del tsconfig — `tsconfig.json` excluye `**/*.test.tsx`/`**/*.stories.tsx`/`src/test`. El TS server del editor los abre en inferred project sin los `paths` `@/` ni la augmentación jest-dom de `setup.ts` → errores rojos (`Cannot find module '@/...'`, `toBeInTheDocument no existe`) que build y test NO detectan. Fix file-local: imports relativos + `import '@testing-library/jest-dom/vitest'`. El dev marcó el principio: los cierres no deben dejar errores → verificar lint/tipos/editor (eslint + prettier + tsc incluyendo excluidos) en cada quality review.
ℹ L2 — testear un componente que usa `useMsal()` sin MSAL real — proveer el contexto: en stories `` (stub con `loginRedirect`+`inProgress`), en unit test `vi.mock('@azure/msal-react')`. Seam limpio, reusable para JOR-008.
✓ Enfoque aditivo verificado — el reviewer aislado confirmó: `MsalProviderWrapper`/`msalConfig` sin diff, ramas del guard intactas, blast radius = solo los archivos del scope. RULE-003 respetada.

Evolución de hipótesis & Q&A

¿Se confirmaron las hipótesis del intake?
Sí, las tres: H1 (feature simple, 1 session — se cumplió: 3 tasks + gate), H2 (consume `useMsal` internamente — confirmado por el test que mockea el hook), H3 (cableado aditivo — el reviewer verificó que solo cambió la presentación de la rama).
¿Por qué `npm test` y `npm run build` pasaban pero el editor mostraba errores?
Porque `tsconfig.json` excluye los test/stories: `tsc` (que usa el build) ni siquiera los type-checkea, y `vitest` no type-checkea en runtime. El editor sí los abre, pero sin los `paths`/types del proyecto. Build verde ≠ editor limpio. De ahí la regla: verificar el editor/lint en el cierre.
¿Cómo se reutiliza esto en JOR-008 (403→login)?
El patrón de testear con `MsalContext.Provider`/`vi.mock` sirve para cualquier componente auth. Y `LoginScreen` ya expone los 3 estados; un flujo 403 podría reusar el estado error con un mensaje distinto.
