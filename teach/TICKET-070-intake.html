Crear un Plan de estudios desde la UI falla siempre

En la suite, crear un Plan (un Curriculum con recordType = Plan) revienta con «La información proporcionada no es válida. Ubicación: > Progression». No es un problema del formulario ni del picker de dueño (eso se cerró en TICKET-069): es que el formulario manda los campos propios del tipo Plan (progression, totalCredits…) a la tabla base curriculum, donde esas columnas no existen. Este teaching te deja el mapa completo del caso —las bases (cómo modela up1 un RecordType y cómo crea registros hoy), el entorno (qué patrones y casos vecinos lo rodean) y el plan (qué vamos a hacer y por qué)— antes de tocar código.

TL;DR — Qué hay: crear un Plan desde la UI siempre falla porque el form crea sobre objectType = Curriculum (la tabla base) y los campos del tipo Plan viven en una tabla de extensión 1:1 rt__Plan__curriculum. Qué se hará: una mutation del mod (createCurriculumWithRecordType) que arma el alias rt<Plan>curriculum y delega en el createInstance de core, ruteando el form vía customEndpoint. Por qué: core ya sabe separar los campos cuando se lo invoca con el alias — reusamos esa lógica en vez de duplicarla, y todo queda mod-only (sin tocar core).

Las bases — cómo funciona hoy

Cuatro conceptos del object-manager (el backend GraphQL de up1) sostienen todo el caso. Si entiendes estos cuatro, el bug y la solución se explican solos. El primero —el modelo RecordType con tabla base + extensión— es el corazón; los otros tres son cómo ese modelo se crea, se rutea desde la UI y se extiende sin tocar core.

RecordType + tabla de extensión 1:1

Un objeto (Curriculum) tiene una tabla base con los campos comunes y, por cada tipo (Plan, Minor…), una tabla de extensión rt__<Tipo>__<base> con los campos propios de ese tipo. progression NO es columna de curriculum; vive en rt__Plan__curriculum.

createInstance (core)

La mutation genérica de creación. Recibe { objectType, data }. Si objectType es un alias rt__…, entra a un early-return que separa el data plano en base/rt/extensión y crea las filas correctas (instance.resolver.js:2508-2682). Con objectType = Curriculum NO entra a ese camino.

customEndpoint (layout)

Un bloque del layout JSON que hace que el formulario genérico (RecordDetail.vue) submitee a una mutation a medida en vez de a createInstance. Mapea campos del form a variables de la mutation (RecordDetail.vue:3660).

Mod resolver + sync

Un mod aporta *.resolver.js + *.schema.graphql en logic/; npm run sync los copia a core. El nombre del export const debe contener Mutation/Query o el auto-loader lo ignora (RULE-mods-004).

El diagrama de abajo contrasta dos caminos del mismo formulario: el actual (roto) y el propuesto (arreglado). Lo que importa mirar es el nodo de decisión: todo se reduce a con qué objectType llega la creación a core. Con Curriculum (base) Prisma rechaza; con el alias rt__Plan__curriculum core hace el split y persiste.

Dos cosas a notar del diagrama. Primero: el camino verde (alias) ya existe y funciona — las 6 secciones curriculares (rt__Modality__curricularsection, etc.) se crean así desde la UI. Segundo: la solución no inventa lógica nueva; solo desvía el formulario al camino que ya está probado. Esto nos lleva a la falla concreta — qué data se manda hoy.

La falla, en una línea de data

// HOY — el form crea sobre la tabla base con campos del tipo Plan mezclados
createInstance({ objectType: 'Curriculum', data: {
  name, code, status, institutionId, ownerType, ownerId,
  progression, totalCredits, totalPeriods, periodType  // ← NO son columnas de `curriculum`
}})
// => Invalid prisma.curriculum.create(): Unknown argument `progression`

// FIX — el mod arma el alias y delega; core separa los campos solo
createInstance({ objectType: 'rt__Plan__curriculum', data: { ...mismos campos... } })
// => fila base `curriculum` + fila extension `rt__Plan__curriculum`, OK

El entorno — qué rodea al caso

El caso no vive solo. A su lado hay dos cosas que conviene tener en el radar: un patrón vecino que vamos a copiar (cómo un mod delega en core) y un caso latente con la misma forma fuera de nuestro alcance (uengagement). La comparación de abajo enfrenta los dos caminos posibles de creación —no es una decisión abierta, es para fijar por qué el alias es el correcto.

Crear sobre la base — objectType = Curriculum

Lo que hace el form hoy. Prisma recibe campos que no son columnas de la tabla base.

− Falla para cualquier tipo con campos propios (Plan).

− No hay split: base/extensión quedan sin separar.

Crear por el alias — objectType = rt__Plan__curriculum

Lo que ya hacen las CurricularSection y lo que el MCP usa (typedRecordName).

+ Core separa base/rt/extensión y castea ints solo.

+ Preserva auth, eventos y audit del path genérico.

El patrón vecino que copiamos vive en el propio mod: sectionValidation.resolver.js:51-67 y polymorphicUpdate.resolver.js cargan el createInstance de core con un dynamic import de doble ruta (sirve para el path del mod en dev y el synced en prod) y delegan. Nuestra mutation usará exactamente ese helper. El caso latente es engagement_Activity_service_create.json de uengagement: mete activityTypeId (campo de rt__Service__Activity) en un layout de la base Activity — la misma trampa. No se toca aquí (DET-16: se reporta a uengagement). Esto importa para entender una decisión clave del plan, que va abajo.

⚠ Atención (disciplina que mantiene válida la solución) — el resolver del mod debe delegar, no reimplementar el split. Si copia la lógica de core, la duplica (divergencia) y rompe la compatibilidad con el MCP, que crea RecordTypes por el mismo alias. Cero lógica de negocio en la mutation UI-only.
ℹ Contrato de retorno — createInstance devuelve InstanceResult { id, data, extended } (RULE-mods-027), no un Curriculum plano. El adapter reshapa a { id, ...data } para que el customEndpoint pueda leer id y name. Eso es traducción de contrato, no lógica de negocio.

Hacia adelante — qué vamos a hacer

El invariante de abajo es la regla que ancla toda la implementación: si en algún momento el resolver empieza a hacer cosas además de delegar, la solución dejó de ser válida y hay que repensarla. Tenlo presente al leer el plan.

La mutation del mod es un adapter delgado: traduce «form plano de Curriculum + recordType» → «createInstance(alias)» y delega. Nada más.
Corolario: tipos nuevos (Minor, futuros) no tocan el resolver. Un campo nuevo sí exige una línea en el customEndpoint — por eso el fix en core (split base→alias dentro de createInstance) escalaría mejor (backlog B1).

El plan es de una sola sesión (S1, tier T2, gate fuerte): el cambio es acotado y el patrón está probado. La cronología de abajo es el orden previsto; el hito crítico es el primero (el resolver que delega) porque todo lo demás depende de que esa pieza cargue el createInstance de core correctamente.

1 · Resolver + schema del mod

curriculum-create.resolver.js (delega vía loadGenericInstanceMutation) + curriculum-create.schema.graphql (createCurriculumWithRecordType(data: JSON!): Curriculum!).

2 · customEndpoint en el layout

Agregar el bloque a default_Curriculum_create.json con inputVariable: "data" + JSON! y campos mapeados (forma corregida tras L1; el source: "formData" whole-object no existe en el engine).

3 · Unit del resolver + npm run sync

Test del adapter (arma alias correcto, delega, reshapa). Sync a core.

4 · Smoke UI + TC-1..TC-4

Crear Plan y Minor desde la suite (Playwright); verificar fila base + extensión e ints persistidos. Quality review + commits + S1.GATE.

Q&A de estudio

¿Por qué no arreglar el wizard RT-aware nativo del front en vez de una mutation del mod?
Porque ese wizard regenera el schema del formulario desde las field-defs (RecordDetail.vue:1383-1392) y rompería el picker polimórfico de dueño (autoPopulate/useOwnerIdOptions), que vive en el layout autorado, no en la field-def (H3 confirmada). D conserva el form autorado y solo cambia a dónde submitea.
¿Cuál es la pregunta abierta más relevante a verificar primero en execute?
Que el dynamic import del createInstance de core funcione sin fricción de contexto/auth desde un resolver del mod (el plan lo marca como hito 1). Si presentara fricción, el ticket escala y se considera el camino B (split en core). El patrón ya existe en sectionValidation, así que el riesgo es bajo, pero es lo que confirma que toda la solución se sostiene.
¿Qué deuda asumimos con esta solución (D) frente a arreglarlo en core (B)?
D resuelve el síntoma solo en Curriculum y deja una mutation a medida + acoplamiento mod→core + la regla de mantener el resolver thin. B (que createInstance derive el alias desde objectType=<base> + data.recordType) lo arreglaría una vez para todos los objetos con RecordType (incluido el caso latente de uengagement) y uniformaría UI/MCP/REST/n8n. Queda como backlog B1: cuando exista, la mutation D se retira.
