Shell / chrome transversal

El "shell" es el marco persistente de la aplicación: el sidebar de navegación, el topbar y el layout que envuelven cada vista. Hoy jormat-front trae un shell de scaffold (heredado del template de cuenta/plataforma) cuyo sidebar enlaza a páginas que no existen y cuyo estilo no consume el sistema de diseño nuevo. Este caso lo reemplaza por el shell de negocio — la navegación de un ERP de distribución de repuestos. Antes de tocar código conviene entender sobre qué bases nos paramos, qué rodea al cambio y por dónde va el camino.

TL;DR — Qué hay: un Sidebar oscuro hardcoded con 4 links en 404 (/users /workspaces /settings /admin) y un TopBar mínimo, sobre tokens de diseño (JOR-003) y stack de tests ya presentes pero sin usar. Qué se hará: reemplazar el shell por Sidebar acordeón de negocio (taxonomía DEC-003), TopBar completo (búsqueda ⌘K, EmpresaSwitcher, ThemeToggle, menú de cuenta), Home lanzador (maqueta 01) y cierre de los 404. Por qué: el shell es la Capa A que habilita todas las vistas de negocio de la Fase B — sus rutas y su navegación son cimiento de JOR-008 y los tickets B.

Las bases — conceptos sobre los que se apoya el caso

Glosario mínimo para entender de qué hablamos. Todo esto ya existe o está decidido; el shell se construye encima.

Shell / chrome

El marco persistente que no cambia entre vistas: Sidebar + TopBar + layout (AppShell). Cada página de negocio se renderiza dentro de él.

Tokens JOR-003 (HSL)

Variables CSS shadcn (--primary, --sidebar, --accent…) en globals.css, con tema claro y oscuro. El shell nuevo las consume; el actual usa colores fijos.

Taxonomía DEC-003

La estructura de módulos del sidebar: Inicio · Ventas · Compras · Inventario · Reportes · Finanzas · Configuración. Decisión de producto ya cerrada (ver entorno).

EmpresaSwitcher

Selector multi-tenant del TopBar. Opera escribiendo localStorage['admin_active_workspace']; el interceptor axios la lee y la manda como header X-Admin-Workspace.

Route group (app)

Patrón del App Router de Next 14 para agrupar rutas protegidas bajo un layout común (donde vive el shell + AuthGuard) sin afectar la URL.

Acordeón / NavGroup

Grupo de menú expandible con chevron; el grupo activo se abre según la ruta. Sus hijos (NavItem) son las subsecciones. El gateo por permisos se cabletea después (JOR-008).

Restricciones y dependencias del entorno

✗ No tocar la auth (RULE-global-003) — AuthGuard, MsalProviderWrapper y el interceptor de api.ts son lógica entregada. El EmpresaSwitcher se apoya en el header X-Admin-Workspace existente (escribe la key de localStorage); no se reescribe el interceptor.
✓ DEC-003 cerrada — la taxonomía del sidebar es decisión de producto y ya está resuelta (Inventario · Pagos clientes en Finanzas · Ventas=Documentos·Crear factura·Notas de crédito). El shell la cabletea tal cual; no hay que re-decidirla.
⚠ RBAC se cabletea aparte — la visibilidad por permisos de cada ítem/grupo del nav (<Can>/useCan) la termina JOR-008. Aquí se construye el shell y se dejan los puntos de extensión, no el gateo real.
ℹ Deuda conocida — colisión del token muted (gris de texto legacy vs fill claro shadcn) anotada en tailwind.config.js; se resuelve consumiendo tokens HSL en los componentes nuevos.

Invariante del caso

El shell refleja lo que las maquetas entregan — no inventa navegación.
Corolario: toda ruta/label del sidebar traza a la taxonomía DEC-003 (derivada del prototipo + auditoría de maquetas). Las vistas sin maqueta existen como ruta placeholder, no como UI inventada.

Q&A de estudio — fija las bases

¿Por qué el EmpresaSwitcher no necesita modificar api.ts?
Porque el interceptor de request ya lee localStorage['admin_active_workspace'] y la inyecta como header X-Admin-Workspace en cada llamada. El switcher solo escribe esa key; el interceptor la recoge en el próximo request. Tocar el interceptor violaría RULE-global-003.
¿Por qué los 4 links del sidebar actual están en 404?
Porque src/app/ solo define /, /dashboard y los route handlers de API. /users /workspaces /settings /admin existen únicamente como strings en Sidebar.tsx, sin archivo de página que los respalde. El shell nuevo los reemplaza por rutas reales o un not-found.tsx amigable.
Si una vista no tiene maqueta, ¿qué se construye en el shell?
Solo la ruta con un estado placeholder "próximamente". El invariante manda: el shell refleja las maquetas, no inventa UI. Las vistas con maqueta (01–06, 08–10) sí tienen pantalla real; el resto es navegación que aterriza en un placeholder.
¿Por qué "Inventario" y no "Items" para el catálogo?
DEC-003 lo cerró: el prototipo consolidado y el doc lo rotulan "Inventario" (con "Items" como sub-ítem de listado). En el legacy "Inventario" era otra cosa (conteos de stock bajo Bodega), pero la maqueta entregable manda sobre el legacy. Es una decisión de producto confirmada con la evidencia a la vista.
