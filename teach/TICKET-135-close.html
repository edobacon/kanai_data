Teach close · Seed de requisitos EST200 reproducible por el editor

TICKET-135UPONE-1541refactorcurriculum-design · cerrado 2026-08-26

En una frase: el arbol de requisitos de ejemplo que el sistema sembraba tenia una forma que el editor visual no podia crear desde cero; este refactor lo reescribio a la forma canonica del alta, sin tocar esquema ni motor de evaluacion, de modo que el ejemplo sembrado sea uno que el usuario podria haber creado el mismo.

El problema

El seed _data-requirement.js (arbol "EST200") tenia una raiz Group[AND] con un Group[OR] anidado y dos condiciones globales colgando de la raiz. El alta del editor (UPONE-1378), en cambio, siempre crea el Group[OR] contenedor en la raiz y cuelga todo bajo una via: no hay camino para poner un Group por encima ni para crear condiciones globales. Resultado: el disenador veia un ejemplo no reproducible, una promesa incumplida del sistema. Ademas un bloque electivo se sembraba sobre un Plan con campos que ninguna pantalla captura (ProgressGate, creditsRequired).

Por que importa (las 2 ideas clave)

1. Distribuir bajo un OR = duplicar lo comun. Al aplanar de (A ∨ B) ∧ C a (A ∧ C) ∨ (B ∧ C), las condiciones globales C (creditos, advisory) hay que duplicarlas en cada via: una condicion que vive en una sola rama de un OR deja de exigirse cuando se cumple la otra. Es una equivalencia logica (distribucion), no una decision de estilo.
2. El guard de idempotencia depende de la determinacion del owner. La raiz aplanada pasa a tener un label generico y compartible ("Cualquiera de las vias"), asi que un guard por-label global haria falso match o replantaria. La solucion: guard por owner, resolviendo la Activity ancla (determinista por code) ANTES del guard. Esto actualizo RULE-curriculum-design-022 de "guard global por label" a "guard coherente con la determinacion del owner".

Gotchas para el proximo

  • El mock de seed-counts.test.ts resuelve findFirst a un id NUEVO por llamada. Para probar re-seed idempotente hay que estabilizar el id de la ancla, o el guard por owner nunca hace match y da un falso "duplica" (artefacto del mock, no bug).
  • Un re-seed sobre una DB con el arbol viejo NO lo convierte: el guard por owner ve la raiz existente y hace skip. Para ver la forma nueva hace falta un reseed limpio (setup:reset dropea+recrea), no un sync incremental.
  • El pool electivo se anclo por code a cursos C-* reales (Active); el findMany(Course) take:6 orderBy id anterior caia en las Activities de menor id (las demo en Draft), inconsistente con el principio "casos reales y alcanzables".
