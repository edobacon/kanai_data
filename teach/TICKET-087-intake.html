Malla — Pestaña "Líneas de formación" (MC-07)

Las líneas de formación (requirementCategory) son los "buckets" de crédito que organizan una malla: Núcleo, Electivos de Profundización, Proyecto de Grado, etc. Cada una declara un rango de créditos [minCredits, maxCredits] y agrupa asignaturas del plan (planEntry.categoryId). MC-07 pide una pestaña en el detalle del Curriculum para gestionarlas (ver, crear, editar, borrar) y alimentar con ellas el selector de la malla (MC-06) y los chips de color (MC-08). Este documento orienta en tres direcciones: las bases del dominio, el entorno (qué ya existe) y el plan de sesiones.

TL;DR — El grounding del código reveló que ~70% de MC-07 ya está construido en la rama UPONE-1267-sp5 (por MC-02 / TICKET-093 / TICKET-094): el objeto, el guard de borrado, la pestaña con un record-list, los layouts CRUD y los pickers de color/ícono. MC-07 se reduce a un delta de gaps: (1) agregar columnas obligatorias/electivas, (2) habilitar el borrado en la UI, (3) mapear "etiqueta corta" a code, (4) verificar la integración con el selector. 2 sesiones, no 4.

Glosario del dominio

requirementCategory (línea)

La "línea de formación". Campos: curriculumId (FK), name, code (código corto), minCredits (req), maxCredits (opcional, sin tope si null), position, description, color, icon. No tiene shortLabel.

planEntry.categoryId

La asignatura colocada apunta a su línea por categoryId (FK nullable a requirementCategory). Declara onDelete: Restrict: la DB bloquea borrar una línea con entries (backstop del guard).

currentCredits (derivado)

NO se persiste. El backend lo enriquece al leer (REQ-10): sumCurrentCredits = suma de effectiveCredits de los entries de la línea. Es la columna "créditos actuales" del record-list.

obligatoria vs electiva

Derivado de blockId: entry con blockId==null → obligatoria; con blockId!=null → electiva (pertenece a un bloque). Helpers puros ya existentes: partitionByElectivity / electivesByCategory.

record-list (config nativo)

La pestaña NO es un componente Vue custom: es un campo "type":"record-list" declarado en el schema del layout default_Curriculum_view.json. Sus columnas, filtros (curriculumId == {{parentId}}) y flags canCreate/canEdit/canDelete son config.

guard de borrado (REQ-09)

requirementCategoryDelete.resolver.js intercepta deleteInstance y corre assertNoEntriesForCategory: si hay entries lanza REQUIREMENT_CATEGORY_HAS_ENTRIES ("reasigna primero"). Ya existe.

Cómo funciona hoy (lo que MC-02/093/094 ya dejaron)

La pestaña "Líneas de formación" ya renderiza. El usuario ve una tabla de líneas, puede crear y editar con un form modal que trae pickers de color e ícono. Lo que falta es marginal (columnas de conteo, borrado desde UI, verificación de integración).

Preguntas abiertas a explorar

No son conclusiones — son las incógnitas que el dev debe tener presentes y validar durante la ejecución.

¿"Etiqueta corta" del mockup se resuelve con code o hace falta un campo nuevo?
El objeto requirementCategory ya modela code ("código corto opcional"), y el ticket declara creates_data:false. Agregar un shortLabel contradice ese flag y toca codegen/migración. Decisión de intake: "etiqueta corta" = code. Se confirma con el dev en el design; si el mockup exige un texto distinto de code, escala a un cambio de modelo (fuera del scope FE).
¿La validación minCredits ≤ maxCredits debe existir en el FE o basta el server-side?
El BE ya la aplica (assertMinMaxCredits en create y update). El form estándar (RecordDetail) puede o no soportar una regla de validación cross-field declarativa. Se evalúa en S2: si el layout soporta una rules de Vueform, se agrega; si no, se documenta que el error se surfacea al submit (server-side) como comportamiento aceptable.
¿Una línea recién creada aparece de inmediato en el selector de MC-06, o hay cache stale?
El selector de MC-06 lee requirementCategory vía useCurriculumMesh (query Apollo). Si el cache de Apollo no se invalida al crear una línea desde otra pestaña, el selector podría no reflejarla hasta un refetch. TC-05 verifica el caso; si hay stale, se resuelve con refetchQueries/policy o recarga del composable.
¿Agregar mandatoryCount/electiveCount al enrichment rompe algún consumidor?
Es aditivo (campos nuevos en item.data), y reusa el mismo planEntry.findMany que ya calcula currentCredits. Riesgo bajo. Se valida que currentCredits siga correcto (no regresión) y que el enrichment de getInstance (item único) también los exponga si aplica.
